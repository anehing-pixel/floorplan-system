## 1. Context（背景）

### 1.1 业务诉求

经销商、主机厂、银行、盘点 App 等外部方需要向本融资平台回传信息
（已售推送、已开票/已出库/已登记、银行回款、盘点结果、登记回执）。

但**核心业务接口不能裸露在公网上**。安全边界必须由：

> **专线/VPN + API 网关 + DMZ 前置服务 + 签名鉴权 + 审计日志** 五层构成。

### 1.2 现状核查（2026-10-26，代码实测）

| 核查项 | 结果 | 证据 |
|---|---|---|
| **外部集成文档设计的 `external-api` 独立入口** | ❌ **从未实现** | 全库 `grep -rn "external" --include=*.java web/` → **0 处** |
| **独立外部鉴权机制** | 🟡 **只有一个点** | `PaymentWebhookVerifier`（银行回调 HMAC-SHA256 + ±300s 防重放） |
| **API 网关** | ❌ 无 | `grep -riE "gateway\|网关"` → 无基础设施痕迹 |
| **DMZ 前置服务** | ❌ 无 | 同上 |
| **专线 / VPN** | ❌ 无 | 同上 |
| **限流** | ❌ 无 | `grep -riE "ratelimit\|限流"` → 0 |
| **IP 白名单** | ❌ 无 | `grep -riE "ip.*whitelist\|白名单"` → 0 |
| **CORS** | ⚠️ **全通配** | `WebMvcConfig.addCorsMappings`：`allowedOriginPatterns("*")` + `allowedHeaders("*")` |
| **请求日志** | ✅ 有 | `RequestLoggingFilter`（脱敏 + traceId + 响应头回传） |
| **业务审计** | ✅ 有 | `audit_events` 表（14 个 Controller / 30 处已改造） |
| **外部调用记录** | ❌ 无 | 外部集成文档 §2.3 要求的 `integration_calls` 表不存在 |

### 1.3 风险敞口

**当前若把 `/api/**` 直接暴露公网，等于同时暴露：**

| 端点 | 暴露后果 |
|---|---|
| `POST /api/advances` | **虚构放款申请** → 占额度、生成真实垫款指令 |
| `POST /api/advances/{no}/disburse` | **无签名也能触发支付提交**（JWT 内部用户可调） |
| `POST /api/advances/{no}/confirm` | 有 HMAC 保护 ✅ ——但**若共用一个全局密钥**，任一方泄露即全盘失守 |
| `POST /api/repayments` | **伪造还款核销** → 额度回补（真实资金损失） |
| `PUT /api/dealers/{id}/risk-grade` | 篡改评级 → 影响利率与风控 |
| `POST /api/disposals/*` | 伪造处置记录 → 污染证据链与清算 |
| `POST /api/purchase-orders/import` | 注入虚假采购数据 → 污染台账与审计 |
| `GET /api/**`（读） | **全量数据泄露**：客户名、VIN、金额、担保登记号、风险等级 |

**读接口的泄露常被低估**。外部集成文档 §2.1 已写明"外部接口暴露字段最小化（不暴露内部 ID、风险等级等敏感字段）"，
但这条约束**目前没有任何代码强制**——因为外部入口还不存在。

### 1.4 为什么"只加签名"不够

一个常见的误解是：给外部接口加个 API Key / HMAC 签名就安全了。

**不够**，因为签名只解决"**请求是不是他发的**"，不解决：

| 威胁 | 签名能否防御 |
|---|---|
| 伪造请求 | ✅ 能 |
| **重放** | ⚠️ 需时间戳 + nonce（现有银行回调只做了时间窗，**无 nonce 去重表**） |
| **暴力尝试 / 撞库** | ❌ 不能（无限流就是无限试） |
| **内部接口被扫描发现** | ❌ 不能（同一端口同一路径空间） |
| **单点密钥泄露 → 全盘失守** | ❌ 不能（需密钥分级与轮换） |
| **无法证明"谁在什么时候调了什么"** | ❌ 不能（需独立审计） |
| **大流量打垮核心库** | ❌ 不能（需限流与熔断） |

**结论**：签名是**纵深防御中的一层**，不是全部。

## 2. Decision（决策）

### 2.1 核心决策

> **采用五层纵深防御。核心业务接口与外部接入在网络层、部署层、认证层完全隔离。**

```
        ╔═══════════════════════════════════════════════════════════════╗
        ║  外部方（经销商DMS / 主机厂 / 银行 / 盘点App / 法务省代办）      ║
        ╚═══════════════════════╤═══════════════════════════════════════╝
                            │
        ┌───────────────────▼───────────────────┐
        │ ① 传输层：专线 / VPN / mTLS          │  ← 未经此层根本到不了下一层
        │   （IPsec 隧道 / SSL VPN / 专线电路）  │
        └───────────────────┬───────────────────┘
                            │
        ┌───────────────────▼───────────────────┐
        │ ② DMZ 前置服务（external-api）        │  ← 外部可达的唯一服务
        │   · 只做：验签 → 限流 → 协议转换 → 入队  │
        │   · 绝不做：业务逻辑 → 直接写核心库     │
        │   · 绝不持有核心库连接                 │
        └───────────────────┬───────────────────┘
                            │
        ┌───────────────────▼───────────────────┐
        │ ③ API 网关                             │  ← 统一入口策略执行点
        │   · 路由 · 配额 · 熔断 · 黑白名单      │
        │   · 报文改写（WAF 规则）                │
        └───────────────────┬───────────────────┘
                            │
        ═════════════════════▼══════════════════════════════════
        ║  核心区（Core Zone）—— **不暴露公网**                ║
        ║  ┌────────────┐   ┌────────────┐   ┌────────────┐  ║
        ║  │ web 内部入口 │   │ application │   │ domain     │  ║
        ║  │ (SSO+RBAC) │──▶│ (用例编排)  │──▶│ (领域模型)  │  ║
        ║  └────────────┘   └────────────┘   └────────────┘  ║
        ║        ↑ ④ 签名鉴权（请求级）                          ║
        ╚══════════════════════════════════════════════════════════
                            │
        ┌───────────────────▼───────────────────┐
        │ ⑤ 审计日志（三路留痕）                 │
        │   接入层日志 · 业务审计 · 集成调用记录 │
        └───────────────────────────────────────┘
```

### 2.2 五层的职责边界（**关键：每层只做一件事，不越界**）

| 层 | 职责 | **明确不做** | 失败时 |
|---|---|---|---|
| **① 传输层**（专线/VPN/mTLS） | 网络可达性控制：只有授权 IP 段能到 DMZ | 不做认证、不做限流 | 连接直接不通 |
| **② DMZ 前置服务** | 验签 → 限流 → 协议转换 → **入队即返回 202** | **不碰核心库、不跑业务逻辑** | 消息进重试队列，不丢 |
| **③ API 网关** | 路由 / 配额 / 熔断 / 黑白名单 / 报文改写 | 不理解业务语义 | 快速拒绝，保护后端 |
| **④ 签名鉴权** | 请求级身份：签名 + 时间戳 + nonce + 密钥版本 | 不做业务权限（那是内部 RBAC 的事） | 401/403 + 记审计 |
| **⑤ 审计日志** | 三路留痕：接入层 / 业务 / 集成调用 | 不参与决策 | **不得因审计故障阻塞业务**（异步落盘） |

> **为什么 DMZ 服务"绝不做业务逻辑"**：
> DMZ 是暴露面最大的部分。一旦它连着核心库且跑着业务逻辑，
> 任何一次 DMZ 入侵都等于核心库沦陷。
> **DMZ 的正确职责是"验真 + 缓冲"，不是"加工"**——
> 消息进核心区的队列后才由内部消费者处理，DMZ 全程不持有核心库连接。

### 2.3 网络分区与地址规划

| 区 | 可访问性 | 承载组件 | 出网策略 |
|---|---|---|---|
| **外部区（External）** | 公网可达 | 外部方系统 | — |
| **DMZ 区** | **仅接受 ① 传输层放行的流量** | `external-api` 服务 | **禁止直连核心库**；只允许连 ③ 网关 + MQ |
| **核心区（Core）** | **完全不可从外部直达** | `web`（内部入口）/ application / domain / PostgreSQL | 只接受 DMZ 经网关进来的流量 |
| **运维区** | 堡垒机跳板 | 运维人员 | 不允许直连核心区应用，仅跳板 |

**数据库**：核心区 PostgreSQL **只监听内网地址**，不绑定 `0.0.0.0` 的公网网卡。
应用连接串走 `localhost`/内网 IP，**不使用数据库公网入口**。

**防火墙矩阵（示意）**：

| 来源 → 目标 | DMZ | 核心应用 | 核心库 | MQ | 运维区 |
|---|---|---|---|---|---|
| 外部方 | ✅（仅白名单 IP） | ❌ | ❌ | ❌ | ❌ |
| DMZ | — | ✅（经网关） | ❌ | ✅ | ❌ |
| 核心应用 | ✅（仅健康检查） | ✅ | ✅ | ✅ | ❌ |
| 运维区 | ❌ | ❌（跳板） | ❌ | ❌ | ✅ |

### 2.4 接入入口的代码分层

**决策：新建独立的 `external-api` Spring Profile / 独立模块，不复用内部 `web` 的 Controller。**

理由：

| 方案 | 问题 |
|---|---|
| 在现有 `web` 里加 `/api/external/**` | ❌ 同一个端口、同一个应用、同一套拦截器——**"网络隔离"根本不存在**。攻击者仍可扫描 `/api/dealers` |
| 独立 `external-api` 应用/模块 | ✅ 独立进程、独立端口、独立鉴权、可单独扩容与熔断 |

**外部接口的三条硬约束**（写进代码规范）：

1. **不暴露内部 ID**：外部用 `account_ref` / `order_no` / `vin` 等业务键，内部主键不外露
2. **不暴露敏感字段**：风险等级、授信额度、利率、内部备注一律不出现在 DTO 里
3. **不复用内部 DTO**：外部 DTO 独立定义（防腐层，外部集成文档 §2.2）

### 2.5 签名鉴权体系

#### 2.5.1 现有的 HMAC 可以复用，但要分级

现有 `PaymentWebhookVerifier` 的机制是对的（HMAC-SHA256 + ±300s 时间窗 + 审计操作人固定非自然人）。
但**当前所有渠道共用一个全局密钥**（`floorplan.payment.webhook-secret`）——
任一方泄露即全盘失守。

**改为按外部方分密钥 + 支持轮换**：

```sql
CREATE TABLE integration_partners (
    id            BIGSERIAL PRIMARY KEY,
    partner_code  VARCHAR(32) UNIQUE NOT NULL,   -- DMS / OEM / BANK / AUDIT_APP / LEGAL
    partner_name  VARCHAR(128) NOT NULL,
    partner_type  VARCHAR(24) NOT NULL,           -- DEALER 经销商 / OEM 主机厂 / BANK 银行 / INTERNAL 内部
    -- 密钥分级：不同外部方用不同密钥，且不同环境不同密钥
    secret_ref    VARCHAR(128),                   -- 密钥引用（**不存明文密钥**，指向密钥管理系统）
    key_version   INTEGER NOT NULL DEFAULT 1,     -- 密钥版本，支持轮换
    allowed_ips   VARCHAR(512),                  -- IP 白名单（逗号分隔；专线/VPN 场景可留空）
    allowed_scopes VARCHAR(512),                  -- 允许的能力范围（逗号分隔的 scope）
    rate_limit_per_minute INTEGER NOT NULL DEFAULT 60,
    status        VARCHAR(16) NOT NULL DEFAULT 'ACTIVE',
    activated_at  TIMESTAMPTZ,
    expires_at    DATE,                            -- 合作到期
    created_by    VARCHAR(64),
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

#### 2.5.2 签名规范（统一）

```
签名原文 = METHOD + "\n" + PATH + "\n" + timestamp + "\n" + nonce + "\n" + SHA256(body)
签名值   = Hex(HmacSHA256(secret, 签名原文))

请求头：
  X-Partner-Code:  DMS_001
  X-Signature:     <hex>
  X-Timestamp:     <Unix 秒>
  X-Nonce:         <随机串，≥16 字符>
  X-Key-Version:   1
```

**比现有银行回调强了三点**：

| 增强 | 作用 |
|---|---|
| **METHOD + PATH 参与签名** | 防止把「查询 X 的签名」重放到「查询 Y」的路径上 |
| **body 摘要参与签名** | 防止参数篡改（现有实现只签 `advanceNo + timestamp + ref`，body 其他字段未覆盖） |
| **nonce + 去重表** | 真正防重放（现有仅靠 ±300s 时间窗，窗口内的重放仍可成功） |

```sql
CREATE TABLE integration_nonces (
    partner_code VARCHAR(32) NOT NULL,
    nonce        VARCHAR(64) NOT NULL,
    used_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (partner_code, nonce)
);
```

**nonce 保留期 = 时间窗 × 2**（如窗口 300s → 保留 600s），过期后可清理。
**用主键去重，重复 nonce 直接 401 + 记审计**。

#### 2.5.3 密钥轮换

```
密钥版本 N 生效
  → 宽限期（建议 7 天）：版本 N 与 N-1 双双有效
  → 宽限期结束：版本 N-1 失效
  → 版本 N-1 的历史请求仍可被审计还原（密钥归档，不删除）
```

**实现**：`X-Key-Version` 头 + `integration_partners.key_version`。
网关按版本选密钥，**不接受高于当前版本的请求**（防止降级攻击）。

### 2.6 限流与配额

| 维度 | 阈值（建议） | 超限行为 |
|---|---|---|
| 单 partner 每分钟请求数 | `rate_limit_per_minute`（默认 60，可按 partner 配） | 429 + `Retry-After` |
| 单 partner 并发 | 20 | 排队 / 429 |
| 单 IP 每分钟 | 120 | 429（防单机多 partner 账号打穿） |
| 单次请求体大小 | 1 MB（批量导入单独放开到 20 MB） | 413 |
| 单 partner 每日事件数 | 可配 | 429 + 告警 |

**限流必须在网关做（第一层快速拒绝），不要打到应用层**——
应用层限流时，请求已经消耗了连接、TLS 握手、Tomcat 线程。

**熔断**：某 partner 连续失败率 > 50% 且请求数 > 100 → 熔断 60s，
期间快速失败（503）而不是继续打后端。**熔断要按 partner 维度**，不能全局。

### 2.7 审计日志（三路留痕）

| 路 | 内容 | 载体 | 保留期 |
|---|---|---|---|
| **① 接入层日志** | 每次外部请求：partner、时间、路径、结果码、耗时、traceId、IP、**签名是否通过** | `integration_calls`（新建）+ 应用日志 | ≥ 7 年（金融合规） |
| **② 业务审计** | 请求引发的业务动作（写库、改状态） | `audit_events`（**已有**） | ≥ 7 年 |
| **③ 集成调用记录** | 我方向外发起的调用：请求/响应/耗时/结果 | `integration_calls` 的 outbound 部分 | ≥ 3 年 |

```sql
CREATE TABLE integration_calls (
    id            BIGSERIAL PRIMARY KEY,
    call_no       VARCHAR(32) UNIQUE NOT NULL,
    direction     VARCHAR(8)   NOT NULL,     -- INBOUND 外部调我 / OUTBOUND 我调外部
    partner_code  VARCHAR(32)  NOT NULL,
    http_method   VARCHAR(8),
    path          VARCHAR(256),
    query_summary TEXT,                      -- 脱敏后的查询参数摘要
    request_digest VARCHAR(64),              -- 请求体摘要（不存原文，含敏感数据）
    response_code VARCHAR(8),
    response_digest VARCHAR(64),
    duration_ms   INTEGER,
    signature_ok  BOOLEAN,
    client_ip     VARCHAR(64),
    trace_id      VARCHAR(64),
    error_summary TEXT,
    occurred_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS idx_ic_partner ON integration_calls (partner_code, occurred_at DESC);
CREATE INDEX IF NOT EXISTS idx_ic_trace ON integration_calls (trace_id);
```

**关键约束**：
- **审计写失败不得阻塞业务**（异步落盘 + 本地缓冲）
- **`request_digest` 只存摘要不存原文**——请求体可能含账号等敏感数据（沿用 ADR-007 的敏感数据原则）
- **`signature_ok=false` 的调用必须留痕**——这是攻击检测的关键信号

### 2.8 内部入口的独立性与 CORS 收紧

**决策：内部 `web` 入口与外部 `external-api` 是两个进程、两个端口、两套鉴权。**

| 项 | 内部入口 | 外部入口 |
|---|---|---|
| 网络位置 | 核心区 | DMZ |
| 鉴权 | JWT + RBAC（`@RequirePermission`） | 签名 + partner + scope |
| 审计操作人 | 自然人（令牌身份） | 非自然人（`partner_code`） |
| 可见数据 | 全量（按权限） | 字段最小化 |
| CORS | 收紧到具体域名 | 不适用（服务端调用，无浏览器） |

**当前 `allowedOriginPatterns("*")` 必须收紧**：

```java
// 开发期：可配置放开（application.yml 里配 allowed-origins）
// 生产：必须配具体域名，禁止 "*"
registry.addMapping("/api/**")
    .allowedOriginPatterns(allowedOrigins.split(","))   // 默认只含同源
    .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")
    .allowedHeaders("Authorization", "Content-Type", "X-Trace-Id")
    .allowCredentials(false);
```

> **当前配置的风险**：`allowedOriginPatterns("*")` + `allowedHeaders("*")`。
> 虽然用的是 Bearer 头而非 Cookie（跨域不带凭证），风险小于 Cookie 场景，
> 但**仍然允许任意站点发探测请求**。生产必须收紧。

### 2.9 事件收件的可靠性（DMZ 服务的核心职责）

外部推送（已售、盘点结果、银行回款）**不能因为一次网络抖动就丢**。

```
外部方 → 网关 → DMZ 服务
   ① 验签（失败 → 401 + 记审计 + 告警）
   ② 限流（超限 → 429）
   ③ 幂等键检查（biz_key）
   ④ **落 inbox 表（先落库再返回）**
   ⑤ 返回 202 Accepted + 受理号
        ↓
   内部消费者异步处理（幂等、可重放）
        ↓
   业务动作 → domain_events → risk_alerts / work_orders
```

**为什么"先落库再返回 202"**：外部方看到 200 就认为"送达"了。
若我们先处理再返回、处理中崩溃，则外部方不知道要不要重试——
**要么丢数据，要么重复处理**。先落库 + 幂等键是唯一可靠解。

**这与 ADR-008 的 `domain_events` 是同一张表**——
外部推送的事件最终也落在 `domain_events`，保持单一事件总线。

### 2.10 失败模式与降级

| 故障 | 检测 | 降级行为 | 业务影响 |
|---|---|---|---|
| 外部方系统挂了 | 熔断器 | 快速 503 | 该 partner 数据延迟，其余不受影响 |
| DMZ 服务挂了 | 健康检查 + 拉起 | 重启；积压消息在 MQ | 数据延迟，**不丢** |
| 核心库不可达 | 连接池 + 熔断 | DMZ 继续收单落 inbox（**inbox 也在核心库，所以实际会一起失败**） | 见下 |
| 网关配置错 | 5xx 率异常 | 回滚配置 | 部分 partner 受影响 |
| 签名密钥泄露 | 异常调用模式 | 轮换密钥 + 拉黑名单 + 通知对方 | 需对方同步换密钥 |
| 审计写失败 | 缓冲积压 | 异步补写；超限则降级为"只记应用日志" | 审计完整性受损，**需告警** |

> **⚠️ 一个必须承认的架构约束**：
> 若 inbox 表与核心库同库，则**核心库不可用时 DMZ 也无法收单**——
> 此时外部方的推送会失败。
> 两种解法：
> ① **接受**（回款/盘点数据延迟可接受，外部方会重试）——**推荐起步方案**
> ② **inbox 独立部署**（独立库或消息队列），代价是运维复杂度上升
>
> 建议**起步用 ①**，但要求外部方**必须实现重试**——这要写进对接文档。

## 3. Consequences（后果）

### 3.1 变得更容易的

| 好处 | 说明 |
|---|---|
| **核心库与核心应用不再暴露公网** | 最大的一类风险直接消除 |
| **外部方接入标准化** | 一套签名规范 + 一套 DTO，所有 partner 复用 |
| **攻击可观测** | `integration_calls` 记录每次外部调用与签名校验结果 |
| **密钥泄露影响面可控** | 按 partner 分密钥 + 版本轮换，单点泄露不全局失守 |
| **重放与篡改被防御** | METHOD+PATH+body 参与签名 + nonce 去重表 |
| **核心库不被外部流量冲击** | 限流/熔断在网关层完成 |

### 3.2 变得 harder 的（代价必须说清）

| 代价 | 说明 | 缓解 |
|---|---|---|
| **部署拓扑复杂化** | 从「一个 jar」变成「DMZ + 核心 + 运维」三区 | 起步可用同一台机器不同容器，但**网络策略必须先落** |
| **外部接入速度变慢** | 每个外部方要走专线/VPN 申请、密钥分发、联调 | 提前启动外部集成文档 §6 的调研清单 |
| **密钥管理成为运维负担** | 分 partner、版本、轮换、归档 | 用密钥管理系统（KMS/Vault），代码只存 `secret_ref` |
| **双写/双套鉴权** | 内部 JWT + 外部签名，两套拦截器 | 外部入口独立应用，代码物理隔离，不会互相污染 |
| **inbox 与核心库同库的约束** | 核心库挂时外部也收不了 | 起步接受，靠外部方重试兜底 |
| **联调环境需要** | 外部方要有测试环境与密钥 | 提供沙箱 partner（密钥固定、可重放事件） |

### 3.3 明确不做

| 项 | 原因 |
|---|---|
| **把内部 `/api/**` 直接暴露公网** | 违反既有架构（外部集成文档 §2.1 双入口分离） |
| **在内部 `web` 里加 `/api/external/**` 路径** | 同一进程同一端口，网络隔离形同虚设 |
| **用 IP 白名单替代签名** | IP 可伪造（尤其对方在同一 NAT 后），白名单只是纵深一层 |
| **只做签名不做限流** | 无限流 = 无限尝试，密钥被撞出来只是时间问题 |
| **审计写失败阻塞业务** | 可用性优先；审计补写 + 告警 |
| **在日志里打印请求体原文** | 可能含账号等敏感数据（ADR-007 原则） |
| **用同一个密钥给所有 partner** | 单点泄露即全盘失守 |
| **DMZ 服务直连核心库跑业务** | DMZ 是最大暴露面，一旦沦陷核心库跟着沦陷 |
| **自动拉黑 partner 而不通知** | 联调期的误封会让对方业务停摆，要人工介入 |

### 3.4 与既有约束的关系

| 既有约束 | 关系 |
|---|---|
| 外部集成文档 §2.1 双入口分离 | ✅ **本 ADR 是它的落地**——从"设计约束"变成"部署与代码规范" |
| 外部集成文档 §2.2 防腐层强制 | ✅ 保留，但明确外部 DTO 独立定义、不复用内部 DTO |
| 外部集成文档 §2.3 Outbound 韧性 + 人工重触发 | ✅ 保留，熔断与重试在此基础上 |
| 外部集成文档 §2.4 对账是兜底 | ✅ 保留 |
| 外部集成文档 §2.5 人工路径一等公民 | ✅ 保留——**人工上传的外部数据与 API 推送走同一 inbox** |
| ADR-006 银行回调 HMAC | ⚠️ **升级**：签名原文纳入 METHOD/PATH/body，新增 nonce 与密钥版本 |
| ADR-007 敏感数据原则 | ✅ 沿用——审计只存摘要不存原文 |
| ADR-008 `domain_events` 事件总线 | ✅ **复用**——外部推送事件最终落同一张表 |

## 4. 迁移路径（分阶段，不阻塞现有链路）

```
阶段零（立即可做，零风险）
  ① 收紧 CORS：allowedOriginPatterns 从 "*" 改为配置项，默认同源
  ② 密钥分级：把全局 webhook-secret 改为按 partner 分（先只拆银行一家）
  ③ 审计补强：integration_calls 表建好，外部调用（含银行回调）落表
  ④ 补 nonce 去重表 + 签名纳入 METHOD/PATH/body（向后兼容：接受旧签名一段时间）

阶段一（网络层，2~4 周）
  ⑤ 网络分区：核心区 / DMZ / 运维区 划定，防火墙矩阵落地
  ⑥ 数据库只听内网，应用连接串改内网地址
  ⑦ 专线/VPN 申请（按外部集成文档 §6 调研清单确定的 partner 优先级）

阶段二（外部入口，4~8 周）
  ⑧ 独立 external-api 应用（Spring Profile 或独立模块）
  ⑨ 网关：路由 / 配额 / 熔断 / 黑白名单
  ⑩ DMZ 服务：验签 → 限流 → inbox 落库 → 202
  ⑪ 沙箱 partner + 对接文档（签名规范 + 重试要求 + 字段最小化清单）

阶段三（接入扩展，与业务对接并行）
  ⑫ 按 partner 逐个接入：DMS 售出推送 → 盘点结果 → 银行回款 → 登记回执
  ⑬ 每个 partner 接入时同步确认其**实现了重试**（否则数据会丢）
```

**每阶段的验收标准**：

| 阶段 | 验收 |
|---|---|
| 零 | 从公网访问 `/api/dealers` → 403/连接不通（视网络策略）；CORS 检查工具无通配 |
| 一 | 从外网扫描核心区端口 → 全闭；核心库端口从 DMZ 连不上 |
| 二 | 未签名请求 → 401 且 `integration_calls` 有记录；超限 → 429；重复 nonce → 401 |
| 三 | 断网重连后事件不丢不重（inbox 重放验证） |

## 5. 待确认事项

| # | 待确认 | 建议默认 | 影响 |
|---|---|---|---|
| 1 | **外部方数量与接入优先级** | 银行（已有）→ 经销商 DMS → 盘点 App → 主机厂 → 法务省 | 专线申请顺序 |
| 2 | **专线 vs VPN vs 公网+mTLS** | 银行/主机厂走专线；经销商用 VPN（数量多、分散） | 成本与运维 |
| 3 | **API 网关选型** | Kong / APISIX / 云厂商网关 | 是否引入新组件 |
| 4 | **密钥管理** | 云 KMS 或 Vault | `secret_ref` 指向什么 |
| 5 | **签名算法** | HMAC-SHA256（沿用银行回调）vs 非对称（RSA/Ed25519） | 对接方实现成本 |
| 6 | **是否要求双向 TLS** | 建议是（配合专线） | 客户端证书管理 |
| 7 | **限流阈值** | 60 次/分/partner | 需按实际流量校准 |
| 8 | **审计保留期** | 接入层 7 年 / 业务 7 年 / 调用记录 3 年 | 合规要求 |
| 9 | **nonce 保留期** | 时间窗 × 2（600s） | 存储与清理 |
| 10 | **外部方是否必须实现重试** | **必须**（否则 inbox 与核心库同库时会丢数据） | 需写进对接文档 |
| 11 | **是否有沙箱环境给外部方联调** | 建议有（固定密钥 + 可重放事件） | 联调效率 |
| 12 | **DMZ inbox 是否独立部署** | 起步不独立（接受核心库挂时收不了单） | 架构复杂度 |
| 13 | **核心区是否允许运维直连** | 不允许，只能堡垒机跳板 | 运维流程改造 |
| 14 | **第三方监管方是否需要接入** | 本项目无实体监管（实地盘点为主），若需则多一类 partner | 范围 |

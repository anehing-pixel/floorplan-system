### 4.3 SELF_PAY 真实化规格（R4.3）

现状是 `passed=false` 硬编码占位。USED 域实现：

```
SelfPayVerdict = Σ over 已放款且仍在库且已实控(IN_STOCK + 有效质押) 的车辆:
                   FLOOR( 当前 ACTIVE 估值 prudent_value × self-pay-ratio(= 该台命中档 max_ratio × 0.85) )
                 − 已占用额度
判定：申请额 ≤ SelfPayVerdict → passed=true，否则 LTV_001
```

- 独立抵押率 **0.85 折扣**是建议默认 `[待定源 D-01]`（需求书只说"独立抵押率"未给数）。
- 「已实控」= `wms_confirmed_at IS NOT NULL` **且** 証書 `status='PLEDGED'`：两者缺一不计入池。
- 该路径**仍受**放款七闸门约束，只是额度来源不同（用自有资产撑开的补充周转额度）。

```
  5  INSERT outbox_events × N（同事务，JdbcOutboxPublisher 不加 @Transactional）
  6  INSERT audit_events
```

> **顺序约束**：G8 需要行锁，因此放在 G1–G7 之后（D05 §4）。
> 「先占额再判 G7」是禁止的（会造成回滚窗口内的假占用）。

### 5.4 `guarantee-gate` 开关不变

`floorplan.core.guarantee-gate.enabled` **默认 `false` 不动**（AGENTS.md §8）。
USED 域靠 G7 的多源权威 + `CONFLICTED` 阻断达成等效保护，而不是打开那个会影响 LEGACY 全量放款的全局开关。
这是 D02 风险 R-4 的处置结果，必须在评审时明确说明（否则有人会说「把开关打开就解决了」）。

## 8. R8 回款匹配与额度回补

**验收点**：一笔回款匹配成功后额度**真实回补**（`availableAfter > before`）；重复消费不重复回补；解押失败整体回滚且不放额度。

### 8.1 单事务编排九步（需求书 R8.2）

```
RepaymentOrchestrationApplicationService.settle(vin, paymentId, idemKey)   @Transactional
 1 写 repayments（幂等 REP:{vin}:{txn}）
 2 冲抵：费用 → 利息 → 本金（顺序固定，D05 §3.8）
 3 collateral_ledger.repaid
 4 expected_receipts 更新
 5 车辆状态推进（SOLD_UNPAID -> ... -> 达清）
 6 担保实体权利消灭 + 抹消待办生成
 7 证据链写入（audit_events + release_orders 关联）
 8 审计
 9 额度回补（最后）
```

> **第 9 步在同事务内**（需求书要求"单事务编排九步"），而 **D09 §8.1 的 S9⑤ 回补是异步事件驱动**。
> 两者不矛盾：**回款结清**路径（本用例）回补在同事务；
> **放车完成**路径（D09 S9）里台账 `SETTLED` 之后的回补走事件，因为跨了 `release` 与 `credit` 两个上下文。
> 这条区分必须写清，否则实现会出现「两条路径都回补一次」的双重回补。
> 唯一防线是幂等键：`CLR:{vin}:{settle_seq}` 两条路径共用同一 `settle_seq`，第二次不生效。

### 8.2 存根替换（R8.1）

| 现状存根 | 目标实现 | 模块 |
|---|---|---|
| `LoggingLoanLookupClient` | `FeignLoanQueryClient`（复用 W0-5 `LoanQueryContract`） | `bank-service` |
| `LoggingCreditLineClient` | `FeignCreditLineClient`（复用 `CreditLineQueryContract`） | `bank-service` |
| `InMemoryPaymentStore` | `JdbcPaymentStore`（V17 三表） | `infrastructure` |
| 五级匹配只有 VIN(95)+金额(60/45) | 补**订单号 / 时间窗 / 付款人**三规则 + 评分表 | `recon` |

### 8.3 资金监管与交叉验证（R8.4）

| 预警 | 触发 |
|---|---|
| `SOLD_UNPAID` | 有 `sold_at` 且超结算窗口无入金 |
| `PAYMENT_WRONG_ACCOUNT` | 入金账户 ∉ 指定受领账户集合 |
| `PAYMENT_UNMATCHED` | 入金无法匹配到 VIN |
| `MULTI_VIN_SPLIT` | 一笔入金需拆多 VIN，但拆分依据冲突 |
| **钱到车未出** | 入金匹配成功 + 指令仍 `SENT/PENDING_RELEASE` 超 `receipt-sla` |
| **车出钱未到** | `RELEASED` + 敞口未清（**红线，必须告警**） |

### 8.4 幂等与错误码

| 项 | 值 |
|---|---|
| 幂等 | `REP:{vin}:{transaction_id}`、`CLR:{vin}:{settle_seq}`、`ALLOC:{repayment_id}:{vin}` |
| 错误码 | `REPAY_001/002`（沿用）、`CREDIT_001/002/003`、`CONFLICT_001` |
| 配置 | `repayment-alloc-fee-then-interest-then-principal=true` `[待定源 X-1]`、`payment-accounts.whitelist`（非空必填，**禁止空=全通过**） |

> **这个布尔键是未签字口径上的形状缺陷，两条处置都还没被批准，本轮只标不删**（D13 §5.1 A26 / §4.7 WU5-02）：
> ① 它把**冲抵顺序**用一个默认 `true` 的开关预先定成「费→息→本」，而 D12 §7 与需求书 §11.1 至今不一致（X-1），
> 按「不预设，只断言守恒」的现行门禁（D12:377），默认值不应被当成裁决；
> ② 它同时是一个**可配置旁路**——改成 `false` 就翻转顺序，形状与当年被 `relaxedDealers` 绕过的 Q21 同类（AGENTS §8）。
> 处置选项写进 D13 §8 X-1 行，**由业务与风控二选一签字**：要么删键并把顺序写死为裁决结果，要么保留但加 USED 作用域
> 与「翻转须二人 + 留痕」的约束（WU4-18 提的是作用域，不是授权翻转）。
> **签字前本包的验收判据只有两条守恒式**，不许断言每桶数字：
> `receivable_total = principal_due + interest_due + penalty_due + fee_due`、
> `loss_amount = receivable_total − net_proceeds`（列名见 D04 §3.19 `liquidation_statements`）。

## 19. 自检

- R1–R14 **逐条有用例号**，且每条需求书验收要点映射到至少一个 UC；UC 总数 ≈ 60。
- 每个写用例有：事务边界、幂等键、错误码、落库对象；每个门禁有 domain 判定方法名。
- LEGACY 保护：§5.3 `guarantee-gate` 不动、§9 UC-R9-5 不改 LEGACY 营业日、§15 表把「改 LEGACY」全部列为需单独裁决项。
- 两条最容易双重发生的风险显式收口：**双重回补**（§8.1 共用幂等键）与**先占额后判定**（§5.3 顺序约束）。
- §15 承认对工单体系（W2-WORKORDER）的外部依赖并给出降级口径，不把"生成工单"当已具备能力。
- 配置项汇总（§16）里 5 条红线项标注「不可关」，防止被当成可配置旁路（AGENTS.md §8 教训）。
- 未产出代码；`[待定源]` 标记与 D00 §17 清单一致。

## 2. 两条平行线：放车与放证

| 维度 | 放车线 | 放证线 |
|---|---|---|
| 标的 | 实车（占有） | 自動車検査証（担保物的凭证） |
| 物理位置 | 监管仓 / 拍卖场金库 | 凭证保管方 |
| 持有方 | `custodians.custodian_type='WMS'` / `'AUCTION_VAULT'` | `'CERT_DEPOSITORY'` |
| 项类型 | `VEHICLE` | `INSPECTION_CERT` |
| 接收方 | 车商 / 买方 / 拍卖场（按售出类型） | 车商（须已办移転登録） |
| 前置 | 资金闸门 + 担保实体权利消灭 | 资金闸门 + 押印解除 |
| 失败后果 | 敞口仍在，车在我方实控下 | **车商拿不到証 → 无法移転登録 → 无法交付买方**，商业损失比放车失败更大 |
| 权威证据 | 对方入库/出库回执 + 照片 + 里程 | 保管方交还回执 + 証書番号一致性 |
| 对应登记 | 抵当権抹消（第二步，另一条线） | 移転登録（车商侧，我方只取证） |

**三条建模要求**

1. **两条线共用指令与状态机，不共用接收方**：一条 `release_orders` 可含 `VEHICLE` 与 `INSPECTION_CERT` 两个 item，
   分别指向不同 `receiver_code`（§4）。
2. **两条线不得互相替代完成状态**：`VEHICLE` 项 `CONFIRMED` 不代表 `INSPECTION_CERT` 已交还；
   指令级状态由**项集聚合**得出（§5.3 聚合规则）。
3. **钥匙是第三项**（`KEY`）：`[待定源 D-09]` 问「拍卖场场内引取/钥匙封签托管是否为实务必需」。
   本文按「是必需」建模（二手车场内引取必须有钥匙），但**是否要求独立回执**待裁决。

## 3. 目标态：放证线状态机（車検証六态）

见 D03 §3.4 与 D04 §3.9。与放车指令的关系用一张图说清：

```
車検証: RECEIVED ─► PLEDGED ─► RELEASE_PENDING ─► RELEASED
                        │            ▲              │
                        │            │              └─► 移転登録后进入车商持有（我方登记 received_by_dealer，不持有）
                        └─► LOST ─► REISSUED ─► PLEDGED
                        (挂失期间禁止一切放车放证指令)

指令: PENDING_RELEASE ─► SENT ─► ACKNOWLEDGED ─► CONFIRMED/PARTIAL ─► RELEASED ─► LIEN_DISCHARGED
                                └► REJECTED / EXPIRED / CANCELLED
                                    ▲                    ▲
                          証書状态必须先进 RELEASE_PENDING ┘
```

**关键不变式（D03 §3.4）**

| # | 不变式 | 违反时 |
|---|---|---|
| C1 | `certificate_no` 与 `vin` 一一对应，且一车同时只有一張非终态証書 | `CERT_002` / `CERT_001` |
| C2 | 有效质押存在性 = `status ∈ {PLEDGED, RELEASE_PENDING}` | `CERT_005`（禁止放车） |
| C3 | 放证须先 `RELEASE_PENDING`，回执后才 `RELEASED` | 状态机拒绝 |
| C4 | `LOST` 期间禁止生成任何放车/放证指令 | `CERT_005` |
| C5 | 换证成链：`predecessor_id` 指旧证，旧证必 `REISSUED` | `CERT_006` |

## 4. 按项接收方（R7.3，`custodians` 首次被真实使用）

### 4.1 解析器

```
resolveReceiver(item_type, vehicle_unit, release_order) -> ReceiverSpec
  ReceiverSpec { receiver_custodian_code, receiver_partner_code, delivery_channel, instruction_text }
```

解析优先级（D03 §3.6 I2）：

1. 指令项显式指定（`release_order_items.receiver_custodian_code`）——人工创建时可指定；
2. 車検証持有方（`inspection_certificates.holder_custodian_code`）——仅对 `INSPECTION_CERT` 项；
3. 车辆实控仓（`vehicle_units.warehouse_custodian_code`）——仅对 `VEHICLE` 项；
4. **解析失败 = 拒发指令**（`RELS_006`），**不允许**默认发给"某个 custodian"。

### 4.2 一张指令的多接收方形态

| `item_type` | 接收方类型 | `delivery_channel` | 出站目标 | 回执来源 |
|---|---|---|---|---|
| `VEHICLE` | `WMS` | `API` | WMS partner | I-07 `/external/wms/release-receipt` |
| `VEHICLE` | `AUCTION_VAULT`（场内引取） | `API` | 拍卖场 partner | 拍卖场回执端点（同族解析器） |
| `VEHICLE` | `DEALER`（自取） | `MANUAL` | 不下发 | `INTERNAL_WITNESS` + 二人，**永久区别于 partner** |
| `INSPECTION_CERT` | `CERT_DEPOSITORY` | `API` / `PORTAL` | 凭证保管方 | 保管方回执 |
| `KEY` | `WMS` / `DEALER` | 随车项 | 同车项 | 与 `VEHICLE` 合并或独立（D-09） |
| `REGISTRATION_DOCS` | `LEGAL_AGENT` | `PORTAL` | 登记代办 | I-08 登记结果 |
| `OUTBOUND_DOC` | `DEALER` | `MANUAL` | — | 随车 |

### 4.3 出站拆分规则

一项指令若含多个不同接收方 → 出站层按 `(order_no, receiver_code)` **拆成多任务**，
每任务幂等键 `RLO:{order_no}:{receiver_code}`（D07 §4.2）。

**由此产生三条必须提前定好的规则**（否则实现会各自发明）：

| 规则 | 本文裁决 |
|---|---|
| 部分下发成功怎么办 | 已拆任务各自独立；指令级 `status` 保持 `SENT`，`details.dispatched_receivers[]` 记录成功集；失败接收方进 `RETRY_WAIT`/`DEAD` + 工单 `DISPATCH_PARTIAL` |
| 撤销怎么传播 | **向所有已下发接收方各发一条 cancel 任务**；任一接收方 `ACKNOWLEDGED` 后撤销需人工确认（`RELS_003`） |
| 回执先到哪条 | 每个 item 独立推进；指令级由 §5.3 聚合规则决定 |

## 5. 十态状态机与转移守卫

### 5.1 目标态（超集）

见 D03 §6.3 Mermaid 与 D05 §5.4。状态定义：

| 状态 | 语义 | 谁写 | 允许停留时长 |
|---|---|---|---|
| `PENDING_RELEASE` | 已生成未下发 | 资金闸门通过 | 无限制（但不生成即不该存在） |
| `SENT` | 已下发，对方尚未表态 | 出站成功 | `valid_until` |
| `ACKNOWLEDGED` | 对方已受理（承诺执行） | partner 受理报文 | `receipt-sla`（`[U-09]`，建议 72h） |
| `CONFIRMED` | 交付事实确认（全量） | 权威回执或降级代录 | 终态前 |
| `PARTIAL` | 实际交付与指令不符（**敞口保持**） | 权威回执 | 工单关闭前 |
| `REJECTED` | 对方拒绝执行 | 权威回执 | 整改后重申 |
| `EXPIRED` | 超 `valid_until` 无回执 | 巡检作业 | 终态 |
| `RELEASED` | 实车已出库 + 証書已交还（**实体交付完成**） | 全 item 完成 + 库存 OUT | → 申请抹消登记 |
| `LIEN_DISCHARGED` | **登记簿抹消完成**（第二段解押） | I-08 登记结果回执 | 终态 |
| `CANCELLED` | 我方撤销 | `/cancel` | 终态 |

### 5.2 转移守卫表（每条转移的前置条件，实现即 `ReleaseStateMachine` 的守卫）

| 转移 | 守卫（全部为 AND） | 违反 |
|---|---|---|
| → `PENDING_RELEASE` | 敞口 = 0（已还本 + 息 + 费）；`vehicle_type='USED'` 或 LEGACY 走原链；质押/实控证据齐；资金闸门通过；无 `OPEN` 的差异工单 | `RELS_002`（红线 1） |
| `PENDING_RELEASE` → `SENT` | 每个 item 都能解析出接收方；出站任务创建成功 | `RELS_006` |
| `PENDING_RELEASE` → `CANCELLED` | 有 `RELEASE_ORDER_CANCEL` 权限 + 理由；未曾下发 | — |
| `SENT` → `ACKNOWLEDGED` | 来源 `signature_ok=true` 且 `partner_code` = 该 item 的 `receiver_partner_code` | 401/403，不推进 |
| `SENT` → `CONFIRMED` | 仅限降级：`confirmation_authority='INTERNAL_WITNESS'` + 二人 + 理由 | `AUTH_003` |
| `SENT` → `EXPIRED` | `now > valid_until` 且无任何受理 | 只能由巡检写 |
| `SENT` → `REJECTED` | 权威回执 `result=REFUSED` + `exception_reason` 非空 | 400 |
| `ACKNOWLEDGED` → `CONFIRMED` | **全部 item** 均有 `signature_ok=true` 回执且项集一致 | 否则 `PARTIAL` |
| `ACKNOWLEDGED` → `PARTIAL` | 项集不一致 / 部分项有回执部分无 | 生成 `RELEASE_RECEIPT_MISMATCH` 工单 |
| `ACKNOWLEDGED` → `REJECTED` | 执行前拒绝 | 工单 |
| `PARTIAL` → `CONFIRMED` | 差异结案（二次指令或人工确认已补交）+ 二人 | 敞口不清零不得结案 |
| `PARTIAL` → `RELEASED` | **仅已收项范围内**，且未收项为**非担保必需项**（`OUTBOUND_DOC` 等） | 缺 `VEHICLE`/`INSPECTION_CERT` 一律禁止 |
| `CONFIRMED` → `RELEASED` | 库存 OUT + 車検証 `status=RELEASED` + 钥匙项结论 | 缺一不推进 |
| `RELEASED` → `LIEN_DISCHARGED` | `registration_applications(MORTGAGE_DISCHARGE).status=COMPLETED`（经入站证据） | 我方内部标记**无效** |
| `EXPIRED`/`REJECTED` → `PENDING_RELEASE` | **新指令号 + 新幂等键**，不复用旧号 | `RELS_004` |

### 5.3 指令级状态聚合规则（多 item 时）

```
若任一 item 为 PARTIAL/REJECTED → 指令级 = PARTIAL 或 REJECTED（取最不利）
否则若全部 item CONFIRMED → CONFIRMED
否则取「最靠前但未完成」的那个状态（SENT < ACKNOWLEDGED）
EXPIRED 只在所有 item 均无进展时由巡检置位
```

> 聚合函数必须是**纯函数 + 单测覆盖**（D11 `ReleaseStatusAggregatorTest`）。
> 「取最不利」这一条是刻意的：部分交付永远不能被系统自动洗成全量交付。

### 5.4 撤销语义（补上现状缺失的 `/cancel`）

| 撤销时点 | 可行性 | 动作 |
|---|---|---|
| `PENDING_RELEASE` | 直接撤 | 状态 → `CANCELLED`，不通知对方（从未发出） |
| `SENT`（对方未受理） | 尽力撤 | 向所有接收方发 cancel 任务；`ACKNOWLEDGED` 前到达则撤成功 |
| `ACKNOWLEDGED` 之后 | **系统不得单方面认为已撤** | 需 `force_reason` + 二人 + 对方确认回执；否则 `RELS_003` |
| `CONFIRMED`/`RELEASED` | 不可撤 | 车辆已离仓，只能走追偿/回购路径（R10） |

**撤销与额度的关系**：撤销**不回补也不扣减**额度（额度在放款时已占用，回补只发生在 `SETTLED`）。
撤销只是把敞口保持在原状。这条要说清，否则有人会试图在撤销时"释放占用"。

### 5.5 `delivery_channel` 参与路由（修断裂 2）

```
dispatch(order):
  for item in order.items:
    spec = resolveReceiver(item)
    if spec.channel == API or PORTAL:  enqueue outbound_task (partner 调用)
    elif spec.channel == MANUAL:       标记待人工执行 + 生成工单，绝不伪装已下发
    else:                              VALID_001 拒
  order.status = 至少一条任务已发出 ? SENT : PENDING_RELEASE
```

**禁止**：无条件调用 `ManualReleaseChannel`（现状）。`MANUAL` 通道的语义是"等人执行"，不是"已执行"。
改造后 `ManualReleaseChannel.dispatch()` 的职责变为**生成人工工单并返回"未下发"结论**——
这与 LEGACY 的行为有差异，须在 LEGACY 冒烟里同步（D11 §4 LEGACY 回归清单）。

## 6. 九步全链（本文主表）

| 步 | 名称 | 前置 | 动作 | 落库 | 门禁 | 失败处理 | 补偿 |
|---|---|---|---|---|---|---|---|
| **S1** | 回款到位并匹配 | 售出登记 | 流水匹配 + 冲抵（费→息→本） | `repayment_allocations`、`interest_ledger` | 匹配唯一、幂等 `REP:{vin}:{txn}` | 未匹配 → 工单，**不猜测归属** | 人工指定二人 |
| **S2** | 申请放车/放证 | 敞口清零可见 | 受理申请，锁 VIN | `release_orders` `PENDING_RELEASE` 草稿 | `RELEASE_ORDER_ISSUE` | 已有未终结指令 → `RELS_005` | — |
| **S3** | **资金闸门** | S1 完成 | 校验 本金+利息+费用 = 0 或按裁决的最低清偿 | 闸门结论入 `audit_events` | 不通过 → `RELS_002` | **任何路径都不得绕过**（红线 1） | 补齐回款后重新申请 |
| **S4** | **担保实体权利消灭**（第一段解押） | S3 通过 | 标记 `lien_extinguished_at`；車検証 `PLEDGED → RELEASE_PENDING`；`security_status` 进解除中 | `release_orders.lien_extinguished_at`（新列）、`certificate_custody_events(event=RELEASE_PENDING)` | 实体权利消灭必须**先于**指令生成 | 失败 → 指令不生成，状态回 `PLEDGED` | 无（幂等重试 S4） |
| **S5** | 生成指令（按项接收方） | S4 完成 | 解析每个 item 接收方、写 `valid_until` | `release_order_items`（含 receiver）+ outbox `RELEASE_ORDER_DISPATCHED`（同事务） | 解析失败 → `RELS_006` | 整事务回滚，无孤儿指令 | 修正 `custodians`/持有方后重申 |
| **S6** | 下发 | S5 事务提交 | `OutboundRelay` → DMZ 签名调用 | `outbound_tasks` 按接收方拆分 | 仅 `PENDING_RELEASE/SENT` 可 dispatch | 5xx/超时 → 退避重试；`DEAD` + 工单 | `locked_at` 超时重投（幂等 `RLO:{no}:{receiver}`） |
| **S7** | 对方受理 | S6 至少一条成功 | partner 回受理报文 | `inbound_messages` + `release_order_items.item_status=ACKNOWLEDGED` | **验签 `partner_code` = 该接收方**（INV-5） | 验签失败 → 401 + 不推进 + 安全审计 | 对方重推（新 nonce） |
| **S8** | 执行与权威回执 | S7 | partner 出库/交还 + 回报实际项集、照片、里程、异常类型 | `release_receipts`（全列，`inbound_message_id` 必填）+ 聚合状态 | 项集一致 → `CONFIRMED`；不一致 → `PARTIAL` | `PARTIAL`/`REJECTED` → **敞口保持** + HIGH 工单 | 二次指令（新号）或差异结案二人签认 |
| **S9** | 实体交付确认 → 登记抹消 → 台账闭环 | S8 `CONFIRMED`/`PARTIAL`(范围内) | ① 库存 OUT、車検証 `RELEASED` → `RELEASED`；② 委托抹消登记；③ 登记完成回执 → `LIEN_DISCHARGED`；④ 台账 `SETTLED`；⑤ **额度回补**；⑥ 证据链闭合 | `inventory_releases`、`registration_applications`、`vehicle_units.status`、`credit_lines`、`audit_events` | **顺序不可交换**（§8） | 登记未完成 → 停在 `RELEASED`，敞口与押印残留继续在报表体现 | 代办结果经 I-08 入站推进 |

> **S4 与 S9③ 之间隔着整条执行链**，这正是「两段式」的含义：
> 第一段消灭的是**我方对标的物的实体权利**（放车的正当性来源），
> 第二段消灭的是**登记簿上的公示对抗要件**（第三方可查的风险）。
> 现状六态只表达了一个笼统的 `LIEN_DISCHARGED`，无法区分这两件事（断裂 6）。

## 7. 权威回执：不可自证（红线 2）

### 7.1 三种 `ConfirmationAuthority` 的语义与效力

| 值 | 怎么产生 | 证据 | 可否推进台账 `SETTLED` | 可否回补额度 | 报表要求 |
|---|---|---|---|---|---|
| `PARTNER_RECEIPT` | 外部 partner **验签通过**的报文 | `inbound_message_id` + `signature_ok=true` | ✔ | ✔ | 默认视图 |
| `INTERNAL_WITNESS` | 我方双人见证代录（降级通道） | 二人权限 + 理由 + `audit_events` | **仅 `VEHICLE` 项在 LEGACY 域按 V24 折中可**；**USED 域不得据此推进 `LIEN_DISCHARGED`** | ✘（USED 域） | **必须单列**，不得与 partner 混在同一 KPI |
| `DEALER_SELF_DECLARED` | 车商自称已收到 | 无独立证据 | ✘ **任何域都不行** | ✘ | 只作线索，触发对账 |

**核心裁决**：`INTERNAL_WITNESS` 的效力上限按域不同——

- `NEW_STOCK`（LEGACY）：沿用 V24 折中「我方见证 = 质押解除的合法权威」，不改行为、不改测试。
- `USED`：**见证 ≠ 外部权威**。放证/登记抹消/额度回补一律要求 `PARTNER_RECEIPT`（或登记代办的入站结果）。
  若 U-09/D-04 裁决「部分 WMS 只有门户、无 API」，则这些仓的 `VEHICLE` 项允许 `INTERNAL_WITNESS`，
  但**必须在 `release_orders` 上留下 `receipt_degraded=true` 标记并进差异报表**，且 `LIEN_DISCHARGED` 仍需 I-08 入站。 `[待定源 U-09]`

### 7.2 结构性防伪造（三层，不靠约定）

| 层 | 保证 | 出处 |
|---|---|---|
| API 层 | `confirmation_authority` **不由报文提供**；由「是否验签通过 + 来源端点 + partner_code 与接收方一致」推导；报文中出现同名字段则忽略并回显 `ignored_fields[]` | D07 §3.5 |
| 事务层 | 写回执与写 `inbound_message_id` 同一事务；无 message_id 则拒写 | D02 §9 禁止事项 3 |
| 数据库层 | `CHECK (confirmation_authority <> 'PARTNER_RECEIPT' OR inbound_message_id IS NOT NULL)` | D04 §6 步骤 4 |

> 需求书 §3.5 断裂 4 说得很清楚：现状 `normalizeAuthority()` 只做判空 + 大写化，**任意字符串都能落库**。
> 只加应用层校验是不够的（下一个 Controller 就会漏）；**必须有 DB CHECK 兜底**，这是 P-5/P-6 的落点。

### 7.3 回执载荷最小集（补断裂 5：`saveReceipt` 只写 7 列）

`release_receipts` 必须写全：`order_no, item_type, actual_items[], receiver_name, odometer_km, photo_paths,
exception_type, exception_reason, confirmation_authority, partner_code, inbound_message_id, signature_ok, received_at`。

| 字段 | 为什么是必需 |
|---|---|
| `actual_items[]` | 没有它就无法判定 `PARTIAL`，部分交付会被当成全量交付 |
| `odometer_km` | 与入库里程闭环（盗抢/调表风险的唯一物理证据） |
| `photo_paths` | 車況交付状态，事后争议的唯一客观材料 |
| `exception_type` | `NONE/MISMATCH/REFUSED/DAMAGED/MISSING_IN_WMS/TIMEOUT` — 现状恒 `NONE`（断裂 5） |
| `inbound_message_id` | INV-5 的证据链锚点 |
| `signature_ok` | 冗余存储，使审计查询不需 join `inbound_messages`（取证场景要求单表可判） |

## 8. 台账联动与额度回补（补断裂 9 / 断裂 10）

### 8.1 顺序（不可交换）

```
S9① 库存 OUT (inventory_releases)      ─┐
S9② 車検証 RELEASED                     ├─ 同一事务（一个 @Transactional 用例）
S9③ 指令 RELEASED                       ─┘
   ↓ （异步事件 RELEASE_ORDER_RECEIPTED 消费完成后）
S9④ 台账 SETTLED                        ── 单独事务：vehicle_units.status → SETTLED, settled_at
   ↓
S9⑤ 额度回补                            ── 最后一步，单独事务 + 幂等 + version 乐观锁
   ↓
S9⑥ 审计与证据链闭合
```

**为什么额度回补必须最后**：回补意味着「这台车的敞口消失、车商可以借下一台」。
若在 `SETTLED` 之前回补，会出现「敞口还在（车没确认出库）但额度已可用」的双重融资窗口（ADR-010 防的同一种事）。

### 8.2 `ReleaseOrchestrator` 的改造点

| 现状 | 目标 |
|---|---|
| `ReleaseOrchestrator.java:109` `availableAfter = before`（注释自认"尚未真实回补"） | `availableAfter = before + 归还本金对应的额度`，且 `used_amount` 同步减少 |
| 解押只记日志 | 解押 = 状态机方法 + 事件 + 审计，无 `UPDATE ... SET status` |
| 无幂等 | 幂等键 `CLR:{vin}:{settle_seq}`，回补事件重复消费不重复加额（`event_consumptions` 兜第一层，`credit_lines.version` 兜第二层） |

### 8.3 回补金额口径（与 D08 一致）

```
回补额 = 该 VIN 放款时占用的额度 = advance_amount（本金占用，不含利息）
```

- 利息与费用**不占额度**，因此也不回补。
- 部分交付（`PARTIAL`）**不回补**（敞口保持）。
- 处置变现后的冲抵（R10）走另一条链：`DISPOSAL_AUCTION_RESULT` → 减少 `advance_amount` 余额 → 结清时才回补。

### 8.4 写入集与跨上下文约束（给排期，不是给绕过）

断裂 9 的本质是「`release-service` 无权改 `core` 的表」。三种解法的取舍：

| 方案 | 评价 |
|---|---|
| A. `release-service` 直接写 `vehicle_units` / `credit_lines` | **否**（AGENTS.md §3.1 禁止跨域直写；物理拆库即失效） |
| B. 经 Feign 调 core 端点 | 部分可用，但消费者内部禁止跨服务调用（D02 §7 纪律 3），且链路易成环 |
| C. **outbox 事件驱动**（本文采用） | `RELEASE_ORDER_RECEIPTED` / `VEHICLE_SETTLED` / `CREDIT_LINE_RESTORED` 三段事件，各上下文只写自己的表 |

采用 C 后，`release-service` 的写入集收窄为：`release_orders`、`release_order_items`、`release_receipts`、
`release_state_history`、outbox 发布；**不碰** `vehicle_units`、`credit_lines`、`inventory_releases`、`audit_events`（后三者由 core 消费事件后写）。
这条边界必须在 D12 的任务卡里写成硬约束，否则会重演「本服务未跨目录修改」的空转。

## 9. 四类巡检作业（R7 验收兜底 + D05 §3.7）

| 作业 | 频率 | 判据 | 动作 | 幂等/防风暴 |
|---|---|---|---|---|
| **J1 超时未回** | 每 30 分 | `status ∈ {SENT, ACKNOWLEDGED}` 且 `now > valid_until` 或超 `receipt_sla` | 置 `EXPIRED` + 工单 `RELEASE_RECEIPT_OVERDUE` | 同工单去重键 `{order_no}:OVERDUE`；**绝不代录、绝不自动推进** |
| **J2 账实不符** | 每日（随对账） | `wms_reconcile_diffs.status='OPEN'` 且类型 ∈ {`MISSING_IN_WMS`,`CERT_MISMATCH`} | HIGH 工单 + 冻结该 VIN 新指令 + 可选出站挂失 | `{vin}:{diff_type}:{biz_date}` |
| **J3 无有效估值** | 每日 | `vehicle_type='USED'` 且 `status ∈ {IN_STOCK,...}` 且无 `ADVANCE_BASE` ACTIVE 估值 | 触发重估作业；重估失败 → 告警 `VALU_001` + 禁止新放车？→ **仅禁止新放款，不影响放车**（放车看资金闸门，不看估值） | `{vin}:REVAL_MISSING` |
| **J4 质押未成立** | 每日 | `status='PLEDGED'` 的車検証与 `security_status='REGISTERED'` 不自洽（有登记无证实物 / 有证实物无登记） | 告警 `GUARANTEE_MISMATCH` + 工单 `COLLATERAL_GAP` | `{vin}:{gap_type}` |

> **J3 的一个刻意区分**：估值有效性约束**放款**（D08 §5.3 G3），不约束**放车**。
> 放车的前置是「钱已还」，与残值无关。把两者混在一起会导致车商还清款却提不了车——
> 那是最容易引发客诉与监管投诉的错误，也是本设计特意写下的反面约束。

| X-13 | 车辆已被处置接管 | `disposal_cases.takeover_state` 非 `NONE` | `DSPO_003` 拒发指令 | ✔ |

## 11. 什么叫做「闭环」（证据链闭合定义）

一条放车/放证只有**同时**满足以下 8 条才算闭环，缺任何一条必须在报表里显示为「未闭合」：

| # | 证据 | 表 |
|---|---|---|
| 1 | 资金闸门通过记录 | `audit_events(GATE_*)` + `release_state_history` |
| 2 | 担保实体权利消灭时间戳 | `release_orders.lien_extinguished_at` |
| 3 | 每个 item 的接收方可解析且有历史 | `release_order_items.receiver_*` |
| 4 | 出站任务 `SENT` | `integration.outbound_tasks` |
| 5 | 权威回执（`signature_ok=true` 且 `inbound_message_id` 非空）**或** 显式降级标记 | `release_receipts` |
| 6 | 库存出库记录 | `inventory_releases` |
| 7 | 車検証终态（`RELEASED`/`REISSUED`）+ 保管事件链 | `inspection_certificates` + `certificate_custody_events` |
| 8 | 登记抹消完成（来自入站证据，非内部标记）+ 台账 `SETTLED` + 额度回补事件消费成功 | `registration_applications` + `vehicle_units.status` + `event_consumptions` |

**未闭合的可见性要求**：门户与报表必须提供「未闭合清单」视图（按缺失证据项分类），
并支持从指令号一键拉出全链（`GET /api/release-orders/{no}/evidence-chain`，D07 §7.6）。
> 这条是主动加的：现状最大的问题不是"没做完"，而是"看起来完成了"。未闭合可见性是防止后者的唯一手段。

## 14. 自检

- 需求书 §3.5 十二条断裂**逐条有落点**（§1 表），其中断裂 12（`inspection_certificates` 不存在）在 §2/§3 展开为独立放证线。
- 两条红线各有 4 条（RL-1a~d）与 4 条（RL-2a~d）可执行断言，均为「构造 → 期望」形式，不写原则。
- 十态全部有守卫与写入者；`EXPIRED`/`PARTIAL`/`REJECTED` 都不存在"自动洗成成功"的路径。
- 权威回执有三层结构性防伪造（API / 事务 / DB CHECK），不只靠约定。
- 额度回补顺序（S9⑤ 最后）与理由写明，并给出违反后的双重融资风险。
- 跨上下文写入集（§8.4）给出方案取舍与最终边界，回应断裂 9 的「本服务未跨目录修改」。
- 主动声明两处待裁决效力问题：`U-09` 门户型 WMS 的降级效力、`D-07` 两段式语义；`X-8` 明确「两种证据冲突时不许机器裁决」。
- 未产出 Java / SQL；未修改 `V1`–`V26`；未触碰共享禁区文件。

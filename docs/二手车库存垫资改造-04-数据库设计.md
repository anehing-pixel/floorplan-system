## 1. 通用列与命名约定

### 1.1 约定

| 项 | 规定 | 理由 |
|---|---|---|
| 主键 | 单表实体 `id BIGSERIAL PRIMARY KEY`；**逐台台账仍以业务键为主**（`vehicle_units.vin VARCHAR(32) PRIMARY KEY`，现状如此） | 不推翻现有 |
| 金额 | `BIGINT NOT NULL DEFAULT 0`，**整数日元** | AGENTS.md §6.3 铁律，禁止 `double`/`float` 参与金额 |
| 比率 / 利率 | `NUMERIC(7,4)`；LTV 比率 `NUMERIC(5,4)` | 与 `advance_ratio`、`annual_rate` 现状一致 |
| 时间戳 | `TIMESTAMPTZ NOT NULL DEFAULT now()` | 时区 `Asia/Tokyo` |
| 业务日期 | `DATE` | 与 `interest_ledger(vin,biz_date)` 一致 |
| 枚举列 | `VARCHAR(24)`（状态）/ `VARCHAR(32)`（类型）+ `CHECK` 或引用字典 | R13.4 双层约束 |
| 乐观锁 | `version INT NOT NULL DEFAULT 0`（并发更新表必备） | `vehicle_units` / `credit_lines` 已有 |
| 审计列 | `created_at` / `updated_at` / `created_by VARCHAR(64)` / `updated_by` | 关键动作另写 `audit_events`，操作人从 `AuditActor` 取 |
| 软删除 | **不做物理删除**；用 `status` + `active BOOLEAN`；LEGACY 有 `DEALER_001` 禁止删车商的先例 | — |
| 外键 | 同上下文内**建 FK**；跨上下文用「逻辑引用」（无 FK），与现状 `release_orders.redemption_id` 一致 | 拆分与并行迁移友好 |
| 唯一性 | 部分唯一索引一律 `CREATE UNIQUE INDEX ... WHERE ...`（**表内 `UNIQUE (...) WHERE` 是非法语法**，V19 踩过） | PROGRESS §7 铁证 |

### 1.3 并行开发下的迁移与表数口径（与 D12 §4.1 同源）

| 规则 | 内容 |
|---|---|
| 一人一套 schema | 并行期本域各包用 `scripts/agent_env.sh` 建独立 schema，连接串 `?currentSchema=<agent>,public`。**第二个 `,public` 不能省**：V5 依赖装在 public 的 pgcrypto `gen_salt()`，只写自己会让迁移在 V5 中断，残留表 + `search_path` 回落 public = 读到别人的数据、冒烟假绿 |
| 表数门槛 | `agent_env.sh check` 的基准默认 **67**（V1–V26 实建表数）。USED 每包必须显式设 `FLOORPLAN_PUBLIC_TABLES=67+本分支实际已应用的 public 迁移数`（**并行同基线时＝67+本包；分支若已合入前序包则含它们**）；**逐包两套值与终态只以 §2.1 为准**（数字不在别处复述，避免又写死一个过时的），实数以 `check` 输出为准与本表互校。**改环境变量，不改共享脚本** |
| 号段 | V40–V79 在各自 schema 内互不冲突，**但合回主干时必须复核顺序与 checksum**；`flyway_schema_history` 不跨 schema 搬；冲突时整块后移、不逐文件穿插（AGENTS.md §6.2 的两次 `V24` 事故是同一个坑的共库版本） |
| `integration` | 六张集成表（V71 partners、V72 inbound+nonces、V73 outbound、V74 call_logs、V71 段内 partner_credentials，见 §4.6）是全局队列 / 幂等 / 防重放表，并行同样互踩 → W-U3 单人独占（D12 §4.1）。角色 `floorplan_dmz` 与其授权是**库级对象，不随分支 schema 复制**，故 §4.1 的授权断言只在主干回归算最终结论 |
| 主干回归 | 合并后在唯一 `public` 跑一次全量冒烟才是交付判据（用户规矩）；分支 schema 的绿灯**不覆盖**并发与幂等类断言（D11 §9.4 ⑦）。基线标签一律 `base-<波次>-<日期>` |

### 2.1 新建表计数（`FLOORPLAN_PUBLIC_TABLES` 的唯一算法来源）

| 包 | 建表文件 | 本包 `public` 新建表 | `public` 累计 | 主干 public 表数基准（67 + 累计） | 本包 `integration` 新建表 |
|---|---|---|---|---|---|
| W-U1 | V45(3)、V51(1)、V52(2) | **6** | 6 | **73** | 0 |
| W-U2 | V55(2)、V56(1)、V57(2)、V60(1)、V61(2)、V62(2)、V64(1) | **11** | 17 | **84** | 0 |
| W-U3 | V71(**2**：partners + partner_credentials)、V72(2)、V73(1)、V74(1) | **0**（本包六张全在 `integration`） | 17 | **84** | **6** |
| W-U4 | V65(1)、V66(3)、V69(1) | **5** | 22 | **89** | 0 |
| W-U5 | V75(1)、V76(1) | **2** | **24** | **91** | 0 |

> **本表 2026-11-22 由 D13 §3 G10 修正**。原稿把 W-U3 的 5 张 `integration` 表也累进了 `public`
> 基准（造成 89 / 96），这是错的：`scripts/agent_env.sh` 的表数判据只查
> `table_schema = '<本 agent 的 schema>'`（`agent_env.sh:112-128`），
> 永远看不到 `integration` schema 里的表，于是按旧基准跑 `check` 会**必然报「表数不足」的假故障**，
> 而人为了把它跑绿就会去建一张不相干的表——那是拿判据迁就数字。
> 修正后的口径：**`public` 终态 67 + 24 = 91；`integration` 独立 6 张（G9 补 `partner_credentials` 后由 5 → 6），不参与 `FLOORPLAN_PUBLIC_TABLES`**。
> `integration` 的表数门槛若需要，单独一条 SQL 数 `information_schema.tables WHERE table_schema='integration'`，
> 不要塞进 `agent_env.sh`（该文件是共享禁区，改动要走 AGENTS §7.1 的授权路径）。

- 只算 `CREATE TABLE`；`custodians`/`advances`/`release_orders`/`release_order_items`（V19/V24 已存在）/
  `disposal_cases`/`risk_concentration_snapshots` 等**加列与加索引不计入**。
- **隔离分支跑 `check` 时的门槛是「67 + 本分支实际已应用的 public 迁移」**，不是上表的终态值：
  W-U1 分支只有 V45/V51/V52 时填 73，W-U3 分支（含 W-U1+W-U2 迁移）填 84。**填成 89/96 会误报**。
  **两套值都以本表为准，别处只照抄**（2026-11-22 D13 G10/A6 二次修正补此行；第一版修正只把
  `integration` 从 public 里摘出去，没写清「分支只含本包迁移」这一层，WU0-09/WU4-20 报的是它）：
  ① **并行同基线**（各分支从同一个 `base-*` 标签切出，只含本包迁移）：W-U1 **73** / W-U2 **78** /
  W-U3 **67** / W-U4 **72** / W-U5 **69**；② **主干累计**（收口方逐包合入后回 `public` 全量验）：
  73 / 84 / 84 / 89 / 91。分支填 ②、或给 `integration` 计数，都是「拿判据迁就数字」的前置动作，禁止。
- **两个条件项**：V40 若落「枚举字典表」、V41 若落「DB 参数表」（而非 yml），各再 +1
  （`public` 上限随之 91 → **93**）。
  这两张表建不建由 §11 的选型决定，**建了就必须同步改本表**，否则 `check` 门槛会误判。
- V64 的豁免规则表**已定名 `aging_exempt_rules`**（2026-11-22 D13 §4.4 WU2-11，列规格 D04 §3.14.1、
  名称与包归属已进 D00 §7.1 第 17 行），本表按 1 张计入，W-U2 门槛 84 不再悬空。
  规则**内容行**仍属 `[待定源 D-05]`：签字前只建表、不预置任何 ACTIVE 规则，也不接判定分支。
- 用法：`FLOORPLAN_PUBLIC_TABLES=<本表基准值> bash scripts/agent_env.sh check <schema>`；
  实建数与本表不符即为**漏建或重复建表**，先查 `flyway_schema_history` 再跑冒烟。

> 跳号（V42–V44、V48–V49、V80 预留）有意保留为**段内缓冲**，避免追加列时抢下一段号。
> 每个迁移文件必须：幂等（`IF NOT EXISTS` / `IF NOT EXISTS` 索引）、无 `DROP`、无 `TRUNCATE`、无 `DELETE`（回填除外，见 §10）。

**「唯一命中」在 DDL 层能做到的与做不到的**（2026-11-22 由 D13 §4.4 WU2-10 改写，原稿只写了一句
「互斥与全覆盖由单测 + 作业保证」，等于把 L1 挂在空气上）：

| | 能否用约束表达 | 本轮定的做法 |
|---|---|---|
| 单行的区间方向、比率范围、priority 唯一 | ✅ 能 | 进 V57 的 `CHECK` / 唯一索引，**建表即生效** |
| 「任意输入**恰好**命中一带」（跨行互斥 + 全覆盖） | ❌ 不能——它是行**集合**在连续维度上的性质，Postgres 无排他约束可表达（`EXCLUDE` 只支持标量/GIST 类型，四维笛卡尔积写不出来） | 改为**可执行的两件**：① `LtvTierResolverTest` 参数化穷举**边界样本集**（样本集本身进 D08 §4.2 定源：每个维度的 min/max、min−1、max+1，加上修復歴/評価点/車検档位的有效组合）；② 上线前校验作业按 D08 §4.4 方案 ①/② 二选一的语义跑一遍全样本，**不通过就不允许 `ACTIVE`** |
| 「不许出现全宽带 / 嵌套带」 | ⚠️ 半能 | 保存时应用层断言：新带的每个维度区间不得是既有带的严格超集且 `max_ratio` 不同；违规报 `LTV_002` |

> 措辞纪律：**不要再写「L1 = 全枚举校验」这种听起来能保证、实际跑不动的话**。
> 连续维度不可能枚举完，能被执行的是「边界样本 + 保存时互斥断言 + 生效前作业」三件套，
> 缺任何一件，分档表都可能带着嵌套带上线（后果见 D13 §4.4 WU2-01：`resolve()` 恒抛 `LTV_002`）。

## 4. `integration` schema 规格（R11，V70–V74）

### 4.1 Schema 与角色（V70）

```sql
-- 规格示意，落盘时按 V70 单文件组织，全部幂等
CREATE SCHEMA IF NOT EXISTS integration;

DO $$ BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'floorplan_dmz') THEN
    CREATE ROLE floorplan_dmz LOGIN PASSWORD 'floorplan';   -- 本地与现状同密；生产由部署注入
  END IF;
END $$;

GRANT USAGE ON SCHEMA integration TO floorplan_dmz;
-- 关键：对 public 一律不授权，且显式撤销（防继承）
REVOKE ALL ON SCHEMA public FROM floorplan_dmz;
REVOKE ALL ON ALL TABLES IN SCHEMA public FROM floorplan_dmz;
ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE ALL ON TABLES FROM floorplan_dmz;
-- integration 下对象的权限在各自建表后授予（避免默认权限依赖执行者）
-- ⚠️ 逐表授 DML，**不给 `ON ALL TABLES IN SCHEMA integration` 通配**：
--    通配会把 partners / partner_credentials 也授成可写，
--    DMZ 一旦失守就能自己插一行 status='ACTIVE' 的密钥版本 = 绕过验签闸门（INV-1 当场失效）。
--    下列语句随各表建表脚本执行（partner_credentials 在 V71 段内，见 §4.6）：
GRANT SELECT, INSERT             ON integration.inbound_messages      TO floorplan_dmz;  -- 状态迁移归 core 领取方
GRANT SELECT, UPDATE             ON integration.outbound_tasks        TO floorplan_dmz;  -- 只读领取 + 回写投递结果
GRANT SELECT, INSERT, DELETE     ON integration.nonces                TO floorplan_dmz;  -- 防重放表由 DMZ 自清 TTL
GRANT SELECT, INSERT             ON integration.call_logs             TO floorplan_dmz;  -- append-only
GRANT SELECT                     ON integration.partners             TO floorplan_dmz;
GRANT SELECT                     ON integration.partner_credentials  TO floorplan_dmz;  -- 只读 key_version→secret_ref 与有效期
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA integration TO floorplan_dmz;
-- 后续新建表默认**只给 SELECT**：要写必须显式补授权，防止「新表自动落进 DMZ 写集」
ALTER DEFAULT PRIVILEGES IN SCHEMA integration GRANT SELECT ON TABLES TO floorplan_dmz;
```

> **本段 2026-11-22 由 D13 §3 G9 / §5.1-A8 补全**。原稿只写了 `GRANT USAGE ON SCHEMA`，
> 而 USAGE 只允许「进入 schema」，**不允许读写任何表**——`external-api` 以 `floorplan_dmz`
> 连上去后第一条 `INSERT INTO integration.inbound_messages` 就会 `permission denied`。
> 授权时机也有坑：`GRANT ... ON ALL TABLES IN SCHEMA` 只作用于**执行时已存在**的表，
> 所以 V71–V74 各自建表后都要补一次（本示例放在 V70 里的那两行只保当刻；
> `ALTER DEFAULT PRIVILEGES` 才管后续新建，且只对**该默认权限的执行者**创建的表生效——
> 迁移由 `floorplan` 用户跑，故 `ALTER DEFAULT PRIVILEGES` 必须以 `AS` 或同一角色身份执行，
> 落地时以 `flyway` 连接的属主为准并在 §4.1 断言里核对）。
> 密码 `'floorplan'` 只在 DO 块内「角色不存在时」生效，属**明文写进迁移**的既有做法（与主干一致），
> 但生产改密必须由部署注入、不得复用该行；本条已在 D02 §8 风险表登记。
>
> **2026-11-22 同批二次修正（逐表授权）**：上一版为省事写了 `GRANT ... ON ALL TABLES IN SCHEMA integration`，
> 连带把 `partners` / `partner_credentials` 授成 DMZ 可写。这不是「权限给宽一点」，
> 而是给 DMZ 留了一条**自签闸门**：改自己那行的 `status='ACTIVE'` 或插一个新 `key_version` 就能让任意伪造报文通过验签，
> 而 INV-1（DMZ 无业务写路径）恰好是这套隔离存在的理由。同一形状的教训见 AGENTS §12「用可配置白名单放宽安全策略」。
> 现在默认权限只发 SELECT，写权限逐表显式给；新增一张 integration 表时如果忘了补授权，
> 症状是 DMZ 报 `permission denied`（响亮），而不是悄悄多了一个可写面（沉默）——**要的是前者**。

**为什么用 `DO $$` 包角色判断**：`CREATE ROLE` 无 `IF NOT EXISTS`，迁移必须幂等
（历史上 V17/V19/V20/V21 全靠 `IF NOT EXISTS` 才能 out-of-order 补齐，见 PROGRESS §0）。

**⚠️ 迁移归属例外声明**：AGENTS.md 规定「只有 `web` 跑 Flyway」。本 schema 的建表脚本
仍放 `infrastructure/.../db/migration/`（V70–V74）由 `web` 执行；`external-api` 保持
`spring.flyway.enabled=false`，并在启动顺序上排在 `web` 之后。**已在 D02 §8.1 与 D01 §4.4 登记，评审须确认。** `[待定源 U-03]`

### 4.6 `integration.partner_credentials`（V71 段内新增，2026-11-22 D13 G9 补）

**问题**：§4.2 的 `partners` 每方只有一行、一个 `secret_ref` + 一个 `key_version` + 一个
`key_grace_until`。这个形状表达不了 D02 §5.6 要求的「宽限期内新旧两版都要能验」——
要验旧版就得**同时持有两个版本的密钥引用**，而单行只有当前版；更麻烦的是第二次轮换会把
第一次的历史彻底抹掉。派发记录 §0 里提到的 `partner_credentials` 表**在全设计集没有规格**，
属于「名字被引用、实体不存在」，正是 AGENTS §12 反模式里「表建了就算功能有了」的反面（连表都没有）。

**规格**（每版本一行，历史不删）：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | BIGSERIAL PK | |
| `partner_code` | VARCHAR(64) NOT NULL | 逻辑引用 `partners` |
| `key_version` | INT NOT NULL | 与 `X-Key-Version` 直接对齐；**单调递增** |
| `secret_ref` | VARCHAR(128) NOT NULL | keystore 引用，**不落明文**（INV-4） |
| `secret_fingerprint` | VARCHAR(64) | 前 8 位，供管理台核对与吊销定位 |
| `status` | VARCHAR(16) | {`ACTIVE`,`GRACE`,`REVOKED`} + CHECK |
| `valid_from` | TIMESTAMPTZ NOT NULL | |
| `valid_until` | TIMESTAMPTZ NULL | `ACTIVE` 为空；`GRACE`/`REVOKED` 必填 |
| `rotated_by` | VARCHAR(64) | 轮换操作人（从 `AuditActor`，不从请求体） |
| `rotate_reason` | VARCHAR(256) | 例行 / 泄露吊销 |

约束与口径：
- **UNIQUE `(partner_code, key_version)`**；**部分唯一 `WHERE status='ACTIVE'` 每方只允许一版 ACTIVE**。
- 验签规则：取 `(partner_code, X-Key-Version)` 行 → 必须 `status IN ('ACTIVE','GRACE')`
  → 且 `X-Timestamp` 落在该行 `[valid_from, coalesce(valid_until, ∞))` 内。
  `GRACE` 行过期后不删（留审计），只由清理作业置 `REVOKED`。
- `partners.secret_ref` / `key_version` / `key_grace_until` 三列降级为**指向本表的缓存**，
  以本表为准（否则两处各说一套，就是 Q27 式的多权威源问题）。
- **keystore 历史查询**（D07 §7.8 管理端点）据此表出「某版密钥的启用/吊销时间与经手人」，
  不返回任何密钥值。

> **表数影响**：integration 由 5 张变 **6 张**；`public` 基准不变（本表在 integration），
> 因此 §2.1 的 public 阶梯 73/84/84/89/91 不受影响。
> **2026-11-22 同步完成**：§2 依赖表第 57 行、§2.1 阶梯 W-U3 行（`V71(2)` / integration **6**）与口径句、
> §4.1 逐表授权、D00 §5.2 边界规定与 §7 号段表、D01 §4.3 影响面、D02 §5.2 职责表（补本表一行）与 §2/§9/§10、
> D06 §14、D11 §0/T4 分层表、D12 §4.1、派发记录 §0 的「五张」表述均已改为**六张**。

## 6. 枚举的 DB 层双层约束（R13.4）

**双层**：Java 枚举（`domain`）+ DB `CHECK` 或字典表。现状反面样例：
`release_orders.confirmation_authority` 是**无约束字符串**，`normalizeAuthority()` 只做判空 + 大写化，
任意字符串（含伪造 `PARTNER_RECEIPT`）都能落库。

**V67 收紧方案（分四步，必须按序，不可一步到位）**：

```
步骤 1  建字典表 integration 无关：public.enum_confirmation_authority(code TEXT PK, allowed_in_used BOOLEAN)
        种子值：PARTNER_RECEIPT / INTERNAL_WITNESS / DEALER_SELF_DECLARED
步骤 2  回填清洗（§10，U-05）：把现存自由文本归一到三个合法值之一
步骤 3  加约束：ALTER TABLE release_receipts ADD CONSTRAINT chk_auth
                  CHECK (confirmation_authority IN
                         ('PARTNER_RECEIPT','INTERNAL_WITNESS','DEALER_SELF_DECLARED'))
        ★ 用 NOT VALID + VALIDATE 两步，避免长表锁；先 NOT VALID 让存量不阻塞上线
步骤 4  USED 域行为约束：PARTNER_RECEIPT 必须存在 inbound_message_id
        用 CHECK (confirmation_authority <> 'PARTNER_RECEIPT' OR inbound_message_id IS NOT NULL)
        ★ 这一条把「伪造外部回执」变成数据库层不可能事件（D02 INV-5 的持久化保证）
步骤 4+ 4 本身只保证「非空」，一个假整数也能满足——原稿到此为止，故 2026-11-22 补三件：
        (a) 真外键：ALTER TABLE release_receipts ADD CONSTRAINT fk_receipt_inbox
            FOREIGN KEY (inbound_message_id) REFERENCES integration.inbound_messages(id)
            NOT VALID → VALIDATE（跨 schema 同库允许，DMZ 角色不因此获得 public 权限，方向是 public→integration）
        (b) 一条入站报文最多只 authorize 一张回执：
            CREATE UNIQUE INDEX ux_receipt_inbox ON release_receipts(inbound_message_id)
              WHERE inbound_message_id IS NOT NULL
            ——否则一条真报文可被复制引用去结清 N 台车，仍是伪造面
        (c) 「引用的那行必须 signature_ok=true 且 message_type/business_ref 与本单一致」
            **CHECK 做不到跨表谓词**，因此写成两条可执行的防线：
              · 唯一写入口 = inbox dispatcher（禁止任何内部端点写 inbound_message_id，见 D07 §13 第 5 条）
              · 每日对账 SQL 把「authority=PARTNER_RECEIPT 但 join 不到 signature_ok=true 行」的
                回执列为 CRITICAL 差异（进 D09 §11 证据链核对，不留成沉默数据）
        ★ 没有 (a)(b) 时，INV-5 的「数据库层不可能」这句结论不成立，D11 A2.4/A1.3 的断言会假绿
```

其余枚举列（`status` / `*_type`）同样加 `CHECK`，但**必须包含存量已有值**，
否则迁移直接失败（Flyway 会回滚整个迁移，历史上 V19 语法错误导致全断的教训）。

## 11. 参数落 DB 还是落 yml（一处需要评审的取舍）

需求书与 D00 §12 用 yml 表达默认值，但**分档 LTV、LTV 阈值、结算窗口、豁免规则**属于

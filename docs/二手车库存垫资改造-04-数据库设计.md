## 1. 通用列与命名约定

### 1.1 约定

| 项 | 规定 | 理由 |
|---|---|---|
| 主键 | 单表实体 `id BIGSERIAL PRIMARY KEY`；**逐台台账仍以业务键为主**（`vehicle_units.vin VARCHAR(32) PRIMARY KEY`，现状如此） | 不推翻现有 |
| 金额 | `BIGINT NOT NULL DEFAULT 0`，**整数日元** | AGENTS.md §6.3 铁律，禁止 `double`/`float` 参与金额 |
| 比率 / 利率 | `NUMERIC(7,4)`；LTV 比率 `NUMERIC(5,4)` | 与 `advance_ratio`、`annual_rate` 现状一致 |
| 时间戳 | `TIMESTAMPTZ NOT NULL DEFAULT now()` | 时区 `Asia/Tokyo` |
| 业务日期 | `DATE` | 与 `interest_ledger(vin,biz_date)` 一致 |
| 枚举列 | `VARCHAR(24)`（状态）/ `VARCHAR(32)`（类型）+ `CHECK` 或引用字典 | R13.4 双层约束 |
| 乐观锁 | `version INT NOT NULL DEFAULT 0`（并发更新表必备） | `vehicle_units` / `credit_lines` 已有 |
| 审计列 | `created_at` / `updated_at` / `created_by VARCHAR(64)` / `updated_by` | 关键动作另写 `audit_events`，操作人从 `AuditActor` 取 |
| 软删除 | **不做物理删除**；用 `status` + `active BOOLEAN`；LEGACY 有 `DEALER_001` 禁止删车商的先例 | — |
| 外键 | 同上下文内**建 FK**；跨上下文用「逻辑引用」（无 FK），与现状 `release_orders.redemption_id` 一致 | 拆分与并行迁移友好 |
| 唯一性 | 部分唯一索引一律 `CREATE UNIQUE INDEX ... WHERE ...`（**表内 `UNIQUE (...) WHERE` 是非法语法**，V19 踩过） | PROGRESS §7 铁证 |

### 1.2 列名避讳（D00 §2.1 落库版）

| 禁止 | 正确 | 原因 |
|---|---|---|
| `registration_no` 存车牌 | `registration_plate` | 与 V10/V25 担保登记编号撞名 |
| 复用 `certificate_no` 存車検証 | 新增 `inspection_certificate_no` | V19 该列注释明确是「车辆合格证号，不是法务局登记证明书」 |
| `mileage` 继续裸用 | 保留 `mileage`（兼容）+ 新增 `mileage_source` / `mileage_captured_on` / `mileage_unit` | R2.3 可追溯 |
| 布尔名 `is_xxx` | `xxx_flag` 或直接形容词（`repair_history` 用枚举不用布尔） | 修复歴非二值 |

## 4. `integration` schema 规格（R11，V70–V74）

### 4.1 Schema 与角色（V70）

```sql
-- 规格示意，落盘时按 V70 单文件组织，全部幂等
CREATE SCHEMA IF NOT EXISTS integration;

DO $$ BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_roles WHERE rolname = 'floorplan_dmz') THEN
    CREATE ROLE floorplan_dmz LOGIN PASSWORD 'floorplan';   -- 本地与现状同密；生产由部署注入
  END IF;
END $$;

GRANT USAGE ON SCHEMA integration TO floorplan_dmz;
-- 关键：对 public 一律不授权，且显式撤销（防继承）
REVOKE ALL ON SCHEMA public FROM floorplan_dmz;
REVOKE ALL ON ALL TABLES IN SCHEMA public FROM floorplan_dmz;
ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE ALL ON TABLES FROM floorplan_dmz;
-- integration 下对象的权限在各自建表后授予（避免默认权限依赖执行者）
```

**为什么用 `DO $$` 包角色判断**：`CREATE ROLE` 无 `IF NOT EXISTS`，迁移必须幂等
（历史上 V17/V19/V20/V21 全靠 `IF NOT EXISTS` 才能 out-of-order 补齐，见 PROGRESS §0）。

**⚠️ 迁移归属例外声明**：AGENTS.md 规定「只有 `web` 跑 Flyway」。本 schema 的建表脚本
仍放 `infrastructure/.../db/migration/`（V70–V74）由 `web` 执行；`external-api` 保持
`spring.flyway.enabled=false`，并在启动顺序上排在 `web` 之后。**已在 D02 §8.1 与 D01 §4.4 登记，评审须确认。** `[待定源 U-03]`

## 6. 枚举的 DB 层双层约束（R13.4）

**双层**：Java 枚举（`domain`）+ DB `CHECK` 或字典表。现状反面样例：
`release_orders.confirmation_authority` 是**无约束字符串**，`normalizeAuthority()` 只做判空 + 大写化，
任意字符串（含伪造 `PARTNER_RECEIPT`）都能落库。

**V67 收紧方案（分四步，必须按序，不可一步到位）**：

```
步骤 1  建字典表 integration 无关：public.enum_confirmation_authority(code TEXT PK, allowed_in_used BOOLEAN)
        种子值：PARTNER_RECEIPT / INTERNAL_WITNESS / DEALER_SELF_DECLARED
步骤 2  回填清洗（§10，U-05）：把现存自由文本归一到三个合法值之一
步骤 3  加约束：ALTER TABLE release_receipts ADD CONSTRAINT chk_auth
                  CHECK (confirmation_authority IN
                         ('PARTNER_RECEIPT','INTERNAL_WITNESS','DEALER_SELF_DECLARED'))
        ★ 用 NOT VALID + VALIDATE 两步，避免长表锁；先 NOT VALID 让存量不阻塞上线
步骤 4  USED 域行为约束：PARTNER_RECEIPT 必须存在 inbound_message_id
        用 CHECK (confirmation_authority <> 'PARTNER_RECEIPT' OR inbound_message_id IS NOT NULL)
        ★ 这一条把「伪造外部回执」变成数据库层不可能事件（D02 INV-5 的持久化保证）
```

其余枚举列（`status` / `*_type`）同样加 `CHECK`，但**必须包含存量已有值**，
否则迁移直接失败（Flyway 会回滚整个迁移，历史上 V19 语法错误导致全断的教训）。

## 8. 数据量与性能预估（评审参考）

| 表 | 年增量估算 | 主要访问模式 | 设计要点 |
|---|---|---|---|
| `auction_lots` | 中（取决于车商规模） | 按 `vin`、按 `(场次,lot_no)` | 双索引；场次批量入站需 `INSERT ... ON CONFLICT DO NOTHING` |
| `vehicle_valuations` + `valuation_inputs` | **大**（每台每月 ≥1 次重估） | 按 `vin` 取 `ACTIVE`；按 `valid_until` 扫过期 | `uk_val_active` 部分索引；历史行按年归档（参照 `interest_ledger_archive` 既有做法） |
| `wms_inventory_snapshots` + items | **最大**（每日每仓全量） | 按 `(仓,日)` 整体读取比对 | items 表按月分区（一期可先不分区，预留 `snapshot_date` 分区键）；快照不可变，可安全归档 |
| `integration.inbound_messages` | 中 | 轮询 `status` + `received_at` | 部分索引只覆盖未完成态，避免全表膨胀；已完成按保留期归档 |
| `integration.call_logs` | **大**（每次出站） | 按 partner + 时间、按 traceId | append-only；建议月分区或定期 `COPY` 到冷存（本地文件，不引入对象存储） |
| `wms_reconcile_diffs` | 小 | 按 `biz_date` | 天然按日聚合 |

**共库风险**：USED 域的估值与快照体量增长会**先于**业务量压垮共用的 `public` schema。
§11 的对拍与报表必须走只读副本或限定时间窗，不能全表扫。

## 11. 参数落 DB 还是落 yml（一处需要评审的取舍）

需求书与 D00 §12 用 yml 表达默认值，但**分档 LTV、LTV 阈值、结算窗口、豁免规则**属于
「风控要能自己改、每次改动要留痕」的参数。本文建议：

| 参数类 | 载体 | 理由 |
|---|---|---|
| 结构性开关（`floorplan.used.enabled`、通道选择、DMZ 数据源、签名时间窗） | **yml** | 部署属性，变更走发布 |
| 风控口径参数（分档 LTV、残值率阈值、结算窗口、库龄递减比例、豁免规则） | **DB 规则表**（`ltv_policies` / `aging_plans.rule_code` / 新增 `used_policy_params`） | 需要启停版本、生效区间、二人审批、审计 |
| 折中：全局默认值 | yml 提供 DB 缺表时的兜底 | 本地开发与冒烟不依赖种子数据 |

若评审决定全部走 yml，则 §3.14 两张表退化为「文档化的配置样例」，
D11 的「改一档 LTV 只动一处」验收断言需相应改写。`[待定源 D-06]`

## 12. 迁移落地纪律（复述，评审必须逐条确认）

1. **`V1`–`V26` 字节不变**；USED 域全部新能力走 V40+（§2 表）。
2. 每个迁移**幂等**、**单文件单主题**、**不建空文件**、**不加 `DROP`**。
3. 加 CHECK 前先核对存量取值集合，必要时 `NOT VALID` + `VALIDATE` 两步。
4. 部分唯一索引一律表外 `CREATE UNIQUE INDEX ... WHERE ...`。
5. 开工前在 `PROGRESS.md` 登记号段（该文件由收口方维护）。
6. 发现 V40 已被在途波次占用 → **整段后移**并同步更新本文 + D12，禁止插队。
7. 验证顺序：单文件在**临时空库**逐文件单事务执行（勿用 autocommit，历史教训：V14 有
   `CREATE TEMP TABLE ... ON COMMIT DROP`），再全量 `mvn -B package`，最后 `run-microservices.sh smoke`。
8. `COMMENT ON` 只用于**加限定语**，不得删除原注释内容（保留审计轨迹）。

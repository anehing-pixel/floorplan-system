## 一、需求：申请垫款之后、放款之前要补齐担保文件

业务人员（业务经办岗）在经销商提交垫款申请之后，要走一段**线下流程**：

1. 与经销商签订**垫付合同**（担保合同正本）；
2. 到**法务局**办理登记，取得**登记编号**；
3. 把合同文件、登记编号等信息**上传系统**，文件存 **AWS S3**；
4. 这些信息要能**对应到每一笔车辆台账**（单车可查）；
5. 信息齐备后，**资金岗才能放款**（`disburseAdvance`）。

**最需要注意的一点**：垫付合同和法务局登记编号都是**针对一批车辆整体签订/办理**的，
不是一台车一份。因此数据模型上必然是"批次级文件 → 多台车"的一对多关系。

### 1.1 两个动作的粒度不一致（本需求的核心矛盾）

| 动作 | 粒度 | 现状 |
|---|---|---|
| 签合同 + 法务局登记 | **一批车一次**（一次登记涵盖 N 台） | — |
| 放款 `disburseAdvance` | **一台车一次**（无批量放款接口） | 现状如此，本需求不改动 |

由此推出后台必须具备的能力：**一次操作，把同一份合同与同一个登记编号挂到一批台账上**，
而不是让业务人员逐台车重复上传 N 遍。这也决定了交互形态是
"**建批次 / 维护批次 → 框选一批车 → 统一上传**"，而不是"在车辆详情页逐台传文件"。

## 二、现状盘点：基础表已具备，缺的是"放款门槛"与"时序"

### 2.1 已经具备的能力（V10 迁移已建，无需重新设计）

| 能力 | 位置 | 说明 |
|---|---|---|
| 批次级登记主表 | `collateral_registration_batches` | 含 `registration_no`（法务局登记编号，唯一）、`contract_no`、`contract_signed_at`、`certificate_no`、`registry_office`、`registered_at`、`expires_at` |
| 批次级合同文件 | 同上 `contract_attachment_id` | 外键指向 `attachments(id)`，注释明确为"S3 存证、担保权成立的**实体依据**" |
| 批次级登记事项证明书 | 同上 `certificate_attachment_id` | 担保权成立的**公示依据**，与合同缺一不可 |
| 批次 → 车辆关联 | `collateral_registration_items` | `(batch_id, ledger_id, vin)`，唯一约束 `(batch_id, vin)` |
| 附件表 | `attachments`（V7） | `object_key`/`bucket`/`region`/`sha256`/`etag`/`object_lock_mode`（COMPLIANCE/GOVERNANCE，一次写入不可删改） |
| 对象存储实现 | `S3AttachmentStorage` / `LocalAttachmentStorage` | 配了 `s3.bucket` 走 S3，否则回退本地磁盘 |
| 上传接口 | `POST /api/attachments/presign`、`/complete` | 预签名直传 + 完成确认 |
| 建批次接口 | `POST /api/collateral/registration-batches` | 已支持一次传入 `vins` + 登记编号 + 合同附件 + 证明书附件 |
| 按车反查批次 | `CollateralRegistrationBatchRepository.findByVin(vin)` | 已有 |

**结论：数据模型与文件存储链路基本完备，本需求不需要新建主表。**

### 2.2 五个缺口（这是本次真正要实现的东西）

**缺口 1（最核心）：`disburseAdvance` 完全没有担保文件校验。**
`AdvanceApplicationService.disburseAdvance()` 目前只校验两件事：垫款状态必须是 `PENDING`、
支付人不得与申请人/复核人同一自然人（职责分离）。**合同有没有签、法务局有没有登记，
一个字都不看**——资金岗点一下就能把钱打出去。这正是需求要堵的口子。

**缺口 2（时序冲突，必须一并解决）：放款前无法登记。**
`collateral_registration_items.ledger_id` 是 **NOT NULL**，外键引用 `collateral_ledger(id)`；
而 `collateral_ledger` 目前是在**放款确认之后**才由 `confirmAdvance → markFinanced → loadOrCreate`
建立的。于是形成死锁：

> 放款前要登记 → 登记需要 ledger → ledger 要放款后才建 → 放款前永远登不上。

**缺口 3：无法向已存在的批次补传文件。**
合同与证明书目前**只能在创建批次的那一刻**一次性传入。而真实流程是先跑法务局、
后拿到编号和证明书（纸质凭证往往比登记编号晚几天），必然需要"建批次 → 后续补传"。

**缺口 4：没有放款就绪度查询。**
资金岗无法在放款前知道"这台车还缺什么"，只能点了放款才知道被拒，被拒信息也零散。

**缺口 5（实测数据）：现有 18 个登记批次的合同与证明书附件全部为空。**
库里 `contract_attachment_id`、`certificate_attachment_id` 两列均为 NULL，
说明"上传"这条链路从未真正跑通过——这与缺口 3 直接相关。
另注：目前每个 VIN 都出现了两个批次（一个正式编号 + 一个 `R-EMPTY-*` 空批次），
后者是测试遗留脏数据，清理时需一并处理。

## 三、关键设计决策

### 决策 1：登记编号冗余到台账，合同文件只存一份由多台台账共享

这两者的处理必须**分开**，因为它们的变更特性完全不同：

| 数据 | 是否落到台账 | 理由 |
|---|---|---|
| **法务局登记编号** | **冗余到 `vehicle_units.registration_no`** | 登记编号由法务局签发、**不可变**，不存在多版本问题；台账列表页与对账导出要直接看到它，联查批次太重 |
| **垫付合同文件（S3）** | **不冗余**，靠批次共享 | 合同会重签、会有补充协议，是多版本的；若把 `attachment_id` 复制到 N 行台账，换版本时要改 N 行且极易漏 |

**"多个台账指向同一份 AWS 合同"的实现方式**：`attachments` 表只存**一行**
（一个 `object_key`、一份 S3 对象），`collateral_registration_batches.contract_attachment_id`
引用它，批次内 N 台车通过 `collateral_registration_items` 共享这一个引用。
**不为每台车复制一份文件**——既不产生 N 倍存储成本，也不会出现"同一份合同的 N 个副本内容不一致"。

单车的查法固定为：
```
vehicle_units.vin → vehicle_units.registration_no           （直接读，快）
vehicle_units.vin → collateral_registration_items.vin
                 → batch_id → collateral_registration_batches → contract_attachment_id
                 → attachments.object_key                   （联查拿合同文件）
```

**冗余字段的一致性怎么保证**：登记编号只在一个地方产生（批次登记成功时），
写入批次的同时按 `items` 回刷 `vehicle_units.registration_no`，放在**同一事务**内。
由于登记编号不可变，不存在"后续被改而忘记同步"的场景；
若将来支持登记变更，则必须走同一个回刷函数，不得散落更新。

**由此确定后台的操作单元是"批次"而非"车辆"**：业务人员在后台新建（或打开）一个登记批次，
框选这一批车，然后**一次**上传合同文件、填合同编号与法务局登记编号——
这一份文件与编号随即对批次内所有台账生效。绝不做成在车辆详情页逐台上传。

车辆框选需支持三种来源（否则几十台车要手输 VIN，不可接受）：

| 来源 | 入参 | 适用场景 |
|---|---|---|
| 按采购订单整单加入 | `purchaseOrderId` | 最常用——同一采购订单的车天然是"一批" |
| 按经销商 + 状态筛选加入 | `dealerId` + `statuses`（通常是 `PENDING_ADVANCE`） | 补登记、漏登记的车 |
| 手动指定 VIN 列表 | `vins[]` | 跨订单拼批、特殊调整 |

三种来源可混用（一次请求里同时传），服务端去重后写入 `collateral_registration_items`。

### 决策 2：放款门槛 = 该 VIN 至少存在一个"三要素齐备"的批次

| 要素 | 字段 | 是否强制 |
|---|---|---|
| 合同编号 | `contract_no` | **必须** |
| 合同文件（S3） | `contract_attachment_id` | **必须** |
| 法务局登记编号 | `registration_no` | **必须** |
| 登记事项证明书 | `certificate_attachment_id` + `certificate_no` | 建议，不阻断 |

**为什么证明书不强制**：登记完成后即可取得登记编号，而登记事项证明书是纸质凭证，
实务上可能晚数日才能拿到并扫描上传。若把它设为硬门槛，会误伤正常业务。
它作为"证据链完整性"的提示项，在 `/api/collateral/evidence-gaps` 里持续暴露缺口即可。

**为什么编号与文件都强制**：合同是担保权成立的**实体依据**，登记是**对抗要件**。
只有编号没有文件，出了纠纷拿不出正本；只有文件没有编号，对第三人不生效。两者缺一不可。

### 决策 3：靠"登记时补建台账"解开时序死锁

在 `registerCollateralBatch` 中，对批次内每台车调用 `loadOrCreate(vin, dealerId)`
取得（或新建）`collateral_ledger`，再写 `collateral_registration_items`。

这样记账顺序变为：**申请垫款 → 签合同 → 法务局登记（此时台账占位已建）→ 上传 → 放款**，
与业务实际顺序一致。新建出来的台账 `financed=false`、`security_status` 保持待登记态，
放款确认时由 `markFinanced` 激活——不改动 `markFinanced` 的既有语义。

### 决策 4：一台车可能属于多个批次，判定用"任一齐备"而非"全部齐备"

存在同一台车被分批登记、或补登记的情形。只要**存在任意一个**批次满足三要素即视为放行；
若只有部分批次齐备，应放行并在响应里提示"另有 N 个批次未补齐"，而不是拒绝。

### 决策 5：文件必须走 S3，且开启 Object Lock

生产环境必须配置环境变量 `ATTACHMENTS_S3_BUCKET`。
当前 `application.yml` 中 `s3.bucket: ${ATTACHMENTS_S3_BUCKET:}` 默认为空，
会回退到 `LocalAttachmentStorage`——本地磁盘**没有** Object Lock 的"不可删改"强保证，
合同这类法律凭证不允许落在本地。这是上线前必须确认的配置项。

| `GET /api/advances/{advanceNo}/readiness` | 放款就绪度：是否放行 + 缺哪几项 + 依据批次 | `ADVANCE_DISBURSE` 等 |

批量追加车辆的入参（三种来源可混用，服务端去重）：
```json
{
  "purchaseOrderId": 1234,
  "dealerId": 56,
  "statuses": ["PENDING_ADVANCE"],
  "vins": ["VIN1", "VIN2"]
}
```
返回 `{ "added": 12, "skipped": 1, "skippedVins": ["VIN3"] }`——
`skipped` 表示已在本批次中（唯一约束 `(batch_id, vin)` 命中）或车辆不存在，
必须逐条回传，否则业务人员不知道自己漏了哪台。

**待登记工作台是刚需**：因为放款是单台的，资金岗会在不同时点对同一批车逐台点击放款。
如果没有一个"这批车还差几台没登记"的清单，就会出现
"以为整批都登记好了，结果点某台车时才发现它没被框进批次"——
这个清单就是放款前的查漏入口。

`readiness` 返回结构（建议）：
```json
{
  "ready": false,
  "missing": ["CONTRACT_FILE", "REGISTRATION_NO"],
  "matchedBatch": null,
  "batches": [
    { "batchNo": "CRB-XXXX", "contractNo": "CT-017527",
      "hasContractFile": false, "registrationNo": null, "hasCertificate": false }
  ],
  "hint": "请先与经销商签订垫付合同并上传 S3，再到法务局办理登记取得登记编号"
}
```

## 五、实现任务清单（供后续编码）

1. **领域层**：新增 `AdvanceReadiness` 值对象（`ready` / `missing` / 命中批次），
   以及 `DisbursementRequirement` 判定逻辑（三要素）。
2. **领域层**：`CollateralRegistrationBatch` 增加 `isDisbursementReady()` 判定方法，
   把"什么叫齐备"收敛到一处，避免规则散落。
3. **应用层**：`CollateralLedgerApplicationService` 新增
   `attachContract(batchId, attachmentId, contractNo, signedAt, actor)`、
   `attachCertificate(batchId, attachmentId, certificateNo, actor)`、
   `addVehicles(batchId, VehicleSelection, actor)`（`VehicleSelection`
   同时容纳 `purchaseOrderId` / `dealerId+statuses` / `vins`，服务端解析并去重）。
4. **应用层**：`registerCollateralBatch` 内改为 `loadOrCreate` 台账（解决时序）；
   创建批次时同样支持上述三种车辆来源。
5. **应用层**：新增放款就绪度查询与**待登记工作台**查询用例；
   `disburseAdvance` 插入门槛校验。
6. **接口层**：新增上表 6 个端点。
7. **前端后台页面**（用户明确要求"后台需要"）：新建"担保登记批次"管理页，
   含 ① 批次列表 ② 新建/编辑批次（框选车辆：按采购订单 / 按经销商+状态 / 手输 VIN）
   ③ 上传合同与填写登记编号 ④ 补传证明书 ⑤ 待登记车辆清单 ⑥ 批次内车辆明细。
   注：现前端 `static/js/` 下**没有**担保相关页面，属新增。
8. **迁移脚本 V15**：`vehicle_units` 增加 `registration_no VARCHAR(64)` 冗余列
   （口径同 `collateral_registration_batches.registration_no`），
   建索引 `idx_vu_registration_no` 以支持按登记编号反查一批车。
   迁移内**回填存量**：按 `collateral_registration_items` 把已有批次的登记编号刷到对应台账；
   一台车命中多个批次时取最新批次（`b.id` 最大）的编号，并把冲突 VIN 打印出来供人工确认。
   如需批次状态字段（`DRAFT` / `REGISTERED`）一并在 V15 加；
   否则可用 `registration_no IS NOT NULL` 表达"已登记"。
9. **数据清理**：处理每个 VIN 的 `R-EMPTY-*` 空批次（测试脏数据），
   否则回填时同一台车会命中两个批次、编号取错。
10. **验收**：冒烟脚本新增"缺合同被拒 → 统一上传合同 → 有合同无登记仍被拒 →
    补登记编号 → 放款放行"的完整链路断言；
    另加"一次上传覆盖 N 台台账"的批量断言（建批次框选 3 台车 → 3 台均放行、
    且 3 台台账的 `registration_no` 均等于该批次编号、合同文件在 `attachments` 里只有 1 行）。

## 六、风险与待确认问题

| # | 问题 | 需要谁定 |
|---|---|---|
| 1 | 一台车被多个批次覆盖、且只有一个批次齐备时，放行还是要求全部齐备？本设计暂定"任一齐备即放行并提示" | 业务 + 风控 |
| 2 | 登记事项证明书是否也要作为硬门槛？本设计暂定为"建议项" | 风控 |
| 3 | 存量 18 个批次（附件全空）是补录还是重建？这些车多数已放款，历史数据无法回到"放款前补齐"状态 | 业务 |
| 4 | `ATTACHMENTS_S3_BUCKET` 生产值、Object Lock 模式（COMPLIANCE 还是 GOVERNANCE）与保留年限 | 运维 + 合规 |
| 5 | 合同重签/补充协议时，是否保留旧版本文件（建议保留，靠 `attachments` 多行 + 版本号区分） | 法务 |
| 6 | **登记编号冗余到台账后的一致性**：目前靠"登记时同事务回刷"保证。若将来支持登记变更/移批，必须复用同一回刷函数，不得散落更新。是否需要加一个对账作业定期校验 `vehicle_units.registration_no` 与批次一致？ | 架构 |
| 7 | 一台车被多个批次覆盖时，台账上冗余的那个编号取哪个？本设计暂定"最新批次"，但业务上可能应以"实际生效的对抗要件"为准 | 风控 |

## 七、一句话总结

**表已经有了，缺的是"放款前校验"这道闸，以及"登记可以早于放款"这个时序修正。**
核心改动量不大，但它是资金出口的最后一道防线——目前资金岗可以在没有任何担保文件的情况下放款。

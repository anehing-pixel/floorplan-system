## 1. 通用约定

| 项 | 规则 |
|---|---|
| 协议 | REST / JSON。**统一入口为网关 `http://127.0.0.1:18080`**，按 URL 路径切到各服务；端口 8080~8084 仅本地直连用 |
| 认证 | Bearer Token（JWT）；登录走 `POST /api/auth/login` 由 auth-service 签发，五个服务用同一密钥本地验签，**网关不验签**（详见登录认证指南 §15） |
| 请求头 | `Authorization: Bearer <token>`（必填）、`Idempotency-Key: <key>`（写接口必填）、`X-Trace-Id`（可选，链路追踪）、`X-Operator-Id`（**已降级为兜底**，审计操作人以令牌身份为准，见登录指南 §14） |
| 金额 | **整数日元**，JSON 中以数字（long）传递，**禁止小数与浮点** |
| 比率 | 以数字传递（如 `0.9000`），服务端按定点处理，落到金额量化为整数日元 |
| 时区 | 统一 **JST**；日期格式 `YYYY-MM-DD`，时间 `YYYY-MM-DDTHH:mm:ss+09:00` |
| 业务日 | 计息/结算以**营业日**为准，节假日表内置 |
| 幂等 | 写接口必须带 `Idempotency-Key`；重复请求返回首次结果，不重复执行 |
| 分页 | `page`（从 0 起）、`size`（默认 20）；响应含 `total`、`totalPages` |

**统一响应结构**

```json
// 成功
{ "code": "OK", "data": { ... }, "traceId": "..." }
// 失败
{ "code": "CREDIT_001", "message": "可用额度不足", "traceId": "...", "details": { "available": 3350000, "required": 4000000 } }
```

### 1.1 端点归属服务（2026-11-20 微服务化）

**URL 路径对客户端完全不变**，但请求经网关 18080 按路径切到不同服务。联调排障时要知道端点落在哪个服务：

| 路径前缀 | 归属服务 | 端口 | 说明 |
|---|---|---|---|
| `/api/auth/**` | auth-service | 8081 | 登录、签发 token（唯一免令牌接口 `/api/auth/login`） |
| `/api/dealers/**`、`/api/credit-lines/**`、`/api/rating-configs/**`、`/api/annual-reviews/**` | credit-service | 8083 | 授信域 |
| `/api/alerts`、`/api/risk/**`、`/api/disposals/**`、`/api/collaterals/**` | risk-service | 8084 | 风控域 |
| `/api/vehicles/{vin}/lien-check` | risk-service | 8084 | 权属核对（**精确路由，优先于下面 web 的 vehicles**） |
| `/api/jobs/bank-fetch` | bank-service | 8082 | 银行回款采集（**精确路由，优先于下面 web 的 jobs**） |
| 其余 `/api/**`（垫款 `/api/advances`、还款 `/api/repayments`、计息、车辆台账、采购单、大部分 `/api/jobs/*`） | web | 8080 | 核心账务，有状态写，事务红线，**未拆** |

> **路由"精确优先"**：网关是首个匹配即命中，所以 `/api/vehicles/{vin}/lien-check` 必须排在
> `/api/vehicles/**` 之前，`/api/jobs/bank-fetch` 必须排在 `/api/jobs/**` 之前——
> 否则会被宽泛规则先吃掉，错投到 web。这两条正是从 web 混合 Controller 里精准摘出来的方法。

### 2.1 已实现的角色边界（RBAC：角色 → 权限点）

**授权模型**：接口声明所需**权限点**（`@RequirePermission`），
用户持有的**角色**各自对应一组权限点，任一角色覆盖全部所需权限点即放行。
读接口不设权限点——所有已登录用户开放。

**三道关卡**：

| 情形 | HTTP | 错误码 | 语义 |
|---|---|---|---|
| 未带令牌 / 令牌失效 / 签名不合法 | 401 | `AUTH_001` | 认证失败——"你是谁"没通过 |
| 令牌有效但权限点不足 | 403 | `AUTH_002` | 授权失败——"你是谁"通过了，但"你能做这件事"没通过 |
| 同一笔业务由同一人自办自批 | 403 | `AUTH_003` | 职责分离——申请人 ≠ 复核人 ≠ 支付人 |

**为什么管理员不碰业务单据**：`SYSTEM_ADMIN` 刻意不持垫款申请/复核/支付、还款核销、处置等权限点。
管理员万能则"双人复核"形同虚设——一个人拿管理员账号就能把两道关都过了。
管理员的操作全部进审计表，事后可查，但**不能**替业务岗审批或放款。

**读为什么不收口**：风控岗要看经销商档案才能判断预警、催收岗要看车辆台账才能跟进。
把读也收口会让"越权"变成"业务干不了活"，这不是控制，是障碍。

**职责分离的两层机制**：
① **角色层**（配置时）——不相容岗位组合给告警提示（如录入岗 × 审核岗）；
② **自然人层**（运行时）——同一笔业务由同一人发起并复核/支付，一律 403 `AUTH_003`。
第二层是硬约束：一人多岗时角色可能相同，但**人必须不同**。

> 实现要点：授权由方法级注解 `@RequirePermission(Permission.XXX)` 声明（不是路径白名单），
> 拦截器通过 `HandlerMethod.getMethodAnnotation()` 判定，令牌携带登录时算好的权限点集合。
> 路径白名单会随接口增加而漏配；注解跟着方法走，改 URL 不会漏鉴权。
> 详见《角色与权限矩阵》第 5 章与《登录认证开发指南》第 4 章。

## 3. 错误码字典

| 码 | HTTP | 含义 | 处理建议 |
|---|---|---|---|
| `AUTH_001` | 401 | 未认证 / Token 失效 | 重新登录 |
| `AUTH_002` | 403 | 无该操作权限 | 检查角色 |
| `AUTH_003` | 403 | 违反发起/执行分离（同一人） | 换人操作 |
| `VALID_001` | 400 | 参数校验失败 | 见 `details` |
| `VALID_002` | 400 | 金额非法（小数/负数/超范围） | 传整数日元 |
| `NOT_FOUND_001` | 404 | 资源不存在 | |
| `CONFLICT_001` | 409 | 幂等键冲突（请求体不同） | 换 Key 或核对原请求 |
| `CREDIT_001` | 422 | **可用额度不足** | 见 `details.available` |
| `CREDIT_002` | 422 | 额度已冻结 | 需先解冻 |
| `VEHICLE_001` | 404 | 车辆（VIN）不存在 | |
| `VEHICLE_002` | 422 | **状态非法流转** | 见 `details.currentStatus` |
| `VEHICLE_003` | 409 | VIN 已存在（重复建账） | |
| `VEHICLE_004` | 422 | 担保类型不支持（默认支持 RETENTION/ASSIGNMENT/OTHER/NONE） | |
| `ADVANCE_001` | 422 | 垫款比例超限（默认上限 100%，yml 可调） | |
| `ADVANCE_002` | 502 | 付款通道失败 | 可重试 / 转人工 |
| `REPAY_001` | 422 | 还款金额不匹配（本金+利息） | 见 `details.expected` |
| `REPAY_002` | 422 | 该台已结清 | |
| `SECURITY_001` | 422 | 担保登记信息不完整 | |
| `VEHICLE_005` | 422 | **重复融资拦截**：该车在他处存在抵押/查封，禁止再次融资（P0-③，数据源 `financing_lien_checks`） | 见 `details.vin/note/source` |
| `CURTAIL_001` | 422 | 该车无进行中的库龄递减还款计划（P0-①） | |
| `DISPOSAL_001` | 409 | 该车已有未结案的处置工单 | |
| `DISPOSAL_002` | 422 | 处置工单状态非法流转 | |
| `DISPOSAL_003` | 404 | 处置工单不存在 | |
| `INSURANCE_001` | 404 | 保险单不存在 | |
| `REPURCHASE_001` | 404 | 厂家回购请求不存在 | |
| `EXTENSION_001` | 404 | 展期请求不存在 | |
| `PAYOFF_001` | 422 | 仅整台结清车辆可出具结清证明 | |
| `ANNUAL_REVIEW_001` | 404 | 年审任务不存在 | |
| `RATING_001` | 422 | 评级口径未配置或已停用，不准入新业务 | 先在 `PUT /api/rating-configs/{grade}` 维护口径 |
| `DEALER_001` | 422 | **经销商名下存在车辆或授信额度，禁止物理删除** | 改为将状态置为「终止合作」（TERMINATED） |
| `DEALER_002` | 422 | 经销商状态流转非法（终止后不可回退） | 见 `details.currentStatus/targetStatus` |
| `SYS_001` | 500 | 系统内部错误 | 凭 `traceId` 排查 |

> **`DEALER_001` 是金融数据护栏，不是缺陷**：经销商是授信台账的主体，
> 物理删除会让历史车辆台账与额度流水失去归属主体、断掉审计链。
> 有业务往来的经销商应当**终止合作**（状态置 TERMINATED）而非抹掉记录——
> 记录仍在，审计链完整，查询与报表不受影响。

> **超出结算窗口**不再使用独立错误码：贴合日本实务实现为"告警但允许"——
> 宽限期（预设 5 个营业日）内仅发 MEDIUM 告警（`SETTLE_GRACE`）不改状态；
> 超宽限期升级 OOT 嫌疑、车辆转 OVERDUE（HIGH 告警），由 `POST /api/jobs/settlement-scan` 驱动。

## 4. 接口详述

### 4.1 POST /api/dealers — 创建经销商

```json
// 请求
{ "dealerCode": "DL-000123", "name": "○○自動車販売株式会社",
  "status": "ACTIVE", "riskGrade": "B", "businessYears": 12 }
// 响应 201
{ "code": "OK", "data": { "id": 10023, "dealerCode": "DL-000123", "status": "ACTIVE" } }
```

### 4.2 POST /api/credit-lines — 核定/调整额度（需审批）

```json
// 请求（发起）
{ "dealerId": 10023, "approvedLimit": 50000000, "reason": "年度复核上调" }
// 响应 201（草稿，待审批）
{ "code": "OK", "data": { "id": "CL-100023", "status": "PENDING_APPROVAL", "approvedLimit": 50000000 } }
// 审批通过后：status → ACTIVE；审批动作由另一角色执行（AUTH_003）
```

**校验**：`approvedLimit` 必须为正整数；调整后 `usedAmount <= approvedLimit`，否则 `CREDIT_001`。

### 4.3 POST /api/vehicles/batch-ingest — 批量到货建账

```json
// 请求
{ "dealerId": 10023, "creditLineId": "CL-100023", "purchaseChannel": "OEM",
  "supplierName": "○○自動車",
  "vehicles": [
    { "vin": "JMA***********1", "brand": "...", "model": "...", "modelYear": 2026,
      "invoiceAmount": 1850000, "advanceRatio": 0.9 },
    { "vin": "JMA***********2", "invoiceAmount": 2400000, "advanceRatio": 0.9 }
  ],
  "idempotencyKey": "ingest-20261025-0001" }
// 响应 201
{ "code": "OK", "data": { "accepted": 2, "rejected": 0,
  "results": [ { "vin": "...1", "status": "CREATED" }, { "vin": "...2", "status": "CREATED" } ] } }
```

### 4.4 POST /api/advances — 申请垫款（核心）

```json
// 请求
{ "creditLineId": "CL-100023", "vin": "JMA***********1",
  "purchaseOrderId": 8801,
  "manufacturerInvoiceAmount": 1850000, "advanceRatio": 0.9,
  "idempotencyKey": "adv-20261025-0001" }
// 响应 201
{ "code": "OK", "data": {
  "advanceId": "ADV-558201", "status": "PENDING",
  "advancedAmount": 1665000, "remainingCredit": 3350000,
  "vehicleStatus": "FINANCED" } }
```

**三段式状态机（ADR-006 已落地，勿回退）**

```
POST /api/advances                  → PENDING    （申请人=操作员 USER，仅申请+占额度，不调网关）
POST /api/advances/{no}/disburse    → PROCESSING （放款人=资金岗 ADMIN @RequireAdmin，提交支付通道）
POST /api/advances/{no}/confirm     → PAID       （银行 webhook，HMAC 签名鉴权）
POST /api/advances/{no}/fail        → FAILED     （银行 webhook，HMAC 签名鉴权）
```

> **职责分离（SOD）**：申请 ≠ 放款。`applyAdvance` 只落 PENDING、占额度，**绝不调支付网关**；
> 放款由资金岗执行，且 `@RequireAdmin` 拦截——操作员自调返回 403 `AUTH_002`。
> `/confirm`、`/fail` 已从 JWT 拦截器排除，只接受 **HMAC 签名**（`PaymentWebhookVerifier`），
> 内部用户（含 ADMIN）一律 401 `PAYMENT_001`——堵死"自己申请自己确认放款"的欺诈路径。

**收款方（ADR-007 提案（最终版），尚未实现）**：放款指令将携带收款方（`payee_supplier_id` / `payee_supplier_type` / `payee_account_snapshot`），
由关联的**采购订单** `purchase_orders.supplier_type` 派生打款模式（`DIRECT_PAY` 代付上游 / `SELF_PAY` 回款经销商），
放款前按两套校验链分别断言（ADR-007 决策五）。

**错误**：`CREDIT_001`（额度不足）、`VEHICLE_002`（状态不允许垫款）、`ADVANCE_002`（付款通道失败）、`ADVANCE_003`（垫款状态非法）。


| 字段语义 | 传参 | 效果 |
|---|---|---|
| 不修改 | `null` / 不传 | 保持原值 |
| 清空 | `""`（空串） | 置为 `null` |
| 修改 | 非空值 | 覆盖原值 |

> 后端用 `blankToNull()` 做归一：**空串 = 清空**是刻意的语义，
> 否则前端无法表达"把这个联系方式清掉"——传 null 会被理解成"不改"。

**状态机**（`DealerStatus.canTransitTo()` 白名单）：

| 当前 | 可流转到 | 不可流转到 |
|---|---|---|
| `ACTIVE`（正常经营） | `SUSPENDED`、`TERMINATED` | — |
| `SUSPENDED`（暂停合作） | `ACTIVE`、`TERMINATED` | — |
| `TERMINATED`（终止合作） | —（**终态，不可回退**） | 任何状态 → `DEALER_002` |

非法流转 → 422 `DEALER_002`，`details` 含 `currentStatus` / `targetStatus` / `reason`。

**校验**：编号唯一（**排除自身**——拿自己的编号提交不算重复）；评级口径有效；状态流转合法。

**审计**：写 `audit_events`（`UPDATE_DEALER`），含操作人、前值快照、后值快照。

**4.15.4 DELETE /api/dealers/{id} — 删除（带引用完整性护栏）**

```json
// 有业务往来时

  "message": "经销商名下存在车辆或授信额度，禁止删除",
```

```json
{ "code": "OK", "data": {
  "dealer": { "id": 207, "dealerCode": "DL-SMOKE-001", "name": "冒烟测试经销商", ... },
  "summary": {

    "avgAgingDays": 42, "maxAgingDays": 88,

  },

```

**汇总口径**：`summary` 的四项金额（采购/垫款/本金余额/已还本金）**等于 `vehicles` 明细逐行求和**，

| `totalPaidPrincipal` | 已还本金合计 |
| `approvedLimit` / `usedAmount` / `frozenAmount` | 名下授信额度总额 / 已用 / 已冻结 |

### 4.16 采购订单与收款方（ADR-007 提案（最终版），⚠️ 尚未实现）

> 本节是**提案态契约**，供评审用。ADR-007（最终版） 明确：打款对象由**采购订单**决定，
> 采购订单是融资放款的**前置主单**，不是"一个待解析的文本文件"。
> **两条导入通道**（API 直连 / Excel·CSV 批量导入）产出**同一份主单**，下游无感知。

#### 4.16.1 POST /api/purchase-orders/import — Excel/CSV 批量导入

```
Content-Type: multipart/form-data
file: 采购清单.xlsx（固定模板）
mode: preview | commit
```

**模板列（与业务确认的清单关键字段一一对应）**：

| 列名 | 必填 | 说明 |
|---|---|---|
| `orderNo` 采购订单号 | ✅ | **幂等锚点**，唯一 |
| `vin` 车架号 | ✅ | 唯一性校验 + **VIN 幂等**（防两单报同一台车） |
| `model` 车型 | ✅ | |
| `modelYear` 年款 | ✅ | |
| `color` 颜色 | ✅ | |
| `supplierType` 供应商类型 | ✅ | `MAKER_SALES_CO`/`REGIONAL_AGENCY`/`WHOLESALER`/`AUCTION`/`USED_WHOLESALER`/`DEALER_SELF`（**决定打款模式**） |
| `invoiceAmount` 采购金额 | ✅ | 与垫款比例上限交叉校验 |
| `payeeAccountRef` 收款账户 | ✅ | **只填业务引用码，系统按引用查账户主数据；不接受明文账号** |
| `vehicleStatus` 车辆状态 | ✅ | 在途 / 在库 / 已质押 / 已解押（**业务侧口径**，落库时映射到领域枚举，见 ADR-007 决策九） |
| `evidenceNo` 契约/発注書号 | | 单据编号 |
| `attachmentId` 附件 ID | | 已在 §4.17 上传完成的凭证附件 |

- `mode=preview`：只校验不落库，返回「将建 N 台 / 拒绝 M 台 / 金额合计」+ **行级错误明细**（行号 + 字段 + 原因），可下载修正后重传；
- `mode=commit`：ADMIN 确认后落库；
- **列头不符直接拒绝整个文件**（不逐行猜测）；
- **幂等**：`orderNo` 唯一，重复导入返回首次结果，不重复建账；
- **审计留痕**：操作人、通道、文件名、文件哈希、行数、成功/失败数。

#### 4.16.2 POST /external/purchase-orders — API 直连（上游系统推送）

```
POST /external/purchase-orders
Headers: X-Signature: HMAC-SHA256(...)   # 与现有 /external/** 同一套签名校验
```

```json
// 请求
{ "orderNo": "PO-20261026-001", "dealerId": 10023, "creditLineId": "CL-100023",
  "supplierType": "REGIONAL_AGENCY", "supplierId": 42,
  "payeeAccountRef": "ACC-KY-001",
  "evidenceNo": "CT-2026-1026", "attachmentId": 8801,
  "purchasedAt": "2026-10-26",
  "vehicles": [ { "vin": "JMA***********1", "model": "AQUA", "modelYear": 2026,
                  "color": "WHITE", "invoiceAmount": 1850000,
                  "vehicleStatus": "在途" } ] }
// 响应 201
{ "code": "OK", "data": { "purchaseOrderId": 8801, "orderNo": "PO-20261026-001",
  "status": "CONFIRMED", "accepted": 10, "rejected": 0 } }
```

**与 Excel 通道的差异（ADR-007 决策四 4.3）**：

| | Excel 通道 | API 通道 |
|---|---|---|
| 落库前人工确认 | **必须**（`preview` → `commit`） | **可豁免**（数据源可信、有契约保证；可配置强制复核） |
| 校验结果 | 确定性（对/错 + 原因） | 同 |
| 幂等 | `orderNo` 唯一 | 同（重推返回首次结果） |
| 附件 | 随文件带 `attachmentId` | 上游给 `attachmentId` 或 `objectKey`；不提供原件时标注"无附件" |

#### 4.16.3 GET /api/purchase-orders/{orderNo} — 主单查询

返回采购订单主单 + 车辆清单 + 收款账户**掩码**（不返明文账号）+ 附件预签名 GET URL（短时效）。

#### 4.16.4 放款前校验分叉（ADR-007 决策五）

`supplier_type` 派生打款模式，**两套校验链各自断言**：

| | `DIRECT_PAY`（代付上游） | `SELF_PAY`（回款经销商） |
|---|---|---|
| 适用 supplier_type | MAKER_SALES_CO / REGIONAL_AGENCY / WHOLESALER / AUCTION / USED_WHOLESALER | DEALER_SELF |
| 三方委托付款协议 | ✅ 必需（已生效、未过期、覆盖本单、金额不超授权上限） | ❌ 不适用 |
| 收款账户 | 上游账户（ACTIVE、非冻结、已过冷静期） | 经销商结算账户（**变更管控更严**，T+2 + 双签） |
| 库存实物核验 | ❌ 不要求（钱付上游与车是否在手无关） | ✅ **要求**：提款对应库存已盘点在库 |
| 估值口径 | 采购价 × 垫款比例上限 | **库存估值（按采购价，不按零售价）× 独立抵押率上限** |
| 审计标注 | 代付上游 | **额外标注"非代付、属营运资金"** |

> **v1 错误警示**：v1 把「三方委托付款协议已生效」设为全局放款硬校验，
> 这在 `SELF_PAY` 场景下会把业务**直接堵死**。两套校验链必须分开实现。

#### 4.16.5 打款模式不可人工覆盖

打款模式是 `supplier_type` 的**派生值**，不落库为独立可编辑字段。
否则"选 `DEALER_SELF` 就绕开代付协议"将成为一个漏洞。
人工可改 `supplier_type`（有审核流），但不能直接改打款模式。

### 4.17 附件（原始凭证存 S3，ADR-007 决策十）⚠️ 尚未实现

> 原始凭证（合同·発注書·請求書·图片·PDF）存 **Amazon S3**，**数据库只存元数据**。
> **预签名 URL 直传，应用不过流**——文件不经过 JVM 堆与临时目录。

#### 4.17.1 POST /api/attachments/presign — 申请上传授权

```json
// 请求
{ "bizType": "PURCHASE_ORDER", "bizId": 8801,
  "filename": "采购契约_20261026.pdf", "contentType": "application/pdf",
  "contentLength": 2481920 }
// 响应 200
{ "code": "OK", "data": {
  "uploadUrl": "https://bucket.s3.ap-northeast-1.amazonaws.com/po/2026/10/<uuid>.pdf?X-Amz-...",
  "objectKey": "po/2026/10/<uuid>.pdf",
  "expiresInSeconds": 900 } }
```

**约束**（签名参数里锁定，防"授权 A 传 B"）：
- 预签名 URL **限定单对象 key + Content-Type + Content-Length**，**15 分钟时效**；
- 对象键用 **UUID/哈希**，不用原始文件名（文件名含客户名/车架号会泄露，且可能冲突）；
- 类型白名单：`application/pdf` / `image/jpeg` / `image/png` / `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` / `text/csv`；
- 单文件大小上限；**附件不落地为可执行文件**。

#### 4.17.2 POST /api/attachments/complete — 上传完成登记

```json
// 请求
{ "objectKey": "po/2026/10/<uuid>.pdf", "etag": "\"d41d8cd98f00b204e9800998ecf8427e\"",
  "sha256": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08" }
// 响应 200
{ "code": "OK", "data": { "attachmentId": 8801, "objectLockMode": "COMPLIANCE" } }
```

**服务端必须回读 S3 对象元数据校验**（`ContentLength`/`ContentType`/`ETag` 与申请值比对），不一致则拒绝登记——否则会出现"上传了 A 却登记了 B"。**校验 ETag/MD5** 防内容被替换。

#### 4.17.3 GET /api/attachments/{id}/url — 获取访问链接

返回**短时效预签名 GET URL**（默认 5 分钟）。
**库里不存永久公开链接，桶不公开读**——附件访问一律经应用签发。

#### 4.17.4 不可变与审计

- 凭证类附件在 S3 侧启用 **Object Lock `COMPLIANCE`**（存储层强制"一次写入、不可删改"）+ **Versioning** + **MFA Delete**；
- 应用 IAM 权限**禁止 `DeleteObject`**；登记后不可删除，只能追加新版本（"补充件"）；
- 上传写审计：操作人、biz 目标、文件名、大小、内容指纹、上传时间。

## 5. 幂等语义表

| 接口 | 幂等键作用域 | 重复请求行为 |
|---|---|---|
| `advances` | 全局唯一 | 返回首次结果；键相同但请求体不同 → `CONFLICT_001` |
| `repayments` | 全局唯一 | 同上 |
| `batch-ingest` | 全局唯一 | 返回首次处理结果（含 accepted/rejected） |
| `sold` | vin + 键 | 已售出再提交 → 返回当前状态（不报错） |
| `security` / `security/release` | vin + 键 | 返回当前担保状态 |
| `interest/settle` | bizDate | 已成功则直接返回历史 `batchRunId` |
| `freeze` | creditLine + 键 | 返回当前冻结状态 |

> 幂等键建议由客户端生成（业务语义 + 日期 + 序号），并在 `advances.idempotency_key`、`repayments.idempotency_key` 上建**唯一索引**作数据库层兜底。

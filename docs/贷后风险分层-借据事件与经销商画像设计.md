# 贷后风险数据分层设计：借据 · 事件 · 经销商画像 + DPD 规则中心

> 文档状态：**待实现**（只做设计，不动代码）
> 撰写日期：2026-10-26
> 对应迁移：**V16**（V15 已预留给"台账冗余登记编号"，本设计顺延）
> 上游依据：ADR-008《逾期状态归属借据实体》（已定借据层，本设计是其**补充与修订**，非推翻）

---

## 0. 一句话结论

**扣款失败、逾期、违约的"当前状态"挂在借据表上，过程记在事件表里；经销商画像表只放聚合出来的指标，不参与任何流程判定。**

三者构成一条**单向依赖链**，写入必须从「事实流水」流向「画像」，不可反向：

```
┌────────────────────────────────────────────────────────────────┐
│ ① 事实流水层（append-only，不可变、可追溯）                      │
│    deduction_failures   扣款失败明细                            │
│    overdue_records      逾期记录（跨 M1→M2→M3 是同一条）         │
│    default_events       违约认定/解除事件                        │
│    loan_status_history  借据状态跃迁留痕                         │
└───────────────────────────┬────────────────────────────────────┘
                            │ 同一事务回写「当前状态」
                            ▼
┌────────────────────────────────────────────────────────────────┐
│ ② 借据当前状态层 loans ← 贷后流程的【唯一】读依赖                │
│    status / current_dpd / deduction_fail_streak / default_flag  │
│    单行 O(1) 判断：能否放款、能否冻结、能否处置                   │
└───────────────────────────┬────────────────────────────────────┘
                            │ 异步聚合（可延迟 / 可重算 / 可失败）
                            ▼
┌────────────────────────────────────────────────────────────────┐
│ ③ 经销商画像层 dealer_risk_profiles ← 只服务分层与报表           │
│    current_overdue_count / max_overdue_days / defaults_12m     │
│    risk_tier A/B/C/D                                            │
└────────────────────────────────────────────────────────────────┘
```

**这条依赖链正是"不影响贷后流程执行"的技术实现方式**——画像是链尾的只读投影，
它算错、算慢、甚至整个表没跑起来，第 ② 层照样能判定，流程一条不断。

### 1.3 ⚠️ 一个容易搞错的点：`risk_grade` 不是画像指标

查证 `dealers.risk_grade` 的真实用途：

```java
// AdvanceApplicationService.java:137-140
String riskGrade = dealer.getRiskGrade();
ratingConfigService.requireAllowed(riskGrade);                        // 准入闸门
BigDecimal effectiveAnnualRate = defaultAnnualRate
        .add(ratingConfigService.resolveSurcharge(riskGrade));        // 利率加价
```

**它是"授信评级"，直接影响能不能贷、利率多少，锚定 `rating_configs`，由人工评定。**
它与"贷后违约了几次"是两回事，**必须留在 `dealers`**，不能迁走。

因此画像表里的 `risk_tier` 是一套**全新的、由贷后数据算出来的分层**，
与 `risk_grade` 并存。二者关系见 §6.2 的决策点。

### 1.4 缺口清单（本次要补的）

1. **无扣款失败载体**——ADR-008 只讲"到期未足额"，没讲自动扣款的失败与重试。
2. **无违约事件表**——ADR-008 只有 `loans.status='DEFAULTED'` 这个终态，没有认定/解除的事件流水。
3. **无经销商画像**——完全空白，`max_overdue_days` / `defaults_last_12m` 这类口径无从谈起。
4. **DPD 与 M 系列写死在文档注释里**——ADR-008 §2.6 把 `M1≥31 / M2≥61 / M3≥91` 写死，
   且 §4 待确认第 5 项"自然日 vs 营业日"悬而未决（正是你这次要求解決的）。
5. **期限字段所有权冲突**——V11 把它挂在 `vehicle_units`，ADR-008 已裁定"期限属于借据"。

## 2. 分层原则：为什么画像表不能进流程

### 2.1 三条铁律

| # | 铁律 | 违反后果 |
|---|---|---|
| 1 | **贷后流程只读 `loans`，禁止读 `dealer_risk_profiles`** | 画像一旦成为判据，它的延迟/算错会直接变成"错误放款"或"错误冻结" |
| 2 | 画像只能是右端投影，**不得反向写入 `loans`** | 双向依赖后，数据不一致时无法判断谁对，且可能循环 |
| 3 | 画像必须**可全量重算**且带 `data_as_of` | 没有数据截止时点，报表口径永远说不清，历史对比全是错的 |

### 2.2 为什么"当前状态"必须冗余在借据上

你可能会问：为什么不能在流程里实时聚合事件表？

因为贷后流程里有三类判断是**高频且 Must-be-fast** 的：

- 放款拦截：经销商名下有正在逾期的债 → 拒绝这笔垫款
- 新车入库：该车所属经销商是否被冻结 
- 处置触发：这台车的逾期是否够格进法务

这些都是**单行 O(1) 判断**。若每次实时 `SUM/MAX` 三张流水表，单次请求要扫 N 条。
把结论物化到 `loans` 一行上，判断就是在读一个对象字段。

**代价**（必须说清）：当前状态是**冗余数据**，有两个来源写就会有不一致。
解法是单一写入点——事件流水落库后，**同一事务**回写 `loans` 的状态字段，
外部严禁直接 `UPDATE loans.status`。这与 ADR-008 §2.7 "派生字段单一写入点"是同一条纪律。

## 3. 表设计（V16）

### 3.1 `loans` 借据表 —— 当前状态载体

在 ADR-008 定义的基础上，**补充扣款失败 / 违约的当前状态字段**（即你要求放到借据表的那部分）。

```sql
CREATE TABLE IF NOT EXISTS loans (
    id                  BIGSERIAL PRIMARY KEY,
    loan_no             VARCHAR(32)  UNIQUE NOT NULL,
    advance_id          BIGINT,              -- 资金来源凭证（钱没到，债不成立）
    vin                 VARCHAR(32)  NOT NULL,
    dealer_id           BIGINT       NOT NULL,
    credit_line_id      BIGINT       NOT NULL,
    purchase_order_id   BIGINT,

    -- ---- 期限（自 vehicle_units 下沉而来，权威源在此）----
    disbursed_at        TIMESTAMPTZ,
    maturity_date       DATE,                -- 合同到期日
    grace_period_days   INT          NOT NULL DEFAULT 0,
    overdue_rate        NUMERIC(10,6),       -- 逾期罚息年利率，NULL=沿用基准
    term_source         VARCHAR(16)  NOT NULL DEFAULT 'UNKNOWN',
        -- CONTRACT 合同录入 / REGISTRATION 登记带出 / MANUAL_REVIEW 人工读合同
        -- / INFERRED 系统推断 / UNKNOWN 未知
    term_confirmed_by   VARCHAR(64),
    term_confirmed_at   TIMESTAMPTZ,

    -- ---- 四项分项余额（承接《放车放证》四级冲抵顺序）----
    principal_outstanding BIGINT NOT NULL DEFAULT 0,
    interest_outstanding  BIGINT NOT NULL DEFAULT 0,
    penalty_outstanding   BIGINT NOT NULL DEFAULT 0,
    fee_outstanding       BIGINT NOT NULL DEFAULT 0,

    -- ---- ① 逾期当前状态（流程读这里）----
    status              VARCHAR(16) NOT NULL DEFAULT 'DRAFT',
        -- DRAFT/ACTIVE/OVERDUE/SETTLING/SETTLED/DEFAULTED/WRITTEN_OFF
    current_dpd         INT      NOT NULL DEFAULT 0,   -- 当前逾期天数
    current_stage_code  VARCHAR(16),                   -- 当前所处阶段（引用 dpd_stage_rules）
    overdue_since       DATE,                          -- 本次逾期起始日
    max_dpd_ever        INT      NOT NULL DEFAULT 0,   -- 历史峰值，【只增不减】
    overdue_count       INT      NOT NULL DEFAULT 0,   -- 累计逾期次数
    current_stage_entered_at TIMESTAMPTZ,

    -- ---- ② 扣款失败当前状态（流程读这里）----
    deduction_fail_streak  INT NOT NULL DEFAULT 0,     -- 当前连续失败次数（成功即清零）
    deduction_fail_total   INT NOT NULL DEFAULT 0,     -- 累计失败次数
    last_deduction_fail_at TIMESTAMPTZ,
    last_deduction_fail_code VARCHAR(24),
        -- INSUFFICIENT_FUNDS 余额不足 / ACCOUNT_FROZEN 账户冻结 / ACCOUNT_CLOSED 销户
        -- / NAME_MISMATCH 户名不符 / BANK_REJECT 银行退票 / NO_ACCOUNT 未签约扣款

    -- ---- ③ 违约当前状态（流程读这里）----
    default_flag        BOOLEAN NOT NULL DEFAULT FALSE,
    defaulted_at        TIMESTAMPTZ,
    default_reason_code VARCHAR(32),
    default_cured_at    TIMESTAMPTZ,     -- 违约解除（不代表债消灭，只是回到正常催收）

    version             INT      NOT NULL DEFAULT 0,   -- 乐观锁
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at          TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS idx_loans_vin_active ON loans (vin)
    WHERE status IN ('DRAFT','ACTIVE','OVERDUE','SETTLING');
CREATE INDEX IF NOT EXISTS idx_loans_dealer ON loans (dealer_id, status);
CREATE INDEX IF NOT EXISTS idx_loans_stage  ON loans (current_stage_code, current_dpd DESC);
```

**为什么 `max_dpd_ever` 要冗余在这里**：画像表要的"最大逾期天数"是
`MAX(loan.max_dpd_ever)`，若不作冗余，每次都要扫 `overdue_records` 的历史序列。
"历史峰值只增不减"这条不变量让聚合变成一次 MAX。

### 3.2 `deduction_failures` 扣款失败流水（新增，ADR-008 未覆盖）

```sql
CREATE TABLE IF NOT EXISTS deduction_failures (
    id                BIGSERIAL PRIMARY KEY,
    deduction_no      VARCHAR(32) UNIQUE NOT NULL,
    loan_id           BIGINT      NOT NULL,
    schedule_id       BIGINT,             -- 冲抵的期次（可空：非计划内扣款）
    vin               VARCHAR(32) NOT NULL,
    dealer_id         BIGINT      NOT NULL,
    bank_account_id   BIGINT,             -- → dealer_bank_accounts.id 定位扣的哪个账户

    attempt_no        INT         NOT NULL DEFAULT 1,   -- 第几次尝试
    due_date          DATE        NOT NULL,
    scheduled_amount  BIGINT      NOT NULL,
    failed_at         TIMESTAMPTZ NOT NULL,

    fail_code         VARCHAR(24) NOT NULL,             -- 同 loans.last_deduction_fail_code
    bank_return_code  VARCHAR(32),
    bank_return_msg   VARCHAR(255),

    next_retry_at     TIMESTAMPTZ,
    resolution_status VARCHAR(16) NOT NULL DEFAULT 'PENDING',
        -- PENDING 待处理 / RETRY_SUCCEEDED 重试成功 / WAIVED 已豁免 / ESCALATED 已升级
    resolved_at       TIMESTAMPTZ,
    linked_work_order_id BIGINT,          -- → work_orders.id

    source_event_id   BIGINT,             -- → domain_events.id 溯源与幂等
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),

    CONSTRAINT uk_deduction_once UNIQUE (loan_id, due_date, attempt_no)
);

CREATE INDEX IF NOT EXISTS idx_df_loan   ON deduction_failures (loan_id, failed_at DESC);
CREATE INDEX IF NOT EXISTS idx_df_dealer ON deduction_failures (dealer_id, failed_at DESC);
CREATE INDEX IF NOT EXISTS idx_df_reso   ON deduction_failures (resolution_status, next_retry_at);
```

**与 `repayments` 的分工**：`repayments` 记**成功**的还款；
扣款失败是"没还成"，语义相反，混进去会让"累计还款额"的口径永远要加 `WHERE 成功`。

### 3.3 `overdue_records` —— 沿用 ADR-008，**不新建逾期事件表**

ADR-008 §2.6 定义的这张表**就是**逾期事件表：它在借据迁入 `OVERDUE` 时创建，
`uk_overdue_loan UNIQUE(loan_id)` 保证"一笔借据同时只有一条未结逾期记录"，
跨 M1→M2→M3 是**同一条记录阶段字段的变化**，不是新开一条。

> ⚠️ 这个约束很重要：若按"每次升档插一条"实现，催收工单会重复派发。

本次**只做一处修订**：把写死的 bucket 改成引用规则中心的 stage_code。

```sql
-- ADR-008 原定义：bucket VARCHAR(8) NOT NULL DEFAULT 'D0'  ← 硬编码，改掉
-- 修订为：
    current_stage_code  VARCHAR(16) NOT NULL,   -- → dpd_stage_rules.stage_code
    max_stage_code      VARCHAR(16) NOT NULL,   -- 本次逾期达到过的最高阶段
    ...
    -- 规则快照（保证事后可复现当时的判定口径）
    stage_rule_version  VARCHAR(16) NOT NULL,
    day_basis_snapshot  VARCHAR(8)  NOT NULL,   -- CALENDAR / BUSINESS
    stage_threshold_snapshot JSONB  NOT NULL,   -- {"M1":30,"M2":60,"M3":90}
```

其余字段（`overdue_no` / `schedule_id` / `overdue_date` / `dpd` / `outstanding` /
`status` / `escalated_at` / `resolved_at`）全部沿用 ADR-008。

### 3.4 `default_events` 违约事件表（新增）

ADR-008 只有 `loans.status='DEFAULTED'` 这个终态，**没有认定过程的记录**。
但违约在实务上是**需要人做出判断的决定**，必须有事件流水。

```sql
CREATE TABLE IF NOT EXISTS default_events (
    id              BIGSERIAL PRIMARY KEY,
    default_no      VARCHAR(32) UNIQUE NOT NULL,
    loan_id         BIGINT      NOT NULL,
    vin             VARCHAR(32) NOT NULL,
    dealer_id       BIGINT      NOT NULL,

    event_type      VARCHAR(16) NOT NULL,
        -- DECLARED 认定 / CURED 解除 / RESTATED 重述（原认定有误，需留痕不可删）

    -- ---- 系统建议 vs 人工认定，必须分开（见下方说明）----
    system_suggested_at  TIMESTAMPTZ,
    system_basis         JSONB,   -- 系统建议的依据快照：{"dpd":93,"stage":"M3","overdue_amount":1200000}
    declared_by          VARCHAR(64),   -- 认定人（自然人，不可是系统）
    declared_at          TIMESTAMPTZ,

    reason_code     VARCHAR(32) NOT NULL,
        -- OVERDUE_OVER_THRESHOLD 逾期超阈值 / DISPOSAL_WITHOUT_PAYMENT 脱信销售
        -- / LOSS_OF_CONTACT 失联 / BANKRUPTCY 破产 / DEDUCTION_FAIL_STREAK 连续扣款失败
        -- / CROSS_DEFAULT 交叉违约 / BREACH_OF_CONTRACT 合同违约
    explanation     VARCHAR(1000),

    amount_at_default  BIGINT,     -- 认定时点的敞口
    recovered_amount   BIGINT NOT NULL DEFAULT 0,
    loss_amount        BIGINT NOT NULL DEFAULT 0,

    linked_case_no  VARCHAR(32),   -- → disposal_cases.case_no
    notice_no       VARCHAR(32),   -- 违约通知书编号
    evidence_refs   JSONB,         -- ["attachment_id", ...]

    -- ---- 规则快照（当时用的是哪条规则、阈值多少）----
    trigger_rule_code    VARCHAR(48),
    rule_version         VARCHAR(16),
    threshold_snapshot   VARCHAR(64),   -- ">90d" / ">60d AND amount>5,000,000"

    restates_default_no VARCHAR(32),    -- event_type=RESTATED 时指向被更正的事件
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS idx_de_loan   ON default_events (loan_id, declared_at DESC);
CREATE INDEX IF NOT EXISTS idx_de_dealer ON default_events (dealer_id, declared_at DESC);
CREATE INDEX IF NOT EXISTS idx_de_sugg   ON default_events (event_type, system_suggested_at)
    WHERE declared_at IS NULL;
```

**为什么系统建议与人工认定要分开**（与 ADR-008 一脉相承）：
ADR-008 §2.4 定了"逾期是客观事实，人工可以**确认**但不能**制造**"。
违约同理——系统可以算出"DPD 已 93 天，够格认定违约"，
但**是否真的认定**要人来点头（可能刚谈判过、正在展期）。
所以三个时点分开存：`system_suggested_at`（系统说够格了）、
`declared_at`（人确认了）、以及 `recovered_amount`（后续追偿）。
只支持插入 `RESTATED` 来更正，**不允许 `DELETE` 或原地修改**。

### 3.5 `dealer_risk_profiles` 经销商画像 —— **只放汇总指标**

```sql
CREATE TABLE IF NOT EXISTS dealer_risk_profiles (
    id                  BIGSERIAL PRIMARY KEY,
    dealer_id           BIGINT UNIQUE NOT NULL,     -- 一个经销商一行

    -- ---- 敞口类 ----
    active_loan_count   INT    NOT NULL DEFAULT 0,
    outstanding_total   BIGINT NOT NULL DEFAULT 0,
    credit_usage_ratio  NUMERIC(7,4),               -- used/approved
    oldest_due_date     DATE,

    -- ---- 逾期汇总（借贷的是 MAX / COUNT，不含明细）----
    current_overdue_count   INT    NOT NULL DEFAULT 0,   -- 当前逾期笔数
    current_overdue_amount  BIGINT NOT NULL DEFAULT 0,
    current_worst_stage     VARCHAR(16),                 -- 当前最差阶段
    max_overdue_days        INT    NOT NULL DEFAULT 0,   -- 历史最大逾期天数
    overdue_count_12m       INT    NOT NULL DEFAULT 0,   -- 近一年逾期次数
    avg_overdue_days_12m    NUMERIC(8,2),
    worst_stage_12m         VARCHAR(16),

    -- ---- 违约汇总 ----
    defaults_last_12m       INT    NOT NULL DEFAULT 0,   -- 近一年违约次数
    defaults_total          INT    NOT NULL DEFAULT 0,
    default_amount_12m      BIGINT NOT NULL DEFAULT 0,
    last_default_at         TIMESTAMPTZ,
    days_since_last_default INT,

    -- ---- 扣款汇总 ----
    deduction_fail_count_30d  INT NOT NULL DEFAULT 0,
    deduction_fail_rate_30d   NUMERIC(7,4),
    deduction_fail_streak_max INT NOT NULL DEFAULT 0,

    -- ---- 分层结果 ----
    risk_tier           VARCHAR(4),          -- A / B / C / D
    tier_reason         VARCHAR(500),        -- 触发的最关键 2~3 条理由原文
    tier_rule_code      VARCHAR(48),
    tier_rule_version   VARCHAR(16),
    scored_at           TIMESTAMPTZ,

    -- ---- 口径元数据（没有它，报表口径永远说不清）----
    data_as_of          DATE   NOT NULL,     -- 数据截止业务日
    computed_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
    computed_by         VARCHAR(32),         -- 重算任务版本/批次号
    updated_at          TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS idx_drp_tier    ON dealer_risk_profiles (risk_tier, max_overdue_days DESC);
CREATE INDEX IF NOT EXISTS idx_drp_asof    ON dealer_risk_profiles (data_as_of);
```

**关键约束：这张表里没有 `vin`，没有 `loan_no`，没有任何明细。**
所有指标都是从 ② 层聚合出来的，所以它天然不具备"影响单笔流程"的能力——
这正是你要的"不影响贷后流程执行"。

**口径定义**（必须写死在文档里，否则不同报表会打架）：

| 指标 | 定义 |
|---|---|
| 当前逾期笔数 | `COUNT(loans WHERE status='OVERDUE')`——**按借据计数**，不按车（一台车可能多笔债） |
| 最大逾期天数 | `MAX(loans.max_dpd_ever)` 跨该经销商全部借据 |
| 近一年违约次数 | `COUNT(default_events WHERE event_type='DECLARED' AND declared_at >= now()-365d)`，被 `RESTATED` 更正的不计 |
| 30 天扣款失败率 | `失败次数 / 总扣款尝试次数`（近 30 天），分母为 0 时置 NULL 而非 0 |

## 4. DPD / M 系列规则中心（你的第二条要求）

### 4.1 为什么必须配置化

你给的分段是：

| DPD | 阶段 | 处置基调 |
|---|---|---|
| 1–30 天 | **M1** | 早期逾期，提醒、催收为主 |
| 31–60 天 | **M2** | 风险升高，限制新增融资、加强盘点 |
| 61–90 天 | **M3** | 严重逾期，启动法务、处置质押车辆 |
| > 90 天（或合同约定阈值） | **违约候选** | 认定违约，进入坏账/处置流程 |

把这套写进代码或文档注释里，会有三个立刻出现的问题：

1. **两套口径打架**：ADR-008 §2.6 写的是 `M1≥31 / M2≥61 / M3≥91`（0-based），
   你给的是 `M1=1-30`（1-based）。两套在中国贷后实务里都见过，
   **靠文档争论永远解决不了**——配置化之后，它变成了一条数据记录，改一下就生效。
2. **合同约定阈值无法表达**：大经销商可能谈到"120 天才算违约"，
   写死的 90 天会误伤。
3. **调整要发版**：贷后策略是**高频调参**（催收强度、冻结力度），
   每次调参都要改代码发版，运营没法自己干活。

> 💡 这条要求顺带解决了 ADR-008 §4 悬而未决的第 5 项
> （"M1/M2/M3 按自然日还是营业日"）——把它做成规则的一个字段即可。
> ✅ **该项已由 Q14 业务定源（2026-11-22）正式关闭：按自然日 CALENDAR**；
> `day_basis` 字段退化为历史快照，不再承担"口径可切换"的职责。

### 4.2 三张配置表

```sql
-- ① DPD 阶段定义（分段 + 计数口径）
CREATE TABLE IF NOT EXISTS dpd_stage_rules (
    id            BIGSERIAL PRIMARY KEY,
    stage_code    VARCHAR(16) NOT NULL,      -- M1 / M2 / M3 / M4 ...
    stage_name    VARCHAR(64) NOT NULL,      -- 早期逾期 / 风险升高 / 严重逾期
    min_dpd       INT         NOT NULL,      -- 下界（含）
    max_dpd       INT,                       -- 上界（含），NULL = 不封顶
    day_basis     VARCHAR(8)  NOT NULL DEFAULT 'CALENDAR',  -- CALENDAR 自然日 / BUSINESS 营业日
    severity      VARCHAR(8)  NOT NULL,      -- LOW / MEDIUM / HIGH / CRITICAL
    sort_order    INT         NOT NULL,
    version       VARCHAR(16) NOT NULL,      -- 口径版本（改数则升版）
    enabled       BOOLEAN     NOT NULL DEFAULT true,
    updated_by    VARCHAR(64),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uk_stage_version UNIQUE (stage_code, version)
);

-- ② 阶段 → 动作绑定（每个阶段触发什么）
CREATE TABLE IF NOT EXISTS dpd_stage_actions (
    id              BIGSERIAL PRIMARY KEY,
    stage_code      VARCHAR(16) NOT NULL,
    action_code     VARCHAR(32) NOT NULL,
        -- NOTIFY 通知 / COLLECTION_CALL 电话催收 / FREEZE_NEW_FINANCING 限制新增融资
        -- / INCREASE_STOCK_CHECK 加强盘点 / LEGAL_REVIEW 法务介入
        -- / DISPOSAL_PREP 处置准备 / DEFAULT_DECLARE 违约认定 / FREEZE_CREDIT 冻结额度

    trigger_delay_days INT NOT NULL DEFAULT 0,   -- 进入阶段后延迟几天执行
    target_role    VARCHAR(32),                  -- 派给哪个角色
    work_order_type VARCHAR(32),                 -- 生成的工单类型
    repeatable     BOOLEAN NOT NULL DEFAULT false,
    enabled        BOOLEAN NOT NULL DEFAULT true,
    updated_by     VARCHAR(64),
    updated_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uk_stage_action UNIQUE (stage_code, action_code)
);

-- ③ 违约认定门槛（支持"合同约定阈值"覆盖）
CREATE TABLE IF NOT EXISTS default_trigger_rules (
    id             BIGSERIAL PRIMARY KEY,
    rule_code      VARCHAR(48) UNIQUE NOT NULL,
    scope          VARCHAR(16) NOT NULL DEFAULT 'GLOBAL',
        -- GLOBAL 全局 / CREDIT_LINE 额度 / DEALER 经销商 / LOAN 单笔借据
    scope_ref_id   BIGINT,                   -- scope 对应的 id（GLOBAL 时为 NULL）
    trigger_type   VARCHAR(24) NOT NULL,
        -- DPD_DAYS 按逾期天数 / STAGE 按所处阶段 / AMOUNT 按金额
        -- / AMOUNT_RATIO 按敞口占比 / FAIL_STREAK 按连续扣款失败次数
    threshold_value NUMERIC(18,4) NOT NULL,
    compare_op     VARCHAR(8) NOT NULL DEFAULT 'GTE',   -- GTE / GT
    require_manual_confirm BOOLEAN NOT NULL DEFAULT true,  -- 是否必须人工确认
    priority       INT NOT NULL DEFAULT 0,    -- 数字越大越优先
    version        VARCHAR(16) NOT NULL DEFAULT 'v1',
    enabled        BOOLEAN NOT NULL DEFAULT true,
    updated_by     VARCHAR(64),
    updated_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS idx_dtr_scope ON default_trigger_rules (scope, scope_ref_id, enabled);
```

### 4.4 规则的优先级解析

```
对一笔借据判定违约门槛时：
  取 scope 匹配且 enabled 的记录，按 priority 降序取第一条
  匹配顺序：LOAN(最高承接) > DEALER > CREDIT_LINE > GLOBAL
  原因：合同单独约定 > 经销商整体约定 > 额度层约定 > 全局默认
```

### 4.5 ⚠️ 配置能改，历史判定必须可复现

这是规则中心最容易埋的坑：**今天是 90 天算违约，下个月改成 120 天**，
那么"上个月认定的那笔违约，用的是哪套？"

解法是每个事件表都存**当时的规则快照**（已在 §3.3 / §3.4 加了字段）：

- `overdue_records.stage_rule_version` + `stage_threshold_snapshot` + `day_basis_snapshot`
- `default_events.trigger_rule_code` + `rule_version` + `threshold_snapshot`

**规则可以被改但不能被删除，只能 `enabled=false`**——
否则历史快照指向的规则消失，事后无法复算。
这与 V11 `risk_alerts.threshold_value` 的做法一致（该项目早有此先例）。

### 4.6 自然日 vs 营业日

> ✅ **Q14 已业务定源（2026-11-22）：一律按自然日 CALENDAR，不切换营业日。**
> 以下 BUSINESS 分支的技术说明保留作设计演进记录，但**该分支不启用**；
> `day_basis` / `day_basis_snapshot` 字段保留仅作事后复现的历史快照，不作为可切换开关。
> 落地证据：`DpdCalculator.daysPastDue()` 用 `ChronoUnit.DAYS.between`（纯日历差，不查营业日历）、
> `DAY_BASIS="CALENDAR"`，并有跨周末防回归单测 `daysPastDue_calendarBasis_doesNotSkipWeekends()`。

- （历史设计）`day_basis='BUSINESS'` 的计算本应依赖 `holidays` 表。
- （历史实测）`holidays` 表当前 0 行——即便要启用营业日口径也须先灌入日历数据，否则 DPD 会被算成 0。
- （原建议，现已作废）"先按 `CALENDAR` 上线、需要时切营业日"——**业务已定源固定为 CALENDAR，不再切换**。
- **同一个 `version` 内不允许混用两种口径**（约束保留，用于快照可复算性）。

### 4.7 为什么不复用 V11 的 `risk_rules`

| 维度 | `risk_rules`（V11） | 本次三张表 |
|---|---|---|
| 表达力 | 单阈值（`threshold_value` + 比较符） | **需要区间** `[min_dpd, max_dpd]` |
| 语义 | 产出 `risk_alerts`（**预警**） | 决定**状态机与动作执行** |
| 关联 | 无阶段-动作的编排 | 阶段→动作→角色→工单 的编排 |

`risk_rules` 表达不了一个区间，硬塞进去要加 `min_value`/`max_value` 列，
会把"预警"和"账龄分期"两种语义混在一张表上。
**结论：新建，但沿用它的运营方式**（后台可改、即时生效、`enabled`、`updated_by`）。
两张配置体系并存，各自后台页面分开。

## 5. 数据流与写入纪律

### 5.1 写入路径

```
银行扣款回执（失败）
    │  domain_events 接入（uk_domain_event 保证幂等）
    ▼
① INSERT deduction_failures（流水，永不修改）
    │  同一事务
    ▼
② UPDATE loans SET deduction_fail_streak=+1, last_deduction_fail_at=now()  ← 唯一写入点
    │  若 streak 命中 default_trigger_rules(FAIL_STREAK)
    ▼
③ 生成 default_events(system_suggested_at=now(), declared_at=NULL)  ← 待人工确认

......每晚 T+1 批处理 ......
④ 计算 DPD → 查 dpd_stage_rules → 归阶段
    │  阶段变化 → INSERT loan_status_history + 回写 loans.current_stage_code
    │  同级跃迁（跨 M1→M2→M3）→ 更新 overdue_records.max_stage_code（同一条）
    ▼
⑤ 按 dpd_stage_actions 编排动作 → work_orders / 冻结 / 降额

......异步，可延迟可重算 ......
⑥ 聚合 → dealer_risk_profiles（带 data_as_of）
```

### 5.2 单一写入点清单（违反即为缺陷）

| 字段 | 唯一写入点 |
|---|---|
| `loans.deduction_fail_streak` 等 | 扣款流水落库后的同事务回写 |
| `loans.current_dpd` / `current_stage_code` | 每晚 DPD 计算 job |
| `loans.status` | 借据状态机（ADR-008 §2.4） |
| `loans.default_flag` | 人工确认违约后的认定动作 |
| `vehicle_units.derived_*` | `LoanOverdueProjection`（ADR-008 §2.7） |
| `dealer_risk_profiles.*` | 画像重算任务（**全量重算，不做增量 patch**） |

> 画像建议**全量重算**而非增量 patch：增量 patch 一旦漏一次后面永远修不回来；
> 而全量重算的成本是 `COUNT(经销商) × AVG(借据数)`，规模可控且天然自愈。

## 6. 需要修订的既有决策

### 6.1 对 ADR-008 的修订（不是推翻）

| ADR-008 原文 | 修订为 | 原因 |
|---|---|---|
| §2.6 `bucket VARCHAR(8) DEFAULT 'D0'`，`M1=≥31 / M2=≥61 / M3=≥91` | `current_stage_code` 引用 `dpd_stage_rules`，默认 1-based（M1=1-30） | 你指定的分段；且改为可配置后口径可调 |
| §2.6 未规定 day_basis | 新增 `day_basis`（CALENDAR/BUSINESS） | 解决 §4 待确认第 5 项 |
| §4 待确认第 5 项 | **已解决**：Q14 业务定源（2026-11-22）固定为 CALENDAR 自然日，BUSINESS 分支不启用；字段仅作快照 | — |
| §3.3 "用 `vehicle_units.overdue_days` 作为逾期依据 → 明确不做" | 维持不变；并把 V11 的空壳期限列下沉到 `loans` | 实测已确认是空壳（§1.2） |

### 6.2 决策点：`risk_tier` 是否要反过来影响授信/定价？

现在画像是个"报表玩具"。一旦让 `risk_tier` 参与**利率定价**或**准入闸门**
（就像现在 `risk_grade` 那样），事情就变了：

- 画像从"只读投影"变成"**流程依赖**"——它算慢一小时，就有一小时的放款判定基于旧数据
- 违反你在 §0 定的"不影响贷后流程执行"原则
- 且会出现**两张表都叫"评级"，评分口径打架**的困惑（`risk_grade` vs `risk_tier`）

**我的建议**：
- 一期 `risk_tier` **只做展示与人工参考**，不自动介入任何流程；
- 若后续要自动影响额度，走**独立的"额度调整建议"流程**（生成待办 → 人确认 → 改 `credit_lines`），
  而不是让代码直接读 `risk_tier` 做判断。这条建议请你定。

## 8. 验收清单

- [ ] 借据建档：放款银行回调确认后，`loans` 自动出现一条 `DRAFT→ACTIVE`
- [ ] 逾期入口唯一：只有还款计划未足额才能进 `OVERDUE`，人工直接 UPDATE 应被拦截
- [ ] 跨段不增记录：同一笔借据从 M1 升到 M3，`overdue_records` 仍是**一条**（`max_stage_code` 更新）
- [ ] 扣款失败幂等：同一 `(loan_id, due_date, attempt_no)` 重复推送不产生第二条流水
- [ ] `streak` 归零：一次扣款成功后 `deduction_fail_streak` 清零，`total` 保留
- [ ] 违约需人工：系统建议产生后 `loans.default_flag` 仍为 false，人工确认后才 true
- [ ] 违约更正留痕：认定错误只能插入 `RESTATED`，原事件不可删改
- [ ] 规则改即时生效：把 M2 下界改成 25 天后，新计算的阶段随之改变，**且不改代码**
- [ ] 历史可复现：改了规则后，去年的 `overdue_records` 凭快照仍能算出当时的阶段
- [ ] 画像不影响流程：停掉画像重算 48 小时，放款/冻结/催收/处置**全部正常**
- [ ] `data_as_of` 存在：任何画像查询都要能回答"这是截至哪天的数据"
- [ ] `max_dpd_ever` 单调：历史峰值不会被后续小额逾期拉低

| 4 | 连续扣款失败几次触发违约建议 | 3 次 | `default_trigger_rules` 种子值 |
| 5 | 违约认定是否需要双人复核 | 单人认定即可，但必须留自然人 | `default_events.declared_by` 校验 |
| 6 | 画像重算频率 | 每日一次 T+1 | 数据新鲜度 vs 计算开销 |
| 7 | **`risk_tier` 是否参与定价/准入**（§6.2） | **一期不参与**，仅展示与人工参考 | 决定是否破坏"画像不入流程"原则 |
| 8 | 画像保留多久历史 | 每日快照另表留存（`dealer_risk_profile_history`） | 风险分层的趋势分析能力 |

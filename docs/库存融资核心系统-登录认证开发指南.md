## 1. 先分清两个词：认证（Authentication）vs 授权（Authorization）

| 词 | 白话 | 回答的问题 | 例子 |
|---|---|---|---|
| **认证** Authentication | 证明"你是谁" | 你是张三吗？ | 输入用户名密码登录 |
| **授权** Authorization | 决定"你能干什么" | 张三能审批放款吗？ | 审批员角色才能调 `/api/approvals` |

登录系统 = 先做认证（本指南主体），授权（角色权限）在其上叠加。

> **2026-10-26 更新**：授权层已从"二值角色"升级为完整 RBAC 体系——
> **13 个业务角色 + 23 个权限点 + 一人多岗 + 两层职责分离**，
> 代码落在 `UserRole` / `Permission` 枚举与 `user_roles` 表。
> 详见《库存融资核心系统-角色与权限矩阵.md》与本文第 8 节。

## 2. 方案选型：三种做法怎么选

| 方案 | 原理 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| A. 拦截器 + JWT | 登录发一个签名令牌，拦截器验签 | 不依赖 Spring Security，代码量小，**每一步都能看懂** | 自己管安全细节 | **学习期/一期推荐** |
| B. Spring Security + JWT | 框架托管过滤器链 | 生产级健壮（防爆破、密码升级、会话管理） | 概念多（FilterChain/Provider...），小白易劝退 | 二期生产化 |
| C. Session + Cookie | 服务端存会话，浏览器带 Cookie | 传统、简单 | 不适合前后端分离/API 调用方（冒烟脚本、厂家系统） | 纯浏览器内部系统 |

**本指南走方案 A**：不引入 Spring Security，用一个拦截器 + JWT 实现，
代码全部落在项目现有四模块里。学懂 A 之后再看 B，会发现 B 只是把这些手写的活儿框架化了。

> **JWT 是什么（大白话）**：一张**防伪签名**的通行证。登录成功后服务端发给你一串字符（三段式
> `头部.载荷.签名`），载荷里明文写着你是谁、什么角色、过期时间；签名用只有服务端知道的密钥生成，
> 改动载荷任何一个字，签名就对不上——所以服务端**不用存会话**，拿到通行证验个签就知道你是谁。
> 代价：签发后**无法主动作废**（改密码/离职前发的令牌在过期前仍有效），敏感系统需配合短有效期 + 刷新令牌。

```sql
-- 用户表：一期只做"操作员登录"，不区分租户
CREATE TABLE users (
    id            BIGSERIAL PRIMARY KEY,
    username      VARCHAR(64)  NOT NULL UNIQUE,          -- 登录名
    password_hash VARCHAR(100) NOT NULL,                 -- BCrypt 散列（绝不存明文！）
    display_name  VARCHAR(64)  NOT NULL,                 -- 显示名（审计里的人名）
    role          VARCHAR(20)  NOT NULL DEFAULT 'OPERATOR',  -- OPERATOR / ADMIN（授权预留）
    status        VARCHAR(20)  NOT NULL DEFAULT 'ACTIVE',    -- ACTIVE / DISABLED
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT now()
);

-- 种子用户：密码是 bcrypt("admin123") 的结果，仅开发环境用，生产必须换
INSERT INTO users (username, password_hash, display_name, role) VALUES
('admin', '$2a$10$N.ZOn9G6/YLFixAOPMg/h.z7pCu6v2XyFDtC4q.jeeGm/K37dPxbW', '系统管理员', 'ADMIN');
```

> **BCrypt 大白话**：单向"搅拌机"。密码进去，出来一坨乱码，没法反推原文；校验时把用户输入的密码
> 再搅一遍，比对两坨乱码是否一致。它自带随机盐（同一密码每次散列都不同），拖库也难撞库破解。
> 生成一条散列：`new BCryptPasswordEncoder().encode("admin123")`。

`application/.../service/AuthApplicationService.java`：

```java
@Service
public class AuthApplicationService {

    private final AuthUserRepository userRepository;
    /** JWT 签名密钥：至少 32 字节。开发默认值放 yml，生产用环境变量覆盖！ */
    @Value("${floorplan.auth.jwt-secret:dev-only-secret-key-change-me-32bytes!}")
    private String jwtSecret;
    /** 令牌有效期（分钟） */
    @Value("${floorplan.auth.jwt-ttl-minutes:480}")
    private long ttlMinutes;

    public AuthApplicationService(AuthUserRepository userRepository) {
        this.userRepository = userRepository;
    }

    /** 登录：验密码 → 签发 JWT。失败一律抛 AUTH_001（不区分"用户不存在/密码错"，防枚举）。 */
    public Map<String, Object> login(String username, String password, String traceId) {
        AuthUser user = userRepository.findByUsername(username)
                .orElseThrow(() -> new BusinessException(ErrorCode.AUTH_001,
                        Map.of("username", username)));          // ← 用户名错和密码错返回同一个错

        if (!"ACTIVE".equals(user.getStatus())) {
            throw new BusinessException(ErrorCode.AUTH_002, Map.of("username", username));
        }
        // BCrypt 比对：把明文再"搅"一遍，和库里的散列比
        if (!new BCryptPasswordEncoder().matches(password, user.getPasswordHash())) {
            throw new BusinessException(ErrorCode.AUTH_001, Map.of("username", username));
        }

        Instant now = Instant.now();
        String token = Jwts.builder()
                .subject(username)                                  // 载荷：登录名
                .claim("role", user.getRole())
                .claim("displayName", user.getDisplayName())        // 审计直接用这个，替代 X-Operator-Id
                .claim("uid", user.getId())
                .issuedAt(Date.from(now))
                .expiration(Date.from(now.plus(ttlMinutes, ChronoUnit.MINUTES)))
                .signWith(Keys.hmacShaKeyFor(jwtSecret.getBytes(StandardCharsets.UTF_8)))
                .compact();

        return Map.of("token", token, "tokenType", "Bearer",
                "expiresInMinutes", ttlMinutes,
                "displayName", user.getDisplayName(), "role", user.getRole());
    }

    /** 验签 + 解析（拦截器调用）。过期/篡改都会抛 JwtException。 */
    public Claims verify(String token) {
        return Jwts.parser()
                .verifyWith(Keys.hmacShaKeyFor(jwtSecret.getBytes(StandardCharsets.UTF_8)))
                .build()
                .parseSignedClaims(token)
                .getPayload();
    }
}
```


### 4.4 web 模块：登录接口 + 拦截器

`web/.../controller/AuthController.java`：

```java
@RestController
@RequestMapping("/api/auth")
public class AuthController {

    private final AuthApplicationService service;

    public AuthController(AuthApplicationService service) { this.service = service; }

    /** 登录：唯一不需要令牌的接口。 */
    @PostMapping("/login")
    public ApiResponse<Map<String, Object>> login(@RequestBody LoginRequest req,
                                                  @RequestHeader(value = "X-Trace-Id", required = false) String traceId) {
        String tid = traceId == null ? UUID.randomUUID().toString() : traceId;
        return ApiResponse.ok(service.login(req.username, req.password, tid), tid);
    }

    public static class LoginRequest {
        public String username;
        public String password;
    }
}
```

`web/.../config/JwtAuthInterceptor.java`（核心：拦住除登录外的所有请求）：

```java
/**
 * JWT 认证拦截器：从 Authorization 头取令牌 → 验签 → 把操作人放进请求属性。
 * 对照学习：GlobalExceptionHandler 是"异常时被回调"，拦截器是"每个请求前被回调"，
 * 注册方式同样是隐形装配（见 WebMvcConfig）。
 */
public class JwtAuthInterceptor implements HandlerInterceptor {

    private final AuthApplicationService authService;

    public JwtAuthInterceptor(AuthApplicationService authService) { this.authService = authService; }

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler)
            throws Exception {
        String auth = request.getHeader("Authorization");
        if (auth == null || !auth.startsWith("Bearer ")) {
            write401(response, "NO_TOKEN", "缺少令牌，请先登录 /api/auth/login");
            return false;                       // false = 请求到此为止，不进 Controller
        }
        try {
            Claims claims = authService.verify(auth.substring(7));   // 去掉 "Bearer " 前缀后验签
            request.setAttribute("operator", claims.get("displayName", String.class));
            request.setAttribute("role", claims.get("role", String.class));
            return true;                        // 放行
        } catch (JwtException e) {              // 过期 / 签名不符 / 格式错误都走这
            write401(response, "BAD_TOKEN", "令牌无效或已过期，请重新登录");
            return false;
        }
    }

    private void write401(HttpServletResponse resp, String code, String msg) throws IOException {
        resp.setStatus(401);
        resp.setContentType("application/json;charset=UTF-8");
        resp.getWriter().write("{\"success\":false,\"code\":\"" + code + "\",\"message\":\"" + msg + "\"}");
    }
}
```

`web/.../config/WebMvcConfig.java`（把拦截器注册进 Spring MVC）：

```java
@Configuration
public class WebMvcConfig implements WebMvcConfigurer {

    private final AuthApplicationService authService;
    public WebMvcConfig(AuthApplicationService authService) { this.authService = authService; }

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new JwtAuthInterceptor(authService))
                .addPathPatterns("/api/**")             // 拦所有 API
                .excludePathPatterns("/api/auth/login"); // 登录接口例外
    }
}
```

> **Windows 坑位提醒**（都是本项目真实踩过的）：
> - **`SERVER__PORT` 环境变量**：WorkBuddy 注入的 `SERVER__PORT=51136` 会被 Spring 宽松绑定读成
>   `server.port`，覆盖 yml 端口且 51136 被自己占用 → 端口冲突。`run-microservices.sh` 已用
>   `env -u SERVER__PORT` 统一规避；手动起单服务时也要先 `unset SERVER__PORT`。
> - **Git Bash 里 curl 要加 `--noproxy "*"`**：环境代理变量会把 localhost 请求劫持成 502
> - **PowerShell 里 `curl` 是 `Invoke-WebRequest` 的别名**，参数完全不同；写 `-H` 会报错。
>   要么用 `curl.exe`，要么干脆用 Git Bash

## 6. 安全要点清单（哪怕一期也要守住的红线）

| # | 要点 | 为什么 |
|---|---|---|
| 1 | 密码**只存 BCrypt 散列** | 拖库不泄露明文；日志/异常信息里也绝不能打密码 |
| 2 | 登录失败**不区分**"用户不存在/密码错误" | 防攻击者用报错差异枚举有效用户名 |
| 3 | JWT 密钥走**环境变量**，不进 git | 密钥泄露 = 任何人可伪造任意身份通行证 |
| 4 | 令牌有效期短（8 小时内）+ HTTPS | JWT 无法主动作废，短有效期是主要止损手段 |
| 5 | 载荷里**不放敏感信息** | JWT 载荷只是 Base64（可逆编码），不是加密，谁拿到都能读 |
| 6 | 生产部署**必须 HTTPS** | HTTP 下令牌、密码在网线上裸奔 |

## 8. 授权层现状与进阶路线（RBAC 已落地）

1. **授权（角色）**：拦截器里已有 `role`，按路由表拦ADMIN-only 接口（如 `PUT /api/rating-configs`），
   再进一步做注解式 `@RequireRole("ADMIN")` + AOP
2. **Spring Security 迁移**：把自研拦截器换成 Security 过滤器链，白拿防爆破、密码强度校验、会话固定防护
3. **刷新令牌**：短期 access token（15 分钟）+ 长期 refresh token，被盗止损更快
4. **对接企业 IdP**：日本客户常见 SSO（Azure AD / Okta），走 OAuth2/OIDC，本系统的 `/api/auth/login` 变成"换取本地令牌"的适配层
5. **放贷业法合规留痕**：登录事件（成功/失败/锁定）写入 `audit_events`，监管检查可回溯

### 10.1 技术选型：为什么是"静态页 + fetch"而不是 Vue/React

| 对比项 | 静态 HTML + fetch（本方案） | Vue/React SPA |
|---|---|---|
| 构建工具 | 无，浏览器直接打开 | Node + npm + 打包链 |
| 部署 | Spring Boot 静态资源自动托管 | 需要额外静态服务器或打包进 jar |
| 改一行看效果 | 刷新浏览器即可 | 重新构建 |
| 适用阶段 | 一期管理后台、学习期 | 页面复杂到需要组件化时再升级 |

管理后台一期页面量少、交互简单，静态页完全够用；等业务页面多起来再上 Vue 也不冲突——
后端 API 契约（ApiResponse 包装、Bearer 头）已经定好，前端换框架不用动后端。

### 10.2 页面与后端的关键约定

1. **同源部署**：页面经网关暴露（`http://127.0.0.1:18080/login.html`，网关转发给 web 静态资源），
   从 18080 打开时 `API_BASE` 走相对路径，天然没有跨域问题；网关另配了全局 CORS 以兼容
   从其他端口/file:// 打开的调试场景。原 8080 直连方式在微服务化后已废弃。
2. **令牌存储用 `localStorage`**：键 `fp_token` / `fp_username`。
   教学要点——localStorage 的 XSS 风险高于 HttpOnly Cookie，但 Cookie 方案需要配套 CSRF 防护，
   一期先 localStorage（简单可理解），二期做安全加固时再迁移。
3. **统一请求封装 `apiFetch()`**（index.html 内）：自动附加
   `Authorization: Bearer <token>` + `X-Operator-Id`（审计头，替代原来手填的 curl 头）；
   收到 401 自动清 token 踢回登录页——这就是拦截器 `NO_TOKEN/BAD_TOKEN/EXPIRED` 在前端的闭环。
4. **JWT 前端可读**：页面用 `parseJwtPayload()` 解析载荷展示签发/过期时间。
   注意：这只是 Base64 **解码**不是解密——再次印证"载荷不能放敏感信息"。

### 10.3 与拦截器配置的衔接（容易踩的坑）

`JwtAuthInterceptor` 注册时务必只拦 `/api/**`：

```java
registry.addInterceptor(jwtAuthInterceptor)
        .addPathPatterns("/api/**")                      // 只拦 API
        .excludePathPatterns("/api/auth/login");         // 登录接口例外
```

如果写成 `addPathPatterns("/**")`，静态页面本身也会被拦，浏览器打开 login.html 直接 401，
连登录表单都看不到。静态资源（`/login.html`、`/index.html`）不需要放行配置——不在 `/api/**` 内天然放行。

## 13. 授权层：从"认证"到"你能干什么"（2026-10-26 落地）

> 第 1 节说"登录系统 = 先做认证，授权在其上叠加"。这一节就是那个"叠加"，
> 已经真实落地并通过双角色实测。

### 13.1 一期只做两个角色

业务上最终会有客户经理 / 运营 / 风控 / 财务 / 系统等多个角色（见《接口文档》2. 权限矩阵），
但一期代码只落地两个：

| 角色 | 值 | 能力 |
|---|---|---|
| 管理员 | `ADMIN` | 全部读写——新增/编辑/删除经销商、调评级、查看名下车辆 |
| 业务操作员 | `USER` | 只读——查看经销商档案、名下车辆台账、车辆详情 |

种子账号（`V6__dealer_profile_and_roles.sql` 用 pgcrypto 的 `crypt/gen_salt` 生成 BCrypt 散列）：

| 账号 | 密码 | 角色 |
|---|---|---|
| `admin` | `admin123` | `ADMIN` |
| `operator` | `operator123` | `USER` |

> `operator` 账号存在的意义就是**验证权限边界**——用它跑一遍所有写接口，
> 确认都是 403 `AUTH_002`。没有第二个账号，权限代码就是自说自话，没法证伪。

### 13.2 两道关卡严格分开

| 关卡 | 问题 | 失败时 | HTTP | 错误码 |
|---|---|---|---|---|
| **认证** Authentication | 你是谁？ | 令牌缺失/失效/签名不符 | 401 | `AUTH_001` |
| **授权** Authorization | 你能干什么？ | 角色不足 | 403 | `AUTH_002` |

**为什么必须分开**：运维排障时，"这个接口 401 还是 403"直接决定往哪查——
401 是登录态问题（令牌过期、前缀写错），403 是权限配置问题（角色没给）。
合成一个码，等于让人猜。

### 13.3 授权怎么声明：注解，不是路径白名单

`web/.../security/RequireAdmin.java`：

```java
@Target({ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
public @interface RequireAdmin { }
```

在 Controller 上标注需要管理员的写接口：

```java
@PostMapping
@RequireAdmin                                   // 新增：仅管理员
public ResponseEntity<ApiResponse<Dealer>> create(...) { ... }

@GetMapping("/{id}")                              // 查询：不加注解 → 全部已登录可读
public ApiResponse<Dealer> get(@PathVariable Long id) { ... }
```

拦截器判定（`JwtAuthInterceptor`）：

```java
private boolean requiresAdmin(Object handler) {
    if (handler instanceof HandlerMethod method) {
        return method.hasMethodAnnotation(RequireAdmin.class)
                || method.getBeanType().isAnnotationPresent(RequireAdmin.class);
    }
    return false;
}
```

**为什么不用路径白名单**（这是本节最关键的取舍）：

| 方案 | 漏配风险 | 改 URL 时 | 维护成本 |
|---|---|---|---|
| 路径白名单（`/api/dealers` 需要 admin） | 新增接口忘了加 → **越权口子** | 改了路径就绕过 | 每加一个接口补一条 |
| **方法级注解** | 忘了加注解 → 接口默认**开放**（读安全） | 改路径不受影响 | 跟着方法走，IDE 可跳转 |

注解方案的"默认失败方向"更安全：新加的读接口忘了标注解 → 所有人可读（不致命）；
路径白名单忘了加 → 该拦的没拦（致命）。

### 13.4 一个曾经踩过的坑：try 块包得太宽

原实现把验签和授权检查都放进同一个 `try`：

```java
try {
    Claims claims = authService.verify(token);
    if (!isAdmin(role)) {
        throw new BusinessException(AUTH_002, ...);   // ← 抛的是 403 业务异常
    }
    return true;
} catch (Exception ex) {
    write401(response, ...);                          // ← 403 被 catch 吞成 401！
    return false;
}
```

`BusinessException`（403）被 `catch` 捕获后统一转成 401 —— **授权失败被伪装成认证失败**。
后果是：用户明明登录了、角色也给对了，却收到"请重新登录"的提示，反复登录也进不去。

**修复**：try 块**只包验签**，授权检查挪到 try 之后。

```java
Claims claims;
try {
    claims = authService.verify(header.substring(7));   // 只包验签
} catch (BusinessException ex) {
    response.setStatus(HttpStatus.UNAUTHORIZED.value());
    // 写 401 JSON
    return false;
}
String role = claims.get("role") == null ? null : String.valueOf(claims.get("role"));
request.setAttribute("authUsername", username);
request.setAttribute("authRole", role);

if (requiresAdmin(handler) && !ROLE_ADMIN.equals(role)) {
    log.warn("越权访问被拒：user={} role={} uri={}", username, role, request.getRequestURI());
    throw new BusinessException(ErrorCode.AUTH_002, Map.of(
            "requiredRole", ROLE_ADMIN,
            "currentRole", role == null ? "NONE" : role,
            "uri", request.getRequestURI()));
}
return true;
```

> 越权被拒时记 `WARN` 日志（含用户、角色、URI）——审计与事后追溯要用。

### 13.5 角色怎么传到前端

**令牌载荷**（`AuthApplicationService` 签发时写入）：

```java
claimsBuilder.claim("role", user.getRole());
claimsBuilder.claim("displayName", user.getDisplayName());
```

**登录响应**也带一份，前端不必解 JWT 就能拿到：

```java
result.put("token", token);
result.put("role", user.getRole());
result.put("displayName", user.getDisplayName());
```

**前端**（`common.js`）解析 Base64URL 载荷取角色：

```js
function parseClaims(token) {
    // JWT = 头部.载荷.签名，中间那段是 Base64URL
    const part = token.split('.')[1].replace(/-/g, '+').replace(/_/g, '/');
    return JSON.parse(decodeURIComponent(escape(atob(part))));
}

const auth = {
    role: function () { return auth.claims().role || localStorage.getItem('fp_role') || 'USER'; },
    isAdmin: function () { return auth.role() === 'ADMIN'; }
};
```

> ⚠️ **前端隐藏按钮只是体验优化，不是安全边界**。
> 前端解析 JWT 本身是可以被绕过的（改 localStorage 就能伪造角色）。
> 真正的边界是后端的 403 `AUTH_002`——前端做的是"不让用户点一个注定失败的按钮"。

### 13.7 二期扩展方向

当前是「一个注解 = 一个角色」，扩展到多角色时：

1. 把 `@RequireAdmin` 升级为 `@RequireRole({"ADMIN", "RISK_MANAGER"})`；
2. `users.role` 单字段改 `user_roles` 关联表（一人多角色）；
3. 权限从代码里的注解移到 `role_permissions` 表 → 后台可视化配置；
4. 加"数据级权限"：同一个接口，不同角色看不同范围（如客户经理只看自己名下经销商）。

> 数据级权限是金融系统的真正难点——接口级权限只能回答"能不能调"，
> 回答不了"能看哪几条"。二期建议优先做这个。

## 14. 审计操作人：从"请求头"到"令牌身份"（2026-10-26 修复）

> 第 13 节把"你是谁"和"你能干什么"分开了。这一节补上第三件事：
> **"你做的这件事，账上记的是谁"**。

### 14.1 发现的问题

写日志指南时查审计表，发现 `audit_events.actor` 存的是 `1`：

```
 actor  |        action        | count
--------+----------------------+-------
 1      | BATCH_INGEST         |   107
 1      | ADVANCE              |    84
 1      | MARK_SOLD            |    48
```

`1` 不是任何用户的 ID，是冒烟脚本传的假值。顺着往下查，发现了根因：

```java
// 修复前：每个 Controller 都这么写
@PostMapping
public ResponseEntity<...> create(
        @RequestBody ApiRequests.CreateDealerRequest req,
        @RequestHeader(value = "X-Operator-Id", required = false) String actor) {
    service.createDealer(..., actor == null ? "system" : actor);
}
```

**`X-Operator-Id` 是客户端可任意伪造的请求头。** 请求方写什么，审计表就记什么。
更讽刺的是——JWT 拦截器明明已经验签并把真实登录名放进了请求属性：

```java
request.setAttribute("authUsername", username);   // ← 只写了，没人读
```

### 14.2 为什么这在金融系统里是严重问题

审计表的存在意义是回答"**谁**在**什么时点**基于**什么依据**做的**这个**判断"。
操作人可伪造，意味着这条链的第一环就断了：

| 能力 | 修复前 | 修复后 |
|---|---|---|
| 查出是谁改的经销商 | ❌ 客户端说什么就是什么 | ✅ 服务端验签的身份 |
| 验证内控"发起与执行分离" | ❌ 角色也是伪造的 | ✅ `actor_role` 自动写入 |
| 事后追责 | ❌ 无法定位自然人 | ✅ 可定位到 `users.username` |

**内控铁律"发起与执行分离"要能验证，靠的就是角色差异**——如果角色也是客户端填的，这条规则根本无法检查。

### 14.3 修复：统一解析，以令牌身份为准

新增 `web/.../config/AuditActor.java`：

```java
public static String resolve(HttpServletRequest request) {
    // 1) 首选：服务端验签得到的登录身份（不可伪造）
    Object authUsername = request.getAttribute("authUsername");
    if (authUsername != null && !authUsername.toString().isBlank()) {
        return authUsername.toString().trim();
    }
    // 2) 兜底：请求头（定时任务等无登录态场景）
    String header = request.getHeader("X-Operator-Id");
    if (header != null && !header.isBlank()) {
        return header.trim();
    }
    // 3) 都没有：系统操作
    return "system";
}
```

**为什么不直接删掉请求头支持**：定时作业（`JobController`）与部分内部调用没有登录态，
仍需要一个标识来区分"人操作"与"系统操作"。保留兜底，但**只要有令牌就一律以令牌身份为准**。

14 个 Controller、30 处调用点统一改造：

```java
// 改前
@RequestHeader(value = "X-Operator-Id", required = false) String actor
actor == null ? "system" : actor

// 改后
HttpServletRequest request
AuditActor.resolve(request)
```

### 14.4 顺带修好的：actor_role 从未被写入

`audit_events` 表**设计时就有** `actor_role` 列，但 `writeAudit` 的 INSERT 语句里根本没这一列 ——
622 条审计记录全是 NULL。表设计者想到了"要记角色"，实现时漏了。

现在按 `actor` 反查 `users.role` 自动补齐：

```java
String role = actorRole;
if ((role == null || role.isBlank()) && actor != null && !actor.isBlank()) {
    role = findRoleByUsername(actor);      // 反查 users.role
}
jdbc.update("INSERT INTO audit_events (actor, actor_role, action, ...) VALUES (?,?,?,...)",
        actor, role, action, ...);
```

**为什么放在仓储层而不是让 30 个调用点都传**：调用点传的是"操作人"，
角色是操作人的**派生属性**——同一个 `actor` 永远对应同一个角色。
在仓储层统一反查，既不用改 30 处签名，也不会出现"同一操作人两个角色"的不一致。

### 14.5 验证：伪造头无效

```bash
# 带 admin 令牌 + 伪造头 X-Operator-Id: forged_hacker 去创建经销商
```

实测结果：

```
审计表 actor = 'admin'        ← 令牌身份（不是 forged_hacker）
审计表 actor_role = 'ADMIN'   ← 角色自动补齐
```

该断言已固化进冒烟测试（`⑲-b 审计操作人不可伪造` 段，共 3 项断言）。

### 14.6 历史数据怎么办

**不回填。** 理由有二：

1. `audit_events` 是 append-only 表——**改写历史本身会破坏审计原则**。
   审计表的价值恰恰在于"记录一经写入便不可篡改"。
2. 当时的**真实身份客观上不存在于任何数据中**——客户端传的就是假值，
   无从推断当时究竟是谁操作的。硬回填一个"看起来对"的值，
   反而是在审计表里写入**新的不实信息**，比留空更危险。

因此处理方式是**在文档中标注清楚**：

| actor 值 | 含义 |
|---|---|
| `admin` / `operator` | 修复后记录，可信 |
| `system` | 定时作业 / 无登录态调用 |
| `1` / `verify-script` / `repair` | **修复前的伪造值，不可信** |

排查时以 `actor_role IS NOT NULL` 作为"这条记录可信"的判据。

## 15. 微服务化后的鉴权：一个 token 五个服务都能用（2026-11-20）

前面 14 章讲的是"单体里怎么加登录"。架构拆成网关 + 5 服务后，鉴权多了一个必须回答的问题：
**用户在 auth-service 登录拿到的 token，凭什么 credit/risk/bank/web 都认？**

### 15.1 三件事不变，两件事变了

**不变的（正是 JWT 的价值）：**

| 项 | 说明 |
|---|---|
| 签发逻辑不变 | `AuthApplicationService.login()` 原样搬到 auth-service，`domain`/`application` 作为共享依赖 |
| token 格式不变 | 还是 `头部.载荷.签名`，载荷里带 username / role / displayName / uid |
| 验签逻辑不变 | 还是 `AuthApplicationService.verify()`，拦截器每个请求前调一次 |

**变的：**

1. **入口变了**：登录请求打网关 18080 → 按 `/api/auth/**` 路由切到 auth-service（8081）；
   业务请求打网关 → 按路径切到 credit/risk/bank/web。**网关本身不验签**。
2. **验签点变多了**：不再是单体里一个拦截器，而是每个下游服务各自装配了同一套
   `JwtAuthInterceptor` + `WebMvcConfig`（从 `common` 模块导入），各自本地验签。

### 15.2 跨服务互通的关键：同密钥 + 本地验签

```
用户登录 → auth-service 签发 token（用密钥 K 签名）
                    │
浏览器存 token（localStorage: fp_token）
                    │ 后续每个请求带 Authorization: Bearer <token>
                    ▼
              网关 18080（只转发，不验签）
                    │ 按路径切流
       ┌────────────┼────────────┬────────────┐
       ▼            ▼            ▼            ▼
   credit-service risk-service bank-service  web
   （用同一密钥 K 本地验签，验过即放行）
```

- **同密钥**：五个服务的 `application.yml` 都配了相同的
  `floorplan.auth.secret`（开发默认 `dev-only-secret...`，生产用环境变量 `FLOORPLAN_AUTH_SECRET` 覆盖）。
  签名和验签用同一把钥匙，所以 auth 签的 token 别的服务也能验——**这是 token 能互通的唯一前提**。
- **本地验签**：每个服务独立验签，不依赖网关、不依赖 auth 服务在线（零信任）。
  即使某服务脱离网关被直连，也不会裸奔。
- **职责分离**：auth 服务只负责签发，不做业务；业务服务只负责验签，不管签发。
  这样密钥泄露面被限制在"需要验签的服务"范围内。

> **为什么不让网关统一验签**：一是改动集中在网关会形成单点，网关失守则全线失守；
> 二是各服务仍要被内部调用/测试直连，网关验签保护不到这些路径。
> 让每个服务自己验签，虽然重复但更符合零信任。等鉴权链完全定型，可再考虑上收到网关。

### 15.3 装配方式：common 模块 + 精确 @Import

七个横切类（`ApiResponse`、`RequirePermission`、`RequireAdmin`、`JwtAuthInterceptor`、
`WebMvcConfig`、`GlobalExceptionHandler`、`AuditActor`）收拢到新建的 `floorplan-common` 模块，
四个新服务通过启动类上的 `@Import` 精确装配，而不是复制四份代码、也不是全包扫描：

```java
@SpringBootApplication(scanBasePackages = "com.company.floorplan.credit")
@Import({
  CreditLineApplicationService.class, JdbcCreditLineRepository.class,
  JwtAuthInterceptor.class, WebMvcConfig.class,   // ← 来自 common，精确导入
  GlobalExceptionHandler.class, AuditActor.class
})
@EnableDiscoveryClient
public class CreditServiceApplication { ... }
```

> **例外**：auth-service 只导入 `GlobalExceptionHandler`，**不导入 `JwtAuthInterceptor`**——
> 否则登录接口本身会被 JWT 拦截器拦住，形成"要令牌才能拿令牌"的死锁。

### 15.4 验证：跨服务切流 + 统一鉴权

`smoke-test.py` 走网关 18080 的完整闭环（182 项断言全绿）就是这套机制的端到端证明：
顶部用 admin 登录拿到 token，后续请求带着它访问 credit/risk/bank/web 各类接口，
任一键不一致或任一服务没装配拦截器，都会立刻 401 暴露。

**排障速查**：

| 现象 | 可能原因 |
|---|---|
| 登录后访问别的服务全部 401 | 各服务 `floorplan.auth.secret` 不一致 |
| 登录接口本身 401 | auth-service 误装了 `JwtAuthInterceptor` |
| 某个服务所有请求 401，其他正常 | 该服务漏导入 `WebMvcConfig` / `JwtAuthInterceptor` |
| 网关 502 | 网关活但目标服务没起，或 `ROUTE_*` 直连端口配错 |

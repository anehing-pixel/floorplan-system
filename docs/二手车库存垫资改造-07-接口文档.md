## 1. 接口分层与方向

```
外部 partner ──(HTTPS + HMAC)──► external-api:18090 ──► integration.inbound_messages ──(核心轮询)──► CORE
CORE ──(业务事务内写 outbox)──► OutboundRelay ──► integration.outbound_tasks ──(DMZ 领取)──► 外部 partner
车商/内勤 ──► gateway:18080 ──► 各业务服务 :8080-8088
```

| 层 | 归属 | 认证 | 幂等载体 | 失败语义 |
|---|---|---|---|---|
| **A. 对外入站** | `external-api` | HMAC 签名 + IP 白名单 + scope | `Idempotency-Key` 或业务组合键 → `inbound_messages.idempotency_key` UNIQUE | 401/403/409/202 |
| **B. 对外出站** | `external-api`（签名与发送） | 我方以 partner secret 签名 | `outbound_tasks.idempotency_key` UNIQUE | 任务态，不进业务事务 |
| **C. 对内服务间** | `common/contract` Feign | 内部服务间沿用现有 JWT / 服务令牌 | 调用方传 `Idempotency-Key` | 4xx 直传，5xx 由调用方决定重试 |
| **D. 对内事件** | `common/event` `DomainEvent`/`EventConsumer` | — | `event_consumptions(event_id, consumer)` | 3 次后 DEAD |
| **E. 面向用户** | gateway → 业务服务 | JWT + `@RequirePermission` | 写操作必须带 `Idempotency-Key` | `ApiResponse.code` |

**四条不可协商的规则**（评审须逐条确认，实现阶段作为 ArchUnit / 冒烟断言目标）：

1. `external-api` **不承载业务逻辑、不写 `public` schema**（D02 §3 铁律）。任何「外部直接推进业务状态」的接口设计一律驳回。
2. `202 Accepted` **只表示报文已受理且验签通过，不表示业务成功**。响应体必须回 `process_status`（`RECEIVED`/`ACCEPTED`/`REJECTED_BY_GATE`）。
3. 跨服务取数**只允许**经 Feign 契约或事件投影；`external-api` 与任何服务**禁止读他人属主的表**（AGENTS.md §3.1）。
4. 消费者内部**禁止跨服务调用**（无 JWT 上下文，D02 §7 纪律 3）。需要对方数据时，读由事件投影出来的本地副本列。

## 2. 对外协议通用规范

### 2.1 传输与寻址

| 项 | 规定 |
|---|---|
| 协议 | HTTPS（TLS 1.2+），生产强制；本地 http 仅限联调 |
| Base URL | `https://<dmz-host>/external`（生产）；本地 `http://localhost:18090/external` |
| 方法 | 入站一律 `POST`（报文语义，非资源语义）；查询类允许 `GET` 并纳入签名串 |
| Content-Type | `application/json; charset=utf-8`；文件形态走 `multipart/form-data` 且 `X-Payload-Digest` 必填（`[D-04]`） |
| 请求体上限 | 单笔 1 MiB，批量端点 5 MiB（超限 413 `VALID_001`，在验签前用 `Content-Length` 早退） |

### 2.2 请求头（入站必填）

| Header | 必填 | 说明 |
|---|---|---|
| `X-Partner-Code` | ✔ | `integration.partners.partner_code`；必须 `ACTIVE` |
| `X-Timestamp` | ✔ | epoch **毫秒**；与本地时钟差超 `±300s` 拒（窗口可配，结构性参数在 yml） |
| `X-Nonce` | ✔ | 16–64 位十六进制；`(partner_code, nonce)` 在 TTL 内唯一 |
| `X-Key-Version` | ✔ | 密钥版本号；宽限期外旧版本一律 401 |
| `X-Signature` | ✔ | 小写十六进制 HMAC-SHA256 |
| `Idempotency-Key` | ✔（写类） | 缺失时按 §3.x 各接口的**业务组合键**自动派生并回显，不因此报错（降低 partner 改造成本） |
| `X-Trace-Id` | △ | 对方自带链路号，原样落 `inbound_messages.trace_id`；缺失则由 `RequestIdFilter` 生成 |
| `X-Payload-Digest` | △ | 文件形态必填，正文 SHA-256 |

### 2.3 签名算法（精确定义，双方按此实现）

```
canonical = METHOD.upper() + "\n"
          + PATH               -- 不含 query，不含 host，形如 /external/wms/inbound-confirm
          + X-Timestamp + "\n"
          + X-Nonce + "\n"
          + lowercase_hex( SHA-256( raw_body_bytes ) )

signature = lowercase_hex( HMAC_SHA256( secret, canonical ) )
```

| 规则 | 说明 |
|---|---|
| `PATH` 取值 | 以**网关剥离前缀之后**的实际服务路径为准，且该规则写入对接文档；变更前缀属破坏性变更 |
| 空 body | `POST` 无 body 时按空字节串取 SHA-256，即 `e3b0c442...9b855`（固定值，双方各自断言） |
| `GET` 查询 | `canonical` 的 body 段替换为 `raw query string`（未排序，按到达原样） |
| 密钥 | 每 partner 一条；轮换时新旧并存 `key_grace_until` 内均可验，期外仅新版本 |
| 校验顺序 | **时间戳 → nonce → 签名 → partner 状态/scope/IP → 幂等**（§2.6，先便宜后昂贵，且失败全留痕） |
| 比较 | 常量时间比较（`MessageDigest.isEqual`），禁止 `String.equals` 摘要 |
| 日志 | 只记 `partner_code` / `path` / 摘要前 8 位 / `signature_reason`；**禁止记 secret、完整签名、完整 body** |

### 2.4 幂等键规范

| 场景 | 键构成 | 落库位置 | 重复处理 |
|---|---|---|---|
| 对方显式传 `Idempotency-Key` | 原值（≤ 64 字符） | `inbound_messages.idempotency_key` | 同摘要 → 返回原 `message_id`（200）；**异摘要 → 409** |
| 未传（写类） | `SRC:{partner_code}:{业务组合键}` | 同上 | 同上 |
| 出站 | 见 D00 §13.2 | `outbound_tasks.idempotency_key` | 由唯一约束保证只建一条 |

> 「同键不同摘要 = 409」是硬要求：静默返回首次结果会掩盖对方的取数 bug，
> 而覆盖写入会让对方看到两次不同结论。本项目对幂等冲突的既有口径是 `CONFLICT_001`（409），保持一致。

### 2.5 响应语义（对外）

| HTTP | `code` | 含义 | 对方应做 |
|---|---|---|---|
| 202 | `OK` | 已受理、验签通过、等待核心消费 | 不要重投；用 §3.9 查询接口或等出站结果 |
| 200 | `OK` | 幂等命中，返回首次受理结果（含原 `message_id`） | 同上 |
| 200 | `OK` | 查询类成功 | — |
| 400 | `VALID_001` | 结构/字段校验失败，`details.field_errors[]` 逐项 | 修正后重投（新 nonce） |
| 401 | `PTNR_001`/`PTNR_003`/`PTNR_004` | 签名/时钟/重放 | 检查时钟与密钥版本 |
| 403 | `PTNR_002` | partner 停用 / scope 不含该端点 / IP 不在白名单 | 联系我方运营 |
| 404 | `NOT_FOUND_001` | 引用的业务对象不存在（如 VIN 未建账） | 核对主数据 |
| 409 | `CONFLICT_001`/`PTNR_005` | 幂等键内容冲突 | **停止重投**，人工对账 |
| 413 | `VALID_001` | 请求体超限 | 拆分批次 |
| 429 | `PTNR_006` | 超过 `rate_limit_per_min` | 按 `Retry-After` 退避 |
| 500 | `SYS_001` | 内部异常（**不吞成 200**，AGENTS.md §10） | 可安全重投（幂等键相同） |
| 503 | `PTNR_007` | partner 熔断开启 | 稍后重试 |

**受理类响应示例**（I-04）：

```json
{
  "code": "OK",
  "message": "已受理，等待业务处理",
  "data": {
    "message_id": 184237,
    "idempotency_key": "INB:WH01-JP-0007:JN1ML6BK7C2000123:IN20260115001",
    "process_status": "RECEIVED",
    "signature_ok": true,
    "received_at": "2026-01-15T11:02:33.481+09:00"
  },
  "traceId": "req-7f3c1a9d2b",
  "details": null
}
```

> `process_status` 只可能是 `RECEIVED` / `ACCEPTED`（已被核心领取但结论未出）/ `PROCESSED` / `REJECTED_BY_GATE`。
> **`RECEIVED` 不等于业务成功**——这条语义必须在对接文档里用加粗体写出来（红线 2）。

### 2.6 限流与配额

- 每 partner `rate_limit_per_min`（DB 列，默认 300）；滑动窗口计数在 `external-api` 内存，**多实例时各自计数**（`[待定源 U-06]`，需求书未指定集中限流组件；一期接受该下界，D02 风险表已登记）。
- 批量端点单次条数上限 500；超限 400，并提示分页/分批。
- 连续 5 次验签失败 → 该 partner 熔断 5 分钟（出站熔断则按 D02 §5.4 影响出站任务）。

### 2.7 数据格式约定

| 类型 | 格式 | 备注 |
|---|---|---|
| 金额 | JSON **整数**（日元） | 禁止字符串数字、禁止小数；`> 2^53` 不接受（实际远小于） |
| 比率 | 字符串 `"0.7500"` 或数字均可，入站统一按字符串解析为 `BigDecimal` | 避免二进制浮点误差 |
| 日期 | `YYYY-MM-DD` | `DATE` 列 |
| 时间 | ISO-8601 带偏移 `2026-01-15T11:02:33+09:00` | `TIMESTAMPTZ` 列 |
| VIN | 17 位 `[A-HJ-NPR-Z0-9]{17}`（排除 I/O/Q） | 日本車台番号同规格；短 VIN 一律 400 |
| 车牌 | 自由格式但去除连字符后存 `registration_plate` | 展示格式属前端 |
| 枚举 | D00 §8 大写值 | 未知值 400，不静默归 `OTHER`（P-7） |
| 空值 | 显式 `null`，不发 `"N/A"` / `""` / `"0"` 伪值 | `"N/A"` 会污染报表与 CHECK |
| 分页 | `page`（0 基）/ `size`（≤200）；响应 `data.total`、`data.page`、`data.size` | 与现有分页习惯一致 |
| 附件 | 只传**我方返回的 attachment 标识**，不在集成报文里传二进制（除文件形态） | 本地文件系统，U-R12 |

### 3.4 I-05 在库快照 / 盘点差异 `POST /external/wms/inventory-snapshot`

scope `WMS_SNAPSHOT_WRITE`；幂等键 `SNAP:{warehouse_code}:{snapshot_date}`。

| 字段 | 说明 |
|---|---|
| `warehouse_code`, `snapshot_date`, `item_count` | `item_count` 必须等于 `items[].length`，否则 400 |
| `items[]` | `{ vin, bin_location, odometer_km, condition_summary, inspection_certificate_no }` |
| `diff_hint` | 对方自评差异 `{ missing_vins[], extra_vins[] }`，**仅作参考**，我方一律重算 |

**语义**：同日重推 → 新行 + 旧行 `SUPERSEDED`，**绝不 UPDATE 明细**（D04 §3.17 不可变）。
快照不直接推进任何业务状态；推进来自 `ReconcileJob` 的差异结论。这是「快照是证据、比对是判定」的分工。
响应额外回 `my_side_count` 与 `preliminary_diff_count`，让对方能立刻发现推送残缺（降低联调成本，成本低收益高）。

### 3.5 I-07 出库 / 放证回执 `POST /external/wms/release-receipt`

scope `RELEASE_RECEIPT_WRITE`；幂等键 `RCP:{release_order_no}:{item_type}`。

| 字段 | 必填 | 说明 |
|---|---|---|
| `release_order_no` | ✔ | 必须处于 `SENT`/`ACKNOWLEDGED`，否则 409 `RELS_001` |
| `item_type` | ✔ | `VEHICLE`/`CERTIFICATE`/`KEY`（LEGACY）或 `INSPECTION_CERT`/`REGISTRATION_DOCS`/`OUTBOUND_DOC`（USED） |
| `result` | ✔ | `DELIVERED` / `PARTIAL` / `REFUSED` / `DAMAGED` / `NOT_FOUND` / `DELAYED` |
| `actual_items[]` | ✔ | 实际交付项集；与指令项集比对得出 `MISMATCH` |
| `received_at` | ✔ | |
| `receiver_name` | ✔ | 自然人姓名（PII，见 §12） |
| `odometer_km` | △ | 出库里程，用于与入库里程闭环 |
| `photo_attachment_ids[]` | △ | |
| `exception_reason` | `result≠DELIVERED` 时必填 | 空值 → 400 |

**验签要求（红线 2 的持久化保证）**：该回执生成的 `release_receipts.confirmation_authority`
**只能是 `PARTNER_RECEIPT`**，且必须写 `inbound_message_id`；DB 层 CHECK 保证二者成对出现（D04 §6 步骤 4）。
**对方不得在报文里自报 `confirmation_authority`**——该值由我方根据「请求是否验签通过且来自该端点」推导，
即使报文里出现同名字段也**一律忽略并记入 `details.ignored_fields[]`**（防社会工程伪造）。

副作用：`release_receipts`；`release_order_items.item_status`；状态机 →`CONFIRMED`/`PARTIAL`/`REJECTED`；

### 3.6 I-08 登记结果回执 `POST /external/registry/applications/{apply_no}/result`

## 4. 对外出站接口（Outbound）

出站由 `integration.outbound_tasks` 驱动，`external-api` 负责签名、发送、重试、留痕。
下表描述**我方发出的报文契约**；`Retry-Policy` 见 D02 §5.4。

### 4.1 I-03 落札款代付指令 `POST {partner_endpoint}/payments`

| 项 | 内容 |
|---|---|
| 幂等键 | `APAY:{auction_code}:{settlement_no}` |
| 触发 | 结算单确认 + 车商放款成功（同事务写事件，中继异步生成任务） |
| 请求体 | `{ settlement_no, auction_code, payee_member_no, amount, currency: "JPY", due_date, our_ref, line_items[] }` |
| 期望响应 | `200/202` + `{ status: "ACCEPTED", instruction_no }`；`instruction_no` 回写 `outbound_tasks.business_ref` |
| 错误映射 | 4xx 不重试（`DEAD` + 人工）；5xx / 超时 → 指数退避 5 次；对方返回「重复请求」语义视为成功（幂等友好） |
| 付款对象 | 拍卖场结算账户（`[待定源 D-01]`；若裁决为付车商，仅 `payee` 与 `partner_code` 变更，任务结构不变） |
| 禁止 | 在业务事务内同步调用；把付款结果直接写 `advances.status`（必须走回执入站） |

### 4.2 I-06 放车 / 放证指令下发与撤销 `POST {partner_endpoint}/release-orders` / `.../cancel`

| 项 | 内容 |
|---|---|
| 幂等键 | 下发 `RLO:{order_no}`；撤销 `RLC:{order_no}` |
| 请求体（下发） | `{ order_no, warehouse_code, vin, valid_until, issued_at, items: [ { item_type, receiver_type, receiver_code, instruction_text } ], trace_id }` |
| **按项接收方** | 每 `item` 自带 `receiver_code`（`WMS` / `AUCTION_VAULT` / `CERT_DEPOSITORY` / `LEGAL_AGENT`），**不使用单一 custodian**（D03 §3.6 I2） |
| 分派 | 若一项指令的 `items[]` 属于不同 `receiver_code`，出站层**按接收方拆成多任务**，每任务幂等键 `RLO:{order_no}:{receiver_code}` |
| 期望响应 | `200/202` + `{ status: "ACKNOWLEDGED", expected_completion_at? }` → 指令 `ACKNOWLEDGED` |
| 撤销前置 | 仅 `PENDING_RELEASE`/`SENT` 可撤；`ACKNOWLEDGED` 之后撤销须先与对方人工确认，系统不得单方面认为已撤（`RELS_003`） |
| 超期 | `expires_at` = `valid_until`；到点未 `ACKNOWLEDGED` → 巡检置 `EXPIRED`，**不自动重发**（重发是新指令号 + 新幂等键） |

### 4.3 I-09 违约车辆再出场委托 `POST {partner_endpoint}/auction/consignments`

| 项 | 内容 |
|---|---|
| 幂等键 | `DIS:{disposal_case_no}:{round}` |
| 请求体 | `{ disposal_case_no, round, vin, reserve_price, valuation_ref, handover_at, vault_code, notes }` |
| `reserve_price` | 处置底线价，来自**重估审慎值 × 政策系数**（R3.5 与 LEGACY 口径不同），须带 `valuation_id` 以便复现 |
| 结果回收 | 走 I-01 同族入站（复用解析器，`message_type=DISPOSAL_RESULT`） |
| 成交 | 写 `disposal_auctions` → `net_proceeds` → `liquidation_statements` DRAFT |
| 流拍 | `UNSOLD` → 告警 + round+1 需签认（X-15） |

### 4.4 I-12 行情 / 查定询价 `POST {partner_endpoint}/valuations/queries`

| 项 | 内容 |
|---|---|
| 幂等键 | `VALQ:{model_key}:{as_of_date}:{provider}` |
| 请求体 | `{ brand, model, model_year, mileage_km, repair_history, grade_hint, region, purpose }` |
| 期望响应 | `{ market_price, sample_count, confidence, trend_30d, as_of_date }` |
| 失败降级 | 全部 provider 失败 → `valuation.primary_source = INTERNAL_DEGRADED`，**禁止用于 `ADVANCE_BASE`**（D03 §2.4 I3）；只用于趋势展示 + 告警 `VALU_003` |
| 频率 | 批量重估走定时作业，单台询价走同步 Feign 到 `valuation` 侧（不直连外部，仍经任务表） |

## 5. 对内 Feign 契约（`common/contract`）

现状已有 `LoanQueryContract`、`CreditLineQueryContract`（W0-5，Feign `url` 开关直连）。USED 域**新增 6 个**，
全部放 `common/contract`，**由各服务实现、由调用方引用**，且每个契约**必须至少有一个真实调用方 + 一条冒烟断言**
（AGENTS.md §12 反模式第 2 条）。

| 契约 | 属主（实现方） | 主要调用方 | 方法 | 说明 |
|---|---|---|---|---|
| `VehicleValuationQueryContract` | `web`/valuation 侧 | loan、risk、release | `getActiveByVin(vin)` → `ValuationView{valuation_id, prudent_value, valid_until, primary_source, ltv_ratio, policy_code, policy_version}` | 放款/重估/处置取基准的**唯一入口**；返回 `null` 即视为无有效估值 |
| `AuctionLotQueryContract` | `web` | credit、risk | `getByLotKey(key)`、`sumOpenSettlementAmount(dealerId)` | 敞口口径：已落札未结算的在途额 |
| `InspectionCertificateQueryContract` | `web`/collateral-reg | loan、release、risk | `getByVin(vin)` → `{certificate_no, status, inspection_expiry_date, holder_custodian_code, encumbrance_status}` | 权属与車検証状态的读侧投影 |
| `CustodianQueryContract` | `web` | release、recon | `getActiveByCode(code)`、`listByPartner(partnerCode)` | `custodians` 首次有读写方的契约面 |
| `ReleaseOrderCommandContract` | release | `external-api`（**仅取指令快照用于出站**） | `snapshot(orderNo)` | ⚠️ `external-api` 只能读，不能借此回写状态（INV-1） |
| `DealerAdmissionQueryContract` | auth/dealer | loan、credit、risk | `admissionState(dealerId)` → `{state, license_valid, memberships[], compliance_valid}` | 闸门 G1 的数据源 |

**契约约束**

1. 契约 DTO 一律 `*View` 后缀、只读语义、字段命名与表列一致；**禁止**把实体直接暴露。
2. 契约路径必须与实现端点**逐字符一致**，且有断言从网关/直连两条路各打一次（AGENTS.md §12 反模式第 3 条）。
3. `external-api` 的 pom **不依赖 `domain`/`application`**，因此它只能用契约的 DTO 视图，不能引用枚举类——
   出站报文里的枚举一律以 `String` 传输，由属主服务负责解析（D02 §3 铁律 4）。
4. 新增/修改契约属**跨服务变更**，由收口方统一落 `common`，并行工作包不得自改 `common` 既有类。

## 6. 对内领域事件契约（`common/event`）

**复用 W0 已冻结的机制**：`DomainEvent`（含 `eventType`/`aggregateKey`/`payload`/`headers`）、
`EventConsumer`（`name()` + `onEvent()`）、`event_consumptions` 幂等、`consumer_offsets` 游标、3 次重试后 `DEAD`。
新增事件名由**收口方**统一加进 `common/contract/OutboxPublisher` 常量表（D00 §10），并行工作包不得各自加常量。

| 事件 | 生产时机 | aggregateKey | payload（**必含 `vin` + `traceId`**） | 消费者（`name()` 建议） |
|---|---|---|---|---|
| `LOAN_ADVANCED`（既有） | 放款成功 | `vin` | `{vin, advance_id, amount, traceId}` | 既有 |
| `CERTIFICATE_PLEDGED` | 車検証实体交付质押 | `vin + "PLEDGE"` | `{vin, certificate_no, holder_custodian_code, traceId}` | `collateral-reg.cert-pledge` |
| `VALUATION_REFRESHED` | 新估值生效 | `vin + "VAL"` | `{vin, valuation_id, prudent_value, primary_source, traceId}` | `risk.valuation-refresh` |
| `LTV_BREACH_DETECTED` | 重估后突破阈值 | `vin + "LTV"` | `{vin, valuation_id, actual_ratio, breach_threshold, traceId}` | `credit.ltv-breach` |
| `WMS_INBOUND_CONFIRMED` | 入库确认受理 | `vin + "INB"` | `{vin, warehouse_code, bin_location, odometer_km, traceId}` | `web.stock-in` |
| `RELEASE_ORDER_DISPATCHED` | 指令下发任务生成 | `order_no + "DISPATCH"` | `{vin, release_order_no, receiver_codes[], valid_until, traceId}` | `web.outbox-relay-seed` |
| `RELEASE_ORDER_RECEIPTED` | 权威回执消费成功 | `order_no + "RECEIPT"` | `{vin, release_order_no, item_type, result, traceId}` | `web.release-receipt` |
| `VEHICLE_SETTLED` | 回执全量 + 台账结清 | `vin + "ST" + settle_seq` | `{vin, settle_amount, traceId}` | `credit.settled` |
| `CREDIT_LINE_RESTORED` | 额度回补完成 | `dealer_id + "CLR"` | `{vin, dealer_id, restored_amount, traceId}` | `recon.credit-restored` |
| `REGISTRATION_DISCHARGED` | 抹消登记完成 | `vin + "DISCHARGE"` | `{vin, apply_no, registration_no, traceId}` | `risk.garage-clause-recheck`（D03 I6） |
| `DISPOSAL_AUCTION_RESULT` | 处置成交/流拍 | `case_no + "D" + round` | `{vin, disposal_case_no, hammer_price, status, traceId}` | `web.liquidation-draft` |

**三条纪律**（照抄 W0 教训，别改）

1. **`aggregateKey` 必须含「业务周期」后缀**（见上表 `"INB"` / `settle_seq` / `round`）。
   原因：`JdbcOutboxPublisher` 的去重键是 `(event_type, aggregate_key)` 且只排 `PENDING/SENT`——
   同 VIN 的第二次入库若用裸 `vin`，会与第一次撞键被静默吞掉（D02 风险 R-3）。
2. **消费者内部禁止跨服务调用**；需要别域数据时读事件投影出的本地副本列（无 JWT 上下文）。
3. **消费者 `name()` 全局唯一**且写进 `event_consumptions.consumer`；改名 = 历史幂等失效，须同步迁移幂等表。

## 9. 接口级校验与枚举字典

所有枚举以 D00 §8 为准，接口不得接受字典外取值。入站映射规则：

| 外部字段 | 我方枚举 | 未知值处理 |
|---|---|---|
| `repair_history` | `RepairHistoryFlag` | `""`/`null` → `UNKNOWN`（等同 `MAJOR` 收紧处理）；其他未知值 → 400 |
| `result`（I-07） | `ReceiptExceptionType` | 未知 → 400（不可静默归 `NONE`） |
| `cost_type` | 见 D04 §3.6 | 未知 → `OTHER`，但 `tax_treatment` 必须非空（税务口径待 D-02） |
| `check_type` / `result` | §3.8 | `UNKNOWN` 按不通过（P-7） |
| `purpose`（I-10） | `SALE_PROCEEDS` 等 | 未知 → `UNKNOWN` + 工单，不自动归属 |

> 未知值的两种处理并存是刻意的：**影响金额的**（税务、回款归属）宁可挂起工单；
> **影响准入的**（合规、修復歴）宁可从严拒绝。两者都不许「默认放行」。

## 10. 版本管理与兼容

| 规则 | 说明 |
|---|---|
| 对外无 URL 版本 | 一期不加 `/v1`；用「只增不改不删」约束 + `X-Api-Version` 记录（可空） |
| 破坏性变更 | 字段删除/语义变更/签名串构成变更 = 破坏性，须提前 60 日通知并双版本并行（`key_version` 并行机制同源） |
| 字段新增 | 直接加可选字段，入站忽略未知字段但回显 `details.ignored_fields[]`（**让对发现拼写错误**，静默忽略是联调黑洞） |
| 对内契约 | 契约方法只加不改签名；需改签名时新建方法并保留旧方法一个发布周期，且冒烟同时断言两条路径 |
| 事件 | 事件 payload 只加字段；消费者须容忍未知字段（Jackson `FAIL_ON_UNKNOWN_PROPERTIES=false`） |
| 下线 | 端点下线须先在 `call_logs` 确认 90 日零调用 |

## 12. 安全与个人信息（R11 / R12 / 個人情報保護法）

| 数据 | 处理 |
|---|---|
| `secret` | 只在 `partners.secret_ref` 存引用；**任何 GET 响应不回显明文**；日志禁止出现 |

| 报文全文 | 只 `inbound_messages` 留文件引用 `payload_ref`；`call_logs` 只留摘要与哈希（需求书 R11.3） |
| 个人住所/氏名 | 明文列**只存在于 `inspection_certificates`**（法律要件，必须保外），其余表引用 `certificate_id`；查询接口默认脱敏，完整视图需 `PII_READ_FULL` 权限并写审计 |
| 银行账号 | 一律 `*_ref` 引用，不落明文 |
| 征信命中详情 | 只回 `hit_summary`，禁止批量拉取原始明细（§3.8） |
| 保留期 | 见 D00 §12 默认（报文与调用留痕 5 年）；到期归档到**本地冷存文件**，不引入对象存储 |
| 越权自查 | `GET /external/messages/{id}` 跨 partner → 403 + 告警 `PARTNER_SCOPE_VIOLATION` |

## 13. 自检

- I-01…I-12 **全部覆盖**（8 入站 + 4 出站），无「表里有列但接口不传」或「接口有字段但库里没落」的悬空项。
- 每条写接口有：scope、幂等键、字段校验表、错误码、副作用（表 + 审计 + 事件）四件套。
- 红线 1（§4.2 `dispatch` 不生成指令、`RELS_002`）与红线 2（§3.5 authority 由验签推导、CHECK 成对、`INTERNAL_WITNESS` 永久区分）在接口面有**结构性**保证，不靠约定。
- 出站报文里枚举以 `String` 传输，符合「`external-api` 不依赖 `domain`」铁律。
- 事件 `aggregateKey` 一律带业务周期后缀，规避 `JdbcOutboxPublisher` 的 `(event_type, aggregate_key)` 去重吞事件（R-3）。
- 未签字项：`D-01`（付款对象）、`D-02`（税务标识与许可有效期）、`D-04`（报文形态与文件通道）、
  `D-09`（`sealed_flag`/`key_handed_over` 是否启用）、`U-09`（回执 SLA 与效力分级）、`U-06`（多实例限流一致性）。

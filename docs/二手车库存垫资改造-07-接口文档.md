## 1. 接口分层与方向

```
外部 partner ──(HTTPS + HMAC)──► external-api:18090 ──► integration.inbound_messages ──(核心轮询)──► CORE
CORE ──(业务事务内写 outbox)──► OutboundRelay ──► integration.outbound_tasks ──(DMZ 领取)──► 外部 partner
车商/内勤 ──► gateway:18080 ──► 各业务服务 :8080-8088
```

| 层 | 归属 | 认证 | 幂等载体 | 失败语义 |
|---|---|---|---|---|
| **A. 对外入站** | `external-api` | HMAC 签名 + IP 白名单 + scope | `Idempotency-Key` 或业务组合键 → `inbound_messages.idempotency_key` UNIQUE | 401/403/409/202 |
| **B. 对外出站** | `external-api`（签名与发送） | 我方以 partner secret 签名 | `outbound_tasks.idempotency_key` UNIQUE | 任务态，不进业务事务 |
| **C. 对内服务间** | `common/contract` Feign | 内部服务间沿用现有 JWT / 服务令牌 | 调用方传 `Idempotency-Key` | 4xx 直传，5xx 由调用方决定重试 |
| **D. 对内事件** | `common/event` `DomainEvent`/`EventConsumer` | — | `event_consumptions(event_id, consumer)` | 3 次后 DEAD |
| **E. 面向用户** | gateway → 业务服务 | JWT + `@RequirePermission` | 写操作必须带 `Idempotency-Key` | `ApiResponse.code` |

**四条不可协商的规则**（评审须逐条确认，实现阶段作为 ArchUnit / 冒烟断言目标）：

1. `external-api` **不承载业务逻辑、不写 `public` schema**（D02 §3 铁律）。任何「外部直接推进业务状态」的接口设计一律驳回。
2. `202 Accepted` **只表示报文已受理且验签通过，不表示业务成功**。响应体必须回 `process_status`（`RECEIVED`/`ACCEPTED`/`REJECTED_BY_GATE`）。
3. 跨服务取数**只允许**经 Feign 契约或事件投影；`external-api` 与任何服务**禁止读他人属主的表**（AGENTS.md §3.1）。
4. 消费者内部**禁止跨服务调用**（无 JWT 上下文，D02 §7 纪律 3）。需要对方数据时，读由事件投影出来的本地副本列。

## 2. 对外协议通用规范

### 2.1 传输与寻址

| 项 | 规定 |
|---|---|
| 协议 | HTTPS（TLS 1.2+），生产强制；本地 http 仅限联调 |
| Base URL | `https://<dmz-host>/external`（生产）；本地 `http://localhost:18090/external` |
| 方法 | 入站一律 `POST`（报文语义，非资源语义）；查询类允许 `GET` 并纳入签名串 |
| Content-Type | `application/json; charset=utf-8`；文件形态走 `multipart/form-data` 且 `X-Payload-Digest` 必填（`[D-04]`） |
| 请求体上限 | 单笔 1 MiB，批量端点 5 MiB（超限 413 `VALID_001`，在验签前用 `Content-Length` 早退） |

### 2.2 请求头（入站必填）

| Header | 必填 | 说明 |
|---|---|---|
| `X-Partner-Code` | ✔ | `integration.partners.partner_code`；必须 `ACTIVE` |
| `X-Timestamp` | ✔ | epoch **毫秒**；与本地时钟差超 `±300s` 拒（窗口可配，结构性参数在 yml） |
| `X-Nonce` | ✔ | 16–64 位十六进制；`(partner_code, nonce)` 在 TTL 内唯一 |
| `X-Key-Version` | ✔ | 密钥版本号；宽限期外旧版本一律 401 |
| `X-Signature` | ✔ | 小写十六进制 HMAC-SHA256 |
| `Idempotency-Key` | ✔（写类） | 缺失时按 §3.x 各接口的**业务组合键**自动派生并回显，不因此报错（降低 partner 改造成本） |
| `X-Trace-Id` | △ | 对方自带链路号，原样落 `inbound_messages.trace_id`；缺失则由 `RequestIdFilter` 生成 |
| `X-Payload-Digest` | △ | 文件形态必填，正文 SHA-256 |

### 2.3 签名算法（精确定义，双方按此实现）

```
canonical = METHOD.upper() + "\n"
          + PATH + "\n"            -- 不含 host，不含 query，形如 /external/wms/inbound-confirm
          + QUERY + "\n"           -- 到达原样的 query string（未排序、未解码）；无 query 时为**空串但仍占一行**
          + X-Timestamp + "\n"
          + X-Nonce + "\n"
          + X-Key-Version + "\n"
          + lowercase_hex( SHA-256( raw_body_bytes ) )

signature = lowercase_hex( HMAC_SHA256( secret, canonical ) )
```

> **本块 2026-11-22 由 D13 §3 G9 修正，是三处口径合一后的唯一规范源**（D02 §5.4 已同步）。
> 原稿有三个会让双方各自实现出不兼容结果的缺陷：
> ① `PATH` 与 `X-Timestamp` 之间**没有分隔符**——`PATH="/a"` + `ts="12"` 与
> `PATH="/a1"` + `ts="2"` 会拼出同一条 canonical，签名的**字段边界不唯一**，
> 这是对签名方案的实质破坏（不是风格问题），中间人可据此把一个请求的合法签名搬到另一个语义上；
> ② `X-Key-Version` 是必传头且**决定用哪把密钥验签**，却不在签名串里——
> 宽限期内可被改写成旧版本或新版本，密钥选择脱离了签名保护；
> ③ `GET` 的 query 参与规则在 D02/D07 各写一套（D02 恒为 `SHA256(body)`，本节把 body 段换成 raw query），
> 于是「同一请求两边签出不同串」。现定：**query 单列一段，永远占位**，body 摘要永远另算，
> 两者不再互相替换；GET 无 body 时末段取空字节串的固定摘要 `e3b0c442…9b855`（与 POST 空 body 同值，规则统一）。
> 编码口径统一为**小写十六进制**（D02 原写 base64，已改）——这一条属对接文档定义，以本节为准。

| 规则 | 说明 |
|---|---|
| `PATH` 取值 | 以**网关剥离前缀之后**的实际服务路径为准，且该规则写入对接文档；变更前缀属破坏性变更 |
| 空 body | `POST` 无 body 时按空字节串取 SHA-256，即 `e3b0c442...9b855`（固定值，双方各自断言） |
| `GET` 查询 | query 走 `QUERY` 段（见上方 canonical），**不再替换 body 段**；无 query 时空串占位 |
| 密钥 | 每 partner 一条；轮换时新旧并存 `key_grace_until` 内均可验，期外仅新版本 |
| 校验顺序 | **时间戳 → nonce → 签名 → partner 状态/scope/IP → 幂等**（§2.6，先便宜后昂贵，且失败全留痕） |
| 比较 | 常量时间比较（`MessageDigest.isEqual`），禁止 `String.equals` 摘要 |
| 日志 | 只记 `partner_code` / `path` / 摘要前 8 位 / `signature_reason`；**禁止记 secret、完整签名、完整 body** |

### 2.4 幂等键规范

| 场景 | 键构成 | 落库位置 | 重复处理 |
|---|---|---|---|
| 对方显式传 `Idempotency-Key` | 原值（≤ 64 字符） | `inbound_messages.idempotency_key` | 同摘要 → 返回原 `message_id`（200）；**异摘要 → 409** |
| 未传（写类） | `SRC:{partner_code}:{业务组合键}` | 同上 | 同上 |
| 出站 | 见 D00 §13.2 | `outbound_tasks.idempotency_key` | 由唯一约束保证只建一条 |

> 「同键不同摘要 = 409」是硬要求：静默返回首次结果会掩盖对方的取数 bug，
> 而覆盖写入会让对方看到两次不同结论。本项目对幂等冲突的既有口径是 `CONFLICT_001`（409），保持一致。

### 2.5 响应语义（对外）

| HTTP | `code` | 含义 | 对方应做 |
|---|---|---|---|
| 202 | `OK` | 已受理、验签通过、等待核心消费 | 不要重投；用 §3.9 查询接口或等出站结果 |
| 200 | `OK` | 幂等命中，返回首次受理结果（含原 `message_id`） | 同上 |
| 200 | `OK` | 查询类成功 | — |
| 400 | `VALID_001` | 结构/字段校验失败，`details.field_errors[]` 逐项 | 修正后重投（新 nonce） |
| 401 | `PTNR_001`/`PTNR_003`/`PTNR_004` | 签名/时钟/重放 | 检查时钟与密钥版本 |
| 403 | `PTNR_002` | partner 停用 / scope 不含该端点 / IP 不在白名单 | 联系我方运营 |
| 404 | `NOT_FOUND_001` | 引用的业务对象不存在（如 VIN 未建账） | 核对主数据 |
| 409 | `CONFLICT_001`/`PTNR_005` | 幂等键内容冲突 | **停止重投**，人工对账 |
| 413 | `VALID_001` | 请求体超限 | 拆分批次 |
| 429 | `PTNR_006` | 超过 `rate_limit_per_min` | 按 `Retry-After` 退避 |
| 500 | `SYS_001` | 内部异常（**不吞成 200**，AGENTS.md §10） | 可安全重投（幂等键相同） |
| 503 | `PTNR_007` | partner 熔断开启 | 稍后重试 |

**受理类响应示例**（I-04）：

```json
{
  "code": "OK",
  "message": "已受理，等待业务处理",
  "data": {
    "message_id": 184237,
    "idempotency_key": "INB:WH01-JP-0007:JN1ML6BK7C2000123:IN20260115001",
    "process_status": "RECEIVED",
    "signature_ok": true,
    "received_at": "2026-01-15T11:02:33.481+09:00"
  },
  "traceId": "req-7f3c1a9d2b",
  "details": null
}
```

> `process_status` 只可能是 `RECEIVED` / `ACCEPTED`（已被核心领取但结论未出）/ `PROCESSED` / `REJECTED_BY_GATE`。
> **`RECEIVED` 不等于业务成功**——这条语义必须在对接文档里用加粗体写出来（红线 2）。

### 2.6 限流与配额

- 每 partner `rate_limit_per_min`（DB 列，默认 300）；滑动窗口计数在 `external-api` 内存，**多实例时各自计数**（`[待定源 U-06]`，需求书未指定集中限流组件；一期接受该下界，D02 风险表已登记）。
- 批量端点单次条数上限 500；超限 400，并提示分页/分批。
- 连续 5 次验签失败 → 该 partner 熔断 5 分钟（出站熔断则按 D02 §5.4 影响出站任务）。

### 2.7 数据格式约定

| 类型 | 格式 | 备注 |
|---|---|---|
| 金额 | JSON **整数**（日元） | 禁止字符串数字、禁止小数；`> 2^53` 不接受（实际远小于） |
| 比率 | 字符串 `"0.7500"` 或数字均可，入站统一按字符串解析为 `BigDecimal` | 避免二进制浮点误差 |
| 日期 | `YYYY-MM-DD` | `DATE` 列 |
| 时间 | ISO-8601 带偏移 `2026-01-15T11:02:33+09:00` | `TIMESTAMPTZ` 列 |
| VIN | 17 位 `[A-HJ-NPR-Z0-9]{17}`（排除 I/O/Q） | 日本車台番号同规格；短 VIN 一律 400 |
| 车牌 | 自由格式但去除连字符后存 `registration_plate` | 展示格式属前端 |
| 枚举 | D00 §8 大写值 | 未知值 400，不静默归 `OTHER`（P-7） |
| 空值 | 显式 `null`，不发 `"N/A"` / `""` / `"0"` 伪值 | `"N/A"` 会污染报表与 CHECK |
| 分页 | `page`（0 基）/ `size`（≤200）；响应 `data.total`、`data.page`、`data.size` | 与现有分页习惯一致 |
| 附件 | 只传**我方返回的 attachment 标识**，不在集成报文里传二进制（除文件形态） | 本地文件系统，U-R12 |

### 4.1 I-03 落札款代付指令 `POST {partner_endpoint}/payments`

**契约约束**

1. 契约 DTO 一律 `*View` 后缀、只读语义、字段命名与表列一致；**禁止**把实体直接暴露。
2. 契约路径必须与实现端点**逐字符一致**，且有断言从网关/直连两条路各打一次（AGENTS.md §12 反模式第 3 条）。
3. `external-api` 的 pom **不依赖 `domain`/`application`**，因此它只能用契约的 DTO 视图，不能引用枚举类——
   出站报文里的枚举一律以 `String` 传输，由属主服务负责解析（D02 §3 铁律 4）。
4. 新增/修改契约属**跨服务变更**，由收口方统一落 `common`，并行工作包不得自改 `common` 既有类。

> 加了字面后缀但**没有周期成分**，`aggregate_key` 对同一 VIN 仍是常量，于是第二次质押、
> 第二次重估、退库后再入库会被 `WHERE NOT EXISTS` 静默吞掉（`JdbcOutboxPublisher.java:41-48` 的判据含 `SENT`）。
> 「带后缀」不等于「每次唯一」，这是本轮最容易看错过去的一处。
> 同理 `LOAN_ADVANCED` 这个名字在主干与 D00 §10 词表里都不存在（实际常量是 `EVENT_LOAN_CREATED`），
> 按 D12 §3 词表纪律改回 `LOAN_CREATED`。

**三条纪律**（照抄 W0 教训，别改）

1. **`aggregateKey` 必须是「这一次发生」的业务主键**（`*_id` / `*_no` / `*_seq`，见上表），
   **裸 `vin` 与「`vin` + 固定后缀」都不合格**。
   原因：`JdbcOutboxPublisher` 的去重键是 `(event_type, aggregate_key)` 且只排 `PENDING/SENT`——
   同 VIN 的第二次入库若用裸 `vin`，会与第一次撞键被静默吞掉（D02 风险 R-3）。
2. **消费者内部禁止跨服务调用**；需要别域数据时读事件投影出的本地副本列（无 JWT 上下文）。
3. **消费者 `name()` 全局唯一**且写进 `event_consumptions.consumer`；改名 = 历史幂等失效，须同步迁移幂等表。

**变更规矩（三句话）**：
1. **新增前缀 = 一次网关变更**，要么复用已有谓词（改路径名去贴前缀），要么由收口方在
   `gateway/.../application.yml` 加路由；并行包**两条都不许自己动手**，写进收口清单。
2. **落 core 兜底是合法落点**，不算「没接上」；但 D11 的每条端点断言必须标明是从 **18080** 打进去的，
   否则「core 兜底把请求接走」和「服务真的实现了」在冒烟里长得一模一样。
3. 上面标 ⚠️ 的 5 行（dealers / releases vs release-orders / release-orders 前缀 / partners 属主 /
   liquidation-statements 属主）是**开工门禁**：W-U1/W-U4/W-U3 各自第一步就是把对应那一行的归属定下来，
   定完再写 Controller——反过来做就是返工。

**`settle_seq` 定源（原稿全设计集只在 D09 引用、无定义，2026-11-22 D13 G7 补）**：

- `settle_seq VARCHAR(64)`，构成 = `{order_no}:{release_receipts.id}`（`vin` 不重复进串——
  D09 §7 的回补幂等键已是 `CLR:{vin}:{settle_seq}`，串里再带 vin 只是把同一标识写两遍）；
  一条回执只结清一台车 ⟹ 该串**天然每「这一次结清」唯一且不可复用**，正好是 D00 §10.2
  为 `VEHICLE_SETTLED` 选的 `aggregate_key` 形态（不用裸 `vin`）。
- 落库：`vehicle_ledger.settle_seq`（V67 段内加列，随 `lien_extinguished_at` 一起，见 D04 §5.2），
  **带部分唯一索引** `WHERE settle_seq IS NOT NULL`。
- 不要拿 `release_order_items.id` 顶替：项可拆多次部分释放（`PARTIAL`），
  用项 id 会把「同一项的第二笔补齐回执」当重复吞掉——与 G2 同一形状的错误。

**`/dispatch` 的重校验清单（原稿写「只能推进既有指令」，没说什么情况下**不许**推进；UC-R7-2 因此无守卫，2026-11-22 D13 G8 补）**：

| 下发时必须重查（**只查不写**，保持幂等） | 不满足 | 错误码 |
|---|---|---|
| 指令仍属本 `dealer`，`status ∈ {PENDING_RELEASE}`（或撤销后重新激活的新号） | 拒发 | `RELS_001` |
| `valid_until` 未到 | 拒发 + 置 `EXPIRED` | `RELS_003` |
| 该借据/额度线**当前未冻结**（`credit_lines.status`、`risk_alerts` 未决 CRITICAL） | 拒发 | `CREDIT_003` |
| 每个 item 仍处可释放态（未被并发取消） | 拒发（整单，不留半单） | `RELS_004` |
| 幂等键 `RLO:{order_no}:{dispatch_seq}` 未消耗 | 返回首次结果，**不重发** | — |

> 建单时查过闸门**不等于**下发时还能过：从建单到下发之间可能插入冻结、过期、并发取消。
> 「创建时校验一次」是这条链路唯一真正的重复放款面，所以重查项要写成清单，不能留给实现者自觉。
> 错误码取自 D00 §12 预留段 `RELS_001`–`006`（主干 `ErrorCode` 目前**没有** `RELS_*`，
> 逐码语义要由 W-U4 在 D00 登记、由收口方落进 `domain/exception/ErrorCode`，
> 不许在 service 里各自 `new BusinessException("RELS_003")` 造出第二套）。

## 9. 接口级校验与枚举字典

所有枚举以 D00 §8 为准，接口不得接受字典外取值。入站映射规则：

| 外部字段 | 我方枚举 | 未知值处理 |
|---|---|---|
| `repair_history` | `RepairHistoryFlag` | `""`/`null` → `UNKNOWN`（等同 `MAJOR` 收紧处理）；其他未知值 → 400 |
| `result`（I-07） | `ReceiptExceptionType` | 未知 → 400（不可静默归 `NONE`） |
| `cost_type` | 见 D04 §3.6 | 未知 → `OTHER`，但 `tax_treatment` 必须非空（税务口径待 D-02） |
| `check_type` / `result` | §3.8 | `UNKNOWN` 按不通过（P-7） |
| `purpose`（I-10） | `SALE_PROCEEDS` 等 | 未知 → `UNKNOWN` + 工单，不自动归属 |

> 未知值的两种处理并存是刻意的：**影响金额的**（税务、回款归属）宁可挂起工单；
> **影响准入的**（合规、修復歴）宁可从严拒绝。两者都不许「默认放行」。

## 10. 版本管理与兼容

| 规则 | 说明 |
|---|---|
| 对外无 URL 版本 | 一期不加 `/v1`；用「只增不改不删」约束 + `X-Api-Version` 记录（可空） |
| 破坏性变更 | 字段删除/语义变更/签名串构成变更 = 破坏性，须提前 60 日通知并双版本并行（`key_version` 并行机制同源） |
| 字段新增 | 直接加可选字段，入站忽略未知字段但回显 `details.ignored_fields[]`（**让对发现拼写错误**，静默忽略是联调黑洞） |
| 对内契约 | 契约方法只加不改签名；需改签名时新建方法并保留旧方法一个发布周期，且冒烟同时断言两条路径 |
| 事件 | 事件 payload 只加字段；消费者须容忍未知字段（Jackson `FAIL_ON_UNKNOWN_PROPERTIES=false`） |
| 下线 | 端点下线须先在 `call_logs` 确认 90 日零调用 |

## 12. 安全与个人信息（R11 / R12 / 個人情報保護法）

| 数据 | 处理 |
|---|---|
| `secret` | 只在 `partners.secret_ref` 存引用；**任何 GET 响应不回显明文**；日志禁止出现 |
| 完整签名 | 日志只留前 8 位 |
| 报文全文 | 只 `inbound_messages` 留文件引用 `payload_ref`；`call_logs` 只留摘要与哈希（需求书 R11.3） |
| 个人住所/氏名 | 明文列**只存在于 `inspection_certificates`**（法律要件，必须保外），其余表引用 `certificate_id`；查询接口默认脱敏，完整视图需 `PII_READ_FULL` 权限并写审计 |
| 银行账号 | 一律 `*_ref` 引用，不落明文 |
| 征信命中详情 | 只回 `hit_summary`，禁止批量拉取原始明细（§3.8） |
| 保留期 | 见 D00 §12 默认（报文与调用留痕 5 年）；到期归档到**本地冷存文件**，不引入对象存储 |
| 越权自查 | `GET /external/messages/{id}` 跨 partner → 403 + 告警 `PARTNER_SCOPE_VIOLATION` |

## 13. 自检

- I-01…I-12 **全部覆盖**（8 入站 + 4 出站），无「表里有列但接口不传」或「接口有字段但库里没落」的悬空项。
- 每条写接口有：scope、幂等键、字段校验表、错误码、副作用（表 + 审计 + 事件）四件套。
- 红线 1（§4.2 `dispatch` 不生成指令、`RELS_002`）与红线 2（§3.5 authority 由验签推导、CHECK 成对、`INTERNAL_WITNESS` 永久区分）在接口面有**结构性**保证，不靠约定。
- 出站报文里枚举以 `String` 传输，符合「`external-api` 不依赖 `domain`」铁律。
- 事件 `aggregateKey` 一律带业务周期后缀，规避 `JdbcOutboxPublisher` 的 `(event_type, aggregate_key)` 去重吞事件（R-3）。
- 未签字项：`D-01`（付款对象）、`D-02`（税务标识与许可有效期）、`D-04`（报文形态与文件通道）、
  `D-09`（`sealed_flag`/`key_handed_over` 是否启用）、`U-09`（回执 SLA 与效力分级）、`U-06`（多实例限流一致性）。

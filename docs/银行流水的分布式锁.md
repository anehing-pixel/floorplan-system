# 银行流水的分布式锁 · 设计说明

> 对应代码：`domain/service/DistributedLock.java`、`LockHandle.java`、
> `infrastructure/lock/RedisDistributedLock.java`、`InMemoryDistributedLock.java`、
> `application/service/BankFetchApplicationService.java`
>
> 一句话：**这是一把"互斥锁"，不是"分布式事务锁"。它保证"同一时刻只有一个执行者"，
> 不提供原子提交，也没有 2PC。锁保效率，约束保正确。**

---

## 一、先证明"这里必须用分布式锁"

判据只有一句：

> **临界区里有没有数据库管不住的东西？**

有（外部调用、跨系统副作用）→ 需要分布式锁。
没有（同库状态变更）→ 行锁 + 唯一约束就够了，加锁是给自己制造"锁与数据不同源"的新窗口。

按这条判据看银行流水采集：

```
拉取（HTTP/SFTP 调银行，耗时不确定、可能超时）
  → 解析（MT940 / CSV 逐行）
  → 逐行写 payment_transactions
```

第一段就把这条路封死了：**数据库事务包不住 HTTP 调用**。

- 包在事务里 → 银行接口超时 30 秒，连接池被占 30 秒；
- 事务回滚 → 文件已经拉下来了、日志已经写了，回滚撤不掉外部副作用。

所以这里的互斥不能靠 `SELECT ... FOR UPDATE`——你没法对"一次文件下载"加行锁。

对照项目里其他几处，差别很清楚：

| 位置 | 临界区里有库外的东西吗 | 用什么 |
|---|---|---|
| 额度占用 / 释放 | 没有 | `SELECT ... FOR UPDATE`，锁与数据同事务 |
| 结清 / 赎回 | 没有 | 同上 |
| 年审冻结 | 没有 | 行锁 + 锁内检查（**检查必须在锁内**，见第十节） |
| 放款出账 | 有（调支付网关） | 锁 + 条件更新 + 幂等键 |
| **银行流水采集** | **有（拉银行文件）** | **本文这把锁** |

## 二、接口设计：四条写进契约的语义

```java
public interface DistributedLock {
    Optional<LockHandle> tryLock(String key, Duration ttl);
    String provider();
}
```

只两个方法，但四条语义是**硬约束**，不是建议：

### 1. 不阻塞，拿不到立刻返回 `empty`

```java
Optional<LockHandle> handle = distributedLock.tryLock(lockKey, lockTtl);
if (handle.isEmpty()) { /* 直接跳过这个账户，不等待、不自旋 */ }
```

理由：批处理拿不到锁就该退出，而不是占着 Tomcat 线程自旋。
一个"等 30 秒再试"的锁，在定时任务里会变成线程堆积——**锁的作用是快速失败，不是排队**。

### 2. 不自动续期

TTL 必须大于外部调用超时，**到期就失效，绝不延长**。

看门狗续期会掩盖一个事实：**"这次外部调用卡住了"**。
一个本该失败的作业被无限延长，锁也就永远不释放，下一轮永远抢不到。
宁可租约到期重跑一次（重复入账由唯一约束挡住），也不要让一个僵死的执行者一直握着锁。

> 「如果业务确实需要更长时间怎么办」「怎么判断是 IO 慢还是真卡死」——见 **附录 B**。
> 结论是缩短锁的作用域，而不是续期。

### 3. 释放必须比对持有者

```java
// 错：只按 key 删除
redis.delete(key);

// 对：Lua 里比对 token 再删
"if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end"
```

失败场景：A 的租约到期 → B 拿到锁 → A 才执行到 `finally` 里的 unlock。
如果 unlock 只按 key 删除，**它会删掉 B 的锁**，于是 C 又能进来，互斥彻底失效。

所以 `LockHandle` 不是简单的 `void unlock()`，它持有**每次唯一的 token**：

```java
public final class LockHandle implements AutoCloseable {
    private final String key;
    private final String token;          // UUID，释放时比对
    private final AtomicBoolean released = new AtomicBoolean(false);

    public void release() {
        if (!released.compareAndSet(false, true)) return;   // 幂等，重复调用无副作用
        try {
            releaser.run();
        } catch (RuntimeException ignored) {
            // 主动忽略：TTL 是最终兜底。此处只吞释放异常，不吞业务异常。
        }
    }
}
```

两点值得说：`release()` **可重复调用**（`try-with-resources` + `finally` 双保险不会互相干扰）；
释放失败**不抛异常**——把释放异常抛出去，只会让已经成功的业务变成失败。

### 4. 锁服务不可用时 fail-closed

```java
try {
    acquired = redis.opsForValue().setIfAbsent(key, token, ttl);
} catch (RuntimeException e) {
    // fail-closed：锁服务不可用 → 作业失败，而不是无锁裸奔
    throw new IllegalStateException("分布式锁服务不可用，作业中止（fail-closed）：key=" + key, e);
}
```

Redis 连不上时，两种选择：

| 策略 | 行为 | 后果 |
|---|---|---|
| fail-open | 当作没锁，直接跑 | 多实例同时跑 → 流水重复拉取、批次统计被污染 |
| **fail-closed** | 作业失败，等人处理 | 少跑一次 |

选 fail-closed 的理由是业务性质：**少跑可以补，多跑收不回。**
流水重复还能被唯一约束兜住，但如果这个模式被用到通知派发上，就是客户手机里多一条短信——撤不回来。

## 三、锁键设计：粒度必须和争用对象对齐

```java
String lockKey = "lock:bank:fetch:" + accountRef + ":" + to;
// 例：lock:bank:fetch:ACC-001:2026-11-08
```

命名规范：`lock:{域}:{动作}:{业务标识}`。

三个决策：

**① 粒度是「账户」，不是「作业」**

| 方案 | 5 个账户并发 | 问题 |
|---|---|---|
| `lock:bank:fetch`（作业级） | 排队串行 | 5 个账户之间毫无冲突，作业时长 ×5 |
| **`lock:bank:fetch:{accountRef}:{date}`** | 并行 | 无 |

同一账户必须串行：并发拉同一账户会同时触发同一批唯一键冲突，浪费连接、污染批次统计；
**不同账户必须并行**：它们争的不是同一份资源。粒度错配的代价是作业时长乘以账户数。

**② 锁键带业务日**

`...:2026-11-08` 这一段让"昨天的补拉"不挡"今天的正常拉取"。
补数据是常态操作，不能因为它占住正常链路。

**③ 键里不放会变的东西**

不要放 `batchNo`、不放 `UUID`、不放精确到秒的时间戳。
锁键是"资源标识"，不是"本次执行标识"——后者每次不同，等于每次都是新锁，互斥归零。

## 四、TTL 设计：一个数字背后的两个约束

```yaml
floorplan:
  bank-fetch:
    lock-ttl-seconds: 300     # 5 分钟
```

两个约束同时成立：

- **下限：TTL > 单账户拉取的最长耗时**（含银行接口超时）。
  配 300 秒是因为银行接口超时一般在 30–60 秒，加解析和入库，留 5 倍余量。
- **上限：TTL 不能长到"进程被杀了锁还在"影响下一轮。**
  作业每 15 分钟一次，TTL 300 秒正好落在两个周期之间——最坏情况是错过一轮，不是错过三轮。

**为什么不续期**（重复第二节）：续期把"上限"这个约束取消了，于是卡死的执行者永远不会被踢出。

## 五、两个 provider，同一套语义

```yaml
floorplan:
  lock:
    provider: ${LOCK_PROVIDER:memory}    # memory（默认）| redis
```

| 实现 | 条件 | 互斥范围 | 用途 |
|---|---|---|---|
| `InMemoryDistributedLock` | `havingValue="memory", matchIfMissing=true` | 单 JVM。**多实例等于没锁** | 开发 / 单实例 / 演示 |
| `RedisDistributedLock` | `havingValue="redis"` | 跨实例 | 多实例部署 |

**为什么要有内存版**，不是偷懒：

- 本地没 Redis 时作业要能跑起来、幂等要能被验证。一个"必须装好中间件才能启动"的项目，演示不了；
- 一个"默认假装有锁"的实现，生产会出事；
- 所以是 **default + 显式切换**，不是"省略"。

**关键是两者行为必须完全一致**，否则切换 provider 会造成行为漂移：

| 语义 | Redis 版 | 内存版 |
|---|---|---|
| 原子抢占 | `SET NX PX`（单线程） | `ConcurrentHashMap.compute`（同 key 原子） |
| 租约到期可抢占 | `PX` TTL | `expiresAtMillis <= now` |
| 释放比对持有者 | Lua `get` + `del` | `computeIfPresent` 里比对 token |

内存版的核心就这几行：

```java
leases.compute(key, (k, current) -> {
    if (current == null || current.expiresAtMillis() <= now) {
        acquired.set(true);
        return new Lease(token, expiresAt);   // 抢占成功
    }
    return current;                            // 别人正持有且未过期
});
```

上层只认 `DistributedLock` 接口，**切换只改一行配置，业务代码不动**。

## 六、Redis 实现：三处必须做对

```java
Boolean acquired = redis.opsForValue().setIfAbsent(key, token, ttl);
```

`SET key token NX PX ttl` 一条命令搞定"不存在才设置 + 带过期"，这是 Redis 锁唯一的正确起点。

**① value 必须是每次唯一的 token**

用固定值（如 `"1"`）时，释放无法区分"我加的锁"和"别人的锁"，会把别人的锁删掉。

**② 释放必须走 Lua**

`GET` 再 `DEL` 是两步，中间可能过期并被别人抢到——于是删掉的是别人的锁。
Lua 在 Redis 里原子执行，比对与删除不会被打断：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
else
  return 0
end
```

返回 `1` = 真删了；返回 `0` = 锁已不属于我（租约到期被别人拿走）——**后者不是错误，是正常结果**。

**③ 不续期**（见第四节）

**还有一条容易被忽略的配置**：

```yaml
spring:
  data:
    redis:
      timeout: 2s            # 命令超时
      connect-timeout: 2s    # 连接超时
```

锁操作不该让业务线程卡住。拿不到就是拿不到，2 秒内必须给出结论。
配合 fail-closed：超时 → 抛异常 → 作业失败，而不是糊里糊涂跑下去。

## 七、锁只是第一道：三层防线

这是整个设计里最该讲清楚的一点。**锁不承担正确性。**

```
第一层  分布式锁          减少并发       丢了只影响效率
第二层  数据库唯一约束     保证正确       丢了就是资损
第三层  批次日志          可追溯/可重放   回答"到底跑没跑"
```

### 第二层：唯一约束（唯一的正确性来源）

```sql
CONSTRAINT uk_payment_txn UNIQUE (account_ref, transaction_id)
```

```sql
-- 返回 1 = 新入账；返回 0 = 重复（被唯一约束挡下）
INSERT INTO payment_transactions (...) VALUES (...)
ON CONFLICT (account_ref, transaction_id) DO NOTHING
```

**为什么锚点是 `(account_ref, transaction_id)` 而不是 `batch_no`**：
银行流水重复拉取是常态（当日多次同步、文件重发、断点续拉）。同一账户一天拉 96 次，
`batch_no` 每次都不同——用它判重等于没有判重。而"账户 + 银行流水号"才是这笔钱在银行侧的唯一身份。

> 这两个字段不是我们编的，是银行报文里就有的：`account_ref` 来自 MT940 的 `:25:`，
> `transaction_id` 来自 `:61:` 的补充参考。详见 **附录 A**。

这条约束不是"约束"，是**资损防线**：
少了它 → 流水翻倍 → 匹配金额虚高 → 系统以为收了双倍的钱 → **超额释放额度**。

这道防线只用**窄键**。用于识别"同一笔钱"的**宽键**
（`account_ref, value_date, amount, currency, bank_ref, direction`）不挂在主表上，
而是放到独立的 `payment_txn_dedup`：主表只增不改高频写，宽索引挂在它身上要付固定税；
去重表只 INSERT、可整表重建，宽索引放那里才安全。详见 **附录 C**。

### 第三层：批次日志

`bank_fetch_batches` 每次拉取一行，`RUNNING → SUCCESS/FAILED`，记 `fetched/inserted/duplicated` 和文件指纹。
它**不承担幂等**（没有唯一约束，同一账户同一天可以多批次——那是正常现象）；
它的作用是：进程在拉取途中被杀，库里留下 `RUNNING`，事后能回答"这次到底是没跑，还是跑到一半死了"。

### 由此得到的分层结论

> **锁失效时的行为是可预期的**：两个实例同时跑 → 第二个的 `insertIfAbsent` 全部返回 0 →
> `inserted=0, duplicated=N` → 数据完全正确，只是多消耗一次银行接口调用。
>
> 这就是"锁保效率、约束保正确"的具体含义：**锁丢了不会错，只会慢。**

## 八、失败矩阵：每种异常下系统怎么走

| 场景 | 锁的行为 | 数据结果 | 是否可接受 |
|---|---|---|---|
| 另一个实例正在跑 | `tryLock` 返回 empty → `SKIPPED_LOCKED` | 无写入 | ✅ 设计内互斥，**不抛异常** |
| Redis 不可达 | 抛 `IllegalStateException`（fail-closed） | 作业失败 | ✅ 宁可少跑 |
| 进程在拉取中被杀 | 租约到期自动失效 | 留一条 `RUNNING` 批次 | ✅ 下一轮可跑，日志可查 |
| 银行接口超时 | 异常 → `batch.fail()` 落库 → 抛出 | 无写入 | ✅ 连续失败是"通道坏了"的证据 |
| 第 37 条流水是脏数据 | 该条跳过（计 `unusable`） | 前 36 条已入账 | ✅ **事务边界是"一行"，不是一批** |
| **锁完全失效 + 两个实例同时跑** | — | `inserted=0, duplicated=N`，数据正确 | ✅ 唯一约束兜住 |
| Redis 主从切换丢锁 | 两个执行者同时在临界区 | 同上，数据正确 | ✅ 代价是多拉一次 |

倒数第二行和最后一行是重点：**它们证明锁不是正确性的必要条件。**

## 九、主从切换丢锁：为什么不加 fencing token

`SET NX` 在主节点成功、未同步到从节点时主节点宕机 → 从节点升主后不知道这把锁存在 → 两个执行者。

**这不是实现缺陷，是"租约式锁"的固有性质，换 etcd 也一样。**

通用解法是 fencing token（资源端记住见过的最大 token，拒绝比它小的写）。但**这里用不上，也不该用**，原因很具体：

fencing 的前提是"**被保护的资源能比较 token**"。而这里的资源是**银行的文件接口**——
你没法在 `GET /statement` 请求里带上 `fence_token=34` 让银行拒绝旧请求。银行不认你的号。

> **对不能比较 token 的资源，唯一的 fence 是它自己的幂等语义。**

所以这个场景的正确兜底不是 fencing，而是 `uk_payment_txn`：
重复拉取 → 重复写入被挡 → 数据正确。**用幂等代替互斥，是跨系统场景里更本质的答案。**

反过来说：项目里额度、车辆、结清三处**绝不用这把锁**，因为那里的互斥必须与数据同事务提交——
`SELECT ... FOR UPDATE` 在同一个事务里锁住同一行，主从切换时整体回滚，不会出现"锁没了但写成功"。
**引入 Redis 锁反而是把"锁与数据同源"降级成"锁与数据不同源"，凭空制造新窗口。**

## 十、这把锁不该出现在哪里

| 位置 | 为什么不该用 | 该用什么 |
|---|---|---|
| 额度占用 / 释放 | 锁与数据不同源，切换时出现"锁没了但写成功" | 同事务 `SELECT ... FOR UPDATE` |
| 结清 / 赎回 | 同上 | 同上 |
| 单号生成 | `ADV-` + UUID 前 8 位，无碰撞压力 | 真要连续号用 DB 序列 |
| 日终批处理（计息/库龄/违约） | 争用对象是**行**，不是**作业** | 行锁 + 锁内检查 + 流水唯一约束 |

最后一行值得展开，因为它是这个项目里真实存在的 bug 类型：

`AnnualReviewApplicationService.initiate()` 有行锁，但**"是否已有进行中年审"的检查在锁外**（在批处理里），
于是两个实例都通过检查，各自 `freeze(usedAmount)` 一次：

```
限额 1000，占用 300，冻结 0，可用 700
A: freeze(300) → 冻结 300，可用 400
B: freeze(300) → 冻结 600，可用 100     ← 凭空冻死 300
```

**加分布式锁也救不了它**——锁只会让两个实例排队，排到队的那个照样冻第二次。
病根是"检查在锁外"，不是"缺锁"。

> 一句话：**锁的粒度必须和争用对象对齐。** 争的是同一行，就用行锁；
> 争的是"这件事只该发生一次"（一次文件下载、一批短信），才用分布式锁。

## 十一、在作业里怎么用（完整时序）

```java
private Map<String, Object> fetchOne(String accountRef, LocalDate from, LocalDate to, String actor) {
    String lockKey = "lock:bank:fetch:" + accountRef + ":" + to;
    Optional<LockHandle> handle = distributedLock.tryLock(lockKey, lockTtl);

    if (handle.isEmpty()) {
        // 不抛异常：这是设计内的互斥结果，不是故障。
        // 抛异常会让"多点了一次"看起来像系统崩溃，值班被无谓唤醒。
        return Map.of("accountRef", accountRef, "status", "SKIPPED_LOCKED");
    }
    try (LockHandle acquired = handle.get()) {      // try-with-resources 保证异常也释放
        return doFetch(accountRef, from, to, actor);
    } catch (RuntimeException e) {
        return Map.of("accountRef", accountRef, "status", "FAILED", "error", e.getMessage());
    }
}
```

时序：

```
① tryLock(key, 300s)                     拿不到 → SKIPPED_LOCKED，退出（不重试）
② 落 RUNNING 批次                         先记账，进程被杀也留痕
③ 调银行接口拉文件                        外部副作用，锁覆盖全程
④ 逐行 INSERT ... ON CONFLICT DO NOTHING  ← 真正的正确性在这一步
⑤ 回填批次 SUCCESS + 计数 + 指纹
⑥ 写审计
⑦ 释放锁（Lua 比对 token）                失败也无所谓，TTL 兜底
```

注意 **③④⑤ 都在锁内，但方法上没有 `@Transactional`**。
理由和 `disburseAdvance` 一样：外部调用不能包事务。
**这里的事务边界是"一行流水"，不是一个批次**——100 条里第 37 条脏数据，不该让前 36 条白拉。

## 十二、面试可以怎么讲（90 秒版）

> 银行流水采集是项目里唯一必须用分布式锁的地方，判据是"临界区里有没有数据库管不住的东西"——
> 这里要调银行接口拉文件，HTTP 调用包不进事务。
>
> 但我没有把它做成"一把大锁锁住整个作业"。锁键是 `lock:bank:fetch:{账户}:{业务日}`，
> 粒度对齐到账户：同账户串行、不同账户并行，昨天的补拉不挡今天的正常拉取。
>
> 接口语义我写死了四条：不阻塞、不续期、释放比对持有者、锁服务不可用就 fail-closed。
> 不续期是因为续期会掩盖"外部调用卡死"这个事实；fail-closed 是因为资金系统里
> **少跑可以补，多跑收不回**。
>
> 最关键的是**这把锁不承担正确性**。真正的防线是数据库唯一约束
> `uk_payment_txn (account_ref, transaction_id)`，幂等锚点是"账户 + 银行流水号"，
> 不是批次号——因为同一账户一天拉 96 次，批次号每次都不同，用它判重等于没判重。
>
> 所以锁完全失效、两个实例同时跑，结果也只是 `inserted=0, duplicated=N`——
> **数据是对的，只是多消耗一次银行接口调用。锁丢了不会错，只会慢。**
>
> 至于 Redis 主从切换丢锁，我没上 fencing token，因为这个资源是银行的文件接口，
> 它没法比较我的 token。**对不能比较 token 的资源，唯一的 fence 是它自己的幂等语义。**

# 附录 A：MT940 长什么样，怎么映射成我们的字段

> 这一段不属于"锁"，但属于"锁保护的那个东西"。
> 而且它回答了一个前面没展开的问题：**`account_ref` 和 `transaction_id` 到底从哪来。**

MT940 是 SWIFT 的**日末对账单报文**，银行每天（或每 15 分钟）通过 SFTP 推一份。
它**不是给人读的**，是给系统解析的：定长字段 + 冒号标签，靠标签定位，不靠列位置。

## A.1 一份完整报文

```
{1:F01BANKAJPJTXXX0000000000}
{2:O9401030121108BANKAJPJTXXX0000000011081030N}
{4:
:20:STMT-20261108
:25:JP1234567890123456
:28C:00099/00001
:60F:C261107JPY5599965,00
:61:2611081108D8404,00NTRF//34-OC-CMI58653
:86:/TYPE/044:ISSUED OVL. C.REF:CMI58653//REM/test3A/BENM/33
:61:2611081108C50000,05NTRF55refer//34-OC-GRE06324
:86:/TYPE/778:RECVD AC-A/CTRANSF/REF:GRE06324//REMI/5a//ORDP/000012
:62F:C261108JPY5641561,05
-}
```

外层的 `{1:}` `{2:}` `{4:` 是 SWIFT 块头（基础头 / 应用头 / 报文体），真正要解析的只有 `{4:` 到 `-}` 之间。
`940` 就是报文类型号——所以叫 MT**940**。

## A.2 标签一览

| 标签 | 示例 | 含义 | 我们的落点 |
|---|---|---|---|
| `:20:` | `STMT-20261108` | 报文参考号，整份对账单的"快递单号"，**不是交易级流水号** | 仅日志 |
| `:25:` | `JP1234567890123456` | 账户标识 | **`account_ref`** |
| `:28C:` | `00099/00001` | 对账单号 / 分页序号，用来判断是否收全 | 完整性校验 |
| `:60F:` | `C261107JPY5599965,00` | 期初余额（`F`=期末/最终，`M`=中间页） | 余额校验 |
| `:61:` | `2611081108D8404,00NTRF//34-OC-CMI58653` | **单笔交易明细**，核心 | 一行流水 |
| `:86:` | `/TYPE/044:...` | 交易附加说明，**非结构化文本** | `payer_name`/`reference` |
| `:62F:` | `C261108JPY5641561,05` | 期末余额 | 余额校验 |

一个容易记混的点：`:60F:` / `:62F:` 末尾的字母是**余额类型码**——
`F` = Final（最终余额，本份对账单结束时的余额），`M` = Intermediate（中间余额，多页或中间报表时使用）。
所以只有**最后一页**是 `62F`，前面的页都是 `62M`。

## A.3 `:61:` 逐段拆解

```
:61:2611081108D8404,00NTRF//34-OC-CMI58653
    ────── ──── ─ ──────── ──── ──────────────────
    起息日  记账日 方向 金额   类型  补充参考
```

| 段 | 示例 | 含义 |
|---|---|---|
| 起息日 | `261108` | 2026-11-08，**钱真正到账那天** → `value_date` |
| 记账日 | `1108` | 11 月 08 日入账（MMDD，无年份） |
| 方向 | `D` | `D`=Debit 出账，`C`=Credit 入账，`RC`/`RD`=冲正 |
| 金额 | `8404,00` | **逗号是小数点**，不是千分位。8,404.00 日元 |
| 类型 | `NTRF` | 4 位码：`N`+`TRF` 转账；另有 `NMSC` 杂项、`NCHK` 支票、`NINT` 利息 |
| 客户参考 | （本例为空） | 付款方填写的参考号，**VIN 常在这里** |
| 补充参考 | `34-OC-CMI58653` | `//` 之后，银行侧分配的交易号 → **`transaction_id`** |

## A.4 映射到我们的模型

```
:25:  JP1234567890123456              →  account_ref
:61:  2611081108D8404,00...//34-OC-CMI58653
      ├─ 261108                       →  value_date = 2026-11-08
      ├─ D                            →  amount = -8404   ← 注意符号
      ├─ 8404,00                      →  8404（逗号换小数点，转整数日元）
      └─ 34-OC-CMI58653               →  transaction_id
:86:  /BENM/33                       →  payer_name
      /REMI/...                      →  reference（VIN 优先从这里取）
      :61: + :86: 两行原文            →  raw（争议时自证）
```

落成代码就是 `BankStatementLine`：

```java
new BankStatementLine(
        transactionId,   // :61: // 之后
        accountRef,      // :25:
        valueDate,       // :61: 起息日
        amount,          // :61: 金额，D 取负、C 取正
        payerName,       // :86: /BENM/ 或 /ORDP/
        payerAccount,    // :86: 可能没有
        reference,       // :86: /REMI/ 或 :61: 客户参考
        raw)             // 原始两行
```

**`D` 取负这一点必须单独说**：表里 `amount` 的注释是"正数=入金，负数=冲正"。
MT940 的 `D` 表示"钱从这个账户出去了"，对收款账户而言正是负数。
这个映射写反了，会出现**金额看着都正常、符号全错**的数据——
比金额错更难发现，因为它不会触发任何范围校验。

## A.5 三个解析难点

**① 金额是逗号小数点，方向靠字母**

`8404,00` 是 8,404.00，`1.250.000,00` 才是 125 万。写成 `parseLong(s.replace(",", ""))` 会得到
840400——**放大 100 倍**。而 MT940 全用逗号，所以正确做法是 `replace(".", "").replace(",", ".")` 再 `BigDecimal`，
最后按最小货币单位转整数（日元无小数位，直接取整数部分；USD/EUR 要乘 100）。

**② `:86:` 完全非结构化**

各家银行格式天差地别：`/BENM/`、`/ORDP/`、`/REMI/`、`/TYPE/044:` 这些是我们的样例银行格式，
另一家可能是自由文本"振込 山田太郎 様 VIN ABC123"。
所以 `:86:` 只能靠**每行银行一份正则配置**，而且解析失败必须允许为空——
`reference` 为空不影响幂等（锚点是 transaction_id），只是匹配层会退化到金额+时间窗口规则。

**③ 分页与截断**

`：28C:00099/00001` 表示第 99 份对账单的第 1 页。一份大账户一天可能几十页，
**只有最后一页的 `:62F:` 才是真期末余额**，前面的都是 `:62M:`（中间余额）。
漏收一页不会报错，只会少几笔流水——而少一笔就是一笔敞口。

## A.6 余额校验：唯一能发现"文件不全"的手段

```
期初余额(:60F:) + Σ 所有 :61: 金额 = 期末余额(:62F:)
```

用 A.1 那份报文验算：

```
5,599,965.00 − 8,404.00 + 50,000.05 = 5,641,561.05   ← 与 :62F: 一致 ✓
```

**这一步不能省。** 假设文件被截断，只收到第一笔 `:61:`：

```
5,599,965.00 − 8,404.00 = 5,591,561.00  ≠  5,641,561.05     ← 差 50,000.05
```

如果不校验余额，这次采集会"成功"入库 1 笔——系统认为收全了，实际上少了 5 万日元。
等到对账日发现差异时，已经过了结算窗口。

> 这就是为什么采集作业里要有 `file_fingerprint` 之外的**内容级校验**：
> 指纹只能证明"这份文件和上次是不是同一份"，不能证明"这份文件自己是不是完整的"。
>
> 实现上很简单：解析完比对 `60F + Σ61 == 62F`，不等就抛
> `BankStatementException`，让整个批次 `FAILED` ——
> **宁可这批不入账，也不要入一半。**

## A.7 换格式不改上层：`BankStatementSource` 这一层就是干这个的

现在代码里是 `CsvBankStatementSource`（网银导出 CSV）。它的注释直接写了这件事：

> 真实银行的 MT940 是定长/带标签格式（`:20:`、`:25:`、`:61:`），比 CSV 复杂得多。
> 这里选 CSV 是因为**格式不是这个类要证明的东西**——要证明的是"采集与匹配解耦、重复拉取由唯一约束兜底"。
> 换成 MT940 只需替换 `parse`，上层一行不用改。

要接 MT940，只需要：

```java
@Component
@ConditionalOnProperty(name = "floorplan.bank-fetch.source", havingValue = "mt940")
public class Mt940BankStatementSource implements BankStatementSource {
    @Override public String source() { return "BANK_FILE"; }
    @Override public BankStatementResult fetch(String accountRef, LocalDate from, LocalDate to) {
        // 1. 按 :25: 定位属于本 accountRef 的报文段
        // 2. 逐 :61: 建行，:86: 补齐 payer/reference
        // 3. 余额校验 60F + Σ61 == 62F，不平就抛
        // 4. 按 value_date 过滤 [from, to]（与 CSV 实现一致）
        // 5. 指纹 = 文件 SHA-256 前 32 位
    }
}
```

**作业层、锁、幂等约束一个字都不用动。** 这正是 `BankStatementSource` 这个端口存在的意义：
格式会变、银行会换、协议会升级，而"按账户加锁、逐行幂等入库"这件事不变。

## A.8 一句话总结（面试可以这么说）

> 银行给的 MT940 是定长报文：`:25:` 是账户，`:61:` 一笔一行，`:60F:`/`:62F:` 是期初期末余额。
> 我的幂等锚点 `(account_ref, transaction_id)` 就是从 `:25:` 和 `:61:` 的补充参考来的——
> **不是我设计的字段，是银行本来就给的唯一身份**。
> 解析要小心的三件事：金额用逗号当小数点、`D` 要取负数、`:86:` 非结构化只能按银行配正则。
> 另外必须做余额校验：`期初 + Σ明细 = 期末`，不平就整批失败——
> 因为**文件截断不会报错，只会少几笔流水，而少一笔就是一笔敞口**。

# 附录 B：为什么本设计不续期

> 第二节把"不自动续期"写成了一条硬语义，这里补齐论证——
> 以及那个必然会被追问的问题：**"如果确实是 IO 慢，需要更长时间呢？"**

## B.1 先分清：你要续的是锁，还是事务

这两个问题听起来一样，诊断证据完全不同。

本项目的采集方法**没有 `@Transactional`**（理由见正文第一节：外部调用不能包事务），
所以这里不存在"事务一直拖着"，只存在"锁一直被握着"。

如果临界区里既有事务又有外部 IO，先去数据库看它到底在等什么——**进程自证不可信，会话视图才是权威**：

| `pg_stat_activity` / `pg_locks` 看到什么 | 含义 | 与锁的关系 |
|---|---|---|
| `state='active'` + 慢 SQL | 事务自己在跑 | 与锁无关，问题在 SQL / 索引 |
| `state='idle in transaction'` + `xact_start` 很旧 | 事务开着不动，**在等应用** | 说明 IO 被包进了事务（设计错误） |
| `pg_locks` 里 `granted=false` | 在等别人的锁 | 查锁顺序、查持有者 |
| 数据库侧一切正常，只是锁没释放 | 应用侧的循环/IO 卡住了 | 这才是"锁该被接管"的场景 |

关键判断：**如果 `pg_stat_activity` 里没有长事务，那就没有"事务出问题"，只有"锁没释放"。**
把这两件事混在一起，会让人误以为"要续期保住事务"——而实际上事务早就提交了，被握着的只是一把锁。

## B.2 判据是「推进」，不是「时长」

"等 IO 等得久"和"卡死"在进程内部看起来是同一件事：线程停在 `read()` 上。
唯一的区别在外部世界——**对面还在给我吐数据吗？**

所以续期的判据不能是"我已经持有 4 分钟了"，必须是"这 4 分钟里我推进了多少"。

```
慢 IO：   ├─●──●──●──●────●──●──●┤     每 2 秒读到一块 → 有推进 → 续期
卡死：    ├─●─────────────────────┤     读到 0 字节后阻塞 → 零推进 → 放弃
                       ↑
                  t=60s 看门狗检查点
```

埋点很简单，不用改架构：

```java
private final AtomicLong lastProgressAt = new AtomicLong(System.currentTimeMillis());

void progress() {                       // 读一块数据、解析一行、入库一条，都调它
    lastProgressAt.set(System.currentTimeMillis());
}
```

这一条就能区分"慢但活着"和"卡死"，因为死锁、半开连接、TCP 重传黑洞的共同特征都是**零推进**。
一个还在吐数据的慢连接，不管多慢，`lastProgressAt` 一直在动。

## B.3 如果非要续期：三道闸门

真要继续期，必须同时满足三个条件，缺一不可：

| 闸门 | 条件 | 不满足时的动作 | 防的是 |
|---|---|---|---|
| ① 推进 | `now - lastProgressAt <= 60s` | 不续，主动 abort | 死锁、半开连接 |
| ② 预算 | `now <= deadline`（`start + 业务可接受最长持锁`） | 不续，主动 abort | "慢但一直在推进"，业务等不了 |
| ③ 次数 | `renewCount <= N`（如 3 次） | 不续，主动 abort | 每 50 秒吐一字节的恶意慢速连接 |

闸门②是容易被忽略的：**deadline 是业务给的，不是锁给的**。
"它一直在推进"不等于"我们可以一直等它"——结账有时间窗，等过了窗口再入账已经没有意义。

还有第四条，比前三条都重要：**续期本身要当心跳用**。

```lua
-- 续期必须比对 token，不能只 PEXPIRE
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('pexpire', KEYS[1], ARGV[2])
else
  return 0            -- 我已经不是持有者
end
```

返回 `0` 是极有价值的信息：说明租约已过期或被接管，**我的状态可能已经过期**。
这时候必须立刻中止，而不是忽略这个返回值继续跑。
**续期失败 = 领导权检查失败**——续期不只是"多要一点时间"，它同时是一次"我还算数吗"的验证。

## B.4 结论：不加续期，因为两种错误的后果不对称

|  | 不续期，判断错了（其实活着） | 续期，判断错了（其实死了） |
|---|---|---|
| 发生什么 | 锁被接管，任务重复执行一次 | 锁永不到期，任务永久挂起 |
| 有兜底吗 | 有：唯一约束挡掉重复 → **多做一次** | 没有：**永远不做**，没人发现 |
| 可观测吗 | 下一轮显式 `FAILED` + 告警 | 下一轮 `SKIPPED_LOCKED`，**监控上一切正常** |

最后一行是致命的：**续期把"可观测的失败"变成了"不可观测的挂起"。**

不加续期时，锁的 TTL 就是一个**分布式看门狗**——不管执行者是死了、卡了、还是被网络分区了，
别人都能接管，而接管**不需要判断你是死是活**。这正是租约的核心价值。
加了续期，等于主动放弃这个能力。

还有个更隐蔽的问题：**续期成功不代表状态有效。**
一个 GC 停顿 40 秒后醒来的线程，续期可能成功，然后基于过期状态继续写——
续期把"我可能已经不可信"这个事实藏起来了。这正是 fencing token 要解决的问题（见正文第九节）。

> 一句话：**租约的价值在于"它不需要判断你是死是活"。续期把这个能力还回去了。**

## B.5 更好的解法：把锁的作用域缩到不需要续期

真正的问题不是"要不要续期"，而是"为什么持锁时间会超过 TTL"。

现状（`fetchOne` 里的锁覆盖整个 `doFetch`）：

```
tryLock(300s) → 落批次 → 拉文件 → 逐行入库 → 回填批次 → 写审计 → 释放
└────────────────────── 持锁 60~180s，随账户流水量波动，不可控 ──────────────────────┘
```

但**入库阶段是纯 DB 操作，由唯一约束保证幂等，本来就不需要锁**。

改法：

```
① tryLock(ttl = 拉取 P99 + 余量)   ← 锁只保护"谁去拉"
② 拉文件（有界：单次超时 + 总 deadline，超了就 abort）
③ 释放锁                            ← 外部副作用已结束，锁的使命完成
④ 逐行 INSERT ... ON CONFLICT DO NOTHING   ← 幂等，谁入都行，不持锁
⑤ 回填批次 / 写审计
```

持锁时长从"拉取 + 入库 + 审计"降到"拉取"，而**拉取有 P99 上界**——TTL 天然够，**续期这个问题就不存在了**。

代价：③④ 之间另一个实例可能也拉了一遍，多一次银行 API 调用。
但重复拉取的后果只是浪费一次调用，数据由 `uk_payment_txn` 保证正确。
**用一次多余的 API 调用，换掉整个续期机制，这是划算的。**

顺带一个判据：如果"入库不持锁"会让批次统计被污染，那说明统计口径有问题——
`fetched/inserted/duplicated` 应该能**从唯一约束的执行结果直接推出来**，
而不是依赖"只有我在写"这个脆弱前提。

> **状态**：这一段是改造方案，当前代码仍是锁覆盖全流程。
> 改动点在 `BankFetchApplicationService#fetchOne`：把 `doFetch` 的入库循环移到 `try (LockHandle ...)` 之外。

## B.6 面试 60 秒版

> 我不加续期。判断"该续还是该放弃"这件事在进程内部是判不出来的——它问的是"外部世界还在推进吗"，
> 而进程能看到的只有"我在等"。所以我不用计时器，用**进度**：每读到一块、每入库一条就更新
> `lastProgressAt`，看门狗检查的是"这段时间有没有推进"，不是"持有了多久"。
> 再加一个业务给的 deadline 兜底，因为"慢但一直在推进"也可能是业务等不了的。
>
> 但真正的理由是后果不对称：**不续期判断错了，最坏是多做一次，唯一约束能兜；
> 续期判断错了，是永远不做，而且没人知道**——锁永不到期，下一轮 `SKIPPED_LOCKED`，
> 监控上看起来一切正常。资金系统里，"多做一次"可以接受，"永远不做"不能接受。
>
> 所以我选了第三条路：**把锁的作用域缩到"拉取"这一段**。入库是幂等的，不需要锁；
> 持锁时长因此有上界，TTL 天然够，续期这个问题就不存在了。

# 附录 C：去重表 `payment_txn_dedup`，把宽索引从主表上摘出去

## C.1 决策

> ⚠️ **本节有一个前提已被推翻。** 下面这把窄键假设了
> "`(account_ref, transaction_id)` 在银行侧唯一"，而真实报文里它经常按天/按期重置
> （MT940 的 `:61:` 银行参考段甚至可以为空）。**前提不成立时，这把键不只是失效，
> 而是会把跨期的真实入账静默判成重复**——详见附录 E。
> 修正后的锚点是 `(account_ref, statement_id, line_no)`，本节其余论证（宽键为什么搬出去、
> 为什么不做硬拒收、为什么同事务）在换锚点后仍然成立。

主表 `payment_transactions` 只保留一把**窄**唯一键：

```
uk_payment_txn (account_ref, transaction_id)
```

用于识别"同一笔钱"的**宽**联合键搬到独立表：

```
payment_txn_dedup (account_ref, value_date, amount, currency, bank_ref, direction)
```

一句话概括这个决策：**主表负责"这笔钱是什么"，去重表负责"这笔钱像不像已经来过"。**
两件事的读写特征完全不同，不该长在同一张表上。

## C.2 为什么宽键不能挂在主表上

宽键挂在主表上的代价不在查询侧，在**写入侧和维护侧**：

| 成本 | 挂在主表 | 放到独立表 |
|---|---|---|
| 每次 INSERT 维护的索引项 | 窄索引 + 6 列宽索引，两个 b-tree 都要插 | 主表只插窄索引；宽索引插在小表 |
| 索引膨胀 | 主表是热表，宽索引页分裂和碎片跟着业务量涨 | 去重表只 INSERT、不 UPDATE，膨胀集中在可独立重建的小表 |
| 改索引（加一列、换顺序） | 锁主表；`REINDEX` 期间影响所有查询 | 只锁去重表，主表完全无感 |
| 加字段、清历史数据 | 动主表 = 动在途业务 | 动去重表 = 动一个纯附属结构 |
| 表体积 | 宽索引可能比主表数据本身还大 | 主表保持"一行一条流水"的紧凑形态 |

主表不是只被采集用。`settle`、`redeem`、对账、未匹配清单都读它，而且 `match_status`、`matched_vin`、`matched_at` 会被反复 UPDATE。**在一张高频更新、多路读取的表上挂一个 6 列唯一索引，等于给每条写入路径都加了一份固定税。**

一个容易被忽略的点：PostgreSQL 的 HOT 更新要求"被更新的列不在任何索引里"。主表现在已经有 `idx_ptx_match (match_status, value_date)` 和 `idx_ptx_vin (matched_vin)`，所以匹配阶段的更新**本来就走不了 HOT**。如果再把宽键挂上来，虽然宽键列不参与更新、不会进一步破坏 HOT 判定，但索引数量增加会实打实抬高每次 INSERT 的 WAL 和页写成本。**判断标准不是"索引会不会拖慢查询"，而是"这张表每天被写多少次"。**

## C.3 表结构

```sql
CREATE TABLE IF NOT EXISTS payment_txn_dedup (
    id             BIGSERIAL PRIMARY KEY,
    txn_id         BIGINT       NOT NULL
                       REFERENCES payment_transactions (id) ON DELETE CASCADE,

    -- 宽指纹：用于识别"同一笔钱"
    account_ref    VARCHAR(32)  NOT NULL,
    value_date     DATE         NOT NULL,
    amount         BIGINT       NOT NULL,
    currency       CHAR(3)      NOT NULL DEFAULT 'JPY',
    bank_ref       VARCHAR(64)  NOT NULL DEFAULT '',   -- 注意 NOT NULL + 默认空串
    direction      CHAR(1)      NOT NULL DEFAULT 'C',  -- C 入金 / D 出金

    created_at     TIMESTAMPTZ  NOT NULL DEFAULT now(),

    CONSTRAINT uk_ptx_dedup UNIQUE
        (account_ref, value_date, amount, currency, bank_ref, direction)
);

CREATE INDEX IF NOT EXISTS idx_ptxdedup_txn ON payment_txn_dedup (txn_id);
CREATE INDEX IF NOT EXISTS idx_ptxdedup_date ON payment_txn_dedup (account_ref, value_date);
```

设计要点：

- **`txn_id` 是外键，不是"再存一份流水号"**。去重表是主表的附属结构，主表删了它就该跟着删（`ON DELETE CASCADE`）。
- **列顺序服务于前缀查询，不服务于语义**。`(account_ref, value_date)` 放前两列，是因为对账要按账户取日期区间；`currency`、`direction` 选择性极低（几乎全是 `JPY`/`C`），必须放最后，否则白白撑宽索引前缀。
- **去重表只 INSERT、不 UPDATE**。这是它能随意重建、随意加列的前提，也是它敢挂宽索引的底气。

## C.4 三个必须处理的坑

### 坑一：`bank_ref` 可空会让唯一约束静默失效

PostgreSQL 的唯一索引里，**两个 NULL 互不相等**。如果 `bank_ref` 允许为空，那么两笔都没有 `bank_ref` 的流水会同时插入成功——去重表在"最需要它工作"的场景下完全失效，而且不报任何错。

解法只有两个：`NOT NULL DEFAULT ''`，或者用表达式索引 `COALESCE(bank_ref, '')`。**前者更简单，优先选前者。**

同样的坑在 `currency`、`direction` 上也存在，所以这三列全部 `NOT NULL` + 默认值，不留一个可空列在唯一键里。

### 坑二：宽键会误判合法重复，而漏记比重复更危险

同一天、同一账户、同一金额、同一付款人的两笔转账是**真实存在**的：经销商分两笔各付 100 万，摘要都写同一个 VIN；或者两台车尾款恰好同额同日到账。

这时宽键会认为"第二笔是重复"。如果去重表做**硬拒收**，结果就是：钱到了银行，系统里没有这条流水 → 账外资金 → 客户投诉"我付了你说没付"。

方向要认清：

| 错误 | 后果 | 能否事后发现 |
|---|---|---|
| 重复入账 | 匹配金额虚高、超额释放额度 | 能，银行余额对不上，对账必现 |
| **漏记入账** | 账外资金、客户已付款但系统未认 | 难，只有客户投诉才暴露 |

**去重的最坏结果应该是"多一条待复核"，不是"少一条流水"。**

所以宽键唯一约束的定位是**原子检测器，不是拒收器**：

```java
// ① 主表：窄键是真防线，重复就跳过
int inserted = jdbc.update("""
    INSERT INTO payment_transactions (...) VALUES (...)
    ON CONFLICT (account_ref, transaction_id) DO NOTHING
    """, ...);
if (inserted == 0) return DUPLICATED;

// ② 去重表：宽键冲突不拒收，只标记
int dedupInserted = jdbc.update("""
    INSERT INTO payment_txn_dedup (txn_id, account_ref, value_date, amount, currency, bank_ref, direction)
    VALUES (?, ?, ?, ?, ?, ?, ?)
    ON CONFLICT ON CONSTRAINT uk_ptx_dedup DO NOTHING
    """, ...);
if (dedupInserted == 0) {
    jdbc.update("""
        UPDATE payment_transactions
           SET needs_review = TRUE, review_reason = 'SUSPECT_DUP'
         WHERE id = ?
        """, txnId);
}
```

这样三段职责分明：
- **窄键**决定"收不收"（真重复，拒收）；
- **宽键**决定"要不要人看一眼"（指纹雷同，收但打标）；
- **`needs_review`** 把人拉进来，而不是让系统替人判断。

两句 SQL 都在同一个事务里，靠唯一约束的原子性完成检测，**不需要先查后插，也不需要锁**。这与前面反复讲的判断一致：能用约束表达的并发控制，就不要用锁。

### 坑三：两表必须同事务，否则会出现"半条流水"

去重表不是独立业务，是主表的函数依赖。写入顺序固定：

```
BEGIN
  ① INSERT payment_transactions  ... ON CONFLICT (account_ref, transaction_id) DO NOTHING
     影响 0 行 → ROLLBACK，返回 DUPLICATED
  ② INSERT payment_txn_dedup     ... ON CONFLICT DO NOTHING
     影响 0 行 → ③
  ③ UPDATE payment_transactions SET needs_review = TRUE (仅在 ② 冲突时)
COMMIT
```

如果①提交了、②没提交，去重表就少一条指纹——**下一次同一笔钱再来，宽键检测不到**，去重能力被静默削弱。反过来如果②提交了、①没提交，去重表里会有一条指向不存在流水的孤儿（外键会挡住这种情况，`ON DELETE CASCADE` 只在删除时生效，插入时仍会校验父行存在）。

**孤儿巡检 SQL**（放进日终对账作业，很便宜）：

```sql
-- 主表有、去重表无：去重能力被削弱，需要补指纹
SELECT pt.id, pt.account_ref, pt.transaction_id
  FROM payment_transactions pt
  LEFT JOIN payment_txn_dedup d ON d.txn_id = pt.id
 WHERE d.id IS NULL
 LIMIT 100;

-- 去重表有、主表无：外键应已挡住，查出来说明有人绕过约束写过
SELECT d.id, d.txn_id FROM payment_txn_dedup d
  LEFT JOIN payment_transactions pt ON pt.id = d.txn_id
 WHERE pt.id IS NULL;
```

第一条查出来的行，修复方式不是删，而是**补建指纹**——去重表是派生结构，永远可以通过主表重建。

## C.5 现有表缺三列，先决定 `direction` 要不要

V15 的 `payment_transactions` 里没有 `currency`、`direction`、`bank_ref`。落地前必须先定：

| 列 | 现状 | 建议 |
|---|---|---|
| `currency` | 无。系统是纯日元（`BIGINT` 整数日元） | 加 `CHAR(3) NOT NULL DEFAULT 'JPY'`。单币种时它是常量，但留着才能接外币账户；**必须放索引末尾** |
| `bank_ref` | 无。现有 `transaction_id` 是银行流水号，`reference` 是摘要 | 加。它对应附录 A 里 `:61:` 的**客户参考段**（如 `TT840JPY`），跨渠道时比流水号稳定 |
| `direction` | 无。`amount` 带符号（正=入金，负=冲正） | **不要加**。方向已经编码在符号里，再加一列是同一个事实的第二个真相源 |

最后一行值得展开：如果 `amount` 已经带符号，`direction` 就是派生列。把它放进唯一键，会出现"同一笔钱，符号对但 `direction` 写错"就被当成两笔的情况——**而这类错误恰恰最难发现**，因为金额范围校验不会报，余额校验也不一定报。

要保留 `direction` 也可以，但必须同时改 `amount` 为绝对值存储。**二者只能选一个**，不能既存带符号金额又存方向，然后两个都进唯一键。

## C.6 这个表是"派生"，不是"第二个真相源"

前面反复出现的一条原则是：同一个事实有两个真相源，一定会漂移。这里必须说清楚为什么它不违规：

- **主表是唯一真相源**——流水本身只存在于 `payment_transactions`；
- **去重表是纯派生**——任何一行都可以由主表重新算出来：

```sql
INSERT INTO payment_txn_dedup (txn_id, account_ref, value_date, amount, currency, bank_ref, direction)
SELECT id, account_ref, value_date, amount, 'JPY', COALESCE(bank_ref,''), 'C'
  FROM payment_transactions
ON CONFLICT DO NOTHING;
```

判断标准是**能不能无条件重建**。能重建的派生结构，损坏了只是"暂时失去去重能力"，不会造成数据错误；不能重建的才是真相源，才需要严格保护。去重表属于前者。

这也解释了为什么"清数据、改索引、加字段都不动主表"是成立的：它本来就是可丢弃的。**一个可以随时 `TRUNCATE` 再从主表重建的结构，才配挂宽索引。**

## C.7 一句话总结（面试可以这么说）

> 把去重键拆到独立表，不是为了"主表看起来干净"，是因为两张表的写入特征完全不同：主表是热表、会被反复 UPDATE、被结算和对账多路读取；去重表只 INSERT、不 UPDATE、可以整表重建。**宽索引挂在只增不改的小表上，膨胀和重建都可控；挂在热表上，就是给每条写入路径加固定税。**
>
> 但宽键有个天生的缺陷：它分不清"同一笔钱的重复"和"两笔长得一样的钱"。所以我的分工是——**窄键 `(account_ref, transaction_id)` 决定收不收，宽键决定要不要人看一眼**。重复入账还能靠对账发现，漏记一笔就是账外资金，所以去重表不做硬拒收，冲突只打 `SUSPECT_DUP` 标。
>
> 还有两件事必须做对：`bank_ref` 这类可空列在唯一索引里 NULL 互不相等，会让去重静默失效，所以全部 `NOT NULL DEFAULT ''`；两表必须同事务写入，否则主表有、去重表没有，去重能力就被静默削弱了。

## C.8 落地清单

1. V16 迁移：`payment_transactions` 补 `currency`、`bank_ref`、`needs_review`、`review_reason` 四列（`direction` 不加）；
2. 同迁移建 `payment_txn_dedup` + `uk_ptx_dedup`；
3. `JdbcPaymentTransactionRepository.saveIfAbsent` 改为「主表插入 → 去重表插入 → 冲突打标」三段，全部在调用方事务内；
4. 日终对账作业增加两条孤儿巡检 SQL；
5. 用演示数据验证：重复拉取 → 主表 `inserted=0`；两笔同额同日不同流水号 → 主表 2 行、第二行 `needs_review=TRUE`。

第 5 条是关键验证：**它同时证明"真重复被挡住"和"长得像但合法的两笔不被吞掉"**，这两件事必须一起验证，只测前者会掩盖假阳性问题。

## C.9 为什么不用内容哈希做主键

有一个很自然的想法：既然 `transaction_id` 可能不稳定，那就自己算一个稳定的业务 ID。

```
biz_id = hash(account_ref + value_date + direction + currency + amount + bank_ref)
```

用 `biz_id` 做主表唯一键，银行参考号怎么变都不影响。**这个直觉的方向是对的——用内容指纹兜住外部标识的不稳定。但落点是错的，而且错在三处。**

### C.9.1 第一处：自指矛盾

哈希的稳定性**完全来自输入的稳定性**。而这个公式里的字段，恰恰是最容易被修正的：

| 字段 | 会不会变 | 什么时候变 |
|---|---|---|
| `bank_ref` | 会 | 银行补全参考号、人工修正摘要、不同渠道给不同格式 |
| `value_date` | 会 | 先给交易日、后更正为起息日；連休前后跨行到账日调整 |
| `amount` | 会 | 手续费扣减、冲正、部分退回 |

**用一个由不稳定字段算出来的值，去解决"不稳定"这个问题，逻辑上不成立。**
`bank_ref` 一变，`biz_id` 就变，同一笔钱立刻变成两行。你想消除的那个问题，只是换了个位置重新出现。

### C.9.2 第二处：哈希分不清"重复"和"两笔同额"

哈希只能回答"描述是否相同"，回答不了"是不是同一笔钱"。而这两件事在银行流水里经常不一致：

- 同一笔钱被报两次 → 描述相同（**应该去重**）
- 两笔各 100 万、同日同额同付款人 → 描述相同（**不应该去重**）

信息论上这是无解的：**输入一模一样，任何函数都只能给出同一个输出。**
所以哈希唯一能给的结论是"这两条长得一样"，而不是"这两条是同一笔"。

把它做成主键，等于把"不确定"硬升级成"冲突拒绝"。而拒绝的方向恰恰是**漏记**——钱到了、系统没有这条流水、账外资金。这个错误比重复入账严重得多（见 C.4 坑二）。

### C.9.3 第三处：内容一变，两行就再也关联不上

这是最要命的一点。假设银行先报 1,000,000，第二天因手续费更正为 999,560：

```
第 1 天：biz_id = hash(..., 1000000, ...) = a3f8...
第 2 天：biz_id = hash(...,  999560, ...) = 7c21...     ← 新的主键
```

结果：两行，两笔金额，**没有任何字段能把它们关联起来**。原来的 `transaction_id` 至少还能让你 `WHERE transaction_id = ?` 把两行都捞出来。换成内容哈希后，连这条线索都没了。

**主键一旦被内容决定，内容修正就等于换了一条记录。**

### C.9.4 正确的做法：身份和标识分层

问题的本质不是"ID 不够稳定"，而是**"同一笔钱有多个外部标识"**。这是映射问题，不是哈希问题。

数据库设计里有个基本区分：**代理键（surrogate key）稳定，自然键（natural key）会变。** 正确做法是让主键与内容无关，把"标识"降级成属性：

| 层 | 字段 | 稳定性 | 作用 |
|---|---|---|---|
| 代理键 | `id BIGSERIAL` | 永不变 | 内部关联（外键都指向它） |
| 业务号 | `txn_no`（`PTX-20261108-000123`） | 永不变、可读 | 对外沟通、审计追溯 |
| 强标识 | `(account_ref, statement_id, line_no)` 唯一 | **我方保证**（见附录 E：银行的流水号不可靠） | 判"收不收" |
| 弱标识 | `content_hash` 普通索引 | 随内容变 | 判"要不要看一眼" |
| 别名 | `payment_txn_aliases` | — | 记录这笔钱的所有外部标识 |

关键在于最后一行——**别名表**：

```sql
CREATE TABLE IF NOT EXISTS payment_txn_aliases (
    id           BIGSERIAL PRIMARY KEY,
    txn_id       BIGINT      NOT NULL REFERENCES payment_transactions (id) ON DELETE CASCADE,
    source       VARCHAR(16) NOT NULL,        -- BANK_API / BANK_FILE / MANUAL_UPLOAD
    external_ref VARCHAR(64) NOT NULL,        -- 该渠道下的流水号
    content_hash CHAR(64)    NOT NULL DEFAULT '',
    first_seen_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_seen_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uk_alias UNIQUE (source, external_ref)
);
```

> 别名表有同一个坑：`external_ref` 若是会重置的流水号，`uk_alias` 会在次日的 `0001` 上撞车，
> 把一笔新钱认成"同一个外部标识又出现了一次"。
> 正确取值是带期号的 `(statement_id + '#' + line_no)`；只在**确认该渠道的号永久唯一**时，
> 才直接用 `external_ref`。判据与附录 E.2 的四个层次一致。

写入流程变成"先认身份，再决定要不要新建"：

```
解析出 (source, external_ref, content_hash)
  ↓
① 查别名 (source, external_ref)
     命中 → 同一笔的外部标识又出现了一次：只更新 last_seen_at，返回已有 txn_id（不新建）
  ↓ 未命中
② 查 content_hash（限最近 N 天）
     命中 → 疑似同一笔换了标识：挂一条新别名指向已有 txn_id，并打 SUSPECT_RELINK
  ↓ 未命中
③ 新建主表记录 + 建第一条别名
```

这样每种变化都有对应处理：

| 变化 | 命中点 | 结果 |
|---|---|---|
| 同一渠道重复推送 | ① 别名 | 不新建，幂等 |
| 换渠道推送（API 改文件） | ① 未命中 → ② hash | 挂别名，不新建 |
| 描述被修正（金额/日期变） | ① 命中（external_ref 没变） | 不新建，只更新别名时间 |
| 两笔同额同日 | ① 未命中 → ② 命中 | 挂别名 + 打标，**仍新建**（可复核） |

**这四行是哈希单独做不到的：它能把"标识变了"和"内容变了"分开处理，而哈希把它们混成一个数。**

类比：身份证号不会因为你改名而变。如果用"姓名 + 生日 + 住址"算哈希当身份证号，搬一次家你就成了另一个人。

### C.9.5 哈希不是不能用，是不能当身份

它有两个正当位置，都在"检测"侧，不在"标识"侧：

1. **批次内去重**：同一份文件里分页重叠、正则重复匹配，会出现完全相同的行。此时描述一定一致，哈希是正确工具——**同批次内用它去重，跨批次用它只会误伤**。
2. **疑似检测**：`content_hash` 建普通索引，查"最近 7 天有没有长得一样的流水"，命中就转人工复核。这正是 C.4 坑二里那个"检测器而非拒收器"的定位。

两个位置共同点：**哈希只输出"候选"，不输出"判定"。**

### C.9.6 如果要算这个 hash，两个细节会咬人

```java
String raw = String.join("\u0001",
        accountRef,
        valueDate.toString(),
        direction,
        currency,
        Long.toString(amount),
        bankRef == null ? "" : bankRef);     // NULL 必须归一，否则整串变 NULL
String contentHash = sha256Hex(raw);
```

- **必须带分隔符**。直接拼 `"AB" + "C"` 和 `"A" + "BC"` 得到同一串，不同流水会算出同一个哈希。
- **NULL 必须先归一成空串**。Java 里 `null` 参与拼接会得到字面量 `"null"`，而 `"null"` 和空串又是两个值；SQL 里 `NULL` 参与 `||` 会让整个结果变 `NULL`。
- 算法用 SHA-256 足够（截前 128 bit 也可以）；MD5 在非对抗场景够用，但没必要为省几十字节留个话柄。

### C.9.7 一句话

> 内容哈希解决的是"这条记录有没有变"，不是"这条记录是谁"。
> **做主键要求的是身份，而身份必须来自记录之外**——要么是银行给的流水号，要么是我方生成的业务号。
> 哈希只能当"疑似同一笔"的探测器；把它提升为主键，等于让内容的变化去改写身份，而资金系统里，身份是不能被内容改写的。

# 附录 D：主从切换丢锁，到底能防到什么程度

## D.1 先把问题问准

"如何保证主从不会失效"这个问法本身没有答案，因为**不存在不失效的锁**。任何基于租约的互斥（Redis、etcd、ZooKeeper 全部包括）都会在租约到期时失效。

能被保证的只有一件事：

> **锁失效时，不变量仍然成立。**

所以问题应该拆成两问：

1. 丢锁的**概率**能压到多低？（工程问题）
2. 丢了之后**后果**能压到多小？（设计问题）

这两问的答案不一样，第二问才是决定性的。

## D.2 两个窗口，别混为一谈

| 窗口 | 成因 | Redis 有 | etcd/ZK 有 | 能否靠续期解决 |
|---|---|---|---|---|
| **复制窗口** | `SET NX` 在主节点成功，异步复制未到从节点，主节点宕机 | 有 | **无**（写入多数派确认才返回） | 不能 |
| **租约窗口** | 客户端 GC 停顿 / 网络抖动，TTL 到期后被别人拿走 | 有 | **有** | 续期能缩小，但会引入新问题（见附录 B） |

**关键区别**：Redis 的问题是"确认"与"持久"分离——客户端收到 `OK` 时，锁可能只存在于一个节点上。etcd/ZK 把两者绑在一起，写入返回即意味着多数派已落盘。

但**租约窗口两者都有**。所以"换 etcd 就安全了"是错的：一个停顿 40 秒的线程，在 etcd 上照样会在醒来后基于过期状态写数据。etcd 消除的是复制窗口，不是租约窗口。

## D.3 六种手段的真实效力

| 手段 | 消除复制窗口 | 消除租约窗口 | 真实定位 |
|---|---|---|---|
| Redisson 看门狗续期 | 否 | 部分（但把"可观测失败"变成"不可观测挂起"） | 不推荐，见附录 B |
| 固定 `leaseTime` | 否 | 否（但保证最终会释放） | 必要，防死锁 |
| `WAIT n timeout` | **收窄，不消除** | 否 | 值得用，但有前提（D.4） |
| Fencing token | 否 | **是**（资源端拒绝旧持有者） | 资源能比较 token 时才可用 |
| 数据库唯一约束 / 条件更新 | **不需要锁** | **不需要锁** | 首选 |
| etcd / ZooKeeper | **是** | 否 | 强互斥且资源在库外时 |

三条常被说错的：

**① "Redisson 3.17+ 已废弃 RedLock"** —— 被标记 `@Deprecated` 的是 `RedissonRedLock` 这个**类**（官方建议改用 `RedissonMultiLock`），Redlock 算法本身仍在实现中。说"争议大、新项目不推荐"可以，但**别背具体版本号**，容易被追问穿。

**② "ZooKeeper/etcd 主节点挂了也不会丢锁"** —— 不严谨。它们保证的是"不会出现客户端以为加锁成功、但集群里没有这把锁"；租约到期照样丢锁。准确说法是**消除了复制窗口**，不是"不会丢"。

**③ "`WAIT` 能保证锁已同步"** —— 不能。`WAIT` 只保证"N 个副本确认收到了这条命令"，**不保证故障转移时被提升的就是那个确认过的副本**（Sentinel 选复制偏移最大的，通常是，但不是协议保证）。它只能收窄窗口。

## D.4 `WAIT` 怎么用才对：必须同连接

这是最容易写错的一处。`WAIT` 是**连接级**命令，它等待的是**当前这条连接此前发出的写命令**被副本确认：

```
连接 C1: SET lock:xxx token NX PX 30000   → OK
连接 C1: WAIT 1 100                        → 1   ← 正确，检查的是 C1 上的写
```

```
连接 C1: SET lock:xxx token NX PX 30000   → OK
连接 C2: WAIT 1 100                        → 0   ← 错误，C2 上没有待复制的写命令
```

所以**不能"用 Redisson 加锁，再用另一个 Jedis 连接 WAIT"**：

- Redisson 的 `tryLock` 从连接池取连接执行 Lua，返回时连接**已归还**；
- 你手上的 `Jedis` 是另一条连接，`WAIT` 在它上面看到的是空队列，永远返回 0（或与锁无关的结果）；
- 而且 Redisson 不暴露"加锁用了哪条连接"，无从对齐。

要用 `WAIT`，就得放弃 Redisson 的封装，自己在**同一个 `RedisCallback` 里**完成 SET 和 WAIT：

```java
Boolean acquired = redis.execute((RedisCallback<Boolean>) conn -> {
    byte[] k = key.getBytes(StandardCharsets.UTF_8);
    byte[] v = token.getBytes(StandardCharsets.UTF_8);

    Boolean ok = conn.stringCommands().set(k, v,
            Expiration.milliseconds(ttl.toMillis()),
            RedisStringCommands.SetOption.SET_IF_ABSENT);
    if (!Boolean.TRUE.equals(ok)) {
        return false;                       // 没抢到，正常退出
    }

    Object r = conn.execute("WAIT".getBytes(StandardCharsets.UTF_8),
                            "1".getBytes(StandardCharsets.UTF_8),
                            "100".getBytes(StandardCharsets.UTF_8));
    long replicated = (r instanceof Number n) ? n.longValue() : 0L;

    if (replicated < 1) {
        // 关键：锁已经 SET 成功了，放弃前必须主动释放，否则要等 TTL 到期
        conn.execute(RELEASE_SCRIPT, new byte[][]{k}, v.getBytes(StandardCharsets.UTF_8));
        return false;
    }
    return true;
});
```

三个必须注意的点：

1. **`WAIT` 返回不足时必须主动释放锁**。这一步最容易漏——`SET` 已经成功，如果直接 `return false`，这把锁会占用到 TTL 结束，后续所有实例都抢不到，作业直接停摆。
2. **单机 Redis 上 `WAIT` 直接返回 0**（没有副本可等）。所以这段代码只在"配了副本"的环境启用，否则会把所有加锁都判成失败。
3. **`WAIT` 会阻塞这条连接**最多 `timeout` 毫秒。作业频率高时要确认连接池够用（项目现在 Hikari 10，Redis 连接池也要相应配）。

## D.5 本项目为什么不加 `WAIT`

三个理由，按重要性排：

**① 丢锁的代价已经被量化，而且很小。**

项目里锁只保护银行流水采集。丢锁的真实后果是：两个实例同时拉同一账户 → 同一批流水插两次 → `uk_payment_txn` 挡住 → `inserted=0, duplicated=N`。**数据正确，只是多调了一次银行接口。**

对一个每天跑 96 次的拉取作业来说，"多拉一次"的成本是几毫秒和一次 HTTP。而 `WAIT` 的代价是每次加锁多一个 RTT，外加一个"复制未确认就放弃"的分支——作业成功率下降，换来的收益是"少一次多余的 API 调用"。**不划算。**

**② 更根本的手段不是加确认，是缩短持锁时间。**

复制窗口的宽度是常数（复制延迟），租约窗口的宽度是持锁时长。**撞上主从切换的概率 ≈ 持锁时长 / 平均故障间隔。**

所以把 `doFetch` 的入库循环移出锁外（附录 B.5），持锁从 100 多秒降到 1 秒级，撞上切换的概率同比例下降——**不需要任何新机制，只是把锁管的事变少**。这比 `WAIT` 划算得多。

**③ 引入 `WAIT` 会把"Redis 可选"变成"Redis 必须配副本"。**

项目现在 `floorplan.lock.provider=memory` 就能跑，单机 Redis 也能跑。加了 `WAIT` 之后，部署形态被绑死：没有副本就永远加锁失败。**为一个已经被约束兜住的问题，牺牲部署灵活性，不值得。**

## D.6 那什么时候必须换 etcd / ZK

判据不是"重要不重要"，而是这三条同时成立：

1. 临界区里有**数据库管不住的外部副作用**（转账、扣库存、调第三方）；
2. 这个副作用**不能幂等**，重复执行会造成不可撤销的损失；
3. 资源端**无法比较 fencing token**（否则用 token 更简单）。

三条都成立时，才值得为一把锁引入第二个共识系统。**本项目三条都不成立**：采集的副作用可幂等（唯一约束）、能重复（多拉一次）、且资源是自己的库。

## D.7 面试 60 秒

> 主从丢锁没法"保证不发生"，因为 Redis 的复制是异步的——`SET NX` 在主节点返回 OK 时，锁可能还没到从节点。客户端收到的是"我写成功了"，不是"集群记住了"。这个窗口换 Redisson、换看门狗都关不掉。
>
> 能做的只有三件事：一是 `WAIT`，在同一连接上加锁后等同副本确认，它能把窗口收窄，但**不能消除**——因为故障转移时被提升的不一定是那个确认过的副本，而且单机上它直接返回 0；二是换 etcd，它写入要多数派确认，复制窗口没了，但**租约窗口还在**，客户端停顿 40 秒照样双持有；三是把锁管的事变少，让丢锁无所谓。
>
> 我选第三条。这个项目里锁只保护银行流水采集，丢锁的后果我算过：两个实例同时拉，唯一约束挡住，结果是 `inserted=0, duplicated=N`——数据是对的，只是多调了一次银行接口。所以我没加 `WAIT`：它每次多一个 RTT，还要求必须配副本，换来的只是少一次多余的 API 调用。
>
> 但我也没停在"反正有约束兜底"。我把入库循环移出了锁，持锁从 100 多秒降到 1 秒级——**撞上主从切换的概率和持锁时长成正比，缩短它比加任何确认机制都有效，而且不需要新组件。**

# 附录 E：当 `(account_ref, transaction_id)` 不唯一

前面 C.1 和 C.9.4 都把 `(account_ref, transaction_id)` 当成了"银行保证的唯一身份"，
并据此设计了"窄键决定收不收、宽键决定要不要看一眼"的分工。

**如果这个前提不成立，整个分工就是建筑在沙子上。** 这一节把前提拆开重做。

## E.1 先拆：不唯一有三种，处理方式完全相反

"流水号不唯一"这句话藏了三件完全不同的事。混在一起谈，方案必然错。

| 情形 | 现象 | 本质 | 正确处理 |
|---|---|---|---|
| **A. 同一笔被报多次** | 同一行在文件里出现两次；或两份窗口重叠的文件都含它 | 描述相同、确实是同一笔 | **去重** |
| **B. 不同笔复用同一个号** | 流水号按天/按月重置，次日第一笔又变成 `0001` | 描述不同、确实是两笔 | **绝不能去重** |
| **C. 根本没有号** | CSV 没这列；MT940 的 `:61:` 银行参考段是可选字段 | 无从判断 | **按文件位置定位** |

情形 B 才是真正致命的那个。原因不是"重复没挡住"，而是**挡错了方向**：

```
账户 ACC-001，流水号按天重置
  11-07  transaction_id = 0001   入金 1,000,000
  11-08  transaction_id = 0001   入金 2,500,000   ← 真实的一笔新钱
```

`ON CONFLICT (account_ref, transaction_id) DO NOTHING` 会在第二行静默返回 `inserted=0`。
系统统计里它被计为 `duplicated_count++`，日志上看起来"重复拉取，正常"。

结果就是：**银行账上有 250 万，系统里没有这条流水。**

C.4 坑二里我论证过"漏记比重复严重得多"——重复还能靠余额对账发现，漏记只能等客户投诉。
而这个唯一键在情形 B 下，**正好把每一笔跨期的真实入账都做成漏记**，且完全静默。

所以它不是"约束不够强"，是**约束指向的字段没有唯一性语义，却被赋予了拒绝写入的权力**。

## E.2 唯一性的四个层次，必须按最弱的那层设计

银行流水号的实际唯一性范围，比想象中窄得多：

| 层次 | 唯一性范围 | 典型来源 | 能否做幂等锚点 |
|---|---|---|---|
| L1 | 全局唯一 | 银企直连 API 的 `txn_id`（含银行码+网点+日期） | 能 |
| L2 | 账户内永久唯一 | 部分银行的连续流水号 | 能 |
| L3 | 账户内**按期**唯一 | **最常见**：按天重置、按月重置、按对账单期重置 | **不能** |
| L4 | 文件内唯一 | 只有行序号；MT940 `:61:` 的银行参考段常为空 | **不能** |

MT940 的 `:61:` 结构是：

```
:61: value_date [entry_date] D/C [funds_code] amount N type // bank_ref // customer_ref
```

其中 `bank_ref`（银行参考号）在 SWIFT 规范里**是可选的**，规范也**没有规定它的唯一性范围**。
日本地方银行的实际实现里，它经常是"当日第几笔"的计数器。附录 A.3 拆过这个字段，但当时没追问
"这个号到底在多大范围内唯一"——这正是这一节要补的洞。

**跨银行不能假设 L1 或 L2。** 所以设计必须落在 L4 上：
把唯一性从"银行给不给号"这件事上摘下来，改成**我方自己保证**。

## E.3 核心动作：把唯一性的责任收回到解析器

这是这一节唯一需要记住的一句话：

> **幂等锚点不能依赖外部系统"应该唯一"的字段，只能依赖我方能证明唯一的字段。**

我方唯一能证明的是什么？

- 一份对账单文件，我读了它，它就是我方的一个**不可变输入**；
- 这份文件里有几行，是我数出来的；
- 第几行是第几行，是我按物理位置定的。

所以唯一的组合是：

```
(statement_id, line_no)   —— 哪份对账单的第几行
```

这两个字段的取值**完全由我方决定**，银行的号怎么变、有没有号、重不重置，都不影响它。
这就是"把不确定性关进笼子"：不是消除银行的不稳定，而是**让不稳定不进入唯一键**。

## E.4 锚点重构：三层，各管一段

| 层 | 键 | 位置 | 唯一性由谁保证 | 冲突时 |
|---|---|---|---|---|
| 对账单 | `UNIQUE (account_ref, statement_id)` | `bank_statement_headers` | 我方（文件身份） | **整份跳过**，不解析 |
| 流水行 | `UNIQUE (account_ref, statement_id, line_no)` | `payment_transactions` | 我方（解析器） | 跳过该行 |
| 内容 | `INDEX (content_hash)` 非唯一 | `payment_transactions` | —（不可靠） | 打 `SUSPECT_OVERLAP` 标，**照样入库** |

三层的职责边界：

- **第一层挡掉 90% 的重复**。真实的重复来源里，重试、并发、定时任务重叠、SFTP 重发，
  全都表现为"同一份文件被投递了多次"。这一层用整份跳过处理，最便宜也最安全——
  因为连解析都不做，不存在解析规则漂移带来的差异。
- **第二层挡掉单份文件内部的重复**。同一文件里分页重叠、正则重复匹配，行号不同但内容相同，
  这时才轮到 `content_hash` 在同一 statement 内做检测。
- **第三层只输出候选**。跨文件的重叠区间（比如 11-08 的文件里含 11-07 最后两笔）
  唯一键挡不住，因为 statement 不同、line_no 不同。这时 `content_hash` 命中只表示
  "这笔钱可能已经来过"，落 `needs_review`，**绝不自动删**（C.4 坑二）。

`transaction_id` 从此**降级为普通索引**，只作检索线索（E.8）。

## E.5 `statement_id` 怎么造：三个来源，优先级固定

| 优先级 | 来源 | 取值 | 说明 |
|---|---|---|---|
| 1 | 银行给的对账单号 | MT940 `:28C:` 的 statement number + `:60F:` 的期初日期 → `20261108-0042` | 最好，但只有 MT940 类报文才有 |
| 2 | 文件名（去扩展名） | `ACC-001-20261108` | 文件交换模式的真相：文件名就是"哪份对账单" |
| 3 | 拉取窗口 + 分页 | `API-20261108-0000-2359-p1` | API 通道没有文件，用请求参数构造 |

第 2 条容易被忽略，但它其实是文件交换模式下最正确的选择：**银行把"对账单的身份"编码在文件名里了**，
只是没写成字段。`ACC-001-20261108.csv` 这个名字本身就表达了"ACC-001 这个账户 11-08 那份对账单"。

### `statement_id` 里必须再存一个 `file_hash`，否则会漏掉"更正后重发"

这是 `statement_id` 方案唯一的天生缺陷：

| 场景 | `statement_id` | `file_hash` | 判断 |
|---|---|---|---|
| 同一文件重发 | 相同 | 相同 | 真正的重复，整份跳过 ✓ |
| 银行更正金额后重发 | 相同 | **不同** | **不是重复**，是同一份对账单的新版本 |
| 跨日窗口重叠 | 不同 | 不同 | 不是重复，靠 `content_hash` 检测 |

如果只按 `statement_id` 跳过，第二种场景会被当成重复直接丢掉——银行更正了一笔金额，
系统还是旧值，**而且永远不知道有更正**。

所以 `bank_statement_headers` 上要同时存 `file_hash`，冲突处理分两路：

```sql
INSERT INTO bank_statement_headers (account_ref, statement_id, file_hash, ...)
VALUES (?, ?, ?, ...)
ON CONFLICT (account_ref, statement_id) DO NOTHING;
-- 影响 0 行 → 再查一次 file_hash 比对：
--   相同 → 真重复，整份跳过，bump reprocessed_count
--   不同 → 同一对账单的新版本，走「更正」流程：
--          旧版本行标 superseded_by，新版本按 line_no 正常入（可能撞行号，见 E.9）
```

`file_hash` 用文件字节的 SHA-256。现有 `bank_fetch_batches.file_fingerprint` 已经在算这个了
（`CsvBankStatementSource.fetch` 里累积 `digest`），只是它算的是"本次所有文件累积"，
粒度错了——**它应该是每份对账单一个哈希，而不是每次拉取一个哈希**。

## E.6 `line_no` 必须是**物理行号**，不是解析后的序号

这个细节会咬人，而且是在上线半年后才咬。

设想解析器里有一个跳过条件（脏行、窗口外、表头）。现在有两种定义：

| 定义 | 重解析时是否稳定 | 风险 |
|---|---|---|
| 解析后的第 N 条有效流水 | **不稳定** | 修一个解析 bug，某行从"跳过"变成"有效"，后面所有行的序号**整体偏移** |
| 文件物理行号（含表头、空行、窗口外的行） | 稳定 | 序号不连续，但唯一性只要求唯一，不要求连续 |

选后者。理由很直接：**`line_no` 的语义是"位置"，不是"第几笔"。** 位置只要文件不变就不变，
而"第几笔"会随解析规则变化——用它做唯一键，等于让代码版本决定数据身份，
**一次解析器升级就能让同一份文件重新入库一遍或漏掉一段**。

落地写法（`CsvBankStatementSource.parse` 里现成的 `rawLines` 下标就是物理行号）：

```java
String[] rawLines = content.split("\n", -1);
for (int i = 0; i < rawLines.length; i++) {
    int physicalLineNo = i + 1;          // 1-based，含表头/空行
    ...
    out.add(new BankStatementLine(statementId, physicalLineNo, txnId, ...));
}
```

`BankStatementLine` 现在的 `isUsable()` 要求 `transactionId` 非空。**这个校验要放开**：
情形 C 下没有流水号是正常数据，不能当脏数据丢掉（否则就是 E.1 的漏记）。
改成 `statementId` + `lineNo` 非空即可用，`transactionId` 允许空。

## E.7 对账单是实体，不是"批次日志"

现在的 `bank_fetch_batches` 把"对账单"和"一次拉取运行"混成了一张表：

```
bank_fetch_batches: batch_no, account_ref, value_date_from/to, status,
                    fetched_count, inserted_count, duplicated_count, file_fingerprint
```

问题在于**一次拉取可以包含多份对账单，一份对账单也可能被多次拉取**——这是多对多，
塞进一张表就只能记"最近一次"，余额链校验需要的期初/期末余额也没地方放。

正确的建模是拆成两张：

```sql
-- 对账单：银行的客观事实，一份一行，是余额链校验的载体
CREATE TABLE IF NOT EXISTS bank_statement_headers (
    id               BIGSERIAL PRIMARY KEY,
    account_ref      VARCHAR(32) NOT NULL,
    statement_id     VARCHAR(64) NOT NULL,     -- 银行对账单号 / 文件名 / 窗口分页
    file_hash        CHAR(64)    NOT NULL,     -- 整份内容的 SHA-256（检测"更正后重发"）
    period_start     DATE        NOT NULL,
    period_end       DATE        NOT NULL,
    opening_balance  BIGINT,                   -- :60F: 期初余额（MT940 必有）
    closing_balance  BIGINT,                   -- :62F: 期末余额
    line_count       INT         NOT NULL DEFAULT 0,
    status           VARCHAR(16) NOT NULL DEFAULT 'PARSED',
        -- PARSED / VERIFIED 余额链通过 / BROKEN 余额链断裂 / SUPERSEDED 被新版本替代
    balance_check    VARCHAR(16),              -- OK / AMOUNT_MISMATCH / BALANCE_GAP
    collected_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uk_stmt UNIQUE (account_ref, statement_id)
);

-- 采集批次：运行日志，多对多挂对账单
CREATE TABLE IF NOT EXISTS bank_fetch_batch_statements (
    batch_no      VARCHAR(64) NOT NULL,
    statement_id  VARCHAR(64) NOT NULL,
    account_ref   VARCHAR(32) NOT NULL,
    PRIMARY KEY (batch_no, account_ref, statement_id)
);
```

`bank_fetch_batches` 保留不动，作为纯运行日志（`fetched_count` / `inserted_count` 仍然有用），
只是不再承担"对账单身份"的职责。

**这一步不是重构癖。** 没有 `opening_balance` / `closing_balance`，E.9 的余额链校验就做不了；
而余额链是唯一能发现"文件不全"的手段（附录 A.6 已经论证过）。

## E.8 `transaction_id` 还能干什么：降级，不删除

它不再是唯一键，但删掉它是另一种损失。它有三个正当用途：

1. **银行客服核对**："这笔钱你们银行给的流水号是多少"——只有这个字段能对上话。
2. **争议自证**：客户说付了、系统说没收到，拿流水号去银行调单。
3. **同账户重号检测**：建**非唯一**索引后，跑一条巡检 SQL 就能发现"情形 B"到底有多严重：

```sql
-- 同一账户内流水号重复 = 银行按天/按期重置的证据
SELECT account_ref, transaction_id, count(*) AS n,
       min(value_date) AS first_date, max(value_date) AS last_date,
       array_agg(DISTINCT statement_id) AS stmts
  FROM payment_transactions
 WHERE transaction_id <> ''
 GROUP BY account_ref, transaction_id
HAVING count(*) > 1
 ORDER BY n DESC
 LIMIT 50;
```

这条 SQL 本身就是**给面试官看的证据**：它不是防御性的"万一重复呢"，
而是"我看过数据，知道它重复，所以我知道唯一键必须建在哪"。

## E.9 余额链：不依赖任何标识符的正确性校验

前面所有方案都还在依赖某个"键"。余额链不依赖任何键，它校验的是**账务恒等式**：

```
对每份对账单，按 line_no 升序：
  expected[0]   = opening_balance + signed_amount[0]
  expected[i]   = expected[i-1]   + signed_amount[i]
  balance_after[i] == expected[i]                      ← 逐笔校验（银行给逐笔余额时）
  balance_after[n-1] == closing_balance                ← 末行校验
```

这条链的强度来自一个性质：**任何重复、任何遗漏、任何金额篡改，都会让它断裂。**

| 错误 | 唯一键能否发现 | 余额链能否发现 |
|---|---|---|
| 同一行入库两次 | 能（若键正确） | **能**（金额被加两次） |
| 漏掉中间一行 | **不能** | **能**（链断开） |
| 金额被改成 990,000 | 不能 | **能** |
| 流水号重置导致误判重复 | **不能，而且它自己制造漏记** | **能** |

最后一行是关键：**唯一键在情形 B 下既发现不了漏记，还是漏记的制造者。** 余额链能。

两种校验强度，取决于银行给不给逐笔余额：

- **有逐笔余额**（多数 CSV 导出）→ 逐笔校验，定位到具体哪一行断了；
- **只有期初期末**（MT940 标准，`:61:` 本身不含余额）→ 退化成总额校验：
  `Σ signed_amount == closing_balance - opening_balance`。

总额校验有个理论盲区：**重复一笔 + 漏一笔，且金额恰好相等时，净额不变，漏检**。
但这种情况要求两个错误同时发生且金额相等，概率远低于"流水号重置"这种每天必发的事件。
**用总额校验替代唯一键，是明显的净收益。**

落地位置：解析完成、入库之前，在 `BankStatementResult` 上做。它现在只有
`List<BankStatementLine> lines` 和一个 `fingerprint`（且注释里还写着"幂等键是
`(account_ref, transaction_id)`"），要扩成按 statement 分组并带上期初期末余额：

```java
public record StatementBlock(
        String statementId,
        String fileHash,
        LocalDate periodStart,
        LocalDate periodEnd,
        long openingBalance,        // 无此信息时用 Long.MIN_VALUE 标记"不可校验"
        long closingBalance,
        List<BankStatementLine> lines) { }
```

校验失败时的动作，**必须是"整份标记 + 告警"，不是"跳过"**：

```
balance_check != OK
  → bank_statement_headers.status = 'BROKEN'
  → 该对账单的流水仍然入库（钱是真的，不能不入）
  → 但全部打 needs_review = TRUE, review_reason = 'BALANCE_GAP'
  → 触发告警：账号 + 期号 + 差额
```

**为什么不拒收**：余额链断裂说明"这份对账单不完整"或"我方解析错了"，
两种情况下钱都是真实存在的。拒收就是制造账外资金——回到 C.4 坑二那条铁律：
**最坏结果应该是"多几条待复核"，不是"少一条流水"。**

## E.10 迁移：已有的重复数据怎么办

现有 V15 的唯一约束 `uk_payment_txn (account_ref, transaction_id)` 如果真实数据里存在情形 B，
它要么根本建不上（V15 执行失败），要么已经把数据挡成了漏记。两条路都要处理。

### 先记住一条硬规则：不要改 V15

Flyway 会校验已应用迁移的 checksum。**改 V15 会让应用下次启动直接失败**
（`Validate failed: Migration checksum mismatch`）。V15 的注释里那句
"`(账户引用码, 银行流水号)` 才是这笔钱在银行侧的唯一身份"是错的，
但**只能在 V16 里纠正，不能在 V15 里改**。

### V16 五步，顺序不能换

```sql
-- ① 摘掉不能成立的唯一约束（先摘，否则后面回填写不进去）
ALTER TABLE payment_transactions DROP CONSTRAINT IF EXISTS uk_payment_txn;

-- ② 加三列，先允许 NULL
ALTER TABLE payment_transactions
    ADD COLUMN IF NOT EXISTS statement_id VARCHAR(64),
    ADD COLUMN IF NOT EXISTS line_no      INT,
    ADD COLUMN IF NOT EXISTS content_hash CHAR(64),
    ADD COLUMN IF NOT EXISTS needs_review   BOOLEAN NOT NULL DEFAULT FALSE,
    ADD COLUMN IF NOT EXISTS review_reason  VARCHAR(32);

-- ③ 历史数据回填：借主键当行号，保证回填后必然唯一
UPDATE payment_transactions
   SET statement_id = 'LEGACY-V15',
       line_no      = id::int
 WHERE statement_id IS NULL;

-- ④ 收紧 NOT NULL —— 此时不可能失败，因为上面已经填满
ALTER TABLE payment_transactions
    ALTER COLUMN statement_id SET NOT NULL,
    ALTER COLUMN line_no      SET NOT NULL;

-- ⑤ 建新唯一索引 + 把旧键降级为普通索引
CREATE UNIQUE INDEX IF NOT EXISTS uk_payment_stmt
    ON payment_transactions (account_ref, statement_id, line_no);

CREATE INDEX IF NOT EXISTS idx_ptx_bankid
    ON payment_transactions (account_ref, transaction_id);
```

**第 ③ 步 "`line_no = id`" 是这次迁移的关键技巧。**
历史数据没有真实的文件行号，但唯一索引要求 `(statement_id, line_no)` 不重复。
用主键填空，等于让每条历史记录自成一个"位置"——索引一定能建起来，不用回头清洗数据。
新数据从 V16 上线那一刻开始填真实行号，历史数据永久停留在 `LEGACY-V15` 这一份"虚拟对账单"里。
这是**先让约束生效，再慢慢把历史迁到正确语义**，而不是"等数据洗干净再建约束"（永远等不到）。

### 为什么唯一索引里还要带 `account_ref`

`statement_id` 由我方生成，理论上已经隐含账户。但保留 `account_ref` 有两个好处：

1. **索引前缀可用**：`(account_ref, statement_id, line_no)` 的前两列能服务"按账户查对账单"；
2. **防御生成规则变更**：某天 `statement_id` 的拼法改了（比如从文件名换成对账单号），
   不同账户可能撞出同一个字符串。带上 `account_ref` 就撞不了。

代价是两个账户字段各多 32 字节。这个代价换来的是"生成规则可以演进"，值得。

## E.11 代码改动清单

| 文件 | 改动 |
|---|---|
| `BankStatementLine` | 加 `statementId`、`lineNo`；`isUsable()` 改为 statement/line 非空，**放开 `transactionId` 必填** |
| `BankStatementResult` | 由"扁平 lines + 一个 fingerprint"改为 `List<StatementBlock>`，每块带期初期末余额 |
| `BankStatementSource` | 接口文档里"去重责任方是 `uk_payment_txn`"这句必须改（这就是 E.1 的错误前提的源头） |
| `CsvBankStatementSource` | `parse` 用物理行号；`statementId = 文件名去扩展名`；每文件独立算 `fileHash` |
| `JdbcPaymentTransactionRepository` | `saveIfAbsent` 的 `ON CONFLICT (account_ref, transaction_id)` → `ON CONFLICT (account_ref, statement_id, line_no)` |
| `JdbcBankFetchBatchRepository` | 增加 `bank_statement_headers` 的 upsert（含 file_hash 比对分支） |
| V16 迁移 | 上面五步 + `bank_statement_headers` + `bank_fetch_batch_statements` |

`saveIfAbsent` 改完之后，`BankFetchApplicationService` 里的统计口径要跟着变：

- `inserted` = 主表实际插入行数
- `duplicated` = 被 `uk_payment_stmt` 挡下的行数（**真正的重复**）
- 新增 `overlapped` = `content_hash` 命中但唯一键未挡下的行数（**待复核**，不是重复）

三个计数分开，是为了让对账时能一眼看出"这批是重发了，还是银行给了重叠区间"。
**混成一个 `duplicated`，等于把"数据正确"和"数据可疑"记成同一件事。**

## E.12 面试 90 秒

> 我一开始把 `(账户, 银行流水号)` 当幂等键，因为直觉上流水号应该唯一。后来查数据发现不是——
> 日本地方银行的流水号很多是按天重置的，`0001` 每天都会出现一次。
>
> 这时那个唯一约束就从"防线"变成了"隐患"：第二天的第一笔真实入账会被 `ON CONFLICT DO NOTHING`
> 静默当成重复丢掉，日志上只是 `duplicated_count++`，看起来完全正常。
> **重复入账还能靠余额对账发现，漏记只能等客户投诉。** 所以这个约束失效的方向正好是最危险的那个。
>
> 我把它拆成三层。第一层是**对账单级**：`(account_ref, statement_id)` 唯一，`statement_id` 用文件名或
> 银行对账单号，冲突就整份跳过——重试、并发、SFTP 重发这些最高频的重复，连解析都不用做就被挡住了。
> 第二层是**行级**：`(account_ref, statement_id, line_no)` 唯一，`line_no` 用**文件物理行号**而不是
> 解析后的序号——因为解析规则一改，序号会整体偏移，等于让代码版本决定数据身份。
> 第三层是**内容指纹**：只做探测器，命中就打 `SUSPECT_OVERLAP` 标进复核队列，绝不自动删。
>
> 关键的一步是**把唯一性的责任从银行收回到解析器**。`statement_id` 和 `line_no` 都是我方能证明的，
> 银行给不给号、重不重置都不影响。`transaction_id` 降级成普通索引，只用来跟银行客服对话。
>
> 最后是正确性怎么保证——不靠键，靠**余额链**：每份对账单按行号累加，`期初 + Σ金额 == 期末`。
> 任何重复、遗漏、金额篡改都会让链断裂，而唯一键只能发现重复、发现不了遗漏。
> 链断了不拒收，钱是真的，全部打 `needs_review` 加告警——**最坏结果是多几条待复核，不是少一条流水。**

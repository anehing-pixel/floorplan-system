## 一、先定调：这个项目在面试里是什么水位

**三十秒版本：**

> 这是一个日本汽车经销商库存融资（Floorplan）的核心账务系统。经销商每进一台车，金融公司替它向厂家垫付 90% 车款，车作为担保物质押在库里；车卖掉后 2 个营业日内必须还款，还完额度回补，可以再进下一台。
>
> 系统的本质不是"贷款审批流"，而是**以车架号为主键的单台独立核算账本**：每台车独立垫款、独立计息、独立结清，额度是循环的。技术上是 **DDD 四层 + Spring Cloud 微服务**：核心账务留在单体守住事务红线，auth/credit/bank/risk/loan/collateral-reg/release/recon 等外围上下文按限界上下文拆成独立服务，网关统一入口切流。难点集中在三处：额度并发不超额、批量计息可重跑、付款与记账的跨系统一致性。

**面试水位判断（诚实版）：**

| 维度 | 评价 |
|---|---|
| 业务建模 | 强。11 环节闭环、状态机白名单、部分唯一索引、终态替代软删除，都有 ADR 支撑 |
| 事务与并发 | 强。事务边界按外部调用切分，`FOR UPDATE` 用得对，自调用绕过代理的坑踩过并解决 |
| 架构演进 | 中上。有清晰的拆分边界与"核心账务不拆"的取舍；服务靠 `@Import` 精确装配而非全包扫描；网关切流 + 跨服务 JWT 互通已跑通。短板是**服务共用同一个库，数据未分库**，且本地无注册中心 |
| 工程完备性 | 中上。**129 个单元测试**覆盖状态机、鉴权、生产检查、调度锁等关键路径；Python 端到端冒烟 **290** 条（主干+事件，走网关）、USED 209 条、浏览器 37 条、Redis 锁 7 条；统一 `common` 收敛横切代码。**短板**：domain 层未做全矩阵覆盖、无 CI |
| 生产就绪 | 中下。作业调度 + 分布式锁 + 生产配置 fail-fast 已落地；但批处理仍有单事务全量扫表、无分片；无 actuator/链路追踪、无压测/灰度、物理拆库未开始、网关本阶段不下沉验签 |

**所以面试策略是：主攻业务建模与事务设计，把微服务拆分作为"架构演进"的加分项展开，主动交代测试短板并给出补法。** 主动认短板比被问出来强十倍。

## 二、业务流程：钱与车的双向闭环

### 2.1 一句话讲清资金流

```
金融公司 ──垫款90%──> 厂家/上游供应商（直付，不经经销商手）
   ↑                        │
   │                     车辆发运
   │                        ↓
   └──还款(本金+利息)── 经销商（车质押在库）──零售──> 终端客户
                          ↑                         │
                          └──────── 车款 ───────────┘
```

关键点（面试官最容易忽略但最体现理解的地方）：

1. **钱不经过经销商**：`DIRECT_PAY` 直接付上游，防止经销商挪用资金。打款对象由采购订单的 `supplier_type` 决定，不由系统规则决定（ADR-007）。
2. **还款发生在售出之后**：不是按月还，是"售出即还"。售出日 + 2 个营业日 = 结算到期日，超期即逾期。
3. **额度是循环的**：还一台、放一台。所以"结清"必须原子完成三件事——核销本金、解除担保、**回补额度**（少做第三件，循环授信就断了）。

### 2.2 十一环节（背这张表）

| # | 环节 | 系统落点 | 一句话风险 |
|---|---|---|---|
| ① | 授信与准入 | `credit_lines` | 发起与审批分离 |
| ② | 验车与确权 | `batch-ingest` + `financing_lien_checks` | 重复融资拦截（P0-③） |
| ③ | 收车申请与放款 | `advances` 三段式 | 打款对象跟订单走 |
| ④ | 担保设定 | `security_records` / `collateral_ledger` | 日本：让与担保，非扣押钥匙 |
| ⑤ | 在库计息 | `interest_ledger` 日终批 | 可重跑、可补算 |
| ⑥ | 库龄递减 | `aging_plans` | 90 天触发，每期还 10% 本金 |
| ⑦ | 零售成交 | `markSold` | 倒计时开始 |
| ⑧ | 解押出库 | 出库指令 + `security/release` | 钱未到不得放车 |
| ⑨ | 额度恢复结清 | `settle` 三件事原子 | 漏解保 = 车还挂在金融公司名下 |
| ⑩ | 违约处置 | `disposal_cases` | OOT（脱信销售）是最严重违约 |
| ⑪ | 额度年审冻结 | `annual_reviews` | 冻结可恢复且留痕 |

**必须能讲的三个业务判断：**

- **为什么"建账"和"申请垫款"是两个状态？** 建账后还有一道线下验车确权。若合并，待放款工作台会把没验过的车列给放款岗，可能对一台未确权的车付款。
- **为什么"已赎回"不能复用"已结清"？** 资金动作完全一样，但车还在库里，可以再融资。合并就再也判断不出"这台车还能不能借"。
- **为什么"逾期"是状态而"逾期天数"是标记？** 逾期天数每天都变，做成状态会导致状态机爆炸；状态只表达"是否已进入违约处置流程"。

### 2.3 状态机（白板必画）

见对话中的生命周期图。代码在 `VehicleStatus.canTransitTo()`（`domain/.../VehicleStatus.java:128`），用 `switch` 表达式实现白名单，**不用任何状态机框架**——理由是 ADR-002「禁止把业务规则藏在框架回调里」。

**追问必答：为什么不用 Spring StateMachine？**
> 状态机框架的回调会让"什么条件下允许流转"散落在配置和监听器里，排障时要跨三个文件才能回答"为什么这台车不能售出"。白名单写在一个 switch 里，读一遍就懂，且能单测。代价是加状态要改代码，但状态本来就是业务契约，改它就该走评审。

**文档与代码的一处漂移（自己先说出来）：**
`业务流程文档.md:122` 写了 `DISPOSING → SETTLED`（处置中补缴的例外），但 `VehicleStatus:140` 只允许 `DISPOSING → CLOSED`。这是文档先行、代码未跟上的典型，面试时可以作为"我如何保证文档与代码一致"的引子——目前靠人，应该用契约测试或从枚举生成状态图。

## 二点五、架构演进：从模块化单体到 Spring Cloud 微服务

> 这一章是后来演进出来的，也是面试里最容易讲出"工程判断力"的地方。
> **核心论点：拆服务是手段不是目的，判断标准是"这块逻辑的价值是否依赖本地事务"。**

### 2.5.1 服务拓扑（白板画这张）

一句话记住：**一个入口 + 九个业务服务 + 一个 DMZ + 一个共享库 + 四层共享代码**。

### 2.5.2 拆哪些、不拆哪些——判断标准是什么

| 服务 | 拆出来的上下文 | 为什么能拆 |
|---|---|---|
| auth-service | 认证授权 | 无业务账务状态，纯读用户表 + 签 token，天然独立 |
| credit-service | 授信主体（经销商/额度/评级/年审） | 读多写少，额度"核定/冻结/解冻"是配置类写入，边界清晰 |
| bank-service | 银行回款流水采集 + 匹配 | 外部集成，高频作业，幂等靠行级唯一约束；匹配结论落库、事件由本服务发布 |
| risk-service | 预警/盘点/处置/担保/权属核对 | 对账与处置逻辑，引用账本但不写核心账 |
| loan-service | 借据 / DPD / 经销商画像 | 读多写少；逾期口径的唯一权威源（ADR-008）；消费 `LOAN_CREATED` |
| collateral-reg-service | 担保权属只读投影 | 权威源是 `collateral_registration_batches`，本服务只读（Q27） |
| release-service | 出库指令状态机 | 跨机构异步协同，不能拖住 core 的同步账本事务 |
| recon-service | 8 条对账规则 | 只读账本、与写链路解耦，不占事务资源 |
| **floorplan-core（web）** | **垫款/还款/计息/车辆台账/采购单** | **不拆——见下** |

**"核心账务为什么不拆"是这章最重要的一题：**

> 垫款、结清、计息这些是**有状态的账本写入**，正确性依赖三样东西：本地事务、`SELECT ... FOR UPDATE` 行锁、数据库唯一约束。比如结清要在**一个事务**里原子完成"核销本金 + 解担保 + 回补额度"，少做一件账实就分叉。这些要保证的是一个强一致的不变量。
>
> 一旦拆成多个服务，这个不变量就跨了网络边界，要么上分布式事务（Seata/TCC），要么做 Saga 补偿——对一个"必须在同一时刻原子成立"的账本操作，这是**用复杂换复杂，还是倒退**。所以我的边界是：**价值依赖本地事务的逻辑留在单体，其余按限界上下文拆出去。**

> 追问："那这不还是单体吗？" 答：核心账务确实还是一个单体进程，但我没有回避——微服务不是"全都拆"，而是**把该隔离的隔离**。八个外围上下文已经是独立进程、独立端口、独立部署，网关切流已验证；核心账务保持单体是**主动的架构取舍**，不是没做完。我在 README 和代码注释里都写明了这条红线。

### 2.5.3 拆开的四层怎么处理——共享依赖 + 精确装配

常见错误是把 `domain`/`application`/`infrastructure` 复制成四份，或者干脆全包扫描把所有 bean 都装进每个服务。这里的做法是**两者都不**：

- 四层作为 **Maven 共享依赖**（jar），编译期复用，代码只有一份；
- 每个服务是一个新的启动类，用 `scanBasePackages` 只扫自己的 controller 包，再用 `@Import` **按类精确注入**它需要的 ApplicationService 和仓储实现：

```java
@SpringBootApplication(scanBasePackages = "com.company.floorplan.auth")
@Import({AuthApplicationService.class, JdbcAuthUserRepository.class,
         GlobalExceptionHandler.class})
@EnableDiscoveryClient
public class AuthServiceApplication { ... }
```

> 追问："为什么不把类直接搬进 auth-service？" 答：迁移成本。这些类的实现和依赖目前被多个服务共享，先靠装配划清"谁用哪些类"，等边界稳定、确认没有交叉引用，再物理搬迁到各服务、最后彻底删掉共享模块里的副本。这是**渐进式拆分**，不是一次性大爆炸重构。装配清单就是拆分的"合同"。

横切代码（统一响应 `ApiResponse`、`RequirePermission`、`JwtAuthInterceptor`、全局异常、审计操作人）抽到 `common` 模块，避免各服务各写一份。`ApiRequests` 这类请求体因为边界不同，故意不抽。

### 2.5.4 网关切流：精确优先 + 双模 URI

- **精确规则在前，兜底在后**——Gateway 是"首个匹配即命中"。`/api/vehicles/*/lien-check` 必须排在 `/api/vehicles/**` 前面（否则权属核对会被核心账务吃掉）；`/api/jobs/bank-fetch` 必须排在 jobs 其他端点前。这两条正是从混合 Controller 里精准摘出来的方法，靠**路由顺序**保证落到新服务。
- **双模 URI**：写成 `${ROUTE_AUTH:lb://auth-service}`。生产走 Nacos 服务发现 + 负载均衡；本地无 Nacos 时用 `ROUTE_*=http://127.0.0.1:<port>` 覆盖成直连。**切换不改代码，只改配置**。
- 切流正确性靠走网关的 **290** 项冒烟断言验证，而不是凭路由表看起来对。

### 2.5.5 跨服务鉴权：统一密钥 + 零信任

- JWT 密钥全服务一致（`floorplan.auth.secret`），auth 签发的 token 各服务都能验；冒烟测试先登录拿 token，再带它访问各服务，正是验证了这一点。
- **网关本阶段不验签**，只透传 `X-Request-Id`；鉴权下沉在各服务。理由：服务脱离网关直连时也不裸奔（零信任）。等端点全部迁完、鉴权链定型，再考虑上收到网关统一验签。
- **权限快照不能当授权依据（2026-11-24 补课）**：令牌里的 `perms/roles` 只作展示；每次请求回查用户启用、`token_version` 与 `user_roles` 现算权限。logout 把版本 +1，旧令牌立即 401；删角色旧令牌立即 403。

### 2.5.6 这一路踩的坑（都能讲，很真实）

| 坑 | 现象 | 解法 / 认知 |
|---|---|---|
| 版本矩阵不兼容 | Gateway 启动 `NoSuchMethodError: HttpHeaders.headerSet()` | Boot 3.2.5 默认 Spring Framework 6.1.6，Gateway 4.1.6 要 6.1.15+；在 Boot BOM **之前** import `spring-framework-bom:6.1.15` |
| 端口被环境变量劫持 | 各服务端口变成 51136，且"Port already in use" | WorkBuddy 注入 `SERVER__PORT=51136`，Spring 宽松绑定解析成 `server.port`；启动一律 `env -u SERVER__PORT` |
| 没有注册中心 | Nacos 连接失败堆栈，但服务其实起来了 | `discovery.fail-fast=false` 容忍注册失败；网关用 `ROUTE_*` 覆盖 `lb://` 为直连 |
| **前端页面回归** | 拆完服务后页面打开但功能全废 | 页面一直在 `static/`，但前端 `API_BASE` 还指向 8080（Controller 已摘除），且网关不托管静态资源。**修法**：页面与 API 统一走网关 18080，网关加静态资源路由 + CORS。**冒烟只打 API 不打页面，所以漏掉了这个回归**——测试维度的教训 |
| 后台进程留不住 | `start` 一返回服务就没了 | Git Bash(Windows) 下 `&` 起的进程随父 shell 退出被回收；`start` 改为前台保活 + `trap` 捕获 Ctrl+C 优雅清理 |
| **网关路由被宽路由吞掉** | `/api/dealers/{id}/bank-accounts` 直连 core 200、经网关 404 | Gateway 首个匹配即命中；精确路由必须排在 `/api/dealers/**` 之前。新增 `GatewayRouteOrderTest` + 网关侧断言，直连 200 不算通 |
| **Feign `fallback` 是死配置** | 配了降级类，故障时不进入 | 仓库无 circuit-breaker，`DefaultFeignTargeter` 不读 `fallback`；fail-closed 由 catch + null 判定保证 |
| **JWT 权限快照过期** | 删角色/禁用后旧令牌仍有效 8 小时 | V82 `token_version` + 每请求回查；logout 版本 +1 |
| **多实例游标互相覆盖** | 两个实例共用一个 `consumer_offsets` 游标 | V83 `lease_owner/lease_until` 原子认领/续租 2 分钟；至少一次 + 业务幂等 |
| **定时作业每个实例都跑** | 多实例重复执行；本地误跑；锁服务挂了裸跑 | `jobs.enabled` 默认 false + `DistributedLock` + 抢不到跳过 + 锁异常 fail-closed |
| **读矩阵过严导致业务 403** | 加读点后 operator 查经销商、USED 导入岗查 LTV 全部 403 | 按真实页面/工作流补最小读点，并在《读接口授权矩阵》登记 3 条实施例外 |

> 那条前端回归值得单独讲一句：**端到端测试全绿，不代表用户路径全绿。** 冒烟测的是 API 链路，页面走的是另一条路径。这和在领域层讲"可测试性 ≠ 实际测试"是同一个认知的不同体现。

### 3.2 六条设计决策（每条都能展开讲）

**① 金额一律 BIGINT 整数日元，比率用 NUMERIC**
```sql
invoice_amount BIGINT, advance_amount BIGINT, principal_balance BIGINT
advance_ratio NUMERIC(5,4), annual_rate NUMERIC(7,4)
```
理由：金融系统禁用 float/double。比率参与计算时用 `BigDecimal`，落金额字段前 `setScale(0, HALF_UP).longValueExact()`。日元最小单位就是 1 元，不需要小数。

> 追问："那多币种怎么办？" 答：当前表没有 `currency` 字段，是明确的单币种假设。要支持多币种，最小改动是加 `currency CHAR(3)` 并把金额改成"最小货币单位的整数"（美元用分），而不是引入小数。

**② VIN 直接作主键，不用自增 id**
```sql
CREATE TABLE vehicle_units ( vin VARCHAR(32) PRIMARY KEY, ... )
```
理由：业务主键就是 VIN，一台车一辈子一条台账。好处是幂等天然（重复建账直接主键冲突），坏处是 VIN 可能录错、且换车架号极罕见但要处理。

**③ 状态与风险标记分离**
`status`（生命周期，受状态机约束） vs `overdue_days` / `risk_level` / `oot_suspected`（风险标记，可每天变）。避免"逾期到底是状态还是标记"的建模歧义。

**④ 用终态代替软删除（这条最有讲头）**
`advances` 不删记录，用 `VOIDED`（未付款作废）/ `REDEEMED`（付款后还清）表达终结。V14 迁移里写了为什么不加 `deleted_at`：

> 软删除后，额度占用、还款核销、审计、对账每一处查询都必须带 `IS NULL`，**漏一处就是资损，且往往季度对账才暴露**。

并且 `VOIDED` 与 `REDEEMED` 必须分开：前者无资金流，后者有真实付款与还款。合并后财务对账分不清"从没付过钱"和"付了又还清"，垫款累计发生额会凭空少一整笔。

**⑤ 业务唯一性落在数据库，不靠应用层自觉**
```sql
-- 一车一笔有效垫款（部分唯一索引）
CREATE UNIQUE INDEX uk_adv_vin_active ON advances (vin)
  WHERE status IN ('PENDING','PROCESSING','PAID');
```
`WHERE` 条件必须与 `AdvanceStatus.occupiesVehicle()` 严格一致。这是整个项目最关键的一条约束，因为它的缺失导致过真实事故（见第五节）。

**⑥ 数据库层兜底业务不变量**
```sql
CONSTRAINT chk_credit_within_limit CHECK (used_amount + frozen_amount <= approved_limit)
```
即使应用层有 bug、有人直连数据库改数，也不可能出现额度超额。这是"不变量要有两道防线"的具体落地。

### 3.3 幂等靠什么（三个唯一约束）

| 约束 | 防什么 |
|---|---|
| `advances.idempotency_key UNIQUE` | 网络重试重复下单 |
| `interest_ledger (vin, biz_date) UNIQUE` | 批处理重跑重复计息 |
| `batch_runs (job_name, biz_date) UNIQUE` | 同一业务日重复执行作业 |

> 面试官爱问："幂等键和唯一约束有什么区别？" 答：幂等键防**同一个请求被重复发送**（调用方生成 key，重试用同一个 key）；唯一约束防**业务上不该出现的重复**（同一台车两笔有效垫款）。前者靠调用方自律，后者不可绕过。**幂等键挡不住业务重复**——这正是下面那个事故的根因。

## 四、事务与并发（面试主战场）

### 4.1 事务边界总表

| 用例 | 事务边界 | 加锁 | 原子动作 |
|---|---|---|---|
| 申请垫款 `stageAdvance` | 独立事务 | 额度 `FOR UPDATE` → 车辆 `FOR UPDATE` | 车辆→PENDING_ADVANCE、`occupy`、插 advance、写审计 |
| 放款 `disburseAdvance` | **无事务** | 无 | 调支付网关（外部 IO） |
| 落 PROCESSING `submitAdvance` | 独立事务 | 无（状态机幂等） | PENDING→PROCESSING、记 channelRef |
| 银行确认 `confirmAdvance` | 独立事务 | 车辆 `FOR UPDATE` | 翻 PAID、FINANCED→IN_STOCK、建担保台账 |
| 通道失败 `markFailed` | 独立事务 | 额度 → 车辆 | `release`、翻 FAILED、车辆回退 CREATED |
| 结清 `settle` | 单事务 | 车辆 → 额度 | 核销+SETTLED+解保+回补+还款单+垫款 REDEEMED |
| 提前赎回 `redeem` | 单事务 | 车辆 → 额度 | 同上，但落 REDEEMED 不是 SETTLED |
| 部分还款 `partialRepay` | 单事务 | 车辆 | 只扣本金，不解保、不回补额度 |
| 日终计息 `runDailyInterest` | 单事务、全量 | 无 | 补算、写流水、累计利息 |

### 4.2 为什么不把付款放进事务（核心答案）

**这是整个项目最值得讲的技术决策。**

```java
// AdvanceApplicationService.java:329
public Map<String, Object> disburseAdvance(String advanceNo, String actor) {   // 故意没有 @Transactional
    ...
    Advance pending = self.stageAdvance(...);        // 独立事务：已提交
    PaymentResult result = paymentGateway.pay(instruction);   // 事务之外调外部
    if (result.isFailed()) { self.markFailed(...); }          // 独立事务
    else { self.submitAdvance(...); }                          // 独立事务
}
```

如果付款和记账在同一个事务里，会同时踩两个坑：

1. **长事务持锁**：银行接口 3 秒超时，期间额度行锁不释放，同一经销商的所有垫款全部阻塞。
2. **钱付了、账没记**（更致命）：事务在 `pay()` 之后、`commit` 之前失败（宕机、连接断），钱已经出账，但数据库回滚了——**没有垫款记录、额度没占用、车还在"已建账"**。这笔钱变成了账外资产，只能靠对账发现。

拆成三段后：
- 第一段提交后，钱一定付得出去（指令已落库）；
- 付款失败有独立的补偿事务（`markFailed` 释放额度、车辆回退）；
- 付款结果未知（`UNKNOWN`）停在 PROCESSING，等银行回调或查单作业收敛。

> 这就是"**本地事务 + 最终一致**"在支付场景的标准解法。面试如果问"分布式事务怎么做"，不要一上来讲 Seata/TCC，先讲这个：**单库内也能靠"事务边界切分 + 状态机 + 幂等回调"解决跨系统一致性**。

**追问："那如果银行回调永远不来呢？"**
答：`PROCESSING` 是悬垂状态，需要查单作业（代码里还没实现，是已知缺口）。工程上必须有三道兜底：① 定时查单（T+0 每 5 分钟查一次未终态指令）；② 对账（银行流水 vs `payment_ref`）；③ 人工干预入口。**状态机里必须允许"悬垂态"存在，不能假设外部系统一定回调。**

### 4.3 行锁与并发

额度是并发风险最高的地方。`CreditLine` 的注释直接把话说死了：

> 本对象**禁止无锁的读-改-写**。调用方必须通过 `findByIdForUpdate` 以数据库行锁加载后再修改，否则并发垫款会导致额度超额——这是金融系统最不能犯的错。

```java
// JdbcCreditLineRepository.java:50
jdbc.query("SELECT * FROM credit_lines WHERE id = ? FOR UPDATE", MAPPER, id)
```

**追问："如果用乐观锁行不行？"**
答：可以，但重试成本高。额度是热点行，抢锁冲突率随并发线性上升，乐观锁会大量失败重试；悲观锁让请求排队，吞吐稳定但延迟上升。**金融账务选悲观锁**，因为它的目标是"绝不超额"而不是"最高吞吐"。

**追问："锁顺序有没有问题？"**（这题答好了很加分）
> 我检查过，**锁顺序不一致**：`stageAdvance` 是额度→车辆，`settle` 是车辆→额度，`markFailed` 又是额度→车辆。
>
> 严格的死锁需要成环。就目前业务，同一台车不可能同时处于 `CREATED`（可申请）和 `SOLD_PENDING`（可结清），状态机把交叉路径挡住了，所以实际上不会成环。
>
> 但这是**靠巧合安全**，不是靠设计安全。一旦新增"按经销商批量冻结额度"这类先锁额度再锁多台车的操作，环就形成了。正确做法是把锁顺序写进编码规范（统一"先额度后车辆"或反之），并在 Repository 层用注释强制。

### 4.4 Spring 事务的三个坑（都踩过）

**坑一：自调用绕过代理**
```java
@Autowired @Lazy private AdvanceApplicationService self;   // 注入自己
...
self.stageAdvance(...)     // 走代理，事务生效
// this.stageAdvance(...)  // 不走代理，@Transactional 完全失效
```
`applyAdvance` 故意不加 `@Transactional`，因为它需要"先提交 PENDING、再单独提交后续步骤"。如果直接 `this.` 调用，所有子步骤会被并进一个大事务，三段式设计立刻失效。

> 面试官问"@Transactional 什么时候失效"：① 自调用；② 方法非 public；③ 异常被 catch 没抛；④ 抛的是受检异常（默认只回滚 RuntimeException）；⑤ 类没被 Spring 管理。这个项目把①明确代码化并写了注释。

**坑二：外部 IO 在事务内**（见 4.2）

**坑三：批处理单事务全量**
```java
@Transactional
public Map<String, Object> runDailyInterest(LocalDate bizDate) {
    for (VehicleUnit unit : units) {          // 全表
        while (cursor.isBefore(bizDate)) {     // 补算 N 天
            interestLedgerRepository.saveIfAbsent(entry);
            unit.accrueInterest(daily, cursor);
        }
        vehicleUnitRepository.save(unit);
    }
}
```
1 万台车 × 补算 30 天 = 30 万行插入在一个事务里。问题是回滚段膨胀、锁持有时间长、任何一台失败全部回滚（重跑成本 = 全量重来）。

**改进方案**（面试时说这个，显示你有生产意识）：按 500 台分片，每片一个事务，`batch_runs` 里记 `last_processed_vin` 做断点续跑；或者直接改成集合式 SQL（见 5.6）。

## 五、已知缺陷（面试的核心差异化）

> 这一节是这份文档最有价值的部分。**能自己指出系统的问题，比背出它的优点更能证明你真的读过代码。**
> 项目里已经有一份 ADR-010 做了类似的事（真实事故复盘），你可以顺着它的风格讲。

### 5.1 【真实事故】同一台车 33 毫秒内被重复垫款 4 次

`ADR-010` 记录了实测复现的资损级缺陷：

```
audit_events: 12:24:42.443  COLA017481  reserved=1665000
              12:24:42.460  COLB017481  reserved=1665000
              12:24:42.476  COLA017481  reserved=1665000     ← 重复
              12:24:42.489  COLB017481  reserved=1665000     ← 重复
```

结果：两台车占了 4 份额度（666 万），真实债务只有 333 万。**四道防线全部失守：**

| 防线 | 为什么没拦住 |
|---|---|
| 应用层校验 | `stageAdvance` 只校验车辆状态是 `FINANCED`，**从不查"该 VIN 是否已有在途垫款"**；而申请阶段车辆状态不变，第二次提交照样通过 |
| 幂等键 | key 由调用方生成，四笔四个不同 UUID。**幂等键防网络重试，不防业务重复** |
| 数据库唯一约束 | `advances` 表对 `vin` 只有普通索引，没有唯一约束 |
| `uk_po_vin_active` | 它在 `vehicle_units` 上、且条件是 `purchase_order_id IS NOT NULL`——管的是"一车不能挂两个采购单"，而这四笔的 `purchase_order_id` 全是 NULL |

**修复**（`V14__advance_vin_unique_and_redeem.sql`）：
```sql
CREATE UNIQUE INDEX uk_adv_vin_active ON advances (vin)
  WHERE status IN ('PENDING','PROCESSING','PAID');
```

**这个故事怎么讲（建议原话）：**
> 这个系统上线前我做过一次数据核查，发现有两台车各有两笔金额完全相同的垫款。查审计表发现是 33 毫秒内连续提交了四次——不是业务上的分批放款，是重复提交。
>
> 我当时以为是幂等没做好，但深挖下去发现幂等键是好的，问题是**幂等键由前端生成，每次点击都是新 UUID**。这让我意识到一个更本质的区别：幂等键防的是"同一个请求被重发"，防不了"用户点了两次"。
>
> 真正的防线必须是业务唯一性，而且必须落在数据库。所以我加了一个部分唯一索引，条件只覆盖 PENDING/PROCESSING/PAID 三种占名额的状态——因为同一台车合法地可以有多条历史垫款（撤销后重提、还清后再借），只有"在途"的那一笔要求唯一。
>
> 这件事让我改了一个认知：**应用层校验是给人看的错误提示，数据库约束才是给系统看的真相。**

### 5.2 版本号是假的乐观锁

```java
// JdbcVehicleUnitRepository.java:238
"UPDATE vehicle_units SET ..., version=version+1, updated_at=now() WHERE vin=?"
//                                                          ↑ 没有 AND version=?
```
`version` 只递增、从不参与条件判断。所以**冲突不会失败，只会静默覆盖**——这不叫乐观锁，叫审计字段。

实际并发保护全靠 `SELECT ... FOR UPDATE`，而批处理里的 `runAgingAdvance` / `runSettlementScan` 用的是无锁 `findByStatus` 再逐条 `save`，两个实例并发跑会互相覆盖（库龄天数回退）。

**正确写法：**
```sql
UPDATE vehicle_units SET ..., version = version + 1
WHERE vin = ? AND version = ?      -- 期望版本
-- 检查 affectedRows == 1，否则抛并发冲突
```

### 5.3 批处理的幂等是 check-then-act，不是原子抢占

```java
if (supportRepository.batchSucceeded("DAILY_INTEREST", bizDate)) return skipped;  // 读
supportRepository.markBatchRunning(...);   // 写：ON CONFLICT DO UPDATE，不报错
```
`markBatchRunning` 用的是 `ON CONFLICT DO UPDATE SET status='RUNNING'`，**第二个线程不会失败，会继续往下跑**。

后果：`interest_ledger` 有唯一约束，流水只有一条（这层是对的）；但紧接着 `unit.accrueInterest(daily, cursor)` 是**无条件累加**，`vehicle_units.accrued_interest` 会翻倍。

**结果：系统里利息有两个真相源，而且会漂移。** 结清时用 `sumInterestByVin`（流水汇总）算应收，所以钱不会错；但 `accrued_interest` 字段显示的数是错的。

**修法：**
```java
boolean inserted = interestLedgerRepository.saveIfAbsent(entry);  // 返回影响行数
if (inserted) { unit.accrueInterest(daily, cursor); }             // 只有插成功才累加
```
并让 `markBatchRunning` 返回"是否抢到"：`INSERT ... ON CONFLICT DO NOTHING RETURNING id`，抢不到直接退出。

> 面试价值：这题能同时讲**幂等分层**（数据层唯一约束 vs 状态层抢占）、**真相源单一性**、**缓存字段与账本的一致性**。

### 5.4 幂等的 check-then-insert 不是原子的

```java
var existing = advanceRepository.findByIdempotencyKey(key);
if (existing.isPresent()) return replay;
... advanceRepository.save(advance);   // 并发下第二个请求撞唯一约束
```
两个并发同 key 请求都能通过检查，第二个插入撞 `idempotency_key` 唯一约束 → `DataIntegrityViolationException` → 全局兜底成 `SYS_001` 500。**语义上应该是"返回首次结果"，实际返回 500。**

**修法**：捕获唯一冲突后重新查询并返回首次结果，或用 `INSERT ... ON CONFLICT (idempotency_key) DO NOTHING RETURNING *`，返回空就说明是重放。

### 5.5 "部分成功"与单一事务的语义冲突

`ingestVehicles` 注释写"部分成功语义（一台脏数据不阻塞整批）"，但整个方法是一个 `@Transactional`，catch 的只有 `BusinessException`。

如果某台车的 `save` 抛 `DataIntegrityViolation`（比如并发同 VIN），**PostgreSQL 会把整个事务标记为 aborted**，后续所有语句全部失败，最终整批回滚——"部分成功"的承诺在 DB 异常下不成立。

严格说这不算 bug（业务校验失败确实不影响其他车），但**语义边界没写清**。正确表述应该是："校验失败逐台跳过，持久化异常整批回滚"，并分开两个事务层。

### 5.6 批处理用应用层循环做集合运算

```java
for (VehicleUnit unit : vehicleUnitRepository.findByStatus(IN_STOCK)) {   // 全表读进内存
    unit.setAgingDays((int) DAYS.between(unit.getStockInDate(), bizDate));
    vehicleUnitRepository.save(unit);                                       // 逐条 UPDATE
}
```
库龄推进完全不需要应用层参与：
```sql
UPDATE vehicle_units SET aging_days = ? - stock_in_date, updated_at = now()
WHERE status = 'IN_STOCK';
```
一条 SQL 顶一万次往返。**这是最容易被面试官抓的低级问题**，主动说出来并给出改法。

## 六、面试官会问的 20 个问题

**Q1：这个系统最难的地方是什么？**
> 不是业务复杂，是**一致性边界**。一笔垫款要同时改四张表（车辆状态、额度占用、垫款指令、审计），还要调一个不受控的外部支付系统。难在"钱已经出去了但数据库不知道"这种情况怎么防。我的解法是把付款切到事务外，用状态机 + 幂等回调收敛。

**Q2：额度会不会超额？怎么保证？**
> 三道：① 应用层 `occupy()` 检查 `used + frozen <= approvedLimit`；② 加载必须走 `SELECT FOR UPDATE`，禁止无锁读改写；③ 数据库 `CHECK` 约束兜底。第二道是关键，因为并发下"读-判断-写"之间会有窗口。

**Q3：为什么金额用 long 不用 BigDecimal？**
> 日元最小单位是 1，没有小数。用整数彻底消灭精度问题，且索引和求和更快。比率才用 BigDecimal，落金额前 `setScale(0, HALF_UP)` 量化。如果是有分币的货币，就用"分"作整数单位，原则一样：**金额永远不用浮点**。

**Q4：日终计息怎么保证不重复、不漏？**
> 两层幂等：`batch_runs(job_name, biz_date)` 挡重复执行，`interest_ledger(vin, biz_date)` 唯一约束 + `ON CONFLICT DO NOTHING` 挡重复写入。补算靠每台车的 `last_interest_date` 作为游标，从它的次日逐天补到今天。
>
> 这里有个细节：入库时把 `last_interest_date` 初始化为"入库日 − 1"，这样首轮补算恰好覆盖入库当天，实现"含当日计息"，既不多算一天也不少算一天。

**Q5：结清要做几件事？为什么必须一个事务？**
> 三件：核销本金、解除担保、回补额度。少做第二件，车在法律上还挂在金融公司名下，经销商卖不掉；少做第三件，循环授信断了，额度永久被占。三者任一失败都必须全部回滚，否则账实分叉。

**Q6：怎么防止同一台车重复融资？**
> 数据库的部分唯一索引 `uk_adv_vin_active`，只约束 PENDING/PROCESSING/PAID 三种"占名额"的状态。应用层也查一遍，但那是为了给用户友好提示，不是防线。**这条索引是踩过事故才加的**（讲 5.1 的故事）。

**Q7：`@Transactional` 什么时候会失效？**
> 五个：自调用、非 public、异常被吞、受检异常不回滚、类不在容器里。这个项目里我特意注入了 `@Lazy self` 来解决自调用——因为 `applyAdvance` 需要调用 `stageAdvance` 且要求后者独立提交，用 `this.` 调用会让事务注解完全失效。

**Q8：为什么不用 JPA？**
> 设计文档的原话是"简单实体用 JPA、复杂账务用 SQL"。这个原型统一用 JdbcTemplate，因为账务查询有大量聚合、行锁、`ON CONFLICT`，ORM 反而碍事。代价是手写 RowMapper，收益是 SQL 完全可控。生产版可以混合：CRUD 用 JPA，账务用原生 SQL。

**Q9：银行回调怎么鉴权？为什么不用 JWT？**
> 银行没有登录态，拿不到用户令牌。如果复用 JWT，任何登录用户都能把 PENDING 改成 PAID，等于虚构放款。所以这两个端点从 JWT 拦截器排除，改用 HMAC-SHA256 + 时间戳（±300 秒防重放），签名里包含单号、时间戳和流水号。比较用常量时间，防时序侧信道。

**Q10：职责分离（SOD）怎么落地的？**
> 两层。角色层：申请人、复核人、出纳是三个不相容岗位，出纳接口有 `@RequireAdmin`。但角色挡不住"一人多岗"，所以还有第二层——**自然人级校验**：复核人不能等于申请人，支付人不能等于申请人也不能等于复核人（`RoleSeparationPolicy.assertNoSelfApproval`）。责任链三环（applicant / reviewer / disburser）都落在垫款单上。

**Q11：如果 QPS 上来，瓶颈在哪？**
> ① 额度行锁——同一经销商的所有垫款串行化，这是设计上的取舍，要扩容只能按经销商分片；② 批处理全表扫——库龄、计息都是应用层循环，应该改集合 SQL + 分片；③ 单库单表——`interest_ledger` 每天每车一行，一年 365 万行/万台，已设计按季度归档。**真正的瓶颈是①，因为它是强一致的代价，不能靠加机器解决。**

**Q12：这个项目你花了多久？哪部分最花时间？**
> （诚实版）业务建模最花时间，不是写代码。11 个环节里有 3 个是靠"排查缺漏"补出来的——比如库龄递减、违约处置、额度年审，最初的设计只有 8 环节。补的过程不是加代码，是回头改状态机、改表、改已有用例的边界。

**Q13：为什么拆成微服务？拆的标准是什么？**
> 标准只有一条：**这块逻辑的价值是否依赖本地事务**。垫款/结清/计息要在同一事务里原子成立，留在单体；auth/credit/bank/risk/loan/collateral-reg/release/recon 是读多写少或跨机构协同的上下文，拆成独立进程。所以我不是"全拆"，而是**把该隔离的隔离，该守的守住**。网关切流 + 走网关的 290 断言冒烟验证了拆分的正确性。

**Q14：拆了服务，为什么还共用一个库？这不矛盾吗？**
> 第一版刻意不拆库。服务先拆、数据后拆，避免一上来就撞跨库 join 和分布式一致性。**代价要说清楚**：现在跨服务的一致性本质是"共享库 + 本地事务"兜住的，不是真正的服务自治。下一步是按上下文分库，届时 core 与 credit 之间的额度读写要改成消息或显式接口。这是一个明确的演进方向，不是我声称已经做到服务自治。

**Q15：拆完服务，token 怎么在各服务间通用？网关验签吗？**
> JWT 密钥全服务一致，auth 签发的 token 各服务都能验。网关本阶段**不验签**，只透传 `X-Request-Id` 做链路追踪；鉴权下沉在各服务。理由是零信任——服务脱离网关直连时也不裸奔。等端点全迁完再考虑把验签上收到网关。

**Q16：微服务改造踩过最隐蔽的坑是什么？**
> 前端页面回归。服务拆完、Controller 摘除后，走网关的冒烟全绿（当时 182 条），但页面打开后功能全废——因为前端 `API_BASE` 还写死 8080，而网关不托管静态资源。**冒烟测试只打 API，没打页面这条路径**，所以全绿不代表用户路径全绿。修法是页面和 API 统一走网关、网关加静态资源路由 + CORS，后来补了 Playwright 浏览器测试。这件事让我记住：**端到端测试的"端"要定义清楚，你没测的那条端就是盲区。**

**Q17：事件重复投递或丢失，怎么保证？**
> 三层。发布端用 `INSERT … WHERE NOT EXISTS` 按 `(event_type, aggregate_key)` 去重，键用 `advanceId` / `paymentRef` 这种「这一次发生」的主键；消费端框架层 `(event_id, consumer)` 挡重复投递，业务层再按 `payment_ref` / `loan_no` 做 L2 幂等；失败重试 3 次进 DEAD 并推进游标，坏事件不阻塞后续。丢失这一侧靠「业务与事件同事务」：事件和业务数据一起提交，业务回滚事件必不在。

**Q18：多实例部署，定时任务和事件消费怎么不重复？**
> 事件消费：V83 给 `consumer_offsets` 加 `lease_owner/lease_until`，每轮原子认领/续租 2 分钟，没抢到就跳过，停机释放租约；语义是至少一次，重复靠业务幂等兜底。定时任务：`floorplan.jobs.enabled` 默认关，每个作业先取 Redis 分布式锁 `lock:job:<name>:<bizDate>`，抢不到跳过，锁服务异常 fail-closed 不执行。生产启动检查强制 `jobs=true` + `lock.provider=redis`。

**Q19：JWT 怎么做到即时失效？**
> V82 给 `users.token_version`，登录时把 `ver` 写进令牌；每次请求回查签名/过期 → 用户启用 → 版本一致 → 从 `user_roles` 现算角色和权限。退出登录把版本 +1，旧令牌立即 401；删角色后旧令牌立即 403。代价是每请求一次主键查询，身份可以短 TTL 缓存，但账本字段绝不缓存。

**Q20：读接口的权限矩阵怎么落的？**
> 13 个细粒度读点 + 14 个角色 `READ_MATRIX`，写点和读点物理分离；21 个 Controller 的 GET 全量注解，唯一豁免是预签名下载 URL。每个请求回查权限，令牌里的读点只作展示。实施后按真实页面和工作流补了 3 处最小授权——这是浏览器测试和 USED 冒烟抓出来的：矩阵表看起来对，但 operator 查经销商、采购岗查 LTV 全 403。

## 九、"你遇到最有挑战的问题是什么？"

> 这是行为面试的核心题。它考的不是"哪个功能难写"，而是**你遇到问题时的思考路径**。
> 好答案的结构：**一个具体的坑 → 认知反转 → 四层排查 → 业务后果 → 方法论沉淀**。

### 9.1 首选答案：重复垫款（90 秒，可直接背）

> 最有挑战的不是某个功能难写，而是**一个我以为已经防住的问题，实际上四道防线全是漏的**。
>
> 我在做数据自检时跑了一句 SQL，看每台车有几笔垫款，发现有两台车各有两笔，金额一模一样。第一反应是业务上允许一车多债——分批付尾款嘛。但我去看审计表的时间戳，四笔集中在 **33 毫秒**内，COLA、COLB、COLA、COLB 顺序提交。分批放款不可能 33 毫秒完成四次，这是重复提交。
>
> 然后我排查为什么没拦住，发现四道防线全部失守：
>
> 第一道，申请垫款时我只校验了车辆状态，**没校验这台车是不是已经有在途垫款**。而申请阶段车辆状态根本不变，所以第二次提交照样通过。
>
> 第二道，我做了幂等键，但幂等键是前端生成的 UUID，每点一次都是新的。这让我意识到一个本质区别：**幂等键防的是同一个请求被重发，防不了用户点两次**。
>
> 第三道，数据库对 VIN 没有唯一约束。
>
> 第四道，我以为有个 VIN 唯一索引能兜住，结果它在另一张表上，而且条件是采购订单不为空——恰好这四笔都是直接建账，订单是空的。
>
> 结果是两台车占了四份额度，666 万，真实债务只有 333 万。如果这四笔都放款成功，就是直接资损。
>
> 修复本身不复杂，加一个部分唯一索引，只约束在途的三种状态。但这件事改了我两个认知：**第一，应用层校验是给人看的错误提示，数据库约束才是给系统看的真相。第二，同一个业务事实如果有两个真相源，一定会漂移。** 后来我把利息也改成以流水汇总为准，不重算，就是这个原则。

### 9.2 这个答案为什么有效

| 要素 | 具体体现 |
|---|---|
| 开场有钩子 | "我以为防住了，实际四道全漏" —— 直接制造张力 |
| 有认知反转 | 以为是"分批放款"，查时间戳发现是"重复提交" |
| 有可验证的数据 | 33 毫秒、4 笔、666 万 / 333 万 |
| 排查有层次 | 应用层 → 幂等层 → DB 约束 → 索引语义，四层逐个排除 |
| 落到业务后果 | 不是"数据不对"，是"直接资损" |
| 有方法论沉淀 | 两条原则，可迁移到其他系统 |

**为什么选这个故事而不是"付款事务拆分"**：后者技术含量更高，但没有"我错了 → 我发现"的过程。面试官问"最有挑战"，本质是在探测**你踩坑后的反应**，不是你的知识面。

### 9.3 必被追问的四个问题

**Q：为什么不直接 `UNIQUE(vin)`？**
> 因为一台车合法地可以有多条历史垫款——撤销后重提、还清后再借。只有"在途"那一笔要求唯一，所以用**部分唯一索引**，`WHERE status IN ('PENDING','PROCESSING','PAID')`。这个 WHERE 条件必须和 Java 枚举里的判定严格一致，否则防线会静默失效——索引建了，但漏掉一个状态就等于没建。

**Q：库里已经有重复数据了，加索引不会失败吗？**
> 会。所以迁移脚本里顺序不能反：先清理存量（保留最早一条，其余置 `VOIDED` 并**释放它们占用的额度**），再建索引。释放额度这步最容易漏——只改状态不减 `used_amount`，额度就被永久占死了。

**Q：幂等键既然没用，为什么还留着？**
> 它防的是另一个场景：请求超时被重发。这个场景真实存在，而且它能让重试返回首次结果而不是报错。**它和业务唯一性解决的是不同层的问题**，一个防网络层重复，一个防业务层重复，不能互相替代。

**Q：为什么测试没发现？**（这题必须诚实）
> 我的端到端脚本是串行跑的。串行下第二次申请会被车辆状态挡住，所以测不出来。这个 bug 只在"连续快速提交"时暴露。**说明我的测试缺了并发维度**——它验证了链路通不通，没验证并发下不变量还成不成立。
>
> 如果补，我会写一个并发用例：10 个线程同时给同一台车申请垫款，断言成功 1 笔、其余全部被拒，且 `used_amount` 只增加一份。

### 9.4 备选答案（按面试官类型切换）

**如果对方是架构 / 技术专家岗 —— 讲付款事务边界：**
> 最难的是"钱已经出去了，但数据库不知道"。最初我把付款和记账放在一个事务里，后来意识到银行接口一旦超时，事务回滚了钱却出账了，系统里查不到这笔垫款，成了账外资产。所以我把付款拆到事务外：先提交指令并占额度，再调网关，结果由银行回调收敛。代价是要接受一个 `PROCESSING` 的中间态，并且必须有查单兜底。

**如果对方偏业务 / 产品背景 —— 讲状态机三次重构：**
> 最难的是把"钱付了没有"这件事表达出来。最初建账直接就是"已垫款"，结果待放款工作台把没验车的车也列给了出纳，可能对一台没确权的车付款。后来拆成建账、待垫款、已放款三个状态。再后来又发现"已结清"不能复用——车卖了叫结清，车还在库里叫赎回，资金动作一样但去向相反，合并了就判断不出这台车还能不能再借。

### 9.5 三个坑（别踩）

1. **不要说成"生产事故"**。这是你自己的项目，说"数据自检时发现"更稳。说成线上事故，面试官追问"多少用户受影响、怎么回滚的、谁背的锅"，你答不上来就崩了。
2. **不要说"这是 AI 帮我发现的"**。但也别撒谎——如果被问"你怎么想到查这个"，答：**"我在写架构决策记录时要求自己对每条不变量给出一条可验证的 SQL，这条就是这么查出来的。"** 这是真话，而且展示了工程习惯。
3. **准备好被追问任意一段代码**。这个项目注释极其详尽，面试官可能随手挑一段问"这里为什么这么设计"。建议面试前挑三个模块（垫款、结清、计息）做脱稿讲解练习，不看代码能讲 3 分钟。

### 9.6 更推荐的开场：从"对拍"讲，不从"设计"讲

> 以下这个版本把叙事起点从"我设计了四道防线"换成"对拍发现账对不上"，可信度高一个档次——因为面试官听过太多"我设计了 X"，很少听到"我的数据错了，我这样定位的"。

> 最有挑战的不是写功能，是**账对不上，而且一开始不知道该信谁**。
>
> 我做了两套对拍：迁移期是 Rails 和 Java 双跑，日终逐个口径比；运行期是系统内部跨表对拍，比如额度占用和垫款明细、应计利息和计息流水。
>
> 第一条差异是额度：某经销商明明还了 40 万，可用额度没变。我第一反应是新系统算错了，一查发现两边都对——**部分还款时我没释放额度，结清时按"剩余本金"释放**，中间那 40 万就永久占死了。这不是算法错，是两个环节对"占用"的口径不一致。
>
> 第二条更危险：应计利息比流水合计多。差额恰好是上一个季度归档掉的利息——**归档作业把主表删了，结清却还在读主表**。同一笔事实两个读法，一个会消失。这条是必现的，跨季的车 100% 中。
>
> 从那以后我的判断顺序变了：先看差异的**形态**——是整笔偏移、整数天、还是某个区间；形态能反推是哪一环写坏的，比从头读代码快得多。

## 十、从对拍开始：数据不一致怎么定位到环节

> 这一节回答一个具体问题：**对拍报了差异，怎么知道是哪一步写坏的。**
> 结论先说：差异的**形态**（方向 + 量级 + 命中的车辆集合）几乎唯一地指向某个环节。会读形态，比会读代码有用。

### 10.1 两套对拍，两种不一致

| 场景 | 比什么 | 出处 | 能发现什么 |
|---|---|---|---|
| **迁移期双跑**（Rails vs Java） | 行数、单据、金额合计、状态分布 | 迁移切换 Runbook §5 T2、§7 影子对账 | 迁移映射错误：金额单位、状态枚举、日期口径 |
| **运行期对拍**（系统内部跨表） | 同一事实的不同表达是否相等 | 本文 10.3 的规则表 | 写入路径错误：漏写、重复写、口径不一致 |

两套的价值不同：迁移对拍是**一次性**的（切完就没了），运行对拍是**每天**都要跑的。项目里 Runbook 写了"影子对账每日、差异不得连续出现"，但**没有落地代码**——这是可以主动讲的一个缺口。

### 10.2 对拍必须做四层，只做金额合计会漏

| 层级 | 判据 | 能发现 | 发现不了 |
|---|---|---|---|
| L1 行数 | 表行数、按状态分组计数 | 丢单、重复单 | 金额错 |
| L2 单据级 | 每台车一张"资金卡"逐字段比 | 错位（A 车多记、B 车少记） | 规则性偏差 |
| L3 金额合计 | 本金/利息/额度占用轧平 | 总额级资损 | **错位**：一多一少，合计仍平 |
| L4 不变量 | 跨表恒等式 + 业务唯一性 | 口径漂移、状态与金额矛盾 | 历史数据已污染的部分 |

**面试可以点一句**：迁移 Runbook 的 T2 只做到 L3（`diff_amount = 0`），这在"单车单笔"的数据上不够——两台车各错 40 万、方向相反，合计依然是 0。所以我在运行期补了 L4。

### 10.3 八条对拍规则（可直接落成 SQL）

记 `active` = `advances.status IN ('PENDING','PROCESSING','PAID')`。

| # | 不变量 | 现状 | 命中环节 |
|---|---|---|---|
| R1 | `credit_lines.used_amount = Σ advances.amount where active` | 部分还款+结清后**不成立** | 还款 / 额度释放 |
| R2 | `vehicle.principal_balance = advance.amount − Σ repayments.principal` | 成立 | — |
| R3 | `vehicle.accrued_interest = Σ interest_ledger.daily_interest` | 归档后**不成立** | 归档 / 计息 |
| R4 | 本期应收利息 = Σ 流水 `where biz_date >= 本次放款日` | **无法计算**（表无借据维度） | 计息 / 表设计 |
| R5 | `Σ repayments.interest = Σ interest_ledger.daily_interest` | 二次融资后**不成立** | 结清 / 计息 |
| R6 | 终态车（SETTLED/CLOSED）`principal_balance = 0` | 处置结案后**不成立** | 处置 |
| R7 | `batch_runs` 同一 (job, biz_date) 只有一条终态记录 | 失败时**无记录** | 批处理 |
| R8 | 同一 VIN 的 `active` 垫款 ≤ 1 笔 | 已由 `uk_adv_vin_active` 兜住 | 建账（已修） |

R2 成立这件事值得讲：**本金这条链是对的，错的全在"利息"和"额度"这两条链上**。因为本金只有一个写入口（结清/部分还款），而利息有两个真相源（流水 + 累加字段），额度也有两个（占用额 + 明细）。

### 10.4 差异形态 → 环节（核心判定表）

这张表是这一节的全部价值。**看到差异先对形态，形态对上就不用读代码了。**

| 差异形态（对拍看到什么） | 判别特征 | 反推环节 | 为什么排除别处 |
|---|---|---|---|
| 应计利息 **>** 流水合计，差额 = 某季度之前的利息 | 只影响 `biz_date < 本季首日` 的车；差异额随季度切换跳变 | **归档**：删主表，结清读主表 | 不是并发：串行跑也必现 |
| 应计利息 **>** 流水，差额 = 整数天 × 单车日息 | 集中在 `batch_runs` 有两条同日记录的车 | **计息**：流水唯一键挡住了重复入账，累加字段没跟着流水走 | 不是归档：差额不是整段区间 |
| 已收利息 **>** 流水合计，差额 = 上一周期利息 | 该 VIN 有 ≥2 条 `REDEEMED/PAID` 垫款 | **结清**：按 VIN 汇总，跨周期串账 | 不是计息：流水本身没多 |
| 额度占用 **>** `Σ active`，差额 = 部分还款本金 | 该车有过 `repayment_type='PARTIAL'` | **还款**：部分还款不释放，结清按余额释放 | 不是建账：占用额与放款额一致 |
| 同车多笔 `active` 垫款，金额相同，时间戳同毫秒 | 集中在并发压测或连点场景 | **建账**：状态未变，唯一索引条件不覆盖 | 不是幂等键：每次 UUID 都是新的 |
| 银行有出账，系统停在 `PROCESSING` | 长期不动，`payment_ref` 为空 | **放款**：未知态没有查单作业收敛 | 不是回调丢失：回调失败也有日志 |
| 终态车仍有本金/占用 | `status='CLOSED'` 且 `principal_balance > 0` | **处置**：结案只改状态 | 不是结清：结清会清零 |
| **全表同向偏移**（×100、差 1 天、状态全错一档） | 所有车一致，与业务无关 | **迁移映射**：单位/枚举/时区 | 不是代码 bug：代码 bug 不会这么整齐 |

### 10.5 四条差异的完整复盘

#### 差异一：归档把"应收利息"删掉了一半（必现，方向是少收）

- **现象**：跨季在贷车辆的 `accrued_interest` 比流水合计大，差额恰好等于已归档区间的利息。
- **链路**：`runArchive` 每季度首日把 `biz_date < 本季首日` 的流水复制到 `interest_ledger_archive`，然后 **`DELETE` 主表**（`JdbcInterestLedgerRepository#archiveBefore`）。而 `settle` / `redeem` / `payoff` / 处置应收，全部走 `sumInterestByVin`，**只 `SUM` 主表**。
- **后果**：库龄跨季的车，结清时应收利息少算一整段。客户少付、公司少收，且是**确定性**的，不是偶发。
- **修复方向**：应收口径改成 `主表 + 归档表` 的 `UNION ALL` 汇总；或流水永不被物理删除（归档只做副本，不做 `DELETE`）。**更根本的是 R4**：流水根本没有借据维度，一张表同时服务"累计账"和"本期应收"，删一行就同时破坏两个口径。
- **为什么这是最好的面试例子**：可复现、可量化、方向明确，而且暴露的是**设计层**问题（一张表两个用途），不是手误。

#### 差异二：部分还款不释放，结清按余额释放（额度永久泄漏）

- **现象**：额度占用比 `Σ active` 垫款金额大，差额 = 该车部分还款本金合计。
- **链路**：`partialRepay` 明确写了"不回补额度"（注释理由：车还在库，占用关系未解除）；但 `settle` 释放的是 `principal`（**剩余**本金），不是垫款原额。
- **后果**：还 40 万，结清后额度仍被占 40 万。循环授信的核心卖点是"还了就能再借"，这条链路直接把它破坏掉——额度越用越少，最后经销商"明明没欠钱却借不出来"。
- **口径之争**：两个环节单独看都自洽。部分还款时"占用=原额"是对的（债权未终止），结清时"释放=剩余"也是对的（只释放这一笔的剩余）。**错的是没有一处记录"已还本金也占着额度"这个临时状态**。要么部分还款时同步释放并调整占用基数，要么结清时按原额释放。
- **修复方向**：结清释放 `advance.amount`（`CreditLine.release` 本身有 `min(amount, usedAmount)` 保护，不会变负）。

#### 差异三：二次融资，利息跨周期串账（多收客户利息）

- **现象**：`Σ repayments.interest` 比 `Σ 流水` 大，差额 = 上一周期利息。
- **链路**：`interest_ledger` 唯一键是 `(vin, biz_date)`，**没有 `advance_id`**；`REDEEMED` 后同一台车可再次融资（`stageAdvance` 允许 `REDEEMED`），复用的是同一个 `vehicle_units` 行，`accrued_interest`、`last_interest_date` 都不重置；结清仍按 `vin` 汇总。
- **后果**：第二周期结清时，把第一周期的利息又算了一遍。客户被多收息是合规问题，比少收更难解释；同时 `settle` 是**精确比对**（`amount != expected` 直接抛 `REPAY_001`），客户按正确金额还款会被系统拒绝——差异从"报表问题"升级成"业务做不下去"。
- **修复方向**：流水加 `advance_id`，应收按借据汇总；`stageAdvance` 时重置利息累计与计息基准日。

#### 差异四：处置结案，本金与额度都不动（在贷余额永远不降）

- **现象**：`status = CLOSED` 的车 `principal_balance > 0`，额度仍被占。
- **链路**：`DisposalApplicationService#close` 只做三件事——算应收、`c.close(...)`、`unit.close()`。不核销本金、不关垫款、不释放额度。
- **后果**：不良率、在贷余额、额度可用额三个口径同时错。而且**对拍容易漏**：如果按"未结清车辆"汇总本金，这台车被过滤掉了，看起来是平的；只有按"本金 > 0"汇总才会暴露。**这说明对拍的口径本身也要被对拍。**
- **修复方向**：结案时核销本金（损失进 `loss_amount`）、垫款置终态、释放额度。

> 第五节讲的"同 VIN 四笔重复垫款"是第五条差异，形态是"整笔金额 × 笔数 + 同毫秒"，属于 L4 业务唯一性那一层，这里不重复。

### 10.6 对拍要工程化，不能是"我跑了个 SQL"

最小可用形态：一张 `recon_diffs` 表 + 一个日终作业 + 自动开工单。

```
recon_diffs(biz_date, rule_code, vin, expected, actual, diff_amount, severity, status, owner, created_at)
```

- 每条规则一个 `rule_code`，差异**逐车主键级**落表，不做汇总——汇总会掩盖错位（10.2 的教训）。
- `severity` 按差异方向定：**少收 / 额度虚占 = HIGH，多收 = CRITICAL**（合规）。
- 与 `work_orders` 打通：HIGH 以上自动建单，派给资金岗；这和项目里已有的 `risk_alerts → work_orders` 是同一套机制，可复用。
- 差异**连续出现**要升级：Runbook 里写了"不一致不得连续出现"，落到代码就是"同一 `rule_code + vin` 连续 3 天未闭环 → 升级"。

这一段的作用是告诉面试官：**我不是发现了一个 bug，我是建了一套能持续发现 bug 的东西。**

### 10.7 被追问时的三个要点

1. **"为什么不让对拍直接修数据？"** —— 对拍只做裁判，不做出纳。自动修数会掩盖上游缺陷，且无法审计。修数必须走业务补偿接口（有单据、有审计、可回放）。
2. **"差异怎么定优先级？"** —— 按"是否影响资金 + 方向"。少收/虚占是 HIGH，多收是 CRITICAL（合规风险），纯状态不一致是 MEDIUM。金额不是唯一标准：差 1 日元的形态如果是"每台车都差"，说明是系统性口径错误，比单台差 40 万更严重。
3. **"这套东西在这个项目里真的跑了吗？"** —— 诚实回答：**8 条规则已经落成 `ReconRuleCode` + 服务端点，不再是"跑了个 SQL"**；但**对拍日终触发尚未接入统一调度**（`RECON_FILE_GEN` 没有 ApplicationService，不造空壳），目前仍需手动/独立触发，差异的工单化也没接。下一步是把对拍触发接进 `ScheduledCoreJobs` 并用工单体系闭环。

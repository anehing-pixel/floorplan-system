## 1. 结论先行

### 1.1 一句话结论

**这不是"给系统加几个二手车字段"，而是一次业务主体、风控范式与外部协同拓扑的整体切换。**

现有系统是按「日本新车渠道 · 品牌授权经销商 · 厂家发票定价 · 厂家回购兜底 · 无第三方实体监管」建成的。目标业务是「独立第三方金融 / 信贩公司 · 中古车销售业者 · 拍卖场收车 · 车辆残值定价 · 车检证质押 + 监管仓实控 · 拍卖再变现」。两者在**金额基准、增信来源、担保标的、物理监管、外部对手方**五条链上全部相反，因此约 60% 的业务规则层需要重定或重建，而账务骨架（额度占用/冻结/回补、计息幂等、借据 DPD、状态机 CAS、审计留痕）约 70% 可以直接复用。

### 1.2 最危险的三处认知反转（先看这三条）

| # | 现有系统的明确结论 | 目标业务必须反转成 | 反转的影响面 |
|---|---|---|---|
| **A** | `业务流程文档 §6:201`、`外部集成接口文档:9-12`、`V24__release_custodian_scope.sql:9-18`、`CustodianType.java:6-9` 明文：第三方监管仓 / 驻场监管 / 扣押钥匙 / GPS / 封签是「中国第三方监管公司对二手车、高风险车商的做法，**不适用于日本新车渠道**」，已主动移除相关字段与流程 | **监管仓 WMS + 实车控制是目标业务的核心风控手段**，车辆不放在车商自有库 | 数据库注释、`CustodianType.isPrimary()`、`ADR-业务口径总定源 §2`、`ManualReleaseChannel`、整个放车回执权威性，全部要重定 |

### 1.3 规模判断

原始需求文档自己已经预警过：`docs/日本汽车库存融资业务与系统需求说明.html:252` —

> 「新车渠道还是二手车渠道？新车由厂家金融主导、流程标准化程度高；二手车高度依赖批发拍卖、车况非标、估值难，**两套系统的复杂度差一个量级**。」

实查印证：现有数据库层其实**已经预留了部分二手车钩子**（`vehicle_units.vehicle_type/purchase_channel/mileage`、`suppliers.supplier_type` 含 `AUCTION`/`USED_WHOLESALER`、`residual_value_*` 三列、`ADR007` 定义了「B. 二手库存采购」场景），但**规则层几乎没有一条按车辆类型分叉**，且顶层口径已把二手车监管方式主动判为「不适用」。所以工作量主要在：

1. 一次**口径反转 + 新一轮业务定源**（治理层面，非代码）；
2. **估值 / 车况 / 车检证 / 车商资质**四组新领域模型与数据表；
3. **外部集成层从 0 到 1**（当前 `external-api` 全库 0 处 Java，`integration_partners/nonces/calls` 三表均未建）；
4. **放车/解押闭环从"内部状态机"到"跨机构异步协同"**，并接通回款链路（当前 `bank-service` 三个存根，`ReleaseOrchestrator` 明确 `availableAfter=before` 未真实回补）。

## 2. 目标业务模型

### 2.1 主体与业务边界

| 维度 | 定义 |
|---|---|
| 资金方 / 系统业主 | 日本**独立第三方金融 / 信贩公司**。非厂家金融、非银行系，与整车厂无资本与回购关系 |
| 借款人（B 端） | **中古车销售业者（二手车车商，法人）**，非品牌授权新车经销商。需持古物商许可、通常为拍卖市场会员 |
| 融资标的 | 车商为补充周转而购入的**二手乘用车 / 商用车库存**，逐台（by VIN / 車台番号）建账 |
| 不做的业务 | **新车垫资**（厂家直供、厂家发票、厂家回购、厂家贴息）、个人消费者分期、多品牌厂家金融、其他产品线 |
| 授信形态 | B2B **循环授信**：逐台放款占用额度 → 该台卖车还款 → 解押 + 放车 → 额度回补 → 可再次收车 |
| 资金流向 | 金融公司 → 拍卖场 / 上游卖方（代付落札款，不经车商账户）；车商卖车回款 → 金融公司指定受领账户 |
| 核心风控三支柱 | ① **B 端车商资质** ② **车辆残值（评估价 / 相場）** ③ **车检证质押**（+ 监管仓实车控制） |
| 外部协同方 | **USS / TAA 等拍卖场系统**、**监管仓 WMS**、（待定）登记事务代办 / 征信 / 银企 |

> **重要边界澄清**：用户表述「不会碰新车」按「目标态以二手车为唯一主业务」理解。现有新车链路属历史错配资产，处理策略见 §4.4，需业务书面确认。

### 2.2 三流模型（资金流 / 货物流 / 凭证流）

```
【收车阶段】
拍卖场(USS/TAA)  ──落札结果/出品票/評価点──►  本系统（建账 + 估值 + 准入）
本系统          ──落札款代付（DIRECT_PAY）──►  拍卖场结算账户
车商            ──申请垫资 + 资质/保证金────►  本系统
拍卖场/运输     ──实车交付────────────────►  监管仓 WMS（入库确认、库位、车况复核）
车商/代办       ──車検証、移転登録文书─────►  金融公司 / 凭证保管方（质押 HELD）
本系统          ──在库对账（VIN × 車検証 × 库位）──◄── 监管仓 WMS

【在库阶段】
本系统：逐台计息（本金 = 实际垫款）、库龄/估值衰减监控、定期盘点与 WMS 库存快照对账、
        残值重估 → LTV 突破 → 追加还款/追加担保

【卖车还款 + 放车解押阶段】（核心闭环，见 §2.5 / §6）
车商卖车（零售 / 批发转售 / 再出场拍卖）
   → 回款进入金融公司指定受领账户
   → 银行流水采集 + 按 VIN 匹配（金额 ≠ 估值，按债权应收匹配）
   → 冲抵（费用/罚息 → 利息 → 本金）
   → 担保实体权利消灭：生成抹消/移転登録待办 + 車検証解押
   → 【资金闸门】未足额到账不得下发放车指令
   → 下发「放车 + 放证」指令给监管仓 WMS（按项指定接收方）
   → WMS 实车出库 + 車検証交还 → 回传权威回执（partner_code 签名）
   → 台账更新：车辆 SETTLED / 质押 RELEASED / 库存 OUT / 额度回补 / 审计留痕
```

三流必须**逐台可勾稽**：一台车 = 一笔垫款 = 一份車検証质押 = 一个 WMS 库位 = 一条出库指令 = 一条回执。

### 2.3 三大风控支柱的目标定义

| 支柱 | 目标态要求 | 现有系统对应能力 |
|---|---|---|
| **① B 端车商资质** | 古物商许可号 / 有效期 / 管辖公安委员会；拍卖市场会员资格与 ID；资本金、年销售额、展位容量、库存周转；经营年限、既往违约；反社会势力排除与 AML 校验；分级准入与差异化 LTV / 利率 | `dealers` 仅 `status / risk_grade / business_years / 联系方式`；评级为 A–D 人工打标（`V3__rating_config.sql`）；**无任何资质字段** |
| **② 车辆残值** | 双源交叉：**落札价（成交事实）** vs **评估价 / 相場（市场公允）**，取审慎值作为放款基准；按车龄 / 里程 / 修復歴 / 評価点 / 車検残存 / 车型热度分档 LTV；在库定期重估，残值跌破即触发追加还款 | 唯一公式 `发票金额 × 0.90`（`AdvanceApplicationService.java:172-177`）；`residual_value_estimated` 三列仅用于预警且**无 Java 写入方**（`V11:287-294`）；全库无「相場 / 查定 / 修復歴 / 評価点」 |
| **③ 车检证质押** | 車検証作为独立质押对象建模：証書番号 / 登録番号 / 車台番号 / 所有者 / 使用者 / 車検満了日 / 抵当権 / 前手权利瑕疵 / 保管者；状态 `HELD → PLEDGED → RELEASED`，与实车、登记文书联动；放证是放车指令的独立释放项 | 「車検証」全仓只作为**附件扫描件 / 事件类型**出现（`贷后监管设计.md:322,332,428,503`），无质押对象、无状态机、无移交返还；`release_orders.certificate_no` 注释写的是「车辆合格证」且明确「不是法务局登记证明书」（`V19:52,90`） |

### 2.5 放车 / 解押的定义与四条红线

**定义**：车商卖车并还清该台垫款后，金融公司解除该车担保，并**通知拍卖场 / 监管仓把实车与車検証交给买方（或车商指定接收方）**的动作。它是「债权消灭 → 物权凭证释放 → 实车出库」三件事的合流，不是一条通知消息。

| # | 红线 | 依据 / 现有落差 |
|---|---|---|
| **L1** | **资金未足额到账并匹配到该 VIN，不得下发放车指令** | `业务流程文档:89` 已定；目标态必须硬门禁。现有回款→解押→回补链路仍是存根（`PROGRESS §8.1 D1`） |
| **L2** | **回执必须由接收方（WMS / 拍卖场）确认，不得由我方代填、不得由车商自证** | `放车放证设计.md:707,726` 原始要求「回执是交付证据，应由接收方确认」；但 V24 因「日本无第三方监管」折中为 `INTERNAL_WITNESS` 我方见证代录（`ReleaseApplicationService.java:57`）。目标态**必须撤销该折中**，默认 `PARTNER_RECEIPT` + `partner_code` 签名 |
| **L3** | **放车与放证是两条独立释放线，允许部分释放，未放证不得视为结清** | `放车放证设计.md:416`「只放了车没放证 = 车交付了但物权凭证未转移，是真实的法律状态差异」；现有 `ReleaseItemType` 仅 `VEHICLE/CERTIFICATE/KEY`，无「車検証 / 移転登録文书 / 出库单」，且 `saveReceipt` 只写 7 列、`exception_type` 从不写入 |
| **L4** | **顺序固定：冲抵 → 解押（实体权利消灭 + 登记抹消待办）→ 下发指令 → 接收方回执 → 台账更新（SETTLED + 库存 OUT + 额度回补 + 审计）** | `放车放证设计.md:236-237` 明确「先冲抵 → 再解押 → 最后才回补额度，否则变成钱收了、额度放了、车还押着」；但现有 `ReleaseStatus` 是 `RELEASED → LIEN_DISCHARGED`（放车后才解押），与 `ADR-业务口径总定源:196` Q11「先解押 → 发指令」**不一致，须先统一口径** |

### 4.3 改造性质判定

**不能按「补几个 adapter」排期。** 理由：

1. `ReleaseChannel` 接口与 ADR009 五层边界是为「真有 partner 系统时」预留的正确接缝，**可复用**；但当前所有口径把第三方监管 / WMS / 拍卖场判为「不适用」并主动移除，因此第一步是**治理层的口径反转**，不是编码。
2. 金额基准从 `invoice_amount` 换成「评估价/落札价 × 分档 LTV」会穿透额度、借据本金、库龄递减、计息、对拍规则 R1–R8 的取数 SQL —— 属于**账务主干改造**，必须整体设计、分批迁移。
3. `ADR-业务口径总定源` 的「不新增待确认 / 不改 V1–V25 / 走配置覆盖」三条硬约束与本次改造直接冲突，需先出上位 ADR（§12.1）。

### 4.4 存量新车数据与系统边界策略（待定源）

用户表述「不会碰新车」按「目标态以二手车为唯一主业务」理解，但库里已有新车口径的存量数据与已落库迁移。三方案对比：

| 方案 | 做法 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| **A. 封存只读（推荐）** | 新开业务一律 `vehicle_type=USED` 且走新规则链；存量新车数据只读封存、不新开、不迁移；V1–V25 字节不变，新增能力全部走 V26+ | 零数据迁移风险、Flyway checksum 不动、可回退 | 库内两套模型并存，报表/对拍需按类型过滤 | ✅ 建议 |
| B. 双模长期并存 | 新车/二手车两套规则链长期并行，按 `product_type` 路由 | 客户若仍有少量新车业务可覆盖 | 规则分叉翻倍、测试矩阵翻倍、与「不碰新车」前提矛盾 | ❌ |
| C. 一次性数据迁移 | 把存量数据清洗成二手车模型 | 模型单一 | 需重写发票→评估价、担保→車検証等不可反推字段，风险极高 | ❌ |

> **待定源 D-01**：目标态是否**完全不保留**新车业务入口（含历史数据是否需归档出库）。本文按方案 A 编写需求，最终以业务书面确认为准。

### R1 · 借款主体与 B 端车商资质

- **现状**：`dealers` 仅 `status / risk_grade / business_years / contact / address`；评级为人工 A–D（`V3`）；`Dealer.java:11-13` 主体写死「品牌授权经销商」；无上游评级（`ADR007:255` 自认缺口）。
- **需求**：

### R3 · 估值、残值与 LTV 定价（**核心改造**）

- **现状**：唯一公式 `发票 × 0.90`（`AdvanceApplicationService:172-177`）；`max-ratio 1.0`；`residual_value_*` 三列无写入方且「仅用于预警、不作处置定价依据」（`V11:287-294`）；`ADR:138-139` 两个全局折旧率；`LTV_BREACH` 枚举存在无触发代码。
- **需求**：
  - R3.1 **放款基准改为「双源审慎值」**：`放款基准 = min(落札价/采购价, 第三方评估价 or 相場行情价)`（或按业务裁决的加权规则），并把「评估价 / 评估机构 / 评估书编号 / 评估日 / 有效期 / 行情快照」作为一等公民落库，杜绝「虚高采购价套超额垫款」。
  - R3.2 **分档 LTV**：垫款比例按「车龄带 × 走行距离带 × 修復歴 × 評価点 × 车型热度 × 車検残存 × 车商资质分」分档可配置，取消全局 0.90 / 1.0；`max-ratio` 下调并对超标申请硬拒 + 工单。
  - R3.3 **在库定期重估**：按拍卖相場 / 行情文件定期刷新估值，`残值率 = 当前估值 / 未偿本金`；跌破阈值（现 1.2，须按车龄带重定）触发 `LTV_BREACH` 告警 → 追加还款 / 追加担保 / 冻结新放款。
  - R3.4 **估值联动库龄递减**：把「按估值比例递减」从设计稿 P2（`库龄递减设计.md:163,166-168`）提为 P0，递减触发由「按天数」改为「**估值衰减 + 天数双因子**」。
  - R3.5 估值同时作为**违约处置定价依据**（现注释禁止），并保留人工估价覆盖与评估报告附件。
  - R3.6 利率定价新增「车辆维度加点」（车龄 / 车况 / LTV 分档），叠加现有评级加点；移除「厂家贴息」轧差链路（`项目设计文档:465`）。
- **优先级**：P0（R3.1–R3.4）、P1（R3.5–R3.6）
- **验收要点**：同一台车落札价 200 万、评估价 160 万时，垫款按审慎值计算而非落札价；修復歴有 / 无得到不同 LTV；重估后 `LTV_BREACH` 能生成追加还款工单；`smoke` 中发票公式断言全部替换为估值公式断言。
- **依赖**：R2、外部相場/查定数据源（D-05）、ADR 定源（推翻 `ADR:138-139,151`）。

### R9 · 计息 / 结算 / 库龄 / 贷后

- **现状**：本金=发票派生垫款；`2 + 5 营业日`；`90/30/10%` 单层且三处口径打架（ADR 20/30/50% vs yml 10%）；`主机厂直供车不递减`；指标全是经销商+时间维度；残值监控零代码；展期理由为「客户贷款审批/过户」。
- **需求**：
  - R9.1 计息引擎、停息点（SETTLED）、幂等、罚息口径**直接复用**；仅把本金来源改为 R3 审定垫款，移除厂家贴息轧差。
  - R9.2 结算窗口按「零售 / 批发转售 / 拍卖回款」分设（窗口 + 宽限期可配置），展期理由与证据改绑「再上架 / 再拍卖 / 车检过户中」；修正 `newDue = plusDays(extDays)` 与营业日口径不一致。
  - R9.3 库龄递减改「估值衰减 + 天数」双因子；统一 ADR / yml / 流程文档三处比例口径；豁免规则由硬编码 `aging.exempt-vins` 改为规则表（拍卖中标待提车 / 整备待上架 / 跨店调拨 / 车检过户中）。
  - R9.4 贷后巡检新增车辆质量维度：车龄结构 / 里程异常 / 車検到期 / 修復歴占比 / 估值衰减率 / 久停 / WMS 账实相符率；集中度维度增加「年式带 / 評価点带 / 价格带 / 修復歴」。
  - R9.5 `RISK_SCAN` 从 P1 提为 P0；`LTV_BREACH`、`CONCENTRATION` 告警真正实现。
- **优先级**：P0（R9.1–R9.3）、P1（R9.4–R9.5）
- **验收要点**：同一台车按零售与拍卖两种售出类型得到不同到期日；估值下跌触发递减而不仅是天数；三处比例口径一致。
- **依赖**：R3、ADR 定源。

### R10 · 违约处置与再拍卖变现

- **现状**：`DisposalApplicationService.close(long proceeds)` 只有手工变现金额；`disposal_cases` 无评估价 / 渠道 / 佣金；`违约处置设计.md:402` 标注「競売变现 ⚠️ 缺失」；`valuation_amount / valuation_ref / disposal_cost / 清算计算书` 全是设计稿未落库；「厂家回购冲抵本金」为兜底。
- **需求**：
  - R10.1 违约收车后走**监管仓接管**（车本就在仓，需定义「担保物接管 / 禁止出库 / 处置授权」状态），而非从车商场地拖车。
  - R10.2 再拍卖变现通道：落 `disposal_method / auction_house / auction_lot_no / auction_date / hammer_price / commission / buyer_type / valuation_amount / valuation_ref / disposal_cost / 清算计算书`；与 USS/TAA 出场委托、成交结果对接。
  - R10.3 评估价与成交价对照、处置费用与佣金入账、`损失 = 应收 − 净变现所得`；清算计算书可导出。
  - R10.4 补齐法律清算状态机 `NOTIFIED / LEGAL_ACTION / CANCELLED` 的 HTTP 端点与通知能力（现 `PROGRESS §8.1 D7` 零通知代码）。
  - R10.5 复核「OOT 跳过收车：车已交付客户」（`ADR:175`）—— 二手车批发转售 / 拍卖在途场景车辆可能仍可追回。
- **优先级**：P1
- **验收要点**：处置单能记录拍卖会、落札价、佣金、评估价并算出净损失；收车后 WMS 不再允许普通出库。
- **依赖**：R6、R8、外部拍卖出场接口。

### R11 · 外部集成架构与安全边界

- **现状**：`external-api` 全库 0 处 Java；`ADR009` 状态 Proposed；`integration_partners/nonces/calls` 三表未建；所有渠道共用全局 webhook 密钥、无 nonce、CORS 全通配。
- **需求**：
  - R11.1 落地 `ADR009` 五层纵深防御：专线/VPN/mTLS → **独立 `external-api` 进程（DMZ）** → API 网关 → 签名鉴权 → 三路审计；DMZ 只做「验签 → 限流 → 协议转换 → inbox 落库 → 202」，不碰核心库、不跑业务逻辑。
  - R11.2 建 `integration_partners / integration_nonces / integration_calls` 三表；`partner_type` 从 `DEALER/OEM/BANK/INTERNAL` 扩到 `AUCTION / WMS / CUSTODIAN / LEGAL / REGISTRY`；per-partner 密钥 + `key_version` 轮换宽限 + `allowed_ips / allowed_scopes / rate_limit`。
  - R11.3 签名规范 `METHOD + PATH + timestamp + nonce + SHA256(body)` + nonce 去重 + ±时间窗；收紧 CORS；`signature_ok=false` 也必须留痕；`integration_calls` 只存请求摘要不存原文。
  - R11.4 Outbound 统一适配层：`IntegrationAdapter` 从现「厂家发票/垫款/入金」三方法扩展为「落札结果拉取出场结算 / 付款发起 / 放车指令下发 / 在库查询 / 凭证移交 / 回执接收」；ACL 强制外部 DTO → 内部 Command；逐笔对账是兜底而非补充。
  - R11.5 外部方**必须实现重试**写入对接合同；我方提供幂等键与人工重触发界面；按 partner 维度限流 / 熔断 / 降级。
  - R11.6 人工路径保留为降级（非长期主路径），与自动路径汇入同一内部命令，下游无感知（沿用 `外部集成接口文档:90-100` 的正确设计）。
- **优先级**：P0（R11.1–R11.3 为放车闭环前置）、P1（R11.4–R11.6）
- **验收要点**：伪造签名 / 重放 nonce / 超限流量被拦且留痕；DMZ 进程不持核心库连接；partner 密钥轮换期间新旧版本并存可用。
- **依赖**：D-04（各外部方接口现实）、部署拓扑（专线/IP 白名单）。

### R12 · 合规、权限与审计

- **现状**：SOD / `audit_events` / JWT+RBAC 已具备；但主体法理判断（`Dealer.java:11-13`「不适用个人借款总量规制」）随主体变化需重做；无外部 partner 审计主体；无車検証个人信息保护口径。
- **需求**：

## 6. 目标态端到端流程与状态机

### 6.1 主流程（12 步）

| 步 | 动作 | 系统内对象 / 门禁 | 外部 |
|---|---|---|---|
| 1 | 车商准入与授信 | 资质档案、双维评级、循环额度（可分产品/拍卖场设子额度） | 征信 / 反社 / 拍卖会员核验 |
| 2 | 拍卖场落札 | 落札结果建 `auction_lots`（落札番号/出品番号/評価点/落札価/決済期限） | USS/TAA → 我方 |
| 3 | 估值与单台准入 | 双源审慎值 + 分档 LTV + 車龄/里程/修復歴/車検残存/権利核查；`LTV` 超限硬拒 | 相場 / 查定 / 登録情報 |
| 4 | 申请垫资 + 付款 | 落札明細核对 + 车商额度行锁占用 + 生成付款指令；代付拍卖场结算 | 我方 → USS/TAA |
| 5 | 实车入监管仓 | WMS 入库确认（VIN/庫位/車況/里程）→ 车辆 `IN_STOCK` 起息 | WMS → 我方 |
| 6 | 車検証质押 + 担保设定 | 車検証 `PLEDGED`、抵当権/移転登録文书、逐台权属权威源登记 → 门禁 `REGISTERED` | 凭证保管 / 登记代办 |
| 7 | 在库监管 | 逐台计息、WMS 快照对账、定期重估与巡检、LTV 突破追加还款、库龄递减 | WMS 双向 |
| 8 | 车商卖车 | 售出类型（零售/批发/再拍卖）+ 售出登记 + 结算窗口起算 | — |
| 9 | 回款入指定账户 | 流水采集 + 按 VIN 匹配 + 冲抵（费用→利息→本金） | 银行 → 我方 |
| 10 | 解押 + 生成指令 | **资金闸门**；担保实体权利消灭 + 抹消待办 + 車検証 `RELEASED` 待交还；生成放车/放证指令（按项指定接收方） | — |
| 11 | 指令下发 + 权威回执 | 下发 WMS/拍卖场；回执由 `partner_code` 验签，支持 ACK/REJECTED/PARTIAL/EXPIRED | 我方 ↔ WMS / 拍卖场 |
| 12 | 台账闭环 | `SETTLED` + 库存 OUT + 额度回补（最后）+ 审计 + 证据链；账实巡检兜底 | — |

### 6.2 放车指令状态机（目标态）

```
PENDING_RELEASE ──下发成功──► SENT ──对方受理──► ACKNOWLEDGED
      │                        │                    │
      ├──撤销──► CANCELLED      ├──超期──► EXPIRED   ├──回执(全量)──► CONFIRMED
      │                        ├──拒收──► REJECTED   ├──回执(部分)──► PARTIAL
      │                        └──降级人工──────────► CONFIRMED(MANUAL/双人见证)
      │
CONFIRMED / PARTIAL ──► RELEASED（实车已出库 + 車検証已交还）
RELEASED ──► LIEN_DISCHARGED（登记抹消完成回执）──► 台账 SETTLED + 额度回补
```

> **顺序口径须先统一**：现有代码是 `RELEASED → LIEN_DISCHARGED`，而 `ADR-业务口径总定源:196` Q11 与 `放车放证设计.md:272-274` 是「先解押 → 发指令」。本文建议采用「**担保实体权利消灭（步骤 10）先于指令下发；登记簿抹消完成（LIEN_DISCHARGED）后于回执**」的两段式解押语义，并把 `LIEN_DISCHARGED` 明确为「登记抹消完成」而非「质押解除」，避免语义混淆。最终以 D-07 定源为准。

### 6.3 两条不可突破的红线（验收必测）

1. **未还款 / 未匹配 → 任何情况下不得生成或下发有效放车指令**（含人工重触发、内部代录、超时自动推进）。
2. **无接收方权威回执 → 不得把车辆推到 `SETTLED`、不得回补额度、不得把車検証标记为已返还**；`PARTIAL` 必须保持敞口并生成工单。

## 11. 验收标准（未来开发阶段的判据）

### 11.1 端到端主用例（必须跑通）

```
车商资质齐备 → USS 落札（落札価 200万 / 評価点 4.5 / 修復歴 無 / 車検残 18月）
→ 第三方评估 160万 → 审慎值 160万 × 分档 LTV 70% = 112万垫款
→ 代付拍卖场结算 112万 → WMS 入库确认 → 車検証 PLEDGED + 抵当権設定 → IN_STOCK 起息
→ 在库重估跌至 130万 → LTV_BREACH → 追加还款工单
→ 车商批发转售 → 回款入指定账户 118万 → 按 VIN 匹配 → 冲抵（息→本）
→ 担保实体权利消灭 + 抹消待办 + 車検証待返还
→ 生成放车指令（VEHICLE→WMS、INSPECTION_CERT→凭证保管方）
→ WMS 出库 + 交证 → partner_code 签名回执（含照片/里程）
→ 车辆 SETTLED / 库存 OUT / 额度回补 112万 / 审计全链路 / 证据链归档
```

### 11.2 红线断言（任一失败即不通过）

| # | 断言 |
|---|---|
| A1 | 回款未匹配到 VIN 时，`POST` 放车指令被拒；人工重触发 / 内部代录 / 超时推进均不能生成有效指令 |
| A2 | 无 `PARTNER_RECEIPT`（或合法双人见证 MANUAL）回执时，车辆不得 `SETTLED`、额度不得回补、車検証不得标记已返还 |
| A3 | `PARTIAL` 回执（只放车未放证）保持敞口并生成 HIGH 工单，不自动结清 |
| A4 | 重复投递同一 `release_order_no` 回执不产生重复台账更新 / 重复额度回补 |
| A5 | 伪造 `X-Partner-Code` / 过期 timestamp / 重放 nonce 被拦且 `signature_ok=false` 留痕 |
| A6 | 落札价虚高（200万）而评估价低（160万）时，垫款按审慎值 112万，而非 `200万 × 0.90 = 180万` |
| A7 | 无車検証质押 / 権利瑕疵 / 车商许可过期的车辆，放款被硬阻断且生成催补工单 |
| A8 | WMS 在库快照与本地台账出现「账有实无」时，产出 HIGH 差异工单且不放行出库 |
| A9 | 解押失败时整体回滚，不出现「钱收了、额度放了、车还押着」 |
| A10 | `mvn clean package` 15/15、`smoke` 全绿、Flyway V1–V25 字节不变且新增迁移全落库、10 服务启停正常 |

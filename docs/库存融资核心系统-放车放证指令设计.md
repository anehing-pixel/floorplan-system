# 库存融资核心系统 · 放车放证指令设计

> **定位**：本文档定义**环节⑧（解押与出库）** 的完整系统设计。
>
> **核心命题**：在经销商库存融资场景里，「发出放车/放证指令」**不是只发一条消息**，
> 而是系统里要完成**资金校验 → 额度处理 → 质押解除 → 指令下发 → 回执确认 → 台账更新**
> 这一整套动作。
>
> **版本**：v1.0　|　**日期**：2026-10-26　|　**状态**：设计稿，待评审
> **上游依据**：《库存融资核心系统-业务流程文档》环节⑧、
> 《库存融资核心系统-十一环节闭环核查报告》（**断点 B2：出库指令环节完全缺失**）、
> 《库存融资核心系统-ADR008逾期状态归属借据设计》（借据状态机）、
> 《库存融资核心系统-贷后监管设计》（事件驱动架构与工单体系）、
> 《库存融资核心系统-回款闭环与资金监管设计》（资金闭环校验）、
> 《库存融资核心系统-ADR009外部接入安全边界设计》（指令下发的外部通道）
> **相关角色**：结算岗（发起赎车）、资金复核岗（资金校验）、担保管理岗（质押解除）、贷后管理岗（异常处理）

## 0. 现状诊断

### 0.1 核查结论：这一环节几乎是空的

《十一环节闭环核查报告》把它列为**严重断点 B2**。逐项核查：

| 用户列的 8 个环节 | 现状 | 证据 |
|---|---|---|
| **1. 发起赎车** | ⬜ **无** | 无赎车申请实体、无接口。全库 `赎车\|redemption` 零命中 |
| **2. 资金校验** | 🟡 **部分** | `settle` 有金额校验（必须精确等于本金+利息），但**无"回款是否到账"的独立校验**、无保证金/受托账户概念 |
| **3. 冲抵与额度处理** | ❌ **不完整** | 现有 `settle` **只能整台结清**，无逐项冲抵（费用→罚息→利息→本金） |
| **4. 质押状态变更** | 🟡 **一半** | `releaseSecurity()` 存在，但**没有"待释放"中间态** |
| **5. 生成释放指令** | ⬜ **无** | 无指令实体、无编号规则、无有效期 |
| **6. 指令下发** | ⬜ **无** | 无接收方概念、无下发通道 |
| **7. 回执确认** | ⬜ **无** | 无回执实体、无状态流转 |
| **8. 台账更新** | 🟡 **一半** | 结清会更新台账（`settle` + 额度回补），但**出库动作本身不落任何账** |

### 0.2 五个必须新建的概念

| 概念 | 说明 | 为什么现有实体承载不了 |
|---|---|---|
| **赎车申请（Redemption）** | 经销商提出"我要把这台车赎出去"的动作 | 现有 `POST /{vin}/sold` 是**标记售出**（车已卖），不是**申请赎车**（车要交付） |
| **释放指令（ReleaseOrder）** | 一张给监管方/保管方的"请放行这辆车"的凭证 | 无此实体。**指令编号、有效期、释放内容、接收方、回执**全无 |
| **接收方（Custodian）** | 第三方监管仓 / 驻场监管员 / 合格证保管点 | 无此实体 |
| **车辆合格证（VehicleCertificate）** | 车的所有权凭证（车辆合格证/产地证明等） | ⚠️ **注意**：`collateral_registration_batches.certificate_no` 是**法务局登記事項証明書**，**不是车辆合格证**，两者不可混用 |
| **还款冲抵明细（Allocation）** | 一笔回款如何分配到费用/罚息/利息/本金 | 现有 `repayments` 只有 `principal` / `interest` 两个总额字段，无逐项分配 |

### 0.3 车辆状态机缺"待释放"这一态

**现状**（`VehicleStatus`）：

```
FINANCED → IN_STOCK → SOLD_PENDING → SETTLED
                                  ↘ OVERDUE → DISPOSING → CLOSED
```

**问题**：`SOLD_PENDING → SETTLED` 是**直连**的。
但真实业务里，零售成交与车辆交付**不是同一时刻**：

```
售出（车已卖给终端客户）
   ↓
客户付款 → 经销商收款 → 金融公司确认到账   ← 这里可能隔几天
   ↓
金融公司核验资金、冲抵、释放质押
   ↓
生成放车指令 → 监管方放行 → 车实际交付    ← 这里可能再隔几天
   ↓
监管方回执确认 → 台账更新
```

**现有状态机把"钱到了"和"车交了"合并成一步 `SETTLED`，这是环节⑧缺失的根源**——
系统无法表达"钱已到账、正在等监管方放车"这个中间态。

## 1. 八环节的完整设计

### 1.1 流程全景

```
① 发起赎车（结算岗代经销商录入 / 经销商系统推送）
      │  校验：VIN 属于该经销商？是否在质押中？是否已结清？
      ↓
② 资金校验（结算岗 + 资金复核岗）
      │  核对：回款是否到账？到哪个账户？金额是否覆盖应还总额？
      ↓
③ 冲抵与额度处理（结算岗执行，资金复核岗复核）
      │  冲抵顺序：费用/罚息 → 利息 → 本金
      │  本金减少后按「额度回补三原则」判定是否回补额度
      ↓
④ 质押状态变更（担保管理岗 / 系统自动）
      │  该 VIN：质押中 → 待释放（已解押待放车）
      ↓
⑤ 生成释放指令（系统自动）
      │  指令内容：VIN + 合格证号 + 监管方 + 释放内容 + 有效期 + 指令编号
      ↓
⑥ 指令下发（系统 → 接收方）
      │  第三方监管仓 / 驻场监管员 / 合格证保管点
      ↓
⑦ 回执确认（接收方回传）
      │  "已放车 / 已放证" → 更新指令状态
      ↓
⑧ 台账更新（系统）
      VIN → 已出库；质押 → 已解押；额度 → 恢复；形成完整审计轨迹
```

### 1.2 各环节的设计要点

#### ① 发起赎车

**动作**：经销商提交赎车申请，选择 VIN。

**校验**（三条，缺一不可）：

| 校验 | 规则 | 失败处理 |
|---|---|---|
| 归属 | VIN 的 `dealer_id` 必须等于申请方 | 拒绝（`REDEEM_001`） |
| 质押中 | 该 VIN 有未结清的担保（`security_status = REGISTERED` 或 `PENDING`） | 拒绝（`REDEEM_002`） |
| 未结清 | 状态为 `SOLD_PENDING`（已售未结清） | 拒绝（`REDEEM_003`）——在库车不能赎车 |

**为什么"未结清"是前置条件**：赎车是"已售出、要交付"的动作。
在库车（`IN_STOCK`）还没卖，赎什么车。

**注意与 `POST /{vin}/sold` 的区别**：
| 接口 | 语义 | 时机 |
|---|---|---|
| `POST /{vin}/sold` | **标记售出**（车已卖给终端客户） | 销售成交时 |
| `POST /redemptions`（新） | **申请赎车**（申请放车交付） | 客户要提车时 |

两者是**不同的事**。现有 `sold` 之后直接 `settle` 结清，把中间"申请赎车 + 等放行"这段吞掉了。

#### ② 资金校验

**这是最不能省的一步。**

**校验三个问题**：

| 问题 | 校验内容 | 数据来源 |
|---|---|---|
| **钱到了吗** | 指定账户是否有对应入账记录 | `payment_transactions`（《回款闭环设计》） |
| **钱对吗** | 金额是否 ≥ 应还总额（本金+利息+费用+罚息） | 借据 + 计息流水 |
| **钱在对的账户吗** | 入账账户是否为该经销商的**指定回款账户 / 保证金账户 / 受托还款账户** | `dealer_bank_accounts` |

**账户类型的扩展**（现有 `dealer_bank_accounts` 只有一般账户）：

```sql
-- 账户用途分类（新增）
ALTER TABLE dealer_bank_accounts
    ADD COLUMN IF NOT EXISTS account_usage VARCHAR(24) NOT NULL DEFAULT 'GENERAL';
        -- GENERAL 一般账户 / REPAYMENT 指定回款账户 / DEPOSIT 保证金账户 /
        -- ESCROW 受托还款账户（第三方监管）
    ADD COLUMN IF NOT EXISTS custodian_id BIGINT;   -- 属受托账户时，指向资金保管方
```

**三种账户的语义**：

| 账户 | 用途 | 谁能收款 | 回款如何核销 |
|---|---|---|---|
| **指定回款账户** | 经销商卖车款应进此账户 | 终端客户付款 | 直接匹配 VIN → 冲抵 |
| **保证金账户** | 经销商缴纳的保证金 | 经销商 | 抵扣欠款（不足部分仍需卖车回款） |
| **受托还款账户** | 第三方监管方代收代付 | 监管方 | 凭回款凭证核销 |

> **⚠️ 现实约束**：日本渠道**不扣押钥匙、不装 GPS**（业务流程文档第 6 节）。
> 但**保证金**与**受托还款账户**在实务中可能存在（尤其主机厂金融与第三方监管的场景）。
> 若客户确认不用保证金，则该账户类型可不做——**这是待确认项**。

**校验不通过的处理**：**不能自动放行**，也不该硬拒绝——
应生成工单给结算岗跟进（客户可能正在付款途中）。

#### ③ 冲抵与额度处理

**冲抵顺序（用户明确给出）**：

```
① 费用 / 罚息        ← 最优先（先收成本与惩罚）
② 利息
③ 本金               ← 最后
```

**为什么这个顺序**：费用与罚息是固定支出且与本金敞口无关；
利息是资金占用的代价；本金才是敞口本身。
先扣费用利息，最后才动本金——这样本金减少得最慢，敞口下降最保守。

**现有实现的缺口**：`settle` 只支持**整台结清**，
且金额必须**精确等于** `本金 + 利息`：

```java
long interest = interestLedgerRepository.sumInterestByVin(vin);
long principal = unit.getPrincipalBalance();
long expected = principal + interest;
if (settlementAmount != expected) {
    throw new BusinessException(ErrorCode.REPAY_001, ...);  // 金额不符直接拒绝
}
```

**不能处理**：
- 金额**超过**应还（多付了，无法核销）
- 有**费用/罚息**成分（无此科目）
- **部分**冲抵后的分项余额

**需要的模型**（借据侧，ADR-008 的 `loans`）：

```sql
ALTER TABLE loans ADD COLUMN IF NOT EXISTS fee_outstanding   BIGINT NOT NULL DEFAULT 0;
ALTER TABLE loans ADD COLUMN IF NOT EXISTS penalty_outstanding BIGINT NOT NULL DEFAULT 0;
ALTER TABLE loans ADD COLUMN IF NOT EXISTS interest_outstanding BIGINT NOT NULL DEFAULT 0;
ALTER TABLE loans ADD COLUMN IF NOT EXISTS principal_outstanding BIGINT NOT NULL DEFAULT 0;
```

**冲抵明细**（一笔回款 → 多个分项）：

```sql
CREATE TABLE repayment_allocations (
    id             BIGSERIAL PRIMARY KEY,
    repayment_id   BIGINT NOT NULL REFERENCES repayments (id),
    loan_id        BIGINT NOT NULL,
    vin            VARCHAR(32) NOT NULL,
    alloc_type     VARCHAR(16) NOT NULL,
        -- FEE 费用 / PENALTY 罚息 / INTEREST 利息 / PRINCIPAL 本金
    alloc_amount   BIGINT NOT NULL,
    alloc_seq      INTEGER NOT NULL,       -- 冲抵顺序号（1=费用/罚息, 2=利息, 3=本金）
    allocated_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uk_alloc UNIQUE (repayment_id, alloc_type)
);

CREATE INDEX IF NOT EXISTS idx_alloc_loan ON repayment_allocations (loan_id);
```

**额度回补**：按**额度回补三原则**（《十一环节闭环核查报告》§⑨-1）判定——
本金冲抵额（C1）✅、质押物状态（C2）、合同规则（C3）、非逾期补款（C4）。

**注意本环节与 §⑨-1 的关系**：卖车回款（结清场景）**应全额回补**——
因为此时质押物也将释放（C2 在环节④成立）。所以额度回补的**实际执行时点在环节④之后**，
或与环节④同事务。**绝不能在本环节（还没解押）就回补额度。**

> **这是一个容易搞错的顺序**：先冲抵（本金下降）→ 再解押 → **最后**才回补额度。
> 若在冲抵时就回补，而解押失败，就变成"钱收了、额度放了、车还押着"——资损。

#### ④ 质押状态变更

**动作**：把该 VIN 从"质押中"改为"待释放 / 已解押"，同时更新合格证、钥匙状态。

**建议新增车辆状态**：

```
SOLD_PENDING → PENDING_RELEASE（待释放：已收款待放车）
                    ↓ 监管方回执确认
                  SETTLED（已出库已解押）
```

> **为什么需要这个中间态**：现有 `SOLD_PENDING → SETTLED` 直连，
> 系统无法表达"钱已到账、指令已下发、等监管方放车"。
> 这个中间态对**盘点**尤其重要——盘点时看到 `PENDING_RELEASE` 的车，
> 要知道"这台车在等放行"，而不是"这台车状态不明"。

**质押状态与车辆状态是两回事**（沿用 ADR-008 的正交维度思想）：

| 维度 | 字段 | 环节④的变化 |
|---|---|---|
| 车辆状态 | `vehicle_units.status` | `SOLD_PENDING → PENDING_RELEASE`（→`SETTLED`） |
| 质押状态 | `collateral_ledger.released` | `false → true` |
| 抹消待办 | `collateral_ledger.registration_due` | `true`（让渡担保需双方共同申请抹消） |
| 合格证状态 | `vehicle_certificates.status` | `HELD → RELEASED`（或 `PENDING_RELEASE`） |
| 钥匙状态 | `vehicle_certificates.key_status` | `HELD → RELEASED` |

> **⚠️ 日本渠道的钥匙处理**（重要，不要照搬中国做法）：
> 本项目**不扣押钥匙**作为控制手段（业务流程文档第 6 节明确）。
> 但"钥匙状态"作为**事实记录**仍有价值——
> 盘点时记录钥匙是否齐全，是证据链的一部分。
> **区分**：钥匙是「事实记录项」，不是「控制手段」。

**登记抹消的衔接**：环节④释放质押，**但法务局的登记抹消需双方共同申请**
（ADR-007 / 《违约处置设计》已确认），不能自动完成。
所以环节④产生的是**抹消待办**，不是抹消完成。

#### ⑤ 生成释放指令

**指令必须包含的六要素**（用户明确列出）：

| 要素 | 说明 | 必填 |
|---|---|---|
| **VIN** | 车架号 | ✅ |
| **合格证号** | 车辆合格证编号（**不是法务局证明书**） | ✅ |
| **监管方** | 接收方（第三方监管仓 / 驻场监管员 / 合格证保管点） | ✅ |
| **释放内容** | 放车 / 放证 / 放钥匙（可组合） | ✅ |
| **有效期** | 指令过期时间 | ✅ |
| **指令编号** | 系统生成，**唯一且可追溯** | ✅ |

**指令模型**：

```sql
CREATE TABLE release_orders (
    id             BIGSERIAL PRIMARY KEY,
    order_no       VARCHAR(32) UNIQUE NOT NULL,     -- 指令编号（如 RO-2026-000123）
    redemption_id  BIGINT NOT NULL,                 -- 关联赎车申请
    dealer_id      BIGINT NOT NULL,
    vin            VARCHAR(32) NOT NULL,
    -- ---- 指令要素 ----
    certificate_no VARCHAR(64),                     -- 车辆合格证号
    custodian_id   BIGINT,                          -- 监管方（接收方）
    release_items  VARCHAR(64) NOT NULL,            -- 释放内容：VEHICLE 放车 / CERTIFICATE 放证 / KEY 放钥匙（逗号分隔）
    valid_until    TIMESTAMPTZ NOT NULL,            -- 有效期
    -- ---- 指令状态 ----
    status         VARCHAR(16) NOT NULL DEFAULT 'ISSUED',
        -- DRAFT 草稿 / ISSUED 已下发 / ACKNOWLEDGED 监管方已接收 /
        -- RELEASED 已放行 / REJECTED 监管方拒收 / EXPIRED 已过期 / CANCELLED 已撤销
    issued_at      TIMESTAMPTZ,
    issued_by      VARCHAR(64),                     -- 下发人（自然人，来自令牌）
    acknowledged_at TIMESTAMPTZ,
    released_at    TIMESTAMPTZ,                     -- 回执确认时间
    rejected_reason VARCHAR(500),
    -- ---- 通道 ----
    delivery_channel VARCHAR(16) NOT NULL DEFAULT 'MANUAL',
        -- MANUAL 人工转交（打印/电话）/ PORTAL 监管方门户 / API 系统直连 / MQ 消息
    delivered_at   TIMESTAMPTZ,
    receipt_id     BIGINT,                          -- 回执
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uk_ro_vin UNIQUE (vin, valid_until)  -- 同一台车同一有效期不重复发指令
);

CREATE INDEX IF NOT EXISTS idx_ro_status ON release_orders (status, valid_until);
CREATE INDEX IF NOT EXISTS idx_ro_dealer ON release_orders (dealer_id, created_at DESC);
```

**指令编号规则**：`RO-{YYYY}-{6位序号}`，全局唯一，**一旦生成不可复用**。
理由：指令是法律凭证——"当时下发了哪张指令、放了什么、什么时候失效"必须唯一可查。

**有效期设计**：

| 时长 | 理由 |
|---|---|
| 默认 **7 个日历日** | 覆盖客户提车、过户、物流周期；过期后可重新申请（生成新编号） |

**过期不等于作废**：过期后 `status = EXPIRED`，但**记录保留**。
若车已实际交付但回执没回，账实会出现缺口——这需要巡检发现（见 §4.3）。

#### ⑥ 指令下发

**接收方（监管方）**：

```sql
CREATE TABLE custodians (
    id             BIGSERIAL PRIMARY KEY,
    custodian_code VARCHAR(32) UNIQUE NOT NULL,
    custodian_name VARCHAR(128) NOT NULL,
    custodian_type VARCHAR(24) NOT NULL,
        -- THIRD_PARTY_WAREHOUSE 第三方监管仓 / ON_SITE_SUPERVISOR 驻场监管员 /
        -- CERTIFICATE_DEPOSITORY 合格证保管点 / DEALER_WAREHOUSE 经销商自有仓库
    contact_name   VARCHAR(64),
    contact_phone  VARCHAR(32),
    contact_email  VARCHAR(128),
    -- 对接信息（外部通道，鉴权见 ADR-009）
    api_endpoint   VARCHAR(256),
    api_secret_ref VARCHAR(128),        -- 密钥引用（不存明文）
    status         VARCHAR(16) NOT NULL DEFAULT 'ACTIVE',
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

**下发通道**（四种并存，按对方能力选）：

| 通道 | 适用 | 说明 |
|---|---|---|
| **人工转交** | 驻场监管员、纸质凭证 | 系统生成指令，打印/拍照发给监管员；监管员电话/系统回执 |
| **监管方门户** | 有门户的第三方监管仓 | 推送待办，监管方在门户确认 |
| **系统直连（API）** | 有接口的 | 走 ADR-009 的 DMZ 入口，签名鉴权 |
| **消息（MQ）** | 有消息能力的 | 事件驱动，符合《贷后监管设计》§2 |

> **重要**：这四种通道最终**汇入同一张 `release_orders`**，下游无感知——
> 沿用外部集成文档 §2.5「人工路径是一等公民」。

**下发失败的处置**：指令生成 ≠ 下发成功。
`status` 从 `DRAFT` → `ISSUED` 只在**确认送达**后。
下发失败（对方系统不可达）应重试 + 降级到人工通道 + 告警。

#### ⑦ 回执确认

**接收方回传"已放车 / 已放证"**，系统更新指令状态。

```sql
CREATE TABLE release_receipts (
    id             BIGSERIAL PRIMARY KEY,
    receipt_no     VARCHAR(32) UNIQUE NOT NULL,
    release_order_id BIGINT NOT NULL REFERENCES release_orders (id),
    -- 回执内容
    released_items VARCHAR(64),                   -- 实际释放的内容（可能部分释放）
    released_at    TIMESTAMPTZ NOT NULL,           -- 实际释放时间
    -- 现场证据（可选但强烈建议）
    photos         VARCHAR(512),                  -- 照片附件 ID 列表
    odometer_km    INTEGER,                       -- 交付时里程（证据链）
    receiver_name  VARCHAR(64),                   -- 接收人签字
    receiver_note  VARCHAR(500),
    -- 异常
    exception_type VARCHAR(24),                   -- REJECTED 拒收 / PARTIAL 部分释放 / DELAYED 延迟
    exception_reason VARCHAR(500),
    -- 确认人
    confirmed_by   VARCHAR(64),                   -- 监管方操作人（非我方自然人）
    confirmed_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    -- 通道
    source         VARCHAR(16) NOT NULL DEFAULT 'PORTAL',
        -- PORTAL / API / MANUAL 人工转录 / MQ
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS idx_receipt_ro ON release_receipts (release_order_id);
```

**回执的三种异常**（必须能表达，否则账实缺口无法解释）：

| 异常 | 含义 | 系统动作 |
|---|---|---|
| `REJECTED` | 监管方拒收（文件不齐、状态不符） | 指令置 `REJECTED`，生成工单给结算岗 |
| `PARTIAL` | 部分释放（放了车但没放证） | 指令保持 `ISSUED`，生成工单 |
| `DELAYED` | 延迟（今天不放，明天放） | 指令保持 `ISSUED`，记录延迟原因 |

> **为什么"部分释放"必须能表达**：合格证与车可能在不同地方保管（车在监管仓、证在保管点）。
> 只放了车没放证 = 车交付了但物权凭证未转移——**这是真实的法律状态差异**，不是数据错误。

#### ⑧ 台账更新

回执确认后，系统一次性完成：

```
VIN 状态：PENDING_RELEASE → SETTLED
质押状态：released = true, released_at, release_reason = REDEEMED
车辆合格证：HELD → RELEASED
额度：按额度回补三原则回补（若之前未回补）
库存：IN_STOCK → OUT（从经销商在库库存中扣除）
审计：完整轨迹写入 audit_events
证据链：release_order + release_receipt 挂入 collateral_evidence_links
```

**"库存"维度的更新**：经销商侧的在库库存台账（本系统 `vehicle_units` 有 `stock_in_date`/`sold_at`，
但没有独立的"经销商库存报表"）。若要出**经销商库存清单**（盘点用），
需要一个视图或表按 `dealer_id + status` 聚合。

**审计轨迹**（用户要求"形成完整审计轨迹"）：

| 事件 | 记录 |
|---|---|
| `REDEEM_REQUEST` | 赎车申请提交 |
| `REDEEM_FUND_VERIFIED` | 资金校验通过（回款流水 ID） |
| `REDEEM_ALLOCATED` | 冲抵明细（费用/罚息/利息/本金各多少） |
| `REDEEM_SECURITY_RELEASED` | 质押解除 |
| `RELEASE_ORDER_ISSUED` | 指令生成与下发（渠道、接收方、编号） |
| `RELEASE_ACKNOWLEDGED` | 监管方接收确认 |
| `RELEASE_CONFIRMED` | 回执确认（实际释放内容、时间、接收人） |
| `VEHICLE_RELEASED` | 台账更新完成 |

> **⚠️ 一个必须保留的中间态**：若"资金已冲抵 + 质押已解除"但指令**未下发成功**，
> 系统处于"钱收了、质押放了、车还在库里"的状态——**这是资损敞口**。
> 因此环节③的额度回补**必须等到环节⑧完成**才执行（见 §1.2 ③ 的说明）。

## 4. 状态机与一致性

### 4.1 赎车申请状态机

```
REQUESTED ──→ FUND_VERIFIED ──→ ALLOCATED ──→ SECURITY_RELEASED ──→ ORDER_ISSUED ──→ CONFIRMED
    │               │                │               │                  │              │
    └───────────────┴────────────────┴───────────────┴──────────────────┴──────→ CANCELLED
```

**不可跳步**：资金校验未过不能冲抵；冲抵未做不能解押；解押未做不能发指令。
**这正是现有实现最大的问题**——`settle` 一步把"核销+解押+回补"全做了，
中间任何一步失败都是整体回滚，没有可观测的中间态。

### 4.2 车辆状态机扩展

```
FINANCED → IN_STOCK → SOLD_PENDING → PENDING_RELEASE → SETTLED
                                  ↘ OVERDUE → DISPOSING → CLOSED
```

**`PENDING_RELEASE` 的状态白名单**：
```
case SOLD_PENDING -> target == SETTLED || target == PENDING_RELEASE || target == OVERDUE;
case PENDING_RELEASE -> target == SETTLED || target == OVERDUE;
```

### 4.3 账实缺口巡检

回执可能丢失（监管方系统故障、快递丢失、人工漏录）。**必须能发现**：

| 缺口类型 | 检测 | 处理 |
|---|---|---|
| 指令 `ISSUED` 超过有效期仍无回执 | 每日巡检 | `RELEASE_ORDER_EXPIRED` 预警 + 工单 |
| 指令已 `RELEASED` 但车辆台账未更新 | 巡检比对 | 预警 + 人工修正 |
| 车辆已 `SETTLED` 但额度未回补 | 巡检比对 | 预警 + 补回补 |
| 车辆 `PENDING_RELEASE` 超时 | 巡检 | 预警（车在等放行，货压着） |

**这条巡检与 ADR-009 的 `integration_calls` 配合**——
外部通道的下发/回执记录都在 `integration_calls` 里，可交叉验证。

### 5.2 与 ADR-008（借据模型）的关系

**环节③ 的冲抵对象是借据，不是车辆**：

```
赎车申请（vin）
   ↓ 找到该 VIN 当前未结清的借据
借据（loan）的分项余额：fee/penalty/interest/principal
   ↓ 按顺序冲抵
repayment_allocations（分项明细）
   ↓ 本金下降
借据.principal_outstanding 减少
   ↓ 按额度回补三原则
credit_lines.used_amount 回补（最后一步，在环节⑧之后）
```

**为什么不能用车辆**：ADR-008 已确立"同一 VIN 可能有多笔借据"（库内实证）。
按 VIN 冲抵会算错——必须按**借据**。

### 5.3 与 ADR-009（外部接入安全）的关系

指令下发与回执若走外部通道（监管方门户/API/MQ），**必须**走 DMZ 入口：
签名按 ADR-009 §2.5 规范（METHOD+PATH+body+nonce+密钥版本），
审计落 `integration_calls`，回执的确认人记为 partner_code。

**人工代录回执**（监管方无系统时）走内部接口，审计记自然人——
两种来源在 `release_receipts.source` 上区分。

### 5.4 与《回款闭环设计》的关系

环节② 的资金校验依赖 `payment_transactions` 与 `expected_receipts`——
即《回款闭环设计》§3 的匹配引擎。**匹配成功 → 该 VIN 的 `expected_receipts.status = FULFILLED`**
→ 才有可核销的回款。

**衔接点**：回款匹配引擎输出"某笔回款属于某台车"，赎车申请环节② 校验"该台车对应的回款是否到账"。

| 12 | **PENDING_RELEASE 期间该车是否继续计息？** | 建议**继续计息**（钱还占用着，未交付） | 决定计息作业口径 |
| 13 | **环节④解押与环节③冲抵的原子性** | 建议**分两步但同事务可保证**，且额度回补放在最后 | 决定事务边界设计 |

> **📌 2026-11-22 口径收敛（针对 #1 / #6 / #10，已落地于 V24，最终仍待业务书面确认）**
>
> - **#1 接收方**：不再「四类都建模、按 type 区分」当成等价候选。《业务流程文档》§6 已确认日本新车渠道**无第三方实体监管**（只做实地盘点，不扣押钥匙/GPS/封签/驻场监管），车物理在经销商库、金融公司靠权属凭证控制。故按释放项分两条线：放车/交钥匙 → `DEALER_WAREHOUSE`，放证 → `CERTIFICATE_DEPOSITORY`；`THIRD_PARTY_WAREHOUSE` / `ON_SITE_SUPERVISOR` 与已确认口径冲突，枚举保留但须业务书面启用。落地为 `release_order_items.custodian_id`（NULL 继承主表 `release_orders.custodian_id`）。
> - **#6 下发方式**：起步收敛为 **MANUAL 人工转交为主、无外部 WMS 系统直连**，与 ADR-009「人工路径一等公民」一致；`PortalReleaseChannel` / `ApiReleaseChannel` / `MqReleaseChannel` 等真有 partner 系统时再实现。
> - **#10 回执**：仍坚持「不能由经销商自证代替」，但日本渠道没有第三方监管方，故把**执行接收方**与**权威确认方**解耦：经销商/保管点执行交付，我方担保管理岗见证代录回执（`source=MANUAL`），并用 `confirmation_authority`（`PARTNER_RECEIPT` / `INTERNAL_WITNESS` / `CERTIFICATE_HANDOVER`）同时写进状态历史与回执，使两类身份在审计上可区分。
> - ⚠️ V19 已执行，**任何表结构或注释调整必须走新迁移（V24）**；改 V19 会让 Flyway checksum 失配、服务启动失败。

## 8. 明确不做（有意边界）

| 项 | 原因 |
|---|---|
| **用"标记售出"代替赎车申请** | 售出是销售事实，赎车是放行请求，两者时点不同、责任人不同 |
| **系统自动确认回执** | 回执是交付证据，必须由接收方（监管方）确认，不能由我方代填 |
| **额度回补放在冲抵环节** | 冲抵时质押物尚未释放，回补了额度但车还押着——资损 |
| **扣押钥匙作为控制手段** | 不适用日本渠道；钥匙只作事实记录 |
| **把法务局登记证明当作车辆合格证** | 两者法律性质完全不同：前者用于抹消，后者是车辆权属凭证 |
| **跳过资金校验直接发指令** | 钱没到就放车是本末倒置 |
| **指令编号复用** | 指令是法律凭证，编号必须唯一可追溯 |
| **回执缺失就默认已交付** | 会掩盖账实缺口；必须由巡检发现并人工处理 |

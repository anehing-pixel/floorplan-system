# loan-service（借据与逾期天数服务，端口 8085）

> 一句话：**放款之后，把“这台车欠公司多少钱、什么时候该还、已经逾期几天”记成一张借据，并给催收、风控、征信一个统一的逾期天数。**

---

## 它在业务里管什么

`floorplan-core` 在付款确认后发出一句“这笔垫款已经放款了”。`loan-service` 收到后，要建一张**借据**（也就是这笔债权的正式记录），之后负责：

- 这笔借据还欠多少本金、利息；
- 应还日期是哪天；
- 截至某一天，已经逾期多少天；
- 这个经销商整体的逾期风险画像。

业务上最重要的是：**逾期天数只能有一个口径。** 催收说逾期 30 天、风控说 25 天、征信报 28 天，就会出问题。所以这个服务是全系统逾期天数的唯一计算方。

---

## 它具体做什么

### 1. 收到放款通知后建借据

- 监听“垫款已放款”通知（事件名 `LOAN_CREATED`，业务键是垫款编号 `advanceId`）；
- 用 `LN-` + 垫款编号作为借据号，重复收到同一条通知不会建第二张借据；
- 通知里缺关键信息（VIN、垫款编号、经销商、额度编号、本金等）时，直接报错进入重试/死信，不会把坏数据当成“已处理”。

### 2. 算逾期天数（DPD）

- 输入是“截至哪一天”（`asOf`），不是系统当前时间；这样补算、回溯、对账都能算同一天；
- 宽限期内不算逾期；
- 按自然日算，周末和节假日照算；
- 分 M1/M2/M3/M4 档；
- 每次计算结果可以留规则版本、口径快照、阈值快照，以后规则改了也能解释“当时为什么算 30 天”。

### 3. 提供借据和 DPD 查询

- 按借据号查详情；
- 按 VIN 查当前在贷借据（bank-service 回款匹配时会来查）；
- 查某笔借据截至某天的 DPD（只算不写库）；
- 手动触发全量 DPD 刷新（批量作业入口，也会定时跑）。

### 4. 经销商风险画像

- 汇总这个经销商名下借据的逾期情况、风险等级；
- 可以手动重算；
- 画像只用于贷后观察，不直接替业务做“放不放款”的决定。

---

## 它不做什么

- 不负责放款、收款、记账——那是 floorplan-core；
- 不负责把回款匹配到借据——那是 bank-service；
- 不负责解除担保——那是 floorplan-core；
- 不直接催收、不发通知；
- 消费通知的线程没有登录用户，所以它不会在后台去调用其他业务服务。

---

## 对外提供的操作

| 操作 | 业务含义 |
|---|---|
| `GET /api/loans/{id}` | 查一笔借据的详情 |
| `GET /api/loans/by-vin/{vin}` | 按 VIN 查当前在贷借据 |
| `GET /api/loans/{id}/dpd?asOf=` | 算这笔借据截至某天的逾期天数（不写库） |
| `POST /api/loans/dpd/refresh` | 批量刷新逾期天数 |
| `GET /api/dealer-profile/risk/{dealerId}` | 查经销商风险画像 |
| `POST /api/dealer-profile/risk/{dealerId}/recompute` | 重算经销商风险画像 |

## 现在真实状态（2026-11-24）

**已经可用：**

- 收到 `LOAN_CREATED` 自动建借据，重复通知不会重复建；
- 借据查询、按 VIN 查询、DPD 计算、DPD 批量刷新、经销商画像查询/重算；
- DPD 定时刷新已接入调度（默认 00:30 日本时间，本地默认关闭）。

**需要知道的问题：**

- 放款通知里目前**没有带“应还日期”和“宽限期天数”**（这两个字段的业务口径还没最终签字），所以新建借据的 `due_date` 可能为空、还款计划表没有生成；
- 这会导致 DPD 和后续对账转不完整：不是借据没建，而是借据的“到期日/还款计划”还不完整；
- 真实逾期催收动作、扣款失败处理、法律阶段都还没接。

---

## 用一句话总结

> `loan-service` 是借据账：放款后建借据，按统一口径算“截至某天逾期几天”，给催收、风控、征信同一个答案；它不碰钱，也不碰担保。

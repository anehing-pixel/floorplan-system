# floorplan-core（核心账务服务，端口 8080）

> 一句话：**这是整套系统的主账本。** 经销商进车、金融公司垫钱、车辆在库计息、卖车还款、结清解押，这些真正动账的事都在这里完成。

---

## 它在业务里管什么

库存融资的主流程是：

```text
经销商要进车
  → 提交采购单/车辆资料
  → 申请垫款
  → 复核
  → 出纳付款给上游
  → 银行确认付款成功
  → 车辆进入在库状态
  → 每天计息
  → 车卖掉
  → 经销商还款
  → 结清、解除担保、恢复额度
```

`floorplan-core` 负责这条主流程里**需要“要么全成功、要么全失败”的记账动作**。比如结清一笔垫款，必须同时完成三件事：

1. 把本金利息核销掉；
2. 把这台车的担保解除；
3. 把额度还回经销商。

这三件事必须一起成功。只做前两件，额度就被永久占住；只做后两件，账上还欠着钱。所以这些动作留在同一个服务、同一个数据库事务里，不拆出去。

---

## 它具体做什么

### 1. 垫款：从申请到付款确认

| 业务动作 | 说明 |
|---|---|
| 申请垫款 | 经销商针对某台车申请一笔钱，系统先占住授信额度 |
| 复核 | 复核人检查资料、金额、收款方 |
| 付款 | 出纳发起付款；付款是外部动作，不能和数据库事务绑死 |
| 确认到账 | 银行回调确认钱已付出，车辆状态变成“已放款/在途” |
| 失败/作废 | 付款失败或申请作废时，释放已占额度，车辆退回可申请状态 |

关键点：**钱先记指令、再付款、最后按银行结果落账**。不会出现“钱付出去了，系统里却没有这笔垫款”的情况。

### 2. 还款、提前赎回与结清

- **正常结清**：车卖了，经销商还清这台车的本金和利息，系统做“核销 + 解除担保 + 回补额度”三件事。
- **提前赎回**：车还没卖，经销商提前把钱还了，车还在自己库里，以后可以再次融资。系统把车标成“已赎回”，不是“已结清”，因为两者车去向不同。
- **部分还款**：先还一部分本金，车还在库、担保还在，不解除担保。

### 3. 计息与库龄

- 每天按剩余本金和利率算利息，写入计息流水；
- 支持补算：系统停过几天，可以从上次计息日接着补；
- 库龄推进：车在库多久，每天更新；
- 库龄递减：在库超过约定天数，强制要求还一部分本金；
- 结算窗口扫描：车卖了但超过约定天数没还款，升级为逾期/脱信销售风险。

这些作业既可以手工触发，也已经接入定时调度（默认本地关闭，生产开启）。

### 4. 车辆、采购单、供应商与收款账户

- 车辆批量建账、车辆详情、标记售出、客户付款确认、设定/解除担保；
- 采购单导入与校验：付款对象跟着真实采购单走，不是系统随便选；
- 供应商档案、供应商收款账户、经销商结算账户；
- 这些是垫款和付款的基础资料。

### 5. 附件与合同证据

- 合同、登记证明、发票等附件的上传、下载、查询；
- 文件不直接塞数据库，走预签名上传/下载，数据库只存引用和元数据。

### 6. 二手车（USED）三条已落地业务链

- **R1 车商资质准入**：古物商许可、拍场会员、合规核查、经营/库存评分，判断这个车商能不能做；
- **R2 车辆主数据**：车况票、里程多来源核对、車検証收证与换发；
- **R3 估值与 LTV**：多来源审慎估值、分档确定可贷比例、人工覆盖的二人签认。

### 7. 对外发通知、对内收通知

- **付款确认后**：发一条“这笔垫款已放款”的通知（事件名 `LOAN_CREATED`），loan-service 收到后建借据；
- **回款匹配成功后**：收到 bank-service 发来的“这笔回款已匹配”通知（`PAYMENT_MATCHED`）。如果确认是全额结清，就解除这台车的担保、更新担保台账、生成抹消登记待办；如果只是部分还款，不动担保；
- **回款通知这件事上不碰额度**：额度回补由 credit-service 消费同一通知后自己处理，core 不重复加额度；但垫款占用和结清释放仍由 core 的账务动作在同一数据库里完成。

---

## 它不做什么

- 不负责算逾期天数、不维护借据生命周期——那是 loan-service；
- 不负责拉银行流水、匹配回款——那是 bank-service；
- 不负责建经销商、核额度、冻结额度——那是 credit-service；
- 不负责实地盘点、风险预警、违约处置——那是 risk-service；
- 不负责给保管方下放车指令——那是 release-service；
- 不负责外部合作方的入站报文和密钥管理——那是 external-api。

## 现在真实状态（2026-11-24）

**已经能跑通的：**

- 垫款申请 → 复核 → 付款指令 → 确认/失败的完整状态流转；
- 结清、提前赎回、部分还款；
- 日终计息、库龄推进、库龄递减、结算窗口扫描、年审扫描、季度归档；
- 车辆建账、售出、担保设定/解除；
- 采购单导入、供应商与收款账户；
- 二手车 R1/R2/R3 三条链；
- 付款确认后发 `LOAN_CREATED`，回款匹配后收 `PAYMENT_MATCHED` 并真正解押。

**还没做完或需要知道的：**

- **真实付款通道还没接**：当前付款是模拟实现（`MockPaymentGateway`），真实银行/支付通道要替换实现；
- **付款前的担保登记检查默认关闭**：代码已经写好，但配置开关默认关着，因为登记查询链路还没完全定稿；打开前需要先补齐数据和链路，否则可能把所有付款都拒掉；
- **部分还款/提前还本之后额度怎么回补**，还有业务口径没有最终签字；
- 二手车 R4–R14（落札、放款前检查、WMS 账实、放车放证、回款回补、外部接入）还在开发中；
- 工单体系目前只有表，没有 Java 实现；风险预警落到 `risk_alerts`，不生成可流转的工单。

---

## 用一句话总结

> `floorplan-core` 是主账本：负责“钱怎么进来、怎么记、怎么还、怎么结清”，以及车辆、采购单、供应商这些基础资料；它保证结清这类动作要么全部成功、要么全部回滚，同时把“放款了”“回款结清了”通知给借据、额度和担保相关服务。

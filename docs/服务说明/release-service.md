# release-service（放车/放证指令服务，端口 8087）

> 一句话：**车卖了、钱到了，金融公司要给保管车和证件的仓库/监管方下指令：可以放车、可以放证；对方确认收到并执行，才算完成。**

---

## 它在业务里管什么

库存融资的车通常停在经销商场地或监管仓，車検証（车辆登记证）也可能由金融公司或监管方保管。经销商还清一台车的钱后，金融公司要通知保管方：

> 这台车可以放给经销商了，这个证件可以还了，担保可以解除了。

这个通知不能是口头一句话，必须有单据、有状态、有回执：

```text
创建出库指令（放车/放证）
  → 已下发，等对方确认
  → 对方确认收到
  → 实际放车
  → 解除担保登记
```

`release-service` 管的就是这张指令和它的状态流转。

---

## 它具体做什么

### 1. 创建出库指令

- 指定要放哪些车、放车还是放证、接收方是谁；
- 接收方可以是经销商、监管仓、拍卖场等，按车辆/证件分别指定；
- 创建后指令进入“已下发”，等对方回执。

### 2. 确认回执

- 保管方确认收到指令；
- 确认时要说明“凭什么有权确认”（自有人员、对方系统回执、书面回执等）；
- 代录回执要留下代录人和确认依据。

### 3. 放车

- 保管方实际把车放给经销商；
- 只有确认过回执的指令才能放车。

### 4. 解除担保登记

- 车放出去后，金融公司办理担保抹消；
- 只有车已经放出的指令，才能做“解除担保登记”。

### 5. 查指令详情

- 查当前状态、每一步的时间、操作人、回执依据。

---

## 它守的两条业务红线

1. **没有确认收到指令，不能放车**：防止“指令刚发出、对方还没确认，车就被放走了”；
2. **车没有实际放出，不能解除担保**：防止“车还在库里、担保已经解除”的资损敞口。

这两条规则写在状态机里，不靠操作人自觉；而且不允许“自己从 A 状态跳回 A 状态”这种假流转。

---

## 它不做什么

- 不负责判断钱有没有到账——那是 core 和 bank 的事；
- 不负责真正去法务局办抹消登记——它只记录“可以解抵/已解抵”；
- 不负责外部 WMS/监管仓的系统对接——目前是人工通道；
- 还没有自动消费“回款已结清”通知来创建出库指令：目前创建指令需要调用方发起，回款事件驱动这一环还没接。

---

## 对外提供的操作

| 操作 | 业务含义 |
|---|---|
| `POST /api/releases` | 创建出库指令（放车/放证），并下发 |
| `POST /api/releases/{id}/confirm` | 保管方确认收到指令 |
| `POST /api/releases/{id}/release` | 确认后实际放车 |
| `POST /api/releases/{id}/discharge-lien` | 放车后解除担保登记 |
| `GET /api/releases/{id}` | 查指令详情和操作历史 |

---

## 现在真实状态（2026-11-24）

- 五个操作都已可用，状态机按“已下发 → 已确认 → 已放车 → 已解抵”推进；
- 跳步、自流转会被拒绝，错误信息会告诉你当前状态和允许的下一步；
- 保管方解析、接收方按车辆/证件分别指定已可用；
- 目前下发通道是人工通道，没有接外部 WMS/监管仓系统；
- 回款结清后自动创建出库指令还没接，需要人工/上游调用创建；
- 与“直接还款”路径共用同一笔结算编号、防止重复释放的机制还没做。

---

## 用一句话总结

> `release-service` 是放车放证的指令本：记录“谁批准放、放给谁、对方有没有确认、车放没放、担保解没解”；没有确认不能放车，车没放不能解押。

## 1. JVM 调优模板（T4-3）

### 1.1 推荐参数

面向 JDK 17 + Spring Boot 3.2.5，统一使用 G1 GC。可直接作为容器启动参数或 `JAVA_TOOL_OPTIONS` 环境变量：

```bash
JAVA_TOOL_OPTIONS="\
-Xms{{HEAP_SIZE}} -Xmx{{HEAP_SIZE}} \
-XX:+UseG1GC \
-XX:MaxGCPauseMillis=200 \
-XX:InitiatingHeapOccupancyPercent=45 \
-XX:G1ReservePercent=10 \
-XX:G1HeapRegionSize={{REGION_SIZE}} \
-XX:ParallelGCThreads={{PARALLEL_GC_THREADS}} \
-XX:ConcGCThreads={{CONC_GC_THREADS}} \
-XX:+HeapDumpOnOutOfMemoryError \
-XX:HeapDumpPath={{DUMP_DIR}} \
-Xlog:gc*,gc+heap=debug,gc+phases=debug:file={{LOG_DIR}}/gc-%t.log:time,uptime,level,tags:filecount=5,filesize=100m"
```

**占位符清单（必须经压测定容后替换，禁止拍脑袋填值）**：

| 占位符 | 含义 | 定容依据 |
|---|---|---|
| `{{HEAP_SIZE}}` | 初始/最大堆，两者**必须相等** | T4-5 压测：稳定态老年代占用峰值 × 1.5~2，且不超过容器内存限额的 60%~70% |
| `{{REGION_SIZE}}` | G1 -region 大小 | 堆 ≤4G 用 2m；4~16G 用 4m/8m；16~32G 用 16m；一般让 G1 自动推断即可 |
| `{{PARALLEL_GC_THREADS}}` | 并行 GC 线程数 | 容器 CPU 限额；一般 = min(限额核数, 8)，CPU 配额 <4 核时显式设小 |
| `{{CONC_GC_THREADS}}` | 并发标记线程数 | 约为 `ParallelGCThreads` 的 1/4，向上取整，至少 1 |
| `{{DUMP_DIR}}` | OOM 堆转储目录 | 挂载持久化卷，确保有 ≥ 2×Xmx 的剩余空间 |
| `{{LOG_DIR}}` | GC 日志目录 | 挂载卷，按 `filecount=5,filesize=100m` 轮转，最多占用约 500MB |

### 1.2 参数理由

- **`-Xms = -Xmx`**：固定堆大小，避免运行时扩容/收缩带来的抖动与额外 Full GC。
- **`-XX:+UseG1GC`**：JDK 9+ 默认收集器，面向服务端大堆，兼顾吞吐与可预测停顿；本系统 Feign 调用多、对象短命，G1 的分代/区域回收更合适。
- **`-XX:MaxGCPauseMillis=200`**：停顿**软目标**（非硬保证）。G1 据此自适应调整 young 区大小；设得过低（如 50ms）会导致 young 区过小、GC 频繁、吞吐骤降。默认 200ms 是本系统 HTTP 接口 P99 的可接受基线。
- **`-XX:InitiatingHeapOccupancyPercent=45`**：并发标记启动阈值（占整堆比例）。保持默认 45%，在分配速率高的服务上可适当下调（如 35%）以提前开始混合回收，防止晋升失败触发 Full GC。**修改前必须看 GC 日志中的 `to-space exhausted` / `Humongous allocation` 记录**。
- **`-XX:G1ReservePercent=10`**：预留 10% 堆给晋升对象，防止 to-space 耗尽；内存紧张时不可低于 5%。
- **`-XX:G1HeapRegionSize`**：大对象（> region 一半）直接进 Humongous 区，region 过小会产生大量 Humongous 对象。若 GC 日志出现频繁 Humongous allocation，应调大 region 或排查大对象（如大响应体、大 JSON）。
- **`-XX:ParallelGCThreads` / `-XX:ConcGCThreads`**：**容器场景务必显式设置**。JVM 默认读取宿主机核数，容器被限 2 核却起 32 个 GC 线程会造成严重上下文切换。
- **`-XX:+HeapDumpOnOutOfMemoryError`**：OOM 时自动 dump，保留现场用于 MAT 分析；前提是 `{{DUMP_DIR}}` 可写且有空间。
- **`-Xlog:gc*...:filecount=5,filesize=100m`**：JDK 9+ 统一日志框架；`%t` 时间戳避免覆盖；`filecount/filesize` 做日志轮转，防止 GC 日志无限增长打满磁盘。日志字段含 `time,uptime,level,tags`，便于与压测报告时间轴对齐。

**明确不配置的项**：

- `-XX:+UseConcMarkSweepGC` / `-XX:+UseParallelGC`：JDK 17 已移除 CMS；Parallel GC 停顿不可控，不适用。
- `-XX:NewRatio`、`-XX:SurvivorRatio`：G1 下手动调这些会破坏 G1 的自适应，除非有明确证据否则不动。
- `-Xincgc` 等已废弃开关：JDK 17 不可用。
- 显式 `PermSize`：元空间已是本地内存，用 `-XX:MaxMetaspaceSize={{METASPACE}}` 单独限制（建议 128m~256m），避免无限增长。

### 1.3 容器内存换算（定容前置条件）

容器内存限额必须覆盖堆 + 堆外，否则会被 OOMKilled（退出码 137）而不是 Java OOM：

```
容器 memory limit ≥ Xmx + MaxMetaspaceSize + 线程数×栈大小(-Xss) + 直接内存(-XX:MaxDirectMemorySize) + 预留(20%)
经验取值：Xmx ≈ 容器 memory limit × 0.6~0.7
```

本系统 Feign/Netty/Undertow 使用直接内存，若出现 `Direct buffer memory` 或容器频繁被 kill，优先怀疑堆外内存未计入。

### 1.4 套用方式（模板文本）

Kubernetes Deployment（交 Wave2 按服务填充）：

```yaml
env:
  - name: JAVA_TOOL_OPTIONS
    value: "-Xms{{HEAP_SIZE}} -Xmx{{HEAP_SIZE}} -XX:+UseG1GC -XX:MaxGCPauseMillis=200 ..."
resources:
  requests:
    memory: "{{REQUEST_MEM}}"
    cpu: "{{REQUEST_CPU}}"
  limits:
    memory: "{{LIMIT_MEM}}"
    cpu: "{{LIMIT_CPU}}"
```

Docker Compose：

```yaml
environment:
  JAVA_TOOL_OPTIONS: "-Xms{{HEAP_SIZE}} -Xmx{{HEAP_SIZE}} -XX:+UseG1GC ..."
mem_limit: "{{LIMIT_MEM}}"
```

> 注意：`JAVA_TOOL_OPTIONS` 会作用于容器内**所有** Java 进程，若一个容器跑多进程需改用启动脚本内联参数。

### 1.5 压测定容流程

1. 预发按 T4-5 脚本施加阶梯负载，观察稳定态老年代峰值与 GC 频率。
2. 以老年代峰值 × 1.5~2 作为 `Xmx` 初值，核对容器内存换算（1.3 节）。
3. 验证标准：Young GC 间隔 ≥ 数秒、无 `to-space exhausted`、无 Full GC、P99 满足 SLA。
4. 不满足则回到第 2 步调整；每次只改一个变量，记录到压测报告。
5. 生产灰度一台，观察 24h GC 日志与容器重启次数，再全量推广。

## 2. 慢 SQL 治理模板（T4-4）

> 本节只给**方法与模板**，不修改任何 SQL、索引或数据库配置（越界）。
> 治理动作由 Wave2/DBA 按清单执行，执行前后都要归档执行计划。

### 2.1 EXPLAIN 用法

**取执行计划的标准命令**（在预发或只读从库上执行，生产大表谨慎）：

```sql
-- 1) 基础计划：看访问类型、可能索引、实际索引、扫描行数、Extra
EXPLAIN SELECT ... FROM {{TABLE}} WHERE ... ORDER BY ...;

-- 2) JSON 格式：字段更完整，便于归档与比对
EXPLAIN FORMAT=JSON SELECT ... FROM {{TABLE}} WHERE ...;

-- 3) 真实执行计划（MySQL 8.0.18+）：会真正跑一次，给出实际耗时与行数
EXPLAIN ANALYZE SELECT ... FROM {{TABLE}} WHERE ...;

-- 4) 写操作要放在事务里，看完立即回滚，禁止污染数据
START TRANSACTION;
EXPLAIN ANALYZE UPDATE {{TABLE}} SET ... WHERE ...;
ROLLBACK;
```

`EXPLAIN` 输出关键字段判读：

| 字段 | 关注点 | 危险信号 |
|---|---|---|
| `type` | 访问类型，优劣顺序：`system` > `const` > `eq_ref` > `ref` > `range` > `index` > `ALL` | `ALL`（全表扫描）、`index`（全索引扫描）需重点治理 |
| `possible_keys` / `key` | 优化器可选索引 / 实际选用索引 | `key = NULL`（没用上索引）；`possible_keys` 有值但 `key` 选错 |
| `key_len` | 实际用到的索引长度 | 远小于索引定义长度 → 联合索引只用到了前几列 |
| `rows` | 预估扫描行数 | 与实际返回行数相差数量级 → 统计信息过期，先 `ANALYZE TABLE {{TABLE}}` |
| `filtered` | 存储引擎返回后经 WHERE 过滤的比例 | 很低（如 <10%）说明索引选择性差或条件顺序不当 |
| `Extra` | 附加信息 | `Using filesort`（额外排序）、`Using temporary`（临时表）、`Using join buffer`（JOIN 无索引） |

**排查顺序**：

1. 先 `SHOW CREATE TABLE {{TABLE}}\G` 与 `SHOW INDEX FROM {{TABLE}}` 看现有索引。
2. `EXPLAIN` 找 `type=ALL`、`key=NULL`、`rows` 过大、`Using filesort/temporary`。
3. 核对统计信息：`ANALYZE TABLE {{TABLE}};` 后重跑 EXPLAIN（生产低峰执行）。
4. 怀疑优化器选错索引时用 `FORCE INDEX({{INDEX_NAME}})` 验证收益，再决定是否固化。
5. 用 `EXPLAIN ANALYZE` 对比实际行数与预估行数，确认根因。

### 2.3 索引补缺清单模板

每发现一条慢 SQL 登记一行，治理完成后更新「验证状态」：

| 编号 | 服务/模块 | SQL 摘要（脱敏） | 表 | 当前 type | 扫描行数 | 关键 WHERE 条件 | JOIN 顺序 | ORDER/GROUP 字段 | 建议索引 | 理由/预期收益 | 验证状态 | 负责人 | 日期 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| SQL-001 | `{{SERVICE}}` | `{{SQL_DIGEST}}` | `{{TABLE}}` | `ALL` | `{{ROWS}}` | `{{COL_A}}=? AND {{COL_B}} BETWEEN ? AND ?` | `{{JOIN_SEQ}}` | `{{COL_C}}` | `{{IDX_A}}, {{IDX_B}}, {{IDX_C}}` | 覆盖查询，消除 filesort，rows 降至 `{{TARGET}}` | 待验证 | `{{OWNER}}` | `{{DATE}}` |

**索引设计原则**：

- **最左前缀**：联合索引 `(a,b,c)` 只能被 `a`、`a,b`、`a,b,c` 条件利用；跳过 `a` 直接查 `b` 用不上。
- **列顺序**：等值条件列在前 → 范围条件列在后 → 排序列紧随其后（消除 `Using filesort`）。例：`WHERE status=? AND created_at BETWEEN ? AND ? ORDER BY id` → `(status, created_at, id)`。
- **覆盖索引**：把 SELECT 用到的列纳入索引，避免回表；但索引列越多写放大越大，需权衡。
- **选择性**：优先把区分度高的列放前面，可用 `SELECT COUNT(DISTINCT col)/COUNT(*)` 评估（越接近 1 越好）。
- **控制数量**：单表索引建议 ≤ 5~6 个；新增索引前先看能否改造已有索引（最左前缀复用），避免重复索引。
- **必须验证**：加索引前后各跑一次 `EXPLAIN ANALYZE`，用实际数据对比 rows 与耗时；治理后观察写入 RT 是否劣化。

### 2.4 执行计划归档规范

**归档路径（Wave2 建立目录，本次不创建）**：

```
docs/performance/explain/{{YYYYMMDD}}-{{SERVICE}}-{{SQL_ID}}/
├── 01-before.sql       # 治理前 SQL + EXPLAIN / EXPLAIN ANALYZE 输出
├── 02-schema.sql       # SHOW CREATE TABLE + SHOW INDEX（治理前）
├── 03-change.sql       # 实际执行的 DDL（CREATE/DROP INDEX），需 DBA 审批记录
├── 04-after.sql        # 治理后 SQL + EXPLAIN / EXPLAIN ANALYZE 输出
└── 05-summary.md       # 结论：rows/耗时前后对比、收益、风险、验证人
```

**归档要求**：

1. **命名**：`{{SQL_ID}}` 用稳定编号（如 `SQL-001`），与 2.3 清单编号一一对应；同一 SQL 的 before/after 放在同一目录。
2. **内容**：每份 `.sql` 文件头写清——服务名、环境、MySQL 版本、执行时间、数据量级、SQL 参数值（脱敏后）。
3. **脱敏**：参数中禁止出现 VIN、经销商名称/代码、手机号、客户姓名等敏感信息，统一替换为 `?` 或 `{{MASKED}}`。
4. **可复现**：记录 `EXPLAIN` 使用的具体参数值（脱敏），保证他人能复跑；`EXPLAIN ANALYZE` 注明是否真实执行及回滚情况。
5. **时机**：治理**前**和**后**各归档一份；未归档 before 的变更不予评审通过。
6. **关联**：压测报告中要引用对应归档目录编号（见 `scripts/loadtest/README.md` 报告模板的「慢 SQL 关联」栏）。
7. **保留**：至少保留一个迭代周期；涉及重大重构的归档随版本长期保留。

**慢 SQL 发现路径（配置改动由 Wave2 完成，本次不改配置）**：

- MySQL 慢查询日志：`long_query_time` 建议先设 `0.5`（秒），`min_examined_row_limit` 设 `1000`，避免抓到大量快查询。
- `performance_schema` / APM（如 SkyWalking）按 RT 排序取 Top N。
- 应急：`SHOW PROCESSLIST` 看是否有长时间运行的 `Sending data` / `Sorting result` 会话。
- 纳入治理的阈值建议：单次执行 > 500ms，或扫描行数 > 1 万，且每日调用 ≥ 100 次。

## 3. 静态检查接入说明（T0-7 配套，需 Wave2 改 pom）

CI 的 `mvn -q -B package` 已覆盖编译与单元测试，但**静态检查插件尚未接入**：接入必然要改 `pom.xml`（新增插件与规则集），属于本次 ENG 边界禁区，故只给方案，不落改动。

Wave2 若决定启用，按以下顺序接入（每步都要在 CI 全模块构建通过后再验证）：

1. **Checkstyle**（代码风格）：父 pom 增加 `maven-checkstyle-plugin`，绑定 `validate` 阶段，规则集建议用 Google Checks 精简版（团队可裁剪）。
2. **SpotBugs**（字节码缺陷）：父 pom 增加 `spotbugs-maven-plugin`，绑定 `verify` 阶段；需要排除生成代码目录。
3. **JaCoCo 覆盖率门禁**：父 pom 增加 `jacoco-maven-plugin` prepare-agent + check，按模块设最低覆盖率（建议先设低值试运行，逐步提高）。
4. CI 中相应把 `mvn package` 改为 `mvn verify`（或显式调用插件 goal），插件失败即阻断合并。

> 风险提示：引入以上插件会使全模块构建时间显著增加，且存量代码可能有大量告警。建议先在单个模块试点，再全仓库启用；切勿一次性开启 failOnViolation 导致流水线长期红灯。

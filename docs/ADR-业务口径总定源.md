## 0. 为什么不再等确认

ADR-Q27 已经把原则说死了，这里重申并推广到全仓：

> 表是本系统自己建的、字段是自己定的、阈值建议值是自己写进设计稿的、
> 枚举是自己编码的。把「以哪张表为准 / 阈值取多少 / 谁触发」包装成「等业务方定」，
> 等于让一个看不见表结构、看不见代码的人，回答一道我们自己才有条件回答的题。

因此本 ADR 做三件事：

1. **内部架构决策**（权威源、状态映射、取数 SQL、字段归属、去重优先级）→ 我直接裁决，不等人。
2. **参数默认值**（阈值、天数、比例、次数）→ 直接采纳设计稿里我自己写的「建议值」，
   定为系统默认，写进 `risk_rules` / `application.yml` 可覆盖，**不因为没人签字就悬空**。
3. **真正的外部事实**（法务省实际登记周期、日本短信服务商报价、银企直连接口、
   拍卖行行情文件、征信报送合规）→ 系统**不凭空对接**，给内部默认值 + 人工留痕，
   接口预留但不在本轮实现。这类属于 PROGRESS §8.1 的 D11「外部系统」，
   **口径已定，但不等价于功能已实现**。

### 0.1 「定口径」≠「已实现」（防止新的假绿）

本 ADR 只消灭「口径未定」这一层悬空，**不把任何占位/存根说成已实现**。逐项标注：

| 标记 | 含义 |
|---|---|
| ✅ **已落地** | 代码/迁移里已存在，本 ADR 只是把口径追认成定稿 |
| ⚙️ **口径已定·默认参数** | 采纳设计稿建议值为系统默认；业务若要改走配置覆盖，不改代码、不阻塞运行 |
| 📌 **口径已定·待工程实现** | 口径明确但代码尚未落地，对应 PROGRESS §8.1 的 D 类，仍是未开发需求 |
| 🌐 **外部事实** | 依赖第三方/合规，系统不对接，给内部默认值 + 人工留痕 |

### 0.2 唯一不变的硬口径（ADR-Q27）

**对拍/门禁类判定一律「两口径数值精确相等才无差异，不等即产出差异」，不做容差、不做舍入猜测。**
注意区分：**回款自动匹配置信度**允许容差（见 §1.5），那是「猜这笔钱对应哪台车」的评分；
**对账 R1–R8 与担保门禁**是「两个已确定的数是否相等」，绝不容差。二者不是一回事。

## 10. R1–R8 对拍规则口径（本轮代码落地）

| 规则 | 期望侧 | 实际侧 | 差异类型 | 状态 |
|---|---|---|---|---|
| R1 | `advances.amount` | `vehicle_units.principal_balance + SUM(repayments.principal)` | BALANCE_MISMATCH | ✅ |
| R2 | 债权存续车辆状态编码 1/0 | 存在未结清垫款编码 1/0 | STATE_MISMATCH | ✅ |
| R3 | `credit_lines.used_amount` | 未终结垫款金额合计 | CREDIT_MISMATCH | ✅ |
| R4 | 已匹配银行入账合计 | `SUM(repayments.total_amount)` | CASH_MISMATCH | ✅ |
| R5 | `vehicle_units.accrued_interest` | `SUM(interest_ledger + interest_ledger_archive.daily_interest)` | INTEREST_MISMATCH | ✅ 本轮落地 |
| R6 | V10 有效登记编码 1/0 | `collateral_ledger.security_status='REGISTERED'` 编码 1/0 | COLLATERAL_MISMATCH | ✅ 本轮落地 |
| R7 | `aging_plans.paid_periods` | `COUNT(curtailment_payments)` | CURTAILMENT_MISMATCH | ✅ 本轮落地 |
| R8 | 处置已结案 CLOSED_* 编码 1/0 | 借据 DEFAULTED/WRITTEN_OFF 编码 1/0 | WRITEOFF_MISMATCH | ✅ 本轮落地 |

**R5 口径细解**：`DAILY_INTEREST` 每次同时写 `interest_ledger` 流水与 `accrued_interest` 累加，
两者本就应精确相等；`INTEREST_ARCHIVE` 只把流水搬到归档表、不减台账，故取数必须
`UNION ALL` 主表 + 归档表，否则归档后必报假差异。

**R6 口径细解**：沿用 ADR-Q27 的有效登记定义（`registration_no IS NOT NULL`
且 `cancellation_status NOT IN ('DONE','CANCELLED')`）。台账标记与权威源不一致
（如结清后台账已 RELEASED 而登记簿仍待抹消）正是本规则要暴露的账实差异，不是 bug。

**R8 口径细解（关键设计判断）**：规则名「处置损失 vs 账务核销」原被误读成金额对拍，
但 `loss_amount`（应收 − 变现所得）与借据未偿本金**本就不该相等**，直接比金额会产出
100% 噪音差异、毫无判别力。故按 R2 同款归一为布尔关系：处置进入 CLOSED_* 终态
↔ 借据进入 DEFAULTED/WRITTEN_OFF 终态，两者应同时成立。当前系统处置结案未联动借据减记，
本规则会如实报出该缺口（正是它的价值），而非假装通过。

**统一判定**：8 条全部走 `ExactValueReconRule` 的 `expected != actual` 精确相等判定，
`ReconApplicationService` 不再有 `implemented=false → continue` 短路，
`ruleCount` 恒为 8，杜绝「报告说 8 条都跑了、实际只跑 4 条」的假绿。

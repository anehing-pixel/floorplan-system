# 库存融资核心系统 · 回款闭环与资金监管设计

> **定位**：本文档定义**"车辆卖出后，钱是否回到指定账户"** 这一核心资金监管问题的系统设计。
>
> **核心命题**：不是"猜钱有没有回来"，而是——
> **指定账户 + 流水自动采集 + VIN 匹配 + 未回款预警 + 自动释放担保**。
>
> **四层结构**：账户层（钱往哪走）→ 流水层（钱有没有到）→ 匹配层（这笔钱对应哪台车）
> → 释放层（回款后自动解押与额度恢复）。
>
> **版本**：v1.0　|　**日期**：2026-10-26　|　**状态**：设计稿，待评审

> **上游依据**：《库存融资核心系统-ADR007上游直付与收款账户设计》（账户只传引用码不传明文）、
> 《库存融资核心系统-贷后监管设计》（五层架构与工单体系）、
> 《库存融资核心系统-业务流程文档》环节⑦⑧⑨、
> 《库存融资核心系统-外部集成接口文档》（防腐层 / 人工路径一等公民 / 对账是兜底）

## 0. 为什么这件事是整个系统的风控命门

### 0.1 一个真实的风控逻辑

库存融资（Floorplan）的业务本质是**以车为抵押的循环授信**：
钱先付给上游，车停在经销商场地作担保，卖一台还一台，额度随之释放。

整个模式成立的前提只有一个：**车卖了，钱必须回来**。

```
若经销商卖车后把钱收进自己的账户，不用于还款：
  → 金融公司看到的是"车没了"，实际拿到的是"车没了 + 钱也没了"
  → 担保物价值归零，但债权依然存在
  → 这是比"车卖不掉"严重得多的损失
```

**「已售未回款」是敞口最大的状态**——车已交付终端客户（不可追回），
钱还没到账（不可控）。此时这台车在本系统里**既没有担保物价值，也没有现金流入**。

### 0.2 为什么"人工盯着问"解决不了

| 人工方式 | 问题 |
|---|---|
| 财务事后查银行流水 | 事后才知道，且靠 Excel 人工比对，漏一笔就是一笔敞口 |
| 定期问经销商要报表 | 经销商自报，可信度低；且滞后 |
| 靠 DMS 的"已售"推送 | 只知道车卖了，**不知道钱去了哪** |
| 靠结算岗人工催收 | 被动，且无法证明"钱没进指定账户" |

**核心缺陷**：所有人工方式都是**事后发现**，而敞口窗口是**实时产生**的。
且没有任何一种方式能回答法律上的关键问题——**"这笔钱是不是从约定账户进来的"**。

### 0.3 四层设计的分工

| 层 | 回答的问题 | 核心产出 |
|---|---|---|
| **账户层** | 钱**应该**进哪个账户 | 指定回款账户（受监管账户/专户）+ 合同约定 |
| **流水层** | 钱**有没有**到 | 银行回款流水（自动采集） |
| **匹配层** | 这笔钱**对应哪台车** | VIN ↔ 流水绑定 + 匹配记录 |
| **释放层** | 匹配上之后**自动做什么** | 额度释放 + 担保解除 + 抹消待办 + 凭证 |

**一句话**：指定账户负责"钱往哪走"，银行流水负责"钱有没有到"，
VIN 匹配负责"这笔钱对应哪台车"，状态机负责"回款后自动释放担保"。

## 1. 账户层：把"指定账户"管起来

### 1.1 现状与缺口

**已有**：`dealer_bank_accounts`（V7 迁移，ADR-007 引入），字段：

| 字段 | 说明 |
|---|---|
| `id` | 账户 ID |
| `dealer_id` | 经销商 |
| `bank_name` | 银行名称 |
| `account_holder` | 账户名义 |
| `account_no_cipher` | 账号密文（AES-GCM） |
| `account_no_mask` | 账号掩码（对外只返这个） |
| `account_ref` | 账户引用码（唯一，业务主键） |
| `status` | 状态 |
| `effective_from` / `effective_to` | 生效区间 |
| `reviewer` | 复核人（变更双人复核） |
| `created_at` / `updated_at` | 时间戳 |

**缺口**（对照本设计需要的字段）：

| 缺失字段 | 为什么必须有 |
|---|---|
| `bank_code` | 银行/金融机关代码——银行流水文件按这个键标识账户，缺了无法自动勾稽 |
| `branch_code` | 支店代码——日本银行账户是「本則+支店」二级结构，缺了定位不到账户 |
| `account_type` | 普通 / 当座 / 当座借越——**当座借越是透支账户，理论上不能收款**，误配会导致流水永远对不上 |
| `is_escrow` | 是否监管账户/专户——**决定回款进这个账户是否满足"回款落点"要求** |
| `agreement_ref` | 对应合同/让渡担保登记编号——把账户与法律依据绑定 |

> **为什么 `is_escrow` 是关键字段**：不是所有回款账户都是监管账户。
> 经销商可能有两个账户：一般账户（日常收付）与专户（回款专用）。
> **合同约定的是"销售车辆后的回款必须进入专户"**——
> 如果系统不区分这两个账户，就无法判定"钱进对了地方"。
> 进了一般账户 = 违反约定 = 预警。

### 1.2 设计：扩展既有表而非新建

**决策**：不新建表，扩展 `dealer_bank_accounts`。

理由：既有表已有加密、掩码、引用码、双人复核、冷静期机制——
新建表等于把这些安全机制复制一遍，且两套账户表并存必然产生"到底哪个是权威"的歧义。

```sql
-- 账户层扩展（V12 迁移）
ALTER TABLE dealer_bank_accounts
    ADD COLUMN IF NOT EXISTS bank_code     VARCHAR(16);   -- 银行/金融机关代码（银行流水文件的键）
ALTER TABLE dealer_bank_accounts
    ADD COLUMN IF NOT EXISTS branch_code   VARCHAR(16);   -- 支店代码
ALTER TABLE dealer_bank_accounts
    ADD COLUMN IF NOT EXISTS account_type  VARCHAR(16) NOT NULL DEFAULT 'CURRENT';
        -- ORDINARY 普通 / CURRENT 当座 / OVERDRAFT 当座借越
ALTER TABLE dealer_bank_accounts
    ADD COLUMN IF NOT EXISTS is_escrow     BOOLEAN NOT NULL DEFAULT FALSE;  -- 是否监管账户/专户
ALTER TABLE dealer_bank_accounts
    ADD COLUMN IF NOT EXISTS agreement_ref VARCHAR(128);  -- 对应合同 / 让渡担保登记编号
ALTER TABLE dealer_bank_accounts
    ADD COLUMN IF NOT EXISTS is_default    BOOLEAN NOT NULL DEFAULT FALSE;  -- 是否默认回款账户
ALTER TABLE dealer_bank_accounts
    ADD COLUMN IF NOT EXISTS sync_status   VARCHAR(16) NOT NULL DEFAULT 'UNKNOWN';
        -- UNKNOWN 未同步 / SYNCED 已同步 / FAILED 同步失败（银行流水按账户键拉取，需确认账户已开户）
```

**账户类型约束**（业务规则，非数据库约束）：

| `account_type` | 能否作为回款账户 | 说明 |
|---|---|---|
| `CURRENT` 当座 | ✅ 首选 | 日本经销商的标准结算账户 |
| `ORDINARY` 普通 | ⚠️ 可但需标记 | 活期账户，用于专户安排 |
| `OVERDRAFT` 当座借越 | ❌ **禁止** | 透支账户原则上不收款；如指定为回款账户必须报异常 |

### 1.3 账户的变更纪律（沿用 ADR-007 的既定口径）

| 动作 | 规则 |
|---|---|
| 新增账户 | 录入岗操作 + **变更双人复核** + **冷静期 T+2**（ADR-007 已定：SELF_PAY 场景账户建议 T+2+双签） |
| 账号明文 | **只在录入瞬间存在**，落库前 AES-GCM 加密；对外只返 `account_no_mask` |
| 停用 | 不物理删除——`status` 改 `DISABLED`，保留历史流水勾稽能力 |
| 换账户 | 旧账户 `effective_to` 截止、新账户 `effective_from` 生效；**期间的流水按入账日期归属** |
| 敏感变更 | 日志与审计**不落明文账号** |

### 1.4 合同约定（业务侧，不是代码）

这一层有一半在系统外——**必须写进合同**：

> 经销商销售车辆后，回款必须进入指定回款账户。
> 若经销商使用自己的一般账户，则需配合 **口座振替 / 自動払出し / 指定振込** 安排，
> 把资金定期划转到债权人可控账户。

**三种资金回流安排的工程含义**：

| 安排 | 含义 | 系统怎么管 |
|---|---|---|
| **直接指定** | 终端客户直接打款到债权人账户 | 最理想——流水 payer 是终端客户，匹配最容易 |
| **口座振替** | 经销商账户 → 债权人账户 的定期自动转账 | 流水 payer 是经销商自己，**金额对应关系需靠 DMS 销售台账** |
| **自动払出し** | 经销商授权金融机构从其账户扣款 | 同上，且需经销商先授权 |

> **⚠️ 关键工程影响**：当采用后两种安排时，**一笔流水可能对应多台车**。
> 系统必须支持"多台车同笔回款"的拆分匹配（见 §3.5 与预警 `MULTI_VIN_SPLIT`）。
> 这是账户安排直接决定的系统复杂度，不能事后补丁。

### 1.5 账户层的产出

| 产出 | 用途 |
|---|---|
| 每个经销商的**默认回款账户**（`is_default=true` 且 `is_escrow=true`） | 流水采集时按这个账户列表拉取 |
| 每个经销商的**合同约定账户**（`agreement_ref`） | 判定"回款进对账户"的依据 |
| 账户与 VIN 的**期望回款账户**（`collateral_ledger.required_account_ref`） | 单车维度的落点校验 |

## 2. 流水层：定时采集银行回款流水

### 2.1 现状与缺口

**现状**：`repayments` 表是**核销记录**（已确认的还款），不是银行流水。
两者区别至关重要：

| | 银行流水 | 还款核销（`repayments`） |
|---|---|---|
| 来源 | 银行 | 我方系统操作 |
| 时机 | 钱到账时 | 人工/自动核销时 |
| 数量 | 全部入账（含非本业务的） | 只有本业务已核销的 |
| 作用 | **事实** | **认定** |

**缺口**：完全没有流水表。**没有流水，就无法证明"钱到了指定账户"**——
现有的 `repayments.account_ref` 是核销时人工填的引用码，**没有与银行流水勾稽**。

### 2.2 设计：回款流水表

```sql
CREATE TABLE payment_transactions (
    id             BIGSERIAL PRIMARY KEY,
    transaction_id VARCHAR(64)  NOT NULL,   -- 银行流水号（与银行对账的唯一锚点）
    account_ref    VARCHAR(32)  NOT NULL,   -- 入账账户（引用码，对应 dealer_bank_accounts）
    account_id     BIGINT,                   -- 账户主键（冗余，便于查询）
    value_date     DATE         NOT NULL,   -- 入账日期（起息日，非交易日）
    amount         BIGINT       NOT NULL,   -- 入账金额（日元）
    payer_name     VARCHAR(256),            -- 付款人名称
    payer_account  VARCHAR(128),            -- 付款人账户（可能不完整，取决于银行提供）
    reference      VARCHAR(512),            -- 摘要/备注（**VIN 常在此处**）
    -- ---- 匹配结果 ----
    match_status   VARCHAR(16)  NOT NULL DEFAULT 'UNMATCHED',
        -- UNMATCHED 未匹配 / AUTO_MATCHED 自动匹配 / MANUAL_MATCHED 人工绑定 /
        -- IGNORED 判定为非本业务 / SPLIT 拆分到多台车
    matched_vin    VARCHAR(32),             -- 匹配的 VIN（单台时）
    matched_loan_id BIGINT,                 -- 匹配的融资编号（repayments.id 或 advances.id）
    matched_at     TIMESTAMPTZ,             -- 匹配时间
    matched_by     VARCHAR(64),             -- 匹配人（人工时）
    match_rule     VARCHAR(32),             -- 命中的匹配规则（可追溯判定依据）
    match_score    NUMERIC(6,2),            -- 匹配置信度
    -- ---- 采集元信息 ----
    source         VARCHAR(16)  NOT NULL DEFAULT 'BANK_FILE',
        -- BANK_API 银企直连 / BANK_FILE 文件（MT940/CSV）/ MANUAL_UPLOAD 人工上传
    raw_reference  TEXT,                    -- 原始报文（争议时自证）
    collected_at   TIMESTAMPTZ  NOT NULL DEFAULT now(),
    batch_no       VARCHAR(64),             -- 采集批次（同一文件同一批，便于整批重跑）
    CONSTRAINT uk_payment_txn UNIQUE (account_ref, transaction_id)
);

CREATE INDEX IF NOT EXISTS idx_ptx_match ON payment_transactions (match_status, value_date);
CREATE INDEX IF NOT EXISTS idx_ptx_vin ON payment_transactions (matched_vin);
CREATE INDEX IF NOT EXISTS idx_ptx_batch ON payment_transactions (batch_no);
```

> **幂等锚点**：`uk_payment_txn (account_ref, transaction_id)`。
> 同一账户同一流水号只入一次——**银行流水重复拉取是常态**（当日多次同步、文件重发），
> 没有这个约束，流水会翻倍，匹配金额会虚高。

### 2.3 采集方式（四种并存）

| 方式 | 协议 | 频率 | 现实可行性 |
|---|---|---|---|
| **银企直连 / 银行 API** | HTTPS + 证书/签名 | 每 15 分钟 ~ 每日 | ⭐ 最佳，但需银行配合与签约 |
| **MT940 / CSV / 网银导出** | SFTP / 门户上传 | 每日 | ⭐⭐ **现实最常见**（日本中小银行多为文件交换） |
| **定时任务拉取** | 触发上述两种 | 见 §2.4 | — |
| **事件触发（银行 webhook / MQ）** | 入账事件推送 | 实时 | ⭐ 需银行支持，不普遍 |

**设计要点：采集方式与匹配逻辑完全解耦。**

```
无论流水从哪来（API / 文件 / 人工上传）
        ↓
   统一写入 payment_transactions（带 source 标记来源）
        ↓
   匹配层处理（§3）
```

这符合外部集成文档 §2.5「人工路径是一等公民」——
人工上传的流水与银行推的流水，下游看到的完全一样。

**MT940 解析要点**：MT940 是 SWIFT 标准银行对账单格式，字段含
付款人名称、付款人账号、金额、起息日、交易附言（**VIN 常在这里**）、交易流水号。
需注意：
- 编码可能为 UTF-8 或 CP932（Shift_JIS）——日本银行文件常用后者
- 金额带千分位与符号
- 附言有长度限制，超长会被截断

### 2.4 采集调度

| 作业 | 频率 | 内容 |
|---|---|---|
| `BANK_FETCH` | 每 15 分钟（高频场景）/ 每日（文件场景） | 拉取指定账户流水 → 写 `payment_transactions` |
| `BANK_RECONCILE` | 每日 07:00 JST | 流水 vs 核销 vs 已售未回款台账 三方勾稽 |
| `PAYMENT_MATCH` | 流水写入后**立即触发**（事件驱动） | 执行匹配（§3） |

**为什么匹配要事件驱动而采集是定时**：采集受限于银行接口能力（只能定时），
但**一旦流水到了就应该立即匹配**——早一刻匹配就早一刻发现敞口，早一刻释放额度。
把匹配挂成定时会让每笔回款都延迟半天到一天才释放额度，无谓占用经销商额度。

### 2.5 流水层的产出

| 产出 | 用途 |
|---|---|
| 每笔入账的事实记录 | **证据链的"钱到了"部分**——回款凭证的基础 |
| 入账账户归属 | 判定"是否进入指定账户" |
| 付款人信息 | 匹配的重要线索（终端客户 vs 经销商自己） |
| 未匹配流水清单 | 贷后跟进的直接对象（预警 `PAYMENT_UNMATCHED`） |

## 3. 匹配层：判断这笔钱对应哪台车

### 3.1 这是最关键的一步

流水进来了，但**一笔 3,500,000 日元的入账，对应哪台车？**

- 可能是：一台车（最理想）
- 可能是：多台车（一笔打包结算）
- 可能是：一台车的一部分（部分还款）
- 可能：根本不是本业务（经销商的其他生意流水混在这个账户里）

**匹配错了的后果**：
- **误匹配**（A车的钱被绑到B车）→ A车被误判为已回款（漏管敞口），B车被误判为未回款（误催收）。**两种错误都很严重**。
- 因此设计上**自动匹配必须带置信度**，低置信度走人工复核，**不能强行自动绑定**。

### 3.2 自动匹配规则（五级，按优先级）

用户给出的五条规则，加上我补充的兜底，构成完整链路：

#### ① VIN 台账匹配（最强信号）

**条件**：
- `payment_transactions.reference`（摘要）里包含某个 VIN
- 且该 VIN 在台账中状态为 `已售未回款`（`sold=true` AND `repaid=false`）
- 且对应融资未结清

**置信度**：**95**（最高）

**这是最强的信号**——日本银行 MT940 的附言栏，客户付款时填的备注往往是 VIN 或订单号。
现实中终端客户付款时填 VIN 的比例不低（尤其车商要求客户注明车辆编号）。

#### ② 订单号 / 经销商编号匹配

**条件**：摘要里含采购订单号（`purchase_orders.order_no`）或经销商编号
**置信度**：90

#### ③ 金额匹配

**条件**：流水金额 ≈ 某台车的应回款金额（本金 + 利息，或销售价）

**容差**：需按金额性质区分（见下表）

| 匹配对象 | 期望金额 | 容差 | 说明 |
|---|---|---|---|
| 整台结清 | `principal + accruedInterest` | ±1 日元 | 台账算出的精确值，应完全匹配 |
| 部分还款 | `≤ 本金余额` | ±1 日元 | 库里龄递减还款常见 |
| 销售回款 | 销售价（发票金额） | ±1% 或 ±5,000 日元 | 谈价、折扣、税费导致差异 |

**置信度**：金额单独命中给 **60**（不够自动绑定，需与其他信号组合）

> **为什么金额单独不够**：经销商专户里可能同时有多台车的回款，金额可能撞车。
> 金额相同的两台车完全可能。**金额是辅助信号，不是主信号。**

#### ④ 时间匹配

**条件**：DMS 推送"已售"后，系统期待在 N 日内收到回款（`expected_receipt_days`，默认按结算窗口 `settle_due_date`）

**用途**：**不用于匹配，而用于发现"应该到但没到"**——
已售车超过 N 日仍无流水 → `SOLD_UNPAID` 预警。

**置信度**：不参与绑定（时间窗口内未匹配的车太多）

#### ⑤ 主机厂 / DMS 交叉验证

**条件**：主机厂或 DMS 已推送销售发票 → 系统自动生成**「应回款记录」**（`expected_receipts`）

**用途**：建立"应收"的台账。没有它，系统只知道"钱到了"，不知道"钱该有多少"。

**置信度**：作为**期望记录**生成，让匹配有基准（见 §3.3）

### 3.3 应回款记录（Expected Receipt）

**这是匹配层的隐含前提**：没有"应收"就没有"匹配"。

```sql
CREATE TABLE expected_receipts (
    id             BIGSERIAL PRIMARY KEY,
    vin            VARCHAR(32)  NOT NULL,
    dealer_id      BIGINT       NOT NULL,
    expected_amount BIGINT      NOT NULL,   -- 应收金额
    amount_type    VARCHAR(24)  NOT NULL,   -- SETTLE_FULL 整台结清 / CURTAILMENT 库龄递减 / PARTIAL 部分还款
    principal_part BIGINT       NOT NULL DEFAULT 0,
    interest_part  BIGINT       NOT NULL DEFAULT 0,
    sold_at        DATE,                     -- 售出日
    due_date       DATE,                     -- 应收截止日（结算窗口）
    source         VARCHAR(16)  NOT NULL,   -- DMS / OEM / MANUAL / SYSTEM
    source_ref     VARCHAR(64),              -- 来源单据（DMS 事件 ID / 发票号）
    status         VARCHAR(16)  NOT NULL DEFAULT 'PENDING',
        -- PENDING 待回款 / PARTIAL 部分回款 / FULFILLED 已回款 / OVERDUE 逾期 / WRITTEN_OFF 核销
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uk_exp_vin_type UNIQUE (vin, amount_type, source_ref)
);
```

**关键**：`expected_receipts` 把"应收"显式化。匹配的本质是
**把一笔实际流水，分配到一条或多条应收记录上**。

### 3.4 匹配流程

```
流水写入 payment_transactions（match_status=UNMATCHED）
        ↓
① 取该账户下所有 status=PENDING 的 expected_receipts（限定同一经销商）
        ↓
② 按规则打分（§3.2）：
   VIN 命中（95） > 订单号命中（90） > 金额+时间窗命中（60+10=70）
        ↓
③ 判定：
   最高分 ≥ 90 且与次高分差距 ≥ 20  → 自动匹配（AUTO_MATCHED）
   最高分 60~89                    → 候选待确认（进入人工队列，但可一键采纳）
   最高分 < 60 或多候选接近        → 不自动匹配（UNMATCHED，进人工）
        ↓
④ 匹配成功 → 更新 expected_receipts.status / 流水标记 / 台账状态
        ↓
⑤ 触发释放层（§4）
```

**为什么要有"次高分差距"判定**：如果 VIN 匹配得 95 分、订单号匹配得 90 分，
两者指向**同一台车**——没问题。但如果指向**不同台车**，说明数据矛盾，
必须人工裁决，不能随便挑一个。

### 3.5 多台车同笔回款的拆分

**这是账户安排决定的必然情况**（见 §1.4）：采用口座振替/自动払出し时，
经销商可能把多台车的回款**打包汇一笔**。

```sql
CREATE TABLE payment_allocations (
    id              BIGSERIAL PRIMARY KEY,
    transaction_id  BIGINT NOT NULL REFERENCES payment_transactions (id),
    expected_receipt_id BIGINT REFERENCES expected_receipts (id),
    vin             VARCHAR(32) NOT NULL,
    allocated_amount BIGINT  NOT NULL,      -- 分配到该车的金额
    allocation_type VARCHAR(16) NOT NULL,    -- AUTO 自动分配 / MANUAL 人工拆分
    allocated_by    VARCHAR(64),
    allocated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    note            VARCHAR(500)
);

CREATE INDEX IF NOT EXISTS idx_palloc_txn ON payment_allocations (transaction_id);
```

**自动拆分算法**（按优先级贪心）：
```
剩余待分配金额 = 流水金额
按 expected_receipts.due_date 升序（先到期先分配）
循环：
  找到金额 ≤ 剩余待分配金额 且状态为 PENDING 的最早到期应收
  若找到 → 分配，剩余 -= 分配额，继续
  若找不到 → 剩余金额作为「未分配余额」，进人工（预警 MULTI_VIN_SPLIT）
```

**拆分后校验**：分配金额之和必须等于流水金额。差值不为零 → 人工处理。

### 3.6 匹配不上怎么办（人工兜底）

**不是失败，是转人工**。贷后人员在工作台看到：
- 该笔流水的金额、付款人、摘要、入账账户
- 该账户下所有待回款的应收记录（VIN、销售日、应收金额、到期日）
- 系统给出的**候选建议**（按分数排序，含命中理由）

人工裁决后：
- 绑定到某台车 → `MANUAL_MATCHED`，记 `matched_by`（自然人，进审计）
- 判定为非本业务 → `IGNORED`，记原因（**这个判断本身有价值**——
  说明这个账户混入了其他生意，是账户安排问题）
- 金额拆分 → 走 `payment_allocations` 手工分配

### 3.7 匹配成功的联动（跨三本台账）

用户列的四条联动，逐条对应到现有表：

| 联动 | 现状 | 设计 |
|---|---|---|
| **VIN 台账**：已售未回款 → 已回款 | `collateral_ledger.repaid` / `repaid_at` / `repaid_amount` ✅ 字段已在 | 匹配成功时写 `repaid=true` + 金额 + 时间 |
| **融资台账**：占用额度减少，本金/利息冲销 | `repayments` 表 ✅ 已有（`principal` / `interest` / `total_amount` / `account_ref` / `designated_use`） | 生成 `repayments` 记录，`account_ref` 写流水所属账户，`designated_use=true` |
| **担保物台账**：该 VIN 解除担保 | `collateral_ledger.released` ✅ 已有 | **注意：不是自动解除，是触发抹消待办**（见 §4.2） |
| **流水表**：标记已匹配 | `payment_transactions.match_status` ✅ 本设计新增 | — |

> **⚠️ 一个必须说清的细节**：担保的**实体权利**在债务还清时消灭，
> 但**登记簿上仍挂着**（让渡担保的抹消登记需权利人与登记义务人共同申请）。
> 所以"回款匹配成功 → 解除担保"这个说法需要精确化：
> **自动发生的是「担保实体权利消灭 + 生成抹消登记待办」**，
> 而不是"担保从登记簿上消失"。后者是双方共同去法务局办的事。
> 这正是担保物台账用 `cancellation_status` 状态机（而非布尔位）的原因。

### 3.8 额度释放的时点

**关键设计决策**：额度什么时候恢复？

| 时点 | 释放 | 理由 |
|---|---|---|
| 流水到账 | ❌ 不释放 | 钱到了不等于钱是给我们的——可能匹配错了、可能是其他业务 |
| **匹配成功** | ✅ **释放** | 已确认这笔钱对应这台车，且落在指定账户 |
| 结清完成 | ✅ 全额释放 | 与匹配成功时点基本重合 |

**理由**：如果到账即释放，一次误匹配就释放了额度，风险敞口立刻扩大。
**匹配成功才释放**是唯一安全的时点。

**释放动作**（沿用既有逻辑）：
```
credit_lines.used_amount -= 本金部分
vehicle_units.principal_balance -= 本金
vehicle_units.paid_principal += 本金
interest_ledger 相应调整
```

## 4. 释放层：回款确认后自动解押

### 4.1 自动执行清单

用户列的五项，逐条对应：

| # | 动作 | 现有实现 | 状态 |
|---|---|---|---|
| 1 | **扣减经销商融资余额** | `credit_lines.used_amount` / `vehicle_units.principal_balance` | ✅ 已有（`RepaymentApplicationService`） |
| 2 | **释放对应 VIN 的担保** | `collateral_ledger.released` + `registration_due` | ✅ 已有（V10） |
| 3 | **更新法务省登记关联的担保物清单** | `collateral_registration_batches.cancellation_status` → `REQUESTED` | ✅ 已有（V10，V11 修正语义） |
| 4 | **恢复经销商可用额度** | `credit_lines.used_amount` 扣减 | ✅ 已有 |
| 5 | **生成回款凭证和清算记录** | `repayments` + `collateral_evidence_links` | ⚠️ 部分（清算计算书待建） |

**新增**：把 5 步串成**一个事务内的编排**，由匹配服务调用。

### 4.2 释放的完整链路（含抹消）

```
匹配成功
  ↓
① 写 repayments（本金/利息拆分、account_ref、designated_use=true）
  ↓
② 更新 collateral_ledger：repaid=true / repaid_amount / repaid_at
  ↓
③ 更新 expected_receipts.status = FULFILLED
  ↓
④ 更新 vehicle_units：principal_balance 减少 / paid_principal 累加
  ↓
⑤ 释放额度：credit_lines.used_amount 减少
  ↓
⑥ 担保实体权利消灭：collateral_ledger.released=true / released_at / release_reason=SETTLED
  ↓
⑦ 抹消待办：批次 cancellation_status = REQUESTED（需双方共同申请）
  ↓
⑧ 证据链：写 collateral_evidence_links（流水ID / 回款凭证 / 销售凭证 / 匹配记录）
  ↓
⑨ 审计：audit_events 记录全链路（含匹配规则、置信度、匹配人）
```

**第⑦步是日本场景的关键**：债务还清了，但**登记簿上的让渡担保还在**，
金融公司的担保权仍可能影响经销商处置车辆。必须办抹消。
而抹消需**权利人（金融公司）+ 登记义务人（经销商）共同申请**——
所以系统只能生成待办，不能自动完成。

### 4.3 证据链留存（用户明确要求）

让渡担保下，债权人处置或清算时需要保留证据链。系统必须留存：

| 证据 | 载体 | 现状 |
|---|---|---|
| **销售凭证** | S3 附件 + `collateral_evidence_links` | ⚠️ 附件类型已有 `SALES_INVOICE_UPLOADED` 事件，但证据链挂接待做 |
| **回款流水** | `payment_transactions`（含 `raw_reference` 原始报文） | ✅ 本设计新增 |
| **VIN 匹配记录** | `payment_allocations` + `match_rule` / `match_score` | ✅ 本设计新增 |
| **额度释放记录** | `repayments` + `audit_events` | ✅ 已有 |
| **清算计算书** | S3 附件（PDF）+ `disposal_cases.loss_amount` | ⚠️ 附件类型已有 `DISPOSAL_EVIDENCE`，但清算计算书未定义 |

**为什么要存原始报文（`raw_reference`）**：若日后与经销商或终端客户发生争议，
"这笔钱到底备注了什么"必须能自证。只存解析后的字段不够——
解析规则会变，原始报文是唯一不可辩驳的证据。

### 4.4 释放失败的处置

匹配成功但释放过程失败（额度更新冲突、抹消批次异常）：

**不能静默失败**——钱已经到账并匹配上了，但额度没释放，是资损风险。

处置：
1. 事务回滚，`payment_transactions.match_status` 保持 `UNMATCHED`（不丢匹配结果）
2. 记录失败原因，生成 `RELEASE_FAILED` 预警（**强制工单**）
3. 人工处理后重跑释放（**释放动作必须幂等**——按 `transaction_id` 判重）

**释放幂等**：同一笔流水重复触发释放，不得重复扣减额度。
实现：释放前检查 `payment_transactions.match_status` 是否已是 `AUTO_MATCHED`/`MANUAL_MATCHED`；
或用 `repayments.idempotency_key`（该字段已存在）作为释放幂等锚点。

## 5. 预警规则：重点盯"已售未回款"

### 5.1 预警清单

用户列的 6 类 + 我补充的 2 类：

| 预警类型 | 触发条件 | 严重度 | 处理方式 | 工单 |
|---|---|---|---|---|
| **已售未回款** `SOLD_UNPAID` | DMS 推送已售，但 N 日无回款（默认按结算窗口 `settle_due_date`） | HIGH | 生成工单，催收跟进 | ✅ 强制 |
| **金额不匹配** `PAYMENT_AMOUNT_MISMATCH` | 回款金额明显低于销售价/应收 | MEDIUM | 人工复核（可能是部分还款或谈价） | 否（批量巡检） |
| **回款进入非指定账户** `PAYMENT_WRONG_ACCOUNT` | 经销商用其他账户收款 | **HIGH** | **风险升级**——违反合同约定 | ✅ 强制 |
| **多台车同笔回款** `MULTI_VIN_SPLIT` | 一笔钱对应多个 VIN 且自动拆分失败 | MEDIUM | 人工拆分 | ✅ 强制 |
| **回款长期未匹配** `PAYMENT_UNMATCHED` | 流水无法自动绑定 VIN | MEDIUM | 贷后跟进 | ✅ 强制 |
| **登记未抹消** `REG_CANCELLATION_DUE` | 融资已结清但未办抹消登记 | HIGH | 提醒办理 | ✅ 强制 |
| **账户异常** `ACCOUNT_ISSUE` | 指定账户停用 / 同步失败 / 类型为当座借越 | MEDIUM | 人工修正账户配置 | ✅ 强制 |
| **账户混用** `ACCOUNT_MIXED_BUSINESS` | 判定为非本业务的流水占比过高 | LOW | 账户安排问题，需与经销商协商 | 否（批量） |

### 5.2 "回款进入非指定账户"的判定

这是本设计**最有价值的一条预警**，但判定要精确：

| 情形 | 是否违规 | 判定依据 |
|---|---|---|
| 回款进**指定回款账户** | ✅ 合规 | `payment_transactions.account_ref` == `dealer_bank_accounts.account_ref`（`is_escrow=true`） |
| 回款进**经销商一般账户** | ⚠️ **违规**（除非合同约定该账户即回款账户） | 账户 `is_escrow=false` 但 `agreement_ref` 指向本合同 |
| 回款进**第三方账户** | 🚨 **严重违规** | 既非指定账户也非经销商名下——可能是私人账户 |
| **无法采集到其他账户的流水** | ❓ **无法判定** | 若只采集了指定账户的流水，其他账户的入账根本看不到 |

> **⚠️ 必须说清的现实限制**：
> **系统只能看到它采集到的账户的流水**。
> 如果经销商用私人账户收车款，系统**根本看不见这笔钱**——
> 这时"非指定账户预警"永远不会触发，系统会安静地等 N 天后报"已售未回款"。
>
> **这正是"账户安排"（§1.4）必须写进合同的原因**：
> 要么经销商把回款直接打到指定账户，
> 要么必须配合口座振替把资金归集到债权人可控账户——
> 否则系统没有技术手段发现资金 diversion（挪用）。
>
> 换句话说：**这个预警的有效性取决于账户安排，不取决于系统实现。**
> 这是设计中必须向业务方讲明的边界，不能给人"系统能管住资金挪用"的错觉。

### 5.3 预警的产出与联动

预警统一进 `risk_alerts` 表（贷后监管设计 §4.2），带：
- `metric_value` / `threshold_value`（阈值快照，可复现）
- `evidence_refs`（指向流水 ID / 台账行 / 合同附件）
- 去重计数 `occurrence_count` + 升级机制

强制工单的转单规则见贷后监管设计 §4.4。

## 10. 明确不做（有意边界）

| 项 | 原因 |
|---|---|
| **流水到账即释放额度** | 到账不等于钱是给我们的。误匹配会立刻扩大敞口。必须匹配成功才释放（§3.8） |
| **自动绑定低置信度流水** | 误匹配的后果是漏管一台车的敞口 + 误催收另一台车。两错都严重 |
| **系统阻止经销商用其他账户收款** | 技术上做不到（钱不进指定账户就看不见）。**这必须靠合同约定**（§5.2） |
| **抹消登记自动完成** | 日本实务需权利人与登记义务人**共同申请**法务局，系统只能生成待办 |
| **在流水表里存明文账号** | 沿用 ADR-007：账号只存密文 + 掩码，流水只存 `account_ref` |
| **以流水报文替代凭证归档** | 原始报文是自证材料，但不等于正式凭证（发票、合同、证明书）仍须独立归档到 S3 |

## 附录 A：匹配规则评分表

| 规则 | 命中条件 | 分值 | 需要人工复核 |
|---|---|---|---|
| VIN 命中 | 摘要含 VIN 且该 VIN 为已售未回款 | 95 | 否 |
| 订单号命中 | 摘要含 `order_no` | 90 | 否 |
| VIN 命中但台账状态不符 | 摘要含 VIN 但该 VIN 不在待回款列表 | 40 | ✅ 是 |
| 金额精确匹配 | 金额 == 应收金额（±1 日元） | 60 | 否（需与其他信号组合） |
| 金额近似匹配 | 金额在容差内 | 45 | 是 |
| 时间窗命中 | 入账日在售出后 N 日内 | 10 | 否（仅辅助） |
| 付款人是终端客户 | `payer_name` 与 DMS 客户记录匹配 | 20 | 否（仅辅助） |
| 账户不符 | 入账账户非指定回款账户 | — | **触发 `PAYMENT_WRONG_ACCOUNT`** |

**判定规则**：
```
自动匹配（AUTO_MATCHED）：
  最高分 ≥ 90  且  (次高分 − 最高分) ≤ −20（即最高分显著领先）
候选待确认：
  最高分 ∈ [60, 89)
转人工（UNMATCHED）：
  最高分 < 60  或  多个候选分数接近（差距 < 20）
```

## 附录 B：端到端时序（正常路径）

```
T0   DMS 推送「车辆已售 COLA001」
     → 写 domain_events(VEHICLE_SOLD)
     → 状态计算：collateral_ledger.sold=true, sold_at=T0
     → 生成 expected_receipts（应收 = 本金 + 利息，due_date = 结算窗口）
     → 若已过 N 日无流水 → SOLD_UNPAID 预警 + 工单

T1   终端客户向指定账户付款 ¥1,850,000，摘要「COLA001」
     → BANK_FETCH 采集（API/MT940）→ payment_transactions（UNMATCHED）

T2   PAYMENT_MATCH 触发
     → 规则打分：VIN 命中 95 + 时间窗 10 = 105；次高（金额 60）差距 45 ≥ 20
     → AUTO_MATCHED，match_rule=VIN_MATCH

T3   释放编排（单事务）
     → repayments（principal=1,850,000, interest=0, account_ref=指定账户, designated_use=true）
     → collateral_ledger.repaid=true, repaid_amount, repaid_at
     → expected_receipts.status=FULFILLED
     → vehicle_units.principal_balance=0, paid_principal=1,850,000
     → credit_lines.used_amount -= 1,850,000      ← 额度释放
     → collateral_ledger.released=true, release_reason=SETTLED
     → 批次 cancellation_status=REQUESTED         ← 抹消待办（双方共同申请）
     → collateral_evidence_links：流水 / 回款凭证 / 销售凭证
     → audit_events：匹配规则、置信度、匹配人（人工时）

T4   人工处理抹消
     → 双方共同申请法务局 → 上传抹消凭证 → completeCancellation
     → 批次 cancellation_status=DONE，registration_due=false
```

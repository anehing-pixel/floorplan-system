### 0.2 五个真实缺口

## 1. 分层规则模型（核心改造）

### 1.1 从单层到分层

**现状**：一条规则，所有超期车一视同仁。

**目标**：库存龄越大，强制还款压力越大——因为**残值跌得越快**。

```
现状（单层）：
  库存龄 ≥ 90 天 → 每 30 天还 10%（固定金额，生成时算死）

目标（分层）：
  0–60 天     正常     仅监控，不干预
  61–90 天    预警     提醒经销商加快销售（不生成还款计划）
  91–120 天   强制还款  余额 × 20%
  121–180 天  强制还款  余额 × 30%（递增）
  181–270 天  强制还款  余额 × 50%（递增）+ 冻结额度
  271 天以上  转违约处置
```

### 1.2 规则表设计（后台可配）

**沿用既有先例**：授信评级口径已经是「后台动态配置 + 即时生效」（`rating_configs` 表）。
递减规则同理——**改规则不改代码**，这是本项目已确立的口径。

```sql
CREATE TABLE aging_rule_tiers (
    id              BIGSERIAL PRIMARY KEY,
    rule_code       VARCHAR(48) NOT NULL DEFAULT 'STANDARD',
        -- 规则集代码（可为不同经销商/产品线配不同规则集）
    tier_no         INTEGER    NOT NULL,     -- 阶梯序号（1 起，递增）
    age_from_days   INTEGER    NOT NULL,     -- 库存龄下界（含）
    age_to_days     INTEGER    NOT NULL,     -- 库存龄上界（含）；-1 表示无上限
    action          VARCHAR(24) NOT NULL,
        -- MONITOR 仅监控 / WARN 仅预警 / REPAY 强制还款 / FREEZE_REPAY 强制还款+冻结额度 / DISPOSE 转违约处置
    amount_type     VARCHAR(24),
        -- BALANCE_RATIO 按余额比例 / FIXED_AMOUNT 固定金额 / VALUATION_RATIO 按估值比例 /
        -- DEALER_AGGREGATE 经销商整体压降（见 §1.4）
    amount_ratio    NUMERIC(10,6),           -- 比例（amount_type=BALANCE_RATIO / VALUATION_RATIO 时用）
    fixed_amount    BIGINT,                  -- 固定金额（JPY）
    period_days     INTEGER,                 -- 递减周期（天）；仅 REPAY 类动作有效
    grace_days      INTEGER NOT NULL DEFAULT 0,  -- 宽限期：到期后几天内还了不算逾期
    auto_deduct     BOOLEAN NOT NULL DEFAULT FALSE,  -- 是否自动划款
    enabled         BOOLEAN NOT NULL DEFAULT TRUE,
    updated_by      VARCHAR(64),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uk_aging_tier UNIQUE (rule_code, tier_no),
    CONSTRAINT chk_aging_action CHECK (action IN
        ('MONITOR','WARN','REPAY','FREEZE_REPAY','DISPOSE'))
);

CREATE TABLE aging_rules (
    id              BIGSERIAL PRIMARY KEY,
    rule_code       VARCHAR(48) UNIQUE NOT NULL,
    rule_name       VARCHAR(64) NOT NULL,
    version         VARCHAR(16) NOT NULL DEFAULT 'V1',
    scope           VARCHAR(16) NOT NULL DEFAULT 'ALL',
        -- ALL 全量 / DEALER 指定经销商 / RISK_GRADE 按评级 / PRODUCT 按产品线
    scope_value     VARCHAR(64),
    effective_from  DATE NOT NULL,
    effective_to    DATE,                    -- 规则失效（版本化，不影响存量计划）
    enabled         BOOLEAN NOT NULL DEFAULT TRUE,
    created_by      VARCHAR(64),
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

**规则版本化的意义**：`aging_plans.rule_version` 字段**已经存在**（当前都是 V1）。
改规则时生成新版本，**存量计划继续按老规则执行**——
避免"改了个参数，全场在跑的还款计划金额全变了"的资损风险。

### 1.3 阶梯匹配逻辑

```
每日巡检：
  对每台 status=IN_STOCK 且 financed=true 且 未结清的车：
    stockAge = 当前业务日 - stock_in_date
    tier = 查 aging_rule_tiers 中匹配 (stockAge ∈ [age_from, age_to]) 且 enabled 的阶梯
        （多规则集时按 scope 优先级：DEALER > RISK_GRADE > ALL）
    按 tier.action 分派：
      MONITOR  → 只更新 stock_age，不生成计划
      WARN     → 生成「库存龄预警」工单，不生成还款计划
      REPAY    → 生成/更新还款计划，按 tier 的金额与周期
      FREEZE_REPAY → 同 REPAY，同时冻结额度（§5.1）
      DISPOSE  → 不生成还款计划，转违约处置（§5.3）
```

**阶梯不重叠校验**：`age_from` / `age_to` 在同一规则集内不得交叉。
建议加启动期自检（沿用 `SqlStructureSelfCheck` 的做法）——阶梯重叠会导致匹配不确定。

### 1.4 四种应还金额口径

你的方案列了四种，系统层面应支持（不是一次全上，按优先级）：

| 口径 | 计算 | 适用 | 优先级 |
|---|---|---|---|
| **按余额比例** | `本金余额 × ratio` | 通用默认 | **P0** |
| **按固定金额** | `fixed_amount` | 小额车、或按车商谈判定的"每台还 X 万" | P1 |
| **按估值比例** | `估算残值 × ratio` | 与残值联动（残值跌得快就多还） | P2（依赖残值估算落地） |
| **经销商整体压降** | `经销商超期库存占用 × ratio` | 整体库存老化时一次性压降 | P2 |

**「按估值比例」的设计要点**：这是最符合业务逻辑的口径——
强制还款的目的是防残值跌破垫款，所以**该还多少应该由残值决定**，不是由天数决定。
但它依赖残值估算（一阶段用车龄+里程折旧曲线），所以排在 P2。

**「经销商整体压降」的实现**：不是逐台生成计划，而是生成**一条经销商级任务**：

```sql
CREATE TABLE dealer_aggregate_reductions (
    id            BIGSERIAL PRIMARY KEY,
    dealer_id     BIGINT NOT NULL,
    trigger_date  DATE   NOT NULL,
    overdue_ratio NUMERIC(10,6) NOT NULL,   -- 超期库存占该经销商在库库存的比重
    threshold_ratio NUMERIC(10,6) NOT NULL, -- 触发阈值
    required_amount BIGINT NOT NULL,        -- 应压降总额
    allocated     BOOLEAN NOT NULL DEFAULT FALSE,  -- 是否已按台分配
    status        VARCHAR(16) NOT NULL DEFAULT 'PENDING',
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

按台分配时，优先分配给**库存龄最长**的车（最紧急的先还）。

### 1.5 应还金额的动态重算（修 G2）

**关键设计**：`reduce_amount` **不能在计划生成时算死**。

改为：计划存**规则引用**（`rule_code` + `tier_no`），每期应还金额在**核销时按当前状态重算**：

```
每期应还金额 = f(当前本金余额, 当前库存龄对应的阶梯, 金额口径)
```

**为什么要动态**：
1. 库存龄跨过阶梯边界（90→120 天）时，比例要从 10% 变 20%
2. 前几期还了之后本金余额变了，按剩余余额算才对
3. 展期/豁免后规则可能变

**但要保留快照**：`curtailment_payments` 已有 `amount`，那是**当期实际扣了多少**，
天然是快照。历史核销不受重算影响。

**改造方式**：不推翻 `aging_plans`，加两列：

```sql
ALTER TABLE aging_plans ADD COLUMN IF NOT EXISTS rule_code VARCHAR(48);
ALTER TABLE aging_plans ADD COLUMN IF NOT EXISTS tier_no INTEGER;
-- reduce_amount 保留：作为"生成时的初始应还额"参考值，实际核销以重算为准
```

```sql
    ADD COLUMN IF NOT EXISTS rule_code     VARCHAR(48);     -- 规则集

    ADD COLUMN IF NOT EXISTS waived          BOOLEAN NOT NULL DEFAULT FALSE;
    ADD COLUMN IF NOT EXISTS waived_reason   VARCHAR(500);

    ADD COLUMN IF NOT EXISTS overdue_days    INTEGER NOT NULL DEFAULT 0;  -- 逾期天数
    ADD COLUMN IF NOT EXISTS last_deduct_at  TIMESTAMPTZ;   -- 上次自动划款时间
    ADD COLUMN IF NOT EXISTS deduct_fail_count INTEGER NOT NULL DEFAULT 0; -- 连续划款失败次数

```

**`waived_until` 是关键**：豁免必须有**有效期**。
没有有效期，豁免就变成永久的——经销商只要豁免一次，这台车永远不再被催。
你的分析里提到"避免被滥用"，落地就是靠这个字段 + 到期自动恢复催款。

### 2.3 计划状态机

```
        生成计划
           │
           ▼
      ┌─────────┐  到期未还   ┌──────────┐
      │ ACTIVE  │────────────►│ OVERDUE  │
      └────┬────┘             └────┬─────┘
           │                       │ 豁免获批
           │ 部分还款               │
           ▼                       ▼
      ┌─────────┐             ┌─────────┐
      │ PARTIAL │             │ WAIVED  │──(豁免到期)──► ACTIVE
      └────┬────┘             └─────────┘
           │ 还清
           ▼
      ┌──────────┐   转违约处置   ┌───────────┐
      │COMPLETED │──────────────►│ DEFAULTED │
      └──────────┘               └───────────┘
```

| 状态 | 含义 | 系统行为 |
|---|---|---|
| `ACTIVE` | 进行中，未到期待还 | 到期前发提醒 |
| `PARTIAL` | 部分还款 | 继续累计 |
| `OVERDUE` | 到期未还（含宽限期） | **升级路径启动**（§5） |
| `WAIVED` | 豁免中 | 暂停催款，到期自动恢复 |
| `COMPLETED` | 已还清 | 解除所有催收动作 |
| `DEFAULTED` | 已转违约处置 | 移出递减流程，交处置岗 |

**注意 `DEFAULTED` 是终态**：转违约后递减流程不再管这台车——
否则两个流程会同时要求还款（流程冲突）。

## 3. 扣款方式（补 G3：自动划款）

### 3.1 四种扣款路径

你列的四条，按自动化程度排序：

| 路径 | 自动化 | 现实可行性 | 优先级 |
|---|---|---|---|
| **回款抵扣** | ✅ **全自动** | ⭐⭐⭐ 最现实——回款本来就进指定账户，到账即抵扣 | **P0** |
| **自动划款（口座振替）** | ✅ 全自动 | ⭐ 需经销商授权 + 银行支持 | P1 |
| **指定振込** | ⚠️ 半自动（系统提醒+人工确认到账） | ⭐⭐⭐ 最通用 | **P0**（做成工单+提醒） |
| **额度冻结** | ✅ 全自动 | ⭐⭐⭐ 无外部依赖 | **P0** |

### 3.2 回款抵扣（P0，最应该先做）

**逻辑**：台账里的「已售未回款」车，回款到账后，**优先抵扣该车的强制还款义务**。

```
回款匹配成功（见《回款闭环与资金监管设计》§3.7）
    ↓
查该 VIN 是否有 OVERDUE 的递减计划
    ↓
有 → 从回款金额中扣减应还额 → 写入 curtailment_payments（自动，actor='system'）
    → 剩余部分才作为正常还款核销（释放额度）
    ↓
无 → 全部作为正常还款核销
```

**为什么优先做这条**：它**零外部依赖**——钱已经在系统里了。
而且它符合业务实质：这台车本来就该被强制还款，回款来了先还它天经地义。

**与「释放额度」的顺序问题**：

```
回款 1,850,000，其中强制还款应还 500,000
  → 先扣 500,000 强制还款（本金减少 500,000，**不释放额度**——部分还款仍占用）
  → 剩余 1,350,000 继续核销，若能结清 → **释放额度**
```

**关键**：强制还款是**部分本金偿还**，不释放额度（与现有 `CurtailmentApplicationService` 的设计一致——
它明确不写 `credit_lines.used_amount`）。这个不变量要保持。

### 3.3 自动划款（P1）

**前置条件（三者都要有）**：
1. 经销商与债权人签有**口座振替授权**（合同层面）
2. 银行侧支持扣款接口或文件指令
3. 经销商账户有足够余额

**流程**：
```
每日扣款窗口（建议 03:00 JST，避开日终计息）
  ↓
取所有 status=OVERDUE 且 waived=false 且 auto_deduct=true 且扣款次数 < N 的计划
  ↓
生成扣款指令（金额 = 当期应还 + 逾期罚息）
  ↓
提交银行（MT940 反向指令 / 银行 API / 文件）
  ↓
结果：
  成功 → 写 curtailment_payments（actor='system'）→ 推进计划
  失败 → deduct_fail_count++ → 连续失败达 N 次 → 生成工单（贷后联系经销商）
```

**幂等**：扣款指令必须带幂等键（`plan_id + 期号 + 业务日`），
防止银行侧重复执行导致重复扣款。

**失败兜底**：连续失败不自动升级（避免因系统故障误判经销商违约），
只生成工单。**连续失败 3 次后由人工判断**是系统问题还是经销商问题。

### 3.4 指定振込（P0，做成工单）

无法自动划款时的默认路径：

```
计划到期 → 生成「强制还款通知」工单（给催收岗）
  ↓
催收岗联系经销商，告知应还金额、截止日、收款账户（指定回款账户）
  ↓
经销商汇款到指定账户 → 银行流水采集 → 回款匹配 → 自动抵扣（§3.2）
  ↓
若经销商汇到非指定账户 → PAYMENT_WRONG_ACCOUNT 预警（见回款闭环设计 §5）
```

**通知的证据留存**：催收通知本身是证据（证明已尽到催收义务），
应作为附件归档到 S3，挂进 `collateral_evidence_links`。

### 3.5 额度冻结（P0）

这是**施压手段**，不是催款手段：

```
逾期超过宽限期（grace_days）且未还
  → credit_lines.frozen_amount += 未还强制还款总额
  → credit_lines.status = FROZEN（若有该状态）
  → 新增放款申请被拒（额度不足）
```

**关键**：冻结的额度**在还款后必须解冻**——否则经销商还了钱额度却没恢复，
是明显的系统缺陷。

```
强制还款核销成功
  → credit_lines.frozen_amount -= 本次还款额（不小于 0）
  → 全部还清且无其他逾期 → 恢复 status = ACTIVE
```

**已有基础**：`credit_lines.frozen_amount` 字段已存在，
`AnnualReviewApplicationService` 已在用它（年审冻结）。
本设计是**第二个使用方**——同一字段不同场景，语义要分清：

| 场景 | 触发方 | 解冻条件 |
|---|---|---|
| 年审冻结 | `annual_reviews` | 年审通过 |
| **超期未还冻结** | `aging_plans`（本设计） | 强制还款还清 |

建议在 `credit_lines` 加 `frozen_reason` 字段区分，否则无法知道额度为什么被冻。

## 4. 豁免机制（补 G4）

### 4.1 为什么必须有

你的分析说得很准：「实务上不可能所有车都机械处理」。

具体场景：
- **主机厂调拨中**：厂家把车调给另一个经销商，途中/待售，不该催款
- **已签销售合同但未交车**：车还在经销商手里，但已有买家，只等过户
- **车辆正在整备/运输**：清洗、整备、跨店调拨中
- **经销商已提供额外担保**：风险已缓释
- **债权人同意展期**：商业安排

**不豁免的后果**：系统会逼经销商**造假**（比如把车标成已售来躲避催款），
或者在不该催的时候催，损害客户关系。**数据一旦被逼出来就不真了**——
这比少收一笔还款严重得多。

### 4.2 豁免申请与审批

```sql
CREATE TABLE aging_waivers (
    id            BIGSERIAL PRIMARY KEY,
    waiver_no     VARCHAR(32) UNIQUE NOT NULL,
    plan_id       BIGINT NOT NULL REFERENCES aging_plans (id),
    vin           VARCHAR(32) NOT NULL,
    dealer_id     BIGINT NOT NULL,
    waiver_type   VARCHAR(24) NOT NULL,
        -- OEM_REALLOCATION 主机厂调拨中 / CONTRACTED_NOT_DELIVERED 已签约未交车 /
        -- IN_PREPARATION 整备运输中 / ADDITIONAL_SECURITY 追加担保 / EXTENSION_AGREED 同意展期
    reason        VARCHAR(500) NOT NULL,
    evidence_attachment_id BIGINT,          -- 证据附件（合同/调拨通知/整备单）
    valid_from    DATE NOT NULL,
    valid_until   DATE NOT NULL,            -- 有效期（必填，强制）
    status        VARCHAR(16) NOT NULL DEFAULT 'PENDING',
        -- PENDING 待审批 / APPROVED 已批准 / REJECTED 已驳回 / EXPIRED 已到期 / REVOKED 已撤销
    applicant     VARCHAR(64) NOT NULL,     -- 申请人（催收岗或经销商对接人）
    approver      VARCHAR(64),              -- 审批人（贷后管理岗）
    approved_at   TIMESTAMPTZ,
    reject_reason VARCHAR(500),
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS idx_waiver_plan ON aging_waivers (plan_id, status);
CREATE INDEX IF NOT EXISTS idx_waiver_expiry ON aging_waivers (valid_until)
    WHERE status = 'APPROVED';
```

### 4.3 豁免的边界（防滥用）

| 约束 | 规则 | 理由 |
|---|---|---|
| **有效期必填** | `valid_until` 不可为空，且 ≤ 180 天 | 永久豁免等于免催款 |
| **证据必填** | `evidence_attachment_id` 必填（除 `EXTENSION_AGREED`） | "已签约未交车"要有合同；"调拨中"要有调拨通知 |
| **审批人 ≠ 申请人** | 申请人与审批人不能同一人 | **延续角色体系的自然人级 SOD** |
| **单台累计豁免次数** | 同一 VIN 累计豁免 > 3 次 → 升级告警 | 反复豁免说明规则对该车不适用，应调规则而非反复豁免 |
| **豁免不释放既有逾期** | 豁免期内不催款，但**逾期记录保留**，恢复时立即计算逾期天数 | 不能靠豁免洗白历史 |
| **豁免到期自动恢复** | `valid_until` 到期 → 计划回 `ACTIVE`，逾期天数继续累积 | 豁免是缓刑不是赦免 |

**「单台累计豁免次数超限 → 升级告警」是重要的设计**：
它把"人工反复豁免"这个滥用模式**显性化**——
贷后管理岗会看到"这台车已经被豁免 3 次"，从而反思是不是规则不对。

### 4.4 豁免与额度冻结的关系

**关键问题**：车被豁免了，但额度还冻着吗？

**建议**：豁免**不自动解冻额度**，但**触发一次人工复核**。

理由：豁免的是"催款动作"，不是"风险消失"。车还在库里占着额度，
风险敞口依然存在。只是暂不催款而已。额度冻结应等**还款或处置**解除。

但这会造成经销商投诉（"我申请了豁免但还是不能放款"），所以：
**豁免审批时必须明确告知"额度冻结不随之解除"**，并在工单里写清楚。

### 4.5 豁免的完整流程

```
① 触发：
   催收岗发现该车不应催款 → 提交豁免申请（选类型 + 理由 + 上传证据 + 填有效期）
② 审批：
   贷后管理岗审批（不同人）→ 批准 / 驳回（驳回须填理由）
③ 生效：
   计划 status = WAIVED，记录 waived_until
   生成「豁免生效」审计 + 通知经销商
④ 到期：
   每日巡检检查 waived_until < 今日 → 计划回 ACTIVE
   恢复时按当前库存龄重算阶梯（可能已进入更严的阶梯）
⑤ 监控：
   累计豁免次数超限 → 生成告警（人工复盘规则）
```

## 5. 未还款升级路径（补 G5）

你的分析给了三级升级：「冻结新增额度 → 限制释放已售车辆担保 → 进入违约处置流程」。

**这三级设计得很对**，尤其第二级——**限制解押出库**是极强的施压手段：
车要卖、要交付，但解押被卡住，经销商会感受到实际损失。

### 5.1 三级升级的实现

| 级别 | 触发条件 | 动作 | 解除条件 |
|---|---|---|---|
| **L1 冻结额度** | 逾期 > 宽限期 | `credit_lines.frozen_amount += 未还额`；新放款被拒 | 还清强制还款 |
| **L2 限制解押** | 逾期 > 宽限期 + 30 天（阶梯 `FREEZE_REPAY`） | 已售车的**解押出库被阻**——`settle` 与 `releaseSecurity` 前置校验 | 还清或豁免获批 |
| **L3 转违约处置** | 逾期 > 阶梯 `DISPOSE` 边界（默认 270 天） | 生成 `disposal_cases` 工单，交违约处置岗 | 处置闭环完成 |

**L2 的实现位置**：在 `RepaymentApplicationService.settle` 与
`SalesApplicationService.releaseSecurity` 前置检查该 VIN 是否有 `OVERDUE` 且未豁免的递减计划。
若阻止，需返回明确错误码（如 `CURTAIL_003`）并附原因。

**L2 的风险提示**：L2 会**卡住客户的正常业务**（车卖了但结不了清）。
这是有意为之的施压手段，但必须有**人工放行通道**——
否则系统可能在业务上造成不可挽回的损害（比如终端客户已付款、车却交付不了）。

**建议**：L2 阻止时**同时生成一个高优先工单**，贷后岗可人工放行（记审计）。
"系统自动卡 + 人工可放"是这类强干预的标准做法。

### 5.2 升级的状态与幂等

**幂等要求**：同一台车**不能被重复升级**。

```
判定：查该 VIN 是否已有 OVERDUE 的递减计划
  有 → 说明已进入升级流程，不再重复触发
```

升级动作本身要幂等（如 `frozen_amount += X` 重复执行会累加错误）。
**建议**：升级时记录 `aging_plans.escalation_level`（0/1/2/3），
按 level 判断而非按"是否已冻结"判断。

### 5.3 转违约的衔接

```
L3 触发 → 生成违约处置工单（order_type = DISPOSAL）
  ↓
违约处置岗接手（DisposalApplicationService 现有闭环）
  ↓
处置结案 → collateral_ledger.released = true
         → 递减计划 status = DEFAULTED（终态，移出催收流程）
         → 额度处理（按处置结果：变现收入冲减，损失部分核销）
```

**关键**：`DEFAULTED` 之后递减流程不再管这台车——
否则两个流程会同时要求还款（流程冲突），且处置可能已把车变现，
继续催"还款"是无意义的。

| 文档 | 关系 |

## 12. 明确不做（有意边界）

| 项 | 原因 |
|---|---|
| **系统自动批准豁免** | 豁免是风控判断，必须人工。系统只提供申请与证据留存 |
| **豁免自动解冻额度** | 豁免的是催款动作，不是风险消失。车还在库里占着额度 |
| **划款失败自动升级违约** | 失败可能是系统故障或银行维护，不是经销商问题。只工单，人工判断 |
| **强制还款释放额度** | 部分本金偿还，额度仍占用。只有结清才释放（与现有实现一致） |
| **在库里按天写减免计划** | 阶梯跨档时才调整，不按天生成。避免计划表膨胀 |
| **已售未回款的车参与递减催款** | 车已交付终端客户，催经销商还款无意义（但该车的**融资期限逾期**由《贷后监管》§1.2 的期限模型管） |
| **用强制还款计划替代融资期限逾期判定** | 两者是不同维度：递减按**库存龄**，期限按**合同到期日**。一台车可以不卖但已超合同期限（这才是更危险的情形） |

## 附录 B：端到端时序（一台车超期未还）

```
T0  放款确认，stock_in_date = T0
T0+90  AGING_RULE_SCAN → 匹配 T3（91–120 档，还 20%）
       → 生成 aging_plans（rule_code=STANDARD, tier_no=3, trigger_stock_age=91）
       → 生成「库存龄预警」工单（提醒经销商加快销售）
T0+91  计划 next_due_date = T0+91+30
       → 经销商未主动还款
T0+120  跨入 T4 档（还 30%）→ 应还额动态重算
T0+121  AGING_ESCALATE → 逾期天数 > 宽限期 → L1 冻结额度
       → credit_lines.frozen_amount += 未还额，frozen_reason=CURTAILMENT_OVERDUE
       → 生成「超期未还」工单（催收岗）
T0+122  催收岗提交豁免申请（已签约未交车 + 合同附件 + 有效期 60 天）
       → 贷后管理岗审批（≠申请人）→ 批准
       → 计划 status = WAIVED，waived_until = T0+182
T0+182  AGING_WAIVER_EXPIRE → 计划回 ACTIVE
       → 库存龄已 182 天 → 匹配 T5（还 50% + 冻结额度）
       → 逾期天数继续累积（豁免不洗白历史）
T0+183  经销商汇款 ¥600,000 到指定回款账户
       → BANK_FETCH 采集 → 流水入账
       → PAYMENT_MATCH → VIN 命中（95 分）→ AUTO_MATCHED
       → 命中 OVERDUE 计划 → **回款抵扣**：扣 600,000 强制还款
       → 写 curtailment_payments（source=AUTO_DEDUCT, payment_transaction_id=...）
       → 计划推进，paid_amount 累加
       → 扣款成功 → credit_lines.frozen_amount -= 600,000
       → 若已还清全部应还 → 计划 COMPLETED，预警解除，额度恢复
       → （若能覆盖全台余额 → 走正常还款核销 → 释放额度）
```

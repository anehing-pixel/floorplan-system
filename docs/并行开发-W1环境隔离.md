## 1. 为什么必须隔离（实测到的三种互相踩踏）

十个服务在本地**共用一个 PostgreSQL 库（宿主 5434，容器 `floorplan-db2`）和一个 8080**。并行时：

| 踩踏 | 后果 |
|---|---|
| 两个 agent 同写 `outbox_events` / `event_consumptions` / `consumer_offsets` | 游标只有一个（按 `consumer` 一行）。A 的 `loan-service` 把游标推到 100，B 刚插的事件 1–99 **永远不会被 B 的实例消费**，B 的冒烟表现为「60s 等不到 DONE」，而代码是对的 |
| 两个 agent 同用 8080/8081/8085… | 后起的服务直接绑定失败；更坏的情况是端口被**上一轮没清干净的旧 jar** 占着，请求打进别人的旧代码，测出一条不存在的 bug |
| 两边都往 `public` 造测试数据 | 计数类断言（`count(*)`、`max(id)`）随对方写入漂移，冒烟时绿时红 |

结论：**schema 隔离数据、偏移量隔离端口**，两者一起做才叫隔离。只改端口不改库 = 还在共表。

## 2. 硬约束一：连接串必须是 `<schema>,public`，不能只写 `<schema>`

这是实测出来的，不是风格选择：

```bash
export SPRING_DATASOURCE_URL='jdbc:postgresql://localhost:5434/floorplan?currentSchema=w1_loan,public'
```

V5 迁移用到 pgcrypto 的 `gen_salt()`，而这个扩展装在 **public** 里（`SELECT extnamespace FROM pg_extension …` 可复核）。
只把 search_path 设成 agent schema 时，Flyway 走到 V5 就报：

```
FUNCTION gen_salt(unknown, integer) does not exist
```

迁移**中止但已建的表留着**。实测那次半途中断后 schema 里只剩 23 张表，服务照样能起来——
查询不到就顺着 search_path 掉回 `public` 拿到别人的数据，冒烟全绿，而这份绿是假的。
所以第二个 `,public` 是功能必需的，同时 `agent_env.sh check` 会把「表数 == 67」作为门槛卡掉半成品 schema。

> `check` 现在卡的是**三条 schema 本地判据**：表数、`${SCHEMA}.flyway_schema_history` 里的 V25+V26、
> `${SCHEMA}` 里有没有 V5 建的 `users`。历史表计数**必须带 schema 限定名**——不带就顺 `search_path`
> 落到 `public`，一个从没迁过的空 schema 也报「2/2」，这道闸等于只剩表数一条腿（W0-9，2026-11-22 修）。
> `gen_salt` 那一项按设计装在 public，它只证明「本会话解析得到这个函数名」，**不是本地判据**，
> 别拿它的恒真当 schema 迁好了的证据。

> ⚠️ **67 会过期，而且是「主干涨了」这种正常过期。** 67 = V1–V26 全部应用后的 `public` 基准（2026-11-22 实测）。
> **二手车（USED）改造并行期门槛不同**：它从 V40 起跳，每落一个交付包基准表数依次是
> **73 / 84 / 89 / 94 / 96**（W-U1…W-U5，映射与阶梯见 `docs/二手车库存垫资改造-04-数据库设计.md §2 / §2.1`
> 第 104–108 行；号段登记在 `PROGRESS.md §2` 的 USED 行）。
> **但 USED 现在还是设计态、零 `.sql` 未落库**，所以今天主干基准仍是 67，别提前按 84 设。
> 脚本已支持覆盖，不必改代码：`FLOORPLAN_PUBLIC_TABLES=84 bash scripts/agent_env.sh check <你的名字>`。
>
> 于是 `check` 报「表数不对」有两种完全不同的病因，先分清再查：
> **① 少于当前基准** → 多半是 V5 那类半途中断，schema 是残的，**这个 schema 不能用**（本节本意，
> 重跑一次 `init` + 起 web 让它把迁移补齐）；
> **② 恰好等于USED阶梯里的下一个数** → 主干基准涨了，你没做错任何事，**按当期阶梯设环境变量即可**，
> 别去改 `agent_env.sh` 里的默认 67（那是 `public` 主干侧的基准，W1 波次还在用）。

## 3. 硬约束二：脚本和服务必须走同一个 search_path

冒烟大量用 `psql` 读库核对真实状态（`event_consumptions` / `consumer_offsets` / `outbox_events`）。
如果服务写 `w1_loan`、脚本读 `public`，脚本会读到另一套数（或空表），断言立刻失真。

`agent_smoke_lib.py` 用 `FLOORPLAN_DB_SCHEMA` 统一这一件事，**给脚本的是 `PGOPTIONS`，不是 `SET search_path`**：

```python
SEARCH_PATH = '%s,public' % DB_SCHEMA          # 逗号后不能有空格
env["PGOPTIONS"] = "-c search_path=%s" % SEARCH_PATH
```

两个都是踩过的坑：

- `psql -c "SET search_path TO x; SELECT ..."` 会把 `SET` 这个命令标签打进 stdout，
  `psql_one()` 拿到的第一行是 `"SET"`，于是 `int(…)` 抛 `ValueError` 或返回错值。
- `PGOPTIONS="-c search_path=w1_demo, public"`（逗号后有空格）→
  `FATAL: invalid value for parameter "search_path": "w1_demo,"`，服务连不上库。

### 3.1 服务没起时返回 `st == 0`，不抛栈

隔离后每个 agent 只起自己要用的那几个进程，别的偏移端口上是空的。
`agent_smoke_lib.call()` 于是把**传输层失败**（连接被拒 / 超时）也收敛成返回值：

```python
return 0, {"code": "TRANSPORT_ERROR", "message": "GET http://127.0.0.1:8183/… → URLError: …"}
```

HTTP 状态码没有 0，所以 `st == 0` 明确区分「进程没在跑」和「进程在跑但报错」。
这不是舒适性问题：初版让一条可选的「现状登记」打印在 8183 没人监听时直接崩栈，
整轮冒烟中断，连带末尾的清理都没执行——脏事件行留在 schema 里，下一轮的计数断言就开始漂。
所以同批加了 `atexit` 注册的清理（`smoke_w0.py:cleanup_rows`），崩溃路径也保证删自己的行。

必需进程（web / auth / loan）仍然在预检硬中止：`login()` 拿到 `st == 0` 就抛
`RuntimeError("预检失败：登录未通过…")`，宁可当场停，也不让几十条断言红成一片。

### 3.2 守卫断言（隔离场景 2 条 / public 场景 1 条）

`scripts/smoke_w0.py` 头部与清理段各钉一枚闸：

```
[PASS] 隔离生效：会话 current_schema 就是目标 schema
[PASS] public.outbox_events 未被本次运行改动
```

第二条的判据不是「我的 schema 干净」，而是「**public 一行都没被碰到**」。
它挂了说明服务连的还是 public，那一轮所有断言都不作数。未设 `FLOORPLAN_DB_SCHEMA`
（跑 public 主干回归）时自动跳过，只打印提示。

## 4. 端口偏移分配（开工前自行核对占用）

| Agent | 偏移 | web | auth | loan | 网关 |
|---|---|---|---|---|---|
| 单人主干跑（W3 收口 / 只有一个人干活） | `0` | 8080 | 8081 | 8085 | **18080** |
| W1-LOAN | 100 | 8180 | 8181 | 8185 | 18180 |
| W1-BANK | 200 | 8280 | 8281 | 8285 | 18280 |
| W1-CREDIT | 300 | 8380 | 8381 | 8385 | 18380 |
| W1-RELEASE | 400 | 8480 | 8481 | 8485 | 18480 |
| W1-COLLATERAL | 500 | 8580 | 8581 | 8585 | 18580 |
| W2-* | 600 | 8680 | 8681 | 8685 | 18680 |

**先核端口再启动**（表里只是排期，别的 agent 可能已经占走）：

```bash
netstat -ano | grep -E "81[0-9][0-9]|18180" | grep LISTEN
```

偏移 0 只有在「当前只有我一个人干活」时才用，否则等于加入踩踏。

启动命令照抄 `agent_env.sh env` 输出末尾的注释行，每行都带 `env -u SERVER__PORT`
（WorkBuddy 注入的 `SERVER__PORT` 会被宽松绑定成 `server.port`，把全部服务挤到同一个端口）：

```bash
env -u SERVER__PORT SERVER_PORT=8180 java -jar web/target/floorplan-web-1.0.0-SNAPSHOT.jar > logs/w1_loan/web.log 2>&1 &
```

服务间调用靠 `FLOORPLAN_CLIENTS_*_URL`（已随偏移量一起给出）。**不注入就会打到 `application.yml`
里的默认值 8081/8083/8085/8086**，也就是隔壁 agent 的进程——这是 W0 那轮实测到的串台路径。

## 5. 合并后的主干全量回归：回到唯一的 `public`

用户定的规矩：**并行期各分一个 DB schema，功能合并以后用唯一一个主 db schema 跑一次全量 test。**

W3 收口时的做法是「什么都不设」——`FLOORPLAN_DB_SCHEMA` 空值就是主干回归模式：

```bash
unset FLOORPLAN_DB_SCHEMA SPRING_DATASOURCE_URL          # 连 jdbc:…:5434/floorplan 的 public
env -u SERVER__PORT PYTHONIOENCODING=utf-8 bash run-microservices.sh smoke   # 偏移 0，全服务 + 全量断言
```

`PYTHONIOENCODING=utf-8` 不是可有可无：Windows 控制台默认 GBK，`smoke-test.py` 的断言文案里
有圈号（㉓ 之类）会直接 `UnicodeEncodeError` 把整轮冒烟炸在打印那一步。
脚本调的是 `python3`，本机只有 miniconda `python` 的话还要给一个 `python3` 转发（PATH 前置，别改共享脚本）。

- `run-microservices.sh` 里搜不到这些变量（`grep -n FLOORPLAN_DB_SCHEMA\|SPRING_DATASOURCE_URL run-microservices.sh` 为空），
  但**它起的 JVM 会继承当前 shell 的环境**——Spring 认 `SPRING_DATASOURCE_URL`。所以那两行 `unset` 是必需的，
  不是排版：忘了 unset，整条「主干全量回归」其实跑在别人留下的 schema 上。
- `run-microservices.sh` 是共享冻结文件，不为了让它支持偏移量而改它；
- `agent_env.sh` 只负责并行期的隔离与清理，主干回归绕开它；
- 冒烟断言里的 schema 感知逻辑保证同一份脚本两边都能跑（public 模式打印提示，隔离模式加 2 条守卫断言）。

**并行期的绿不能替代合并后的绿。** schema 隔离解决的是「别互相踩」，不是「集成没问题」：
各 agent 在自己的 schema 里全绿，合并后仍可能因为迁移顺序、共享 seed、跨服务契约漂移而失败。
合并后那一次 public 全量回归才是交付判据（AGENTS 铁律 2）。

## 6. 回收

```bash
bash scripts/agent_env.sh drop w1_loan    # 必须逐字重打 schema 名；DROP SCHEMA … CASCADE 只作用于该 schema
```

删之前先停掉自己那一轮的服务（它们仍占着这个 schema 的连接）。
不要为了「省事」复用别人的 schema：`check` 会告诉你表数对不对，但不会告诉你里面有没有别人的游标和事件。

## 7. 遗留与边界（如实说明）

1. **建 schema 是分钟级**（26 个迁移全跑，其中 5 个带 seed INSERT：V3 评分配置 / V5 账号 / V6 经销商画像与角色 / V8 用户角色 / V9 角色账号）。每人每分支一次，别在冒烟循环里重建。
2. **只隔离 DB 与 HTTP 端口，不隔离仓库**。`git worktree` 仍是唯一必需的代码隔离手段
   （见多Agent并行开发拆分方案）；分支、迁移号段、写入集纪律照原样适用。
3. **Flyway 在每个 schema 各建一份 `flyway_schema_history`**，这正是隔离想要的（V26 在 `public` 成功
   不代表在 `w1_loan` 成功，`smoke_w0.py` 查的是当前 schema 那张）。
4. **`public` 里已有的脏数据不迁移、不清理。** 隔离只对新建 schema 生效；主干 `public` 的整理属 W3 收口范围。
5. **共库带来的跨服务直读别人的表**（AGENTS 明令禁止新代码这么写）在 schema 隔离下**变得更扎手**：
   表还在同一个库里，代码「能跑」，只是读到了别人的行。隔离不解决这个，只有 outbox/Feign 接线解决。
6. 未验：多 agent 同时建 schema 的并发（各建各的 schema，理论上无锁冲突）、`drop` 时仍有活动连接
   （`DROP … CASCADE` 会被挡，先停服务）。

### 8.1 W0-9 修复后的复核（2026-11-22 15:00，基线 = `7360e1b` 之后）

新建 `w0_v9` → 起 web/auth/loan（`currentSchema=w0_v9,public`，偏移 0）→ Flyway 实测把
**历史表也建进了 agent schema**，所以加严后的判据不会把合法隔离环境误判成残：

| 判据 | 空 schema（迁移前） | 迁好后 | public（主干） |
|---|---|---|---|
| 表数 | `0/67` | `67/67` | `67/67` |
| 本 schema V25+V26 | **`-1`**（旧版这里报 `2/2`，是空过） | `2/2` | `2/2` |
| 本 schema V5(`users`) | `0` | `1` | `1` |
| gen_salt（public 可解析，非本地判据） | `2` | `2` | `2` |
| `check` 退出码 | 1 | 0 | 0 |

同一环境跑 `smoke_w0.py`（隔离模式）→ **断言 35 条、失败 0、EXIT 0**，其中含改造后加严的两条：
「V26 两张表在当前 schema 已存在」与「Flyway 在【目标 schema 自己的】历史表里就有 V26」，
两者现在都显式 `<schema>.` 限定，不再靠 search_path 兜。
用完清理：三个 java 进程按端口取回 PID kill 后 8080/8081/8085 无 LISTEN，
`drop w0_v9`，复核 `public基表=67 / 最新迁移=26 / 残留 agent schema 数=0`。

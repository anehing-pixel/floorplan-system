## 1. 主体模型

三类主体，**不得混用同一列**：

| 主体 | 载体 | `actor_type` | 令牌/凭证 | 审计记录 |
|---|---|---|---|---|
| 内部自然人 | 用户 + JWT | `USER` | `JwtAuthInterceptor` | `AuditActor` 取用户名，**禁止从请求体读**（AGENTS.md §6.3） |
| 外部 partner | `partner_code` | `PARTNER` | HMAC 签名（D07 §2.3） | 记 `partner_code` + `message_id`，**不得记成任何内部用户名** |
| 系统 | `system:{jobName}` | `SYSTEM` | 无（作业） | 记 `system:ReconcileDiffJob` 等，与人工动作可区分 |

**四条硬约束**

| # | 约束 | 违反后果 |
|---|---|---|
| S-1 | 审计操作人**只能**从 `AuditActor` / 验签上下文取，任何请求体里的 `operator` 字段一律忽略并回显 `ignored_fields[]` | 审计可伪造 → 证据链失效 |
| S-2 | partner 主体只能出现在"外部事实的接收"动作上（回执、结果、报文）；**不得**出现在内部业务决策动作上（审批、豁免、结清） | 外部方间接操纵我方决策 |
| S-3 | `SYSTEM` 动作**只能推进被设计为自动的状态迁移**（巡检 `EXPIRED`、重估、对账）；不得执行"代人审批"类动作 | 把自动推进伪装成人工决策（红线 1 的常见绕过形态） |
| S-4 | 同一逻辑操作的 `actor` 与 `co_signed_by` **不得相同**（二人签认对） | `AUTH_003` |

## 4. SOD 矩阵（不得兼掌对）

| # | 对 | 为什么（资金/证据后果） | 校验点 |
|---|---|---|---|
| D-1 | 垫款发起 ↔ 垫款执行 | 自放自款 | 既有 `RoleSeparationPolicy` |
| D-2 | 垫款执行 ↔ 担保登记确认 | 放了款再补登记，把硬门禁变软 | 既有 |
| D-3 | **评分录入 ↔ 评分终值确认** | 自证评级 → 额度与准入被搬动 | `DEALER_SCORE_SET` vs `DEALER_RATING_CONFIRM` |
| D-4 | **估值录入 ↔ 人工覆盖** | 覆盖无人复核 = 基准可被单人抬高 | `VALUATION_RECORD` vs `VALUATION_OVERRIDE` |
| D-5 | **政策维护 ↔ 政策审批** | 自己改 LTV 自己生效 | `LTV_POLICY_MANAGE` vs `LTV_POLICY_APPROVE` |
| D-6 | **质押指定 ↔ 放证确认** | 押印未解先放证 = 担保物失控 | `CERTIFICATE_PLEDGE` vs `CERTIFICATE_RELEASE` |
| D-7 | **差异承认 ↔ 差异忽略** | 忽略无人复核 = 账实断裂被掩盖 | `RECON_ACK` vs `RECON_IGNORE` |
| D-8 | **指令生成 ↔ 指令撤销** | 一人可发可撤 = 可反复试探对方 | `RELEASE_ORDER_ISSUE` vs `RELEASE_ORDER_CANCEL` |
| D-9 | **降级代录 ↔ 台账结清** | 用 `INTERNAL_WITNESS` 把自己放的车洗成结清（红线 2 最直接的绕过） | `RELEASE_RECEIPT_MANUAL` vs `EXPOSURE_CLOSE` |
| D-10 | **计算书编制 ↔ 计算书签认** | 净回收与损失无人复核 | `LIQUIDATION_STATEMENT_PREPARE` vs `_CLOSE` |
| D-11 | **接管决定 ↔ 再拍卖委托** | 接管无复核即变现，处置权滥用 | `DISPOSAL_TAKEOVER` vs `DISPOSAL_CONSIGN` |
| D-12 | 密钥轮换 ↔ partner 停用 | 一人可换钥可停人 = 可造成对外不可用或伪造入口 | `PARTNER_KEY_ROTATE` vs `PARTNER_CONFIG_MANAGE` |

**实现要求**：SOD 校验放在 `application` 层的用例入口（`RoleSeparationPolicy` 复用与扩展），
不在前端隐藏按钮了事；**后端必须返回 `AUTH_003`**，且每次触发写 `audit_events(SOD_VIOLATION_BLOCKED)`。
D11 里每个 SOD 对至少一条断言（同人被拒 + 换人成功）。

## 7. 候选适用法规映射（**待法务回答，非结论**）

> 用法：每行是一个**必须被法务确认的问句** + 我方系统已经准备好的控制点。
> 法务回答"适用"→ 对应控制点转为强制；回答"不适用"→ 记录理由并保留列/权限以备复评。
> **签字前不得据本节宣称合规。**

| 法规 / 制度 | 触发场景（二手车） | 我方的控制点 | 需法务回答 | 状态 |
|---|---|---|---|---|
| **貸金業法** | 独立第三方资金方对 B2B 库存垫资是否构成"貸付業"、是否需要登録 | 放款主体在 `advances` 上显式记录；partner 类型不含"车商互贷" | 库存融资（金消契約形态、手形割引的）是否需登録？额度合同与放款凭证的法定记载项？ | 待 `[D-02]` |
| **割賦販売法** | 车商对下游消费者分期付款时的中介 | 本系统不做 C 端分期；`sale_channel` 只记录不介入 | 我方是否可能被认定为"割賦販売"的当事人？ | 待 `[D-02]` |
| **古物営業法** | ① 车商中古车买卖资质；② **我方处置再拍卖是否构成"古物営業"** | `dealer_licenses.license_type='FURIGUSHO'` + 到期预警；`disposal_auctions.buyer_type` 记录 | 我方受托处置再变现是否需要古物商许可？主帳簿（取引記録）保存义务落在谁？ | 待 `[D-02]`（**这是 USED 域最可能被忽视的一项**） |
| **自動車登録関係**（車検証・抵当権・移転登録・抹消） | R5 全部 | `inspection_certificates` 全字段 + `registration_applications` 三类型 + I-08 入站证据 | 抵当権设定/抹消是否强制司法書士？電子申請可否由代办完成？識別情報通知的管理义务？ | 待 `[D-03]` |
| **動産譲渡登記** | Q21/Q27 让与担保登记路径在二手车的适用 | `collateral_registration_batches.authoritative_source_type` + 顺位 | 5 年不可续展的既有约束在二手车场景如何处理（D00 §17 U-10）？与抵当権并存时的顺位与优先受偿？ | 待 `[D-02]` |
| **個人情報保護法** | 車検証含個人所有者/使用者氏名住所；个人车商 | §8 专项 | 取得目的告知与利用范围？第三者提供（向拍卖场/代办）是否需同意？保留年限？ | 待 `[D-02]` |
| **犯罪収益移転防止法（AML）** | 车商与客户身份确认、交易 Monitor | `dealer_compliance_checks`（`AML`/`IDENTITY`/`ANTI_SOCIAL`）+ 有效期 + `UNKNOWN` 视同不通过 | 本业务是否属于"特定事業者"？本人确认的法定时点与记录项？ | 待 `[D-02]` |
| **反社会势力排除** | 车商、上游、处置买方 | 同上 + 拒绝即阻断准入（G-A3） | 暴力团排除的法定/契约义务范围？确认频次与记录保存？ | 待 `[D-02]` |
| **自賠責保険・リサイクル券・自動車税** | R2.2 検査票字段 | `vehicle_condition_reports` 对应三列 + 未齐备阻断入库 | 未携リサイクル券 / 自賠責切れ 的车辆，担保权人（我方）的合规风险？ | 待 `[D-02]` |
| **消費税（中古车マージン課税）** | R4.5 落札费用与计税口径 | `auction_lot_costs.tax_treatment ∈ {TAXABLE,NON_TAXABLE,MARGIN_TAX}` | 垫款基准、结算总额、处置损益各按含税还是不含税？`MARGIN_TAX` 下如何还原？ | 待 `[D-02]`（影响 D08 全部金额口径） |
| **手形・当座貸越約定 / 金銭消費貸借** | 额度合同法律形态 | 不在系统内（法务文书） | 额度占用与回补在系统内的记录是否满足证据要求？ | 待 `[D-02]` |
| **電子記録・保存（帳簿書類）** | 报文留存、审计不可改 | `inbound_messages.payload_ref` + `call_logs` append-only + `audit_events` append-only | 保存年限（现行税务相关多为 7 年）与介质要求？我方默认 5 年（`payload-retention-days=1825`）**可能不足** | 待 `[D-02]`（**若法务答 7 年，须改配置并回填策略**） |

> **本节的诚实结论**：需求书 R12.1 列了 8 类法规，本表把它扩成 12 个必须回答的问句，
> 其中三处**最可能改变系统设计**：
> ① 古物営業法（我方处置变现可能需要许可并建主帳簿）→ 影响 `disposal_auctions` 的字段与保留；
> ② 消費税口径 → 影响 D08 全部金额是含税还是不含税；
> ③ 保存年限 → 5 年默认值可能不满足要求。
> 这三处**不是**"签字后补字段"就行的：它们会反向修改 D04 的列语义与 D08 的公式输入，
> 因此列为 `D-02` 的**必答前置项**（需求书 §12.3 已把 D-02 标为 P0、R12.1 标为开发前置输入）。

## 8. 个人信息（車検証 PII）专项

### 8.1 PII 清单与落点

| 数据 | 落点 | 必要性 | 默认展示 |
|---|---|---|---|
| 所有者氏名 / 住所 | `inspection_certificates.owner_name/owner_address` | 法定要件，必须存 | **脱敏**（`山田太郎` → `山田 〇〇`；住所到都道府県） |
| 使用者氏名 / 住所 | 同上 `user_*` | 法定要件 | 脱敏 |
| 登録番号 / 車台番号 | 同上 | 业务必需 | 明文（非 PII，是物识别） |
| 个人车商的商号/代表者 | `dealers`（现状） | 业务必需 | 内部明文，对外接口不回传 |
| 接收人姓名 | `release_receipts.receiver_name` | 证据必需 | 脱敏列表 + 明文详情需 `PII_READ_FULL` |
| 征信命中详情 | **不落库**，只存 `hit_summary` | — | §3.8 D07 |
| 报文原文（可能含 PII） | `payload_ref` 本地文件 | 留痕必需 | 文件权限收紧 + 访问记审计 |

### 8.2 控制要求

1. **最小返回**：所有列表/下拉/报表默认脱敏；全量视图需 `PII_READ_FULL`（二人授权 + 每次记 `PII_VIEWED_FULL`）。
2. **对外不回传**：`external-api` 的任何响应与任何出站报文**不得包含** PII 全量字段；
   给代办/保管方只需 `certificate_no` + `vin` + 保管指示。
3. **不入日志**：日志白名单机制（既有 `maskSecret` 同族），PII 字段一律不进 `log` 与 `details`。
4. **保留与删除**：`expires_on` / 结案后 N 年（`[D-02]`）后转归档文件；**禁止物理删除**（税务与诉讼证据需要，且与 §6 append-only 一致）。
5. **不引入对象存储**（U-R12）：归档为本地文件 + DB 存引用，访问受同一权限约束。

## 9. AML / 反社 / 准入的闭环（R1.2）

```
申请前  → G-A3 检查四类合规有效期（PASS 且未过期）→ UNKNOWN 即拒（P-7）
在库中  → 合规到期作业每日扫描 → 告警 + admission_state 重算
新申请  → G1 阻断新垫款；**不影响存量**（存量按裁决走：追加担保 or 到期不再延展） `[待定源 D-02]`
处置时  → buyer_type 记录；异常买方 → 告警 + 计算书签认前复核
```

**必须显式的一条判断**：合规失效**不自动**触发提前到期或加速收车（那是法律行动，需人工决策 + D-11 SOD），
系统只做「阻断新增 + 告警 + 工单」。把它写成自动化会构成越权的"系统代法务行事"。

## 11. 越权防御分层（与 ADR009 五层对齐）

| 层 | 措施 | 实现位置 | USED 新增点 |
|---|---|---|---|
| L1 网络 | 专线/VPN/mTLS、IP 白名单 | 部署 + `partners.allowed_ips` | 新增 |
| L2 入口 | 独立 `external-api`（DMZ），无 `public` 权限 | 角色 `floorplan_dmz`（D04 §4.1） | 新增 |
| L3 网关 | 对外不经过 18080；内部端点**不暴露**到 `external-api` | 部署拓扑（D02 §8） | 明确禁止 |
| L4 签名 | HMAC + 时钟窗 + nonce + key_version | `SignatureVerifier` | **修正现状**：现状所有渠道共用一个全局密钥且无 nonce |
| L5 审计 | 三路留痕（业务审计 / 报文原文 / 调用摘要） | `audit_events` + `payload_ref` + `call_logs` | 新增两张表 |
| L6 授权 | `@RequirePermission` / `@RequireAdmin` | 各 Controller | **新服务也必须标**（AGENTS.md §10）；`external-api` 用 scope 而非用户权限 |

> CORS 收紧（现状全通配）与内部服务令牌，属 L3/L4 的既有债务，随 W-U3 一并收口，
> 但**不得**把"改了 CORS"当作外部安全已解决——真正的边界是 DB 角色（L2）。

## 13. 前端权限与可见性（需求缺口 5 的联动）

| 项 | 说明 |
|---|---|
| 现状 | 前端 8 个模块 0 页面，后端 110+ 端点仅约 1/4 被调用（`PROGRESS §8`） |
| USED 域新增页面需求 | 资质档案、落札明细、估值与政策（含 `simulation`）、車検証台账与押印一览、放车放证工作台（含证据链视图）、账实差异、处置与计算书、集成运维（inbox/outbox/partner） |
| 权限点驱动 | 页面与按钮可见性由 `@RequirePermission` 的同一权限点驱动，**不得**在前端写角色名硬编码 |
| 双人操作的 UI | 二人签认的 UI 必须是"第一人提交 → 第二人在待办列表确认"，**不得**在同一表单里填两个名字（会造成代签） |
| 脱敏展示 | §8.1 的脱敏规则在 API 层实现（返回已脱敏），前端不做二次遮蔽（否则日志与缓存仍含明文） |

> 这条不是"顺手加前端需求"：如果二人签认没有 UI 支撑，实现会退化成"一个弹窗填两个工号"，
> SOD 形同虚设。**权限设计必须与 UI 交互设计同时定稿**，因此写在本文而不是单开文档。

## 14. 自检

- 需求书 R12.1–R12.4 逐条落点：R12.1 → §7（12 个法务问句，含三处会影响列语义/公式的高危项）；
  R12.2 → §1 主体模型 + §5 scope 矩阵 + `SECURITY_MAINTAIN` 禁代填；R12.3 → §6 三流 46 动作 + append-only + 不可伪造；
  R12.4 → 金额/比率/时区/报文留存分别在 D04 §1、D08 §0、D07 §2.7、§10。
- 34 权限点全部给出风险级、二人要求、关联需求；12 对 SOD 全部给出资金/证据后果与校验点。
- 10 条不可配置旁路红线单独成表，与 D00/D02/D06/D08/D09 的红线互相印证（无自造新红线）。
- 法规部分**未下任何结论**，全部以"待法务回答的问句"形式给出，并明确"签字前不得据此宣称合规"。
- PII 的七条控制（脱敏/最小返回/不入日志/不入报文/访问审计/保留/本地归档）与 U-R12「不引入对象存储」一致。
- §13 把 SOD 与 UI 交互绑定，避免"权限有、界面逼着代签"的自相矛盾。
- 未产出代码；未修改既有权限点定义（只新增 USED 点，由收口方落 `common`）。

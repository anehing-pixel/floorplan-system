# 库存融资核心系统 · 角色与权限矩阵

> 版本 v1.0（2026-10-26 定稿）　适用系统：汽车库存融资（Floorplan）核心系统
> 目标客户：日本新车渠道
>
> **本文档回答三个问题**：
> 1. 除管理员外，系统应该有哪些角色？（§1 角色清单 + §2 角色从哪里来）
> 2. 每个角色能做什么、不能做什么？（§3 权限矩阵 + §4 职责分离）
> 3. 这些角色在代码里怎么落地、怎么校验权限？（§5 落地机制 + §6 扩展指引）

---

## 0. 结论速览

| 项 | 结论 |
|---|---|
| 角色总数 | **13 个业务角色 + 1 个兼容角色**（`READONLY_USER`） |
| 权限点数 | **23 个**原子操作权限点 |
| 权限模型 | RBAC：角色 → 权限点（并集）；接口声明所需权限点 |
| 一人多岗 | **支持**（`user_roles` 表），权限取并集 |
| 职责分离 | **两层**：① 角色不相容（配置层，可告警）② 自然人不相容（运行层，硬阻断） |
| 管理员定位 | **只管系统，不碰业务单据**——这是本设计的关键取舍 |
| 垫款链路 | 录入 → 审核 → 申请 → 复核 → 支付，**五段四岗** |

## 1. 角色清单

按业务域分组。角色代码即 `UserRole` 枚举名，同时是数据库 `user_roles.role_code` 的取值。

### 1.1 平台管理域

| 角色代码 | 中文名 | 职责 | 权限点 |
|---|---|---|---|
| `SYSTEM_ADMIN` | 系统管理员 | 用户与角色管理、系统配置、批量作业运维、经销商主数据、上游主体准入 | `CONFIG_MAINTAIN` `JOB_TRIGGER` `DEALER_MAINTAIN` `SUPPLIER_MAINTAIN` |
| `READONLY_USER` | 通用只读岗 | 仅登录与查询（承接历史 `USER` 账号，供审计与回归测试用） | 无 |

> **管理员为什么不给业务写权限？**
> 这是本设计最重要的一条取舍。早期方案里 `ADMIN` 是"什么都能干"的万能角色，
> 一旦如此，"双人复核"就形同虚设——一个人拿管理员账号就能把申请、复核、打款三道关全过了。
> 所以现在管理员**只管系统配置与主数据，不碰垫款单据**。
> 管理员的所有操作都进审计表，事后可查，但**不能**替业务岗审批或放款。

### 1.2 授信风控域

| 角色代码 | 中文名 | 职责 | 权限点 |
|---|---|---|---|
| `CREDIT_REVIEWER` | 授信审查岗 | 授信额度建账与调整、额度冻结/解冻、年审、经销商风险评级调整 | `CREDIT_MANAGE` `ANNUAL_REVIEW` `RISK_GRADE_ADJUST` |

### 1.3 采购准入域

| 角色代码 | 中文名 | 职责 | 权限点 |
|---|---|---|---|
| `PURCHASE_OPERATOR` | 采购数据录入岗 | 采购清单导入（Excel/CSV）、上游收款账户录入、原始凭证上传 | `PURCHASE_IMPORT` `BANK_ACCOUNT_MAINTAIN` `ATTACHMENT_UPLOAD` |
| `PURCHASE_REVIEWER` | 采购审核岗 | 资料审核 + 实地验车确权 + 权属核验、实地盘点、账户有效性复核 | `VEHICLE_VERIFY` `INVENTORY_AUDIT` `ATTACHMENT_UPLOAD` `BANK_ACCOUNT_CONTROL` |

### 1.4 放款资金域（环节③，链路最长）

| 角色代码 | 中文名 | 职责 | 权限点 |
|---|---|---|---|
| `BUSINESS_OPERATOR` | 业务经办岗 | 发起垫款申请（占额度、落 PENDING 指令） | `ADVANCE_APPLY` |
| `FUNDING_REVIEWER` | 资金复核岗 | 复核放款要素：收款方、账户有效性、金额比例、委托付款协议 | `ADVANCE_REVIEW` |
| `FUNDING_CASHIER` | 资金出纳岗 | 向支付通道提交放款指令（推 PROCESSING） | `ADVANCE_DISBURSE` |

### 1.5 贷后处置域（随车辆状态变化的责任岗）

| 角色代码 | 中文名 | 职责 | 权限点 |
|---|---|---|---|
| `COLLATERAL_OFFICER` | 担保管理岗 | 担保设定与解除登记 | `SECURITY_MAINTAIN` |
| `POST_LENDING_MANAGER` | 贷后管理岗 | 风险告警处置、实地盘点（贷后视角） | `RISK_HANDLE` `INVENTORY_AUDIT` |
| `COLLECTION_OFFICER` | 催收岗 | 库龄递减核销、逾期催收、部分还款核销 | `CURTAILMENT_EXECUTE` `REPAYMENT_EXECUTE` |
| `SETTLEMENT_OFFICER` | 结算岗 | 售出标记、还款核销与额度回补、结清证明、解除担保 | `VEHICLE_SOLD` `REPAYMENT_EXECUTE` `PAYOFF_ISSUE` `SECURITY_MAINTAIN` |
| `DISPOSAL_OFFICER` | 违约处置岗 | 处置开单、收车、变现、损失认定、结案 | `DISPOSAL_EXECUTE` |
| `RISK_ADVISORY_OFFICER` | 增信业务岗 | 保险绑定与理赔、厂家回购兑现、展期续贷 | `INSURANCE_REPURCHASE` |

## 2. 角色从哪里来（推导过程）

角色不是拍脑袋定的，而是沿《库存融资核心系统-业务流程文档》的**十一环节**逐段找出
"谁在这个环节动手"，把动手的人聚成岗位：

```
①授信准入 ──→ ②验车确权 ──→ ③收车放款 ──→ ④⑤担保监管 ──→ ⑥库龄递减
   │                │              │                │              │
 授信审查岗      采购审核岗     ┌──┴──┐          担保管理岗      催收岗
                              │录入│审核│申请│复核│支付              │
                              └────┴────┘                        │
                            采购录入/审核/经办/复核/出纳            ↓
                                                          ⑦零售赎车 ──→ ⑧解押出库
                                                                 ↓
                                                        ⑨额度恢复结清 ──→ ⑩违约处置
                                                           结算岗          处置岗
                                                                 ↓
                                                          ⑪额度年审 ──→ 授信审查岗
```

**环节③为什么要拆成五段四岗**——这是全系统最复杂的部分：

| 段 | 动作 | 承担者 | 为什么必须分开 |
|---|---|---|---|
| 1 | 人工导入采购清单 | 采购数据录入岗 | 数据搬运与判断分离 |
| 2 | 资料审核 + 实地验车 | 采购审核岗 | 录入者不审自己的单 |
| 3 | 发起垫款申请 | 业务经办岗 | 申请与审批分离 |
| 4 | 复核放款要素 | 资金复核岗 | 填单与批单分离 |
| 5 | 提交支付通道 | 资金出纳岗 | 批单与打款分离 |
| — | 银行确认付款结果 | 支付通道（非系统角色） | 内部人员一律无法自行确认放款 |

> **段 2 为什么把"资料审核"与"实地审核"合成一个岗位？**
> 用户口述的"审核人员的资料和实地审核"两个动作，都属于"对录入内容做独立确认"，
> 业务连续性强，且在中小团队里本就常由同一人承担。拆成两岗会让流程空转。
> 如果将来团队规模够、监管要求更细，拆成两个角色只需新增枚举值 + 拆分权限点，
> 不影响其他角色（这也是为什么权限点要与角色分开定义）。

## 3. 权限点清单（23 个）

权限点是原子操作，由接口决定；角色是权限点的打包。

| 权限点 | 中文 | 归属角色 | 涉及接口（示例） |

| `SUPPLIER_MAINTAIN` | 上游主体准入管理 | 管理员 | `POST/PUT /api/suppliers/**` |
| `BANK_ACCOUNT_MAINTAIN` | 收款账户录入 | 采购录入岗 | `POST /api/suppliers/{id}/accounts` |
| `BANK_ACCOUNT_CONTROL` | 收款账户冻结与恢复 | 采购审核岗 | `PUT /api/bank-accounts/{id}/status` |
| `CONFIG_MAINTAIN` | 系统配置维护 | 管理员 | `PUT /api/rating-configs/{grade}` |
| `JOB_TRIGGER` | 批量作业手工触发 | 管理员 | `POST /api/jobs/**` |
| `CREDIT_MANAGE` | 授信额度建账与调整 | 授信审查岗 | `POST /api/credit-lines` |
| `ANNUAL_REVIEW` | 额度年审与冻结恢复 | 授信审查岗 | `POST /api/annual-reviews/**` |

| `INVENTORY_AUDIT` | 实地盘点核查 | 审核岗 / 贷后管理岗 | `POST /api/inventory/audit` |
| `ADVANCE_APPLY` | 垫款申请 | 业务经办岗 | `POST /api/advances` |

>
> **⚠ 2026-11-24 已变更**：读接口现按《读接口授权矩阵》（`docs/读接口授权矩阵.md`）的
> **B 功能矩阵**执行——13 个域读点 + 14 角色 `READ_MATRIX`，○ 在数据范围 C 落地前按 —。
> 上面这句仅保留为历史口径，不再是当前标准。

## 4. 职责分离（SOD）

### 4.1 两层机制

| 层次 | 问的问题 | 机制 | 违反后果 |
|---|---|---|---|
| **角色层**（配置时） | 这个人的岗位组合合理吗？ | `RoleSeparationPolicy.findConflicts()` | **告警提示**，不阻断（一人多岗现实中常见） |
| **自然人层**（运行时） | 这一笔业务是几个人做的？ | `RoleSeparationPolicy.assertNoSelfApproval()` | **硬阻断**（403 `AUTH_003`） |

> **为什么角色层不硬阻断？**
> 中小金融机构里"财务既复核又结算"是常态，硬阻断会让系统直接不可用。
> 但**同一笔业务**上的自办自批是真实的资损风险，必须挡死。
> 所以：岗位配置给提示，单笔业务做硬校验——两层各管一段，互不替代。

### 4.2 不相容角色对

| 角色 A | 角色 B | 不相容理由 |
|---|---|---|
| 采购数据录入岗 | 采购审核岗 | 录入者自审自签，采购清单失真无人把关 |
| 业务经办岗 | 资金复核岗 | 自己填的申请自己批 |
| 业务经办岗 | 资金出纳岗 | 自己申请自己放款（ADR-006 明确禁止） |
| 资金复核岗 | 资金出纳岗 | 自己批完自己打，金额与收款方可被同时篡改 |
| 催收岗 | 结算岗 | 催收认定与收款核销同一人，可掩盖挪用 |
| 担保管理岗 | 违约处置岗 | 担保物处置由担保登记人自己定，处置估值易被操纵 |
| 系统管理员 | 任何业务写岗 | 管理员能改配置又能代行业务，双人复核失效 |

### 4.3 自然人级硬校验（垫款链路）

垫款单 `advances` 表记录三个自然人，构成完整责任链：

| 字段 | 写入时机 | 约束 |
|---|---|---|
| `applicant` | 申请时 | —— |
| `reviewer` | 复核时 | **≠ applicant**（`AUTH_003` 阻断） |
| `disburser` | 支付时 | **≠ applicant 且 ≠ reviewer**（`AUTH_003` 阻断） |

> 一人多岗时，申请人与复核人可能持有**同一个角色**（比如一人既是经办岗又是复核岗），
> 但**必须是两个人**。角色区分挡不住这种情况，只有按自然人身份比对才行。

## 5. 落地机制

### 5.1 三层代码结构

```
domain/model/Permission.java          权限点枚举（23 个原子操作）
domain/model/UserRole.java             角色枚举（14 个），持有 Set<Permission>
domain/service/RoleSeparationPolicy.java  权限并集解析 + 不相容矩阵 + 自然人校验
        ↑
web/security/RequirePermission.java   接口声明所需权限点
web/config/JwtAuthInterceptor.java     拦截器按权限点判定
```

### 5.2 数据模型

```sql
users.role          VARCHAR(64)   -- 主角色（显示与审计用），角色代码 = UserRole 枚举名
user_roles.username VARCHAR(64)   -- 一人多岗关联表
user_roles.role_code VARCHAR(40)  -- UserRole 枚举名
user_roles.is_primary BOOLEAN      -- 主角色标记
```

`users.role` 保留是为了兼容既有审计字段与旧令牌；**真正的授权判定读 `user_roles`**。

### 5.3 判定流程

```
请求 → JWT 拦截器验签
     → 从令牌取 perms（后端登录时按角色并集算好后签发）
     → 读取接口上的 @RequirePermission
     → 权限点全部命中？ → 放行
     → 否则 403 AUTH_002（错误体里带上"需要什么/你有什么"）
```

> **权限点放在令牌里而不是每次查库**：避免每个请求查一次 `user_roles`。
> 代价是角色调整要等令牌过期才生效（默认 8 小时）——
> 紧急撤权走"禁用账号"通道，禁用后重新登录即失效。

### 5.4 状态码约定

| 码 | 含义 | 场景 |
|---|---|---|
| 401 `AUTH_001` | 未认证或令牌失效 | 无令牌 / 令牌过期 |
| 403 `AUTH_002` | 无该操作权限 | 角色不匹配（**不含** SOD 冲突） |
| 403 `AUTH_003` | 违反发起与执行分离 | 同一自然人自办自批 |

## 6. 车辆状态 × 责任角色

对应用户提出的"随着汽车状态变化由不同角色负责"：

| 车辆状态 | 主责角色 | 该阶段的动作 | 参与角色 |
|---|---|---|---|
| `FINANCED` 已垫款（未到货） | 采购审核岗 | 到货验车、权属核验 → 转 `IN_STOCK` | 催收岗（跟进） |
| `IN_STOCK` 在库 | 贷后管理岗 | 盘点核查、库龄监控、告警处置 | 担保管理岗（担保登记）、催收岗（递减计划） |
| `SOLD_PENDING` 已售待还 | 结算岗 | 确认收款、结清核销、额度回补 | 催收岗（结算窗口内催收）、担保管理岗（解押） |
| `SETTLED` 已结清 | 结算岗 | 出具结清证明、解除担保、触发出库 | 担保管理岗 |
| `OVERDUE` 逾期 | 催收岗 | 上门催收、协商、递减核销 | 贷后管理岗（风险定级）、处置岗（准备收车） |
| `DISPOSING` 处置中 | 违约处置岗 | 收车、变现、损失认定 | 担保管理岗（担保物处置配合） |
| `CLOSED` 已关闭 | 违约处置岗 | 结案归档 | —— |

## 8. 扩展指引

### 8.1 新增一个权限点

1. `Permission` 枚举加一项（写清中文标签与归属）；
2. 需要新角色才能做 → `UserRole` 里把该权限点加进对应角色的 `set(...)`；
3. 在对应接口上加 `@RequirePermission(Permission.XXX)`；
4. 前端若要隐藏按钮，在视图里用 `FP.auth.can('XXX')` 判断。

### 8.2 新增一个角色

1. `UserRole` 枚举加一项，指定所属 `RoleDomain` 与权限点集合；
2. `V8` 之后的迁移里更新 `user_roles.role_code` 的 `CHECK` 约束
   （枚举值必须与数据库约束同步，否则插入会失败）；
3. 若与其他角色不相容，在 `RoleSeparationPolicy.INCOMPATIBLE` 补一条；
4. 建种子账号验证。

### 8.3 拆分现有角色

因为权限点与角色是两层，拆分不需要动其他角色：
新增角色 + 调整权限点归属即可，接口侧一行不用改。

### 8.4 权限点不能"跨角色组合"生效

注解里多个权限点是**且**关系（全部具备才放行），
不表达"两个岗协同才能做"。要表达协同，正确做法是拆成两个接口各自校验自己那一半——
否则权限推理会变得不可读。

## 9. 与既有设计的衔接

## 1. 全局设计原则（八条，D01–D12 不得违反）

| # | 原则 | 含义 | 违反的后果 |
|---|---|---|---|
| **P-1** | **封存优先于迁移** | LEGACY 域数据、迁移、枚举值一律不动；USED 域能力**只新增不改写**。`V1`–`V26` 字节不变 | Flyway checksum 失配 → 全仓启动失败（本仓已踩过两次） |
| **P-2** | **显式分叉，禁止隐式默认** | 所有规则链路由 `vehicle_units.vehicle_type` 判定，**不允许**「默认新车」的隐式分支（现状 `PurchaseOrderApplicationService:194,305` 硬编码 `NEW_STOCK` 是反面样例） | 新业务走老规则链 → 用发票公式给二手车定价 → 资损 |
| **P-3** | **双闸门可回退** | ① 配置闸门 `floorplan.used.enabled`（默认 `false`）② 数据闸门 `vehicle_type='USED'`。任一切断，USED 域全部新代码路径不可达 | 评审未通过就上线；无法灰度回退 |
| **P-4** | **未签字不编码** | §17 待定源清单逐项标注确认方与影响面；确认前只出设计、不出实现 | 需求书 §12.1 的治理风险落地 |
| **P-5** | **幂等必须两层** | 框架层幂等（`event_consumptions(event_id,consumer)`）+ 业务层唯一键。一层都不许省（`JdbcOutboxPublisher` 注释已论证并发窗口） | 重复放款 / 重复回补额度 = 资损 |
| **P-6** | **权威回执不可自证** | USED 域的放车放证结论**只能**由 partner 签名回执产生；内部代录必须在数据上与 `PARTNER_RECEIPT` 严格区分且不可互转 | 撤销 V24 折中又折中回去；`confirmation_authority` 现可伪造（需求书 §3.5） |
| **P-7** | **门禁 fail-closed** | USED 域放款/放车的每一道前置校验，异常/超时/无数据一律**拒**，不降级放行。且**不留可配置绕过**（Q21 被 `relaxedDealers` 绕过的教训） | 硬策略退化成软放行 |
| **P-8** | **拆分须成套** | 新增服务 = 拆能力 + 迁数据 + 通链路 + 有端点 + 有断言，五件齐了才算。否则并进已有服务（AGENTS.md §12 反模式第一条） | 出现「有目录没功能」的空壳服务 |

## 3. 限界上下文与模块归属

### 3.1 上下文划分

USED 域**新增 4 个逻辑上下文**，但**只新增 1 个部署单元**（原则 P-8）。

| 上下文 | 性质 | 核心对象 | 落点模块 / 服务 | 说明 |
|---|---|---|---|---|
| `valuation` 估值与定价 | 🆕 新 | `VehicleValuation`、`LtvPolicy`、`MarketSnapshot` | `domain` → `application` → **`web`(core)** | 参与放款闸门，**必须与垫款同一本地事务域**，故不拆服务 |
| `auction` 落札与采购 | 🆕 新 | `AuctionLot`、`AuctionSettlement`、`AuctionHouse` | 同上 → **`web`(core)** | 挂在现有 `purchase_orders` 采购上下文之下，是其 USED 分支 |
| `certificate` 车检证质押 | 🆕 新 | `InspectionCertificate`、`CertificateCustody`、`RegistrationApplication` | **`collateral-reg-service`**(8086) | 担保权属上下文的自然延伸；权威源类型扩展见 §5 |
| `custody` 监管仓实控 | 🆕 新 | `Custodian`(扩展)、`InventorySnapshot`、`ReconcileDiff` | 主数据+快照 → **`web`(core)**；差异 → **`recon-service`**(8088) | 快照属库存台账（core），账实差异属对账（recon） |
| `integration` 外部协同 | 🆕 新 | `Partner`、`InboundMessage`、`OutboundTask` | **`external-api-service`**(18090，DMZ) + `common/contract` | **唯一新增进程**，见 §4 |
| `release` 放车放证 | ⚠️ 改造 | `ReleaseOrder`、`ReleaseItem`、`Receipt` | **`release-service`**(8087) | 从内部状态机升级为跨机构异步协同 |
| `dealer` 车商资质 | ⚠️ 改造 | `DealerQualification`、`License`、`ComplianceCheck` | **`credit-service`**(8083)（准入与授信同源） | 资质是授信前置，与评级同处 |
| `collateral` 担保 | ⚠️ 改造 | `CollateralBatch` 权威源类型 | **`collateral-reg-service`** + V10 | 沿用 ADR-Q27 逐台架构，只换权威源类型 |
| `loan` / `interest` / `credit` 账务骨架 | ✅ 复用 | — | 不动 | 需求书 §3.3 已论证与车辆类型无关 |
| `disposal` 违约处置 | ⚠️ 改造 | `DisposalAuction`、`LiquidationStatement` | **`risk-service`**(8084) | 再拍卖变现通道 |

### 3.2 上下文集成关系（谁是权威源）

```
auction（落札事实）──审慎值输入──► valuation（估值定价）
                                      │ 放款基准 prudent_value
                                      ▼
dealer（资质闸门）──准入结论──► core:AdvanceApplicationService（金额基准唯一入口）
                                      │
                    ┌─────────────────┼──────────────────┐
                    ▼                 ▼                  ▼
             credit(额度占用)  certificate(质押设定)  custody(实车入库)
                    │                 │                  │
                    └───────► collateral 权属权威源 ◄─────┘
                                    │ 门禁 REGISTERED
                                    ▼
                             release(放车放证) ──outbox──► core 台账 + credit 回补
                                    ▲
                          integration(指令/回执双向)
```

**权威源裁决（谁的数据算数）**：

| 事实 | 权威源 | 只读投影 | 禁止 |
|---|---|---|---|
| 车辆实物在库状态 | `custody` WMS 入库确认 + 快照 | `vehicle_units.status` | 无 WMS 入库确认不得进 `IN_STOCK`（R6 验收） |
| 放款金额基准 | `valuation.prudent_value` | `vehicle_units.advance_amount` | 禁止用 `invoice_amount × ratio`（LEGACY 公式） |
| 逐台担保权属 | V10 `collateral_registration_batches`（扩展多源类型，沿用 ADR-Q27） | `vehicle_units.security_status` / V18 | 禁止新代码直读别上下文表（AGENTS.md §3.1） |
| 放车结论 | `integration` partner 签名回执 | `release_orders.status` | 禁止内部用户填 `PARTNER_RECEIPT`（P-6） |
| 结清与额度回补 | core 单事务 | — | 顺序见 D09 §4（两段式解押，待 D-07） |

## 4. 进程拓扑、端口与网络分区

### 4.1 端口分配（8080–8088 与 18080 已被占用）

| 进程 | 端口 | 分区 | 状态 | 变更 |
|---|---|---|---|---|

### 4.2 三区网络模型

```
        ┌──────────── Internet / 专线（USS · TAA · WMS 供应商）────────────┐
        │                          │ mTLS + 签名                        │
        ▼                          ▼                                    ▼
┌───────────────── DMZ 区 ─────────────────┐      ┌────── 内网区（trusted）──────┐
│  external-api :18090                     │      │  gateway :18080 → 9 业务服务 │
│  · 入站：验签 → 限流 → 幂等 → inbox → 202 │      │  web(core) :8080             │
│  · 出站：拉 outbound_tasks → 签名 → 调用  │      │  auth/bank/credit/risk/loan  │
│  · 只连 schema `integration`             │ ◄──► │  collateral-reg/release/recon│
│  · 不连 schema `public`，不跑业务逻辑     │ 同一 │                            │
│  · Flyway enabled=false                  │ PG   │  唯一跑 Flyway：web         │
└──────────────────────────────────────────┘      └────────────────────────────┘
```

**四条边界规定**：

1. `external-api` 用**独立 DB 角色** `floorplan_dmz`，仅授予 `USAGE ON SCHEMA integration` + 该 schema 下的 DML；对 `public` schema **不授予任何权限**。
2. DMZ **不持有任何业务实体的写路径**：`integration.*` 六张表里它只写
   `inbound_messages`（受理）、`nonces`（防重放）、`call_logs`（流水）三张，`outbound_tasks` 只读领取 + 回写投递结果，
   `partners` 与 `partner_credentials` **只读**（凭证表连写都不给：能写就等于能自己签发密钥版本，见 D04 §4.1 逐表授权）。
3. 内网 → DMZ **不允许**（DMZ 不接受内部推送）；DMZ → 内网仅允许 `gateway` 上的白名单回传端点，且带服务间令牌。
4. 核心调用 DMZ 拥有的数据（如人工重触发、partner 配置）走**内部端点 + 权限点**，不直连表（AGENTS.md §3.1 跨服务规则）。

### 4.3 为什么只新增 1 个进程（对抗 P-8 反模式）

| 备选 | 为什么不选 |
|---|---|
| 再拆 `valuation-service` | 估值参与放款**同步**门禁，跨进程会把本地事务变成分布式事务；且需自建「拆能力+迁数据+通链路」全套，收益为负 |
| 再拆 `auction-service` | 落札数据最终要写 `purchase_orders`/`vehicle_units`（core 所有），拆出去等于把同一聚合劈成两半 |
| 再拆 `certificate-service` | 車検証是担保权属的一部分，`collateral-reg-service` 已存在且已具备逐台权威源语义，复用优于新建 |
| 不建 `external-api`，让 core 直连 partner | 违反 ADR009 五层防御；partner 密钥与核心库同进程，一旦 DMZ 侧被攻破即全库暴露 |

## 10. 事件契约扩展（复用 W0 已冻结机制，不另造）

### 10.1 基线事实

`8ea23ab` 已落地，USED 域**直接复用**，D02/D09 不得重新设计：

| 组件 | 位置 | 关键约束 |
|---|---|---|
| `outbox_events` 表 | `V21` | `(event_type, aggregate_key)` + status 去重；**payload 必含 `vin` + `traceId`** |
| `event_consumptions` / `consumer_offsets` | `V26` | 主键 `(event_id, consumer)`；重试上限 **3** 次后 `DEAD` 并推进游标 |
| `OutboxPublisher` 契约 | `common/contract` | 实现 `JdbcOutboxPublisher`：**不加** `@Transactional`，跟随调用方事务 |
| `DomainEvent` / `EventConsumer` | `common/event` | `consumer()` 用**服务名不用类名**；`consume()` 抛异常＝失败且游标不动；**消费者内禁止服务间调用**（调度线程无 JWT 上下文） |
| 调度装配 | 9 个启动类 | `@EnableScheduling` + `@Import` 两个 bean 已就位 |

### 10.2 新增事件类型（USED 域提案）

现状契约只有 3 个常量（`LOAN_CREATED` / `PAYMENT_MATCHED` / `COLLATERAL_CHANGED`），并注明
「取值只用这三个常量，不许自由命名」。**扩展常量属于共享层 `common` 的改动，必须由收口方统一添加**
（AGENTS.md §7.1 共享禁区）。USED 域各设计文档只声明需求，不自行往 `common` 里写：

| 提案事件名 | 生产方 | 主要消费方 | 业务键 `aggregate_key`（**每次发生唯一**） | 触发时机 |
|---|---|---|---|---|
| `CERTIFICATE_PLEDGED` | collateral-reg | core（车辆担保态）、risk | `inspection_certificates.id`（换证/再発行各建新行） | 車検証设质完成 |
| `VALUATION_REFRESHED` | core(valuation) | core(aging 递减)、risk(LTV 告警) | `vehicle_valuations.id` | 重估生效 |
| `LTV_BREACH_DETECTED` | core(valuation) | risk（工单）、credit（冻结新放款） | `risk_alerts.id`（突破告警行主键） | 残值率跌破阈值 |
| `WMS_INBOUND_CONFIRMED` | core(inbox 处理后) | core（车辆 `IN_STOCK` 起息） | `wms_inbound_confirms.inbound_no` | WMS 入库确认落账 |
| `RELEASE_ORDER_DISPATCHED` | release | integration（出站任务生成） | `order_no` + `dispatch_seq`（撤销后重下会同号） | 指令下发 |
| `RELEASE_ORDER_RECEIPTED` | integration | release、core（台账） | `release_receipts.id` | partner 回执验签通过 |
| `VEHICLE_SETTLED` | core | credit（额度回补）、loan | `settle_seq`（D09 结清流水，与部分唯一索引同源） | 台账结清（**在解押之后**，见 D09 §4） |
| `CREDIT_LINE_RESTORED` | credit | recon、loan | `credit_restores.id`（回补凭证主键；一条额度线可回补多次） | 额度真实回补完成 |
| `REGISTRATION_DISCHARGED` | collateral-reg | release（`LIEN_DISCHARGED` 推进） | `registration_applications.apply_no` | 登记抹消回执到达 |
| `DISPOSAL_AUCTION_RESULT` | integration | risk（清算计算书） | `disposal_auctions.id`（每次再拍卖成交新建） | 再拍卖成交 |

> **本表的键列于 2026-11-22 由 D13 §3 G2 修正**。原稿有 6 行写 `vin`、1 行写 `credit_line_id`，
> 而发布端 `JdbcOutboxPublisher` 的 `WHERE NOT EXISTS` 判据含 `SENT` 行（`JdbcOutboxPublisher.java:41-48`），
> 于是**同一台车的第二次质押 / 第二次重估 / 第二次结清、同一条额度线的第二次回补会被静默丢弃且不可补发**。
> 这不是「去重太松」而是「吃掉合法业务事件」，且直接违反 AGENTS.md §6.3
> 「`aggregate_key` 标的是『这一次发生』，禁止用 `vin`」的硬规定。
> 选键规则：用**每次新建的那行记录的主键**（`*Id` / `*_no` / `*_seq`），不用对象标识符。

**两条硬规定**（写进 D09/D11 验收）：

1. 事件名扩展**一次一批**：W0 已冻结常量风格，新增常量须由收口方在同一提交内
   更新 `OutboxPublisher` 与《事件机制实现说明》，避免消费端订阅集合对不上。
2. **顺序敏感链不用事件传递控制流**：`RELEASE_ORDER_RECEIPTED → VEHICLE_SETTLED → CREDIT_LINE_RESTORED`
   每一跳都可能滞后与重放，因此每个消费方**只依据自己表里的业务态判断**，
   不得假设「上游事件已到我这里」。幂等靠两层（P-5）。

```
OUT 再出场委托 : DAL:{disposal_case_no}:{lot_no}

```

**三条规则**：① 一律大写字母 + 半角冒号分段；② 业务键**不含内部自增 ID**（R7.3「不暴露内部 ID」）；
③ 同一幂等键重复投递：首次执行，后续返回首次结果 + `MessageStatus=DUPLICATE`，**不重复产生副作用**（P-5）。

### 13.3 消费侧业务幂等键 `AEF:*`（2026-11-22 由 D13 §4.4 WU2-09 补，原先全文档只出现一次且无构成）

D12 W-U2 行写「消费 `PAYMENT_MATCHED`，幂等键 `AEF:*`」却没说键怎么拼。补定源：

```
AEF:{auction_code}:{settlement_no}:{paymentRef}
```

- `paymentRef` = 主干 `PAYMENT_MATCHED` 的 `aggregate_key`（`EventDispatcher.java:248` 注释即此约定），
  本身已是「这一次匹配」的唯一值；
- 键只由**业务事实**组成，**禁止**掺 `event_id` / `traceId` / 时间戳——掺了就等于每次都不撞键，
  业务层幂等当场失效；
- 落点：写进该次核销动作产生的行（`auction_settlements` 的支付引用列，D04 §3.7）并加唯一约束，
  **不是**另建一张键表。

**四层拦截必须分清楚，不要以为有一层就够**（这是 D13 G2 与 WU2-09 合起来的教训）：

| 层 | 键 | 拦的是什么 | 谁负责 |
|---|---|---|---|
| L0 传输 | `inbound_messages.idempotency_key`（§13.2 `IN *`） | partner 把同一条消息重投 | W-U3 / DMZ |
| L1 框架 | `event_consumptions (event_id, consumer)` | **同一事件行**被同一消费者跑两次 | W0 已交付，无需业务代码 |
| L2 业务 | `AEF:*` 之类 + 目标表唯一约束 | **不同 `event_id`、同一业务事实**：死信人工重放、partner 换消息重发、一笔款拆两条匹配事件 | 各消费方自己 |
| L3 金额 | `settle_seq` / `version` 乐观锁 | 并发更新把两次核销叠成错误余额 | 各写路径 |

> L1 的存在**不能**代替 L2：`event_id` 变了 L1 就放行，而业务事实没变。
> 反过来 L2 也不能代替 L1：L1 是框架统一保证的，L2 需要每条写路径自己建唯一约束。
> 判据：任何会被重试的写操作必须有 L2 唯一约束兜底（AGENTS.md §10「幂等」）。

# 库存融资核心系统 · 日志查看指南

> **适用版本**：2026-11-20 起（微服务版；早期单体版见 §1.6）
> **一句话**：这个系统有 **4 层日志载体**，查什么要找对层。运行日志看文件，审计看表，告警看 API，批处理看表。
>
> **架构现状（2026-11-20）**：已拆成网关 + 5 服务（web/auth/bank/credit/risk），
> 每个服务各自落盘到 `logs/microservices/<服务名>.log`。**先确定请求被切到哪个服务，再去对应的日志文件查**——
> 这是微服务化后排障与单体最大的不同。

---

## 0. 先搞清：4 层日志不是一回事

排查问题时第一件事是判断"我要找的东西在哪一层"。用错层会白折腾很久。

| 层 | 载体 | 记什么 | 留存 | 怎么查 |
|---|---|---|---|---|
| **① 运行日志** | 单体 `logs/floorplan.log`；微服务 `logs/microservices/<服务>.log` | 进程级事件：启动、异常、越权、批处理调度 | 30 天（滚动归档） | `tail` / `grep` |
| **② 审计日志** | `audit_events` 表 | **谁**在**何时**对**哪个对象**做了什么 | 永久（append-only） | SQL / 前端「盘点监管」页 |
| **③ 风险告警** | `alerts` 表 | 系统判定的风险事实：脱信嫌疑、盘点差异等 | 永久 | API / 前端「风险告警」页 |
| **④ 批处理记录** | `batch_runs` 表 | 定时作业跑没跑、跑成功没有、失败原因 | 永久 | SQL |

**最常见的误判**：用户反馈"某某业务出问题了"，你去翻 ① 运行日志找线索，翻半天找不到——
因为**业务操作本身不写运行日志**（见第 5 节），业务轨迹在 ② 审计表里。

## 1. 运行日志

### 1.1 日志在哪

> 微服务版（当前）：`run-microservices.sh` 把每个服务的 stdout/stderr 重定向到独立文件。
>
> ```
> floorplan-system/logs/microservices/
> ├── web.log          ← 核心账务（垫款/还款/计息/车辆台账）
> ├── auth-service.log ← 登录与签发给 token
> ├── bank-service.log ← 银行回款采集
> ├── credit-service.log ← 经销商/额度/评级/年审
> ├── risk-service.log ← 盘点/处置/担保/权属核对
> ├── gateway.log      ← 网关路由与 X-Request-Id
> └── *.err            ← 各服务标准错误（堆栈常在这里）
> ```
>
> 排障第一步：**看请求 URL 判服务**。`/api/auth/**` → auth-service.log；
> `/api/dealers|credit-lines|rating-configs` → credit-service.log；
> `/api/alerts|risk/**|lien-check` → risk-service.log；
> `/api/jobs/bank-fetch` → bank-service.log；其余核心账务 → web.log；网关层问题 → gateway.log。
> 不确定就看 gateway.log 的路由日志，或响应头里的 `X-Request-Id` 串起全线。

单体版（历史，`run-local.sh` 时代的落盘布局，仍可对照理解滚动策略）：

```
floorplan-system/logs/
├── floorplan.log          ← 当前日志（正在写）
├── console.log            ← 控制台重定向副本（可选启动参数产生）
└── archive/               ← 滚动归档目录
    └── floorplan.2026-10-26.0.log.gz
```

**滚动策略**（见 `web/src/main/resources/logback-spring.xml`）：

| 参数 | 值 | 说明 |
|---|---|---|
| 单文件上限 | 50 MB | 超了切新文件 |
| 归档命名 | `floorplan.%d{yyyy-MM-dd}.%i.log.gz` | 按天 + 序号，gzip 压缩 |
| 保留天数 | 30 天 | 超过自动删除 |
| 总量上限 | 2 GB | 防止磁盘被撑爆 |

### 1.2 常用命令

> 以下命令以单体版 `logs/floorplan.log` 为例。微服务版把 `logs/floorplan.log`
> 换成 `logs/microservices/<服务>.log` 即可，其余 grep/tail 手法完全一致。

```bash
cd floorplan-system

# 实时跟踪（最常用）
tail -f logs/floorplan.log

# 只看最后 100 行
tail -100 logs/floorplan.log

# 只看异常（排障第一步）
grep -E "ERROR|WARN" logs/floorplan.log

# 按 traceId 精确追踪（接口报错时最有用的手段）
grep "<traceId>" logs/floorplan.log

# 按 VIN 追踪某台车的全部日志
grep "TESTVIN001" logs/floorplan.log

# 按错误码追踪
grep "VEHICLE_001" logs/floorplan.log

# 统计各级别条数（快速判断问题严重程度）
awk '{print $3}' logs/floorplan.log | sort | uniq -c | sort -rn

# 查看历史归档
zcat logs/archive/floorplan.2026-10-25.0.log.gz | grep "ERROR"
```

### 1.2.1 在 PowerShell 里看日志（Windows 开发者最常用）

> **推荐直接用封装好的脚本**（在 `floorplan-system/` 目录下）：
>
> ```powershell
> .\view-log.ps1                      # 看末尾 50 行
> .\view-log.ps1 -Follow              # 实时跟踪（Ctrl+C 退出）
> .\view-log.ps1 -Filter DEALER_001   # 按错误码/关键字过滤
> .\view-log.ps1 -Level ERROR -Tail 100   # 按级别过滤
> .\view-log.ps1 -Filter "6acd3ad3-055a-4f5b-9fab-ae96b0fc2614"   # 按 traceId 精确追踪
> .\view-log.ps1 -File .\logs\console.log    # 指定文件
> ```
>
> 脚本已处理下面三个坑，无需自己操心。

**如果想手写命令，注意三个坑：**

#### 坑 1：编码 —— 不加 `-Encoding UTF8` 中文必乱码

Windows 控制台默认代码页是 936（GBK），而日志文件是 UTF-8 写的。
`Get-Content` 在 **Windows PowerShell 5.1** 下默认按 ANSI(GBK) 读，中文全是乱码。

```powershell
chcp 65001                                    # 切控制台到 UTF-8（必须先做）
Get-Content .\logs\floorplan.log -Tail 50 -Encoding UTF8
```

> PowerShell 7+ 默认就是 UTF-8，`-Encoding UTF8` 可省略；
> 但 `chcp 65001` 仍建议执行，否则**输出**到控制台时仍可能按 936 渲染。
> 本机实测：PowerShell 7.6.9 + 代码页 936，加与不加 `-Encoding UTF8` 都能正常显示中文——
> 但这是因为日志文件本身带 UTF-8 BOM 无关、内容已被正确识别。**换台机器不要想当然。**

#### 坑 2：文件被 Java 独占锁定 —— 必须用共享读方式

日志文件正被 Java 进程持有写句柄，**不能用** `ReadAllBytes` / 独占方式打开，会抛：

```
The process cannot access the file because it is being used by another process.
```

正确写法是 `File.Open` + `FileShare.ReadWrite`：

```powershell
$fs = [System.IO.File]::Open($p, 'Open', 'Read', 'ReadWrite')
$bytes = New-Object byte[] $fs.Length
$fs.Read($bytes, 0, $bytes.Length) | Out-Null
$fs.Close()
```

> 但 `Get-Content` / `Select-String` 本身没问题，它们内部就是共享读——所以上面第一条命令能直接跑。

#### 坑 3：NUL 空洞 —— 已被污染的日志要剔除 NUL

**现象**：`console.log` 打开后前面是一大段空方块，实际有效内容在末尾。

**原因**（本项目真实踩过，2026-10-26）：
日志文件被外部程序**就地截断**，但写入方（`tee` / logback）仍持有旧句柄并继续按原偏移写入，
于是文件前半段留下 NUL 空洞（16282 字节空洞 + 尾部有效内容，总长与原文件一致）。

**触发路径**：`run-local.sh` 启动时会 `rm -f logs/console.log`，
在 Windows 上「删除正被进程持有的文件」不会断开持有者的句柄 → 必然产生空洞。
已修复为**归档而非删除**（见 `run-local.sh`），但历史文件仍带空洞。

**清理方法**：

```powershell
# 读出来先剔除 NUL
$raw = Get-Content .\logs\console.log -Raw -Encoding UTF8
$clean = ($raw -replace "`0", "") -split "`r?`n" | Where-Object { $_.Trim() -ne '' }
$clean | Select-Object -Last 50
```

#### 常用的 PowerShell 原生命令

```powershell
# 看末尾 N 行
Get-Content .\logs\floorplan.log -Tail 50 -Encoding UTF8

# 过滤（Select-String 比 Select-String 的 -SimpleMatch 更常用）
Select-String -Path .\logs\floorplan.log -Pattern "DEALER_001" -Encoding UTF8 |
    Select-Object -Last 10 | ForEach-Object { $_.Line }

# 按级别过滤（注意：正则里的级别要匹配行首第 3 段）
Select-String -Path .\logs\floorplan.log -Pattern "\sERROR\s" -Encoding UTF8

# 统计各级别条数
# 注意：日志行首是「日期 时间 级别」，拆分后索引 0=日期 1=时间 2=级别
Get-Content .\logs\floorplan.log -Encoding UTF8 |
    ForEach-Object { ($_ -split '\s+')[2] } | Group-Object | Sort-Object Count -Descending |
    Format-Table Count, Name -AutoSize

# 实时跟随（原生等价于 tail -f，Ctrl+C 退出）
Get-Content .\logs\floorplan.log -Tail 30 -Wait -Encoding UTF8

# 实时跟随 + 过滤
Get-Content .\logs\floorplan.log -Tail 30 -Wait -Encoding UTF8 |
    Select-String -Pattern "DEALER_001"

# 按 traceId 追踪（最高效的排障手段）
Select-String -Path .\logs\floorplan.log -Pattern "<traceId>" -Encoding UTF8

# 查看历史归档（.gz 需要解压）
Get-ChildItem .\logs\archive\*.gz | ForEach-Object {
    $name = $_.Name
    & gzip -dc $_.FullName 2>$null | Select-String "ERROR" | ForEach-Object { "[$name] $($_.Line)" }
}
```

### 1.3 日志格式

```
2026-10-26 13:46:28.369 WARN  [http-nio-8080-exec-2] c.c.f.web.config.GlobalExceptionHandler - 业务异常 code=VEHICLE_001 traceId=24ebb4bb-... msg=车辆不存在：NOSUCHVIN001
│                      │      │                        │                                    │
│                      │      │                        │                                    └─ 消息正文
│                      │      │                        └─ 简写类名
│                      │      └─ 线程名（http-nio-8080-exec-N = HTTP 请求线程；main = 启动；scheduler-* = 定时任务）
│                      └─ 级别（INFO / WARN / ERROR）
└─ 精确到毫秒的时间戳
```

**关键约定：每条业务异常都带 `traceId`**，它同时出现在 HTTP 响应体的 `traceId` 字段里。
用户报错时让他把 `traceId` 给你，就能直接定位到那一行日志——这是最高效的排障入口。

### 1.4 三个值得记住的日志点

代码里目前只有 3 处主动打日志，全在 web 层：

| 位置 | 级别 | 内容 | 什么时候看 |
|---|---|---|---|
| `GlobalExceptionHandler.handleBusiness` | WARN | 业务异常 + code + traceId | 业务报错时（最常见） |
| `GlobalExceptionHandler.handleUnknown` | ERROR | 未预期异常 + 完整堆栈 | 程序有 bug 时 |
| `JwtAuthInterceptor` | WARN | 越权访问被拒（用户/角色/URI） | 排查权限问题 |

> 越权日志长这样：
> ```
> WARN ... JwtAuthInterceptor - 越权访问被拒：user=operator role=USER uri=/api/dealers
> ```
> 这是审计与事后追溯的依据，不要关掉。

### 1.5 调整日志级别

改 `web/src/main/resources/application.yml`：

```yaml
logging:
  level:
    root: INFO
    com.company.floorplan: INFO      # 改成 DEBUG 可看本项目的详细日志
```

改完重启生效。Spring Boot 会自动应用这个配置，与 `logback-spring.xml` 不冲突。

> **注意**：本项目 application / domain / infrastructure 三层**目前没有任何日志埋点**
> （只有 web 层那 3 处）。把 `com.company.floorplan` 调到 DEBUG 也看不到业务过程日志——
> 因为业务轨迹在审计表里，不在日志里。详见第 5 节。

## 2. 审计日志（audit_events 表）

### 2.1 为什么它是金融系统的核心

`audit_events` 是 **append-only**（只 INSERT，永不 UPDATE/DELETE）的操作留痕表。
每条记录都带 `actor`（谁）、`actor_role`（什么角色）、`action`（做了什么）、
`before_snapshot` / `after_snapshot`（改前改后）、`trace_id`。

监管追溯要求"能证明谁在什么时点基于什么依据做的判断"——答案全在这张表里。

> ⚠️ **历史数据说明（2026-10-26 修复前）**：
> 修复前 `actor` 取自请求头 `X-Operator-Id`，**客户端可任意伪造**。
> 因此库里存着 `1`、`verify-script`、`repair` 这类假操作人。
> **这些历史行无法追溯到真实自然人**——不是数据丢了，是当时根本没记对。
>
> | actor 值 | 含义 |
> |---|---|
> | `admin` / `operator` | 修复后记录，真实登录身份（可信） |
> | `system` | 定时作业 / 无登录态调用（本就没有自然人） |
> | `1` / `verify-script` / `repair` | **修复前的伪造值，不可信** |
>
> 排查时先看 `actor_role`：非 NULL 才是修复后可信记录。
> 历史行不做回填——append-only 表改写历史本身会破坏审计原则，
> 且当时的真实身份客观上已不存在于任何数据中。

### 2.2 直接查 SQL

```bash
docker exec floorplan-db2 psql -U floorplan -d floorplan -c "
SELECT id, actor, actor_role, action, target_type, target_id, created_at
FROM audit_events ORDER BY id DESC LIMIT 20;"
```

**按对象查**（查某个经销商/车辆的全部操作轨迹）：

```bash
docker exec floorplan-db2 psql -U floorplan -d floorplan -c "
SELECT created_at, actor, actor_role, action, before_snapshot, after_snapshot
FROM audit_events
WHERE target_type = 'DEALER' AND target_id = '207'
ORDER BY id;"
```

**查变更详情**（看改了哪些字段）：

```bash
docker exec floorplan-db2 psql -U floorplan -d floorplan -tAc "
SELECT before_snapshot||'  ==>  '||after_snapshot
FROM audit_events WHERE action = 'UPDATE_DEALER' ORDER BY id DESC LIMIT 3;"
```

**按操作人查**（谁做了什么）：

```bash
docker exec floorplan-db2 psql -U floorplan -d floorplan -c "
SELECT actor, actor_role, action, count(*) FROM audit_events
GROUP BY actor, actor_role, action ORDER BY count(*) DESC;"
```

**只看可信记录**（排除修复前的伪造值）：

```bash
docker exec floorplan-db2 psql -U floorplan -d floorplan -c "
SELECT created_at, actor, actor_role, action, target_id
FROM audit_events WHERE actor_role IS NOT NULL
ORDER BY id DESC LIMIT 20;"
```

**按 traceId 关联运行日志**：

```bash
docker exec floorplan-db2 psql -U floorplan -d floorplan -tAc "
SELECT trace_id, actor, action FROM audit_events
WHERE trace_id IS NOT NULL ORDER BY id DESC LIMIT 10;"
```

### 2.3 常见 action 取值

| action | 含义 |
|---|---|
| `CREATE_DEALER` / `UPDATE_DEALER` / `DELETE_DEALER` | 经销商增删改 |
| `CREATE_CREDIT_LINE` / `FREEZE_CREDIT_LINE` / `UNFREEZE_CREDIT_LINE` | 授信额度与冻结 |
| `UPDATE_RISK_GRADE` | 调整授信评级 |
| `RATING_CONFIG_UPSERT` | 评级口径变更 |
| `BATCH_INGEST` | 批量收车建账 |
| `ADVANCE` | 垫款放款 |
| `MARK_SOLD` | 标记车辆已售 |
| `CURTAIL_PAY` | 库龄递减还款核销 |
| `ANNUAL_REVIEW_INIT` / `ANNUAL_REVIEW_DONE` | 额度年审发起与完成 |
| `INVENTORY_AUDIT` | 实地盘点 |

> 完整清单见《数据库设计文档》3.22 节。

### 2.4 操作人是**怎么**定的（2026-10-26 修复）

修复前：各 Controller 直接取请求头 `X-Operator-Id` —— **客户端可任意伪造**，
请求方写什么审计表就记什么，整条审计链形同虚设。

修复后：新增 `web/config/AuditActor.java` 统一解析，优先级从高到低：

| 优先级 | 来源 | 可信度 |
|---|---|---|
| 1 | **令牌身份**（`authUsername`，服务端验签得来） | ✅ 不可伪造 |
| 2 | 请求头 `X-Operator-Id` | ⚠️ 仅无令牌场景兜底（定时作业） |
| 3 | 字面量 `system` | 系统操作 |

**验证方法**（冒烟测试 ⑲-b 段已内置）：

```bash
# 带 admin 令牌 + 伪造头 X-Operator-Id: forged_hacker 去创建经销商
# 然后查审计表 —— actor 应该是 admin，不是 forged_hacker
docker exec floorplan-db2 psql -U floorplan -d floorplan -tAc "
SELECT actor, actor_role FROM audit_events
WHERE action='CREATE_DEALER' ORDER BY id DESC LIMIT 3;"
```

> `actor_role` 此前从未被写入（表里有列，622 条全是 NULL）。
> 现在按 `actor` 反查 `users.role` 自动补齐 —— 内控铁律"发起与执行分离"
> 要能验证，靠的就是角色差异。

## 3. 风险告警（alerts 表 + API）

### 3.1 通过 API 查（推荐）

```bash
# 先登录拿 token（走网关 → auth-service）
TOKEN=$(curl -s --noproxy '*' -X POST http://127.0.0.1:18080/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"admin123"}' \
  | python3 -c "import sys,json;print(json.load(sys.stdin)['data']['token'])")

# 查告警（走网关 → risk-service）
curl -s --noproxy '*' "http://127.0.0.1:18080/api/alerts?limit=20" -H "Authorization: Bearer $TOKEN"
```

也可用前端页面：**风险告警**（`#/alerts`），侧边栏带未处理数量徽章。

### 3.2 通过 SQL 查

```bash
docker exec floorplan-db2 psql -U floorplan -d floorplan -c "
SELECT created_at, alert_type, severity, status, vin, detail
FROM alerts ORDER BY id DESC LIMIT 20;"
```

**只看待处理的**：

```bash
docker exec floorplan-db2 psql -U floorplan -d floorplan -c "
SELECT alert_type, severity, count(*) FROM alerts
WHERE status = 'OPEN' GROUP BY alert_type, severity ORDER BY count(*) DESC;"
```

### 3.3 告警类型速查

| 类型 | 级别 | 含义 |
|---|---|---|
| `SETTLE_GRACE` | MEDIUM | 超结算窗口但在宽限期内（**告警但允许**继续） |
| `OOT_SUSPECTED` | HIGH | 超宽限期未还款，车辆转 OVERDUE，脱信销售嫌疑 |
| `AGING` | MEDIUM | 库龄达阈值，触发递减还款计划 |
| `CREDIT_FROZEN` | HIGH | 授信额度被冻结 |
| `DISPOSAL_OPEN` | HIGH | 违约处置工单已开 |
| `AUDIT_MISMATCH` | HIGH | 实地盘点账实不符 |
| `AUDIT_UNEXPECTED` | MEDIUM | 现场发现台账外车辆 |
| `INSURANCE_CLAIM` | MEDIUM | 保险出险待评估是否冲抵垫款 |

> ⚠️ **重要边界（2026-10-26 核查确认）**：
> 告警**不会**自动改变经销商的授信评级。`dealers.risk_grade` 只有一个人工写入口
> `PUT /api/dealers/{id}/risk-grade`。这是有意的设计边界（金融内控：评级变更须人工复核）。
> 详见《业务流程文档》默认值清单第 7 项。

## 4. 批处理记录（batch_runs 表）

### 4.1 查作业运行情况

```bash
docker exec floorplan-db2 psql -U floorplan -d floorplan -c "
SELECT job_name, biz_date, status, started_at, finished_at, error_detail

### 4.2 已知作业

| job_name | 干什么 |
|---|---|
| `DAILY_INTEREST` | 每日计息 |
| `INTEREST_ARCHIVE` | 计息流水季度归档 |
| `SETTLE_WINDOW_SCAN` | 结算窗口扫描（超期转脱信嫌疑） |
| `DEFAULT_DISPOSAL` | 违约处置开单 |
| `ANNUAL_REVIEW_SCAN` | 额度年审扫描 |

**幂等键是 `(job_name, biz_date)`**——同一天同一作业重复跑会被拦掉，
所以排障时重跑作业前要意识到这一点（`INSERT ... ON CONFLICT DO NOTHING`）。

## 5. 一个必须知道的现状

### 5.1 业务操作不写运行日志

本项目当前**只在 web 层有 3 处日志埋点**（见 1.4），应用层（`application`）、
领域层（`domain`）、基础设施层（`infrastructure`）**均无日志**。

意味着：

| 你想知道 | 去哪查 |
|---|---|
| 这次请求报了什么错 | ① 运行日志（有 traceId） |
| **谁在什么时候改了哪个经销商** | ② `audit_events` 表 |
| 系统判定了哪些风险 | ③ `alerts` 表 |
| 定时作业跑没跑 | ④ `batch_runs` 表 |

**业务轨迹查审计表，不查运行日志。**

### 5.2 为什么这样设计（不是遗漏）

审计表是 append-only 的结构化表，能按对象/操作人/时间精确检索，比翻日志文本可靠得多；
金融系统的追溯要求本来就落在结构化审计上，而不是靠 grep 日志。

运行日志的定位是**技术排障**（进程启停、异常堆栈、越权拦截），不是业务追溯。

### 5.3 如果要补业务日志

在应用层加 `log.info` 是可行的，但要注意两点：

1. **别把业务轨迹只写日志**——日志会滚（30 天）、会丢、无法结构化查询。
   真正需要追溯的动作必须写 `audit_events`。
2. **别在事务里打 INFO 级日志做关键节点**——事务回滚后日志不会回滚，
   会出现"日志说有这笔操作，数据库里没有"的错觉。

### 5.4 操作人已经可信了（2026-10-26 修复）

此前 `audit_events.actor` 来自可伪造的请求头，现已改为服务端验签的令牌身份。
详见 2.4 节。**这意味着审计表现在可以真正回答"谁做的"**——
但仅对修复后产生的记录成立（历史行的 actor 是假值，见 2.1）。

## 7. 附：编码问题（已修复，供参考）

**现象**：日志里中文全是 `ҵ���异常` 这样的乱码。

**根因**：Windows 环境 JVM 默认 `file.encoding=GBK`（控制台代码页 936），
而日志文件被按 GBK 写入、按 UTF-8 读取，必然乱码。

**修复**（2026-10-26 已落地）：

1. `logback-spring.xml` 里所有 encoder 加 `<charset>UTF-8</charset>`
2. 启动加 `-Dfile.encoding=UTF-8 -Dstdout.encoding=UTF-8`
3. `run-local.sh` / `run-docker.sh` 已固化上述参数

**验证**：日志文件中的中文为 UTF-8 三字节序列（`e8 bd a6 ...`），
严格 UTF-8 解码通过，控制台与文件两侧一致。

> **如果看到乱码**，先检查启动命令里有没有 `-Dfile.encoding=UTF-8`。
> 临时补救：`iconv -f GBK -t UTF-8 logs/floorplan.log`（仅适用于本项目修复前的旧日志）。

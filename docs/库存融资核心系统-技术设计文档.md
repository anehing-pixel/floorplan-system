## 1. 技术选型与分工

| 领域 | 选型 | 分工理由 |
|---|---|---|
| 框架 | Spring Boot 3.2.5 + Spring Cloud 2023.0.5（Maven 多模块） | 起步为模块化单体，后期按限界上下文物理拆成网关 + 5 服务；核心账务因事务红线保留单体 |
| 简单实体 CRUD | Spring Data JPA | 经销商、字典类等简单实体，提升开发效率 |
| **计息 / 对账 / 复杂报表** | **MyBatis 或 JdbcTemplate 手写 SQL** | 精确可控，避开 JPA 懒加载与 N+1；账务正确性优先 |
| 批处理 | Spring Batch + Quartz / `@Scheduled` | 日终作业需可重跑、有执行记录 |
| 安全 | Spring Security + 自定义投票器 | 落实"发起与执行分离"的方法级鉴权 |
| 数据库 | PostgreSQL | 沿用现有；行锁、唯一约束能力强 |
| 金额 | Java `long`（整数日元）；比率用 `BigDecimal` | 消灭浮点误差 |
| 外部对接 | 独立 `integration` 模块 + 防腐层 | 隔离外部变更（见外部集成文档） |

**JPA / MyBatis 边界（重要）**

```
JPA      → dealers、holidays、字典类、简单查询
MyBatis  → interest_ledger 写入与汇总、对账、报表、
           vehicle_units 批量扫描（计息/库龄/结算窗口）
禁止     → 在 JPA 实体上写复杂业务规则回调（ADR-002）
```

## 2. 分层与依赖规则

```
web / external-api     接口层（校验、呈现、鉴权）
        ↓
application            用例编排 · @Transactional 事务边界 · 权限审批
        ↓
domain                 聚合根 · 不变量 · 状态机 · 计息规则（不依赖 Spring）
        ↑
infrastructure         JPA/MyBatis 映射 · 事件表 · 外部适配
integration            厂家/支付/登记对接（隔离外部变更）
```

**铁律**
1. `domain` **不依赖任何框架**（无 Spring 注解），保证领域逻辑可单测、可迁移
2. `@Transactional` **只出现在 `application` 层**；嵌套调用语义显式声明
3. 事务内**禁止外部 IO**（远程调用、文件读写、消息发送）——见 ADR-006
4. `web`/`external-api` **不得直接修改领域对象**，必须经应用服务

## 2.5 授权层设计（RBAC，2026-10-26 落地）

> 完整角色清单与业务映射见《库存融资核心系统-角色与权限矩阵.md》。此处只记技术要点。

### 2.5.1 三层结构

```
domain/model/Permission.java            权限点枚举（23 个原子操作）
domain/model/UserRole.java               角色枚举（14 个），持有 Set<Permission>
domain/service/RoleSeparationPolicy.java 权限并集解析 · 不相容矩阵 · 自然人级校验
        ↑
web/security/RequirePermission.java     接口声明所需权限点
web/config/JwtAuthInterceptor.java       按权限点判定
```

**为什么权限点与角色分两层**：角色随组织调整而变，权限点由接口决定、相对稳定。
若把动作直接挂在角色上，每新增一个接口就得改角色定义，权限矩阵会迅速腐化。
现在新增接口只动接口一侧，新增岗位才动角色一侧。

### 2.5.2 判定流程

```
请求 → JWT 拦截器验签 → 取令牌里的 perms（登录时按角色并集算好）
     → 读接口上的 @RequirePermission → 权限点全部命中则放行，否则 403 AUTH_002
```

**权限点放令牌而非每次查库**：避免每请求查一次 `user_roles`。
代价是角色调整要等令牌过期（默认 8 小时）——紧急撤权走"禁用账号"通道。

### 2.5.3 两层职责分离

| 层 | 时机 | 机制 | 违反后果 |
|---|---|---|---|
| 角色层 | 人员配置时 | `RoleSeparationPolicy.findConflicts()` | **告警提示**，不阻断（一人多岗现实中常见） |
| 自然人层 | 业务运行时 | `RoleSeparationPolicy.assertNoSelfApproval()` | **硬阻断** 403 `AUTH_003` |

> 自然人层是防资损的最后一道闸：一人多岗时申请人与复核人可能持有同一角色，
> 但**必须是两个人**。角色区分挡不住这种情况。

### 2.5.4 关键设计取舍

**管理员不碰业务单据**：`SYSTEM_ADMIN` 刻意不持垫款申请/复核/支付、还款核销、处置等权限点。
管理员万能则双人复核形同虚设。管理员操作全部进审计表，可查但不能代行业务审批。

**读接口不设权限点**：所有已登录用户开放。风控岗要看档案、催收岗要看台账，
把读也收口会让"越权"变成"业务干不了活"。

**`users.role` 保留 + `user_roles` 新增**：既有审计字段 `actor_role` 依赖单值列，
删列会连带改审计链。保留它做主角色与展示，授权判定另走关联表。

## 3. 领域层设计

> **v1.1 扩展**：补齐业务流程文档的 P0/P1 缺口对应的领域对象——库龄递减还款（`CurtailmentPlan`）、违约处置（`DisposalCase`）、权属校验（重复融资拦截）、保险/回购/结清证明/年审。

| 聚合根 | 不变量 | 关键行为 |
|---|---|---|
| `Dealer` | 授信额度 ≤ 核定上限 | 评级调整、准入/终止、**年审（`annualReview()`）** |
| `CreditLine` | 占用 + 冻结 ≤ 核定；释放须对应还款 | `occupy(amount)`、`release(amount)`、`freeze(amount)`、**解冻 `unfreeze(amount)`** |
| `VehicleUnit` | 状态机合法流转；一台车唯一状态；售出须先结清 | `finance()`、`stockIn()`、`markSold()`、`settle()`、`toOverdue()`、**`repossess()`、`dispose()`** |
| `OwnershipCheck` | **VIN 全局唯一；不得在他处抵押/查封** | `verify(vin)`：建账前权属校验（**P0-③ 重复融资拦截**） |
| `CurtailmentPlan` | 已还期数 ≤ 总期数；每期金额 = 原始垫款 × 比例 | `generate()`、`due()`、`payPeriod()`（**P0-① 库龄递减还款**） |
| `DisposalCase` | 处置状态合法流转；残值核算不超应收 | `open()`、`repossess()`、`liquidate()`、`closeWithLoss()`（**P0-② 违约处置**） |
| `InsurancePolicy` / `RepurchaseRequest` / `PayoffCertificate` | 关联 VIN；状态机合法 | 保险报案/理赔、厂家回购兑现、结清证明出具（**P1**） |

**状态机实现**：显式方法 + 枚举流转表，**不使用框架回调**。非法流转抛领域异常 → `VEHICLE_002`。

```java
// 显式流转白名单（示例，含违约处置）
FINANCED     → IN_STOCK, CLOSED
IN_STOCK     → SOLD_PENDING, OVERDUE, DISPOSING
SOLD_PENDING → SETTLED, OVERDUE
OVERDUE      → SETTLED, DISPOSING          // 补缴可恢复结清
DISPOSING    → CLOSED, SETTLED             // 处置中补缴为例外
```

**重复融资拦截（P0-③）**——`OwnershipCheck.verify(vin)` 在 `batch-ingest` 落库前执行：
1. 查本系统 `vehicle_units` 是否已存在该 VIN（`VEHICLE_003`）；
2. 查外部权属/抵押查封登记（渠道见外部集成文档；无接口时走人工录入的 `financing_lien_checks`）；
3. 任一项命中 → 拒绝建账并标记 `duplicateFinanced`。

## 4. 事务与并发设计

| 场景 | 机制 |
|---|---|
| 额度占用/释放 | `SELECT ... FOR UPDATE` 行锁（同一 `credit_lines` 行）→ 校验 → 更新 → 提交 |
| 车辆状态流转 | `version` 乐观锁；冲突重试 |
| 垫款原子性 | 业务事务内：占额度 + 建台账 + 写支付指令（**支付是否同事务见 ADR-006**） |
| 结清原子性 | 还款核销 + 解除担保 + 额度回补，**三者同一事务** |
| 批处理 | 按业务日幂等；`batch_runs` 唯一约束防重跑 |

**并发陷阱清单**

| 陷阱 | 对策 |
|---|---|
| 无锁读-改-写导致额度超额 | 强制行锁，禁止 `SELECT` 后 Java 内计算再 `UPDATE` |
| JPA 懒加载 / N+1 | 复杂查询走 MyBatis；报表批量分页读取 |
| 事务传播混乱 | `@Transactional` 仅 `application`；跨聚合调用显式声明传播行为 |
| 长事务持锁 | 事务内不做外部 IO（ADR-006） |

## 5. 计息引擎设计（核心）

### 5.1 计算规则

```
日息 = 未偿本金 × 年利率 ÷ 365        默认 365 天基准
累计利息 = Σ 每日日息
```

- 起息日：垫款支付日（默认含当日，已实现并经冒烟验证）
- 止息日：结清日（售出结清即停止）
- 利率变更：每次计息写入 `rate_snapshot`；利率调整后**支持按历史快照重算**

### 5.2 精度与舍入（默认口径）

推荐方案：**逐日量化 + 结清以流水汇总为准**

1. 日息计算用高精度定点（`BigDecimal`）中间值
2. 落 `interest_ledger.daily_interest` 时**量化为整数日元**（默认四舍五入）
3. 结清时的应收利息 = `interest_ledger` 按 VIN **汇总值**（而非重算）

> 理由：每日金额为整数便于逐笔对账与审计；以流水汇总为准避免"重算与流水不一致"。
> **风险**：逐日舍入会产生微小累积误差。**替代方案**是"日息保留高精度、账单周期末舍入一次"——更精确但对账粒度变粗。**默认采用逐日四舍五入（已实现并经冒烟验证）**。

### 5.3 可重跑与可追溯

- 幂等基石：`interest_ledger(vin, biz_date)` **唯一约束**
- 重跑语义：同一业务日重复执行 → 冲突跳过（不覆盖、不翻倍）
- 执行记录：`batch_runs(job_name, biz_date)` 唯一约束
- 追溯：每次计息存 `rate_snapshot` 与 `principal_balance`，可还原任何一天的计息依据

### 5.4 边界用例（测试必须覆盖）

| 用例 | 说明 |
|---|---|
| 提前还款 | 计息止于还款日 |
| 部分还款 | 本金变更后日息基数随之变化 |
| 利率中途变更 | 变更前用旧快照、变更后用新快照 |
| 跨月 | 按月边界正确切分 |
| 节假日 | 按营业日历，计息逐自然日计提，营业日历仅用于结算窗口与宽限期（默认周末为非营业日，法定假日经 /api/jobs/holidays 维护） |
| 厂家贴息轧差 | 贴息与利息抵扣后的净额计算 |
| 闰年 | 365 基准下的处理 |

## 7. 领域事件与异步消费

**事件**：`VehicleSold` / `AdvancePaid` / `RepaymentSettled` / `AgingTriggered` / `AuditMismatch` / `CreditFrozen`

**机制**：事件与业务操作**同一事务写入事件表**（保证不丢），由独立消费者异步处理。

| 要点 | 设计 |
|---|---|
| 投递保证 | 至少一次（at-least-once） |
| 消费幂等 | 消费者按 `event_id` 去重，业务侧幂等 |
| 失败重试 | 指数退避；超次数进死信，告警人工介入 |
| 顺序 | 同一 `vin` 的事件需保序（按事件表自增 ID 或版本号） |
| 监控 | 积压量、消费失败率纳入告警 |

## 8. 日志、监控与告警

**日志**
- 全链路 `traceId`（接口 → 应用 → 批处理），错误响应返回 `traceId`
- 账务类操作（垫款/还款/计息/额度变更）**必打审计日志**
- 禁止日志输出完整 VIN、金额明细等敏感信息（脱敏）

**核心监控指标**

| 类别 | 指标 |
|---|---|
| 批处理 | 作业成功率、耗时、失败次数、积压 |
| 账务 | 计息金额日环比异常、对账差异笔数 |
| 额度 | 额度使用率、冻结笔数、超额拒绝次数 |
| 风险 | OOT 告警数、逾期笔数、盘点差异数 |
| 集成 | 外部调用成功率、超时率、重试次数 |
| 接口 | QPS、错误码分布、P95 延迟 |

**告警规则（默认按事件类型固定级别，一期不做数值化阈值配置）**

| 告警 | 触发 |
|---|---|
| 批处理失败 | `DAILY_INTEREST` 失败 → **立即告警**（阻断次日业务） |
| 对账差异 | `diff_amount != 0` → 告警（金融系统零容忍） |
| 支付失败 | 连续失败 N 次 → 告警 + 转人工 |
| OOT 告警 | `OOT_SUSPECTED` 产生 → 高优先级通知风控 |
| 额度超额拒绝 | 频次突增 → 排查是否额度配置异常 |

## 10. 性能考量

本系统**低 QPS + 事务密集 + 批处理量大**，性能重点不在接口而在批处理：

| 关注点 | 设计 |
|---|---|
| 计息批量 | 分页批量读取在库车辆（避免全表加载）；批量写入 `interest_ledger` |
| 锁竞争 | 额度行锁粒度为单经销商；热点经销商（大量并发垫款）需关注，必要时评估分段额度 |
| 报表查询 | 走 MyBatis 手写 SQL + 只读副本（避免拖慢生产主库） |
| 数据归档 | `interest_ledger`、`audit_events` 增长快，需设计归档策略（默认：`interest_ledger` 按季度归档已实现；`audit_events` 二期） |

## 11. AI 辅助编程约束（落地要点）

1. AI 只出样板：Entity / DTO / Mapper / Controller 骨架、MyBatis XML、测试骨架
2. 计息、额度、批处理核心 **100% 人工 review + 强测试**
3. 维护编码规范文件（分层、金额 `long`、事务边界、不变量），作为 AI 输入约束
4. **禁止把业务规则藏在框架回调中**（Rails 的 callback 债不得在 Java 重现）

## 12. 默认值汇总（已采纳，可配置调整）

| # | 项 | 预设值 | 影响 |

| 7 | 告警阈值 | 按事件类型固定级别（见第 8 节） | 告警配置 |

| 9b | 上游直付与收款账户（ADR-007（最终版）） | **提案待评审**：打款对象由**采购订单**（`purchase_orders`）决定——订单携带 `supplier_type` + `payee_account_ref`，放款时冻结账户快照；`supplier_type` 派生打款模式：`DIRECT_PAY`（代付上游：销售公司/总代理/批发/拍卖）vs `SELF_PAY`（回款经销商，属营运资金），**两套放款校验链**；**导入两条通道**（API 直连 / Excel·CSV 批量），落库前人工确认按通道分级（API 可豁免）；**原始凭证存 S3**（预签名 URL 直传、应用不过流、Object Lock 保不可变、库只存元数据） | 放款收款方 |
| 10 | 报表是否走只读副本 | 一期不引入（数据量小），预留只读副本扩展 | 生产库负载 |
| 11 | 授信评级分级口径 | **预设 A(+0)/B(+0.5%)/C(+1.0%)/D(+2.0%，暂不准入)**，后台动态配置、可随时经 `/api/rating-configs` 调整 | 执行利率、准入 |
| 12 | 结算窗口宽限期 | 5 个营业日（告警但允许，超限升级 OOT） | `SETTLE_WINDOW_SCAN` |

## 13. 流程缺口对照（与业务流程文档 P0/P1 对齐）

> 本节把业务流程文档的缺漏结论落到技术侧。**P0/P1 的基础闭环均已实现**，
> 并由 `smoke-test.py`（⑧~⑱ 节）覆盖。
>
> ⚠️ **"基础闭环"≠"完整闭环"**：P0-①、P0-② 仍各有增强项未做，
> 且 §4/§8 存在断点，完整清单以《十一环节闭环核查报告》§3、§8 为准。
> 本节仅说明"每个缺口有代码落点"，**不表示该环节已贯通**。

| 缺口 | 技术落点 | 现状 |
|---|---|---|
| P0-① 库龄递减还款 | `CurtailmentApplicationService` 三件事：扣本金（`applyPrincipalPayment`）→ 推进计划（`paid_periods+1`、顺延 `next_due_date`）→ 写核销流水（`curtailment_payments`，幂等键唯一兜底）；**不释放额度**，本金减少后日息基数随之下降 | ✅ 已实现 |
| P0-② 违约处置闭环 | `DisposalCase` 状态机 OPEN → REPOSSESSED → LIQUIDATING → CLOSED_LOSS/CLOSED_RECOVERED；损失=应收（本金+利息流水汇总）−变现；`SETTLE_WINDOW_SCAN` 贴合日本实务"告警但允许"（宽限期预设 5 营业日内仅 MEDIUM 告警，超限升级 OOT → OVERDUE），`DEFAULT_DISPOSAL` 扫描对 OVERDUE 车自动开单 | ✅ 已实现 |
| P0-③ 重复融资拦截 | `financing_lien_checks` 权属核对录入（`POST /api/vehicles/{vin}/lien-check`）+ `batch-ingest` 前置校验（最新核对 `encumbered=true` → `VEHICLE_005` 拒绝） | ✅ 已实现 |
| P1 额度年审冻结恢复 | `AnnualReviewApplicationService`：发起冻结（量=发起时 `used_amount`）→ 复核通过解冻恢复 ACTIVE；`ANNUAL_REVIEW_SCAN` 对超期未审的 ACTIVE 额度自动发起 | ✅ 已实现 |
| P1 保险/展期/回购/部分还款/结清证明 | 保险投保→理赔（ACTIVE→CLAIMED）；展期顺延 `settle_due_date` 并清除 OOT 标记；厂家回购兑现冲抵本金不自动结清；部分还款只扣本金不解押不回补（`repayments.repayment_type=PARTIAL`）；结清证明（`PAYOFF_001` 仅整台结清可开） | ✅ 已实现 |
| 授信评级分级口径 | **后台动态配置**（默认口径 A/B/C/D）：口径落 `rating_configs` 表（V3 迁移，预置 A/B/C/D 种子），`GET/PUT /api/rating-configs` 运行时维护、**即时生效无需发版**；执行利率=基准年利率+评级加点（建账时按经销商评级解析）；加点上限 `floorplan.rating.max-rate-surcharge`（预设 0.05）；`allowed=false` 停用等级不准入新业务（`RATING_001`）；变更写审计（`RATING_CONFIG_UPSERT`/`UPDATE_RISK_GRADE`） | ✅ 已实现 |
| 计息流水归档 | 预设**按季度**归档：`POST /api/jobs/archive` 把早于本季度首日的流水复制到 `interest_ledger_archive`（`LIKE ... INCLUDING ALL`）后删除，幂等可重跑 | ✅ 已实现 |

> 接口契约见接口文档 §4.14；表结构见数据库设计文档 §3.21（V2/V3 迁移）。

## 1. Context（背景）

### 1.1 业务诉求

日本新车渠道的库存融资（Floorplan）在贷后管理上有两条必须分开的业务主线：

| 主线 | 业务含义 | 时点 |
|---|---|---|
| **快逾期预警** | 还款日临近，**预防性提醒** | 到期前 T-3 / T-1 |
| **正式逾期** | 到期未足额还款，**进入逾期流程** | 到期日之后 |

两者的**动作完全不同**：

- 快逾期：通知经销商与客户经理、必要时降低额度、提高检查频次
- 正式逾期：标记逾期、计算 DPD/M1M2M3、触发催收、冻结额度、生成盘点任务、进入处置

**快逾期不得标记逾期**——否则预警频次会把逾期统计污染，DPD（逾期天数）失去意义，
风控口径失真。

### 1.2 现状与问题

2026-10-26 核查（代码与数据库实测）：

| 事实 | 证据 |
|---|---|
| `vehicle_units` 40 个字段中**无任何期限字段** | `\d vehicle_units` |
| `overdue_days` 是**死字段** | 全库仅 `AdvanceApplicationService:184`、`ExtensionApplicationService:62` 两处 `setOverdueDays(0)`，**从未被计算** |
| `vehicle_units.advance_id` 字段**存在但从未写入** | 26 台车全部为 NULL；仅 `JdbcVehicleUnitRepository:88` 有读取代码，无 `setAdvanceId` 调用 |
| **同一 VIN 可能有多笔 advance** | 库内 `COLA017481`、`COLB017481` 各有 2 笔<br>⚠️ **2026-10-26 经 ADR-010 深度核查更正：该实证是"重复提交"脏数据，非业务一车多债**，见 §1.5 |
| **不存在借据实体** | `advances` 的 status 是 `PENDING→PROCESSING→PAID`，是**支付指令状态**，不是债务状态 |
| **不存在还款计划实体** | `aging_plans` 是库龄递减还款计划（另一种还款形态），不是按期还款计划 |

### 1.3 我此前设计中的错误（需修正）

《贷后监管设计》§1.2 提出：在 `vehicle_units` 上加 `maturity_date` /
`grace_period_days` / `overdue_rate` / `term_source`，
并以 `maturity_date` 为基准计算 `overdue_days`。

**这个设计是错的。** 错在把**债务状态挂在资产实体上**。

### 1.4 架构问题诊断

**VIN 台账是"车"的视图，借据是"债"的视图。二者不是一对一。**

```
一车一债？  否。
```

实证：库内 `COLA017481` 有 2 笔 advance。业务上这意味着：
一台车被**两次融资**（先融资 A 买入 → 售出 → 再融资 B 买入），
或**部分融资**（同一批采购多笔放款）。

> ⚠️ **2026-10-26 勘误（见 ADR-010 §7.1）**：上述"库内实证"**不能作为业务一车多债的证据**。
> 经深度核查，那 2 笔 advance 是**同一笔垫款申请被重复提交两次**造成的脏数据
> （33 毫秒内提交 4 次、金额完全相同、`idempotency_key` 各不相同、`purchase_order_id` 全为 NULL），
> 且导致额度被重复占用 4 份——属**资损级实现缺陷**，非业务场景。
>
> **但本 ADR 的结论不变**："一车多债"在业务上确实允许（分批放款 / 结清后再融资），
> 借据模型依然是正解；只是需要**另行举业务例证**，不能用该脏数据来证明。
> 本勘误反而**强化**了借据模型的必要性——没有借据就没有额度占用的唯一锚点，
> 一车多债也无法被正确表达（详见 ADR-010 §5.4）。

在这种情况下，单个 VIN 上挂一个 `maturity_date` 会产生三个具体错误：

| 错误 | 表现 |
|---|---|
| **多债覆盖** | 第二次融资的期限覆盖了第一次的期限，第一笔债的逾期无法表达 |
| **历史污染** | 车已结清、重新融资后，旧的逾期天数若未清零，新债会被误判为"已逾期 N 天" |
| **审计断链** | 逾期是**债务事件**，挂在车上有违事实归属——同一台车不同时期的债务责任混在一起 |

**债务的期限、还款计划、履约记录，其归属主体是"借据"**——
借据有独立生命周期（发放→存续→分期偿还→结清/核销/转处置），
可以独立于车存在（车已处置，债仍在）。

## 2. Decision（决策）

### 2.1 核心决策

> **逾期状态挂在借据（Loan）实体上；VIN 台账上的逾期标记是派生结果，不是数据源。**

三层实体，各司其职：

```
┌─────────────────────────────────────────────────────────────┐
│ ① 借据层（Loan）—— 债务的事实来源                            │
│    loan_id / vin / 金额 / 期限 / 到期日 / 宽限期 / 罚息利率   │
│    status: DRAFT→ACTIVE→OVERDUE→SETTLING→SETTLED/DEFAULTED  │
│    逾期状态机住在这里                                        │
└──────────────────────┬──────────────────────────────────────┘
                       │ 一对多（同一 VIN 可有多笔借据）
                       ▼
┌─────────────────────────────────────────────────────────────┐
│ ② 还款计划层（RepaymentSchedule）—— 到期的来源              │
│    每期：期号 / 到期日 / 应还本息 / 已还 / 状态              │
│    还款日未足额还款 → 触发借据状态机                         │
└──────────────────────┬──────────────────────────────────────┘
                       │ 派生
                       ▼
┌─────────────────────────────────────────────────────────────┐
│ ③ VIN 台账层（vehicle_units）—— 快速查询视图                │
│    loan_overdue_flag / derived_overdue_days / derived_dpd   │
│    ⚠️ 派生字段：由借据状态同步而来，不可独立写入              │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 为什么 `advances` 不能直接充当借据

| 维度 | `advances`（支付指令） | 借据 `loans`（债务） |
|---|---|---|
| 生命周期 | PENDING→PROCESSING→PAID（付款流程） | ACTIVE→OVERDUE→SETTLED（债务存续） |
| 数量关系 | 一次放款一条 | 一次放款产生一笔债 |
| 关键属性 | 付款人、付款参考号、幂等键 | 期限、到期日、还款计划、履约记录 |
| 何时结束 | 银行回调确认即结束 | 债务还清/核销才结束 |
| 可否回滚 | PROCESSING 可转 FAILED | 不可回滚（债已产生） |

**关系**：`advance` 是**资金的流动**，借据是**债权的产生**。
一次放款 = 一笔 advance + 一笔 loan（且 loan 引用 advance 作为资金来源凭证）。

> **建模提醒**：`loan.advance_id` 指向 `advances.id`，
> `advance` 是 loan 的**资金来源证明**，不是 loan 本身。
> 银行回调（PAID）确认后才创建 loan——**钱没到，债不成立**。

### 2.3 两层触发严格分离

这是本次决策的第二个核心。**两层的产物、动作、数据源全部不同**：

| 维度 | 快逾期预警层 | 正式逾期层 |
|---|---|---|
| 触发时点 | 到期前 T-N 天（N 可配，默认 3/1） | 到期日之后（宽限期届满） |
| 数据源 | 还款计划的**未来到期日** | **已过期的还款计划 + 实际回款** |
| 判定 | 即将到期 + 余额/代偿能力/历史逾期 | 到期日已过 + 未足额还款 |
| 产物 | 预警记录（`pre_due_alerts`） | **借据状态迁移** + 逾期记录（`overdue_records`） |
| 是否改借据状态 | ❌ **绝对不改** | ✅ 迁到 `OVERDUE` |
| 是否写 VIN 逾期标记 | ❌ **绝对不写** | ✅ 写（派生） |
| 动作 | 通知经销商/客户经理、降额、提高检查频次 | 催收、冻结额度、盘点任务、处置、征信报送 |
| DPD 计算 | ❌ 不算 | ✅ 算 |

**硬约束**（违反即为缺陷）：

1. 预警 job **不得**调用借据状态机的逾期迁移方法
2. 预警 job **不得**写 `vehicle_units` 的任何逾期派生字段
3. 逾期记录只在借据状态机迁移到 `OVERDUE` 时**创建**，不独立产生
4. VIN 派生标记**只由借据状态同步器写入**，全库无第二个写入点

> **为什么第 4 条重要**：派生字段有两个写入点，就会有"某处写了 A 值、某处写了 B 值"的
> 永久不一致，且没人能查清谁对。**单一写入点是派生字段的生命线**。

### 2.4 借据状态机

```
      ┌──────────┐
      │  DRAFT   │  借据草稿（放款已发起未确认）
      └────┬─────┘
           │ 银行回调确认（PAID）→ 债成立
           ▼
      ┌──────────┐   还款日未足额 + 宽限期届满
      │  ACTIVE  │─────────────────────────┐
      └────┬─────┘                         │
           │ 足额还款（全部计划结清）        ▼
           │                          ┌──────────┐
           │                          │ OVERDUE  │ ← 唯一的逾期入口
           │                          └────┬─────┘
           │                               │ 补还结清
           │                               ├──────────────► SETTLING ──► SETTLED
           │                               │ 转违约处置
           │                               └──────────────► DEFAULTED
           ▼
      ┌──────────┐
      │ SETTLING │  结清流程中（核销 + 解押 + 额度恢复）
      └────┬─────┘
           ▼
      ┌──────────┐
      │ SETTLED  │  终态：债权消灭
      └──────────┘
```

| 状态 | 含义 | 关键不变量 |
|---|---|---|
| `DRAFT` | 放款指令已提交，债未成立 | 银行回调失败则回退，不留债 |
| `ACTIVE` | 债存续，正常还款计划执行中 | 按期足额则永不迁移 |
| `OVERDUE` | 已逾期 | **只能由还款计划未足额触发**，不可人工直接置入 |
| `SETTLING` | 结清中 | 额度释放与担保解除在此阶段 |
| `SETTLED` | 终态，债权消灭 | 不可回退 |
| `DEFAULTED` | 终态，转违约处置 | 转入 `disposal_cases` |

**"不可人工直接置入 OVERDUE"** 是有意的：
逾期是**客观事实**（到期未付），由系统按数据判定。
人工可以**确认**逾期（认定），但不能**制造**逾期。

### 2.5 还款计划是到期的来源

**没有还款计划，就没有"到期"这个概念。**

```sql
CREATE TABLE repayment_schedules (
    id             BIGSERIAL PRIMARY KEY,
    loan_id        BIGINT      NOT NULL,
    period_no      INTEGER     NOT NULL,      -- 期号（1 起）
    due_date       DATE        NOT NULL,      -- 应还日
    principal_due  BIGINT      NOT NULL,      -- 应还本金
    interest_due   BIGINT      NOT NULL,      -- 应还利息
    total_due      BIGINT      NOT NULL,      -- 应还合计
    principal_paid BIGINT     NOT NULL DEFAULT 0,
    interest_paid  BIGINT      NOT NULL DEFAULT 0,
    paid_at        TIMESTAMPTZ,
    status         VARCHAR(16) NOT NULL DEFAULT 'PENDING',
        -- PENDING 待还 / PARTIAL 部分还 / PAID 已还清 / OVERDUE 已逾期 / WRITTEN_OFF 核销
    CONSTRAINT uk_rs_loan_period UNIQUE (loan_id, period_no)
);

CREATE INDEX IF NOT EXISTS idx_rs_due ON repayment_schedules (due_date, status);
```

**注意与 `aging_plans` 的关系**：两者是**不同形态的还款计划**，不是同一张表。

| | `aging_plans` | `repayment_schedules` |
|---|---|---|
| 形态 | 库龄递减还款（超期后强制还部分本金） | 按期还款（合同约定的固定计划） |
| 触发 | 库存龄达阈值自动生成 | 放款确认时按合同生成 |
| 频次 | 每期一次，周期固定 | 按合同约定（可能一次性/按月/按季） |
| 是否导致逾期 | **不导致**（是超期后的补救手段） | ✅ **是逾期的判定来源** |

> **一个容易搞混的点**：`aging_plans` 的存在**不影响**是否逾期。
> 车在库里、库存龄 200 天、强制还款计划一直在正常执行，
> 但**融资期限**已过——这台车**依然逾期**。
> 库龄递减是"预防残值跌破"的手段，融资期限是"债是否到期"的依据。
> **两者独立**，这条不变量在《库龄递减与强制还款设计》中已声明，此处再次确认。

### 2.6 逾期记录与 DPD 分层

```sql
CREATE TABLE overdue_records (
    id             BIGSERIAL PRIMARY KEY,
    overdue_no     VARCHAR(32) UNIQUE NOT NULL,
    loan_id        BIGINT      NOT NULL,
    vin            VARCHAR(32) NOT NULL,      -- 冗余：便于盘点/催收直接查
    dealer_id      BIGINT      NOT NULL,
    schedule_id    BIGINT      NOT NULL,       -- 触发逾期的期次
    overdue_date   DATE        NOT NULL,       -- 逾期起始日（首个未足额期的到期日）
    dpd            INTEGER     NOT NULL DEFAULT 0,  -- Days Past Due
    bucket         VARCHAR(8)  NOT NULL DEFAULT 'D0',
        -- D0 逾期当期 / M1 / M2 / M3 / M3PLUS（账龄分层，催收与征信口径）
    outstanding    BIGINT      NOT NULL,       -- 逾期未还金额
    status         VARCHAR(16) NOT NULL DEFAULT 'OPEN',
        -- OPEN 逾期中 / RESOLVED 已补还 / ESCALATED 已升级 / DEFAULTED 已转处置
    escalated_at   TIMESTAMPTZ,
    resolved_at    TIMESTAMPTZ,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uk_overdue_loan UNIQUE (loan_id)      -- 一笔借据同时只一条未结逾期记录
);
```

**DPD 的计算口径**（必须明确，否则不同报表会打架）：

```
DPD = 今日 − 逾期起始日
逾期起始日 = 首个未足额还款期的 due_date
M1 = DPD ≥ 31 天（按自然日）
M2 = DPD ≥ 61 天
M3 = DPD ≥ 91 天
```

> **⚠️ 待确认**：M1/M2/M3 的分界日按**自然日**还是**营业日**？
> 征信报送（国内）通常按自然日；日本的催收实务更倾向按**营业日**。
> 本设计默认自然日（与 DPD 的通行定义一致），需业务确认。

**「一笔借据同时只一条未结逾期记录」** 的约束很关键：
同一笔债跨 M1→M2→M3 是**同一条记录的 bucket 变化**，
不是产生多条记录。否则催收工单会重复派发。

### 2.7 VIN 侧的派生标记

```sql
ALTER TABLE vehicle_units
    ADD COLUMN IF NOT EXISTS loan_overdue_flag    BOOLEAN NOT NULL DEFAULT FALSE,
    ADD COLUMN IF NOT EXISTS derived_overdue_days INTEGER NOT NULL DEFAULT 0,
    ADD COLUMN IF NOT EXISTS derived_dpd_bucket   VARCHAR(8),
    ADD COLUMN IF NOT EXISTS derived_loan_id      BIGINT,     -- 当前逾期的借据
    ADD COLUMN IF NOT EXISTS derived_synced_at    TIMESTAMPTZ;
```

**命名带 `derived_` 前缀是刻意的**——看字段名就知道它不是数据源。

**同步器**（唯一写入点）：

```
借据状态变更（应用层）
    ↓
LoanOverdueProjection（领域服务）
    ├─ 借据 ACTIVE → 派生标记：false / 0 / null
    ├─ 借据 OVERDUE → 派生标记：true / DPD / bucket / loan_id
    └─ 借据 SETTLED/DEFAULTED → 派生标记：false / 0 / null（清零）
    ↓
vehicle_units 更新（同一事务）
```

**为什么同事务**：派生标记与借据状态**必须一致**。
若异步同步，中间存在窗口——盘点 job 可能查到"标记未逾期"的车而漏掉。

**代价**（必须说清）：
- 同步是**写放大**——每台车每次状态变化都多一次 vehicle_units 更新
- 但 `vehicle_units` 的行数是**车辆数**（万级），不是交易数（百万级），
  且同事务的写放大在数据库层面是可接受的

> **替代方案（已否决）**：不存派生标记，盘点时实时 JOIN 借据表。
> 否决理由：盘点是**批量查询 + 现场作业**，网络中断时无法实时查库；
> 且盘点人员需要**离线清单**。派生标记是这个场景的正确解法。
> **代价**：必须保证单一写入点，否则会出现标记与事实不一致。

### 2.8 快逾期预警的设计

```sql
CREATE TABLE pre_due_alerts (
    id             BIGSERIAL PRIMARY KEY,
    alert_no       VARCHAR(32) UNIQUE NOT NULL,
    loan_id        BIGINT      NOT NULL,
    schedule_id    BIGINT      NOT NULL,
    vin            VARCHAR(32) NOT NULL,
    dealer_id      BIGINT      NOT NULL,
    trigger_days   INTEGER     NOT NULL,      -- 提前几天（T-3 / T-1）
    due_date       DATE        NOT NULL,
    due_amount     BIGINT      NOT NULL,      -- 应还金额
    account_balance BIGINT,                   -- 账户余额（可空：未接入账户时）
    dealer_capacity VARCHAR(16),              -- 经销商代偿能力档（STRONG/NORMAL/WEAK）
    history_overdue_count INTEGER,            -- 历史逾期次数
    action_taken  VARCHAR(32) NOT NULL DEFAULT 'NOTIFIED',
        -- NOTIFIED 已通知 / LIMIT_CREDIT 已降额 / INCREASE_FREQ 已提频 / NO_ACTION 无动作
    notified_at   TIMESTAMPTZ,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uk_pre_due UNIQUE (schedule_id, trigger_days)   -- 同一期同一提前量只预警一次
);
```

**预警 job 的判定逻辑**（只读，不写借据）：

```
每日 T-N 执行：
  查 repayment_schedules 中 due_date ∈ [今日, 今日+N] 且 status=PENDING 的期次
  对每一期：
    计算应还金额 vs 账户余额
      余额充足 → 不预警（或仅记录）
      余额不足 / 未知 → 预警
    叠加风险因子：
      经销商代偿能力 WEAK → 提高预警级别
      历史有逾期记录 → 提高预警级别
    生成预警记录（不碰借据）
    触发通知（经销商 + 客户经理）
    必要时：建议降额 / 提高检查频次
```

**「余额未知」的处理**：银行流水可能采集中（见《回款闭环设计》§2），
此时账户余额不可知。设计成**照常预警**（保守），
但预警级别标注"余额数据不完整"——避免因为采集中就漏掉预警。

### 2.9 逾期后按 DPD 分层触发

| 阶段 | DPD 阈值 | 触发动作 | 系统落库 |
|---|---|---|---|
| **即将逾期** | 到期前 T-3/T-1 | 短信/邮件通知经销商 | `pre_due_alerts` |
| **逾期初期** | D0（宽限期届满） | 通知经销商、提醒还款 | `overdue_records` + `notifications` |
| **逾期升级** | M1（DPD ≥ 31） | 人工催收、外访 | 催收任务（`work_orders`）+ 联系记录 |
| **风险升高** | M2（DPD ≥ 61） | 冻结额度、限制新增融资 | `credit_line_freezes` |
| **资产风险** | M2+ 或 OOT 嫌疑 | 现场盘点、车辆位置核查 | 盘点任务（`work_orders`） |
| **严重逾期** | M3（DPD ≥ 91） | 委外、法务、车辆处置 | `disposal_cases` + 审批流 |

> **⚠️ 日本渠道的调整**：本项目**不做 GPS 核查**（那是中国第三方监管做法）。
> 「资产风险」阶段对应的是**实地盘点**与**登记状态核查**。
> 见《业务流程文档》第 6 节「🇯🇵 日本客户适配」。
> 用户原始描述中的 "GPS核查" 在本项目**替换为"实地盘点 + 担保登记状态核查"**。

### 2.10 盘点 job 不自行判断逾期

**这是本决策的关键推论，也是最容易被违反的一条。**

```
借据 overdue_status = OVERDUE
    → VIN 台账 loan_overdue_flag = Y（派生）
    → 盘点 job 查 loan_overdue_flag = Y 的 VIN
    → 写入盘点明细
    → 核对车辆位置、里程、保险、销售状态
    → 生成处置任务
```

**盘点 job 禁止的写法**：
```java
// ❌ 禁止：盘点自己判断逾期
if (unit.getOverdueDays() > 30) { ... }

// ❌ 禁止：盘点自己算逾期
if (ChronoUnit.DAYS.between(unit.getStockInDate(), today) > 90) { ... }
```

**盘点 job 允许的写法**：
```java
// ✅ 正确：读派生标记
if (unit.isLoanOverdue()) { ... }
```

**为什么这条如此重要**（用户原话："这样 VIN 盘点、催收、额度控制、担保释放、征信报送才不会互相冲突"）：

五个下游（盘点 / 催收 / 额度控制 / 担保释放 / 征信报送）若各写各的逾期判断，
会出现**同一天、同一台车，在五个地方得到五个不同的结论**——
比如催收岗说逾期 20 天（按还款计划算）、征信说逾期 35 天（按入库日算）、
盘点说未逾期（读的是另一个字段）。**这种不一致在监管检查中是致命的**。

**单一事实来源 → 派生 → 多处消费**，是唯一能保证一致性的结构。

### 2.11 状态变更留痕

**借据状态的每一次迁移都要留痕**——这是审计、征信报送、处置追溯的共同要求。

```sql
CREATE TABLE loan_status_history (
    id          BIGSERIAL PRIMARY KEY,
    loan_id     BIGINT NOT NULL,
    from_status VARCHAR(16),
    to_status   VARCHAR(16) NOT NULL,
    reason      VARCHAR(500),
    operator    VARCHAR(64) NOT NULL,      -- 'system' 或自然人
    occurred_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

**留痕内容**：谁（system 还是具体人）、何时、从什么状态到什么状态、依据什么。
催收时的人工处置、处置岗的结案，都必须在此留痕。

## 3. Consequences（后果）

### 3.1 变得更容易的

| 好处 | 说明 |
|---|---|
| **多笔融资可正确表达** | 每笔债有独立期限与计划，VIN 侧取"当前逾期的那笔" |
| **五个下游口径统一** | 全部读派生标记，不会互相打架 |
| **审计链完整** | 逾期事件的完整轨迹在 `loan_status_history` |
| **征信报送有据** | DPD/M1M2M3 口径统一且可复算 |
| **预警不污染逾期统计** | 快逾期只写 `pre_due_alerts`，`overdue_records` 只由状态机产生 |
| **补跑可复现** | 状态迁移是幂等的（同一输入同一结果），补跑历史日期能复现同样的判定 |

### 3.2 变得 harder 的（必须说清代价）

| 代价 | 说明 | 缓解 |
|---|---|---|
| **新增两张核心表 + 三张辅助表** | `loans` / `repayment_schedules` / `overdue_records` / `pre_due_alerts` / `loan_status_history` | 一次建好，比以后补建便宜 |
| **写放大** | 每次借据状态变更多写一次 `vehicle_units` | 车辆数远小于交易数，可接受 |
| **派生字段会"过期"** | 若同步器漏跑，标记与事实不一致 | **同事务写入**（§2.7）+ 启动期对账校验 + 每日一致性巡检 |
| **需要还款计划才能建借据** | 放款确认时要生成还款计划 | 合同要素（期限、还款方式）本就是放款必需信息 |
| **改动面大** | 现有 `repayments` / `settle` / `aging` 流程都要接借据 | 分期实施：先建借据与同步器（只读不写），再切换写入 |
| **一个 VIN 多笔债的"当前逾期"要定义** | 派生标记指向哪一笔？ | 定义为**最新一笔未结清的逾期借据**（`overdue_records` 中 OPEN 的那条） |

### 3.3 明确不做

| 项 | 原因 |
|---|---|
| **人工直接把借据置为 OVERDUE** | 逾期是客观事实，由数据判定。人工可确认、可处置，但不能制造 |
| **盘点 job 自行计算逾期** | 会造成五下游口径冲突（§2.10） |
| **预警 job 写借据状态** | 预警是预防，不是逾期 |
| **用 `vehicle_units.overdue_days` 作为逾期依据** | 现有字段是死字段且语义混乱（历史归零 + 未来可能计算），应废弃不用 |
| **GPS 核查** | 不适用日本渠道，替换为实地盘点 + 登记状态核查 |
| **按入库日算逾期** | 入库日是库存概念，与债务期限无关 |

### 3.4 迁移路径（不停机切换）

```
阶段一（只读）：建 loans / repayment_schedules / overdue_records / pre_due_alerts /
                loan_status_history 五表 + 借据读取视图（从现有 advances + repayments 推导）
                → 不改现有写入路径，用对账脚本验证推导结果与实际一致

阶段二（建档）：放款确认时创建 loan + 生成 repayment_schedules
                → 仍不改现有还款流程，只是并行建档

阶段三（切换）：还款核销改为写 repayment_schedules（按期冲销）
                → 借据状态机上线，overdue_records 开始产生

阶段四（派生）：启动 LoanOverdueProjection，同步 vehicle_units 派生标记
                → 盘点/催收/额度控制改读派生标记

阶段五（清理）：废弃 vehicle_units.overdue_days 的写入
                → 停用旧路径，冒烟测试全量回归
```

**每阶段可独立验证、可回滚**——这是选择"新增实体"而非"改造现有实体"的代价：
多几张表、多几个阶段，换来不破坏已跑通的链路。

## 4. 待确认事项

| # | 待确认 | 建议默认 | 影响 |
|---|---|---|---|
| 1 | 借据的还款方式形态 | 一次性 / 按月 / 按季 / 不定（业务约定） | `repayment_schedules` 生成逻辑 |
| 2 | 融资期限的典型值与录入责任 | 放款时录入（辅以人工读合同） | 借据建档要素 |
| 3 | 宽限期天数 | 0 天 | 逾期起算点 |
| 4 | 罚息利率 | 合同约定 | 逾期后计息 |

| 6 | 预警提前天数 | T-3 / T-1 | 预警频次 |

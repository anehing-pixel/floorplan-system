# 库存融资核心系统 · 违约处置与法律清算设计

> **定位**：本文档定义**环节⑩（违约处置与脱信销售 OOT）** 的完整系统设计，
> 覆盖从**触发违约**到**法律清算**再到**人工后台处理台账**的全链路。
>
> **核心命题**：
> **触发违约（逾期 / 已售未回款 / 库存流失 / 经销商经营恶化）→ 通知（短信・邮件）→ 法律清算 → 人工后台处理台账**。
>
> **设计原则**：系统负责**发现、记录、留痕、强制执行**；人负责**判断、决定、处置**。
> 自动触发不等于自动终局——**法律清算的每一个动作都有法律后果，必须有人签字**。
>
> **版本**：v1.0　|　**日期**：2026-10-26　|　**状态**：设计稿，待评审
> **上游依据**：《库存融资核心系统-业务流程文档》环节⑩（P0-② 违约处置闭环）、
> 《库存融资核心系统-贷后监管设计》（预警→工单→处置的驱动关系）、
> 《库存融资核心系统-库龄递减与强制还款设计》（L3 转违约的入口）、
> 《库存融资核心系统-角色与权限矩阵》（违约处置岗职责）、
> 《库存融资核心系统-ADR007上游直付与收款账户设计》（账户证据）

## 0. 现状诊断

### 0.1 已有实现（P0-② 基础闭环已落地）

| 能力 | 实现 | 状态 |
|---|---|---|
| 处置工单状态机 | `DisposalStatus`：`OPEN → REPOSSESSED → LIQUIDATING → CLOSED_RECOVERED/CLOSED_LOSS`，白名单流转（非法流转抛 `DISPOSAL_002`） | ✅ 正确 |
| 开单 | `POST /api/disposals/open` | ✅ |
| 收车 | `POST /api/disposals/{caseNo}/repossess` | ✅ |
| 变现 | `POST /api/disposals/{caseNo}/liquidate`（记录 `proceeds`） | ✅ |
| 结案 | `POST /api/disposals/{caseNo}/close`（计算 `loss_amount`） | ✅ |
| 车辆状态联动 | `IN_STOCK/SOLD_PENDING/OVERDUE → DISPOSING → CLOSED` | ✅ |
| 担保物台账联动 | 处置结案 → 担保实体权利消灭 + 抹消待办（V10） | ✅ |
| 幂等保护 | 开单前查 `findLatestByVin`，已有未结案工单则跳过 | ✅ |
| 权限控制 | `@RequirePermission(DISPOSAL_EXECUTE)`（违约处置岗） | ✅ |
| 审计留痕 | `audit_events`（`DISPOSAL_OPEN` / `DISPOSAL_CLOSE`） | ✅ |

**已有设计正确的两处**：
1. **终态不可回退**——`CLOSED_RECOVERED` / `CLOSED_LOSS` 是终态，防止结案后反复重开
2. **处置前检查车辆状态**——`open` 时校验 `unit.getStatus()`，只允许特定状态进处置

### 0.2 五个真实缺口

对照你给的四段链路，现状是**四段里有一段半是空的**：

| # | 缺口 | 现状 | 后果 |
|---|---|---|---|
| **G1** | **触发源单一** | `runDefaultDisposal` **只扫 `status=OVERDUE`** 的车 | 你列的四类触发源，**只有一类能被触发**（且那一类还得先有人把状态改成 OVERDUE） |
| **G2** | **「库存流失」无触发路径** | 盘点缺失只置 `ootSuspected=true`（布尔标记），**不改状态** | 车在盘点时"台账有、现场无"——最严重的脱信信号——**永远不会进入处置流程** |
| **G3** | **零通知能力** | 全库无 `Notification`/短信/邮件任何代码 | 违约通知、催告函、处置意向**全部无法送达**——法律上"已通知"是要件 |
| **G4** | **无法律清算阶段** | 状态机 `OPEN → REPOSSESSED → LIQUIDATING → CLOSED_*`，**没有"法律程序"这一段** | 实际日本实务中，从违约到变现之间有**担保权行使、催告、协商、诉讼/仲裁**等法律步骤，现在被压缩成"收车→变现" |
| **G5** | **处置完全不联动额度** | `DisposalApplicationService` 里 grep `frozen`/`usedAmount` **零命中** | 违约了额度不冻结——经销商还能继续放款。**这是明显的风控漏洞** |

**补充缺口**：

| # | 缺口 | 说明 |
|---|---|---|
| G6 | **无「经销商经营恶化」判定** | 没有任何经销商维度的恶化指标（连续逾期率、库存龄结构、周转放缓），只有车辆维度 |
| G7 | **无送达证明留痕** | 通知发出去了，但**对方收到了没有**没有证据。法律催告需要送达凭证 |
| G8 | **结案即终止，无复核** | `close` 直接终态，无"结案后申诉/复议"通道 |

## 1. 四类触发源的判定

### 1.1 触发源全景

你的四类触发源，落到系统里是**四种不同的数据来源与判定口径**：

| # | 触发源 | 判定依据 | 数据来源 | 严重度 | 当前状态 |
|---|---|---|---|---|---|
| **T1** | **逾期** | 融资担保期限已过（`maturity_date`）或强制还款连续未付 | `vehicle_units` + `aging_plans` + `financing_terms` | HIGH | ⚠️ **部分**（只扫 OVERDUE 状态） |
| **T2** | **已售未回款（OOT）** | 已售出 + 超过结算窗口 + 宽限期仍未回款 | `vehicle_units.sold_at` + `collateral_ledger.repaid` + `repayments` | **CRITICAL** | ⚠️ **部分**（有 OOT_SUSPECTED 告警，但不改状态） |
| **T3** | **库存流失** | 盘点时"台账有、现场无"（`audit_mismatch_count` 累积） | `inventory_audit` 提交结果 | **CRITICAL** | ❌ **完全没有** |
| **T4** | **经销商经营恶化** | 经销商维度的聚合指标恶化 | 多表聚合计算 | HIGH | ❌ **完全没有** |

### 1.2 四个触发的具体判定

#### T1 逾期（借据状态为 OVERDUE / 强制还款未付）

> **⚠️ 2026-10-26 修订**：本节初版写的是"读 `vehicle_units.maturity_date`"，
> **已按 ADR-008 改正**——逾期状态归属**借据**，VIN 侧只是派生标记。

```
条件（任一）：
  ① 借据状态：loans.status = OVERDUE
     （由还款计划未足额触发，ADR-008 §2.1）
     且 loans.term_source ≠ INFERRED（推断期限不单独触发处置，只触发预警）
  ② 强制还款：aging_plans.status = OVERDUE
     且 overdue_days > 阶梯 DISPOSE 边界（如 270 天）
动作：车状态 → OVERDUE；生成违约处置工单
```

**⚠️ 一条硬约束**：处置流程**不得**自己判断"这台车是不是逾期"。
它只读 VIN 的**派生标记** `loan_overdue_flag`（由 `LoanOverdueProjection` 写入）。
理由见 ADR-008 §2.10——盘点/催收/额度控制/担保释放/征信报送五个下游
若各写各的判断，会出现同一天同一台车在五个地方得到五个不同结论。

**注意**：T1 的两个来源要分开处理——
**期限逾期**是合同权利（金融公司有权要求还款），**强制还款未付**是合同约定的额外约束。
法律清算时这两者的依据不同（合同条款 vs 让渡担保合同），要分别记录。

#### T2 已售未回款（OOT / 脱信销售）

```
条件：
  sold = true（已交付终端客户）
  AND repaid = false
  AND today > settle_due_date + settleWindowGraceDays（结算宽限期）
动作：车状态 → OVERDUE；oot_suspected = true；生成违约处置工单
```

**OOT 是最严重的场景**，原因在《回款闭环设计》§0.1 已论证：
车已交付终端客户（不可追回），钱还没到账（不可控）——
此时这台车**既无担保物价值，也无现金流入**。

**OOT 的特殊性**：`repossess`（收车）**对它无意义**——车已经不在经销商手里了。
所以 OOT 案件应**直接进入法律程序**，不走收车步骤。这需要在状态机上体现。

#### T3 库存流失（盘点发现车不在场）

```
条件：
  盘点提交时，台账有该车但现场扫描不到
  AND audit_mismatch_count >= N（默认 1，即首次缺失即触发）
动作：
  车状态 → OVERDUE（现仅置 oot_suspected=true）
  生成违约处置工单
  同时：同经销商的所有在库车进入「待复核」标记（可能是系统性盘点错误，也可能是集体脱信）
```

**T3 是当前最大的漏洞**，理由：

盘点缺失是**唯一能发现"车实际已经不在经销商手里"的手段**。
系统所有其他信号（期限、结算窗口、库存龄）都是"结果指标"——
而盘点是"事实指标"。车不在了，其他指标会在几十天后才反映出来。

**但要防误报**：盘点可能是操作员漏扫、经销商临时挪车去交车、盘点表没更新。
所以设计成：
- 首次缺失 → 置 `OVERDUE` + **P1 工单**（催收岗核实，不必立刻走法律程序）
- 连续 N 次缺失（默认 2 次）或超过 X 天未澄清 → 升级为违约处置工单

**同时提醒**：整个经销商的车集体盘点缺失，可能是**盘点 App 故障**而不是集体脱信。
所以要加一个"同批次盘点异常率"的前置检查——若某经销商本次盘点缺失率异常高，
先查是不是系统问题。

#### T4 经销商经营恶化（经销商维度）

```
条件（任一）：
  ① 连续 M 个月逾期率 > 阈值（默认 3 个月 / 30%）
  ② 库存龄结构恶化：超期库存占比 > 阈值（默认 40%）
  ③ 额度占用率 > 阈值（默认 90%）且无新增回款
  ④ 强制还款连续未执行期数 >= K
动作：经销商维度处置（不是单车）→ 冻结额度 + 全面催收 + 发违约通知
```

**T4 与 T1–T3 的本质区别**：前三类是**单车触发**，T4 是**主体触发**。
T4 触发时不是处置某一台车，而是**对整个经销商的授信关系启动违约程序**。

**T4 的处置对象是额度，不是车**：
```
经销商经营恶化
  → 冻结全部额度（used_amount 不动，frozen_amount = approved_limit）
  → 存量车要求加速还款/展期审批
  → 停止一切新增放款
  → 发违约通知
  → 若持续恶化 → 进入法律清算（对经销商整体）
```

### 1.3 触发的去重与幂等

**现有实现是对的**：`runDefaultDisposal` 开单前查 `findLatestByVin`，已有未结案工单则跳过。
这个不变量要保留并扩展到四类触发源。

**扩展后的去重规则**：

```
触发判定（任一触发源命中）：
  查该 VIN 是否有非终态处置工单
    有 → 不重复开单，但更新工单的 trigger_sources（记录本次是哪一类触发）
    无 → 开新工单
```

**`trigger_sources` 应该是数组**：一台车可能同时命中 T1 和 T3。
记录全部触发源，对后续法律清算有意义——多重违约是加重情节。

### 1.4 触发与「标记违约」的边界

你说「系统自动标记违约，冻结额度」——这里有个必须区分的概念：

| 概念 | 含义 | 谁来定 | 后果 |
|---|---|---|---|
| **违约事实** | 客观事实（期限已过、车不在了、钱没回） | **系统自动判定** | 生成工单 + 预警 |
| **违约认定** | 法律意义的违约认定（含抗辩、协商、宽限） | **人工（违约处置岗 + 法务）** | 走法律程序、发正式通知 |

**设计**：系统自动做「**标记违约待处理**」，**不能自动发正式违约通知**。

理由：正式违约通知是**法律行为**，需要准确的事实认定与法律文书。
系统因为口径或数据问题误判（期限录错、盘点漏扫、流水未采集）而自动发出违约通知，
会**直接损害与客户的关系**，且在争议中构成己方过错。

**所以流程是**：
```
系统自动：标记违约 + 冻结额度 + 生成工单（附完整事实与依据）
        ↓
人工核实：确认事实无误 → 批准发出通知
        ↓
系统发出：短信 + 邮件 + 书面送达（可配置是否自动发）
```

**唯一例外**：若合同明确约定"逾期 X 日自动视为违约并触发条款"，且期限数据
`term_source = CONTRACT`（合同录入，非推断），可配置为自动发通知。
**`term_source = MANUAL_REVIEW` 或 `INFERRED` 时一律不自动发**——
人工读来的期限也需要人再确认一次。

## 2. 违约通知

### 2.1 通知的种类与法律意义

| 通知类型 | 送达方式 | 法律意义 | 是否可自动发 |
|---|---|---|---|
| **催告（第一次）** | 短信 + 邮件 | 提示违约、给补救机会 | ✅ 可自动（低风险） |
| **催告（第二次/最终）** | 短信 + 邮件 + 书面 | 宽限期届满前的最后警告 | ⚠️ 需审批 |
| **违约通知** | 书面（送达证明）+ 邮件 | **正式宣告违约**，启动合同条款 | ❌ **必须人工审批** |
| **处置意向通知** | 书面 + 邮件 | 告知将行使担保权（收车/变现） | ❌ **必须人工审批** |
| **法律程序启动通知** | 书面（律师函） | 委托律师、进入催告/诉讼/仲裁 | ❌ **必须审批 + 法务确认** |

**短信与邮件的定位**：日本实务中，**短信（SMS）与邮件通常不是法定的有效送达方式**，
它们是**辅助通知与留痕**。真正的有效送达是**书面（書留/内容証明）**。

所以设计上：
- **短信 + 邮件 = 快速触达 + 送达留痕**（证明系统尽到了通知义务）
- **书面正式文书 = 法律有效送达**（需人工或外部渠道）
- 系统两者都记录，但**法律清算阶段只认书面送达证明**

### 2.2 通知能力建设（补 G3）

**现状：零通知能力。** 需要新建通知抽象层：

```java
// domain 层接缝（与 AttachmentStorage 同样的写法）
public interface NotificationChannel {
    String channelName();                      // SMS / EMAIL / POSTAL / WEBHOOK
    NotificationResult send(NotificationRequest request);
}

public class NotificationRequest {
    private String channel;
    private String dealerId;
    private String recipientName;
    private String recipientContact;   // 手机号 / 邮箱 / 收件地址
    private String subject;
    private String body;
    private String templateCode;        // 模板代码（可配置文案）
    private Map<String, String> variables;   // 模板变量
    private String relatedCaseNo;       // 关联处置工单（用于回溯）
    private String idempotencyKey;      // 幂等键：防重复发送
}
```

**四个实现**：

| 实现 | 用途 | 现实性 |
|---|---|---|
| `SmsChannel` | 短信 | ⭐ 需短信服务商（Twilio / 日本 NTT Docomo / 商务短信平台） |
| `EmailChannel` | 邮件 | ⭐⭐ 简单，SMTP |
| `PostalChannel` | 书面送达（记录送达凭证） | ⭐⭐ 系统只**记录**送达事实与凭证，实际寄送由人工/外部代办 |
| `WebhookChannel` | 客户自有的消息网关 | ⭐ 视客户系统 |

**`PostalChannel` 的特殊设计**：它不真的寄信，而是**记录一次"书面通知已寄出/已送达"**，
并接收送达凭证附件。这是"人工路径一等公民"（外部集成文档 §2.5）的又一体现。

### 2.3 通知记录表

```sql
CREATE TABLE notifications (
    id            BIGSERIAL PRIMARY KEY,
    notification_no VARCHAR(32) UNIQUE NOT NULL,
    channel       VARCHAR(16)  NOT NULL,   -- SMS / EMAIL / POSTAL / WEBHOOK
    notification_type VARCHAR(24) NOT NULL,
        -- REMINDER 催告（第一次）/ FINAL_REMINDER 最终催告 / DEFAULT_NOTICE 违约通知 /
        -- DISPOSAL_INTENT 处置意向 / LEGAL_ACTION 法律程序启动 / WAIVER_RESULT 豁免结果 /
        -- CURTAILMENT_DUE 强制还款到期 / REG_EXPIRY 登记到期
    dealer_id     BIGINT,
    vin           VARCHAR(32),
    case_no       VARCHAR(64),              -- 关联处置工单
    recipient_name VARCHAR(128),
    recipient_contact VARCHAR(256),         -- 手机/邮箱/地址（注意：属敏感信息，评估是否加密）
    subject       VARCHAR(256),
    body          TEXT,
    template_code VARCHAR(48),
    status        VARCHAR(16) NOT NULL DEFAULT 'PENDING',
        -- PENDING 待发 / SENT 已发 / DELIVERED 已送达 / FAILED 发送失败 /
        -- APPROVAL_REQUIRED 待审批 / APPROVED 已批准待发 / REJECTED 已驳回 / CANCELLED 已取消
    sent_at       TIMESTAMPTZ,
    delivered_at  TIMESTAMPTZ,
    failure_reason TEXT,
    -- 送达证明：书面通知的关键证据
    delivery_proof_attachment_id BIGINT,    -- 送达凭证附件（S3）
    delivery_proof_no VARCHAR(64),          -- 送达证明编号（如内容証明の番号）
    requires_approval BOOLEAN NOT NULL DEFAULT FALSE,
    approved_by   VARCHAR(64),
    approved_at   TIMESTAMPTZ,
    created_by    VARCHAR(64) NOT NULL,     -- system 或操作人
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    idempotency_key VARCHAR(128) UNIQUE     -- 防重复发送
);

CREATE INDEX IF NOT EXISTS idx_notif_case ON notifications (case_no, notification_type);
CREATE INDEX IF NOT EXISTS idx_notif_status ON notifications (status, created_at);
```

**`delivery_proof_attachment_id` 是核心字段**：书面通知的法律效力全靠送达证明。
没有送达证明，"已通知"这件事在争议中无法主张。

**`idempotency_key` 唯一约束**：防止同一通知重复发送（催告短信连发三条是商务事故）。

### 2.4 通知的审批流

```
生成通知（触发违约时）
   ↓
requires_approval = true（违约通知/处置意向/法律程序）
   ↓
→ work_orders（order_type = NOTICE_APPROVAL）→ 违约处置岗审批
   ↓
批准 → 状态 APPROVED → 发送（SMS/EMAIL 自动；POSTAL 生成待寄送任务 + 人工带回凭证）
驳回 → REJECTED + 理由
```

**审批时的展示内容**（人工需要看到才能判断）：
- 违约事实与依据（期限、流水、盘点记录逐条列出）
- 触发源（T1/T2/T3/T4）
- 历次通知记录（是否已催告过、几次）
- 客户配合度历史
- **建议的处置意向**（收车/展期/法律程序）

### 2.5 通知模板

模板可配置（后台可改），关键是把**金额与日期算准**：

```

{dealer_name} 様

### 2.6 日本渠道的特殊要求

| 要求 | 说明 |
|---|---|
| **敬语体** | 对客户的通知必须用敬語（尊敬語/謙譲語）。模板需日语母语审校 |
| **金额单位** | 建议用「円」，大额可用「万円」便于阅读 |

| **时限表达** | 「本日中」「○営業日以内」——日本客户对"营业日"敏感 |
| **联系人** | 通知需写明担当负责人与联系方式（便于协商） |

> **建议**：模板文案由日本本地人员审校后入库，
> 系统**只做变量填充与发送**，不改写措辞。

## 3. 法律清算

### 3.1 现状与缺口（补 G4）

**现有状态机**：
```
OPEN → REPOSSESSED → LIQUIDATING → CLOSED_RECOVERED / CLOSED_LOSS
```

**缺的是"法律程序"这一段**。实际日本实务中，从违约到变现之间有这些法律步骤：

| 步骤 | 内容 | 系统对应 |
|---|---|---|
| 催告（履行催告） | 书面催告 + 宽限期 | ⚠️ 缺失 |
| 担保权行使通知 | 告知将行使让渡担保权 | ⚠️ 缺失 |
| 协商/展期 | 与客户协商延期或分期 | ⚠️ 缺失（部分可走展期流程） |
| 受任通知（律师受托） | 委托律师处理 | ⚠️ 缺失 |
| 强制执行（差押） | 法院扣押车辆/账户 | ⚠️ 缺失 |
| 競売（竞拍） | 司法拍卖变现 | ⚠️ 缺失 |

### 3.2 扩展后的状态机

```
                      ┌─────────────────────────────┐
                      ↓                             │
  ┌──────────┐   ┌────────────┐   ┌──────────────┐  │
  │  OPEN    │──→│ NOTIFIED   │──→│ LEGAL_ACTION │  │
  │ 已开单   │   │ 已通知     │   │ 法律程序中   │  │
  └────┬─────┘   └─────┬──────┘   └──────┬───────┘  │
       │               │                 │          │
       │               │                 ↓          │
       │               │          ┌─────────────┐   │
       │               │          │ REPOSSESSED │   │
       │               │          │ 已收车      │   │
       │               │          └──────┬──────┘   │
       │               │                 │          │
       │               │                 ↓          │
       │               │          ┌─────────────┐   │
       │               │          │ LIQUIDATING │   │
       │               │          │ 变现中      │   │
       │               │          └──────┬──────┘   │
       │               │                 │          │
       │               │                 ↓          │
       │               │          ┌──────────────────────────┐
       │               │          ↓                          │
       │               │   ┌──────────────────┐    ┌────────────────┐
       └───────────────┴──→│ CLOSED_RECOVERED │    │  CLOSED_LOSS   │
                           │ 终态：残值覆盖应收 │    │ 终态：认定损失  │
                           └──────────────────┘    └────────────────┘
```

**新增三个状态**：

| 状态 | 中文 | 含义 | 谁能推进 |
|---|---|---|---|
| `NOTIFIED` | 已通知 | 违约通知已送达（含送达证明），进入补救期 | 违约处置岗 |
| `LEGAL_ACTION` | 法律程序中 | 已委托律师 / 已申请强制执行 / 已进入竞拍 | 违约处置岗（法务确认） |
| `CANCELLED` | 已撤销 | 客户在补救期内还清或达成和解 → 撤销处置 | 违约处置岗（需审批） |

**`CANCELLED` 是重要的**——违约处置不是单向门。客户在宽限期内还清、
或协商展期成功，处置应当撤销。**没有撤销通道会导致"客户已还钱但系统还在处置"**，
这是最伤客户关系也最容易被投诉的错误。

**OOT 特殊路径**：
```
T2（已售未回款）触发 → 直接 OPEN → NOTIFIED → LEGAL_ACTION
                                    （跳过 REPOSSESSED：车已交付客户，收车无意义）
```

### 3.3 法律清算的信息结构

现有的 `disposal_cases` 表字段不足以承载法律程序：

**现状字段**：`case_no / vin / dealer_id / credit_line_id / reason / status / repossessed_at / proceeds / loss_amount / opened_at / closed_at`

**需要扩展**：

```sql
-- 触发与定级
ALTER TABLE disposal_cases
    ADD COLUMN IF NOT EXISTS trigger_sources VARCHAR(64),   -- 多触发源：T1,T3
    ADD COLUMN IF NOT EXISTS severity VARCHAR(8) NOT NULL DEFAULT 'HIGH',
    ADD COLUMN IF NOT EXISTS principal_at_open BIGINT,       -- 开单时本金（算损失要用，不能用现在的）
    ADD COLUMN IF NOT EXISTS interest_at_open BIGINT,
    ADD COLUMN IF NOT EXISTS outstanding_at_open BIGINT,    -- 开单时应收合计（本金+利息+费用）
    ADD COLUMN IF NOT EXISTS breach_date DATE,               -- 违约日
    ADD COLUMN IF NOT EXISTS grace_until DATE,              -- 补救期截止日
    ADD COLUMN IF NOT EXISTS recognized_by VARCHAR(64),      -- 违约认定人（人工确认）
    ADD COLUMN IF NOT EXISTS recognized_at TIMESTAMPTZ,      -- 认定时间

-- 法律程序
ALTER TABLE disposal_cases
    ADD COLUMN IF NOT EXISTS law_firm VARCHAR(128),         -- 委托的律师事务所
    ADD COLUMN IF NOT EXISTS lawyer_contact VARCHAR(128),
    ADD COLUMN IF NOT EXISTS legal_action_type VARCHAR(32),  -- 催告 / 受任 / 差押 / 競売
    ADD COLUMN IF NOT EXISTS legal_action_at TIMESTAMPTZ,
    ADD COLUMN IF NOT EXISTS legal_action_ref VARCHAR(128),  -- 案号 / 事件番号
    ADD COLUMN IF NOT EXISTS court_ref VARCHAR(128),         -- 法院 / 執行庁

-- 清算结果
ALTER TABLE disposal_cases
    ADD COLUMN IF NOT EXISTS valuation_amount BIGINT,        -- 评估价（人工估价）
    ADD COLUMN IF NOT EXISTS valuation_ref VARCHAR(128),     -- 评估书编号
    ADD COLUMN IF NOT EXISTS valuation_attachment_id BIGINT, -- 评估报告（S3）
    ADD COLUMN IF NOT EXISTS disposal_cost BIGINT,           -- 处置费用（拖车/仓储/拍卖佣金）
    ADD COLUMN IF NOT EXISTS recovered_amount BIGINT,        -- 实际回收合计
    ADD COLUMN IF NOT EXISTS written_off_amount BIGINT;      -- 核销/减免金额

-- 撤销
ALTER TABLE disposal_cases
    ADD COLUMN IF NOT EXISTS cancelled_at TIMESTAMPTZ,
    ADD COLUMN IF NOT EXISTS cancelled_by VARCHAR(64),
    ADD COLUMN IF NOT EXISTS cancel_reason VARCHAR(500);
```

**`outstanding_at_open` 是关键**：损失 = 应收 − 回收 − 处置费用。
应收必须是**开单当时**的快照，不能用结案时的值——因为期间可能还有利息产生、
可能有部分还款。混用会算出错误的损失金额。

### 3.4 清算计算书

**你明确要求保留清算证据链**，清算计算书是核心。

```sql
CREATE TABLE liquidation_statements (
    id            BIGSERIAL PRIMARY KEY,
    statement_no  VARCHAR(32) UNIQUE NOT NULL,
    case_no       VARCHAR(64) NOT NULL,
    dealer_id     BIGINT NOT NULL,
    -- 应收侧
    principal_amount BIGINT NOT NULL,
    interest_amount  BIGINT NOT NULL,
    fee_amount       BIGINT NOT NULL DEFAULT 0,
    other_amount     BIGINT NOT NULL DEFAULT 0,
    total_receivable BIGINT NOT NULL,
    -- 回收侧
    valuation_amount BIGINT,              -- 评估价
    proceeds_amount  BIGINT NOT NULL DEFAULT 0,  -- 变现实得
    recovered_amount BIGINT NOT NULL DEFAULT 0,  -- 其他回收（担保物残值、保险理赔等）
    disposal_cost    BIGINT NOT NULL DEFAULT 0,  -- 处置费用
    -- 结果
    loss_amount      BIGINT NOT NULL,     -- 损失 = 应收 - 回收 - 费用
    written_off_amount BIGINT NOT NULL DEFAULT 0,
    -- 证据
    calculation_basis JSONB,              -- 计算过程明细（可复算）
    attachment_id   BIGINT,               -- 清算计算书 PDF（S3）
    prepared_by     VARCHAR(64) NOT NULL,
    prepared_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    reviewed_by     VARCHAR(64),          -- 复核人（≠ 编制人）
    reviewed_at     TIMESTAMPTZ,
    status          VARCHAR(16) NOT NULL DEFAULT 'DRAFT',
        -- DRAFT 草稿 / PENDING_REVIEW 待复核 / APPROVED 已批准 / FINAL 已定稿
    CONSTRAINT uk_liq_stmt UNIQUE (case_no)
);

COMMENT ON TABLE liquidation_statements IS '清算计算书：应收 - 回收 - 费用 = 损失，全程可复算、可复核';
COMMENT ON COLUMN liquidation_statements.calculation_basis IS '计算过程明细（JSON）——使清算结果可复算，避免口径争议';
```

**`calculation_basis` 存计算过程**：不只是结果，是**每一步怎么算出来的**。
争议时能逐项复算——这比一个最终数字有用得多。

**`prepared_by ≠ reviewed_by`**：编制与复核分离，延续 SOD 原则。

### 3.5 处置证据清单

| 证据 | 载体 | 说明 |
|---|---|---|
| 违约通知 + 送达证明 | `notifications` + 附件 | **证明已通知**（法律要件） |
| 催告记录（历次） | `notifications` | 证明给了补救机会 |
| 评估报告 | S3 附件 + `valuation_attachment_id` | 残值认定的依据 |
| 变卖凭证 | S3 附件 | 拍卖记录、成交凭证 |
| 收车凭证 | S3 附件 | 拖车单、交接单（若走收车） |
| 清算计算书 | S3 附件 + `liquidation_statements` | 损失金额的推导 |
| 法院文书 / 律师函 | S3 附件 | 法律程序的证据 |
| 台账变化轨迹 | `audit_events` | 每次状态变更留痕 |
| VIN 证据链 | `collateral_evidence_links` | 合同/登记/盘点/销售/回款 |

**全部挂进 `collateral_evidence_links`**（V10 已有的证据链表），
让单车的违约处置证据可完整串起来。

## 4. 额度冻结联动（补 G5）

### 4.1 现状问题

`DisposalApplicationService` 里 **grep 不到任何额度相关操作**——处置不冻结额度。

**这是明显的风控漏洞**：经销商有一台车违约进入处置，但额度照用，
还能继续收车放款。**处置一台车，结果是继续放款给同一个违约客户。**

### 4.2 冻结规则

```
触发违约（T1–T4 任一）
  ↓
冻结额度：
  单车触发（T1/T2/T3）：
    credit_lines.frozen_amount += 该车 outstanding_at_open（开单时应收）
    frozen_reason = 'DEFAULT_DISPOSAL'
  经销商触发（T4）：
    credit_lines.frozen_amount = approved_limit（全额冻结）
    frozen_reason = 'DEFAULT_DISPOSAL'
  ↓
status = FROZEN（若有该状态）
  ↓
新增放款申请被拒（额度不足）
```

**`credit_lines.frozen_reason` 必须能区分场景**（V11 已加该字段）：

| `frozen_reason` | 触发场景 | 解冻条件 |
|---|---|---|
| `ANNUAL_REVIEW` | 年审冻结 | 年审通过 |
| `CURTAILMENT_OVERDUE` | 强制还款超期未还 | 强制还款还清 |
| **`DEFAULT_DISPOSAL`** | **违约处置** | 处置结案或撤销 |

**三者可叠加**：一台车同时触发强制还款超期与违约处置，
`frozen_amount` 累加但**不重复计算同一笔**——
解冻时按各自来源分别回退。

> **建议**：把冻结拆成**明细表**而非单一金额字段，才能正确回退：
> ```sql
> CREATE TABLE credit_line_freezes (
>     id            BIGSERIAL PRIMARY KEY,
>     credit_line_id BIGINT NOT NULL,
>     freeze_reason VARCHAR(32) NOT NULL,
>     amount        BIGINT NOT NULL,
>     ref_type      VARCHAR(32),      -- DISPOSAL / CURTAILMENT / ANNUAL_REVIEW
>     ref_id        VARCHAR(64),      -- case_no / plan_id
>     frozen_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
>     released_at   TIMESTAMPTZ,
>     released_by   VARCHAR(64)
> );
> ```
> `frozen_amount` 变为该表的汇总（冗余），解冻按行回退——
> **否则多重冻结解冻时无法知道该退多少**。

### 4.3 解冻

```
处置结案（CLOSED_RECOVERED / CLOSED_LOSS）：
  → 处置实际回收冲减 used_amount（回收部分）
  → 损失部分按核销流程处理（减 used_amount 或走坏账核销）
  → 释放对应冻结额
处置撤销（CANCELLED）：
  → 释放对应冻结额
  → 车状态回退（OVERDUE → IN_STOCK/SOLD_PENDING）
```

**「处置回收冲减 used_amount」要谨慎**：回收的钱如果已通过正常还款核销过，
再冲一次就是双减。所以结案时必须核对：回收款是否已入账核销，
已核销的部分**只释放冻结，不重复冲减**。

## 5. 人工后台：违约台账处置

### 5.1 人工处理的四类工作

你说「最后人工在后台处理这些违约的台账」——具体是四类：

| # | 工作 | 触发 | 人工要做的判断 | 工单类型 |
|---|---|---|---|---|
| 1 | **违约事实核实** | 系统标记违约待处理 | 核实事实是否成立（期限录错？盘点漏扫？流水未采集？） | `DEFAULT_REVIEW` |
| 2 | **通知审批与发出** | 违约通知/处置意向待发 | 批准、调整措辞、决定发送方式 | `NOTICE_APPROVAL` |
| 3 | **法律程序决策** | 客户拒不补救 | 委托律师？申请执行？还是协商展期？ | `LEGAL_DECISION` |
| 4 | **清算与结案** | 变现完成或损失确定 | 审清算计算书、确认损失、结案 | `LIQUIDATION_REVIEW` |

### 5.2 违约工作台视图

| 视图 | 内容 | 默认排序 |
|---|---|---|
| **违约待认定** | 系统标记但未经人工确认的案件 | 严重度降序 |
| **待审批通知** | 违约通知、处置意向、法律程序启动 | 严重度降序 |
| **法律程序中** | 已委托律师/已申请执行的案件 + 下一步节点 | 案号 |
| **待复核清算** | 清算计算书待复核 | 损失金额降序 |
| **经销商全景** | 该经销商全部案件 + 敞口 + 冻结 + 历史 | — |
| **单车轨迹** | VIN 从融资到处置的全链路证据 | — |

### 5.3 违约认定的界面要点

**人工核实事实时，界面必须把"依据"全部摊开**，否则核实无从谈起：

```
【违约案件】CASE-2026-00123
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
车辆   ABC1234（TOYOTA CAMRY 2026）   经销商  山田自動車（株）
触发源  T3 库存流失（盘点缺失）  ⚠️  T1 融资期限届满
严重度  CRITICAL

【事实依据】
  ① 盘点记录
     2026-10-15  盘点：台账 12 台 / 现场 11 台 → 缺失 1 台（ABC1234）
     2026-10-29  盘点：台账 12 台 / 现场 11 台 → 缺失 1 台（ABC1234）
     → 连续 2 次缺失，累计 audit_mismatch_count = 2
  ② 融资期限
     到期日 2026-10-20（来源：CONTRACT 合同录入，确认人 operator）
     今日 2026-10-29 → 逾期 9 天
  ③ 回款情况
     已售出 2026-08-15（结算窗口 2026-09-14）
     回款：无流水记录（指定账户近 30 天无入账）
  ④ 盘点异常率检查
     该经销商本次缺失率 8.3%（其他经销商 0.5%）→ ⚠️ 个案，非系统性

【金额】
  开单时本金      ¥1,850,000
  开单时利息      ¥   28,400
  应收合计        ¥1,878,400
  当前冻结额度    ¥1,878,400（reason=DEFAULT_DISPOSAL）

【历史】
  通知：催告 1 次（2026-10-22 短信+邮件，已送达）  豁免：无
  展期：无        额度占用率：78%
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[ 核实无误 → 批准通知 ]  [ 事实不成立 → 撤销 ]  [ 补充调查 ]
```

**"盘点异常率检查"这一项很关键**：上面例子里该经销商缺失率 8.3%，
而其他经销商 0.5%——如果是盘点 App 故障，**所有经销商都会异常**。
这个横向对比能帮人工快速判断是"这个经销商在脱信"还是"我们系统有问题"。

### 5.4 处置的人工决策点

| 决策点 | 选项 | 后果 |
|---|---|---|
| 客户在补救期内还清 | 撤销处置 | 解冻额度、车状态回退 |
| 客户申请展期 | 走展期审批（有权限点约束） | 处置暂停、宽限期延长 |
| 客户协商分期 | 生成分期方案（人工录入计划） | 处置暂停 |
| 客户拒不配合 | 进入法律程序 | 委托律师、申请执行 |
| 车辆已不在经销商处 | 跳过收车，直接法律程序 | 状态机走 OOT 路径 |
| 客户失联 | 视为拒绝补救，进入法律程序 | — |

**每一个决策都要留痕**（谁在什么时间基于什么依据做了什么决定）——
`audit_events` + 工单动作记录。

## 12. 明确不做（有意边界）

| 项 | 原因 |
|---|---|
| **系统自动发正式违约通知** | 正式通知是法律行为，需事实认定。系统误判（期限录错/盘点漏扫/流水未采）而自动发出会直接损害客户关系，争议中构成己方过错 |
| **系统自动委托律师 / 申请强制执行** | 法律程序有实体要件与时限，系统只记录信息与留痕，实体行为由人+律师执行 |
| **系统自动计算并确认损失** | 损失是财务与法律结论，必须人工复核（编制≠复核） |
| **处置后不可撤销** | 客户在补救期内还清是常态。无撤销通道会造成"客户已还钱但系统还在处置" |
| **系统判断「经营恶化」是否构成违约** | 系统只算指标并提示，人工决定是否构成违约 |
| **短信/邮件作为有效送达方式** | 日本实务中短信邮件非法定送达方式。系统把它们作为辅助触达与留痕，**法律清算只认书面送达证明** |
| **用短信内容替代书面文书** | 短信不承载合同条款的正式表述。文书模板需日语母语审校 |

一、项目文档

1.1 项目背景与目标

公司战略决定所有业务统一用 Java 实现，本系统当前为 Ruby on Rails 实现的库存融资（Floorplan）核心系统，须重写为 Java。系统服务于金融公司内部，面向新车渠道：金融公司向品牌授权经销商提供以库存车为担保的周转资金，车辆售出后即时还款、额度回补。

目标：在保持业务等价的条件下，完成 Rails→Java 重写；领域模型保留、实现架构按 Java 最佳实践重做；具备账务正确性、审计合规、批处理与对账能力。

1.2 范围

做（第一版）不做（防膨胀）
客户授信与额度管理、单台台账、垫款与付款、还款与结清、计息与账务、库龄递减、风控预警、实地盘点、厂家贴息结算、审计留痕、批处理 多品牌/多厂家扩展、多产品（试驾车/设备/建店资金）、规则引擎全可视化、对外车商门户、多币种、多地区部署

1.3 技术栈与架构

  • 架构：Spring Boot 模块化单体（Maven 多模块），逻辑拆、物理不拆。
  • 模块：domain（聚合/不变量/状态机/计息，不依赖 Spring）· application（用例编排+事务边界）· infrastructure（JPA/MyBatis/事件表/适配）· web（接口层）· integration（厂家/支付/登记对接）。
  • ORM：简单实体用 Spring Data JPA；计息/对账/报表用 MyBatis 或 JDBC Template 手写 SQL。
  • 数据库：PostgreSQL；金额列 bigint 映射 Java long（日元无小数）。
  • 批处理：Spring Batch / @Scheduled + Quartz。
  • 权限：Spring Security + 自定义投票器，落实"发起与执行分离"。

1.5 关键架构决策（ADR 摘要）

ADR-001 模块化单体：低 QPS + 强一致 + 事务密集，边界未验证前不引入分布式事务；可逆性高（模块边界清晰，未来物理拆分成本低）。
ADR-002 等价重写优先：战略决定 Java，但禁止"翻译式迁移"；领域层保留、实现层按 Java 重做；测试资产（尤其计息边界用例）必须平移为 JUnit 作为等价证据。
ADR-003 先测后码（AI 纪律）：AI 辅助编程只承接样板；计息/额度/批处理等核心 100% 人工 review + 强测试；禁止把业务规则藏在框架回调中。

二、业务文档

2.1 业务本质

经销商的库存即资产负债表——库存车露天停放占用资金。库存融资解决"收车须即时付款、卖车数月后才回款"的错配：金融公司直接向上游（厂家）付款，车辆在经销商场地作担保，售出一台即还一台，额度自动回补。

2.2 角色与权限（内部职能切分）

角色职责权限敏感点
授信 / 客户经理经销商关系、核定额度可发起额度调整，不能直接放款
运营 / 垫款处理受理垫款、付款、单据核对付款需双人复核
风控 / 盘点库龄监控、盘点、违约处置可发起冻结，动作全程留痕
财务 / 会计计息、对账、入账利率与计息规则变更需审批流
内部控制铁律："发起"与"执行"必须分离（客户经理提额度、另一人批；运营提付款、财务执行）。任何单人走完全流程的设计都是不合规的。

2.3 五大核心机制

机制要点
单台独立核算以车架号为主键，每台车独立建账、独立计息，绝不做总额
售出即还零售成交后结算窗口（如 24–72h）内必须结清该台垫款
库龄递减还款在库超 60/90/120 天未售，强制偿还部分本金，防残值跌破垫款
实地盘点定期到场逐台扫描车架号，账实不符当场升级
脱信销售车已售却不还款——最严重违约，可致整个额度被收回。系统价值核心即对抗此风险

2.4 领域模型（聚合根）

聚合根守的不变量关键子实体
经销商 Dealer授信额度 ≤ 核定上限；额度占用 + 可用 = 核定额度记录、经营档案
额度 CreditLine占用额不得超额（并发加锁）；释放须对应还款占用明细、冻结记录
车辆单元 VehicleUnit状态机合法流转；一台车同一时刻唯一状态；售出须先结清垫款、还款、计息记录、登记状态

2.5 术语表（中文）

中文含义
库存融资 / Floorplan以库存车为担保向车商提供周转资金，售车即还
垫款金融公司代付给厂家的购车款，形成对车商的债权
结算窗口车辆零售后须还清该台垫款的期限
库龄递减在库超期强制偿还部分本金的机制
脱信销售车已售但车商未上报/未还款
所有权保留还清前车辆登记在金融公司/信贩名下（日本新车未上牌时无法落地，须另确认担保路径）
厂家贴息厂家对部分利息的补贴，须与利息轧差结算

2.6 日本本地合规要点

  • 总量规制不适用：本场景为 B2B（金融公司对经销商），不受《放贷业法》个人借款"年收入 1/3"约束；但书面交付、登记等义务仍须关注。
  • 新车未上牌的担保落地：车辆停在经销商场地时常未完成登记，"所有权保留登记"无登记对象。担保可能靠让与担保合同 / 动产让渡登记 / 厂家回购承诺 / 经销商信用——待确认，直接决定"担保登记"模块做不做。
  • 书面交付义务：契约书、明细书等须按日本金融实务交付并留痕。
  • 涉及放贷与担保的部分，须经日本当地合规人士复核。

三、业务流程图

对齐业务需求文档「资金与车辆的流转闭环」七环节：授予额度 → 车商收车申请 → 垫款支付 → 设定担保 → 在库计息 → 零售成交 → 结清释放（还款·解除担保·回补额度），并以回环体现循环授信特性。右侧为在库期间并行活动，左侧为违约分支。

图例：蓝=主干环节与资金流；绿=车辆流与结清；橙=在库期间并行活动（计息/库龄/盘点）；红=违约分支；灰虚线=额度回补闭环。

3.1 业务闭环 ↔ 系统落点对照

确保业务需求文档「资金与车辆的流转闭环」七个环节在系统设计中均有明确落点，避免环节在实现阶段被遗漏。

环节业务动作系统落点说明 / 风险
① 授予额度金融公司核定车商循环授信上限POST /api/credit-lines（需审批）发起与执行分离；冻结/恢复须可追溯、可审计
② 车商收车·申请厂家渠道中标/下单，就该台车提交垫款申请POST /api/advances；批量到货 /api/vehicles/batch-ingest须记录上游卖方与采购渠道（新车渠道=厂家）
③ 垫款支付金融公司直接付款给上游，不经车商账户垫款原子流程：占额度 + 建台账 + 付款防挪用底线；付款为外部调用，事务边界待确认
④ 设定担保该台车纳入担保范围（日本为逐台）车辆单元担保字段 + 设定担保接口新车未上牌时担保路径待确认，直接决定本环节是否落地
⑤ 在库计息按日计息、累计库龄；超阈值触发递减；定期盘点日终计息批处理 / 库龄递减 / 实地盘点（并行）计息须可重跑、有执行记录；盘点差异升级为风控工单
⑥ 零售成交车卖给终端客户，触发该台立即还款义务POST /api/vehicles/{vin}/sold进入结算窗口倒计时；sold 触发源待确认（零售系统对接 or 人工）
⑦ 结清释放还款后解除担保、释放额度，可继续收下一台POST /api/repayments：还款核销 + 解除担保 + 额度回补结清须原子完成三件事，不可只做还款而漏解除担保
闭环关键：第 ⑦ 步的"额度回补"必须回连到第 ①② 步——这是循环授信与一次性贷款的本质区别。系统须保证额度释放后立即可用于下一台垫款，图中灰色虚线即此闭环。原流程图为线性（止于"已结清"），未表达该循环特性，现已补正。

四、接口设计文档

4.1 通用约定

  • 协议：REST/JSON（内部系统，可走内网网关）。
  • 认证：内部 SSO + 角色令牌；每个写操作须带操作人身份（审计）。
  • 金额：一律整数日元，JSON 中以数字（long）传递，禁止小数与浮点。
  • 时区：统一 JST；计息/结算日期以"营业日"为准，节假日表内置。
  • 幂等：写接口须带 Idempotency-Key，防止重复垫款/重复还款。
  • 错误码：统一 {code, message, traceId}；额度不足、状态非法、幂等冲突等区分。

4.2 核心接口列表

方法路径说明权限
POST/api/dealers创建经销商档案客户经理
POST/api/credit-lines核定/调整额度（需审批）客户经理+审批
POST/api/vehicles/batch-ingest批量到货建账（一次多台）运营
POST/api/advances申请垫款（原子：占额度+建台账+付款）运营+复核
POST/api/vehicles/{vin}/security设定担保（逐台登记）待确认运营

POST/api/repayments还款结清（核销垫款+解除担保+释放额度）财务

4.3 关键接口详述

① 申请垫款（原子操作）

POST /api/advances
{
  "creditLineId": "CL-100023",
  "vin": "JMA***********",
  "manufacturerInvoiceAmount": 1850000,   // 厂家发票金额（日元整数）
  "advanceRatio": 0.9,                    // 垫款比例
  "idempotencyKey": "adv-20261025-0001"
}
// 响应 201
{
  "advanceId": "ADV-558201",
  "status": "PAID",                        // PAID=已付款
  "advancedAmount": 1665000,
  "remainingCredit": 3350000,
  "vehicleStatus": "IN_STOCK"               // 已垫款·在库
}

事务边界：校验额度 → 行锁占用额度 → 建车辆单元台账 → 发起厂家付款；任一失败整体回滚，绝不允许"钱付了额度没扣"。

② 还款结清

POST /api/repayments
{
  "vin": "JMA***********",
  "settlementAmount": 1679200,   // 本金 + 截至结算日利息
  "idempotencyKey": "rep-20270115-0007"
}
// 响应 201
{
  "repaymentId": "REP-77812",
  "vehicleStatus": "SETTLED",    // 已结清
  "releasedCredit": 1665000,     // 额度回补
  "interestAccrued": 14200
}

③ 单台台账查询

GET /api/vehicles/{vin}
{
  "vin": "...",
  "status": "IN_STOCK",
  "advance": { "amount": 1665000, "paidAt": "2026-10-25" },
  "agingDays": 37,
  "accruedInterest": 5230,
  "registration": { "owner": "FINCO", "type": "RETENTION", "status": "PENDING_PLATE" },
  "nextAction": "NONE"           // 或 AGING_REDUCTION / AUDIT_DUE
}

4.5 事件与对账

  • 领域事件：VehicleSold / AdvancePaid / RepaymentSettled / AgingTriggered / AuditMismatch / CreditFrozen，供风控与盘点异步消费。
  • 对账：日终批处理后生成对账文件（垫款 vs 付款通道、利息 vs 账务），与核心账务系统轧差。
  • 双跑比对（迁移期）：同一批历史数据 Rails 与 Java 并行计算，逐笔核对利息/本金/余额。

五、注意事项

5.1 迁移纪律（三条铁律）

① 等价重写，不趁机升级：业务范围、对外行为、字段类型保持与 Rails 一致；重写不是镀金机会。
② 测试资产平移：RSpec 计息边界用例（提前还/部分还/利率变更/跨月/节假日/贴息轧差）逐条翻成 JUnit，作为等价证据。
③ 数据原样不动：schema 照搬；金额 bigint→long，不改为 BigDecimal；不趁机改字段/加字段。

5.2 技术踩坑

风险应对
金额用 float / BigDecimal 小数日元无小数 → 一律 long 整数日元
并发额度超额额度占用用数据库行锁 / 乐观锁，禁止"读-改-写"无锁
JPA 懒加载 / N+1复杂查询走 MyBatis/JDBC 手写 SQL；报表用 find_in_batches 等价批读
事务传播混乱@Transactional 边界只在 application 层；嵌套调用语义显式
时区/营业日口径错全系统 JST；节假日表内置；计息按营业日
批处理不可重跑作业幂等 + 执行记录表；失败可定位、可续跑

5.3 合规（日本）

  • 必须经日本当地合规人士复核放贷与担保相关设计。
  • 书面交付义务（契约书/明细书）须留痕。
  • 新车未上牌担保路径待确认（让与担保/动产让渡/厂家回购/经销商信用）——直接影响"担保登记"模块。
  • 总量规制不适用于本 B2B 场景，但不可据此忽略其他金融实务义务。

5.4 AI 编程纪律

  • AI 只出样板（entity/dto/mapper/controller 骨架、MyBatis XML、测试骨架）。
  • 计息/额度/批处理核心 100% 人工 review + 强制测试覆盖。
  • 维护 CLAUDE.md / 编码规范，约束 AI 产出（分层、金额 long、事务边界、不变量）。
  • 禁止把业务规则藏在框架回调中（Rails 的 callback 债不得在 Java 重现）。

5.5 范围与节奏（18 个月专属风险）

18 个月的最大风险是镀金与范围 creep：时间充裕易诱使加功能（规则引擎/多品牌/对外门户）。余量应用于提质量水位与吸收不确定性（压测、故障演练、监控运维、合规复核、双跑差异修复），而非加业务范围。建议按"12 个月做完主体 + 6 个月加固"推进，避免前松后紧与人员流动导致的知识丢失。

5.6 待确认清单

  1. 系统当前是否已上线？（决定绞杀者 vs 一次性重写）
  2. 真实业务参数：结算窗口、库龄递减天数与比例、垫款比例、利率结构、厂家贴息、违约阈值。
  3. 新车未上牌时担保落地路径。
  4. 日本本地接口现实：厂家系统、车辆登记、经销商库存、支付通道（有接口 or 人工）。

# 微服务落地：真实问题与解决

> **定位**：本项目从模块化单体拆到 11 个可部署进程的过程中，实际踩过、修过、并留下验证证据的问题清单。
> 不是"微服务最佳实践"泛论，每条都能指向代码、迁移或冒烟断言。
>
> **口径**：事实以 `PROGRESS.md` 为准；架构现状见《库存融资核心系统-目标微服务架构设计.md》§0；
> 事件契约见《接口契约-事件与Feign.md》；权限口径见《读接口授权矩阵.md》。
>
> **适用场景**：面试讲"微服务改造遇到什么问题"、新人接手排障、评审时判断某个坑是否已经闭环。

## 1. gateway：精确路由被兜底路由吞掉

**现象**

`POST /api/dealers/{id}/bank-accounts` 直连 core `:8080` 正常，经网关 `:18080` 返回 404。
历史上 `/api/payments/**` 也出现过同样问题：端点存在、服务也起来了，网关就是打不进去。

**根因**

Spring Cloud Gateway **首个匹配即命中**：

- `/api/dealers/**` 的宽路由先于精确路由命中，请求被送到 credit-service；
- 没有显式路由的路径落到 `/api/**` 的 core 兜底路由；
- 路由表"看起来有这条路径"和"请求真的落到那个服务"是两件事。

**解决**

1. 精确路由排在宽路由之前，例如 `core-dealer-bank-accounts`（`Path=/api/dealers/*/bank-accounts`）排在 `credit` 的 `/api/dealers/**` 之前。
2. 新增 `GatewayRouteOrderTest`：不启动网关，直接解析 `application.yml` 的路由顺序，用 AntPath 模拟"首个命中"，对 15 条代表路径 + 1 条顺序做断言。
3. 每条新路由必须配一条**从网关打进去**的端到端冒烟断言，而不是只断言服务直连。

**验证**

- `GatewayRouteOrderTest` 通过；
- `smoke-test.py` ㉑ 前新增经网关的 `/api/dealers/{id}/bank-accounts` 断言。

**面试一句话**

> 网关路由的坑不在"有没有配"，在"谁先匹配"。我把路由顺序做成构建期单测，再用网关侧断言兜底——因为直连 200 不能证明网关通。

## 2. common / bank：Feign 契约没有调用方，`fallback` 也不生效

**现象**

`common/contract/` 定义了 Feign 契约，但很长时间没有真实调用方；给 `@FeignClient(fallback = ...)` 写了降级类，故障时却没有进入 fallback。

**根因**

1. **只有 `web` 装配了 `@EnableFeignClients`**。其他服务即使注入了契约接口，也拿不到 Feign 代理——这不是"忘了实现"，是装配边界问题。
2. **仓库没有 circuit-breaker / resilience4j 依赖**。Spring Cloud 2023.0.5 默认的 `DefaultFeignTargeter` 不读 `fallback` 字段，写了也不会生效。

**解决**

- bank-service 启动类加 `@EnableFeignClients(clients = LoanQueryClient.class)`，`FeignLoanLookupClient` 走冻结契约 `LoanQueryClient` 真实查询借据；404 表示"无在贷借据"，5xx 抛出进入失败处理。
- 放款担保门禁的 fail-closed **不依赖 fallback**：`FeignGuaranteeLookup` 捕获异常返回 null，`RoleSeparationPolicy.evaluateGuarantee` 判 null 硬阻断。
- 删除没有调用方的 `CreditLineClient` 死契约；`CreditLineQueryClient` 的服务端 `/available` 端点已实现，但消费方仍未接，继续登记为开放项。

**验证**

- 事件冒烟 C 组：回款匹配经 Feign 查到借据并推进；
- 冒烟覆盖 `GET /api/credit-lines/{id}/available`。

**面试一句话**

> 契约不是"定义了就通了"，必须有一个真实调用方和一条通过的断言。降级也不能想当然——没有熔断依赖时 `fallback` 是死配置，fail-closed 要自己用 catch + 判空兜住。

## 3. outbox：发布去重不能靠唯一索引

**现象**

事件重试可能重复发布；但 `outbox_events` 是已落库迁移，改表加唯一索引会触发 Flyway checksum 失败，整栈起不来。

**根因**

- 已落库迁移**永不修改**是硬约束；
- 发布端需要"同一业务事实只发一次"，但数据库层没有现成的唯一约束可用。

**解决**

`JdbcOutboxPublisher` 用应用侧条件插入实现同语义：

```sql
INSERT INTO outbox_events (...)
SELECT ...
WHERE NOT EXISTS (
  SELECT 1 FROM outbox_events
  WHERE event_type = ? AND aggregate_key = ?
)
```

按 `(event_type, aggregate_key)` 去重；调用方必须传入"这一次发生"的业务主键。

**验证**

事件冒烟 B1–B5：同一匹配重放不会新增第二条 `PAYMENT_MATCHED`。

**面试一句话**

> 不能改已落库迁移，就在应用层用 `WHERE NOT EXISTS` 实现唯一语义；代价是要接受"并发下仍可能双写"的理论窗口，靠消费端幂等兜底。

## 4. outbox：`aggregate_key` 选错，事件要么被吞要么等于没去重

**现象**

早期有人想用 `vin` 或 `traceId` 做聚合键，两者都会出问题。

**根因**

- 用 `vin`：同一辆车的第二笔垫款被判定为"同一事件"，直接吞掉；
- 用 `traceId`：每次请求都不同，等于没有去重；
- 用 `event_type` 单键：所有同类型事件互相吞。

**解决**

`aggregate_key` 必须标**这一次发生**，不是**这个对象**：

| 事件 | 正确键 | 理由 |
|---|---|---|
| `LOAN_CREATED` | `advanceId` | 每笔垫款一次放款确认 |
| `PAYMENT_MATCHED` | `paymentRef` | 每笔匹配一次结清事实 |
| `COLLATERAL_CHANGED` | 待业务定源 | 键与 status 取值域未签字，**不猜** |

**验证**

- 事件契约文档冻结写法；
- 冒烟断言同车第二笔垫款仍能发布（用 `advanceId` 而非 `vin`）。

**面试一句话**

> 聚合键选"这一次发生"的主键。选对象 ID 会把同对象的后续事件吞掉，选请求 ID 等于没去重。

## 5. 消费端：框架幂等挡不住"同一事实重新发布"

**现象**

`event_consumptions(event_id, consumer)` 能挡住同一事件重复投递，但挡不住"同一笔业务事实被重新发布成一个新 `event_id`"。

**根因**

框架幂等键是事件 ID，不是业务事实 ID。上游重试、人工重放、补偿任务都可能产生新的 event_id。

**解决**

两层幂等：

| 层 | 键 | 落点 |
|---|---|---|
| 框架层 | `(event_id, consumer)` | `event_consumptions` 复合主键 |
| 业务层 L2 | `payment_ref` | `credit_line_restorations`（V80） |
| 业务层 L2 | `payment_ref` | `payment_security_releases`（V81） |
| 业务层 | `advanceId` | `loans.loan_no = "LN-" + advanceId` 唯一键 |

**验证**

事件冒烟 C2：同一 `PAYMENT_MATCHED` 重放，额度不重复回补、解押不重复执行。

**面试一句话**

> 框架幂等防"同一事件重复投递"，业务幂等防"同一事实换了个事件又来了"。两层都要有。

## 6. credit + core：同一事件两个消费者，部分成功怎么办

**现象**

`PAYMENT_MATCHED` 有两个消费者：

- credit-service 回补额度；
- floorplan-core 解押并释放担保台账。

两者是**独立事务**。如果 credit 成功、core 进入 DEAD，系统会出现"额度已回补、担保未解除"的部分状态。

**根因**

这是最终一致性的固有形态，不是 bug。分布式事务能消除部分状态，但代价是金融账务不可接受的全局锁与回滚复杂度。

**当前解法（诚实版）**

1. 两个消费者各自 L2 幂等，失败可重放；
2. 失败进入 DEAD，不静默吞掉；
3. 消费方按同一业务键（`payment_ref`）独立收敛；
4. **未做**：`LEDGER_GAP` 巡检（扫描"额度已回补但担保未释放"的差异并告警）。

**面试一句话**

> 最终一致不是"保证都成功"，而是"失败可见、可重放、有巡检兜底"。部分状态是这套方案的已知代价，不能假装不存在。

## 7. EventDispatcher：多实例共用游标会互相覆盖

**现象**

`consumer_offsets` 原来按 `consumer` 一行。两个实例同时轮询时，后写的游标覆盖前一个，导致重复消费或漏消费。

**根因**

游标是共享状态，但没有"谁在消费"的租约。

**解决**

V83 给 `consumer_offsets` 加 `lease_owner` / `lease_until`：

- 每轮用原子 SQL 认领或续租（租期 2 分钟）；
- 没抢到租约的实例直接跳过，不读事件；
- `@PreDestroy` 优雅停机立即释放租约，重启不用等租期过期；
- 接管语义是 at-least-once，重复由 `event_consumptions` + 业务 L2 幂等兜底。

**验证**

事件冒烟 3 条 `lease_owner` 断言：租约生效、非持有者不消费、停机释放。

**面试一句话**

> 多实例消费不是加个 `@Scheduled` 就行，游标本身也要有租约。租约到期接管 + 至少一次 + 业务幂等，是 DB 轮询版 outbox 的最小可用解。

## 8. 作业调度：每个实例都会跑 cron

**现象**

`@Scheduled` 在 10 个服务进程里各自生效；本地开发一启动就可能跑日终计息；Redis 挂了作业仍然裸跑，多实例重复执行。

**根因**

Spring 调度器没有分布式协调；"加了注解"不等于"生产可运行"。

**解决**

1. `floorplan.jobs.enabled` 默认 `false`，本地不跑；prod profile 启动检查强制 `true`。
2. 每个作业先 `DistributedLock.tryLock("lock:job:<jobName>:<bizDate>", 30 分钟)`；
3. 抢不到直接跳过并记日志；
4. 锁服务异常 **fail-closed**：不执行 + ERROR 日志，不降级为裸跑；
5. 锁 key 带业务日期，跨天不互相阻塞；`try-with-resources` / 显式释放；
6. `lock.provider` 本地 `memory`、生产 `redis`；prod 检查拒绝 `memory`；
7. `run-redis.sh` 起 Redis 实例，`redis-smoke` 用 `LOCK_PROVIDER=redis` 验证锁真的生效。

**验证**

- `redis-smoke` 7 条：`lockProvider=redis`、并发触发无 500、账户数 > 0；
- `FLOORPLAN_JOBS_ENABLED=true` 启动 web/bank/loan 三服务无 bean/cron 错误；
- `ScheduledCoreJobsTest` 3 条：抢到锁执行、锁被占用跳过、锁服务不可用 fail-closed。

**未做**

Quartz 动态 cron、任务暂停/恢复、执行历史表、Redis HA。当前 9 个作业都是固定 cron + 配置覆盖。

**面试一句话**

> 定时任务要回答三个问题：多实例谁跑、锁服务挂了怎么办、本地怎么不误跑。我的答案分别是分布式锁、fail-closed、默认关闭 + prod 强制开启。

## 9. auth：JWT 里的权限是快照，删角色后旧令牌还能用

**现象**

令牌载荷带 `roles/perms`，登录时签发。管理员删掉用户角色、禁用账号后，旧令牌在 8 小时有效期内仍然能访问。

**根因**

下游服务本地验签只验证签名和过期，信任令牌里的权限快照；权限变更没有失效机制。

**解决**

1. V82 `users.token_version`；
2. 登录时把 `ver` 写进令牌；
3. 每次请求回查：签名/过期 → 用户是否启用 → `token_version` 是否一致 → 从 `user_roles` 现算角色与权限；
4. 新增 `POST /api/auth/logout`，把版本 +1，旧令牌立即 401；
5. 拦截器不再信任令牌里的 `perms/roles`，只把它们当展示信息。

**代价**

每请求一次数据库查询。当前用主键查询 + 连接池承受；身份信息可以短 TTL 缓存，但**账本字段绝不缓存**。

**验证**

冒烟 ㉖ 7 条：删除 `user_roles` 后同一令牌立即 403；logout 后旧令牌 401；重新登录成功。

**面试一句话**

> JWT 的无状态是"验签无状态"，不是"权限永不失效"。撤销要么维护黑名单，要么给用户一个版本号——我选了版本号，因为它是数据库里的一行，不引入额外中间件。

## 10. 权限：读接口曾经大量裸奔，隐式读层又把查询打成 403

**现象**

写端点基本都有 `@RequirePermission`，GET 大量没有；后来加隐式读层，又因为读点从未参与令牌签发，带注解的查询端点对所有角色 403。

**根因**

- "读接口不设权限点"是旧口径，与最小权限原则冲突；
- 读点没有进入令牌，`can()` 的读层放行没有生效路径。

**解决**

1. `Permission` 新增 13 个细粒度读点（`CREDIT_READ` / `VEHICLE_READ` / `ADVANCE_READ` / `LOAN_READ` / `REPAYMENT_READ` / `PAYMENT_READ` / `COLLATERAL_READ` / `RISK_READ` / `DISPOSAL_READ` / `SUPPLIER_READ` / `BANK_ACCOUNT_READ` / `ATTACHMENT_READ` / `JOB_READ`）；
2. `UserRole.READ_MATRIX` 按 14 个角色授权，写点/读点物理分离；
3. 21 个 Controller 的 GET 加 `@RequirePermission`；唯一豁免是 `/api/attachments/local-download`（预签名 URL 自鉴权）；
4. 每次请求回查权限，令牌里的读点只作展示；
5. 实施后按真实工作流补了 3 处最小授权（`BUSINESS_OPERATOR` + `CREDIT_READ`/`RISK_READ`，采购岗 + `LTV_POLICY_READ`），并在《读接口授权矩阵.md》登记为例外。

**验证**

- 主干 + 事件 290 PASS；
- USED 冒烟 209 PASS；
- 浏览器测试 37 PASS（operator 页面不再 403）。

**未做**

数据范围 C（`OWN_DEALER` / `OWN_PARTNER`）、PII 二人授权流程、合作方 scope。当前是功能矩阵，不是数据行级隔离。

**面试一句话**

> 权限矩阵不能只在表里"看起来对"，要按真实页面和工作流跑一遍。我们就是被浏览器测试和 USED 冒烟抓出"矩阵过严导致正常业务 403"的。

## 11. common / web：异常信息泄露与客户端错误 500

**现象**

未知异常直接把 SQL、表名甚至密码片段回给客户端；缺必填参数却返回 500 `SYS_001`。

**根因**

全局异常处理只有一个兜底分支，没有区分"客户端传错"和"服务端故障"；异常 message 直接进了响应体。

**解决**

1. `handleUnknown` 只回固定文案 `SYS_001` + traceId，完整堆栈进服务端日志；
2. 新增 `handleBadRequest`，把 `MissingServletRequestParameterException` / `MethodArgumentTypeMismatchException` / `HttpMessageNotReadableException` 映射为 400 `VALID_001`；
3. 单测覆盖脱敏；浏览器测试补两条缺参断言。

**面试一句话**

> 错误响应也是安全边界。客户端错误和服务端错误必须分档，未知异常只能给 traceId，不能给内部结构。

## 12. core / credit：共库让跨域直写"能跑"，但拆库那天会断

**现象**

服务已经拆成独立进程，但共用同一个 `public` schema。新代码如果直接读别的服务的表，本地能跑，物理拆库时立刻失效。

**根因**

第一版刻意不拆库，降低跨库 join 与分布式一致性的启动成本；但"共库"不能变成"随便跨域写"。

**解决**

1. 明确每类数据的**唯一权威写者**：

| 数据 | 权威写者 | 其他服务 |
|---|---|---|
| 账本（垫款/还款/计息） | core | 只读接口，不直写 |
| 额度/评级 | credit | core 通过 Feign 查询，不落本地副本 |
| 借据/DPD | loan | bank 通过 Feign 查借据 |
| 担保权属 | 批次表 + core 释放，collateral-reg 只读投影 | 不跨域直写 |

2. `PAYMENT_MATCHED` 拆成两个消费者：credit 只回补额度，core 只解押，**不互相写对方的表**；
3. 新代码禁止直接读别的服务的表，优先 Feign 契约或事件；
4. 两个消费者各自 L2 幂等，避免重复回补/重复释放。

**未做**

物理拆库、release-service 的指令域消费、「银行匹配 vs 直接还款」共用 `settle_seq` 的双重释放防线、部分状态巡检。

**面试一句话**

> 共库是过渡态，不是服务自治。边界要在代码层先立起来：谁能写、谁只能读、跨域只能走契约或事件——否则拆库那天就是一次性重构。

## 13. 生产配置：错误配置应该在启动时失败，而不是上线后才发现

**现象**

JWT 用开发默认密钥、数据库密码是 `floorplan`、锁用 `memory`、银行流水用 `demo` 数据源、作业开关关着——这些配置单看都能启动，带上生产就是事故。

**解决**

`common` 新增 `ProductionReadinessCheck`（Spring Boot 自动配置，十服务 + web 一次覆盖）：

- 激活 `prod` / `production` profile，或 `floorplan.security.strict-secrets=true` 时，命中以下任一项**拒绝启动**：
  - JWT 密钥为开发默认或不足 32 字节；
  - webhook 密钥为开发默认；
  - DB 密码为 `floorplan` / `floorplan_dmz`；
  - `lock.provider` 不是 `redis`；
  - `bank-fetch.source=demo`；
  - `floorplan.jobs.enabled=false`。
- 本地无 profile 只 WARN，不阻塞开发。

**验证**

`ProductionReadinessCheckTest` 11 条。

**面试一句话**

> 安全配置不能靠"上线前记得改"。让错误配置起不来，比写十条上线检查清单可靠。

## 14. 验证体系：编译通过不等于网关通

**现象**

- `mvn package` 成功，但端点经网关 404；
- `mvn ... | tail` 的退出码是 `tail` 的，BUILD FAILURE 也能报 0；
- 冒烟脚本 stdout 重定向后 Python 回落 cp936，带圈数字崩栈，屏幕上半屏绿，实际只跑了 51 条断言。

**根因**

验证对象错了：编译验证语法，不验证链路；管道退出码不是命令退出码；Windows 控制台编码不是 UTF-8。

**解决**

1. 验收判据固定为：`PYTHON=python PYTHONIOENCODING=utf-8 bash run-microservices.sh smoke` **EXIT 0 且 FAIL = 0**；
2. 每条新能力必须加一条端到端断言，写进 `smoke_*.py` 并收进统一命令链；
3. 浏览器路径单独用 `browser-test.py` 覆盖（37 条），因为 API 冒烟测不到页面；
4. 命令输出重定向到文件，退出码自己取 `$?`，不经管道；
5. 冒烟、浏览器、USED、Redis 锁四套脚本分别有明确入口。

**验证**

当前快照：主干 + 事件 290 PASS / 0 FAIL；USED 209 / 0；浏览器 37 / 0；Redis 锁 7 / 0。

**面试一句话**

> 编译通过只说明语法对。验收要认"从用户入口打进去的端到端断言"，而且退出码不能被管道偷走。

## 15. 面试讲法：把问题串成一条演进线

不要按"我用了哪些技术"讲，按"系统怎么一步步变得可上线"讲：

1. **先拆进程**：网关 + 核心单体 + 8 个外围服务，核心账务因为强一致事务不拆；
2. **再通链路**：网关路由顺序单测 → Feign 真实调用方 → outbox 两条事件链；
3. **再补一致性**：发布去重、两层幂等、消费游标租约、部分状态可见；
4. **再补安全**：JWT 可撤销 + 权限回查 + 读接口矩阵 + 异常脱敏 + 生产配置 fail-fast；
5. **再补运行**：作业调度 + 分布式锁 + Redis 实例 + 冒烟/浏览器验证；
6. **最后诚实说没做的**：物理拆库、`COLLATERAL_CHANGED`、release-service 消费、工单体系、前端 8 模块、Quartz/Redis HA。

这条线的价值不在于"全做完了"，而在于**每一步都有验证证据，且知道下一步的边界在哪**。

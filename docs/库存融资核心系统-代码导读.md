# 库存融资核心系统 · 代码导读（小白版）

> 本文档面向第一次接触本项目的开发者，尤其是刚学 Spring Boot 的同学。
> 目标：读完本文，你能在 30 分钟内知道"代码在哪儿、从哪儿读起、每份文件管什么"。

---

## 一、先看懂大局：这个系统是做什么的？

一句话：**汽车经销商进车缺钱，我们（金融公司）按车垫款，车卖掉后经销商还钱**。
系统管理的就是这条资金链的完整生命周期：

```
授信额度 → 收车垫款 → 在库计息 → 卖车 → 还款解押 → 额度恢复
                ↓（卖不掉/超期）
          库龄递减还款 / 违约处置
```

对应 11 个业务环节，详见《库存融资核心系统-业务流程文档.md》。

## 二、一张图看懂：一次 HTTP 请求的旅行

本项目是 **DDD 四层架构**，一个请求自上而下穿过 4 层，**依赖方向永远向下**。

> **架构现状（2026-11-20）**：系统已演进为 **DDD 四层 + Spring Cloud 微服务**。
> 下面这张"四层旅行图"依然成立——因为 `domain`/`application`/`infrastructure` 作为**共享依赖**
> 被每个服务复用，服务本身只是新的"启动入口 + 精确装配"。
> 变化的是入口：请求先打**网关 18080**按路径切到对应服务（web/auth/bank/credit/risk），
> 再在服务内部走这四层。核心账务（垫款/还款/计息/台账）仍留在 web 服务，不拆——
> 它是本地事务 + 行锁 + 唯一约束守护的正确性红线。服务拓扑与拆、不拆的判断标准见
> 《库存融资核心系统-面试解析.md》二点五节。

```
浏览器/App 发请求
     │
     ▼
┌─────────── web 层 ────────────┐
│ Controller（接待员：收请求、验参数）      │
│ DTO（请求/响应的表格模板）              │
│ GlobalExceptionHandler（总服务台：统一报错格式）│
└───────────────┬───────────────┘
                ▼
┌───────── application 层 ──────┐
│ XxxApplicationService（流程指挥者：        │
│   编排步骤、管事务、写审计日志）           │
└───────────────┬───────────────┘
                ▼
┌─────────── domain 层 ──────────┐
│ 领域模型（业务规则真正住在这里）          │
│ 仓储接口（只声明"我需要存取数据"，不写 SQL）│
│ 领域服务（纯计算：利息/营业日历）          │
└───────────────┬───────────────┘
                ▼
┌──────── infrastructure 层 ─────┐
│ JdbcXxxRepository（把接口变成真 SQL）    │
│ MockPaymentGateway（模拟银行付款）       │
│ Flyway 迁移脚本（建表）                 │
└───────────────────────────────┘
```

**为什么分层？**（小白常见疑问）
- 业务规则（domain）不依赖 Spring、不依赖数据库 → 换数据库、换框架，规则不用重写
- SQL 集中在 infrastructure → 想改查询性能只改一个地方
- 每层只做一件事 → 出 bug 时能快速定位在哪层

```
floorplan-system/
├── pom.xml                  # Maven 父工程：10 个模块 + 公共依赖版本（Boot/Cloud/Alibaba BOM）
├── README.md                # 项目自述：架构、启动、七环节、已知简化

├── ── 四层共享依赖（DDD 核心，被所有服务复用）──

├── application/             # ② 应用层 —— 用例流程的"指挥家"
├── infrastructure/          # ③ 基础设施层 —— 数据库与外部世界的"翻译官"
├── common/                  # 横切：ApiResponse / JWT 拦截器 / 异常处理等 7 类
│
├── ── 启动模块（Spring Boot 应用，各自 mainClass + 端口）──
├── web/             (8080)  # ④ 接口层 + 核心账务（垫款/还款/计息/台账，勿拆）
├── auth-service/    (8081)  # 登录与 token 签发
├── bank-service/    (8082)  # 银行回款流水采集
├── credit-service/  (8083)  # 经销商 / 额度 / 评级 / 年审
├── risk-service/    (8084)  # 盘点 / 处置 / 担保 / 权属核对
└── gateway/         (18080) # 唯一入口：按路径切流 + X-Request-Id + CORS
```

> 四层共享依赖没变，变的是"谁把它组装成一个可运行进程"——以前只有 web 一个启动模块，
> 现在有六个，每个用 `@Import` 精确装配自己需要的类，而不是全包扫描。

**阅读难度**：domain ★★★（纯 Java，无框架魔法）／ application ★★／ web ★★／ infrastructure ★（套路重复，会一个就会全部）

## 六、infrastructure 层：数据库与外部世界（20 个文件 + 3 个 SQL）

路径：`infrastructure/src/main/java/com/company/floorplan/infrastructure/`

### persistence/ —— 18 个 JdbcXxxRepository

**全部是同一个套路的复制**：把 domain 层的仓储接口用 SQL 实现。

```java
// 一个 Jdbc 仓储的固定骨架（会一个 = 会全部）：
// 1. 构造器注入 JdbcTemplate（Spring 提供的数据库操作工具）
// 2. save()      → INSERT/UPDATE SQL
// 3. findByXxx() → SELECT + RowMapper（把数据库一行 → Java 对象）
// 4. FOR UPDATE 行锁 → 防止两个人同时操作同一台车
```

| 文件 | 对应表 | 特别之处 |
|---|---|---|
| `JdbcVehicleUnitRepository.java` | vehicle_units | 行锁查询 `findByVinForUpdate` |
| `JdbcInterestLedgerRepository.java` | interest_ledger | `saveIfAbsent`（幂等）+ `archiveBefore`（归档先复制后删除） |
| `JdbcRatingConfigRepository.java` | rating_configs | `ON CONFLICT DO UPDATE`（upsert） |
| `JdbcSupportRepository.java` | audit_events / batch_runs | 审计留痕 + 作业幂等标记 |
| 其余 14 个 | 各业务表 | 标准套路 |

### integration/ —— 1 个文件

| 文件 | 功能 |
|---|---|
| `MockPaymentGateway.java` | 模拟银行付款：永远返回成功（配置开关可模拟失败，验证事务回滚）。生产环境换真实现，业务代码一行不改——这就是依赖接口的好处 |

### resources/db/migration/ —— 3 个建表脚本（Flyway）

| 文件 | 内容 |
|---|---|
| `V1__init.sql` | 基础表：经销商/额度/车辆/垫款/还款/计息流水/告警/审计… |
| `V2__business_gap_features.sql` | 缺口功能表：库龄计划/递减支付/处置工单/保险/展期/回购/年审/归档表… |
| `V3__rating_config.sql` | 评级口径表 + A/B/C/D 预置种子数据 |

> Flyway 是"数据库版本管理器"：按版本号顺序执行，改过的脚本不会重复跑。

## 九、小白高频疑问速答

**Q1：为什么有的类是 interface（接口）？**
接口 = "能力清单"。domain 层只写清单，infrastructure 层写具体实现。好处：业务代码不关心数据存在 PostgreSQL 还是 MySQL。

**Q2：`@Service`、`@Transactional`、`@RestController` 都是啥？**
- `@Service`：告诉 Spring"这个类请帮我创建并管理"（不用自己 new）
- `@Transactional`：这个方法里的所有数据库操作要么全成功、要么全回滚（转账场景的"原子性"）
- `@RestController`：这个类的公开方法会变成 HTTP 接口
- 每个类头部的 javadoc 里都有更细的白话解释，直接看注释

**Q3：为什么请求头要带 `X-Operator-Id`？**
> **（现状更新）** 这个请求头**已降级为兜底**：正常请求的审计操作人来自 JWT 令牌里验签过的身份，
> 不可伪造。`X-Operator-Id` 只在定时作业等无登录态场景兜底用。
> 详见《登录认证开发指南》§14「审计操作人：从请求头到令牌身份」。

历史上它确实直接作为操作人身份写进审计日志（audit_events 表）——金融系统谁动了数据必须留痕；
但请求头是客户端可伪造的，所以后来改成了以令牌身份为准。这个演变本身就是一道好面试题。

**Q4：idempotencyKey（幂等键）是干嘛的？**
防重复提交。网络抖动时客户端可能重发同一笔垫款请求，服务端靠这个键识别"这单我处理过了"，直接返回上次结果，不会重复扣款。

**Q5：怎么验证我改的代码没破坏功能？**
改完跑 `SMOKE_BASE=http://127.0.0.1:18080 python3 smoke-test.py`（需先起服务），
182 项断言全绿即安全。注意端到端脚本只覆盖 API，不覆盖页面路径——
改前端后还要实际打开网关页面验证（这正是曾遗漏过的回归）。

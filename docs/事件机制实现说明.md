## 1. 为什么是 DB 轮询，不是 MQ

| 考虑 | 结论 |
|---|---|
| 现在有几个库 | **十个服务共用一个 PostgreSQL**（`floorplan-db2`，localhost:5434）。本地不启 Kafka/RocketMQ/Rabbit，也不启 Nacos |
| 引入 MQ 的代价 | 多一个中间件要装、要配、要排障；本地冒烟从"起 jar + 跑脚本"变成"起 docker-compose 全家桶"；每个 agent 的复现成本 ×10 |
| 业务允许的延迟 | 放款后的事后动作（建据、回补、DPD、解押指令）**明确允许秒级延迟**，需求文档里没有毫秒级要求 |
| 一致性要求 | 不能丢。**至少一次 + 消费幂等**就能满足，不需要 exactly-once 流 |
| 已有地基 | `outbox_events` 是 V21 就建好的表，`OutboxPublisher` 接口签名已冻结 |

所以：**Transactional Outbox + 库里游标轮询**。零新增依赖、零新增进程、本地一条命令能验。

同理不用 Seata：AT 模式的全局锁 + 回滚在金融账务上风险和成本都太高。**门禁类即时拦截走同步 Feign
（fail-closed），事后状态同步走 outbox** —— 这两条路的分工是整个事件地基的设计前提，改之前先确认要动的场景属于哪一类。

### 关键取舍

| 决定 | 理由 | 代价 |
|---|---|---|
| 轮询 `fixedDelay=1000ms`（不是 `fixedRate`） | 一轮耗时超过间隔时 `fixedRate` 会让任务堆积并发执行，两个线程同时读写同一个游标就是数据错乱 | 最坏投递延迟 ≈ 轮询间隔 + 处理时间 |
| 每轮每消费者最多 100 条 | 太小追不上积压，太大一次占住连接与内存 | 积压 >100 条时需要多轮才清空 |
| **不按 status 过滤**读取 | 一条事件可能被多个服务的消费者订阅，先处理完的标成 SENT，慢的必须还能读到 | 已 SENT 的行会被重新扫到（靠 `event_consumptions` 挡住，成本是一次索引查） |
| 游标按 `consumer` 一行 | 断点续读、单实例部署下最简单 | **多实例互相覆盖游标**（§5） |
| 幂等表主键 `(event_id, consumer)` | "这条事件对这个消费者有没有结论"是框架唯一能客观回答的问题 | 业务去重仍要消费者自己做（契约 §3.2） |

## 2. 三个组件各自的位置

| 组件 | 模块 | 职责 | 装配方式 |
|---|---|---|---|
| `JdbcOutboxPublisher` | infrastructure | 在**调用方事务内**写 `outbox_events`，带 `NOT EXISTS` 去重 | `@Import`（类上**故意不加** `@Component`） |
| `EventDispatcher` | infrastructure | 按游标轮询、分发给本服务的 `EventConsumer`、写幂等表与游标 | `@Import` + `@EnableScheduling` |
| `EventConsumer` / `DomainEvent` / `JsonPayloadReader` | common | 消费者的接口约定与 payload 取数口径 | 消费者用 `@Component`（在各服务自身包内） |

### 为什么发布/分发两个 bean 必须"无注解 + 只 `@Import`"

这不是风格选择，是被这个仓库的扫描配置逼出来的唯一解：

- `web` 单体的 `@ComponentScan(basePackages = "com.company.floorplan")` **覆盖全包**（只排除 `common..*`）；
- 9 个微服务各自只扫自己的包（`com.company.floorplan.loan` 等）。

于是：类上带 `@Component` → web 扫到一份、微服务 `@Import` 又一份 → **同类型两个 bean，
按类型注入直接 `NoUniqueBeanDefinitionException`，服务起不来**；
只带 `@Component` 不 `@Import` → 微服务扫不到，事件地基在它那里是死的。
**统一 `@Import`、类上无注解**，两边才都恰好一份。新增基础设施 bean 沿用这个形状。

`EventDispatcher` 在没有消费者的服务里 `poll()` 第一行就 return（一条 SQL 都不发）——
否则 9 个服务同时空转轮询会白白吃掉连接池。这是刻意的入口拦截，不是可有可无的优化。

## 3. 投递与失败的完整语义

```
drain(consumer):
  offset = consumer_offsets.last_event_id（没有这行则以 0 建档）
  rows = SELECT ... WHERE id > offset AND event_type IN (订阅集) ORDER BY id LIMIT 100
  for row in rows:
      handle(consumer, event):
          INSERT event_consumptions ... ON CONFLICT DO NOTHING
          读回 status/attempts
          DONE 或 DEAD        → 跳过，返回"有定论"        （consume 不再被调）
          attempts ≥ 3         → 补标 DEAD，返回"有定论"
          否则 consume(event):
              成功 → DONE, attempts+1, last_error=NULL     → 有定论
              异常 → FAILED, attempts+1, last_error=摘要    → 无定论（除非这次刚好到 3 → DEAD）
          有定论 → writeOffset(id)（仅当 last_event_id < id）+ markSent（仅当 status='PENDING'）
          无定论 → 直接 return，本轮剩下的事件不处理        ← 顺序保证
```

三条容易读错的地方：

1. **失败会卡住这个消费者的后续事件**，直到重试成功或达到 3 次上限。
   这是"顺序性"和"不被一条坏数据堵死"之间的显式取舍：卡住 → 最多卡 3 轮 → `DEAD` 放行。
2. **`attempts` 成功时也会 +1**。判"首次即成功"要看 `attempts = 1`，不是 0。
3. **`DEAD` 不等于"这条可以忽略"**，等于"自动机制已放弃，需要人来"。
   业务上它意味着一笔债/一次回补没有落地，必须当作账务差异处理（W1-RECON 的口径范围）。

## 4. 排障手册（本地实测可用）

```bash
# 容器里的 PostgreSQL 监听 5434（不是默认 5432）。不给 -p 会连不存在的 socket。
docker exec floorplan-db2 sh -c "psql -h 127.0.0.1 -p 5434 -U floorplan -d floorplan -Atc \"<SQL>\""
```

| 症状 | 查什么 |
|---|---|
| 事件发了没人处理 | `SELECT id,event_type,status FROM outbox_events ORDER BY id DESC LIMIT 20;` 看 `event_type` 是否拼对、是否已有 `PENDING` 同键行挡住了发布 |
| 消费者没起来 | 该服务日志有无 `Started XxxApplication`；`SELECT * FROM consumer_offsets;` 有没有这个 consumer 的行（没有 ⇒ 调度任务根本没跑：`@EnableScheduling` 或 `@Import` 缺了） |
| 处理到一半停住 | `SELECT event_id,consumer,status,attempts,last_error FROM event_consumptions WHERE status IN ('FAILED','DEAD') ORDER BY updated_at DESC;` —— `last_error` 有异常摘要，`FAILED` 说明游标正被它挡住 |
| 怀疑重复消费 | `SELECT event_id, count(*) FROM event_consumptions WHERE consumer='xxx-service' GROUP BY event_id HAVING count(*)>1;`（应为 0 行） |
| 想重放历史事件 | `UPDATE consumer_offsets SET last_event_id=0 WHERE consumer='xxx-service';` —— 已 `DONE` 的不会重跑 `consume`（框架幂等），要看 `updated_at` 有没有变来判断是否真重跑 |
| Feign 调不通 | 确认调用方启动类有 `@EnableFeignClients(basePackages="com.company.floorplan.common.contract")`；确认 `floorplan.clients.<key>.url` 有没有值（空 = 走 lb，本地没 Nacos 必然失败） |
| 端口不生效 | WorkBuddy 注入的 `SERVER__PORT` 会被宽松绑定解析成 `server.port`，**启动必须 `env -u SERVER__PORT`** |

日志判据别只看 `exit 0`：`bash run-microservices.sh smoke` 之前先看
`logs/microservices/<svc>.log` 里有没有 `APPLICATION FAILED TO START`。

## 5. 已知限制（没有藏）

| 限制 | 现状影响 | 触发条件 | 处理方向 |
|---|---|---|---|
| **多实例共游标** | 同一 `consumer` 起两个进程会互相覆盖 `last_event_id`，漏读或重复读 | 任一服务横向扩容 | `FOR UPDATE SKIP LOCKED` 认领事件，或按实例名分片游标 |
| 单实例单线程轮询 | 一条事件处理时间长会拖慢整个服务的事件吞吐 | 消费逻辑里有慢查询/大批量 | 按 event_type 分队列，或改成批量 + 并行认领 |
| `outbox_events` 永久增长 | 无归档，查询靠 `(status, created_at)` 与 `(event_type, aggregate_key)` 两个索引 | 长期运行 | 加归档任务（W3+） |
| 死信无人工重放入口 | `DEAD` 只能人工改库或改代码重投 | 出现坏事件 | 运维入口，接缝已留 |
| 发布去重无端到端验证 | 冒烟里只能用 psql 直插，绕过了发布端 | —— | 需要 `infrastructure` 单测（超出 W0 卡面写集，待批准） |

## 6. 拆库 / 换 MQ 时的迁移路径

现在这套之所以能这么简单，前提是"共库 + 本地无中间件"。**拆库那天必须动的是这三个类，
消费者一行都不用改** —— 这是当初把接口和实现分开的唯一理由。

1. **`JdbcOutboxPublisher`**：写哪张表变成写哪张表 + 是否改走 MQ 的 transactional producer。
   接口 `publish(eventType, aggregateKey, payload)` 不变，`payload` 仍是 JSON 文本。
2. **`EventDispatcher`**：`SELECT ... WHERE id > :offset` 换成
   - MQ：consumer group + broker 侧 offset（游标表可以退役，`event_consumptions` **必须留着**，
     因为业务幂等仍锚在 `event_id` 上，而 MQ 的重投身份是 message id —— 要保证两者可对应，
     迁移时把 `outbox_events.id` 塞进消息头）；
   - HTTP 回调：投递器改成按订阅关系推 + 重试队列，游标语义换成投递记录。
3. **`consumer_offsets`**：只在"库内游标"这一种投递方式下有意义，换 MQ 后自然废弃。

**跨库带来的额外一件事**：`event_consumptions` 和 `outbox_events` 会分属两个库，
`markSent` 与 `writeOffset` 不再和消费在同一个本地事务里 —— 现在的"游标只前进 + 幂等表挡住重复"
仍然成立（两处都是各自库内的单行更新），但**不再有"消费成功与游标推进原子"**，
重投概率会上升。这正是 §3 那套幂等语义要留着的理由，别在迁移时当成冗余删掉。

**Feign 这条路的迁移更简单**：契约已经是 `url = "${...:}"` 形状，生产给空串走 `lb://`、
拆分过渡期给显式地址直连，切换只动配置不动代码。要动的是网关路由与鉴权，不是接口签名。

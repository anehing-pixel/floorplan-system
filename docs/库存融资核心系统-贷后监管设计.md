# 库存融资核心系统 · 贷后监管设计文档

> **定位**：本文档定义**环节④（担保设定与贷后监管）** 与 **环节⑤（在库计息与动态贷后监管）** 的系统设计，
> 把"贷后"从当前实现里的**被动告警接收**升级为**主动监管体系**。
>
> **核心原则**：**事件驱动为主，定时任务兜底，人工后台只处理例外和复核。**
> 人工不逐条盯车——系统负责发现异常、定位责任、派发工单、跟踪时效；
> 人只做规则无法判定的判断（复核、补录、审批、处置决策）。
>
> **版本**：v1.0　|　**日期**：2026-10-26　|　**状态**：设计稿，待评审
> **上游依据**：《库存融资核心系统-业务流程文档》环节④⑤、《库存融资核心系统-外部集成接口文档》架构约束五条、
> 《库存融资核心系统-角色与权限矩阵》、《库存融资核心系统-ADR007上游直付与收款账户设计》、
> 《库存融资核心系统-ADR006垫款状态机与支付事务边界》

## 0. 结论速览

### 0.1 为什么现在做这件事

核查现状（2026-10-26，代码与数据库实测）：

| 流程文档要求 | 实际状态 | 结论 |
|---|---|---|
| `RISK_SCAN` 风险扫描作业 | **不存在**（7 个批处理作业中无此项） | 缺扫描层 |
| 残值监控 | **零代码**（无残值/市价/折旧任何字段） | 缺指标 |
| 集中度监控（车型/经销商敞口） | **零代码** | 缺指标 |
| 逾期率、账龄分布等风险指标 | **零代码** | 缺指标 |
| **融资担保期限（到期日）** | **无字段**（40 个字段中无任何期限字段） | **缺地基** |
| **`overdue_days` 逾期天数** | 字段存在但**从未被计算**（全库仅放款/展期两处归零） | **死字段** |
| **罚息利率** | 无字段，计息不区分是否逾期 | 缺 |
| **展期对期限的影响** | 只做 `setOverdueDays(0)`（空操作），不顺延任何期限 | 逻辑缺失 |
| 风险等级动态调整 | `risk_level` 字段存在但**从无代码写入**（只读不写） | 空字段 |
| 告警 → 处置闭环 | 告警仅能标记"已处理"，**无处置动作、无处置记录、无升级机制** | 缺工单层 |
| 事件驱动接入 | **无事件表**（36 张表中无任何 event/inbox 表） | 缺接入层 |
| 盘点任务生成与频次管控 | 盘点差异判定已实现（missing/unexpected + `ootSuspected`），但**无计划生成、无频次要求** | 半成品 |
| 担保物台账（V10，本轮新增） | ✅ 已建表、已跑通端到端 | **可作状态底座** |

**一句话诊断**：贷后当前只有"其他流程顺带产生的告警"（9 处 `createAlert` 调用，
类型全是 `AGING` / `SETTLE_GRACE` / `OOT_SUSPECTED` / `CREDIT_FROZEN` / `AUDIT_MISMATCH` /
`AUDIT_UNEXPECTED` / `DISPOSAL_OPEN` / `INSURANCE_CLAIM`），
**没有一条是"风险维度主动算出来的"**。监管是"被动等信号"，不是"主动看指标"。

## 1. 状态计算层：VIN 逐车台账

### 1.1 设计要点

状态**不是单一状态机**，而是**一组独立的事实标记**（正交维度）。
理由：真实业务里一台车可以同时是"已售 + 未回款 + 已登记 + 逾期 + 90 天未盘点"——
若用单状态枚举，这些组合表达不了，代码会退化成大量 if-else 组合判断。

已有的 `collateral_ledger` 正是这个结构，本节只补齐缺口。

### 1.2 融资担保期限与逾期模型（核心）

> **⚠️ 2026-10-26 修订**：本节初版把期限与逾期字段直接挂在 `vehicle_units`（VIN 台账）上，
> **这是错误的**——把**债务状态挂在了资产实体上**。
> 经 ADR-008 决策改正：**逾期状态归属借据实体，VIN 台账仅承载派生标记**。
> 完整论证见《库存融资核心系统-ADR008逾期状态归属借据设计.md》。

#### 1.2.1 为什么不能把逾期挂在 VIN 上

**VIN 台账是"车"的视图，借据是"债"的视图，二者不是一对一。**

实证：库内 `COLA017481`、`COLB017481` **各有 2 笔 advance**——一台车被两次融资。
单车挂一个 `maturity_date` 会导致：多债覆盖、历史污染（新债被误判为已逾期）、
审计断链（不同期间的债务责任混在一起）。

**债务的期限、还款计划、履约记录，其归属主体是借据。**

#### 1.2.2 三层实体

```
① 借据层 loans —— 债务的事实来源
   期限 / 到期日 / 宽限期 / 罚息利率 / 状态机（DRAFT→ACTIVE→OVERDUE→SETTLING→SETTLED/DEFAULTED）
   ↓ 一对多（同一 VIN 可有多笔借据）
② 还款计划层 repayment_schedules —— 到期的来源
   每期：期号 / 到期日 / 应还本息 / 已还 / 状态
   ↓ 触发
   还款日未足额还款 → 借据状态机迁到 OVERDUE → 生成 overdue_records
   ↓ 派生
③ VIN 台账层 vehicle_units —— 快速查询视图
   loan_overdue_flag / derived_overdue_days / derived_dpd_bucket（只读派生，单一写入点）
```

**`advances` 不能当借据用**：它的 status 是 `PENDING→PROCESSING→PAID`，
是**支付指令状态**而非债务状态；且一次放款一条、付款完成即结束。
关系是 `loan.advance_id → advances.id`（**advance 是 loan 的资金来源证明**），
**钱没到，债不成立**——银行回调 PAID 后才创建 loan。

#### 1.2.3 两层触发严格分离

| 维度 | 快逾期预警 | 正式逾期 |
|---|---|---|
| 触发时点 | 到期前 T-3 / T-1 | 到期日之后（宽限期届满） |
| 数据源 | 还款计划的**未来到期日** | **已过期计划 + 实际回款** |
| 产物 | `pre_due_alerts` | 借据状态迁移 + `overdue_records` |
| 改借据状态 | ❌ **绝对不改** | ✅ 迁到 `OVERDUE` |
| 写 VIN 逾期标记 | ❌ **绝对不写** | ✅ 写（派生） |
| DPD 计算 | ❌ | ✅ |

**四条硬约束**（违反即为缺陷）：
1. 预警 job 不得调用借据逾期迁移方法
2. 预警 job 不得写 `vehicle_units` 的任何逾期派生字段
3. `overdue_records` 只由借据状态机迁移到 `OVERDUE` 时创建，不独立产生
4. VIN 派生标记**只由 `LoanOverdueProjection` 写入**，全库无第二个写入点

#### 1.2.4 期限数据的来源（不变）

期限来自合同，而合同在本系统外——这是日本实务的常态（外部集成文档 §3：
车辆登记对民间基本无开放接口，实务靠登记事项证明书或委托代办）。

| 来源 | 途径 | 权威性 |
|---|---|---|
| **A. 放款时录入** | 经办岗按合同录入 | **高** |
| **B. 人工读合同** | 工单驱动 → 读法务省登记合同/经销商合同 + 台账反推 → 录入 | **中**，需复核 |
| **C. 登记批次带出** | 登记回执载明的期限 | 中 |
| **D. 系统推断** | 无合同依据时的兜底，**须标注"待确认"** | 低，只触发预警不触发处置 |

**期限字段落在借据上**（`loans.maturity_date` / `grace_period_days` /
`overdue_rate` / `term_source`），**不再落在 VIN 上**。

`term_source` 必须留痕的原因：若期限来自 `INFERRED`（系统猜的），
基于它的逾期判定可信度更低，处置动作应更谨慎。

#### 1.2.5 逾期判定与 DPD 分层

```
DPD = 今日 − 逾期起始日
逾期起始日 = 首个未足额还款期的 due_date
M1 = DPD ≥ 31 天   M2 = DPD ≥ 61 天   M3 = DPD ≥ 91 天
```

**一笔借据同时只一条未结逾期记录**——跨 M1→M2→M3 是同一条记录的 bucket 变化，
否则催收工单会重复派发。

#### 1.2.6 逾期后的分层动作

| 阶段 | DPD 阈值 | 触发动作 | 系统落库 |
|---|---|---|---|
| 即将逾期 | 到期前 T-3/T-1 | 通知经销商 | `pre_due_alerts` |
| 逾期初期 | D0 | 通知经销商、提醒还款 | `overdue_records` + `notifications` |
| 逾期升级 | M1（≥31） | 人工催收、外访 | 催收任务 + 联系记录 |
| 风险升高 | M2（≥61） | 冻结额度、限制新增融资 | `credit_line_freezes` |
| 资产风险 | M2+ 或 OOT 嫌疑 | **实地盘点 + 担保登记状态核查** | 盘点任务 |
| 严重逾期 | M3（≥91） | 委外、法务、车辆处置 | `disposal_cases` + 审批流 |

> **日本渠道调整**：原描述中的"GPS 核查"在本项目**替换为实地盘点 + 登记状态核查**
> ——GPS/钥匙/封签是中国第三方监管做法，不适用日本新车渠道（业务流程文档第 6 节）。

#### 1.2.7 盘点 job 不自行判断逾期（关键推论）

```
借据 OVERDUE → VIN 派生标记 = Y → 盘点 job 查该标记 → 盘点明细 → 生成处置任务
```

```java
// ❌ 禁止：盘点自己判断逾期
if (unit.getOverdueDays() > 30) { ... }

// ✅ 正确：读派生标记
if (unit.isLoanOverdue()) { ... }
```

**为什么这条如此重要**：盘点 / 催收 / 额度控制 / 担保释放 / 征信报送
若各写各的逾期判断，会出现**同一天、同一台车、在五个地方得到五个不同结论**——
催收说逾期 20 天（按还款计划）、征信说 35 天（按入库日）、盘点说未逾期。
**这种不一致在监管检查中是致命的。**

#### 1.2.8 状态变更留痕

`loan_status_history` 记录借据状态的每一次迁移：谁、何时、从什么到什么、依据什么。
催收的人工处置、处置岗的结案都在此留痕——这是审计、征信报送、处置追溯的共同要求。

#### 1.2.9 期限缺失时的降级链

| 期限状态 | 系统行为 | 预警 |
|---|---|---|
| 借据有 `maturity_date` | 正常判定 | 按 §1.2.6 |
| 期限为空且 `term_source=UNKNOWN`，放款已超 3 天 | **不判逾期**，生成「期限待确认」工单 | `TERM_MISSING`（强制工单） |
| 期限为空且 `term_source=INFERRED` | 按推断期限判，**预警标注"基于推断期限"** | 逾期预警降一级 |

**缺失本身是必须处理的异常**——不补就永远判不了。

### 1.4 需要新增的三个状态维度

**① 回款超期天数 `unpaid_days`**

「已售未回款」是当前最关键的敞口，但现有实现只能回答"现在还没回款"，
**回答不了"已经拖了多久"**——而后者才是判断是否升级处置的依据。

计算：以 `sold_at` 为起点，按工作日历推进至当前日（需用 `holidays` 表，
项目已有 `biz_date` / `is_business_day`）。销售结算窗口 `settle_due_date` 已有，
超过该日期即为超期。

**② 久停天数 `stalled_days`**

车还在库里，但**长时间没有任何业务动作**——既不售出、不盘点、不还款、不结清。
这类车是残值缓慢下跌但账面不动的情况，最容易被忽略。

判定基线：以 `last_audit_date`（最近盘点）与 `stock_in_date`（入库）取较早者，
配合一个可配置阈值。

**③ 风险等级 `risk_level` 的写入方**

当前字段存在但无写入方。需要明确：`risk_level` 是**系统按指标自动算**，
还是**人工按工单结论定**？

**建议：系统算「风险指标分」，人工定「风险等级」**——即：
- 系统每次巡检算出一组指标（残值率、集中度、回款超期、逾期、盘点差异），
  按规则映射出**建议等级**，写入 `suggested_risk_level`；
- 人工工单处理后确认或调整，写入 `risk_level`（唯一生效值）。

理由：`risk_level` 若由系统自动写，会触发既有的**评级变更审计链**（授信评级是
人工唯一写入口），把两个不同性质的"评级"混在一起，审计上说不清是谁改的。
分两列后，系统建议可追溯、人工生效可审计。

> **⚠️ 这条与既有约定相关**：`MEMORY.md` 记录着"告警不自动改评级（有意边界）"。
> 本设计**不推翻**该边界——授信评级（`dealers.risk_grade`）仍只由人工
> `PUT /api/dealers/{id}/risk-grade` 写入。车辆级 `risk_level` 是**单台车的风险标记**，
> 与经销商授信评级是两个层次的东西，自动化程度可以不同。

### 1.5 车辆状态双语义映射（沿用 ADR-007 决策九）

业务侧口径（在途 / 在库 / 已质押 / 已解押）≠ 领域枚举 `VehicleStatus`，
映射表在 `domain/model/VehicleStatusMapping.java`。

> **⏳ 待补**：该映射表的**单元测试仍未写**（ADR-007 明确要求）。
> 本设计不依赖它变更，但它属于贷后状态计算的地基，应尽快补齐。

## 2. 数据接入层：事件驱动为主

### 2.0 技术栈落地（工程选型）

> **选型结论**（2026-10-26 确认）：
> 后端 Spring Boot 承载 **VIN 台账 / 融资台账 / 回款匹配**三套服务；
> 定时任务用 **Quartz / Spring Schedule** 拉银行流水与巡检；
> 事件用 **Kafka / RabbitMQ** 接收 DMS / 主机厂销售推送；
> **匹配结果与未回款预警写入关系型数据库**；
> **文件凭证与车检证扫描件放对象存储**（S3）。

#### 2.0.1 选型与本设计五层的对应

| 技术 | 承担的设计层 | 具体承载 |
|---|---|---|
| **Spring Boot** | ② 状态计算层 | VIN 台账服务、融资台账服务、回款匹配服务 |
| **Quartz / Spring Schedule** | ① 接入层（兜底）+ ③ 预警层 | 拉银行流水、6 个巡检作业 |
| **Kafka / RabbitMQ** | ① 接入层（主通道） | 接收 DMS / 主机厂销售推送 |
| **PostgreSQL** | ②③④⑤ 全部 | `domain_events` / `risk_alerts` / `work_orders` / `financing_terms` / `collateral_ledger` 等 |
| **Amazon S3** | ① 接入层（文件体） | 合同扫描件、车检证扫描件、登记证明书、盘点照片、银行回单 |

#### 2.0.2 三套核心服务的职责边界

Spring Boot 不做"一个大服务"，而是按**数据归属**切三块，各自有明确的表与不变量：

| 服务 | 负责 | 关键表 | 核心不变量 |
|---|---|---|---|
| **VIN 台账服务** | 逐车状态的事实来源：是否在库/已售/已回款/已解押/已登记/已盘点/已逾期 | `vehicle_units` + `collateral_ledger` + `financing_terms` | 一台车一行台账；状态只能通过业务用例变更，不能裸改 |
| **融资台账服务** | 资金侧：垫款申请/复核/支付、额度占用、期限、计息、还款核销 | `advances` + `credit_lines` + `interest_ledger` + `repayments` | 申请≠复核≠支付（自然人级 SOD）；垫款三段式不可越级 |
| **回款匹配服务** | 把银行流水匹配到还款与销售回款，识别未回款 | `domain_events`(PAYMENT_RECEIVED) + `repayments` + `risk_alerts` | 幂等（biz_key 唯一）；匹配不上就出预警，绝不静默丢弃 |

**三者的协作关系**：

```
回款匹配服务 ──(识别到已售未回款)──→ VIN 台账服务(更新状态) ──→ 融资台账服务(释放额度)
       │                                    │
       └──→ risk_alerts(未回款预警) ←───────┘
```

**为什么按这个边界切**：三者的**变更频率与事务边界不同**——
台账状态变更最频繁（每次盘点、每笔还款），额度与计息次之，
回款匹配是批处理驱动的。混在一个服务里会导致批量匹配的长事务
阻塞台账的日常写入。

#### 2.0.3 消息队列的落地细节

**Kafka vs RabbitMQ 的取舍**：

| 维度 | Kafka | RabbitMQ | 本项目建议 |
|---|---|---|---|
| 吞吐 | 极高 | 中 | **本项目量级两者都够**（日均千级事件） |
| 消息顺序 | 分区内有序 | 单队列有序 | 都需要**按 VIN 保序**（售出事件不能早于放款事件） |
| 事件重放 | **天然支持**（按 offset 重放） | 需额外设计 | **Kafka 占优**——重放是本设计的核心诉求 |
| 运维复杂度 | 较高（ZK/KRaft） | 较低 | 团队熟悉度优先 |
| 死信队列 | 需额外机制 | **原生支持** | RabbitMQ 占优 |

**结论**：
- **首选 Kafka**——事件重放能力直接服务于"人工重触发""失败重试""对账回溯"三个硬需求；
- 若团队运维资源有限、或更看重死信队列与低延迟，**RabbitMQ 亦可**，
  但必须补一个「事件重放」机制（把 `domain_events` 表作为重放源，
  消息只做投递信号、真相在库里——这一点两种选型都成立）。

**关键设计：消息只做"投递信号"，真相在 `domain_events` 表**

```
Kafka/RabbitMQ  →  消费者收到消息  →  按 biz_key 写 domain_events（幂等）  →  应用层处理
                                          ↑
                              这是唯一真相源；消息丢了可以从定时兜底补录
```

这样做的三个好处：
1. **消息丢失不丢数据**——定时兜底能从 `domain_events` 补
2. **消息重复不重复处理**——`uk_domain_event` 唯一约束兜底
3. **换 MQ 不影响业务**——消费者读的是表，不是消息格式

> **保序策略**：Kafka 按 `vin` 作为分区键（同一台车的事件进同一分区，保证顺序）；
> RabbitMQ 用一致性哈希 exchange 或按 VIN 路由到固定队列。
> **放款事件必须先于售出事件**——否则会出现"先收到售出、找不到台账行"。

#### 2.0.4 定时任务的落地

**Quartz vs Spring Schedule**：

| 维度 | Spring Schedule | Quartz |
|---|---|---|
| 集群调度 | ❌ 不支持（多实例会重复执行） | ✅ 支持（数据库锁） |
| 动态调整 | 需改配置重启 | ✅ 运行时改 cron |
| 依赖 | 零（Spring 自带） | 需引 jar + DB 表 |
| 复杂度 | 低 | 中 |

**建议**：
- **一期用 Spring Schedule**（零依赖，配合 `batch_runs` 表的 `uq_batch_job_date`
  唯一约束做幂等——即使多实例重复触发，数据库也会挡住）
- **生产多实例部署时换 Quartz**（或加分布式锁）

**银行流水拉取的具体安排**：

```
每日 06:00 (JST)  BANK_FETCH    拉银行入金文件（FTP/SFTP/API/人工上传）
                              → 逐笔写 domain_events(source=BANK, event_type=PAYMENT_RECEIVED)
                              → 立即触发回款匹配服务

每日 07:00 (JST)  BANK_RECONCILE  对账：流水 vs repayments vs 已售未回款台账
                                  → 不匹配的三类各出预警

每周一 05:00 (JST)  REGISTRATION_EXPIRY_SCAN  登记到期巡检
每日 05:30 (JST)  TERM_CHECK / DEALER_METRIC_SCAN / RISK_SCAN
每周一 06:00 (JST)  INVENTORY_PLAN  盘点任务生成
```

**时区**：全部按 **JST** 调度。项目已有 `holidays` 表与 `BusinessCalendar`，
业务日计算走工作日历。

#### 2.0.5 对象存储的边界

### 2.1 事件模型

新增 `domain_events` 表作为**统一事件总线**。所有外部数据先落事件表，
再由应用层消费——这样**任何时点的数据变更都可回溯、可重放、可对账**。

```sql
CREATE TABLE domain_events (
    id            BIGSERIAL PRIMARY KEY,
    event_type    VARCHAR(48)  NOT NULL,   -- 事件类型（见 §2.2）
    source        VARCHAR(32)  NOT NULL,   -- 来源：DMS / OEM / BANK / AUDIT_APP / LEGAL / MANUAL
    dealer_id     BIGINT,                  -- 关联经销商（可空：批量事件）
    vin           VARCHAR(32),             -- 关联车辆（可空：批次级事件）
    biz_key       VARCHAR(128),            -- 业务主键（幂等锚点，如银行流水号）
    payload       JSONB        NOT NULL,   -- 事件原始载荷（防腐层转换前的外部格式）
    ref_type      VARCHAR(32),             -- 转换后引用的对象类型
    ref_id        VARCHAR(64),             -- 转换后引用的对象 ID
    event_time    TIMESTAMPTZ  NOT NULL,   -- 事件发生时间（对方系统时间，非我方接收时间）
    received_at   TIMESTAMPTZ  NOT NULL DEFAULT now(),
    status        VARCHAR(16)  NOT NULL DEFAULT 'RECEIVED',
        -- RECEIVED 已接收 / PROCESSED 已处理 / FAILED 处理失败 / IGNORED 判定为无效 / DUPLICATED 重复
    error_detail  TEXT,
    processed_at  TIMESTAMPTZ,
    -- 幂等：同一来源同一业务主键只处理一次
    CONSTRAINT uk_domain_event UNIQUE (source, event_type, biz_key)
);
```

**为什么用事件表而不是直接调应用服务**：

1. **幂等有物理保障**——唯一约束在数据库层，重复推送不会重复处理
2. **失败可重放**——处理失败的状态留在表里，人工/定时可重试
3. **原始载荷留存**——日本场景下双方数据冲突时要能回看"对方到底报了什么"
4. **对账有依据**——外部文件与内部台账的差异可逐笔追到事件行

### 2.2 事件类型清单

| 事件类型 | 来源 | 触发效果 | 现实可行性 |
|---|---|---|---|
| `VEHICLE_SOLD` | 经销商 DMS | 标记已售 → 挂回款义务 | ⚠️ 需经销商配合 |
| `VEHICLE_DELIVERED` | 经销商 DMS | 标记已交车（区别于已开票） | ⚠️ 同上 |
| `VEHICLE_INVOICED` | 主机厂 | 标记已开票（确认采购订单履行） | ⚠️ 主机厂多为文件交换 |
| `VEHICLE_SHIPPED` | 主机厂 | 标记已出库（到货在途） | ⚠️ 同上 |
| `VEHICLE_REGISTERED` | 主机厂/法务省 | 确认已登记 | ⚠️ **对民间基本无接口**，实务靠证明书 |
| `PAYMENT_RECEIVED` | 银行 | 回款到账 → 触发还款核销 | ⚠️ 入金消佐可能半人工 |
| `SALES_INVOICE_UPLOADED` | 经销商 | 销售发票入证 | ✅ 人工上传（门户/Excel） |
| `INSPECTION_CERT_UPLOADED` | 经销商 | 车检证入证 | ✅ 人工上传 |
| `AUDIT_RESULT` | 盘点 App | 盘点结果 → 差异判定 | ✅ **可落地**（已有盘点接口） |
| `REGISTRATION_RECEIPT` | 法务省/代办 | 登记回执 → 登记完成 | ⚠️ 人工为主 |
| `CANCELLATION_COMPLETED` | 法务省/代办 | 抹消完成 | ⚠️ 人工为主 |
| `MANUAL_CORRECTION` | 人工后台 | 人工补录/修正 | ✅ 人工路径一等公民 |

**关键现实约束（来自外部集成文档 §3）**：

> 车辆登记对民间**基本无开放接口**，实务靠登记事项证明书等书面文件或委托代办；
> 厂家系统多为 EDI/CSV 文件交换，REST 少见；银行入金消佐可能半人工。

因此本设计的**工程重心不在"接通所有外部系统"**，而在：

1. **事件模型统一**——无论数据来自 API、文件还是人工录入，都落同一张 `domain_events`，
   下游状态计算逻辑**完全一致**（这是外部集成文档 §2.5「人工路径是一等公民」的落地）
2. **定时兜底不可省**——既然多数外部数据最终靠文件/人工，必然有延迟甚至遗漏，
   定时巡检是**唯一能保证"不漏"的机制**
3. **对账是兜底不是补充**——外部集成文档 §2.4 的定论，本设计完全采纳

### 2.3 防腐层（ACL）

沿用外部集成文档 §2.2 的强制约束：

```
外部 DTO → [ACL 转换] → 内部命令（Command）→ application → domain
```

- 事件表的 `payload` 存**外部原始格式**（便于回溯与纠纷举证）
- ACL 转换器负责外部字段 → 内部枚举/语义映射
- 外部格式变更**只影响 ACL 层**，不污染领域模型
- 车辆状态双语义映射（`VehicleStatusMapping`）就是 ACL 的一部分

### 2.4 接入通道

| 通道 | 协议 | 触发方式 | 优先级 |
|---|---|---|---|
| 外部推送（Inbound） | REST + 签名 | 实时事件 | **主** |
| 文件投递 | CSV / EDI | 定时拉取 | **主**（现实更常见） |
| 定时巡检 | 内部计算 | 批处理 | **兜底** |
| 人工补录 | 门户表单 / Excel | 人工触发 | **兜底**（不是过渡方案，是长期形态） |

四条通道**汇入同一事件表**，下游无感知。

### 3.2 逐个作业设计

#### ① BANK_RECONCILE（回款对账，每日）

> **📄 完整设计见《库存融资核心系统-回款闭环与资金监管设计.md》**
> ——该文档按**账户层 / 流水层 / 匹配层 / 释放层**四层展开，
> 包含指定回款账户表扩展、银行流水表、五级自动匹配规则与置信度、
> 多台车拆分、释放编排与证据链留存。本节只列作业级摘要。

**为什么必须有**：回款是**资金闭环的最后一环**。"卖出一台车后，回款是否进入指定账户
或用于还款"——这是日本落地要点第二条，也是最容易被绕过的一环。
经销商完全可以卖车后把钱先收进自己的账，等催收才还。

**流程**：

```
① 采集银行流水（API / MT940 / CSV / 人工上传）→ payment_transactions
② 匹配层执行自动匹配（VIN > 订单号 > 金额+时间窗）→ payment_allocations
   低置信度 → 转人工队列（贷后工作台）
③ 校验已核销还款的「实际到账账户」是否为指定回款账户
   - 否 → 「回款进入非指定账户」预警（PAYMENT_WRONG_ACCOUNT）
④ 对台账中「已售未回款」的车，检查其回款是否已到账
   - 到账但未匹配 → 「待核销」预警（PAYMENT_UNMATCHED）
⑤ 匹配成功 → 释放层（扣本金 / 释放额度 / 担保实体消灭 / 抹消待办 / 证据链）
```

**产出预警**：`PAYMENT_UNMATCHED`（回款长期未匹配）、`PAYMENT_AMOUNT_MISMATCH`（金额不匹配）、
`PAYMENT_WRONG_ACCOUNT`（回款进入非指定账户）、`MULTI_VIN_SPLIT`（多台车同笔回款需人工拆分）。

> **⚠️ 有效性的前置条件**：**系统只能看到它采集到的账户的流水**。
> 若经销商用未采集的账户收款，系统根本看不见——"非指定账户预警"永远不会触发。
> **这个预警的有效性取决于账户安排（合同约定），不取决于系统实现。**
> 详见回款闭环设计 §5.2。

#### ② VIN_LEDGER_RECONCILE（VIN 台账比对，每日）

**为什么必须有**：不能只信经销商自报。这是"交叉验证"落地的地方。

**流程**：

```
① 拉取经销商 DMS 库存快照（在库 VIN 清单）
② 与债权人 VIN 台账逐 VIN 比对：
   - 台账有、DMS 无 → 「台账有车现场无」预警（可能已脱信销售，最高优先级）
   - DMS 有、台账无 → 「台账外车辆」预警（可能已被其他金融公司融资）
   - 双方都有但状态不符（如台账已售、DMS 仍在库） → 「状态冲突」预警
③ 与主机厂侧数据（已开票/已出库/已登记）三方交叉，
   不一致时产出「数据冲突」工单交人工裁决
```

**产出预警**：`LEDGER_VIN_MISSING`（台账有车现场无）、`LEDGER_VIN_EXTRA`（台账外车辆）、
`LEDGER_STATE_CONFLICT`（状态冲突）。

> **注意**：手工盘点（`AUDIT_RESULT`）与 DMS 比对是**两条独立路径**，
> 前者是人工到现场，后者是系统比数据。两条路径都指向同一台账——
> 这正是"交叉验证"的意义：单靠经销商上报不可信，单靠人工盘点覆盖不了每天。

#### ③ REGISTRATION_EXPIRY_SCAN（登记到期巡检，每周）

**为什么必须有**：让渡担保登记**有 5 年法定期限且不可续展**（ADR-007 已确认）。
到期未重新设定 = 担保公示效力消灭，是个"静默失效"——不主动扫就会一直挂着。

**流程**：

```
① 取 collateral_registration_batches 中 expires_at 临近且 cancellation_status
   非 DONE/CANCELLED 的批次
② 剩余天数分档：
   ≤90 天  → 高优先预警（须安排重新登记）
   ≤30 天  → 紧急预警（逾期即失去公示效力）
   已过期  → 严重预警（须人工评估风险敞口与补救）
③ 检查证据链完整性：合同附件 / 登记证明书是否齐备（缺口 → 证据链预警）
```

**产出预警**：`REG_EXPIRING_90` / `REG_EXPIRING_30` / `REG_EXPIRED` / `REG_EVIDENCE_GAP`。

> 现有 `collateral_registration_batches` 已建 `idx_crb_expires` 索引与
> `GET /api/collateral/registration-batches/expiring` 接口，**只差批处理驱动**。

#### ④ DEALER_METRIC_SCAN（经销商经营指标巡检，每日）

**为什么必须有**：车辆级指标看不见经销商整体恶化。某台车还正常，但某经销商
库存龄全面拉长、周转全面放缓——这是**额度层面的风险**，比单车问题更早暴露。

**指标清单**：

| 指标 | 口径 | 数据源 | 预警方向 |
|---|---|---|---|
| 销售周转天数 | 库存平均在库天数 | `vehicle_units.stock_in_date` → `sold_at` | 走高 |
| 库存龄分布 | 按在库天数分档台数与占比 | 同上 | 老化 |
| 逾期率 | 逾期台数 / 在库台数 | `overdue_days`（**期限模型计算**）/ `aging_plans` | 走高 |
| 额度占用率 | `used_amount` / `approved_limit` | `credit_lines` | 走高 |
| 库龄递减执行率 | 已核销期数 / 应核销期数 | `aging_plans` / `curtailment_payments` | 走低 |
| 盘点缺失台数 | `audit_mismatch_count > 0` | `vehicle_units` | 走高 |
| 担保登记覆盖率 | 已登记台数 / 在库台数 | `collateral_ledger.security_status` | 走低 |

**产出预警**：`METRIC_TURNOVER_SLOW` / `METRIC_AGING_HEAVY` / `METRIC_OVERDUE_RATE`、
`METRIC_CREDIT_UTILIZATION` / `METRIC_CURTAILMENT_BEHIND` / `METRIC_AUDIT_MISSING`、
`METRIC_SECURITY_COVERAGE`。

#### ⑤ INVENTORY_PLAN（盘点任务生成，每周）

**为什么必须有**：当前盘点是"谁来提交就什么时候提交"，没有计划、没有频次、
没有漏盘提醒——漏盘的车永远不会有人发现（除非恰好触发别的巡检）。

**流程**：

```
① 按经销商维度确定盘点频次（可配置：按经销商 / 按额度等级 / 固定周期）
② 找出"距上次盘点已超过频次"的在库车
③ 生成盘点任务（工单），指派贷后管理岗
④ 逾期未执行 → 自动升级预警（盘点逾期本身是风险信号）
```

**产出**：`inventory_tasks`（盘点任务）+ 工单 + `AUDIT_OVERDUE`（盘点逾期预警）。

**盘点频次（已由 ADR §5 #7 裁决为系统默认，按经销商分档）**：

| 经销商类型 | 建议频次 |
|---|---|
| 额度占用率 > 80% 或有逾期 | 每月 |
| 正常在库 | 每季度 |
| 新准入（前 3 个月） | 每月 |

#### ⑥ RISK_SCAN（风险扫描，每日）

**指标层 + 扫描层的合体**，逐台车算风险指标并映射预警。
详见 §3.3。

### 3.3 RISK_SCAN 指标设计

#### 3.3.1 残值监控

**这是最难的一项，因为系统里没有任何残值数据。**

**问题**：残值（车的当前市价）从哪来？

**现实约束**：日本新车渠道的新车残值有公开数据源（主机厂指导价、二手拍卖行情），
但：
- 指导价 ≠ 残值（指导价是新车价，残值是二手价）
- 拍卖行情按**车型 + 车龄 + 里程 + 事故史**定价，不是按 VIN
- 残值数据在系统里**目前一个字段都没有**

**建议方案（三阶段渐进）**：

| 阶段 | 做法 | 说明 |
|---|---|---|
| **一阶段（可立即落地）** | **用车龄 + 里程的规则化折旧曲线**估算残值 | 不需要外部数据。用 `model_year`（年款）+ `mileage`（里程）按行业经验折旧率算，再与 `invoice_amount` 比，算出**残值率**。这是**估算值**，标注为估算，不作为处置定价依据 |
| **二阶段** | 主机厂/拍卖行**行情文件接入** | 外部集成文档已列"厂家系统"通道。接入后用真实行情替换估算 |
| **三阶段** | **人工估价覆盖**（处置时） | 违约处置环节由人工评估出`评估价`，作为残值的权威值 |

**残值率告警**：`残值率 = 估算残值 / 垫款余额`。当残值率低于阈值（建议 1.2，
即垫款不超过残值的 83%）时预警——这是"垫款快覆盖不住车了"的信号。

> **为什么阈值是 1.2 而不是 1.0**：日本新车渠道处置变现周期长（拍卖、过户、
> 运回国内或本地分销），且存在折价。留 20% 缓冲是经验值，**裁决为系统默认阈值 1.2（ADR §5 #2），可配置覆盖**。

**二阶段三阶段的接口位**：`vehicle_units` 需加 `residual_value_estimated` /
`residual_value_source`（ESTIMATED / MARKET / MANUAL）/ `residual_value_at` 三个字段。
一阶段先落第一个字段。

#### 3.3.2 集中度监控

**口径选择**：这是需要业务判断的地方，两个维度都要：

| 维度 | 口径 | 说明 |
|---|---|---|
| **经销商维度** | 单一经销商敞口 / 总敞口 | 分散度不足 = 单一客户风险 |
| **车型维度** | 单一车型敞口 / 总敞口 | 日本市场小众车型（MPV、kei、轻商）残值跌幅远大于主流车型——**车型集中度风险比经销商集中度更致命** |
| **品牌维度** | 单一品牌敞口 / 总敞口 | 品牌政策变动（召回、停产、降价）会同时冲击整批车 |
| **区域维度** | 单一区域敞口 / 总敞口 | 灾害、区域需求波动 |

**为什么车型维度更重要**：日本新车市场价格战时，厂商对特定车型降价会**瞬间击穿残值**。
一台主流车型降价 5% 是常态，某款小众 MPV 停产则可能一夜之间跌 30%。
押注单款小众车型的经销商，其风险不是"这批车卖不掉"，而是"这批车同时贬值得很惨"。

**已裁决阈值（ADR §5 #4，可配置）**：单一车型敞口占比 > 20% → 预警；> 30% → 高优先。

**实现**：需新增 `risk_concentration_snapshots` 表存每日快照（否则"占比"无法算——
分母每天在变，必须有历史序列才能算趋势）。

#### 3.3.3 逾期与回款超期

| 指标 | 阈值（建议） | 说明 |
|---|---|---|
| 单台逾期天数 | > 30 天 → MEDIUM；> 60 天 → HIGH | `overdue_days`（**期限模型计算，§1.2.5**） |
| 回款超期（已售未回款）天数 | > 结算窗口 + 7 天 → HIGH | **需新增 `unpaid_days`** |
| 库龄递减连续未执行 | 连续 2 期 → HIGH | 已有 `aging_plans` 可算 |

#### 3.3.4 久停监控

车在库但无任何动作的天数。基线取 `max(stock_in_date, last_audit_date)`，
阈值建议 90 天无动作 → 预警。

#### 3.3.5 担保覆盖率

`已登记台数 / 在库台数`。这直接暴露我上一轮发现的缺口：**放款后未登记担保的车会正常计息、
正常进入库龄递减，没有任何环节会拦住它**。

**建议**：在库台账中 `security_status` 为空/PENDING 的车 → 逐台预警。
这是一条**确定性极强**的预警（不是估算，是事实），应该是 P0。

### 3.4 预警规则的可配置性

**沿用既有先例**：授信评级口径已经是"后台动态配置 + 即时生效"（`rating_configs` 表），
不要为预警阈值重造一套。

新增 `risk_rules` 表：

```sql
CREATE TABLE risk_rules (
    id            BIGSERIAL PRIMARY KEY,
    rule_code     VARCHAR(48) UNIQUE NOT NULL,   -- 规则代码
    metric        VARCHAR(32)  NOT NULL,          -- 指标标识
    threshold_type VARCHAR(16) NOT NULL,         -- GT / GTE / LT / LTE / OUTSIDE
    threshold_value NUMERIC(18,4) NOT NULL,
    unit          VARCHAR(16),                   -- DAY / RATIO / COUNT / PERCENT
    severity      VARCHAR(8)  NOT NULL,          -- LOW / MEDIUM / HIGH / CRITICAL
    window_days   INTEGER,                       -- 观察窗口（用于趋势类规则）
    enabled       BOOLEAN NOT NULL DEFAULT TRUE,
    applies_to    VARCHAR(16) NOT NULL DEFAULT 'ALL',  -- 规则适用范围（可按经销商类型）
    updated_by    VARCHAR(64),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

配套接口：`GET /api/risk-rules`、`PUT /api/risk-rules/{code}`（管理员/授信岗）。
**改阈值不改代码**——与既有评级配置的口径一致。

## 4. 预警层

### 4.1 预警的六个属性

一条预警必须能回答：**什么车 / 什么问题 / 为什么严重 / 谁来处理 / 什么时候前处理完 / 依据是什么**。

### 4.2 `alerts` 表的定位调整

现有 `alerts` 表只有 `dealer_id / vin / alert_type / severity / status / detail / created_at`，
**不足以承载预警**（无指标值、无依据、无去重键、无升级路径、无关联工单）。

**方案**：不改造 `alerts`（它已被 9 处代码使用，且语义清晰），
**新增 `risk_alerts` 表**承载新预警，`alerts` 保留兼容旧流程。

```sql
CREATE TABLE risk_alerts (
    id             BIGSERIAL PRIMARY KEY,
    alert_code     VARCHAR(48) NOT NULL,     -- 预警类型（如 REG_EXPIRING_30）
    severity       VARCHAR(8)  NOT NULL,     -- LOW/MEDIUM/HIGH/CRITICAL
    dealer_id      BIGINT,
    vin            VARCHAR(32),
    batch_id       BIGINT,                   -- 登记批次级预警
    metric_value   NUMERIC(18,4),            -- 触发时的指标值
    threshold_value NUMERIC(18,4),           -- 当时的阈值（存快照：阈值会改，历史预警要能复现）
    detail         TEXT,                     -- 人类可读描述
    evidence_refs  JSONB,                    -- 依据（事件ID/附件ID/证据链ID）
    first_seen_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_seen_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    occurrence_count INTEGER NOT NULL DEFAULT 1,  -- 重复发生次数
    status         VARCHAR(16) NOT NULL DEFAULT 'OPEN',
        -- OPEN 待处理 / ACKNOWLEDGED 已受理 / IN_PROGRESS 处理中 /
        -- RESOLVED 已解决 / DISMISSED 已忽略（误报）/ AUTO_CLOSED 自动闭环
    -- 去重键：同一对象同一预警类型只保留一条 OPEN 记录，重复触发只累加计数
    CONSTRAINT uk_risk_alert_open UNIQUE (alert_code, COALESCE(vin,''), COALESCE(batch_id::text,''))
        WHERE status IN ('OPEN','ACKNOWLEDGED','IN_PROGRESS')
);
```

**为什么存阈值快照**：阈值是可配置的，今天 90 天、明天改成 60 天。
历史预警如果只存"当前阈值"，事后复盘就说不清当时为什么报警。
**存快照是审计要求，不是过度设计**。

### 4.3 预警的去重、升级与抑制

**去重**：唯一约束保证同一车同一类型只有一条未闭环预警，重复触发累加 `occurrence_count`
并更新 `last_seen_at`。

**升级**：
```
同一预警 occurrence_count 达阈值（如 3 次）→ severity 自动升一级
severity 达 CRITICAL → 强制生成工单（不允许只挂在预警列表里等人刷）
```

**抑制（误报处理）**：人工判定误报 → `status = DISMISSED`，记录判定依据。
**同一规则 + 同一对象 90 天内不再重复生成**（抑制期入库，避免人工判定一次误报后
每天被同一件事刷屏——这是工单系统最常见的体验灾难）。

### 4.4 预警 → 工单的自动转换

**不是所有预警都要工单**。转换规则：

| 预警类型 | 是否自动转工单 |
|---|---|
| `REG_EXPIRED`、`LEDGER_VIN_MISSING`、`RECON_ACCOUNT_DEVIATION`、`METRIC_SECURITY_COVERAGE` | **强制**（严重，必须有人跟） |
| `REG_EXPIRING_30`、`RECON_UNMATCHED`、`METRIC_OVERDUE_RATE` | **强制** |
| `AUDIT_OVERDUE`、`LEDGER_STATE_CONFLICT`、`METRIC_TURNOVER_SLOW` | 按阈值（可配置） |
| `AUDIT_MISMATCH`、`LEDGER_VIN_EXTRA`、`METRIC_CURTAILMENT_BEHIND` | 否（进预警列表，贷后岗每日巡检时批量处理） |

**设计意图**：人工时间是最贵的资源。**能在列表里批量看一眼关掉的，不给它开工单。**
只有"必须有人单独跟进、能拖、拖了会出事"的才升级成工单。

## 5. 工单层

### 5.1 为什么需要独立的工单层

现有 `alerts` 只能"标记已处理"——没有：
- **责任人**（谁该处理）
- **SLA**（多长时间内必须处理）
- **处置动作**（允许做什么，不能做什么）
- **处理记录**（做了什么、依据是什么）
- **升级机制**（超期自动上报）

这些是贷后管理的核心，告警表承载不了。

### 5.2 工单模型

```sql
CREATE TABLE work_orders (
    id            BIGSERIAL PRIMARY KEY,
    order_no      VARCHAR(32) UNIQUE NOT NULL,
    order_type    VARCHAR(32) NOT NULL,
        -- 盘点差异 / 已售未回款跟进 / 资料补录 / 登记异常 /
        -- 数据冲突裁决 / 违约处置 / 清算审批 / 额度冻结解冻
    source_alert_id BIGINT REFERENCES risk_alerts (id),
    dealer_id     BIGINT,
    vin           VARCHAR(32),
    batch_id      BIGINT,
    severity      VARCHAR(8) NOT NULL,
    priority      VARCHAR(8) NOT NULL,     -- P1/P2/P3（与 severity 独立：severity 是风险度，priority 是处理顺序）
    status        VARCHAR(16) NOT NULL DEFAULT 'OPEN',
        -- OPEN 待受理 / ACKNOWLEDGED 已受理 / IN_PROGRESS 处理中 /
        -- PENDING_EXTERNAL 待外部（等经销商/银行/法务局） / RESOLVED 已解决 / CANCELLED 已取消
    assignee      VARCHAR(64),            -- 处理人（自然人，来自令牌身份）
    sla_due_at    TIMESTAMPTZ NOT NULL,    -- 处理时限
    sla_breached  BOOLEAN NOT NULL DEFAULT FALSE,
    resolution    TEXT,                   -- 处理结论
    resolution_code VARCHAR(32),          -- 结论分类（便于统计与复盘）
    created_by    VARCHAR(64),             -- 创建人（系统自动时为 'system'）
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    acknowledged_at TIMESTAMPTZ,
    resolved_at   TIMESTAMPTZ,
    -- 责任人不得与创建人相同（若为人工发起）——延续 SOD 原则
    CONSTRAINT chk_wo_status CHECK (status IN
        ('OPEN','ACKNOWLEDGED','IN_PROGRESS','PENDING_EXTERNAL','RESOLVED','CANCELLED'))
);

CREATE TABLE work_order_actions (
    id          BIGSERIAL PRIMARY KEY,
    order_id    BIGINT NOT NULL REFERENCES work_orders (id),
    action_type VARCHAR(32) NOT NULL,
        -- ACKNOWLEDGE 受理 / ASSIGN 转派 / COMMENT 备注 / REQUEST_DOC 索取资料 /
        -- ESCALATE 升级 / RESOLVE 解决 / CANCEL 取消 / ATTACH 附证据
    action_data JSONB,
    attachment_id BIGINT,                  -- 补录的证据（照片/证明书/银行回单）
    operator    VARCHAR(64) NOT NULL,      -- 操作人（自然人）
    operated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### 5.3 SLA 规则

| 工单类型 | SLA | 超期动作 |
|---|---|---|
| 盘点差异 | 2 个工作日 | 升 HIGH + 通知上级 |
| 已售未回款跟进 | 3 个工作日 | 升 HIGH |
| 登记异常 / 即将到期 | 5 个工作日 | 升 HIGH |
| 数据冲突裁决 | 5 个工作日 | 升 MEDIUM |
| 资料补录（经销商不配合） | 10 个工作日 | 升 HIGH + 计入经销商配合度考核 |
| 违约处置 / 清算审批 | 按处置流程 | 转处置岗，**脱离 SLA**（走处置闭环） |

**SLA 用工作日历计算**（项目已有 `holidays` 表）——日本节假日不能按自然日算。

### 5.4 工单与角色的对应

| 工单类型 | 处理岗 | 需要的权限点 |
|---|---|---|
| **期限确认** | 贷后管理岗 | `WORK_ORDER_HANDLE` |
| 盘点差异 | 采购审核岗 / 贷后管理岗 | `INVENTORY_AUDIT` |
| 已售未回款跟进 | 结算岗 / 催收岗 | `REPAYMENT_EXECUTE` / `CURTAILMENT_EXECUTE` |
| 资料补录 | 贷后管理岗 | `ATTACHMENT_UPLOAD` |
| 登记异常 / 到期 | 担保管理岗 | `COLLATERAL_MAINTAIN` |
| 数据冲突裁决 | 贷后管理岗 | `RISK_HANDLE` |
| 违约处置 / 清算审批 | 违约处置岗 | `DISPOSAL_EXECUTE` |
| 额度冻结 / 解冻 | 授信审查岗 | `ANNUAL_REVIEW` / `CREDIT_MANAGE` |

**新增权限点**：

| 权限点 | 中文名 | 授予角色 |
|---|---|---|
| `WORK_ORDER_HANDLE` | 工单受理与处理 | 贷后管理岗、催收岗、结算岗、担保管理岗 |
| `WORK_ORDER_ESCALATE` | 工单升级与转派 | 贷后管理岗（上级） |
| `RISK_RULE_CONFIG` | 风险规则与阈值配置 | 授信审查岗、系统管理员 |

### 5.5 工单与既有流程的衔接

工单**不替代**既有流程，而是**驱动**它们：

| 工单 | 完成后触发的既有流程 |
|---|---|
| **期限确认** | → `PUT /api/vehicles/{vin}/financing-term`（录入期限并立即重算逾期） |
| 盘点差异复核 | → `POST /api/inventory/audit`（正式提交盘点） |
| 已售未回款跟进 | → `POST /api/repayments`（回款核销） |
| 登记异常 | → `POST /api/collateral/registration-batches`（补登记）/ 抹消三段推进 |
| 违约处置审批 | → `POST /api/disposals/*`（处置闭环） |
| 额度冻结解冻 | → `PUT /api/credit-lines/{id}/status` |

**关键**：工单处置**不直接改台账**，而是调用既有的业务接口——
保证状态流转只有一条路径，不出现"工单里直接 update 台账"绕过业务规则的情况。

## 6. 人工后台：贷后工作台

### 6.1 核心原则

> **人工不逐条盯车。** 人工只处理系统算出来的**例外**和需要**判断**的事。

工作台的信息架构按「今天要做什么」组织，而不是按「数据表」组织。

### 6.2 七类人工工作

| # | 工作类型 | 触发来源 | 人工要做的事 | 工单类型 |
|---|---|---|---|---|
| 0 | **期限待确认** ⚠️ | 放款后未录入期限 | 打开法务省登记合同 / 与经销商签的合同，或结合台账反推 → 录入到期日 | 期限确认 |
| 1 | **盘点差异复核** | 盘点差异预警 | 判断差异性质（临时挪车 / 已售未回款 / 失联），决定是否升级为 OOT | 盘点差异 |
| 2 | **已售未回款跟进** | 回款超期预警 | 联系经销商催收，记录承诺；必要时冻结额度 | 已售未回款 |
| 3 | **经销商不配合上传资料** | 资料补录预警 | 记录不配合行为，计入配合度考核，必要时升级 | 资料补录 |
| 4 | **法务省登记异常** | 登记到期 / 证据缺口预警 | 补登记、委托代办、评估补救方案 | 登记异常 |
| 5 | **主机厂与经销商数据冲突** | 三方交叉验证预警 | 裁决以哪方为准，记录依据，必要时冻结相关车辆 | 数据冲突 |
| 6 | **违约处置 / 清算审批** | 逾期升级 | 走处置闭环，认定损失 | 违约处置 |
| 7 | **额度冻结 / 解冻** | 年审 / 风险集中 | 调整额度状态 | 额度冻结解冻 |

## 7. 证据留存清单

### 7.1 盘点证据

| 项 | 内容 | 留存方式 |
|---|---|---|
| 照片 | 每台车的车况照（不少于 4 方位）、铭牌照、里程表照 | S3 附件 + `collateral_evidence_links` |
| VIN 核对 | 逐台扫码/人工核对记录 | 盘点提交时记录 `matched/missing/unexpected` |
| 里程 | 实测里程（与建账时对比，差异大是异常信号） | 盘点记录 |
| 存放地点 | 经销商具体存放位置（防止车已转移至他处） | 盘点记录 |
| 钥匙 | **备注**：日本渠道不做钥匙扣押，仅记录钥匙是否齐全 | 盘点记录 |
| 盘点人 / 时间 | 实地盘点人（自然人）、时间 | `audit_events` + `last_audit_by` |

> **关于钥匙**：这是**有意的边界**。日本新车渠道不采用扣押钥匙/GPS/封签
> （那是中国第三方监管做法，见外部集成文档）。盘点时**记录**钥匙情况是事实采集，
> **不作为控制手段**。

### 7.2 清算证据

| 项 | 内容 | 留存方式 |
|---|---|---|
| 违约通知 | 催告函、书面通知（送达凭证） | S3 附件 |
| 评估 | 残值评估报告（人工估价覆盖残值估算） | S3 附件 + `residual_value_source=MANUAL` |
| 变卖 | 拍卖记录、变卖成交凭证 | S3 附件 |
| 清算计算书 | 应收本金 + 利息 + 费用 − 变现收入 = 损失 | `disposal_cases.loss_amount` + 附件 |
| 处置决定 | 审批记录（谁批的、依据什么） | `audit_events` + 工单 |

### 7.3 证据链完整性检查

**已有**：`GET /api/collateral/evidence-gaps`（担保物台账 V10 已实现），
检查合同/证明书/抹消凭证的缺失。

**需要扩展**：把证据缺口检查从"担保物维度"扩展到"全链路维度"：

| 缺口类型 | 检查内容 |
|---|---|
| 担保凭证 | 合同 / 登记证明书 / 抹消凭证 |
| 销售凭证 | 销售发票 / 车检证 |
| 盘点凭证 | 照片 / 盘点记录 |
| 清算凭证 | 违约通知 / 评估 / 变卖凭证 / 清算计算书 |

**缺口的处理**：不阻断流程（会卡死业务），但**生成证据链预警工单**——
由贷后岗补齐或说明原因。

### 9.4 明确不做（有意边界）

| 项 | 原因 |
|---|---|
| 告警自动改授信评级 | 既有约定：评级唯一写入口是人工 `PUT /api/dealers/{id}/risk-grade`。告警只写预警表 |

| 工单里直接改台账 | 状态流转只走既有业务接口，避免绕过业务规则 |
| 未登记担保就阻断计息 | 计息是合同义务（钱已付、占用在计），阻断会引发台账问题。用告警+工单不用阻断 |
| 逐台车的人工巡检列表 | 与"人工只处理例外"原则冲突 |
| 残值的一阶段估算作为处置定价依据 | 估算值仅用于预警，处置定价必须人工评估 |

| **0c** | **罚息利率** | 需业务给数值（是合同约定还是系统默认） | 逾期后计息 |

| **0e** | **到期未结清时是否强制还款** | 建议不强制（允许展期），但强制预警 + 工单 | 处置力度 |
| **0f** | **人工读合同的 SLA** | 3 个工作日（放款后 3 天内必须补录） | 期限缺失暴露速度 |
| 1 | 残值口径 | 一阶段用车龄+里程折旧曲线估算 | 残值告警的准确度 |
| 2 | 残值率告警阈值 | 1.2（垫款 ≤ 残值 83%） | 告警数量 |
| 3 | 集中度维度 | 车型 + 品牌 + 经销商 + 区域**四个都要** | 覆盖度 vs 噪声 |
| 4 | 集中度阈值 | 单一车型 > 20% 预警、> 30% 高优先 | 告警数量 |
| 5 | 风险等级档位 | 4 档（低/中/高/严重） | 与预警严重度是否合并 |
| 6 | 风险等级是否自动写 | **建议：系统给建议值，人工确认生效** | 审计链完整性 |
| 7 | 盘点频次 | 高风险经销商每月 / 正常每季度 / 新准入每月 | 盘点工作量 |
| 8 | 盘点逾期 SLA | 2 个工作日 | 响应速度 |
| 9 | 回款超期阈值 | 结算窗口 + 7 天 | 催收启动点 |
| 10 | 已售未回款处置动作 | 催收 → 冻结额度 → 违约处置 | 处置闭环 |
| 11 | 担保登记覆盖率阈值 | 在库台账中未登记即逐台预警 | P0 必做 |
| 12 | 工单处理人分配规则 | 按经销商归属人 / 按工单类型 / 抢单 | 工作台可用性 |

## 11. 与其他文档的关系

| 文档 | 关系 |
|---|---|
| 《业务流程文档》环节④⑤ | 本文档是这两环节的**系统落地设计**，补充其中标注的 `RISK_SCAN` 作业 |
| **《回款闭环与资金监管设计》** | 本文档的 §3.4 回款对账、§5 资金闭环校验的**完整展开**——账户层/流水层/匹配层/释放层四层设计。两者共用 `risk_alerts` / `work_orders` / `domain_events` 三张表与同一套工单体系 |
| **《库龄递减与强制还款设计》** | 环节⑥（库龄递减还款）的落地设计。分层递增规则 + 自动扣款 + 豁免审批 + 未还款升级（L1 冻结额度 → L2 限制解押 → L3 转违约）。与本文档共用 `work_orders` 工单体系与 `risk_alerts` 预警表；其「库存龄」与本文档 §1.2 的「融资担保期限」是**两个独立维度**（递减按在库天数，逾期按合同到期日） |
| **《违约处置与法律清算设计》** | 环节⑩（违约处置与 OOT）的落地设计。四类触发源 + 违约通知 + 法律清算 + 人工台账处置。本文档的预警/工单在此汇聚为处置案件；`work_orders` 与 `risk_alerts` 为共用体系 |
| **ADR-009** | 外部接入安全边界（专线/VPN → DMZ → 网关 → 签名 → 审计 五层）。本文档 §2 的 `domain_events` 是**内部与外部共用的事件总线**——外部推送事件须经 DMZ inbox 汇入同一张表，**不得由外部方直写** |
| **ADR-008** | 逾期状态归属借据而非 VIN。**本决策推翻了本文档 §1.2 的初版设计**（初版把期限与逾期字段挂在 `vehicle_units` 上——把债务状态挂在资产实体上是错的）。§1.2 已按 ADR-008 重写：三层实体（借据 / 还款计划 / VIN 派生标记）、快逾期与正式逾期严格分离、盘点 job 禁止自行判断逾期 |
| **本节 §1.2 融资担保期限模型** | 期限是逾期判定与计息的地基；回款闭环解决的是"钱有没有回来"，期限模型解决的是"该还了没有"，两者叠加才构成完整的贷后时间轴 |
| 《外部集成接口文档》 | 数据接入层直接复用其五条架构约束；本文档补充事件模型与定时兜底清单 |
| 《角色与权限矩阵》 | 新增 3 个权限点，工单类型与岗位的对应关系需回填该文档 |
| 《数据库设计文档》 | 新增 5 张表（V11 迁移）需回填 |
| 《接口文档》 | 新增工单/预警/规则/事件接口需回填 |
| 《管理控制台说明》 | 新增贷后工作台页面需回填 |

## 0. 为什么需要先定源

仓库里对"读接口要不要权限点"存在**两条相反的口径**：

| 来源 | 原文 | 含义 |
|---|---|---|
| `docs/库存融资核心系统-角色与权限矩阵.md` §3 尾注 | 「**读接口不设权限点**：所有已登录用户可访问。风控岗要看全量台账、催收岗要看车辆档案，如果读也按角色卡，业务就没法协同。」 | 现状标准：登录即可读全部 |
| `docs/二手车库存垫资改造-10-权限与合规矩阵.md` §2/§3 | 列了 `DEALER_READ`/`VALUATION_READ`/`RECON_READ` 等 L 级读点，并给出角色 × 权限组矩阵；`○`＝仅本方数据 | 目标标准：读也分域、分角色、分数据范围 |

按仓库规矩（AGENTS §0 / 全局「先定义的标准优先」），**不能静默选一个**。本文把冲突、
可选方案与建议矩阵摊开，等业务签字后再动代码。

## 1. 现状实查（2026-11-24）

- 全仓控制器 GET 端点约 **44 个**（去重后）；其中 **36 个没有权限注解**，8 个带
  `@RequirePermission`（集中在 USED R2/R3 的读点）。
- `UserRole.READ_TIER` 目前只含 6 个 USED 读点（`VALUATION_READ`、`LTV_POLICY_READ`、
  `AUCTION_HOUSE_READ`、`AUCTION_LOT_READ`、`RELEASE_READ`、`RECON_READ`），
  由 `implicitReadPermissions()` 并给**所有角色**——即"读点存在，但等于全员可读"。
- 核心域（授信、车辆、垫款、借据、回款、担保台账、风控、处置、供应商、附件、作业状态）
  **没有读点**，全靠"无注解 + 登录即可"。
- `users` 表没有 `dealer_id`/`partner_code` 绑定，**没有任何行级数据范围模型**；
  即使加了读点，也无法阻止一个车商子账号读别家台账。

结论：现状的风险不是"少几个 `@RequirePermission`"，而是**功能权限与数据范围两层都缺**。

## 2. 方案取舍

| 方案 | 内容 | 评价 |
|---|---|---|
| A. 保持现状 | 读接口不设权限点，登录即可读全部 | 业务协同最顺，但跨车商/跨合作方数据暴露；作为**已书面接受的风险**可保留 |
| B. 功能权限矩阵 | 为读接口加域读点，按角色授予；数据范围仍为全部 | 防止"不该看这个域的人"看到，但不能防止同域内跨车商 |
| C. 数据范围隔离 | 增加 `ALL / OWN_DEALER / OWN_PARTNER` 范围，查询按归属过滤 | 真正解决跨车商泄露；需要 `users` 绑定与全量查询改造 |
| **B + C（建议）** | 先定读点与角色，再定数据范围 | 两层都补；工作量最大，但这是"读授权"的完整形态 |

> **如果业务选择 A**，本文转为「风险接受记录」，在 §8 Q-R1 写明接受人与范围；
> 不再改代码。**不要让"读接口不设权限点"与"我们以为已经按角色收紧了"同时存在。**

## 5. 数据范围模型（方案 C）

### 5.1 现状

- `users` 只有 `username/role/enabled/token_version`，没有经销商/合作方归属。
- 所有查询按主键/条件查，没有统一的"归属过滤"入口。
- 外部 partner 的 scope 在 D10 §8 有定义（按 `partner_code` 隔离），但 `external-api` 仍是骨架。

### 5.2 建议

新增（待签字，不在本草案实施）：

```sql
-- 用户数据范围绑定：一个内部员工可为 ALL；车商子账号/合作方为 OWN_*
CREATE TABLE user_data_scopes (
    username    VARCHAR(64) NOT NULL,
    scope_type  VARCHAR(16) NOT NULL,   -- ALL / OWN_DEALER / OWN_PARTNER
    scope_value VARCHAR(64),            -- dealer_id 或 partner_code；ALL 时为空
    granted_by  VARCHAR(64),
    granted_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (username, scope_type, scope_value)
);
```

- 查询层统一从 `AuthContext` 取 `DataScope`，在 Repository 的列表/详情 SQL 上追加
  `AND dealer_id = :scopeDealerId` / `AND partner_code = :scopePartnerCode`。
- **不改变**写路径的职责分离；数据范围只影响读。
- 需要明确：总部风控/催收/审计是 `ALL`；车商子账号是 `OWN_DEALER`；
  partner（WMS/拍卖场/保管方）是 `OWN_PARTNER`，且只应看到自己 `partner_code` 的对象。

## 9. 风险与反模式

- **假收紧**：只加读点但不做数据范围，跨车商仍可读；必须在报表/前端明确当前范围。
- **读点爆炸**：每个端点一个读点会让角色矩阵不可维护；按域粗分，端点映射到域。
- **与写点混淆**：读点不得用于任何写接口；写接口仍按现有 `@RequirePermission`。
- **绕过通道**：报表/导出/调试接口如果不在矩阵内，会成为新的读漏洞；新增端点必须同步登记。
- **READ_TIER 全员授予**：如果保留 `READ_TIER` 并把它并给所有角色，等于换名字的"全员可读"；
  签字后必须逐角色授予，或只保留给 `READONLY_USER`/`SYSTEM_ADMIN`。

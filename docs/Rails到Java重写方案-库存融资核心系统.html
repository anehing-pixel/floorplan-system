一、战略背景与三条铁律

动因已定：公司战略决定所有业务统一用 Java 实现，本 Rails 项目必须改为 Java。这不是技术选型讨论，而是执行策略讨论。

但"统一用 Java"绝不等于"把 Rails 代码翻译成 Java"。若带翻译心态，会把 Rails 该还的债（藏在 before_save 回调里的业务规则、靠 gem 撑着的审计、散落的 boolean 字段）原样搬进 Java，导致战略上迁了、架构上退步。

铁律 ① 等价重写，不趁机升级 —— 业务范围、对外行为、字段类型保持与 Rails 版一致；重写不是镀金机会。
铁律 ② 测试资产平移 —— 把 RSpec 里计息引擎的边界用例（提前还、部分还、利率中途变更、跨月、节假日）逐条翻成 JUnit。它们是"Java 版与 Rails 版算出来一致"的唯一硬证据。
铁律 ③ 数据原样不动 —— schema 照搬；金额 bigint → Java long（日元无小数，消灭浮点误差）；不趁机改字段类型或加字段。

二、团队画像与 AI 编程对策

5 人利用 AI 辅助编程（Copilot / Cursor / Claude Code 类），代码产出接近"准 8–10 人"，但质量保证不能外包给 AI。金融账务是边界条件密集、正确性优先的系统，AI 极易生成"看起来对、边界却错"的代码。

从 Rails schema 生成建表脚本		 领域不变量（额度占用、车辆单元状态机）

AI 编程的最大风险：放大"翻译式迁移"诱惑——AI 翻代码极快，团队会倾向于"先把所有文件翻完再说"，从而跳过领域萃取和测试基准，直接掉进"坏设计一起搬走 + 无验证锚点"的坑。

强制流程纪律

  • 先测后码：M1–M2 先把 RSpec 边界用例翻成 JUnit 并跑通，作为"等价基准"，之后才允许 AI 生成实现。
  • 领域核心人工 review：计息、额度、批处理代码 100% 人工 review + 强制测试覆盖，AI 仅出初稿。
  • 统一规范喂给 AI：维护一份 CLAUDE.md / 编码规范，明确分层、金额用 long、事务边界、不变量，约束 AI 产出。

三、目标架构（模块化单体）

5 人单组开发，物理拆分微服务无任何收益。保持"逻辑拆、物理不拆"，用 Maven / Gradle 多模块表达边界——第一版单进程部署，模块边界即未来物理拆的接缝。

inventory-finance/      (Maven / Gradle 多模块)
├── domain/         聚合根·不变量·状态机·计息规则（不依赖 Spring）
├── application/    用例编排 + 事务边界（@Transactional 画在这）
├── infrastructure/ JPA/MyBatis 映射·append-only 事件表·外部适配
├── web/          接口层，只做校验与呈现
└── integration/   厂家/支付/登记对接（隔离外部变更）

ORM 选型：简单实体用 Spring Data JPA 无妨；计息、对账、复杂报表建议 MyBatis / JDBC Template 手写 SQL（精确可控，避开 JPA 懒加载与 N+1 坑）。

五、数据策略

  • 共享数据库：迁移期 Rails 与 Java 共用同一 PostgreSQL，零数据迁移风险。
  • Schema 原样：表结构、字段、索引照搬；金额列 bigint 在 Java 端用 long 映射，不改为 BigDecimal。
  • 写竞争隔离：迁移期按用例划分"当前由谁写"，避免两边同时写同一张表；用网关路由保证单用例单写方。

情形 A：已上线（推荐绞杀者）情形 B：未上线（一次性重写）
总体策略绞杀者模式：Java 与 Rails 并存，按用例切流，随时回滚一次性重写为 Java，仍保留双跑比对关卡
运行时Rails 持续服务，期间需并行维护两套无并行负担，纯开发
1 年净工时需扣除"维持 Rails + 双跑"并行成本全部可用于 Java 开发
风险低（任何时刻可用、可回滚）中（写完直接上，靠双跑兜底）

无论哪种，第一步都是双跑比对：同一批历史数据，Rails 与 Java 并行计算，逐笔核对利息、本金、余额，全部一致才算过关。

八、测试平移策略（RSpec → JUnit）

  • 优先级最高：计息引擎边界用例——提前还款、部分还款、利率中途调整、跨月、节假日、贴息轧差。这是"等价"的核心证据。
  • 额度并发占用（模拟多笔同时提交不超额）。
  • 车辆单元状态机流转（非法流转被拒）。
  • 批处理幂等（重复执行不产生重复计息/还款）。
  • 双跑比对测试：给定历史数据，断言 Java 输出与 Rails 输出逐笔一致。

十一、待确认

  1. 系统当前是否已上线？（决定绞杀者 vs 一次性重写，影响排期与并行成本）
  2. 真实业务参数（结算窗口、库龄递减天数与比例、垫款比例、利率结构、厂家贴息、违约阈值）—— 影响计息引擎与风控模块的具体实现，须从客户处取得。
  3. 新车未上牌时的担保落地路径（让与担保合同 / 动产让渡登记 / 厂家回购 / 经销商信用）—— 决定"担保登记"模块是否要做、怎么做。
  4. 日本本地接口现实（厂家系统、车辆登记、经销商库存、支付通道，哪些有接口、哪些人工）—— 决定自动化程度与集成层工作量。

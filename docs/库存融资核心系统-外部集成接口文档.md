## 1. 核心认知：集成是双向的

| 方向 | 含义 | 设计要点 |
|---|---|---|
| **Outbound**（本系统调用对方） | 查发票、发起付款、拉入金明细、查登记/征信 | 重试、幂等、超时、熔断、**可人工重触发** |
| **Inbound**（对方调用本系统） | 到货通知、付款结果回调、入金通知、登记变更、售出事件 | 入口分离、鉴权、限流、防腐层、审计留痕 |

> 此前文档把集成写成单向（只调外部），本文档补上 Inbound 与双向的设计约束。

## 2. 架构约束（五条）

### 2.1 入口分离

```
web（内部，SSO）          external-api（外部）
  ├ 内部运营/风控/财务       ├ 厂家系统
  └ 鉴权：SSO + 角色         ├ 银行/支付通道
                            ├ 登记/征信（回调或人工）
                            └ 鉴权：双向证书 / 签名 / IP 白名单 / API Key
```

- 两个入口**鉴权模型完全不同**，不得混用
- 外部接口**暴露字段最小化**（不暴露内部 ID、风险等级等敏感字段）
- 外部调用同样写入 `audit_events`，留痕不可少

> **📄 落地设计见《库存融资核心系统-ADR009外部接入安全边界设计.md》**
>
> 本节是**代码层的入口分离**约束；ADR-009 给出**部署层的纵深防御**：
> **专线/VPN → DMZ 前置服务 → API 网关 → 签名鉴权 → 审计日志**五层，
> 以及核心接口不裸放公网的网络分区方案。
>
> **2026-10-26 核查现状**：
> - ❌ `external-api` 入口**从未实现**（全库零 `external` 相关代码）
> - ❌ 无网关 / DMZ / 专线 / VPN / 限流 / IP 白名单任何基础设施痕迹
> - 🟡 唯一的外部鉴权是银行回调 `PaymentWebhookVerifier`（HMAC-SHA256 + ±300s 时间窗）
>   ——但**所有渠道共用一个全局密钥**，且**无 nonce 去重**（窗口内重放仍可成功）
> - ⚠️ CORS 为 `allowedOriginPatterns("*")` 全通配，生产必须收紧
> - ✅ 请求日志（`RequestLoggingFilter`，脱敏 + traceId）与业务审计（`audit_events`）已具备
> - ❌ 外部调用记录表 `integration_calls` 不存在
>
> **ADR-009 对本节的四点强化**：
> ① 签名原文纳入 **METHOD + PATH + body 摘要**（现有只签 `advanceNo + timestamp + ref`，body 未覆盖）
> ② 新增 **nonce 去重表**（真正防重放）
> ③ 密钥**按 partner 分级 + 版本轮换**（替代全局单密钥）
> ④ 外部入口**独立进程独立端口**——在同一应用里加 `/api/external/**` 路径，网络隔离形同虚设

### 2.2 防腐层（ACL）是强制的

外部数据模型（厂家发票格式、银行入金格式）**绝不能直接落进领域对象**：

```
外部 DTO → [ACL 转换] → 内部命令（Command） → application → domain
```

理由：外部系统字段变更不应污染核心模型；这也是"隔离外部变更"原则的落地方式。

### 2.3 Outbound 韧性 + 人工重触发

- 标配：超时、重试（指数退避）、幂等键、熔断
- **关键**：对方接口挂了要能**人工重触发**（运维界面点"重新推送"），不能让业务停摆
- 所有 Outbound 调用落 `integration_calls` 记录（请求/响应/耗时/结果），便于排查与重放

### 2.4 对账是兜底，不是补充

跨系统**没有分布式事务**。以下必须逐笔对账：

| 对账项 | 本系统侧 | 对方侧 |
|---|---|---|
| 垫款付款 | `advances`（已付款） | 银行汇出明细 |
| 车商还款 | `repayments`（已核销） | 银行入金明细（含虚拟账号） |
| 厂家贴息 | 贴息应收 | 厂家结算单 |

### 2.5 人工路径是一等公民

**不是临时过渡方案，而是日本现实的长期形态**。设计上同一业务能力必须同时支持"自动触发"与"人工触发"：

```
同一业务能力（如"获取发票"）
  ├ 自动：REST 拉取 / SFTP 收文件 / 对方回调
  └ 人工：运维界面上传 CSV 或手工录入 → 审核 → 进入同一内部流程
```

两条路径最终汇入**同一个内部命令**，下游无感知。

## 3. 外部方能力矩阵（⚠️【预设】待核实）

| 外部方 | Outbound（我调对方） | Inbound（对方调我） | 预设协议 | 现实风险 |
|---|---|---|---|---|
| **厂家系统** | 查车辆/发票、提交垫款申请、拉贴息结算 | 到货通知、发票推送、贴息结果回调 | ⚠️【预设】电子数据交换（EDI）/ CSV 文件交换为主，REST 少见 | 可能无 API，仅文件 |
| **银行 / 支付通道** | 发起付款指令、查汇款状态、拉入金明细 | 付款结果回调、入金通知（虚拟账号） | ⚠️【预设】银行间结算数据文件（汇出/入金）、网银导出，或专用客户端 | API 化程度中等；入金消込可能半人工 |
| **车辆登记** | 查登记状态（若有） | 登记完成/变更通知 | ⚠️【预设】**对民间基本无开放接口**，实务靠登记事项证明书等书面文件或委托代办 | **极可能只能人工** |
| **征信机构** | 查企业/经销商信用记录 | —（一般无回调） | ⚠️【预设】专用线路/需审查的接口，接入周期长 | 接入审批耗时 |
| **零售/销售系统** | 拉零售成交数据 | 推送售出（sold）事件 | 若同属公司内部：REST / 消息；若外部：同厂家 | 决定 sold 是否自动 |

## 4. 接口设计（按外部方）

### 4.1 厂家系统

**Outbound**

| 能力 | 预设调用 | 幂等/重试 |
|---|---|---|
| 查询发票/车辆 | 按 VIN 或批次查询 | 幂等（查询） |
| 提交垫款申请 | 提交 `{vin, amount, dealer}` | 幂等键必填，可重推 |
| 拉贴息结算数据 | 按期间拉取 | 按期间幂等 |

**Inbound（本系统提供）**

| 接口 | 方法 | 说明 |
|---|---|---|
| `/external/manufacturer/arrival` | POST | 到货通知（车辆到店） |
| `/external/manufacturer/invoice` | POST | 发票推送 |
| `/external/manufacturer/subsidy` | POST | 厂家贴息结果回调 |

**文件交换形态（若无 API）**：约定 SFTP 目录 + CSV 格式 + 命名规则 + 对账文件；系统提供**文件上传与解析界面**，解析失败逐行报错可修正后重传。

#### 4.1.1 采购订单导入（两条通道，ADR-007 决策四）

上游不只是"厂家"——实际形态是**制造商销售公司 / 区域总代理 / 批发公司 / 拍卖行 / 中古批发商**多层渠道，
且各方的系统能力差异极大。**采购订单导入确定采用两条通道**：

| 导入方式 | 数据来源 | 对接方 | 系统内形态 |
|---|---|---|---|
| **API / 系统直连** | 主机厂销售公司、区域总代理、拍卖平台、经销商 DMS/ERP | 优先谈厂商销售公司 → 总代理 → 拍卖平台 → 经销商 DMS | 走 `/external/purchase-orders`（签名校验 → 限流 → ACL → 字段校验 → 落主单），**可豁免人工确认** |
| **Excel/CSV 批量导入** | 经销商提交的车辆采购清单 | 经销商（含长尾中小经销商） | 走 `/api/purchase-orders/import`（固定模板 → 行级报错 → 预览确认 → 落主单），**必须人工确认** |

**两条通道长期并存，不是成熟度替代关系**——它们服务的是**能力不同的对手方**：
API 直连面向有系统、有对接意愿的主机厂/总代理/拍卖平台/DMS；
Excel 面向只有表格的中小经销商，且**已接 API 的对手方的零星补录、临时采购、异常单也永远走 Excel**。

**统一产出「采购订单主单」**（`purchase_orders`），下游（车辆台账、垫款、放款）无感知——
与本文档 §5 的 `IntegrationAdapter` 三路适配体例同源，本域实际启用 `api` 与 `file` 两条：

```java
public interface PurchaseOrderIngest {
    ParseResult parse(InputBlob blob);   // Api / Excel
}
// ingest.channel = api | excel —— 配置项决定启用哪些，下游只看 PurchaseOrder 主单
```

**清单关键字段（两条通道共用同一口径）**：

| 字段组 | 字段 |
|---|---|
| 标识 | 采购订单号（幂等锚点） |
| 车辆 | VIN / 车架号、车型、年款、颜色 |
| 上游 | 供应商类型（制造商销售公司 / 总代理 / 拍卖行 / 批发商 / 中古批发商 / 经销商自身） |
| 金额 | 采购金额 |
| 收款 | 收款账户（**只传引用码 `payeeAccountRef`，不传明文账号**） |
| 状态 | 车辆状态（在途 / 在库 / 已质押 / 已解押） |
| 凭证 | 合同/発注書/請求書 的原件附件 + 单据编号 |

**三条不可让步的约束**：

1. **账户不随文件明文传输**：导入模板与 API 契约中收款账户只填 `account_ref`（业务引用码），
   系统按引用查账户主数据。**两条通道都不接受明文账号**——Excel 是人工可编辑文件，
   放明文账号等于把导入通道变成"塞入任意账户"的后门。
2. **原始文件必须留存**：合同/発注書/請求書 原件随主单留存，**不能只存解析结果**——否则无法自证。
   文件本体存 **Amazon S3**（`/external/**` 侧由上游给 `objectKey`，或我方经预签名 URL 上传）；
   API 通道上游不提供原件时，留存单据号 + 上游可追溯凭据并标注"无附件"。
3. **幂等双锚点**：`order_no` 唯一防"同一张单重复导入"；**VIN 幂等**防"两个不同订单号报同一台车"。

**落库前的人工确认按通道分级**：API 直连可豁免（数据源可信 + 有契约保证，可配置强制复核）；
Excel 必须走 `preview` → 人工核对 → `commit`。

### 4.2 银行 / 支付通道

**Outbound**

| 能力 | 预设调用 | 说明 |
|---|---|---|
| 发起付款指令 | 生成汇出数据文件 / 调 API | 生成后需**人工复核**再送出（内控） |
| 查汇款状态 | 拉状态或查回执文件 | |
| 拉入金明细 | 拉入金数据文件 / 网银导出 | 用于还款核销与对账 |

**Inbound（本系统提供）**

| 接口 | 方法 | 说明 |
|---|---|---|
| `/external/payment/result` | POST | 付款结果回调（成功/失败/退票） |
| `/external/payment/incoming` | POST | 入金通知（含虚拟账号→车商/车辆映射） |

> **虚拟账号入金**是日本实务常见做法：为每个车商/每台车分配专用收款账号，入金即自动匹配还款。**若客户采用此方案，需设计"虚拟账号 ↔ 车商/车辆"映射表**（⚠️【预设】需确认是否采用）。

### 4.3 车辆登记与担保设定

**预设结论：极可能无接口 → 走人工路径**

- **担保设定**（对应流程环节 ④⑧）：日本渠道担保以**所有权保留 / 让与担保 / 动产·债权让渡登记**为主，新车未上牌时可能仅靠让与担保合同 + 厂家回购承诺。提供**担保状态录入界面**（字段：登记编号、所有者名义、设定日、解除日、文书状态），支持上传登记事项证明书/合同扫描件留证；录入后进入审核流（发起/执行分离）。
- **车辆登记查询**：对民间基本无开放接口，实务靠登记事项证明书等书面文件或委托代办；提供登记状态录入界面而非实时查询。
- 若客户确认有可用接口，再增 Outbound 查询与 Inbound 变更通知。

> **物理监管（重要）**：日本新车渠道**不集成**钥匙扣押/GPS/封签类监控（非本地实务）。本系统的"监管"= **实地盘点**（`POST /api/inventory/audit` 逐台扫 VIN + 拍照），无对应外部硬件接口。

### 4.4 征信机构

- Outbound 查询（经销商/法人信用），结果入 `dealers.risk_grade` 参考
- 接入需审查与专用线路，**周期长，应尽早启动**（排期风险点）
- 查询结果须留痕（查询时间、机构、结果摘要）

### 4.5 零售 / 销售系统

- 决定 `sold` 是**自动**还是**人工**
- 若自动：Inbound `/external/retail/sold`（推送售出）或 Outbound 定时拉成交数据
- 若人工：运营在内部界面标记（当前默认路径）
- **此项直接影响脱信销售（OOT）识别的及时性**——自动推送越及时，OOT 越早发现

## 5. 统一适配框架（实现建议）

```java
// 每个外部方一个 Adapter，内部统一接口
public interface IntegrationAdapter {
    List<InvoiceDTO> fetchInvoices(Period period);
    SubmitResult submitAdvance(AdvanceCommand cmd);
    List<IncomingDTO> fetchIncoming(Period period);
}

// 三种实现，按对方实际能力选择
ApiManufacturerAdapter    // REST 调用
FileManufacturerAdapter   // CSV/SFTP 解析（自动）
ManualManufacturerAdapter // 人工录入（兜底）
```

- 三条路径产出**同一内部 DTO**，下游无感知
- 配置项决定用哪个实现：`integration.manufacturer.mode = api | file | manual`
- **人工模式不是"没做完"，而是正式支持的一种模式**

**Inbound 统一入口**：`external-api` 模块 → 签名校验 → 限流 → ACL 转换 → 内部命令 → 落 `integration_calls` + `audit_events`

## 7. 排期风险提示

集成层工作量**极不确定**：

- 若全部有 API：工作量可控
- 若部分为文件交换：需开发解析、校验、重传、人工修正界面
- 若大部分人工：需开发完整的录入 + 审核 + 留痕体系

**工期估算应按"最坏情况（全人工）"做**。主文档排期中集成排在 M12–M14（3 个月），存在低估风险；建议预留缓冲，并在调研清单回收后重新评估。

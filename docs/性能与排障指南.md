## 1. 灰度发布与回滚 Runbook（T4-6）

### 1.1 适用范围与前置条件

适用对象：Spring Boot 微服务（gateway / auth / bank / credit / risk / loan / collateral-reg / release / recon / web-core），服务发现为 Nacos，网关统一入口 `:18080`。

**发布前必须全部满足**：

- [ ] 变更已通过 CI（`mvn -q -B package`，含全模块单测），Code Review 通过。
- [ ] 镜像已构建，tag 唯一可追溯到 commit sha；**禁止使用 `latest`**。
- [ ] 旧版本镜像 tag 仍存在且未被清理（回滚前提）。
- [ ] 数据库迁移向后兼容：新代码兼容旧 schema，旧代码兼容新 schema（expand-contract）；
      破坏性变更必须有单独方案与回退 SQL，不得夹带在普通发布中。
- [ ] 健康检查可用：`/actuator/health`（若未引入 actuator，需 Wave2 补齐，本文按此约定写）。
- [ ] Nacos 注册列表、接口 5xx/P99、GC 日志、DB 连接池、队列指标均可查。
- [ ] 回滚脚本已在预发演练过，值班人到位。

### 1.2 灰度步骤（按实例比例推进）

| 阶段 | 放量比例 | 最短观察时长 | 通过标准 | 立即中止条件 |
|---|---|---|---|---|
| 0 准备 | 0 | — | 前置条件全绿、记录旧 tag | 任一前置项不满足 |
| 1 金丝雀 | 1 台 / 约 5% | 10~15 分钟 | 5xx = 0，P99 ≤ SLA，业务冒烟通过 | 5xx > 1%，或 P99 连续 5 分钟超 SLA |
| 2 小流量 | 25% | 20 分钟 | 同阶段 1，且无异常日志增长 | 同上，或错误日志量环比翻倍 |
| 3 半量 | 50% | 30 分钟 | 同上，DB 连接数/队列无异常 | 同上，或 DB 连接池打满、队列持续积压 |
| 4 全量 | 100% | 持续观察 2 小时 | 指标回到/优于基线 | 任一核心链路不可用 |

**执行步骤（每一阶段重复）**：

```bash
# 1) 记录当前版本（回滚基线）
kubectl get deployment {{SERVICE}} -n {{NS}} \
  -o jsonpath='{.spec.template.spec.containers[0].image}'

# 2) 更新镜像，触发滚动发布（K8s 默认 maxSurge=25%/maxUnavailable=25%）
kubectl set image deployment/{{SERVICE}} {{CONTAINER}} \
  {{REGISTRY}}/{{SERVICE}}:{{NEW_TAG}} -n {{NS}}

# 3) 等待 rollout 完成
kubectl rollout status deployment/{{SERVICE}} -n {{NS}} --timeout=5m

# 4) 确认 Nacos 实例数与健康状态
curl -fsS "http://{{NACOS_ADDR}}/nacos/v1/ns/instance/list?serviceName={{SERVICE}}"

# 5) 健康检查
curl -fsS "http://{{SERVICE}}.{{NS}}.svc.cluster.local:{{PORT}}/actuator/health"
```

**每阶段必须观测的指标**（任一项恶化即停止放量）：

- 网关与各服务访问日志：HTTP 5xx 率、业务错误码分布、请求量是否突降。
- APM / 日志：`P95/P99` 延迟、接口超时次数（重点看灰度实例 vs 旧实例对比）。
- JVM：Young GC 频率、Full GC 次数、堆使用（参数见 `docs/工程化配置模板.md` 第 1 节）。
- DB：连接池活跃数、慢 SQL 数量、锁等待（见 `docs/工程化配置模板.md` 第 2 节）。
- 中间件：Nacos 实例上下线、Redis 连通性、OutboxPublisher 发布延迟与积压。
- 业务核对：登录、查询、放款、还款、对账等关键链路冒烟结果；交易笔数无异常波动。

> **放量纪律**：一次只放一个服务；禁止同时发布多个服务后再观察。每级观察时长不满足不得进入下一级。

### 1.3 一键回滚

**Kubernetes（推荐）**：

```bash
# 回滚到上一 revision
kubectl rollout undo deployment/{{SERVICE}} -n {{NS}}
kubectl rollout status deployment/{{SERVICE}} -n {{NS}} --timeout=5m

# 或：明确指定旧 tag（更可控，推荐用于跨多版本回滚）
kubectl set image deployment/{{SERVICE}} {{CONTAINER}} \
  {{REGISTRY}}/{{SERVICE}}:{{OLD_TAG}} -n {{NS}}

# 回滚后验证
kubectl get pods -n {{NS}} -l app={{SERVICE}}
kubectl get deployment {{SERVICE}} -n {{NS}} \
  -o jsonpath='{.spec.template.spec.containers[0].image}'
curl -fsS "http://{{SERVICE}}.{{NS}}.svc.cluster.local:{{PORT}}/actuator/health"
```

**Docker Compose（本地/单机环境）**：

```bash
# 把 compose 文件中的镜像 tag 改回 {{OLD_TAG}} 后重建
sed -i "s|{{NEW_TAG}}|{{OLD_TAG}}|g" {{COMPOSE_FILE}}
docker compose -f {{COMPOSE_FILE}} up -d {{SERVICE}}
docker compose -f {{COMPOSE_FILE}} ps {{SERVICE}}
```

**一键回滚脚本模板**（保存为 `scripts/rollback.sh`，按环境填充）：

```bash
#!/usr/bin/env bash
set -euo pipefail
SERVICE="{{SERVICE}}"
NS="{{NS}}"
OLD_TAG="{{OLD_TAG}}"
REGISTRY="{{REGISTRY}}"
CONTAINER="{{CONTAINER}}"
PORT="{{PORT}}"

echo "[rollback] 当前镜像："
kubectl get deployment "$SERVICE" -n "$NS" \
  -o jsonpath='{.spec.template.spec.containers[0].image}'; echo

kubectl set image deployment/"$SERVICE" "$CONTAINER" \
  "$REGISTRY/$SERVICE:$OLD_TAG" -n "$NS"
kubectl rollout status deployment/"$SERVICE" -n "$NS" --timeout=5m

echo "[rollback] 健康检查："
curl -fsS "http://$SERVICE.$NS.svc.cluster.local:$PORT/actuator/health"
echo "[rollback] 完成，请确认 5xx/P99 回落至基线并核对业务数据"
```

**数据库回滚原则（务必单独确认）**：

- 应用回滚 ≠ 数据库回滚。迁移脚本默认**不自动回滚**。
- 若新版本写入了旧代码不认识的数据（新增非空列、字段语义变更），先评估数据兼容性，
  再决定是否执行预置的回退 SQL（仅删除新增列/索引，不删业务数据）。
- 回退 SQL 必须 DBA 审批、先在备份上验证；涉及 V21 outbox 表与 `OutboxPublisher` 的变更必须配套回滚，
  禁止只回滚应用或只回滚表结构。
- 出现数据不一致时按第 2 节灾备流程从备份恢复，优先保证账务正确性。

> **回滚时限**：灰度窗口内一旦触发中止条件，**5 分钟内执行回滚**，不在故障现场做调试或“再观察一会儿”。

### 1.4 演练检查表

**发布前**：

- [ ] 本服务变更单、审批、CI 结果齐备
- [ ] 镜像 tag 唯一且可追溯 commit；旧 tag 可用
- [ ] 数据库迁移兼容性确认；回退 SQL 备好并验证
- [ ] Nacos / 配置中心变更 diff 已核对
- [ ] 监控大盘、告警阈值确认；值班人与回滚执行人明确

**灰度中**：

- [ ] 关键业务链路冒烟通过（登录/查询/放款/还款/对账）

## 2. 灾备与备份恢复 Runbook（T4-7）

### 2.1 备份策略

**备份对象清单**：

| 对象 | 内容 | 备份方式 | 频率 | 保留 |
|---|---|---|---|---|
| MySQL 业务库 | 借据、垫款、还款、流水、V21 outbox 表等 | 全量 `mysqldump` + binlog 增量 | 全量每日，binlog 实时/每小时归档 | 全量：日备 7 天、周备 4 周、月备 3 月；binlog ≥ 7 天 |
| Nacos 配置 | 各服务 `application.yml`、dataId 配置 | 配置导出 | 每次变更后 + 每日 | 30 天 |
| 对象存储/附件 | 合同、单据、图片 | 版本控制 + 跨区复制 | 实时 | 按合规要求 |
| 代码与镜像 | commit、构建产物、镜像 tag | Git tag + 镜像仓库 | 每次发布 | 长期（至少覆盖回滚窗口） |
| 日志 | 业务日志、GC 日志 | 日志采集归档 | 实时 | 30~90 天 |

**备份执行命令模板**（在跳板机/备份机执行）：

```bash
# 1) MySQL 全量逻辑备份（InnoDB 一致性快照，--single-transaction 不锁表）
mysqldump -h{{DB_HOST}} -P{{DB_PORT}} -u{{DB_USER}} -p \
  --single-transaction --routines --triggers --events --hex-blob \
  --databases {{DB_NAME}} \
  | gzip > {{BACKUP_DIR}}/mysql-full-{{YYYYMMDD}}.sql.gz

# 2) 备份完整性校验（每日任务必须做）
gzip -t {{BACKUP_DIR}}/mysql-full-{{YYYYMMDD}}.sql.gz && echo "备份文件完整"

# 3) binlog 增量归档（需提前开启 log-bin=ROW）
mysqlbinlog --read-from-remote-server --host={{DB_HOST}} --user={{DB_USER}} \
  --password --raw --result-file={{BINLOG_DIR}}/ {{BINLOG_FILES}}

# 4) Nacos 配置导出
curl -fsS "http://{{NACOS_ADDR}}/nacos/v1/cs/configs?dataId={{DATA_ID}}&group={{GROUP}}&export=true" \
  -o {{BACKUP_DIR}}/nacos-config-{{YYYYMMDD}}.zip
```

**备份原则**：

- 遵守 **3-2-1**：至少 3 份副本、2 种不同介质、1 份异地（跨可用区/跨地域）。
- 备份文件必须校验完整性（`gzip -t`），并定期做恢复演练——**没演练过的备份不算备份**。
- 备份机与生产数据库网络隔离、最小权限，备份账号只读。
- 备份任务要有监控与失败告警；连续失败两次必须人工介入。

**RPO / RTO 目标（建议值，需业务方确认后固化）**：

| 数据/系统等级 | 示例 | RPO（最大数据丢失窗口） | RTO（最大恢复时长） |
|---|---|---|---|
| 核心账务 | 借据、垫款、还款、银行流水、outbox | ≤ 5 分钟 | ≤ 30 分钟 |
| 重要业务 | 经销商/额度、风控预警、对账结果 | ≤ 1 小时 | ≤ 2 小时 |
| 辅助数据 | 配置、字典、日志、附件 | ≤ 24 小时 | ≤ 4 小时 |

### 2.2 恢复步骤

**通用原则**：

1. 恢复前先对当前状态做一次快照（即使数据疑似损坏），避免二次破坏。
2. **绝不在生产原库上直接演练恢复**；先在隔离环境验证。
3. 恢复期间发布公告并停止写入（服务降级/只读），避免新旧数据交叉。
4. 账务数据恢复后必须做一致性核对（笔数、金额合计、状态、outbox 未发布事件）。

**场景 A：误删/误改数据 → 时间点恢复（PITR）**

```bash
# 1) 立即停写入，归档当前 binlog（保留故障现场）
FLUSH LOGS;  # 在 MySQL 执行，切换 binlog

# 2) 用最近一份全量备份恢复到临时实例
gunzip -c {{BACKUP_DIR}}/mysql-full-{{YYYYMMDD}}.sql.gz \
  | mysql -h{{TMP_DB_HOST}} -P{{TMP_DB_PORT}} -u{{DB_USER}} -p

# 3) 用 binlog 前滚到故障发生前的时间点
mysqlbinlog --stop-datetime="{{YYYY-MM-DD HH:MM:SS}}" {{BINLOG_FILES}} \
  | mysql -h{{TMP_DB_HOST}} -u{{DB_USER}} -p

# 4) 在临时实例核对数据 → 导出受影响表 → 回写生产（或切换流量到临时实例）
mysqldump -h{{TMP_DB_HOST}} -u{{DB_USER}} -p \
  --where="{{WHERE_CLAUSE}}" {{DB_NAME}} {{TABLE}} > {{PATCH_FILE}}.sql
```

核对 SQL：

```sql
SELECT COUNT(*), SUM({{AMOUNT_COL}}) FROM {{TABLE}} WHERE {{CONDITION}};
CHECKSUM TABLE {{TABLE}};
-- 重点核对：借据状态分布、当日交易笔数与金额、outbox 未发布事件数
SELECT status, COUNT(*) FROM {{LOAN_TABLE}} GROUP BY status;
SELECT COUNT(*) FROM outbox WHERE published = 0;
```

**场景 B：整库/机房故障 → 异地备份重建**

1. 在异地环境创建同版本 MySQL 实例（参数与生产一致，含 `binlog_format=ROW`）。
2. 导入最近全量备份 + binlog 前滚（同场景 A 第 2、3 步）。
3. 导入 Nacos 配置备份，确认各服务配置指向新 DB 地址（**配置变更按第 1 节灰度流程执行**）。
4. 启动服务，按第 1 节灰度顺序逐个放量；确认健康后切流。
5. 业务方核对账务数据，确认无差异后解除降级公告。

**场景 C：配置丢失（Nacos）**

```bash
# 导入配置备份后在 Nacos 控制台核对 dataId / group，并触发各服务刷新
curl -X POST "http://{{NACOS_ADDR}}/nacos/v1/cs/configs" \
  -d "dataId={{DATA_ID}}&group={{GROUP}}&content={{URL_ENCODED_CONTENT}}"
```

### 2.3 RTO / RPO 验证方法

**每季度一次全链路恢复演练**，在隔离环境进行，不影响生产：

1. 随机抽取一份近期备份集（不提前通知备份维护人，检验真实可用性）。
2. 按 2.2 场景 A 在隔离实例执行恢复与 PITR。
3. 用 2.2 的核对 SQL 对比：记录数、金额合计、`CHECKSUM TABLE`、关键业务表状态分布。
4. 记录各步骤耗时与总耗时。
5. 计算：
   - **实测 RTO** = 从故障宣布到服务恢复可用（含恢复+验证+切流）的总时长。
   - **实测 RPO** = 故障时刻与最后一份可恢复数据时刻之间的时间差。
6. 验收：实测 RTO ≤ 目标 RTO 且实测 RPO ≤ 目标 RPO；不达标则提高备份频率或优化恢复流程，并出具改进项。

**演练报告模板**：

```markdown
# 灾备恢复演练报告 - {{YYYY-MM-DD}}

- 演练场景：{{误删恢复 / 整库重建 / 配置丢失}}
- 使用备份集：{{文件名与日期}}　参与人：{{名单}}
- 步骤耗时：全量恢复 {{T1}}min / binlog 前滚 {{T2}}min / 核对 {{T3}}min / 切流 {{T4}}min
- 数据核对结果：记录数 {{一致/不一致}}，金额合计 {{一致/不一致}}，CHECKSUM {{通过/失败}}
- 实测 RTO：{{X}}min（目标 {{Y}}min）　实测 RPO：{{A}}min（目标 {{B}}min）
- 发现问题：{{清单}}　改进项与责任人：{{清单}}
```

### 2.4 恢复后验证清单

- [ ] 应用健康（`actuator/health`），Nacos 注册实例数恢复正常。
- [ ] 关键表记录数、金额合计、状态分布与故障前快照一致。
- [ ] OutboxPublisher 恢复正常，未发布事件无积压、无重复投递。
- [ ] 定时任务未重复执行（检查幂等键/执行记录）。
- [ ] 对账任务跑通，无差异；核心链路冒烟通过。
- [ ] 业务方确认数据正确，解除降级公告。
- [ ] 演练或真实恢复的时间线、耗时、问题已归档

## 3. 常见故障排障路径

### 3.0 通用流程与信息收集

任何故障先按下面四步走，避免“边看边猜”：

1. **定界**：确认影响范围（哪个服务/接口/用户群）、起始时间、是否与最近发布/配置变更/流量突增重合。
2. **分层定位**：网关（`:18080`） → 服务实例 → JVM（GC/线程） → 依赖（DB / Redis / Nacos / 下游 Feign） → 主机/网络。
3. **验证假设**：每次只改一个变量，用日志/监控确认；无法确认的假设不要当成结论。
4. **恢复优先**：先止损（回滚/扩容/限流/降级），再查根因；恢复后补复盘。

**现场信息收集清单（故障单里填写）**：

| 项目 | 内容 |
|---|---|
| 时间线 | 故障开始/发现/止损/恢复时间，关键操作时间点 |
| 现象 | 报错原文、HTTP 状态码、影响接口、失败率 |
| 最近变更 | 发布 tag、配置 diff、DB 变更、流量变化 |
| 证据 | 日志片段（带 traceId）、监控截图、`kubectl describe/logs` 输出 |
| 环境 | 集群/命名空间、服务版本、实例数、数据量级 |

### 3.1 服务起不来

**先识别启动失败的类型**：

```bash
# 容器状态与上次崩溃日志
kubectl get pod -n {{NS}} -l app={{SERVICE}}
kubectl describe pod {{POD}} -n {{NS}}
kubectl logs {{POD}} -n {{NS}} --previous | tail -200

# 本地/单机模式
docker compose logs --tail=200 {{SERVICE}}
```

**按退出码/日志关键字定位**：

| 线索 | 可能原因 | 处置 |
|---|---|---|
| 退出码 `137` / `OOMKilled` | 容器内存不足或堆外内存未计入 | 按 `docs/工程化配置模板.md` 1.3 节重算内存，降 Xmx 或升容器限额 |
| `APPLICATION FAILED TO START` | Spring 上下文启动失败 | 看紧随其后的 `Description`/`Action` 段落，按提示修 |
| `BeanCreationException` / `UnsatisfiedDependencyException` | Bean 缺失或循环依赖 | 核对 component scan、条件注解、Nacos 配置是否生效 |
| `Web server failed to start. Port ... was already in use` | 端口冲突 | Windows: `netstat -ano \| findstr :{{PORT}}`；Linux: `ss -lntp \| grep {{PORT}}` |
| `Failed to configure a DataSource` / `Access denied for user` | DB 连接配置错误或库不可达 | 见 3.4 节 |
| `Unable to pull config` / 占位符 `${...}` 未替换 | Nacos 不可达或环境变量缺失 | 核对 `NACOS_ADDR`、`SPRING_PROFILES_ACTIVE`、必需环境变量 |
| `Flyway ... failed` / `Validate failed` | 迁移脚本失败或校验和不匹配 | 见 3.5 节 |
| 进程存活但健康检查失败 / Nacos 无实例 | 启动“成功”但注册失败 | 注意 gateway 的 `fail-fast: false` 会掩盖依赖不可达，核查 Nacos 实例列表 |

**通用检查顺序**：

1. 确认 JDK 版本 = 17（`java -version`）。
2. 确认 `SPRING_PROFILES_ACTIVE` 与环境变量（DB/Nacos/Redis 地址）正确，占位符均已替换。
3. 确认 Nacos 可达：`curl -fsS http://{{NACOS_ADDR}}/nacos/v1/console/health/readiness`。
4. 确认 DB/Redis 可达（见 3.4）。
5. 确认端口未被占用、磁盘/文件句柄未耗尽（`df -h`、`ulimit -n`）。
6. 仍无法定位时，用第 1 节回滚到上一版本，先恢复服务。

### 3.2 Feign 调用 401 / 403

先区分 **401（未认证：token 缺失/无效/过期）** 与 **403（已认证但无权限）**，排查路径不同。

```
401?
├─ 网关直接返回 401 → 检查登录态、请求头是否被网关注入/透传
├─ 下游服务返回 401 → 检查 Feign 是否透传 Authorization
└─ 403 → 检查角色/权限配置（docs/库存融资核心系统-角色与权限矩阵.md）
```

**排查清单**：

1. **调用链定位**：用 traceId 串起网关 → 调用方 → 被调方日志，确认 401 是谁返回的（网关还是下游）。
2. **Token 透传**：检查 Feign 的 `RequestInterceptor` 是否从 `RequestContextHolder` 取出 `Authorization` 并写入下游请求；异步线程/`@Async` 场景需手工传递上下文。
3. **网关透传**：确认自定义 Gateway Filter 没有丢弃 `Authorization`/`Cookie` 头。
4. **Token 有效性**：核对 JWT `exp`、签发方与校验方密钥是否一致；检查服务器时区导致 token 提前过期。
5. **免鉴权白名单**：内部健康检查、Feign 回调接口是否误加/漏加白名单（`/actuator/**`、内部接口）。
6. **403 场景**：核对用户角色与接口所需权限，确认 Nacos 中权限配置未漂移。

**临时排查手段**（联调环境）：

- 用 `curl -v -H "Authorization: Bearer {{TOKEN}}" http://{{GATEWAY}}:18080/{{PATH}}` 直接验证网关行为。
- 临时开启 Feign DEBUG 日志观察实际发出的请求头（日志含 token，**仅限联调环境，禁止打印到生产日志**）。
- 对比“直接调下游服务”和“经网关调用”的结果，快速区分是网关还是服务问题。

> 权限设计详见 `docs/库存融资核心系统-登录认证开发指南.md` 与 `docs/库存融资核心系统-角色与权限矩阵.md`。

### 3.3 数据库连接问题

**典型报错**：

- `HikariPool-1 - Connection is not available, request timed out after 30000ms`
- `Communications link failure` / `The last packet sent successfully ...`
- `Too many connections`
- `Access denied for user '{{USER}}'@'{{HOST}}'`

**排查顺序**：

```sql
-- 1) 当前连接与会话
SHOW GLOBAL STATUS LIKE 'Threads_connected';
SHOW VARIABLES LIKE 'max_connections';
SHOW PROCESSLIST;

-- 2) 是否有长事务/锁等待占用连接
SELECT * FROM information_schema.INNODB_TRX ORDER BY trx_started;
SELECT * FROM performance_schema.data_lock_waits;

-- 3) 慢查询（见 docs/工程化配置模板.md 第 2 节）
SELECT * FROM mysql.slow_log ORDER BY start_time DESC LIMIT 20;
```

**常见原因与处置**：

| 原因 | 证据 | 处置 |
|---|---|---|
| 连接池过小 / DB `max_connections` 打满 | `Threads_connected` 接近上限 | 临时调大连接池或 DB 上限；治本看慢 SQL 与连接泄漏 |
| 慢 SQL 长时间占用连接 | `SHOW PROCESSLIST` 大量 `Sending data`/`Sorting result` | 按 T4-4 治理；紧急时 kill 长查询（需 DBA 审批） |
| 连接泄漏 | 事务/ResultSet 未关闭，连接数单调增长 | 检查代码 try-with-resources、事务边界；重启实例临时恢复 |
| 网络/防火墙/安全组 |  telnet/nc 不通，间歇性 `Communications link failure` | 检查安全组、DNS、VIP 漂移 |
| 凭据错误/过期/权限变更 | `Access denied` | 核对配置中心与 DB 授权；轮换后同步所有实例 |
| 从库只读或主从延迟 | 写操作报只读；读到旧数据 | 确认读写分离配置，检查复制状态 |

**处置纪律**：kill 会话、改 DB 参数属于有共享影响的操作，需 DBA 审批并在低峰执行；先确认回滚方式。

### 3.4 迁移失败

**典型报错**：`Flyway Validate failed`、`Migration ... failed`、`Found non-empty schema but no schema history table`、`checksum mismatch`。

**排查顺序**：

```sql
-- 查看迁移历史与失败记录
SELECT version, description, type, state, success, installed_on
FROM flyway_schema_history ORDER BY installed_rank;
-- Liquibase 对应：SELECT id, author, filename, exectype FROM databasechangelog;
```

| 现象 | 原因 | 处置 |
|---|---|---|
| `checksum mismatch` | 已应用的迁移文件被修改（**禁止改已发布迁移**） | 用 `flyway repair` 修正校验和，或新增补偿迁移；需 DBA 确认 |
| 脚本语法错误 / 对象已存在 | SQL 不幂等、环境残留对象 | 修正脚本（仅未应用的版本）；已应用版本不可改 |
| DDL 被长事务阻塞 | `metadata lock` / `Waiting for table metadata lock` | 找出并结束阻塞事务（审批后），或在低峰重试 |
| 权限不足 | 迁移账号无 DDL 权限 | 使用专用迁移账号并授予最小必要 DDL 权限 |
| 版本号冲突 | 多服务共用库、版本号撞车 | 规划版本号区间；核对各服务迁移目录 |
| `non-empty schema` | 空库接入已有数据的实例 | 按 `baseline` 流程初始化，勿清空数据 |

**处置流程**：

1. 停止相关服务写入，避免部分数据被迁移到一半的状态污染。
2. 对当前库做一次快照备份（即使迁移失败）。
3. 记录失败版本号与错误信息，判断是“修脚本重试”还是“repair + 补偿迁移”。
4. 在备份/隔离环境先验证修复方案，再在生产执行。
5. 迁移成功后启动服务，核对 flyway 历史全绿、业务读写正常。

> **V21 outbox 迁移与 `OutboxPublisher` 接口已在 Wave0 建好**，排障时不要重复实现或改动它们；只核对迁移状态与发布任务是否健康。

### 3.5 队列 / Outbox 积压

**识别信号**：下游数据延迟、业务状态不同步、监控显示队列长度持续上升、消费者日志出现重复报错。

**按队列类型排查**：

```sql
-- 数据库 outbox 表（V21）
SELECT status, COUNT(*) FROM outbox GROUP BY status;
SELECT COUNT(*) FROM outbox
 WHERE published = 0 AND created_at < NOW() - INTERVAL 5 MINUTE;
SELECT * FROM outbox WHERE published = 0 ORDER BY created_at LIMIT 20;
```

```bash
# Redis Stream / List
redis-cli LLEN {{QUEUE_KEY}}
redis-cli XINFO STREAM {{STREAM_KEY}}
redis-cli XINFO GROUPS {{STREAM_KEY}}

# RabbitMQ（如引入）
rabbitmqctl list_queues name messages consumers
```

**排查清单**：

1. **消费者是否存活**：实例数、健康状态、线程是否被阻塞；灰度期间是否只剩新版本实例在消费。
2. **消费 vs 生产速率**：速率差持续为正才会积压；短时抖动可自愈，不必干预。
3. **消费报错**：反序列化失败、下游 5xx、唯一键冲突（幂等）、DB 连接耗尽（见 3.3）。
4. **慢 SQL / 锁**：消费事务是否因慢 SQL 或锁等待变慢。
5. **配置**：消费者线程数/批量大小是否被改小；是否误关了自动消费。
6. **死信队列**：是否有消息反复失败进入 DLQ（需人工介入补发）。

**处置**：

- 先止损：扩容消费者 / 临时提高并发 / 暂停非关键生产者。
- 修复根因后按幂等键补发；**补发前确认幂等**，避免重复放款/重复扣减。
- 积压清理后核对业务数据一致性（尤其账务），并记录积压时长与峰值。
- 若消费者长时间不可用，考虑降级：暂停入口流量，待消费恢复后再放量。

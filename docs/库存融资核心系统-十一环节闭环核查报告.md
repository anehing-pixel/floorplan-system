>
> **核查对象**：《库存融资核心系统-业务流程文档》第 1 节「资金与车辆流转闭环（十一环节）」

### 0.2 为什么用"写入点计数"

本次核查最关键的发现，都来自这一招：

> `CreditLine` 领域模型有 `occupy()` 和 `release()` 两个方法。

## 1. 两条流转线的闭环判定

流程文档画了两条线：**资金流**与**车辆流**。闭环的标准是：

> **资金流**：额度占用 → 垫款支付 → 归还核销 → **额度回补** → 再次占用
> **车辆流**：采购建账 → 入库 → 售出 → 结清 → **解押出库** → 车辆流走

### 1.1 资金流闭环判定

```
授信建额 ─→ 放款占额 ─→ 银行支付 ─→ 车入库 ─→ 售出 ─→ 回款核销 ─→ 结清
   ↑                                                                    │
   └──────────────────── 额度回补 ❌ 断裂 ────────────────────────────────┘
```

**判定：✅ 闭环。** 结清时 `line.release(principal)` 回补额度（`RepaymentApplicationService:121`），
放款失败时 `line.release(a.getAmount())` 回滚（`AdvanceApplicationService:498`），
两处都用 `findByIdForUpdate` 行锁保护，并发安全。

### 1.2 车辆流闭环判定

```
采购建账 ─→ 验车确权 ─→ 放款 ─→ 入库 ─→ 担保设定 ❌ 断点 ─→ 售出 ─→ 结清 ─→ 解押 ─→ 抹消
                                              ↓
                                        在库无担保却照常计息、照常库龄递减
```

**判定：⚠️ 部分闭环。** 担保设定与放款之间无衔接；出库指令环节完全缺失。

#### 🔴 关键断点：担保登记是放款**前**的门禁，但系统没有这道门

> **⚠️ 2026-10-26 修订（依业务答复 Q5）**
>
> 业务确认：**担保登记发生在「收到垫款申请之后、放款之前」**，
> 且是**债权人与债务人去法务省办理的线下业务**（系统不自动完成，只记录结果）。
>
> **本节初稿的时序判断有误**——初稿写的是"放款后担保登记无衔接"，
> 隐含假设登记是放款**之后**的事。按业务实际，登记在放款**之前**，
> 因此问题的性质完全变了：**不是"放款后忘了登记"，而是"没登记也放款了"。**

**正确流程与系统现状的对照**：

```
【业务正确流程】
  ① 垫款申请（经办岗）        ← 系统 ✅
  ② 线下签让渡担保合同 + 去法务省登记（**人工线下**）
  ③ 登记完成回填系统（登记编号 + 合同 + 证明书）  ← 系统 🟡 V10 有路径，但无流程门禁
  ④ 资金复核岗核对放款要素    ← 系统 ✅（`ADVANCE_REVIEW`）
  ⑤ 资金出纳岗打款           ← 系统 ✅（`ADVANCE_DISBURSE`）
  ⑥ 银行回调确认              ← 系统 ✅

【系统现状】
  ① 垫款申请 ✅ → ②③ 无人管 → ④ 复核 ✅ → ⑤ 打款 ✅ → ⑥ 回调 ✅
                    ↑↑↑
              完全没有门禁：系统不检查担保状态就打款
```

**实证一：放款流程完全不检查担保状态**

`AdvanceApplicationService` 全文检索 `securityStatus` / `security` → **零命中**
（仅有两处 `collateralService` 调用，都在放款**确认后**建台账行）。
即：**申请 → 复核 → 打款**，全流程不要求"担保已登记"。

**实证二：23 台在流转中的车，担保字段全空**（`vehicle_units` 全表分组统计）：

| status | security_type | security_status | 台数 |
|---|---|---|---|
| FINANCED | (空) | (空) | **8** |
| IN_STOCK | (空) | (空) | **8** |
| SOLD_PENDING | (空) | (空) | **6** |
| SETTLED | RETENTION | RELEASED | 1 |
| SETTLED | (空) | RELEASED | 1 |

只有 2 台 SETTLED 车有担保记录（走 V10 新路径）。

**为什么这比"放款后没登记"更严重**：

| 维度 | 放款后没登记 | 放款前没门禁（本项） |
|---|---|---|
| 风险敞口 | 已放款后才暴露 | **放款瞬间即无担保**——钱已出去，法律担保未成立 |
| 可补救性 | 可事后补登记（时间成本） | **钱已付出，担保未成立**，只能靠合同追索 |
| 优先顺位 | 登记补办后仍有公示效力 | 无对抗要件的场合（如所有权保留）尚可，**让渡担保则可能丧失优先权** |
| 审计追溯 | 事后可查 | 系统内**无任何记录证明该检查过**——问题在流程设计上就不可见 |

**这正是 ADR-006「五段四岗」里缺的一段**：
录入 → 申请 → **复核 → 打款** 之间，本应有「担保登记确认」这一环——
它是**线下动作 + 系统回填 + 放款前校验**三者的组合。

#### 🟡 「登记编号被丢弃」仍是真问题

老接口 `POST /{vin}/security` 收了 `regNo`（法务省登记编号）、`ownerName`（担保权人），
但 `VehicleUnit` 无这两个字段（grep 零命中）——**接口返回成功，登记编号丢失**。
这比"接口不存在"更糟：使用方以为登记了。

**注意与 V10 的关系**：V10 已建 `collateral_registration_batches`
（批次级 `registration_no` + 合同附件 + 证明书附件 + 抹消三段），
**新路径是对的**。问题是**老接口还在，且与新路径并存**——
两条路径都能"设定担保"，但只有新路径真的存登记编号。
应废弃老接口或让它委托到 V10 批次表。

#### ✅ 流程补齐建议（放款前的门禁）

```
垫款申请（经办岗）
   ↓
**担保登记确认（新增门禁）**
   · 登记是否已完成？（查 collateral_registration_batches 中该 VIN 的 REGISTERED 批次）
   · 登记编号 + 合同 + 证明书是否齐备？
   · 未完成 → 阻断放款，生成「担保待登记」工单给采购审核岗
   ↓
资金复核（复核岗）—— 复核项新增：担保登记已完成
   ↓
资金出纳打款（出纳岗）
```

**门禁的强度选择**：

| 方案 | 规则 | 适用 |
|---|---|---|
| **硬阻断**（推荐） | 无 REGISTERED 批次 → 拒绝打款 | 合同约定"先登记后放款"时 |
| **软告警** | 允许打款但强制工单 + 高优预警 | 合同允许"放款后 N 日内登记"时 |
| **可配置** | 按 `credit_line` / 经销商 / 产品线配置门槛 | 多种业务形态并存时 |

> **建议默认硬阻断**，可按经销商放宽——因为让渡担保在未登记期间**可能丧失优先权**，
> 这不是能靠事后补救的风险。

### ⑧ 解押与出库 🔴

| 项 | 状态 | 证据 |
|---|---|---|
| 解押接口 | ✅ | `POST /{vin}/security/release` |
| 幂等 | ✅ | 无担保时直接返回，不报错 |

| **监管方放车环节** | ⬜ | 无 |
| 抹消登记 | ✅（V10） | `collateral_registration_batches` 抹消三段 |

**🔴 关键断点：出库指令环节完全缺失**

流程文档环节⑧ 写的是「**解押与出库**：监管方见指令放车 · 金融解抵」。
现实中的出库是一个**跨机构协同动作**：
```
结清完成 → 金融公司下达出库指令 → 经销商/监管方核对 → 放车 → 金融公司解抵（登记抹消）
```
现在只有"金融公司单方解押"这一步，**没有"下达指令"和"对方执行"的环节**。

**为什么这在法律上重要**：让渡担保的解除需要**权利人与登记义务人共同申请**。
出库环节是"确认车可以交给终端客户"的时点——
没有这个环节，系统在结清后就解押，但**车可能还没交出去**，
终端客户拿着车却没完成登记，权利链条断裂。

### ⑨ 额度恢复与结清 ✅

| 项 | 状态 | 证据 |
|---|---|---|
| 整台结清 | ✅ | `POST /api/repayments`，`unit.settle()` → `SETTLED` |
| 部分还款 | ✅ | `POST /api/repayments/partial`，只扣本金不回补额度 |
| 结清证明 | ✅ | `POST /api/payoffs/issue` |
| 担保解除 | ✅ | 结清时 `releaseSecurity()` |
| 抹消待办 | ✅（V10） | `registration_due = true` |
| **额度回补** | ✅ | `RepaymentApplicationService:121` `line.release(principal)` + 行锁 |
| 放款失败回滚 | ✅ | `AdvanceApplicationService:498` `line.release(a.getAmount())` |

**额度回补的实现（核查确认）**：

```java
// 4) 额度回补（行锁）
long released = 0L;
if (unit.getCreditLineId() != null) {
    CreditLine line = creditLineRepository.findByIdForUpdate(unit.getCreditLineId())
            .orElseThrow(() -> new BusinessException(ErrorCode.NOT_FOUND_001, "额度不存在"));
    released = principal;
    line.release(principal);
    creditLineRepository.save(line);
}
```

`CreditLine.release` 内部有 `Math.min(amount, usedAmount)` 保护（不会减成负数）。
**两处占用点（放款成功 / 放款失败）都有对应的释放点，且用行锁防并发超扣——实现是严谨的。**

> **⚠️ 一次误判的记录（保留以示警惕）**
>
> 本报告初稿把"额度回补断裂"列为**最严重发现**，依据是
> `grep -rn "\.release()" --include=*.java .` 返回 0 处。
> **这个正则只匹配无参调用** `release()`，而实际调用是 `release(principal)` / `release(amount)`
> ——带参数的调用完全不匹配，于是产生了假阳性。
>
> 进一步的实库查询也强化了这个误判：dealer 288/289/290 的 `used_amount` 为 3,330,000 / 6,660,000，
> 而对应车辆 `principal_balance=0`（看起来"车全清了额度还占着"）。
> **但真相是**：这些车状态为 `FINANCED`、`advance_status=PENDING`——
> **钱还没付出去**（银行未回调），`principal_balance=0` 是因为**尚未放款**，
> 不是"已还清"。此时占用额度是**完全正确**的（垫款已申请即占额，ADR-006 的设计）。
>
> **教训**：①检索"某方法是否被调用"时，**不能用只匹配无参形式的正则**，
> 必须用 `\.release\(` 之类含括号的模式；②用数据反证代码时，
> **要先确认数据的业务含义**（`principal_balance=0` 有"未放款"和"已还清"两种完全不同的含义）。
> 假阳性比假阴性更危险——它会把修复资源引向错误的方向。

#### ⑨-1 额度回补的判定原则（依业务答复，2026-10-26）

> **业务给出的核心原则**：
> **额度回补必须与「质押物释放」「本金敞口下降」「合同规则一致」三者同时成立。**
>
> 推论：库存融资里"**卖车回款 / 提前还本金**"通常应当回补额度；
> 但"**只还利息 / 逾期补款 / 未解押部分还款**"一般不回补可用额度。

**四个判定条件**（缺一不可）：

| 条件 | 含义 | 判定依据 |
|---|---|---|
| **C1 本金敞口下降** | 这笔还款确实减少了未偿本金 | `principal_balance` 减少额 > 0 |
| **C2 质押物释放** | 该车的担保权益已解除（或该部分对应的担保物已处置） | `security_status = RELEASED` 或该台车已处置 |
| **C3 合同规则一致** | 合同约定的还款用途与本次行为相符 | 合同/还款计划约定的 `designated_use` |
| **C4 非逾期补款** | 不是为清偿逾期欠款而临时补的 | 欠款性质判定 |

**回补规则矩阵**：

| 还款场景 | C1 本金下降 | C2 质押物释放 | C3 合同一致 | C4 非逾期补款 | **是否回补额度** | 现状 |
|---|---|---|---|---|---|---|
| **整台结清**（卖车回款） | ✅ | ✅（结清即解押） | ✅ | ✅ | ✅ **全额回补** | ✅ 已实现 |
| **提前还本金**（车未售、主动还款） | ✅ | ❌ 车仍在库、担保未解除 | 需看合同 | ✅ | ⚠️ **应回补但现状不回补** | ❌ **缺口** |
| **未解押部分还款**（车已售、未结清） | ✅ | ❌ 未解押 | ✅ | ✅ | ❌ 不回补 | ✅ 现状正确 |
| **只还利息** | ❌ 本金未降 | ❌ | — | ✅ | ❌ 不回补 | ✅ 现状正确 |
| **逾期补款** | ✅ | 视情况 | 视合同 | ❌ | ❌ 不回补 | ✅ 现状正确 |
| **处置变现回收** | ✅ | ✅（担保消灭） | ✅ | — | ✅ **全额回补** | 🟡 处置不碰额度（断点 B3） |

#### 🔴 缺口：`partialRepay` 不区分车辆状态，"提前还本金"被误伤

**现状**（`RepaymentApplicationService.partialRepay`）：

```java
// 只扣本金，不解除担保、不回补额度
unit.applyPrincipalPayment(principalAmount);
```

**问题**：该方法只校验"不是已结清/已关闭"，**不区分车辆状态**——
在库车（`IN_STOCK`）与已售未回款车（`SOLD_PENDING`）走完全相同的路径，一律不回补额度。

**但这两类车的业务性质不同**：

| 车辆状态 | 业务含义 | 按原则应否回补 |
|---|---|---|
| `IN_STOCK`（在库） | 车还在经销商场地，担保物完好；经销商**主动提前还本金** | ⚠️ **应回补**（本金敞口真实下降，且这是资信良好的表现） |
| `SOLD_PENDING`（已售未回款） | 车已交付终端客户，担保物价值已归零，**未解押** | ❌ **不回补**（C2 不成立） |

**同一台车、同一个接口、同一笔操作，因为车辆状态不同而应有不同结果——
而现在不区分。** 这是把"提前还本金"这个正面行为与"未解押部分还款"混为一谈。

**修复方向**（不是简单加个 if，而是引入判定函数）：

```
// 建议：额度回补判定抽为领域服务，与业务规则同源
public class CreditReleasePolicy {

    /**
     * 判定一笔还款是否应回补额度。
     * 依据：质押物释放 + 本金敞口下降 + 合同规则一致（业务答复，2026-10-26）
     */
    public ReleaseDecision evaluate(VehicleUnit unit, long principalPaid) {
        // C1：本金敞口是否真的下降
        if (principalPaid <= 0) return ReleaseDecision.none("仅结息，本金未降");

        // C2：质押物是否已释放
        boolean securityReleased = unit.getSecurityStatus() == SecurityStatus.RELEASED;
        boolean vehicleDisposed = unit.getStatus() == VehicleStatus.DISPOSING
                              || unit.getStatus() == VehicleStatus.CLOSED;

        if (vehicleDisposed) {
            return ReleaseDecision.full("车辆已处置，担保消灭，本金敞口清零");
        }
        if (securityReleased) {
            return ReleaseDecision.full("担保已解除，质押物已释放");
        }
        // 未解押：看是否为"提前还本金"（在库且本金下降）
        if (unit.getStatus() == VehicleStatus.IN_STOCK) {
            return ReleaseDecision.partial(principalPaid,
                "在库车提前还本金：本金敞口下降，按合同规则回补对应额度");
        }
        // 已售未回款：质押物价值已归零且未解押，不回补
        return ReleaseDecision.none("已售未解押：质押物未释放，不回补额度");
    }
}
```

**注意 C3「合同规则一致」尚未实现**——当前 `repayments.designated_use` 字段已存在
（`partialRepay` 时恒为 false，`settle` 时恒为 true），但**没有承载"合同约定用途"的语义**。
要真正实现 C3，需要：
- 还款时记录**本次还款的用途**（结清 / 提前还本金 / 利息 / 逾期补款）
- 额度占用时记录**该笔占用的合同用途**（可回补 / 不可回补）
- 两者匹配才回补

**这是一次需要业务进一步定义的口径**（见 §6 疑问 Q20）。

## 4. 两条线的真正断点在哪里

把上面的断点按"资金流/车辆流"归位，会看到**问题不是分散的，而是集中在三个接缝**：

```
【接缝一】③垫款申请 ──→ ④担保登记 ──→ ③放款   ← 应有的门禁位置
   现状：申请 → 复核 → 打款，中间无门禁，系统不查担保状态
   影响：钱已付出而法律担保未成立；让渡担保可能丧失优先权
   ↓
【接缝二】⑨结清 ──→ ⑧出库指令 ──→ ⑧解押
   现状：结清后直接解押，没有"下达指令/对方执行"环节
   影响：车可能还没交出去，权利链条断在中间
   ↓
【接缝三】⑩盘点缺失 ──→ ⑩处置流程
   现状：只置 oot_suspected 布尔标记，不改状态，处置 job 扫不到
   影响：最严重的脱信信号进不了处置闭环
```

> **资金流的"结清→额度回补"不在断点之列**——该接缝是通的
> （`RepaymentApplicationService:121`，有行锁保护）。
> 初稿曾误判此处断裂，纠正记录见 §⑨。

**共同特征**：**都是"上一环节做完了，下一环节没接上"**。
每个环节内部都做得不错（幂等、留痕、状态校验），
但**环节与环节之间的移交没有触发机制**。

这与 ADR-008 揭示的是同一类问题：
> **系统里缺的不是"能力"，是"移交"**——
> 状态变更没有自动驱动下游动作，下游要靠人记得去调。

## 8. 复核补记（2026-10-26 21:50，二次核查）

> 本节是对 §1–§7 的**增量复核**：代码与实库重新验证一遍，确认原断点仍然成立，
> 并补记原报告**未发现的 5 项问题**（8.1–8.5）与由此产生的 5 个疑问（§8.6 Q26–Q30）。
>
> 复核结论：§3 的 B1–B4、B1b、M1–M12 **全部仍然成立**，无一项已修复。

### 8.1 🔴 新发现：担保数据"三源并存、互不一致"

原报告 §④ 只查了 `vehicle_units.security_status`（得出"23/26 台担保全空"）。
复核发现系统里**同时存在三处担保状态，三者数字对不上**：

| 数据源 | 粒度 | 实库结果（2026-10-26 21:50） | 能否回答"这台车登记了吗" |
|---|---|---|---|
| `vehicle_units.security_status` | 按 VIN | 26 台车：**1 台 RELEASED，25 台为空** | ✅ 能，但基本全空 |
| `collateral_ledger.security_status` | 按 VIN | **仅 10 行，全部 REGISTERED**（缺 16 台车） | ✅ 能，但只有 10 台有台账行 |
| `collateral_registration_batches` | **按批次** | **14 条登记号，无任何 VIN 字段**，`vehicle_count` 多为 0 | ❌ **不能** |

**核心结构缺陷：批次表没有 VIN。**

```
collateral_registration_batches   registration_no ✅   vin ❌   vehicle_count(仅数字)
collateral_ledger                 vin ✅              security_status ✅   registration_no ❌
                                                     ↑
                              两张表各管一半，中间没有桥
```

- 有**登记编号**的表（批次表）**不知道是哪几台车**；
- 知道**是哪台车**的表（台账/车辆）**没有登记编号**。

**直接影响 B1 门禁设计**：§④ 建议的门禁判定是"查 `collateral_registration_batches` 中该 VIN 的 REGISTERED 批次"——
**按现有表结构这个查询写不出来**。门禁必须先解决"批次 → VIN"的关联（新增 `collateral_registration_items(batch_id, vin)` 明细表，
或把 `registration_no` 冗余到 `collateral_ledger`）。

**这也解释了"14 条登记却 25 台车担保为空"**：登记确实做了 14 次，但系统无法把它对应到具体车。

### 8.2 B1b 已在实库产生真实实例

原报告 B1b 是"推理出来的缺口"，复核找到**一笔真实数据**：

```
repayments:  vin=TESTRP1026195105  type=PARTIAL  principal=100,000
vehicle_units: status=IN_STOCK  principal_balance=732,500  security_status=(空)
```

一台**在库车**主动还了 10 万本金（本金 832,500 → 732,500），
按 §⑨-1 的原则属"提前还本金"→ **应回补 100,000 额度**；
现状 `partialRepay` 一律不回补，**该经销商的可再用额度被少放了 10 万**。

这不是假想场景，是已经发生过的业务动作。

### 8.3 🟡 新发现的规则冲突：库龄递减（强制）vs 提前还本金（自愿）

两处文档对"在库车还本金是否回补额度"给出了**相反结论**，且都能自圆其说：

| 文档 | 结论 | 理由 |
|---|---|---|
| 《库龄递减与强制还款设计》§0.1 | **不释放额度 ✅ 正确** | 部分还款仍占用额度，区别于结清 |
| 《闭环核查报告》§⑨-1 / B1b | **应回补但未实现 ❌ 缺口** | 本金敞口下降（C1 成立）、车在库（C2 争议） |

**根因：四条件（C1–C4）里没有"还款动因"这一维。**
同样是"在库车本金下降 10 万"，业务含义完全不同：

| 场景 | 动因 | 风控含义 | 应否回补 |
|---|---|---|---|
| 库龄递减还款 | **强制**（超期被逼还） | 车卖不掉，风险在上升 | ❌ **不回补**（压降敞口就是这个动作的目的） |
| 主动提前还本金 | **自愿**（经销商主动降杠杆） | 资信良好的信号 | ✅ **回补**（奖励 + 释放可再用额度） |

**若按 B1b 的"本金下降就回补"直接修，会把库龄递减的回补一起改错**——
那样"车卖不掉被强制还款"反而让经销商拿回额度去进新车，风险敞口不降反升。

→ 结论：B1b 的修复**不能只按车辆状态分支**，必须同时引入"还款动因"维度。见 Q26。

### 8.4 🟡 文档与代码的作业名不一致（4 处，会误导运维排查）

实库 `batch_runs` 实际值 vs 文档写法：

| 代码 / 实库（正确） | 文档写法（错误） | 位置 |
|---|---|---|
| `SETTLE_WINDOW_SCAN` | `SETTLEMENT_SCAN` | 业务流程文档 §7 环节⑦⑩（**已修正**）；技术设计文档 §325/§337（**未修**） |
| `INTEREST_ARCHIVE` | `ARCHIVE` | 业务流程文档 §7 环节⑤（**已修正**） |
| 技术设计文档 §211/§317 用 `SETTLE_WINDOW_SCAN`，§325/§337 用 `SETTLEMENT_SCAN` | — | **同一文档内混用两种写法** |

**为什么这不是小事**：`GET /api/jobs/status?jobName=` 是精确匹配。
按文档写 `SETTLEMENT_SCAN` 去查，永远返回"未运行"——排查时会误判成"作业没跑"。

### 8.7 复核后的一句话

## 1. 背景（Context）

### 1.1 问题的本质：收款方不是系统规则能推出来的

「直付上游」不是一种产品，而是**按融资用途分岔的三条路由**：

| 场景 | 钱打给谁 | 原因 | 融资性质 |
|---|---|---|---|
| **A. 新车库存采购** | 制造商销售公司 / 区域总代理 / 批发公司 / 指定收款账户 | 用途是「采购车辆」，资金需覆盖采购款 | 代付采购款（资金出账到上游） |
| **B. 二手库存采购** | 拍卖行 / 中古批发商 / 上游卖方 | 车源不是工厂，是拍卖/批发渠道 | 代付采购款（资金出账到上游） |
| **C. 已有库存抵押补充周转** | **经销商自身账户** | 这是库存抵押贷款，不是代付采购款 | 营运资金（资金回经销商） |

**A/B 与 C 的差别是根本性的，不是收款人换个名字**：
- 资金流向不同（C 的钱回经销商自己手里、可自主支配；A/B 的钱直接出账给上游）；
- 法律基础不同（A/B 靠三方委托付款，C 是普通抵押融资）；
- 风控重心不同（A/B 的风险是「付了款车没来」，C 的风险是「挪作他用 + 库存估值虚高」）。

### 1.2 日本新车流通里，「工厂」不是一个收款对象

经销商通常**不直接向汽车工厂下单**，而是通过多层渠道采购：

| 上游类型 | 说明 | 日本实务中的典型角色 |
|---|---|---|
| `MAKER_SALES_CO` | 制造商销售公司 | 厂商在日的销售法人，握有车辆分配权 |
| `REGIONAL_AGENCY` | 区域总代理 | 一县一店的区域批发代理，握有车源与配额 |
| `WHOLESALER` | 批发公司 | 多品牌 / 跨区域批发 |
| `AUCTION` | 拍卖行 | 中古车竞拍成交对手方 |
| `USED_WHOLESALER` | 中古车批发商 | 二手批发渠道 |

另有一条常被忽略的路径：**经销商指定的采购款受取口座**。

> 结论：系统里不该有「厂家（factory）」这个单一收款方概念。收款方是**采购订单上的一个角色**，由 `supplier_type` 决定。

### 1.3 现状缺口（已核实代码）

| 位置 | 现状 | 问题 |
|---|---|---|
| `domain/service/PaymentGateway.java` | `pay(String vin, long amount, String orderNo)` | **签名里没有收款方**——付给谁、付到哪个账户，系统无从表达 |
| `application/dto/VehicleDraft.java` | **无 supplier 字段** | 单台草稿不含上游标识 |
| `ApiRequests.BatchIngestRequest` | `purchaseChannel` / `supplierName` 均为**自由文本** | 拼写错误无人拦截；`supplierName` 是批次级，定位不到主数据 |
| `domain/model/VehicleUnit.java` | `supplierName`（String 冗余快照）、`purchaseChannel` | 同上 |
| `vehicle_units.purchase_channel` 实际取值 | 库里只有 `OEM`，`vehicle_type` 全 NULL | 枚举定义在文档里，**但代码不校验**，字段形同虚设 |
| `dealers` / `credit_lines` 表 | **无任何银行账户列** | 场景 C 连账户都没有地方存 |
| 数据库 | 无采购订单表、无上游主数据表、无账户表、无附件表 | 五张表都要新建 |
| 文件存储 | **零文件上传能力**（无 `MultipartFile`、无 POI、无 multipart 配置、无对象存储客户端） | 原始凭证无处存 |

## 2. 决策（Decision）

### 决策一（核心）：打款对象由「采购订单」决定，不由系统规则决定

融资申请 → **关联采购订单** → 采购订单携带 `supplier_type` 与 `payee_account_ref` → 打款对象 = 工厂 / 总代理 / 拍卖行 / 经销商。

```
purchase_orders（采购订单）—— 新增，融资的凭证锚点
   │  order_no, dealer_id, supplier_type, payee_account_id(→账户主数据),
   │  payee_account_snapshot, total_amount, purchased_at,
   │  evidence_no(合同/发注书号), evidence_attachment_id(→附件)
   │
   ├──1:N──> vehicle_units（建账时挂 purchase_order_id；一张采购单可能含多台车）
   │
   └──1:N──> advances（垫款时挂 purchase_order_id + 冻结 payee 快照）
```

**为什么锚点是采购订单，而不是"每台车标注账户"**：

| 方案 | 一单多车 | 场景 C（打给经销商） | 审计能否回答"这钱付给谁" | 结论 |
|---|---|---|---|---|
| 每台车冗余存一套账户 | 一单 N 台车要重复录 N 遍，易错 | 无法表达（收款方不是上游） | 只能靠时间戳比对，脆弱 | ✗ |
| 只存 supplierId、放款时实时读 | 同上 | 无法表达 | 无法冻结历史事实；申请后改账户即可劫款 | ✗ |
| **车辆挂采购订单 → 订单挂上游 + 账户 → 放款冻结快照** | 一单多车天然承载 | 订单上 `supplier_type=DEALER_SELF` 即可 | 精确（垫款指令自带账户事实） | ✓ **采纳** |

一句话：**车辆记录"这车属于哪张采购单"，采购订单记录"这张单付给谁"，垫款指令记录"这笔钱实际付到了哪个账户"**——三者性质不同，不该混在一张表重复。

### 决策二：`supplier_type` 驱动打款模式路由，且区分「直付上游」与「回款经销商」

新增枚举 `supplier_type`，**打款模式由它派生，不由人工勾选**：

| supplier_type | 打款对象 | 打款模式 | 资金流向 | 代付协议 |
|---|---|---|---|---|
| `MAKER_SALES_CO` 制造商销售公司 | 销售公司 | `DIRECT_PAY` | 上游 | 必需 |
| `REGIONAL_AGENCY` 区域总代理 | 总代理 | `DIRECT_PAY` | 上游 | 必需 |
| `WHOLESALER` 批发公司 | 批发公司 | `DIRECT_PAY` | 上游 | 必需 |
| `AUCTION` 拍卖行 | 拍卖行 | `DIRECT_PAY` | 上游 | 必需 |
| `USED_WHOLESALER` 中古批发商 | 中古批发商 | `DIRECT_PAY` | 上游 | 必需 |
| `DEALER_SELF` 经销商自身 | **经销商结算账户** | `SELF_PAY` | **经销商** | **不适用** |

**决策要点**：
1. **`SELF_PAY` 不是 `DIRECT_PAY` 的特例**，它有独立的校验链与法律基础（决策五）。把「代付协议已生效」列为放款硬校验，在场景 C 下会**直接把业务堵死**——这是早期版本的一个实质错误。
2. **`DEALER_SELF` 的账户从哪来**：经销商自己的结算账户，需**新增 `dealer_bank_accounts`**（`dealers` 表目前完全没有账户列）。该账户变更管控须**严于**上游账户——它是唯一「钱能自主支配」的出口。
3. **打款模式不允许人工覆盖**。它是 `supplier_type` 的派生值，人工可改 `supplier_type`（有审核流），但不能直接改打款模式——否则「选 `DEALER_SELF` 就绕开代付协议」成为一个现成漏洞。

### 决策三：上游主数据 + 账户主数据，车辆挂引用、放款冻结快照（三层）

```
suppliers（上游主数据）
   └─ 1:N supplier_bank_accounts（上游收款账户：银行/户名/账号密文/掩码/状态/生效期/复核状态）
                    ↑ 外键引用
purchase_orders.supplier_id + supplier_type + payee_account_id
                    ↓ 放款时冻结
advances.payee_supplier_id + payee_supplier_type + payee_account_snapshot（放款那一刻的账户事实）

dealer_bank_accounts（经销商结算账户）—— 场景 C 专用
```

**为何三层**：改一处可查影响面；审计能精确回答"付给了谁、当时账户是什么"；变更受控 + 冷静期把欺诈面压到最小。

### 决策四：采购订单进系统——**两条通道：API 直连 + Excel/CSV 批量导入**

#### 4.1 两条通道

| 通道 | 数据来源 | 系统内形态 | 关键差异 |
|---|---|---|---|
| **API 直连** | 主机厂销售公司、区域总代理、拍卖平台、经销商 DMS/ERP | 走 `/external/purchase-orders`（签名校验 → 限流 → ACL → 字段校验 → 落主单） | **数据源可信 + 有契约保证 → 可豁免人工确认** |
| **Excel/CSV 批量导入** | 经销商提交的车辆采购清单 | 走 `/api/purchase-orders/import`（固定模板 → 行级报错 → 预览确认 → 落主单） | **人工填写的表格 → 必须人工确认** |

**两条通道长期并存，不是成熟度替代关系**——它们服务的是**能力不同的对手方**：

| 通道 | 服务对象 | 为什么长存 |
|---|---|---|
| **API 直连** | 主机厂销售公司、区域总代理、拍卖平台、经销商 DMS/ERP | 这些对手方有系统、有对接意愿，直连数据质量最高 |
| **Excel/CSV** | 上述对手方之外的所有经销商，以及**长尾小批量场景** | 大量中小经销商只有 Excel 台账；即使已接 API，**零星补录、临时采购、异常单**仍走 Excel |

**结论**：Excel 不是"等 API 上线就废弃"的临时方案，而是**长期存在的正式通道**，必须与 API 同等对待（同样的幂等、同样的审计、同样的字段校验）。

**未采用的通道**（经评估否决，理由见 §3）：门户上传 PDF·图片、人工单条录入、OCR+AI 解析、Word 合同自动解析。

#### 4.2 核心原则：采购订单是**融资放款的前置主单**，不是"一个待解析的文本文件"

系统里**先有采购订单主单，再有垫款**：

```
经销商发起融资申请
→ 上传采购车辆清单（Excel/CSV）或由上游 API 推送采购订单
→ 系统校验 VIN、车型、供应商类型、金额、收款账户引用
→ 与供应商主数据、采购价、车辆信息做交叉校验
   （VIN 唯一 / 重复融资 / 权属 / 账户状态 / 金额上限）
→ 生成「采购订单主单」（purchase_orders）+ 车辆台账（挂 purchase_order_id）
→ 触发放款审批（资金岗 disburse）
→ 放款成功后关联车辆质押 / 入库状态
```

**为什么必须先落主单**：主单是**唯一的放款依据**。绕过主单直接产生垫款，等于把「未经校验的导入内容」直接变成资金指令。

#### 4.3 落库前的确认闸门：按通道分级

| 通道 | 闸门 | 理由 |
|---|---|---|
| **API 直连** | **可豁免人工确认**（配置项可强制开启复核） | 数据源是主机厂/总代理/拍卖平台/DMS，**对接有契约与签名保证**，错误可在源系统更正后重推 |
| **Excel/CSV** | **必须人工确认**（`preview` → `commit` 两段式） | 表格是经销商自己填的，**错误率不可控**；但账户走引用码后风险已被大幅压缩 |

| 环节 | 产物 | 谁做 |
|---|---|---|
| 导入/推送 | `ParsedOrder`（VIN 列表 / 车型 / 供应商类型 / 金额 / 收款账户引用 / 附件） | 系统（API / Excel） |
| 校验 | 逐字段校验结果 + 错误清单 | 系统 |
| 确认 | 复核界面（账户号脱敏显示供比对） | 业务 / 风控（**API 通道可跳过**） |
| 落库 | `purchase_orders` + `vehicle_units`（挂订单） | 系统 |

#### 4.4 导入哪些信息（**两条通道共用同一份字段口径**）

以下为业务方确认的**清单关键字段**。两条通道（API 直连 / Excel 导入）**导入的信息完全一致**——这是"两种方式产出同一份主单"的落地基础。

| # | 字段组 | 字段 | 类型 / 取值 | 必填 | 校验规则 | 落库位置 |
|---|---|---|---|---|---|---|
| 1 | **标识** | 采购订单号 `orderNo` | 字符串 ≤64 | ✅ | **唯一**（幂等锚点） | `purchase_orders.order_no` |
| 2 | **车辆** | VIN / 车架号 `vin` | 字符串 ≤17 | ✅ | 唯一性 + **VIN 幂等**（防两单报同一台车）+ 重复融资拦截 | `vehicle_units.vin` |
| 3 | | 车型 `model` | 字符串 | ✅ | 非空 | `vehicle_units.model` |
| 4 | | 年款 `modelYear` | 4 位年 | ✅ | 合理区间 | `vehicle_units.model_year` |
| 5 | | 颜色 `color` | 字符串 | ✅ | 非空 | `vehicle_units.color` |
| 6 | **上游** | 供应商类型 `supplierType` | `MAKER_SALES_CO` / `REGIONAL_AGENCY` / `WHOLESALER` / `AUCTION` / `USED_WHOLESALER` / `DEALER_SELF` | ✅ | **枚举校验**（6 值，不可自由文本）→ **派生打款模式** | `purchase_orders.supplier_type` |
| 7 | | 上游 ID `supplierId` | 整数 | ⭕ | `DEALER_SELF` 时可空；须命中上游主数据 | `purchase_orders.supplier_id` |
| 8 | **金额** | 采购金额 `invoiceAmount` | 整数（日元） | ✅ | > 0；≤ 垫款比例上限；与订单总额勾稽 | `vehicle_units.invoice_amount` / `purchase_orders.total_amount` |
| 9 | **收款** | 收款账户 `payeeAccountRef` | 引用码（如 `ACC-KY-001`） | ✅ | **只接受引用码，拒绝明文账号**；须命中账户主数据且状态 ACTIVE、已过冷静期 | `purchase_orders.payee_account_id` |
| 10 | **状态** | 车辆状态 `vehicleStatus` | 在途 / 在库 / 已质押 / 已解押 | ✅ | 业务侧口径，**落库时映射到领域枚举**（见决策九） | `vehicle_units.vehicle_status` + 担保标记 |
| 11 | **凭证** | 单据编号 `evidenceNo` | 字符串 ≤64 | ⭕ | 契约 / 発注書 / 請求書 号 | `purchase_orders.evidence_no` |
| 12 | | 原始附件 `attachmentId` | 附件 ID | ⭕ | **原件留存**（合同·图片·Excel 原始文件），见决策十；API 通道上游不供原件时留空并标注"无附件" | `purchase_orders.evidence_attachment_id` → `attachments` |
| 13 | **归属** | 经销商 `dealerId` | 整数 | ✅ | 须存在且状态 ACTIVE | `purchase_orders.dealer_id` |
| 14 | | 授信额度 `creditLineId` | 字符串 | ✅ | 须存在且可用额度充足 | `purchase_orders.credit_line_id` |
| 15 | | 采购日 `purchasedAt` | 日期 | ⭕ | 不得晚于当前日 | `purchase_orders.purchased_at` |
| 16 | **溯源** | 导入通道 `ingestChannel` | `API` / `EXCEL` | ✅ | 系统自动写入 | `purchase_orders.ingest_channel` |
| 17 | | 导入批次 `importBatchId` | 整数 | ⭕ | API 推送为空 | `purchase_orders.import_batch_id` |

**三条贯穿全部字段的硬约束**：

1. **`payeeAccountRef` 只传引用码，不传明文账号**（两条通道均如此）。Excel 是人工可编辑文件，放明文账号等于把导入通道变成"塞入任意账户"的后门；API 侧同理，明文账号会进入请求日志与审计留痕。
2. **原始文件必须留存**。只存解析结果无法自证"这笔采购单据说的是这个账户"。
3. **幂等双锚点**：`orderNo` 唯一防"同一张单重复导入"；**VIN 幂等**防"两个不同订单号报同一台车"——导入侧就拦，不等放款才发现。

#### 4.5 「导入通道」与「凭证留存」正交拆解

```
导入通道（数据怎么进系统）          凭证留存（原始文件怎么进系统）
├─ API 直连 → 应用 → 主单            └─ 预签名 URL 直传 → S3 → attachment 元数据
└─ Excel/CSV → 应用 → 主单                 ↑
                                      主单持有 attachment_id，两条通道共用
```

**附件留存是主单的必备属性，不是某个通道的附属功能**。两条通道共用同一套留存机制——**不需要为此新增第三条导入通道**。

### 决策五：两套放款校验链，按打款模式分叉

#### 5.1 `DIRECT_PAY`（代付上游）放款前校验

| # | 校验 | 不通过 |
|---|---|---|
| 1 | 垫款状态 = PENDING | 409 ADVANCE_003 |
| 2 | 车辆状态 = FINANCED | 422 VEHICLE_002 |
| 3 | 车辆已挂 `purchase_order_id`，订单状态有效 | 422 |
| 4 | `supplier_type` ∈ {MAKER_SALES_CO, REGIONAL_AGENCY, WHOLESALER, AUCTION, USED_WHOLESALER}（即非 `DEALER_SELF`） | 422 |
| 5 | **三方委托付款协议已生效、未过期、覆盖本订单** | 422 |
| 6 | 本次金额 ≤ 协议授权上限（且累计未超） | 422 |
| 7 | 收款账户状态 ACTIVE、非冻结、已过冷静期 | 422 + 告警 |
| 8 | 金额 ≤ 采购单金额 × 垫款比例上限 | 422 ADVANCE_001 |
| 9 | 可用额度充足 | 422 CREDIT_001 |
| 10 | 同一 VIN 无在途（PROCESSING）垫款 | 409（防重复付款） |
| 11 | 审计留痕：申请人、资金岗、收款方类型、账户掩码、金额 | 写审计表 |

#### 5.2 `SELF_PAY`（回款经销商，场景 C）放款前校验

| # | 校验 | 不通过 | 与 DIRECT_PAY 的差别 |
|---|---|---|---|
| 1 | 垫款状态 = PENDING | 409 ADVANCE_003 | 相同 |
| 2 | 车辆状态 = FINANCED | 422 VEHICLE_002 | 相同 |
| 3 | 车辆已挂 `purchase_order_id`，且订单 `supplier_type=DEALER_SELF` | 422 | 订单语义不同 |
| 4 | 经销商结算账户存在、状态 ACTIVE | 422 | **不需要委托付款协议** |
| 5 | 经销商账户变更已过冷静期 | 422 + 告警 | **这是唯一能自主支配资金的出口，管控须更严** |
| 6 | **本次提款对应库存已盘点在库**（现货核对） | 422 | **DIRECT_PAY 不需要此校验**——钱付给上游与车是否在手无关 |
| 7 | 库存估值口径 = 采购价（不按零售价） | 422 | 避免虚高抵押 |
| 8 | 金额 ≤ 库存估值 × 抵押率上限（**可低于垫款比例**） | 422 | 抵押融资应有独立、更保守的比例 |
| 9 | 可用额度充足 | 422 CREDIT_001 | 相同 |
| 10 | 同一 VIN 无在途（PROCESSING）垫款 | 409 | 相同 |
| 11 | 审计留痕（**额外标注"非代付、属营运资金"**） | 写审计表 | 审计口径不同 |

**要点**：`SELF_PAY` 的第 6、8 条是 `DIRECT_PAY` 完全没有的——钱回到经销商手里，必须自己确保「抵押物在库、估值不虚高」；而 `DIRECT_PAY` 的第 5、6 条（代付协议）在 `SELF_PAY` 下完全不适用。

### 决策六：三方委托付款协议是放款前置要件（**仅 `DIRECT_PAY` 适用**）

在 `DIRECT_PAY` 下，资金**先于车辆交付**离开金融公司，敞口从「经销商不付」扩展为「**上游收钱不发货 / 上游倒闭**」——已付款未提车即为直接损失。因此：

- **委托付款协议已生效是放款前置要件**，且必须**覆盖本订单**、金额**不超授权上限**（决策五第 5、6 项）；
- 上游须纳入授信风控主体（当前 `rating_configs` 只覆盖经销商，上游无评级）——至少需要上游准入状态与回购协议覆盖关系；
- **厂家回购义务必须覆盖「已付款但未交付/未售出」的车辆**（回购是现有第 ⑩ 环节，需扩口径）；
- 建议增加**付款前提车验收**（车辆在库核验后放款），把交付风险前移到付款之前。

> **注意**：`REGIONAL_AGENCY` / `WHOLESALER` 这类**中间层级**的回购能力通常弱于厂商本身，`AUCTION` 更是没有厂商回购——回购覆盖关系需**按 supplier_type 分别核实**，不能一刀切。

### 决策七：账户信息按敏感数据处理

| 要求 | 落地 |
|---|---|
| 存储 | 账号加密落库（AES-GCM，主密钥走环境变量/密钥管理，不入库） |
| 对外返回 | 只返回银行名 + 掩码（`****1234`）+ 户名；**不返回完整账号** |
| 日志/审计 | 请求体与审计表不落明文账号（`request-log.sensitive-fields` 白名单需补 `bankAccount`/`accountNo`/`payeeAccount`） |
| 导出/报表 | 脱敏；导出需二次授权并留痕 |
| 变更管控 | 双人复核 + 生效冷静期（T+1/T+2）；冷静期内的新放款仍走旧账户 |
| 冻结/注销 | 账户可置为 FROZEN/CLOSED，放款时拒绝付款并告警 |

**额外**：`SELF_PAY` 的经销商结算账户变更管控应**严于**上游账户（建议 T+2 + 资金岗 + 风控双签），因为它是唯一「钱可直接被经销商自主使用」的出口。

### 决策八：两条导入通道的安全边界

| 要求 | 落地 | 覆盖通道 |
|---|---|---|
| **账户只传引用码** | 模板与 API 契约中 `payeeAccountRef` 只填业务引用码，系统按引用查主数据；**两条通道都不接受明文账号** | API / Excel |
| **按通道分级的确认闸门** | API 走 `preview`→`commit` 的 `commit` 直落（可配置强制复核）；Excel 必须 `preview` → 人工核对 → `commit` | API / Excel |
| **原始文件留存** | 合同/発注書/請求書 的**原件**必须随主单留存；API 通道上游不供原件时，留存单据号 + 上游可追溯凭据并标注"无附件" | API / Excel |
| **模板固定** | 系统提供标准模板；**列头不符直接拒绝整个文件**，不逐行猜测 | Excel |
| **行级校验** | 每行独立校验，逐行报错（行号 + 字段 + 原因），可下载错误明细修正后重传 | Excel |
| **幂等双锚点** | `order_no` 唯一 + **VIN 幂等**（同一 VIN 不得出现在两个未结算订单中） | API / Excel |
| **留痕** | 导入动作写审计：操作人、通道、文件名、文件哈希、行数、成功/失败数 | API / Excel |

### 决策九：车辆状态的**双语义**必须显式映射

业务方的字段口径是「在途 / 在库 / 已质押 / 已解押」——这是**库存视角**（车在哪儿、担保解没解）。但代码里的领域枚举是另一套：

```
domain/model/VehicleStatus.java
FINANCED     已垫款：已付款，车辆尚未到货入库
IN_STOCK     在库：停在经销商场地作为担保物，开始计息
SOLD_PENDING 已售待还
SETTLED      已结清（终态）
OVERDUE      逾期
DISPOSING    处置中
```

**两套语义不是一一对应**——业务侧"已质押/已解押"在领域模型里不是状态而是**别的维度**：

| 业务侧字段值 | 领域状态映射 | 说明 |
|---|---|---|
| 在途 | `FINANCED` | 已付款未到货 |
| 在库 | `IN_STOCK` | 已到店、开始计息 |
| 已质押 | `IN_STOCK` + 担保标记 | **不是独立状态**，是"在库且已设押" |
| 已解押 | `SETTLED` 或 `SOLD_PENDING` | 取决于是否已还款结清 |

**决策**：导入层的 `vehicle_status` 字段**只接受业务侧口径**，在映射层转成领域枚举 + 担保标记；**禁止把业务侧字符串直接塞进领域枚举**。落地要求：

1. 映射表放在**领域层**（与 `VehicleStatus.canTransitTo` 同一处），不放在 web/application 层；
2. 导入时点的状态通常只有"在途"（车还没到）——"在库/已质押"是到店验收后的状态，导入模板里给这两个值时应给出提示但允许（经销商清单可能反映"已到店"的实况）；
3. **映射表必须有单元测试**——这是两套语义最容易错的地方，错了会静默污染台账状态。

### 决策十：原始凭证存 **Amazon S3**，应用只存元数据

原始凭证（合同·発注書·請求書·图片·PDF）存 **Amazon S3**；**数据库只存元数据，禁止 BLOB / Base64 存 PostgreSQL**（BLOB 撑爆库、备份膨胀、流式能力差）。

#### 10.1 为什么是 S3

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **本地磁盘** | 零依赖、最快 | 多实例部署要共享存储；**"不可删除"无法保证**；备份靠快照，RPO 粗；容器化部署天然易丢 | ✗ |
| **自建 MinIO** | S3 兼容、数据可不出境 | **多运维一个有状态组件**；要自己做 HA/备份/升级；本项目已在 WSL/Docker 踩过多个坑（容器网络沙箱丢失、WSL 自动关机致容器退出） | ✗ |
| **AWS S3** | 托管高可用；**Object Lock + Versioning 天然满足凭证 WORM**；按量计费；生命周期策略可自动转低频/归档；东京·大阪 region 满足日本境内驻留 | 引入 AWS SDK 依赖；需 IAM 与凭证管理；出境合规需评估 | ✓ **采纳** |

**关键理由不是"便宜好用"，而是「Object Lock」**：金融凭证的核心要求是**不可篡改、不可删除**。Object Lock 在**存储层**强制这一条，比在应用层写"禁止删除"的软约束可靠得多——运维误删、脚本清空、生命周期规则误配都删不掉。

#### 10.2 核心机制：预签名 URL 直传，应用不过流

```
❌ 应用代理上传：客户端 → 应用（multipart 解析，文件进 JVM 堆/临时目录）→ S3
   问题：大文件打满应用带宽；multipart 吃内存易 OOM；应用成瓶颈与故障点；重启丢临时文件

✅ 预签名 URL 直传：
   ① 客户端 → 应用：申请上传授权（orderNo、文件名、大小、类型）
   ② 应用 → 客户端：返回 S3 预签名 PUT URL（15 分钟时效）
   ③ 客户端 → S3：直接 PUT 文件（不经过应用）
   ④ 客户端 → 应用：提交完成（objectKey + etag）
   ⑤ 应用：回读 S3 元数据校验 → 落 attachment 记录
```

**必须补的校验**（否则会出现"上传了 A 却登记了 B"）：
- 预签名 URL **限单对象 key + Content-Type + Content-Length + 短时效**；
- 上传完成后**应用回读 S3 的对象元数据**（`ContentLength`/`ContentType`/`ETag`）与申请值比对，不一致则拒绝登记；
- **校验 ETag/MD5**（单次 PUT 的 ETag 即 MD5），防内容被替换。

#### 10.3 安全与合规

| 要求 | 落地 |
|---|---|
| **凭证不入库不入代码** | AWS 凭证走 **IAM Role / 环境变量**注入（与项目既有 `PAYMENT_WEBHOOK_SECRET` 同一纪律） |
| **不可篡改** | 凭证类附件启用 **Object Lock `COMPLIANCE`**；桶开启 **Versioning**（防误覆盖与恶意删除）；开启 **MFA Delete** |
| **加密** | 服务端加密 SSE-KMS（密钥轮换与吊销由 KMS 控）；传输走 HTTPS |
| **访问最小化** | 应用只持有特定 bucket 前缀的 `PutObject`/`GetObject`/`HeadObject` 权限；**禁止 `DeleteObject`** |
| **数据驻留** | 桶建在**东京或大阪 region**，满足日本境内驻留；跨境同步需评估合规 |
| **类型与大小白名单** | 只允许 PDF / JPEG / PNG / XLSX / CSV；单文件大小上限；**附件不落地为可执行文件** |
| **链接不外泄** | 访问附件一律**由应用签发短时效预签名 GET URL**，**不存永久公开 URL**，桶不公开读 |

#### 10.4 对象键与元数据

- `object_key` 用 **UUID/哈希**，**不用原始文件名**——文件名含客户名/车架号会泄露，且可能冲突；
- `original_filename` 仅展示用，不参与寻址；
- 存 `sha256` + `etag` 做**自证与防替换**；
- 凭证类附件**登记后不可删除**，只能追加新版本（"补充件"）。

## 3. 被否决的备选方案

**备选 A：Word 采购合同自动解析入库**
- 优点：无需经销商整理表格；
- 缺点：合同是散文，账户/金额/受取方在日文合同里格式极不固定；**解析错一个账户号就是资金打错地方**，代价不可逆；实务中"一笔采购一单多台车"的对应关系合同里往往不写明；
- 结论：**否决**。合同原件作附件留痕，关键要素走结构化字段。

**备选 A2：OCR + AI 解析通道**
- 优点：能吃扫描件与非结构化单据，无需经销商整理表格；
- 缺点：需置信度模型 + 候选人工确认界面 + 多格式解析管线，投入产出比最低；**它要防的风险（账户号识别错误）在"账户只传引用码"后已被消灭**——账号根本不从文件里读，就不存在"识错账号"这件事；
- 结论：**否决**。

**备选 A3：经销商门户上传 PDF/图片作为独立通道**
- 优点：贴近"经销商自助上传"形态；
- 缺点：需 multipart 上传 + 解析管线 + 候选确认界面；且上传的 PDF 最终仍只是**附件**，而附件留存能力在 Excel 通道已具备（决策四 4.5）；
- 结论：**否决**。附件留存作为主单必备属性存在，不作第三条通道。

**备选 B：共管／监管账户（不直付上游）**
- 做法：金融公司先把款付入上游在金融公司开立的专项账户，车辆交付验收后再划转；
- 优点：彻底消除「付了款上游不发货」的资金敞口；
- 缺点：上游现金流被占用（通常不接受）、协调与对账成本高、交付环节易拖延；
- 结论：不作默认模式，对**高风险上游**保留为可选风控开关（`directPayMode: DIRECT / ESCROW`）。

**备选 C：维持现状（自由文本 supplierName + 放款不带收款方）**
- 优点：零改动；
- 缺点：直付上游无法落地；付款指令无收款方；账户不可管、不可审、不可冻结；场景 C 无账户可存；
- 结论：**不可接受**，属必须关闭的能力缺口。

**备选 D：文件存本地磁盘或自建 MinIO**
- 缺点：**「凭证不可篡改」无法在存储层保证**；自建 MinIO 引入有状态常驻组件，是运维负债；
- 结论：**否决**。选 S3，用 Object Lock + Versioning 换存储层的强不可变保证。

**备选 E：文件走应用代理上传**
- 缺点：文件流经 JVM 堆与临时目录——打满带宽、吃内存易 OOM、应用成吞吐瓶颈与故障点、重启丢临时文件；
- 结论：**否决**。改用预签名 URL 直传（决策十 10.2）。

## 4. 后果（Consequences）

**变容易的**
- 打款对象不再靠系统规则猜，而是**跟着真实采购单走**——与实际资金流一致；
- 一单多车天然承载（订单 1:N 车辆），Excel 逐台导入与台账口径对齐；
- 审计可完整回答"这笔垫款付给了谁、当时账户是什么、这笔钱是代付还是营运资金"；
- 上游回购、上游评级有了数据基础（按 supplier_type 分别核实）；
- **导入侧不需要** OCR/AI 解析、置信度模型、候选人工确认界面、多格式附件解析管线——落地面从"做通用导入框架"收缩为"**一个 Excel 模板解析器 + 一个 API 契约**"；
- **最危险的风险源被消灭**：AI 误识账户号会导致资金打错地方；账户只传引用码后，账号根本不从文件里读，"识错账号"不再可能；
- 两条通道的**校验逻辑可共用同一套字段规则**，只有"是否需要人工确认"一个分支。

**变 harder 的**
- 新增 5 张表：`purchase_orders`、`suppliers`、`supplier_bank_accounts`、`dealer_bank_accounts`、`attachments`；车辆与垫款各加外键与快照列；
- `batch-ingest` 与新增的 `purchase-orders/import` 需协同（建账时挂订单号，或先建订单再建账）；
- `PaymentGateway.pay(...)` 签名必须改为携带收款方的指令对象（**接缝变更**，所有实现类同步改）；
- **放款校验必须分叉成两套**（`DIRECT_PAY` / `SELF_PAY`），不能共用一套断言；
- 引入 POI 依赖 + AWS SDK v2 + Excel 模板 + 行级错误明细 + S3 桶配置；
- 敏感数据处理带来额外的加解密与脱敏工作量；
- **车辆状态存在两套语义**，必须做显式映射（决策九）。

**不可逆的**
- `payee_account_snapshot` 一旦写入即为历史事实，不可修改（与审计链一致性要求一致）；
- Object Lock `COMPLIANCE` 模式下的对象**到期前不可删改**——这正是金融凭证想要的效果。

10. **对象存储与附件留存**：
    - 新增 `attachments` 表 + `purchase_orders.evidence_attachment_id`；
    - S3 桶：东京/大阪 region + **Versioning** + **Object Lock（COMPLIANCE）** + SSE-KMS + **MFA Delete**；桶**不公开读**；
    - `AttachmentStorage` 接口 + `S3AttachmentStorage` 实现（AWS SDK v2）；密钥走 IAM Role / 环境变量注入，**不入库不入代码**；
    - **预签名 URL 直传**：`POST /api/attachments/presign` → 客户端直传 S3 → `POST /api/attachments/complete`（回读 S3 元数据校验大小/类型/ETag → 落库）；
    - 附件访问一律由应用签发**短时效预签名 GET URL**，库里不存永久公开链接；
    - 凭证类附件**登记后不可删除**（只能追加新版本）。
11. 账户变更：双人复核 + 冷静期（`SELF_PAY` 账户更严）；敏感字段加解密 + 掩码返回 + 日志脱敏。
12. **车辆状态双语义映射**（决策九）：业务侧口径 ↔ 领域 `VehicleStatus` 枚举，**显式映射表 + 单元测试**。

### P2：风控与对账
13. 上游纳入评级与准入；厂家回购协议覆盖"已付款未交付"车辆，**按 supplier_type 分别核实覆盖能力**。
14. 付款前提车验收作为 `DIRECT_PAY` 放款前置可选开关。
15. 三方流水对账（金融公司→上游付款、上游→交付、经销商→金融公司还款）。

## 7. 待确认事项（需业务/客户拍板）

1. **一单几台车**：现实里采购单与车辆是 1:1 还是 1:N？——决定订单与台账的关联粒度与 Excel 模板的列结构。
2. **API 直连优先对接谁**：厂商销售公司 / 区域总代理 / 拍卖平台 / 经销商 DMS——决定对接顺序与商务谈判优先级。
3. **`SELF_PAY`（场景 C）本期是否要做**：若一期只做代付上游，可先不建 `dealer_bank_accounts`，但要**在数据模型里留位**（否则后期迁移成本高）。
4. **上游评级与经销商评级是否共用 `rating_configs` 口径**？还是独立一套？
5. **账户录入方式**：上游自助维护，还是金融公司代录？——决定权限模型与审核流。
6. **账户变更冷静期**：T+1 还是 T+2？`SELF_PAY` 账户是否要更严？
7. **代付协议凭证形态**：电子签平台对接，还是上传扫描件 + 编号？
8. **直接付 vs 共管**：默认全量直付，还是按上游风险/担保能力区分直付/共管（备选 B）？
9. **Excel 通道的提交主体**：经销商自己上传，还是金融公司运营人员代录？——决定权限模型（自助 vs 内部代录）与账号体系。
10. **车辆状态双语义映射口径**（决策九）：业务侧"在途/在库/已质押/已解押"与领域枚举如何对应？尤其"已质押/已解押"在导入时刻通常尚未发生——**导入时点车辆多处于在途**。
11. **S3 区域与合规**（决策十）：桶建在**东京还是大阪**？是否需要跨境灾备？
12. **S3 账号与凭证形态**：走 IAM Role（推荐，部署环境自动注入）还是静态 AccessKey（环境变量）？
13. **附件保留期限与生命周期策略**：Object Lock 合规模式下保留期设为多久（金融凭证通常 5~10 年）？是否用 S3 Lifecycle 自动转低频/归档控成本？

## 9. 决策演进对照（历史痕迹，供评审参考）

| # | 早期结论 | 最终结论 | 变更原因 |
|---|---|---|---|
| 1 | 上游＝厂家单一实体，`suppliers` 即厂家表 | 上游是**多层渠道**，`supplier_type` 6 值枚举 | 日本经销商不直接向工厂下单（销售公司/总代理/批发/拍卖） |
| 2 | 全场景直付上游 | **三场景分岔**：A/B 代付上游、C 回款经销商 | 场景 C 是库存抵押营运资金，不是代付 |
| 3 | 代付协议是**全局**放款硬校验 | 代付协议**仅 `DIRECT_PAY` 适用**（决策六），`SELF_PAY` 不需要 | 全局硬校验会把场景 C 业务直接堵死 |
| 4 | 账户挂在供应商，车辆引用 | 账户挂在**采购订单**，车辆挂订单 | 融资申请需关联采购订单（凭证锚点）；一单多车 |
| 5 | 一套放款校验 | **两套校验链**（`DIRECT_PAY` 11 项 / `SELF_PAY` 11 项） | 场景 C 需「库存在库 + 估值口径 + 独立抵押率」 |
| 6 | 未考虑经销商自身账户 | 新增 `dealer_bank_accounts` | 场景 C 的钱打给经销商自己，`dealers` 表原本无账户列 |
| 7 | 五通道并存（API/门户PDF/Excel/人工/OCR+AI），按成熟度演进 | **两条通道**：API 直连 + Excel/CSV 批量导入 | 业务方拍板。砍掉的三条要么需重投入（OCR 置信度 + 候选确认界面），要么与 Excel 重复（门户上传、人工单条） |
| 8 | Excel 是"过渡期方案"，API 成熟后取代 | **两条按对手方能力分层、长期并存** | API 面向主机厂/总代理/拍卖平台/DMS；Excel 面向长尾中小经销商 + 零星补录，永不废弃 |
| 9 | 附件留存与导入通道混在一起讨论 | **正交拆解**：导入＝数据怎么进，凭证留存＝文件怎么存。附件是主单必备属性，**不需第三条通道** | 门户上传通道存在的唯一理由是存附件，而附件能力可在 Excel 通道内实现 |
| 10 | 上游统一要求回购 | **按 supplier_type 分别核实**回购覆盖能力 | 中间层级/拍卖行普遍无厂商回购 |
| 11 | 未要求原件留存 | **原始文件必须留存**，不能只存解析结果 | 只存解析结果无法自证 |
| 12 | 安全边界 9 项 × 5 通道 | **7 项 × 2 通道**，并新增 **VIN 幂等** | 砍掉 OCR 后"AI 误识账户号"风险源消失；`order_no` 唯一防不住两单报同一台车 |
| 13 | 车辆状态未涉及双语义 | **新增决策九**：业务侧口径 ↔ 领域 `VehicleStatus` 须显式映射 | 核对代码发现领域枚举是 `FINANCED/IN_STOCK/SOLD_PENDING/...`，与业务侧"在途/在库/已质押/已解押"不是同一套语义 |
| 14 | 附件留存只说"必须留存"，未指定存储 | **新增决策十**：文件存 **Amazon S3**（东京/大阪 + Versioning + Object Lock COMPLIANCE + SSE-KMS + MFA Delete）；**预签名 URL 直传、应用不过流**；库只存元数据，禁 BLOB；新增通用 `attachments` 表 | 金融凭证要求"一次写入、不可删改"，存储层强制强于应用层软约束；系统当前零文件存储能力，此处必须定选型 |

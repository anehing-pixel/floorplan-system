## gateway 网关（已完成：骨架 + 路由 + 透传，鉴权暂留下游）
- 父 pom modules 加 gateway（在 web 后）。新模块 gateway/{pom, GatewayApplication, RequestIdFilter, application.yml}，端口 18080（避开 web 8080）。
- 依赖：spring-cloud-starter-gateway + nacos-discovery + spring-cloud-starter-loadbalancer（lb:// 必需）。WebFlux 栈，独立应用，与下游 MVC 不冲突。显式 repackage。
- **职责边界**：本阶段网关只做路由 + 请求头透传，不做 JWT 验签。鉴权留各下游服务自带的 common JwtAuthInterceptor（零信任，服务脱离网关也不裸奔）。网关不依赖 jjwt/application，很轻量。等全部端点迁移+鉴权定型后再把验签上收到网关。
- RequestIdFilter：GlobalFilter + Ordered(HIGHEST_PRECEDENCE)，无 X-Request-Id 则生成 UUID，mutate 写回下游请求头；ApiResponse.traceId/审计链依赖它。
- **路由配置要点**：specific 在前（Gateway 首个匹配即命中）——
  /api/vehicles/*/lien-check → risk 必须先于 /api/vehicles/** → core；
  /api/jobs/bank-fetch → bank 必须先于 /api/jobs/** → core。
  分流：/api/auth/**→auth；/api/dealers|credit-lines|rating-configs|annual-reviews/**→credit；
  /api/inventory|alerts|disposals|collateral/**→risk；其余 /api/** →core(web 兜底，核心账务全留 web)。
- **URI 双模**：`${ROUTE_AUTH:lb://auth-service}` 等占位符——生产默认 lb:// 走 Nacos；本地验证传 `--ROUTE_AUTH=http://127.0.0.1:端口` 覆盖，不依赖 Nacos。
- **踩坑1（重要）：NoSuchMethodError HttpHeaders.headerSet()**。Gateway 4.1.6 用到 headerSet()，
  Boot 3.2.5 默认的 Spring Framework 6.1.6 没有该方法。官方 release notes（Cloud 2023.0.4）明示：
  需 Spring Framework 6.1.15+（Boot 3.2.12+/3.3.6+）。修法：父 pom dependencyManagement 里
  **在 boot-dependencies 之前** import `spring-framework-bom:6.1.15`（Maven BOM 取先声明者）。
  已验证 dependency:tree spring-web/core=6.1.15，网关恢复正常。
- **踩坑2**：Nacos discovery 本地启动报端口占用（Nacos 客户端临时端口）。
  `--spring.cloud.nacos.discovery.enabled=false` 无效，要用总开关 `--spring.cloud.discovery.enabled=false` 才彻底。
- **验证方法**：用 5 个 Python HTTPServer 回显 SERVICE_PORT 当下游，网关配 http 指向它们，发请求看返回端口。
  10 条路径全部命中正确目标（含两个 specificity）；X-Request-Id 双模式（生成/透传）通过。
  比看 401 响应体可靠（各服务响应无区分度）。已清理测试进程。
- **web 旧 Controller 摘除：评估后决定暂缓**（关键判断）：
  smoke-test.py 全打 `http://localhost:8080`（web 单体），摘掉 web 旧 Controller 会让 18 组冒烟测试立即失败；
  且 DB 未起（5434 不可连）无法端到端验证。当前 web(8080) 与网关(18080) 是独立端口，重复端点不冲突。
  正确时机：DB 起来 + 冒烟测试目标切到网关 18080 + 全绿后再摘。届时整段迁出的整段删（Auth/CreditLine/Dealer/RatingConfig/AnnualReview/Risk/Disposal/Collateral），

  1) `gateway/application.yml` 新增 `console-static` 路由：`Path=/,/index.html,/login.html,/css/**,/js/**` → `ROUTE_CORE`(floorplan-core)，置于精确路由之前；新增 `globalcors.cors-configurations['/**']`（allowedOriginPatterns:* / GET,POST,PUT,DELETE,OPTIONS / allowedHeaders:*）。
  2) `static/js/common.js` 与 `static/login.html` 的 `API_BASE`：`location.port==='18080' ? '' : 'http://127.0.0.1:18080'`（原 8080）。`FP.api.base` 复用同一值，upload 一并跟走网关。
  3) login.html 错误提示文案改为网关地址与启动命令。
- 验证：编译通过；网关 18080 访问 login.html/index.html/js/common.js 均 200；登录走网关切到 auth-service 返回完整 token；跨源 OPTIONS/GET 均返回 Access-Control-Allow-Origin。**正确页面入口：`http://127.0.0.1:18080/login.html`**（不再是 8080）。
- 结论：从 8080 打开页面已失效（Controller 摘除），必须走网关 18080。

## run-microservices.sh 加固（端口竞态）
- 事故：用户在自己终端 start，恰逢 AI 收尾上一轮 TaskStop 保活任务，`&` 起的 java 成孤儿占着 8081，双方共用同一 pid 文件互相覆盖 → auth 报 "Port 8081 already in use"，脚本 exit 1 不留清理，留下半套进程。
- 沙箱限制：工具调用结束后会回收它派生的后台进程（连 Start-Process 起的也回收）；`run-microservices.sh start` 用 `&`，在本沙箱里无法常驻。用户在自己终端跑则可常驻（终端不关）。
- 脚本改动：① 新增 `port_in_use()`，do_start 开头预检 8080-8084/18080，被占则明确报错返回；② 所有 `wait_one ... || exit 1` 改为 `|| { do_stop; exit 1; }`，失败时清理已拉起进程。bash -n 通过。
- 排错口诀：遇到 "Port already in use" 先看 netstat 找 OwningProcess，别盲目 kill；多半是上一次残留或并发 start。

## start 前台保活修复（关键）
- 根因：用户自己终端 `bash run-microservices.sh start` 后显示"全部就绪"、回到提示符，服务随即全关。原来 `start)` 分支只是 `do_start` 就 `;;` 退出；Git Bash(Windows) 下 `&` 起的后台 java 会随父 shell 退出被回收。**不是脚本显式 stop**。
- 修复：`start)` 改为 `do_start || exit 1` → 打印保活提示 → `trap 'echo; do_stop; exit 0' INT TERM` → `wait` 阻塞。Ctrl+C 时先清理再退出，不留孤儿。用法注释同步说明。
- 验证：后台任务跑 start 后停在 wait 不退出；从独立命令访问 login.html=200、登录拿 token、 dealers 跨服务返回真实数据；TaskStop 后 6 端口全释放。
- 关键认知：**本地演示必须用保活任务或在同一条命令内启动+访问**；单纯 `start` 返回即死。用户在自己终端跑新版 start，终端保持开着即可持续访问，Ctrl+C 停止。
